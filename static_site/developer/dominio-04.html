Amazon CloudWatch

Serviço de monitoramento e observabilidade — métricas, logs, alarmes e dashboards.

Metrics e Custom Metrics

Métricas PadrãoBuilt-in
EC2 (a cada 5 min, detailed: 1 min):
• CPUUtilization, NetworkIn/Out
• DiskReadOps, DiskWriteOps
• StatusCheckFailed
⚠️ NÃO inclui: memória, disco (precisa agent)

Lambda:
• Invocations, Duration, Errors
• Throttles, ConcurrentExecutions
• IteratorAge (streams)

API Gateway:
• Count, Latency, IntegrationLatency
• 4XXError, 5XXError, CacheHitCount

DynamoDB:
• ConsumedReadCapacityUnits
• ConsumedWriteCapacityUnits
• ThrottledRequests
• SystemErrors
Custom MetricsPutMetricData
• Enviar métricas customizadas via API
• PutMetricData API
• Resolução: Standard (60s) ou High (1s)
• Dimensões: até 30 por métrica
• Namespace customizado

import boto3
cw = boto3.client('cloudwatch')
cw.put_metric_data(
    Namespace='MyApp',
    MetricData=[{
        'MetricName': 'OrdersProcessed',
        'Value': 42,
        'Unit': 'Count',
        'Dimensions': [{
            'Name': 'Environment',
            'Value': 'prod'
        }]
    }]
)

Embedded Metric Format (EMF):
• Métricas dentro de logs estruturados
• Automaticamente extraídas como métricas
• Sem chamada PutMetricData separada
• Ideal para Lambda (custo menor)

CloudWatch Logs

Logs StructureOrganização
Hierarquia:
• Log Group: /aws/lambda/my-function
  └── Log Stream: 2024/01/15/[$LATEST]abc123
      └── Log Events: timestamp + message

Retention: 1 dia a 10 anos (ou never expire)
Encryption: KMS opcional

Fontes comuns:
• Lambda (automático)
• ECS (awslogs driver)
• EC2 (CloudWatch Agent)
• API Gateway (access/execution logs)
• VPC Flow Logs
• Route 53 DNS queries

Export:
• S3 (batch, até 12h delay)
• Kinesis Data Firehose (near real-time)
• Subscription Filters → Lambda, Kinesis, Firehose
Logs InsightsQuery
• Query language para análise de logs
• Busca em múltiplos log groups
• Visualizações (bar, line, stacked)

Exemplos de queries:
# Top 20 erros
fields @timestamp, @message
| filter @message like /ERROR/
| sort @timestamp desc
| limit 20

# Latência média por endpoint
filter @type = "REPORT"
| stats avg(@duration) as avgDuration
  by bin(5m)

# Requests por status code
fields @timestamp
| filter ispresent(status)
| stats count(*) by status

Campos automáticos:
• @timestamp, @message, @logStream
• @log (log group)
• Lambda: @duration, @billedDuration,
  @memorySize, @maxMemoryUsed

Alarms e Dashboards

CloudWatch AlarmsAlertas
Estados:
• OK: métrica dentro do threshold
• ALARM: métrica excedeu threshold
• INSUFFICIENT_DATA: dados insuficientes

Configuração:
• Metric + Statistic (Average, Sum, Max, p99)
• Period: 10s, 30s, 60s, ou múltiplos de 60s
• Evaluation Periods: quantos períodos avaliar
• Datapoints to Alarm: quantos devem violar

Actions:
• SNS notification (email, SMS, Lambda)
• Auto Scaling action (scale out/in)
• EC2 action (stop, terminate, reboot)
• Systems Manager action

Composite Alarms:
• Combina múltiplos alarms (AND/OR)
• Reduz alarm noise
• Ex: CPU HIGH AND Memory HIGH
DashboardsVisualização
• Visualização customizada de métricas
• Cross-account e cross-region
• Auto-refresh (10s, 1m, 5m, 15m, 1h)
• Widgets: line, stacked area, number, gauge, text

Custo:
• 3 dashboards gratuitos (até 50 métricas)
• $3/dashboard/mês adicional

Boas práticas:
• Dashboard por serviço/aplicação
• Incluir métricas de negócio
• Alarmes visíveis no dashboard
• Annotations para eventos importantes

🎯 Para o exame: EC2 não monitora memória/disco nativamente (precisa CloudWatch Agent). EMF para métricas em Lambda (custo menor). Logs Insights para queries ad-hoc. Subscription Filters para streaming de logs. Composite Alarms para reduzir noise.

AWS X-Ray

Distributed tracing para análise e debug de aplicações distribuídas e microservices.

Conceitos Fundamentais

Tracing ComponentsEstrutura
Trace:
• Representa uma request end-to-end
• Composto por múltiplos segments
• Trace ID: identificador único

Segment:
• Representa um serviço/recurso
• Contém: nome, ID, start/end time
• Status: OK, error, fault, throttle

Subsegment:
• Detalhe dentro de um segment
• Chamadas a AWS services, HTTP, SQL
• Permite granularidade fina
• Pode ser remoto (downstream service)

Service Map:
• Visualização gráfica dos serviços
• Mostra latência e erros entre serviços
• Identifica gargalos automaticamente
Annotations & MetadataDados
Annotations:
• Key-value pairs INDEXADOS
• Podem ser usados para filtrar traces
• Tipos: string, number, boolean
• Ideal para: user_id, order_id, environment

xray_recorder.put_annotation('user_id', '12345')
xray_recorder.put_annotation('payment', 'credit')

Metadata:
• Key-value pairs NÃO indexados
• Qualquer tipo de dado (objetos, arrays)
• Não podem ser usados para filtrar
• Ideal para: request body, response, debug info

xray_recorder.put_metadata('response', data)

⚠️ Annotations = filtráveis (busca)
⚠️ Metadata = apenas visualização (debug)
Sampling RulesCusto
• Controla quantas requests são traced
• Reduz custo e overhead

Regra padrão:
• Reservoir: 1 request/segundo (garantido)
• Rate: 5% das requests adicionais

Custom rules:
• Por service name, HTTP method, URL path
• Prioridade (menor número = maior prioridade)
• Pode ter reservoir e rate diferentes

Exemplo:
• /health: 0 reservoir, 0% rate (não traçar)
• /api/payments: 10 reservoir, 100% rate
• Default: 1 reservoir, 5% rate

⚠️ Sampling reduz custo mas pode perder traces
⚠️ Aumentar sampling para debugging

Integração com Serviços

Lambda + X-RayServerless
Habilitar:
• Active tracing na configuração da função
• Ou via SAM: Tracing: Active

Permissões necessárias:
• AWSXRayDaemonWriteAccess na execution role

Variáveis de ambiente (automáticas):
• _X_AMZN_TRACE_ID: trace header
• AWS_XRAY_DAEMON_ADDRESS: daemon endpoint

SDK:
from aws_xray_sdk.core import patch_all
patch_all()  # instrumenta boto3, requests, etc.

⚠️ Lambda cria segment automaticamente
⚠️ Você adiciona subsegments para detalhes
EC2 / ECS + X-RayDaemon
EC2:
• Instalar X-Ray Daemon (UDP port 2000)
• Daemon envia traces para X-Ray API
• IAM role com permissões de X-Ray

ECS:
• X-Ray daemon como sidecar container
• Ou como daemon service (1 por host)
• Task role com permissões de X-Ray

Fargate:
• Sidecar container obrigatório
• Não tem acesso ao host

API Gateway:
• Habilitar X-Ray tracing no stage
• Cria segment para cada request
• Mostra latência de integração

⚠️ Daemon coleta e envia em batch
⚠️ Sidecar pattern para containers

🎯 Para o exame: Annotations são indexadas (filtráveis). Metadata não são indexadas. Sampling controla custo. Lambda: Active Tracing + execution role. ECS: sidecar container. Service Map mostra gargalos visualmente.

AWS CloudTrail

Auditoria e governança — registra todas as chamadas de API feitas na conta AWS.

Tipos de EventosAuditoria
Management Events (padrão):
• Operações de gerenciamento de recursos
• CreateBucket, RunInstances, CreateUser
• Sempre habilitado (90 dias gratuito)
• Read events + Write events

Data Events (custo adicional):
• Operações nos dados dos recursos
• S3: GetObject, PutObject, DeleteObject
• Lambda: Invoke
• DynamoDB: GetItem, PutItem
• Alto volume → custo significativo

CloudTrail Insights:
• Detecta atividade incomum automaticamente
• Baseline de uso normal
• Alerta quando há desvio
• Ex: pico de API calls, erros incomuns
ConfiguraçãoTrail
Trail:
• Entrega logs para S3 bucket
• Pode enviar para CloudWatch Logs
• Multi-region trail (recomendado)
• Organization trail (todas as contas)

Log File:
• JSON com detalhes da API call
• eventTime, eventSource, eventName
• userIdentity (quem fez)
• sourceIPAddress
• requestParameters
• responseElements

Integridade:
• Log file validation (digest files)
• Detecta se logs foram alterados/deletados
• S3 Object Lock para imutabilidade

⚠️ CloudTrail = quem fez o quê e quando
⚠️ CloudWatch = métricas e performance
⚠️ X-Ray = tracing de requests distribuídas

🎯 Para o exame: CloudTrail = auditoria de API calls (quem, quando, o quê). Management events gratuitos (90 dias). Data events têm custo adicional. Insights detecta anomalias. Diferente de CloudWatch (performance) e X-Ray (tracing).

Estratégias de Caching

Diferentes camadas de cache para melhorar performance e reduzir custos.

ElastiCache: Redis vs Memcached

CaracterísticaRedisMemcached
Estruturas de dadosStrings, Lists, Sets, Hashes, Sorted Sets, StreamsApenas strings (key-value simples)
PersistênciaSim (RDB snapshots, AOF)Não (apenas memória)
ReplicaçãoSim (read replicas, Multi-AZ)Não
Cluster ModeSim (sharding automático)Sim (multi-node)
Pub/SubSimNão
Backup/RestoreSimNão
Multi-threadedNão (single-threaded)Sim
Caso de usoSessions, leaderboards, real-time analytics, queuesCache simples, objetos grandes, multi-threaded

Caching Patterns

Lazy Loading (Cache-Aside)Read
Fluxo:
1. App verifica cache
2. Cache hit → retorna dados
3. Cache miss → busca no DB
4. Armazena no cache
5. Retorna dados

Vantagens:
• Apenas dados requisitados são cacheados
• Node failure não é fatal (busca do DB)
• Cache se preenche naturalmente

Desvantagens:
• Cache miss = 3 round trips (penalty)
• Dados podem ficar stale (desatualizados)
• Cold start: cache vazio inicialmente
Write-ThroughWrite
Fluxo:
1. App escreve no cache E no DB
2. Cache sempre atualizado
3. Reads sempre do cache (fresh data)

Vantagens:
• Dados nunca stale no cache
• Sem cache miss penalty (dados já estão lá)

Desvantagens:
• Write penalty (2 writes por operação)
• Dados no cache podem nunca ser lidos
• Node failure = dados perdidos até re-write

Combinação ideal:
• Write-Through + Lazy Loading
• TTL para expirar dados não acessados

Outras Camadas de Cache

DAXDynamoDB
• Cache in-memory para DynamoDB
• Latência de microssegundos
• API compatível com DynamoDB
• Write-through (automático)
• Item cache + Query cache
• Ideal para: read-heavy, hot partitions
• Não suporta strongly consistent reads
API Gateway CacheAPI
• Cache de responses no API Gateway
• Apenas REST API (não HTTP API)
• TTL: 0-3600s (padrão: 300s)
• Tamanho: 0.5 GB a 237 GB
• Por stage, pode ser por method
• Invalidar: Cache-Control: max-age=0
• Custo por hora (não por request)
CloudFrontCDN
• Cache na edge (global)
• TTL controlado por headers:
  - Cache-Control: max-age
  - Expires
• Invalidation: criar invalidation request
• Behaviors: cache por path pattern
• Origin Shield: camada extra de cache
• Ideal para: conteúdo estático, APIs globais

🎯 Para o exame: Redis = mais recursos (persistência, replicação, pub/sub). Memcached = simples, multi-threaded. Lazy Loading = cache miss penalty. Write-Through = dados sempre fresh. DAX = DynamoDB cache (microssegundos).

Lambda Optimization

Técnicas para otimizar performance, custo e cold starts em funções Lambda.

Memory & PerformanceTuning
Memória (128 MB - 10.240 MB):
• CPU é proporcional à memória
• Mais memória = mais CPU = execução mais rápida
• Pode ser mais barato com mais memória
  (executa mais rápido, cobra menos tempo)

AWS Lambda Power Tuning:
• Ferramenta open-source (Step Functions)
• Testa função com diferentes memórias
• Encontra melhor custo-benefício
• Gráfico de custo vs duração

Boas práticas:
• Minimizar tamanho do pacote de deploy
• Usar layers para dependências compartilhadas
• Reutilizar conexões (keep-alive)
• Processar em batch quando possível
Cold StartsLatência
Cold Start = primeira invocação (ou após inatividade):
1. Download do código
2. Inicializar runtime
3. Executar código de inicialização (fora do handler)
4. Executar handler

Fatores que aumentam cold start:
• Pacote grande (mais download)
• VPC (ENI attachment: +1-2s)
• Runtime pesado (Java > Python > Node)
• Muitas dependências

Soluções:
• Provisioned Concurrency (elimina cold start)
• Manter funções "warm" (ping periódico)
• Reduzir tamanho do pacote
• Inicializar SDK fora do handler
• Usar SnapStart (Java only)
• Evitar VPC se não necessário
Best PracticesCódigo
# FORA do handler (reutilizado entre invocações)
import boto3
dynamodb = boto3.resource('dynamodb')
table = dynamodb.Table(os.environ['TABLE_NAME'])

def handler(event, context):
    # DENTRO do handler (executado a cada invocação)
    item = table.get_item(Key={'id': event['id']})
    return item

Boas práticas:
• Conexões DB/SDK FORA do handler
• Variáveis de ambiente para config
• /tmp para cache de arquivos (512 MB - 10 GB)
• Idempotência (mesma request = mesmo resultado)
• Timeout < 30s para APIs (API Gateway limit)
• Usar X-Ray para identificar gargalos
• Async para operações não-críticas

🎯 Para o exame: Inicializar SDK/conexões FORA do handler. Provisioned Concurrency elimina cold starts. Mais memória = mais CPU. SnapStart para Java. VPC aumenta cold start. Lambda Power Tuning para encontrar memória ideal.

DynamoDB Optimization

Técnicas avançadas de design de tabelas e otimização de performance.

Partition Key DesignDistribuição
Boa partition key:
• Alta cardinalidade (muitos valores únicos)
• Distribuição uniforme de requests
• Evitar "hot partitions"

Exemplos bons:
• user_id (milhões de valores)
• order_id (UUID)
• device_id + timestamp

Exemplos ruins:
• status ("active"/"inactive" — 2 valores)
• date (todos acessam "hoje")
• country (poucos valores, distribuição desigual)

Capacidade por partição:
• 3000 RCU + 1000 WCU por partição
• Hot partition = throttling mesmo com capacidade sobrando
Write ShardingAnti-pattern
Problema: hot partition (muitos writes na mesma PK)

Solução: Write Sharding
• Adicionar sufixo aleatório à partition key
• Distribui writes entre múltiplas partições

Exemplo:
• Original PK: "2024-01-15" (hot!)
• Sharded PK: "2024-01-15_0", "2024-01-15_1", ..., "2024-01-15_9"
• 10x mais throughput

Trade-off:
• Reads precisam fazer Scatter-Gather
  (query em todas as shards e agregar)
• Mais complexidade no código
• Ideal para: write-heavy com PK previsível
GSI OverloadingSingle Table
Single Table Design:
• Múltiplas entidades na mesma tabela
• GSI com atributos genéricos (SK, GSI1PK, GSI1SK)
• Reduz número de tabelas e queries

Exemplo:
PK          | SK           | GSI1PK      | GSI1SK
USER#123    | PROFILE      | EMAIL#a@b   | USER#123
USER#123    | ORDER#001    | STATUS#open | 2024-01-15
USER#123    | ORDER#002    | STATUS#done | 2024-01-14
ORG#abc     | MEMBER#123   | USER#123    | ORG#abc

Access patterns:
• Get user profile: PK=USER#123, SK=PROFILE
• Get user orders: PK=USER#123, SK begins_with ORDER#
• Get orders by status: GSI1PK=STATUS#open
• Get user's orgs: GSI1PK=USER#123, GSI1SK begins_with ORG#

⚠️ Complexo mas muito eficiente
⚠️ Planeje access patterns ANTES de criar a tabela

🎯 Para o exame: Alta cardinalidade na partition key evita hot partitions. Write Sharding para distribuir writes. GSI Overloading para single-table design. Planejar access patterns antes de criar a tabela. DAX para hot keys de leitura.
