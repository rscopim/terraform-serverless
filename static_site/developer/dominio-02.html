AWS IAM (Identity and Access Management)

Controle de acesso granular para recursos AWS. Fundamento de segurança para todo o ecossistema.

Tipos de Policy

TipoOnde é AnexadaGerenciamentoCaso de Uso
AWS ManagedUsers, Groups, RolesAWS mantémPermissões comuns (ReadOnlyAccess, AdminAccess)
Customer ManagedUsers, Groups, RolesVocê mantémPermissões customizadas da organização
InlineDiretamente no principalVocê mantémRelação 1:1 estrita (não reutilizável)
Resource-basedNo recurso (S3, SQS, Lambda)Você mantémCross-account access, acesso direto ao recurso
Permission BoundaryUsers, RolesVocê mantémLimitar permissões máximas (delegação segura)
SCP (Service Control Policy)AWS Organizations (OU/Account)Org adminGuardrails para toda a organização

Policy Evaluation Logic

Evaluation OrderDecisão
1. Explicit Deny → DENY (sempre vence)
2. SCP → se não permite, DENY
3. Resource-based policy → se permite, ALLOW
4. Permission Boundary → se não permite, DENY
5. Session Policy → se não permite, DENY
6. Identity-based policy → se permite, ALLOW
7. Implicit Deny (padrão)

Regra de ouro:
• Deny SEMPRE vence Allow
• Sem permissão explícita = Deny implícito
• Resource-based pode conceder cross-account
Policy StructureJSON
{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "AllowS3Read",
    "Effect": "Allow",
    "Action": [
      "s3:GetObject",
      "s3:ListBucket"
    ],
    "Resource": [
      "arn:aws:s3:::my-bucket",
      "arn:aws:s3:::my-bucket/*"
    ],
    "Condition": {
      "StringEquals": {
        "aws:RequestedRegion": "us-east-1"
      }
    }
  }]
}

IAM Roles, STS e Cross-Account

IAM RolesAssume Role
• Credenciais temporárias (não permanentes)
• Trust Policy: quem pode assumir a role
• Permission Policy: o que a role pode fazer
• Duração: 1h a 12h (padrão: 1h)

Casos de uso:
• EC2 Instance Profile
• Lambda Execution Role
• Cross-account access
• Federation (SAML, OIDC)
• Service-linked roles
AWS STSTokens
Security Token Service — credenciais temporárias:

• AssumeRole: assume role na mesma ou outra conta
• AssumeRoleWithSAML: federation com SAML
• AssumeRoleWithWebIdentity: federation com OIDC
  (Cognito Identity Pool é preferido)
• GetSessionToken: MFA para usuário IAM
• GetCallerIdentity: "quem sou eu?"

Retorna:
• AccessKeyId
• SecretAccessKey
• SessionToken (obrigatório nas chamadas)
• Expiration
Cross-Account AccessMulti-conta
Opção 1: Resource-based Policy
• Adicionar conta B na policy do recurso
• Não precisa assumir role
• Principal mantém suas permissões originais

Opção 2: AssumeRole (recomendado)
1. Conta A cria role com trust policy para conta B
2. Conta B assume a role via STS
3. Recebe credenciais temporárias da conta A

⚠️ Resource-based: não perde permissões originais
⚠️ AssumeRole: assume APENAS as permissões da role
Permission BoundariesLimite
• Define o MÁXIMO de permissões que um user/role pode ter
• Effective permissions = Identity policy ∩ Boundary
• Não concede permissões por si só
• Ideal para delegação segura:
  - Admin cria boundary
  - Dev cria roles dentro do boundary
  - Dev não pode escalar privilégios

Exemplo:
• Boundary permite: s3:*, dynamodb:*
• Identity policy permite: s3:*, ec2:*
• Effective: apenas s3:* (interseção)

🎯 Para o exame: Explicit Deny sempre vence. Permission Boundary = interseção com identity policy. Cross-account com resource-based policy mantém permissões originais. STS retorna credenciais temporárias.

Amazon Cognito

Serviço de identidade para aplicações web e mobile — autenticação, autorização e gerenciamento de usuários.

User Pools vs Identity Pools

CaracterísticaUser PoolsIdentity Pools (Federated Identities)
FunçãoAutenticação (quem é você?)Autorização (o que você pode fazer na AWS?)
RetornaJWT Tokens (ID, Access, Refresh)Credenciais AWS temporárias (STS)
Caso de usoSign-up, sign-in, MFA, social loginAcesso direto a serviços AWS (S3, DynamoDB)
ProvidersPróprio, Google, Facebook, SAML, OIDCCognito User Pool, Google, Facebook, SAML, OIDC
IntegraçãoAPI Gateway (Cognito Authorizer), ALBIAM Roles para acesso a recursos AWS

Authentication Flows e Tokens

Auth FlowsFluxos
USER_SRP_AUTH:
• Secure Remote Password (recomendado)
• Senha nunca trafega pela rede

USER_PASSWORD_AUTH:
• Envia username + password diretamente
• Menos seguro, mais simples

CUSTOM_AUTH:
• Lambda triggers para lógica customizada
• Desafios personalizados (CAPTCHA, OTP)

ADMIN_USER_PASSWORD_AUTH:
• Server-side (backend)
• Requer credenciais admin

Refresh Token:
• Obtém novos ID/Access tokens
• Sem re-autenticação do usuário
• Validade: 1 dia a 3650 dias
TokensJWT
ID Token:
• Identidade do usuário
• Claims: email, name, phone, custom attributes
• Usado para personalização no frontend
• Validade: 5 min a 1 dia

Access Token:
• Autorização para APIs
• Claims: scopes, groups
• Usado no header Authorization: Bearer
• Validade: 5 min a 1 dia

Refresh Token:
• Obtém novos tokens sem re-login
• Validade: 1 dia a 10 anos
• Pode ser revogado

⚠️ ID Token = quem é | Access Token = o que pode
MFA & SecurityProteção
MFA:
• TOTP (Google Authenticator)
• SMS (menos seguro)
• Pode ser obrigatório ou opcional

Advanced Security:
• Adaptive authentication
• Compromised credentials detection
• Account takeover protection
• Risk-based MFA

Lambda Triggers:
• Pre sign-up: validação customizada
• Post confirmation: welcome email
• Pre token generation: custom claims
• Custom message: personalizar emails
• Migrate user: migração de legacy

🎯 Para o exame: User Pool = autenticação (JWT). Identity Pool = autorização (credenciais AWS). Fluxo comum: User Pool autentica → Identity Pool fornece credenciais AWS. API Gateway usa Cognito Authorizer com User Pool tokens.

AWS KMS (Key Management Service)

Gerenciamento centralizado de chaves de criptografia para proteger dados em repouso e em trânsito.

Tipos de CMK (Customer Master Key)

TipoGerenciamentoRotaçãoCaso de Uso
AWS OwnedAWS (invisível)VariaServiços AWS internamente (SSE-S3)
AWS ManagedAWS (visível, aws/service)Automática (1 ano)Serviços AWS com sua chave (aws/s3, aws/ebs)
Customer ManagedVocê gerenciaConfigurável (opcional)Controle total, cross-account, auditoria

Envelope Encryption e Key Policies

Envelope EncryptionPadrão

Padrão usado para criptografar dados maiores que 4 KB.

Processo:
1. GenerateDataKey → retorna:
   • Plaintext data key (para criptografar)
   • Encrypted data key (para armazenar)
2. Criptografa dados com plaintext data key
3. Descarta plaintext data key da memória
4. Armazena encrypted data key junto aos dados

Decrypt:
1. Envia encrypted data key ao KMS
2. KMS retorna plaintext data key
3. Usa plaintext data key para decriptar dados

⚠️ KMS só criptografa até 4 KB diretamente
⚠️ Para dados maiores: SEMPRE envelope encryption
Key Policies & GrantsAcesso
Key Policy (obrigatória):
• Toda CMK tem uma key policy
• Define quem pode usar/gerenciar a chave
• Sem key policy = ninguém acessa (nem root)
• Default: permite root account gerenciar

Grants:
• Permissões temporárias e granulares
• Programáticas (via API)
• Não precisam alterar key policy
• Ideal para: acesso temporário, delegação
• Podem ser revogados (RevokeGrant)

IAM Policy + Key Policy:
• Ambos devem permitir para funcionar
• Key policy deve permitir IAM policies
  (statement com "Enable IAM User Permissions")
Data Key CachingPerformance
AWS Encryption SDK:
• Cache de data keys para reutilização
• Reduz chamadas ao KMS (custo + latência)
• LocalCryptoMaterialsCache

Configurações:
• Max age: tempo máximo no cache
• Max bytes encrypted: limite de dados
• Max messages encrypted: limite de mensagens

Quando usar:
• Alto volume de encrypt/decrypt
• Latência é crítica
• Custo de KMS API calls é relevante

⚠️ Trade-off: segurança vs performance

🎯 Para o exame: Dados > 4 KB = Envelope Encryption (GenerateDataKey). Key Policy é obrigatória. Customer Managed Key para controle total e cross-account. AWS Encryption SDK para data key caching.

Secrets Manager vs SSM Parameter Store

Dois serviços para armazenar configurações e segredos, com características diferentes.

CaracterísticaSecrets ManagerSSM Parameter Store
PropósitoSegredos (senhas, API keys, tokens)Configurações e segredos
Rotação automáticaSim (Lambda built-in para RDS, Redshift, DocumentDB)Não nativo (precisa Lambda + EventBridge)
CriptografiaSempre criptografado (KMS)Opcional (SecureString com KMS)
VersionamentoSim (automático)Sim (labels: latest, v1, v2)
Cross-accountSim (resource policy)Não nativo (precisa assumir role)
Custo$0.40/segredo/mês + $0.05/10K API callsStandard: gratuito | Advanced: $0.05/parâmetro/mês
Tamanho máximo64 KBStandard: 4 KB | Advanced: 8 KB
HierarquiaNãoSim (/app/prod/db/password)
Integração CloudFormationDynamic referenceDynamic reference + resolve
Secrets ManagerRotação
Rotação automática:
• Lambda function rotaciona o segredo
• Built-in para: RDS, Redshift, DocumentDB
• Custom Lambda para outros serviços
• Schedule: dias ou cron expression

Uso no código:
import boto3
client = boto3.client('secretsmanager')
response = client.get_secret_value(
    SecretId='prod/myapp/database'
)
secret = json.loads(response['SecretString'])

⚠️ Cache o segredo no código (não buscar a cada request)
Parameter StoreHierarquia
Tipos de parâmetro:
• String: texto simples
• StringList: lista separada por vírgula
• SecureString: criptografado com KMS

Hierarquia:
/myapp/
  /prod/
    /db/host
    /db/password (SecureString)
    /api/key (SecureString)
  /dev/
    /db/host
    /db/password

GetParametersByPath:
• Busca todos os parâmetros de um path
• Recursive: busca subpaths
• WithDecryption: decripta SecureStrings

Tiers:
• Standard: 4 KB, 10K params, gratuito
• Advanced: 8 KB, 100K params, policies

🎯 Para o exame: Precisa de rotação automática → Secrets Manager. Configurações simples e gratuitas → Parameter Store. Hierarquia de parâmetros → Parameter Store. Segredos de banco com rotação → Secrets Manager.

Criptografia em Repouso e em Trânsito

Padrões de criptografia para proteger dados em diferentes estados.

Encryption at RestArmazenamento
S3:
• SSE-S3: chave gerenciada pela AWS (padrão)
• SSE-KMS: chave KMS (auditoria, controle)
• SSE-C: chave fornecida pelo cliente
• Client-side: criptografa antes de enviar

DynamoDB:
• AWS owned key (padrão, gratuito)
• AWS managed key (aws/dynamodb)
• Customer managed key (CMK)

EBS:
• AES-256 (aws/ebs ou CMK)
• Snapshots criptografados automaticamente

RDS:
• AES-256 com KMS
• Deve ser habilitado na criação
• Read replicas herdam criptografia
Encryption in TransitRede
TLS/SSL:
• HTTPS para APIs AWS (obrigatório)
• TLS 1.2+ recomendado
• Certificate Manager (ACM) para certificados

VPN:
• Site-to-Site VPN (IPSec)
• Client VPN

Serviços específicos:
• S3: bucket policy para forçar HTTPS
  "aws:SecureTransport": "false" → Deny
• RDS: rds.force_ssl = 1
• ElastiCache: in-transit encryption
• DynamoDB: sempre HTTPS (endpoint)

⚠️ Sempre forçar HTTPS via policies
⚠️ SSE-C requer HTTPS obrigatoriamente

API Gateway Authorizers (Detalhado)

Mecanismos de autenticação e autorização para APIs.

Lambda AuthorizerCustom
Fluxo:
1. Client envia request com token/params
2. API Gateway invoca Lambda Authorizer
3. Lambda valida e retorna IAM Policy
4. API Gateway cacheia policy (opcional)
5. Request é permitido ou negado

Retorno da Lambda:
{
  "principalId": "user123",
  "policyDocument": {
    "Statement": [{
      "Effect": "Allow",
      "Action": "execute-api:Invoke",
      "Resource": "arn:aws:execute-api:..."
    }]
  },
  "context": { "org": "acme" }
}

• Cache: 0 a 3600 segundos
• Custo: Lambda invocation + API Gateway
Cognito AuthorizerJWT
Fluxo:
1. Client autentica no Cognito User Pool
2. Recebe JWT tokens (ID + Access)
3. Envia token no header Authorization
4. API Gateway valida JWT automaticamente
5. Sem invocação de Lambda

Configuração:
• Especificar User Pool ID
• Token source: header Authorization
• Validação: signature, expiration, issuer

Vantagens:
• Sem custo adicional (sem Lambda)
• Validação automática de JWT
• Integração nativa

Limitações:
• Apenas Cognito User Pool tokens
• Sem lógica customizada
• Sem acesso a headers/query params
IAM AuthorizationSigV4
Fluxo:
1. Client assina request com SigV4
2. API Gateway valida assinatura
3. Verifica IAM policy do caller
4. Verifica resource policy da API

Quando usar:
• Chamadas entre serviços AWS
• Cross-account access
• Usuários IAM/Roles
• Não precisa de token externo

Configuração:
• Authorization: AWS4-HMAC-SHA256
• SDK assina automaticamente
• Resource policy para cross-account

⚠️ Melhor para service-to-service
⚠️ Não ideal para usuários finais (web/mobile)

🎯 Para o exame: Lambda Authorizer = lógica customizada, tokens de terceiros. Cognito Authorizer = JWT do Cognito, sem Lambda. IAM Auth = service-to-service, SigV4. Para OAuth/OIDC de terceiros → Lambda Authorizer.
