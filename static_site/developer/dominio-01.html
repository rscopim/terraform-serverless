AWS Lambda

Serviço de computação serverless que executa código em resposta a eventos sem provisionar ou gerenciar servidores.

Conceitos Fundamentais

HandlerEntry Point

Função que o Lambda chama para iniciar a execução. Recebe o evento e o contexto.

# Python
def handler(event, context):
    return {
        'statusCode': 200,
        'body': json.dumps('Hello')
    }

# Node.js
exports.handler = async (event, context) => {
    return { statusCode: 200, body: 'Hello' };
};
ConfiguraçõesLimites
• Timeout: 1s a 15 min (padrão: 3s)
• Memória: 128 MB a 10.240 MB (64 MB increments)
• CPU: proporcional à memória alocada
• Disco (/tmp): 512 MB a 10.240 MB
• Pacote deploy: 50 MB (zip) / 250 MB (unzipped)
• Variáveis de ambiente: 4 KB total
• Payload síncrono: 6 MB
• Payload assíncrono: 256 KB
• Concurrent executions: 1000 (padrão por região)

Tipos de Invocação

TipoComportamentoRetryExemplos
SíncronoEspera resposta. Caller gerencia erros.Nenhum (caller decide)API Gateway, ALB, CloudFront, Cognito
AssíncronoRetorna 202 imediatamente. Lambda gerencia retry.2 retries (total 3 tentativas)S3, SNS, EventBridge, CloudWatch Events
Event Source MappingLambda faz polling da source. Processa em batches.Retry até expirar ou sucessoSQS, Kinesis, DynamoDB Streams, Kafka

Concorrência

Reserved ConcurrencyLimite

Reserva um número fixo de instâncias para a função. Garante capacidade mas também limita.

• Garante que a função sempre terá X instâncias disponíveis
• Limita a função a no máximo X execuções simultâneas
• Throttling (429) se exceder o limite
• Definir como 0 = desabilita a função
Provisioned ConcurrencyWarm

Mantém instâncias pré-inicializadas (warm). Elimina cold starts.

• Instâncias sempre prontas (sem cold start)
• Custo adicional (paga por instância provisionada)
• Pode usar Auto Scaling para ajustar
• Ideal para funções com latência crítica
• Funciona com aliases e versões publicadas

Layers, DLQ, Destinations, Versions e Aliases

Lambda LayersCompartilhamento

Pacotes de código/bibliotecas compartilhados entre funções.

• Até 5 layers por função
• Tamanho total (função + layers): 250 MB unzipped
• Montado em /opt
• Versionado independentemente
• Pode ser compartilhado entre contas
DLQ e DestinationsErro Handling

Tratamento de falhas em invocações assíncronas.

DLQ (Dead Letter Queue):
• SQS ou SNS como destino de falhas
• Apenas para invocações assíncronas
• Envia após todos os retries falharem

Destinations (recomendado):
• Suporta sucesso E falha
• Destinos: SQS, SNS, Lambda, EventBridge
• Mais informações no payload que DLQ
• Pode encadear funções
Versions & AliasesDeploy

Controle de versão e roteamento de tráfego.

Versions:
• Snapshot imutável (código + config)
• $LATEST = versão mutável (dev)
• Cada publish cria v1, v2, v3...

Aliases:
• Ponteiro nomeado para uma versão
• Ex: "prod" → v3, "dev" → $LATEST
• Weighted alias: split traffic (canary)
  - prod: 90% → v3, 10% → v4
• Não pode referenciar outro alias

🎯 Para o exame: Destinations > DLQ (mais flexível). Provisioned Concurrency elimina cold starts. Event Source Mapping faz polling (SQS, Kinesis, DynamoDB Streams). Weighted aliases permitem canary deployments.

Stages, Throttling e Caching

StagesAmbientes

Ambientes de deploy da API (dev, staging, prod).

• Cada stage = URL diferente
  https://api-id.execute-api.region.amazonaws.com/prod
• Stage variables: variáveis por stage
  - Referenciar Lambda aliases: ${stageVariables.alias}
• Canary deployments no stage
  - % do tráfego para nova versão
• Deploy history com rollback
ThrottlingRate Limit

Proteção contra excesso de requisições.

Limites padrão (por região):
• 10.000 requests/segundo (steady-state)
• 5.000 requests burst

Níveis de throttling:
1. Account level (regional)
2. Stage level (usage plan)
3. Method level (per-method)

Resposta: HTTP 429 Too Many Requests

Cross-Origin Resource Sharing para chamadas de browsers.

Headers necessários:

API Gateway Caching

CachePerformance
• Disponível apenas em REST API
• Cache por stage (0.5 GB a 237 GB)
• TTL: 0 a 3600 segundos (padrão: 300s)
• Pode invalidar com header:
  Cache-Control: max-age=0
• Custo adicional por hora
• Pode ser por método específico
• Encrypt cache data: opcional

🎯 Para o exame: HTTP API é mais barato e rápido que REST API, mas REST API tem mais recursos (caching, API keys, WAF). LAMBDA_PROXY é o tipo de integração mais usado. Com LAMBDA_PROXY, o Lambda deve retornar headers CORS manualmente.

Amazon DynamoDB

Banco de dados NoSQL serverless, totalmente gerenciado, com latência de milissegundos em qualquer escala.

Modelo de Dados

ChavesPrimary Key
Partition Key (PK):
• Obrigatória
• Determina a partição física
• Deve ter alta cardinalidade
• Hash function distribui dados

Sort Key (SK) — opcional:
• Permite múltiplos itens por PK
• Ordenação dentro da partição
• Permite range queries (begins_with, between)

Composite Key = PK + SK
• Combinação deve ser única
• Ex: PK=UserId, SK=OrderDate
Índices SecundáriosGSI / LSI
GSI (Global Secondary Index):
• PK e SK diferentes da tabela base
• Pode ser criado a qualquer momento
• Tem própria capacidade (RCU/WCU)
• Eventually consistent apenas
• Até 20 GSIs por tabela
• Projeção: ALL, KEYS_ONLY, INCLUDE

LSI (Local Secondary Index):
• Mesma PK, SK diferente
• Deve ser criado na criação da tabela
• Compartilha capacidade da tabela
• Suporta strongly consistent reads
• Até 5 LSIs por tabela
• Limite: 10 GB por partition key

Capacity Modes

ModoCobrançaQuando UsarCaracterísticas
ProvisionedRCU/WCU definidosTráfego previsívelAuto Scaling disponível, Reserved Capacity para desconto
On-DemandPay-per-requestTráfego imprevisível, novo appSem planejamento de capacidade, 2.5x mais caro por request
RCU / WCUCálculo
RCU (Read Capacity Unit):
• 1 RCU = 1 strongly consistent read/s (até 4 KB)
• 1 RCU = 2 eventually consistent reads/s (até 4 KB)
• Transactional: 2 RCUs por read (4 KB)

WCU (Write Capacity Unit):
• 1 WCU = 1 write/s (até 1 KB)
• Transactional: 2 WCUs por write (1 KB)

Exemplo: Item de 6 KB
• Strong read: ceil(6/4) = 2 RCUs
• Eventually: ceil(6/4) / 2 = 1 RCU
• Write: ceil(6/1) = 6 WCUs

DynamoDB Streams, TTL, DAX e Transactions

DynamoDB StreamsCDC

Captura mudanças na tabela em tempo real (Change Data Capture).

Stream Views:
• KEYS_ONLY: apenas as chaves
• NEW_IMAGE: item após a mudança
• OLD_IMAGE: item antes da mudança
• NEW_AND_OLD_IMAGES: ambos

• Retém dados por 24 horas
• Processado por Lambda ou Kinesis
• Garante ordem por partition key
• Ideal para: replicação, triggers, analytics
TTLExpiração

Remove itens automaticamente após timestamp expirar.

• Atributo com epoch timestamp (seconds)
• Sem custo adicional (não consome WCU)
• Deletado em até 48h após expiração
• Item expirado aparece em queries até deletar
• Pode filtrar com FilterExpression
• Deletions aparecem no DynamoDB Streams
• Ideal para: sessões, logs temporários, cache
DAXCache

DynamoDB Accelerator — cache in-memory para DynamoDB.

• Latência de microssegundos (vs ms)
• Compatível com API do DynamoDB
• Write-through cache
• Item cache: GetItem, BatchGetItem
• Query cache: Query, Scan results
• TTL padrão: 5 minutos
• Multi-AZ (mínimo 3 nodes recomendado)
• Não suporta: strongly consistent reads
• Ideal para: read-heavy, hot keys
TransactionsACID

Operações ACID em múltiplos itens/tabelas.

• TransactWriteItems: até 100 itens
• TransactGetItems: até 100 itens
• All-or-nothing (atomicidade)
• Consome 2x capacidade (RCU/WCU)
• Idempotent com ClientRequestToken
• Casos: transferências, pedidos, inventário

PartiQL:
• SQL-compatible query language
• SELECT, INSERT, UPDATE, DELETE
• Funciona com console, CLI e SDK
• Suporta transactions

🎯 Para o exame: GSI pode ser criado depois, LSI apenas na criação. DAX = cache de leitura (microssegundos). Streams retém 24h. TTL não consome WCU. Transactions consomem 2x capacidade. On-Demand é mais caro mas sem planejamento.

Lifecycle, Versioning, Presigned URLs

Lifecycle RulesAutomação
Transition Actions:
• Mover entre storage classes
• Ex: Standard → IA após 30 dias
• Ex: IA → Glacier após 90 dias

Expiration Actions:
• Deletar objetos após X dias
• Deletar versões antigas
• Deletar incomplete multipart uploads

Filtros:
• Por prefixo (pasta)
• Por tags
• Por tamanho do objeto
VersioningHistórico
• Habilitado no nível do bucket
• Cada versão tem ID único
• Delete = adiciona "delete marker"
• Recuperar: deletar o delete marker
• Não pode ser desabilitado (apenas suspenso)
• MFA Delete: proteção extra
• Integra com Lifecycle (versões antigas)
• Custo: armazena todas as versões
Presigned URLsAcesso Temporário
• URL com credenciais temporárias
• Upload ou download
• Expira após tempo definido
  - Console: até 12h
  - CLI: até 7 dias (168h)
• Herda permissões de quem gerou
• Ideal para: conteúdo privado, uploads diretos

# Gerar presigned URL (CLI)
aws s3 presign s3://bucket/key \
  --expires-in 3600
Event NotificationsTriggers
Eventos:
• s3:ObjectCreated:*
• s3:ObjectRemoved:*
• s3:ObjectRestore:*

Destinos:
• SNS Topic
• SQS Queue
• Lambda Function
• EventBridge (todos os eventos)

• Filtro por prefixo e sufixo
• EventBridge: mais flexível, mais destinos
• Pode ter múltiplas notificações por bucket

Transfer Acceleration

S3 Transfer AccelerationPerformance
• Usa CloudFront edge locations para acelerar uploads
• Endpoint: bucketname.s3-accelerate.amazonaws.com
• Custo adicional por GB transferido
• Ideal para: uploads de longa distância, grandes arquivos
• Multipart upload: recomendado para arquivos > 100 MB (obrigatório > 5 GB)

🎯 Para o exame: Presigned URLs herdam permissões do criador. Event Notifications → SNS, SQS, Lambda ou EventBridge. Versioning não pode ser desabilitado após habilitado. Multipart upload obrigatório acima de 5 GB.

Amazon SQS

Serviço de filas de mensagens totalmente gerenciado para desacoplamento de componentes.

Standard vs FIFO

CaracterísticaStandardFIFO
ThroughputIlimitado300 msg/s (3000 com batching)
OrdenaçãoBest-effort (pode desordenar)Garantida (FIFO)
DuplicatasAt-least-once (pode duplicar)Exactly-once (deduplication)
Nome da filaQualquer nomeDeve terminar com .fifo
Message Group IDN/AObrigatório (ordena dentro do grupo)

Configurações Importantes

Visibility TimeoutLock
• Tempo que mensagem fica "invisível" após ser lida
• Padrão: 30 segundos
• Mínimo: 0s | Máximo: 12 horas
• Se consumer não deletar a tempo → mensagem reaparece
• ChangeMessageVisibility: estender timeout
• Deve ser > tempo de processamento

⚠️ Se mensagens são processadas 2x:
   → Aumentar visibility timeout
DLQDead Letter Queue
• Fila para mensagens que falharam N vezes
• maxReceiveCount: tentativas antes do DLQ
• Redrive policy: configuração do DLQ
• Mesmo tipo (Standard DLQ para Standard, FIFO para FIFO)
• Retention: até 14 dias
• Redrive to source: reprocessar mensagens do DLQ

Boas práticas:
• Alarme no DLQ (CloudWatch)
• Retention do DLQ > retention da fila original
Long PollingEficiência
Short Polling (padrão):
• Retorna imediatamente (mesmo vazio)
• Mais requests = mais custo

Long Polling (recomendado):
• Espera até ter mensagem (ou timeout)
• WaitTimeSeconds: 1-20 segundos
• Reduz requests vazios
• Reduz custo
• Configurar na fila ou no ReceiveMessage

⚠️ Sempre usar Long Polling em produção
Batch OperationsPerformance
• SendMessageBatch: até 10 mensagens
• ReceiveMessage: até 10 mensagens (MaxNumberOfMessages)
• DeleteMessageBatch: até 10 mensagens
• Tamanho máximo por mensagem: 256 KB
• Batch total: 256 KB
• Reduz custos (cobrado por request)
• Extended Client Library: mensagens > 256 KB (usa S3)

Delay Queue:
• DelaySeconds: 0-900s (15 min)
• Mensagem invisível por X segundos após envio
• Diferente de visibility timeout

🎯 Para o exame: FIFO garante ordem e exactly-once. Long Polling reduz custo. Visibility Timeout deve ser maior que o tempo de processamento. DLQ deve ser do mesmo tipo da fila. Extended Client Library para mensagens > 256 KB.

Amazon SNS

Serviço de mensagens pub/sub para comunicação entre serviços e notificações.

Topics, Subscriptions e Fan-Out

Topics & SubscriptionsPub/Sub
Tipos de Topic:
• Standard: alta throughput, best-effort ordering
• FIFO: ordenação garantida, deduplication

Protocolos de Subscription:
• HTTP/HTTPS (webhooks)
• Email / Email-JSON
• SQS (fan-out pattern)
• Lambda
• SMS
• Kinesis Data Firehose
• Platform application (push mobile)

• Até 12.5M subscriptions por topic
• Até 100.000 topics por conta
Fan-Out PatternArquitetura

SNS + SQS para processar a mesma mensagem de formas diferentes.

SNS Topic
  ├── SQS Queue A → Service A (email)
  ├── SQS Queue B → Service B (analytics)
  └── SQS Queue C → Service C (archive)

Benefícios:
• Desacoplamento total
• Cada consumer processa independentemente
• Retry independente por fila
• Adicionar consumers sem alterar publisher

SNS FIFO + SQS FIFO:
• Ordenação end-to-end garantida
• Fan-out com ordem
Message FilteringFiltro

Filtrar mensagens por subscription usando filter policies.

Filter Policy (JSON):
{
  "eventType": ["order_placed"],
  "store": ["store-a", "store-b"],
  "price": [{"numeric": [">=", 100]}]
}

• Aplicado por subscription
• Sem filtro = recebe tudo
• Reduz processamento desnecessário
• Filtro por atributos da mensagem
• Suporta: exact match, prefix, numeric,
  exists, anything-but, IP address

🎯 Para o exame: SNS = push (entrega imediata). SQS = pull (consumer busca). Fan-out = SNS → múltiplas SQS. Message Filtering evita processamento desnecessário nos subscribers.

Orquestração visual de workflows serverless usando state machines.

Duração máxima1 ano5 minutos

Tipos de Estado

StatesTipos
• Task: executa trabalho (Lambda, ECS, etc.)
• Choice: decisão condicional (if/else)
• Parallel: execução paralela de branches
• Map: iteração sobre array (loop)
• Wait: pausa por tempo definido
• Pass: passa input para output (debug/transform)
• Succeed: finaliza com sucesso
• Fail: finaliza com erro
Error HandlingResiliência
Retry:
• ErrorEquals: tipos de erro
• IntervalSeconds: tempo entre retries
• MaxAttempts: máximo de tentativas
• BackoffRate: multiplicador exponencial

Catch:
• ErrorEquals: tipos de erro para capturar
• Next: estado de fallback
• ResultPath: onde colocar o erro

Erros predefinidos:
• States.ALL: qualquer erro
• States.Timeout: timeout
• States.TaskFailed: falha na task
• States.Permissions: sem permissão
Service IntegrationsIntegrações
Padrões de integração:
• Request Response: chama e espera resposta
• Run a Job (.sync): espera job completar
  - ECS, Glue, Batch, CodeBuild
• Wait for Callback (.waitForTaskToken):
  - Pausa até receber token de callback
  - Ideal para aprovações humanas

Serviços integrados:
• Lambda, ECS, Fargate, Batch
• DynamoDB, SQS, SNS
• Glue, SageMaker, EMR
• API Gateway, EventBridge

🎯 Para o exame: Standard = workflows longos (até 1 ano). Express = alto volume e curta duração (até 5 min). Retry + Catch para error handling. .waitForTaskToken para aprovações humanas. Map state para processar arrays.
