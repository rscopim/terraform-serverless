CI/CD Pipeline — AWS Developer Tools

Suite de serviços para automação completa do ciclo de desenvolvimento.

CodeCommit, CodeBuild, CodeDeploy, CodePipeline

CodeCommitSource
• Repositório Git gerenciado pela AWS
• Privado, criptografado, altamente disponível
• Sem limite de tamanho de repositório
• Integração com IAM para acesso
• Triggers: SNS, Lambda (push events)
• Pull Requests com aprovações
• Cross-account access via IAM role

Autenticação:
• HTTPS: Git credentials ou credential helper
• SSH: SSH keys no IAM user
• Não suporta: anonymous access
CodeBuildBuild
• Serviço de build serverless (pay-per-use)
• Compila código, roda testes, gera artefatos
• Ambientes: Docker containers gerenciados
• Escala automaticamente

buildspec.yml (na raiz do repo):
version: 0.2
env:
  variables:
    ENV: "prod"
  secrets-manager:
    DB_PASS: prod/db:password
phases:
  install:
    runtime-versions:
      nodejs: 18
  pre_build:
    commands:
      - npm install
  build:
    commands:
      - npm run build
      - npm test
  post_build:
    commands:
      - echo "Build complete"
artifacts:
  files:
    - '**/*'
  base-directory: dist
cache:
  paths:
    - node_modules/**/*
CodeDeployDeploy
• Deploy automatizado para EC2, ECS, Lambda, On-premises
• Rollback automático em caso de falha
• Deployment groups: conjunto de instâncias

appspec.yml (EC2/On-premises):
version: 0.0
os: linux
files:
  - source: /
    destination: /var/www/html
hooks:
  BeforeInstall:
    - location: scripts/install_deps.sh
      timeout: 300
  AfterInstall:
    - location: scripts/configure.sh
  ApplicationStart:
    - location: scripts/start_server.sh
  ValidateService:
    - location: scripts/health_check.sh

appspec.yml (Lambda):
version: 0.0
Resources:
  - MyFunction:
      Type: AWS::Lambda::Function
      Properties:
        Name: my-function
        Alias: live
        CurrentVersion: 1
        TargetVersion: 2

Lifecycle Hooks (EC2):
ApplicationStop → DownloadBundle →
BeforeInstall → Install → AfterInstall →
ApplicationStart → ValidateService
CodePipelineOrquestração
• Orquestra o pipeline CI/CD completo
• Visual workflow com stages e actions
• Integra todos os Developer Tools

Stages típicos:
1. Source: CodeCommit, GitHub, S3, ECR
2. Build: CodeBuild, Jenkins
3. Test: CodeBuild, terceiros
4. Deploy: CodeDeploy, ECS, S3, CloudFormation
5. Approval: manual approval (SNS notification)

Características:
• Artifacts entre stages (S3)
• Parallel actions dentro de um stage
• Cross-region actions
• Cross-account deployments
• CloudWatch Events para triggers
• Webhook para GitHub

⚠️ Cada stage deve ter pelo menos 1 action
⚠️ Manual approval para gates de produção

🎯 Para o exame: buildspec.yml = CodeBuild. appspec.yml = CodeDeploy. CodePipeline orquestra tudo. CodeBuild é serverless (sem gerenciar servidores). CodeDeploy hooks definem scripts em cada fase do deploy.

Estratégias de Deployment

Diferentes abordagens para atualizar aplicações em produção com diferentes trade-offs de risco e velocidade.

EstratégiaDowntimeRollbackCustoDescrição
All-at-OnceSimRe-deployBaixoAtualiza todas as instâncias simultaneamente
RollingParcialRe-deployBaixoAtualiza em batches (capacidade reduzida durante deploy)
Rolling with Additional BatchNãoRe-deployMédioCria batch extra antes de atualizar (mantém capacidade)
ImmutableNãoRápido (terminar novas)AltoCria novas instâncias, troca quando saudáveis
Blue/GreenNãoInstantâneo (swap)Alto (2x)Ambiente novo completo, swap de DNS/LB
CanaryNãoRápidoMédio% pequeno do tráfego para nova versão, depois 100%
LinearNãoRápidoMédioIncremento gradual do tráfego (10% a cada 10 min)
CodeDeploy — EC2Estratégias
In-Place Deployment:
• AllAtOnce: todas de uma vez
• HalfAtATime: metade por vez
• OneAtATime: uma por vez
• Custom: definir % ou número

Blue/Green Deployment:
• Cria novo Auto Scaling Group
• Registra no Load Balancer
• Desregistra instâncias antigas
• Rollback: re-route para blue
CodeDeploy — LambdaTraffic Shifting
• Canary10Percent5Minutes:
  10% por 5 min, depois 100%
• Canary10Percent10Minutes:
  10% por 10 min, depois 100%
• Linear10PercentEvery1Minute:
  +10% a cada 1 minuto
• Linear10PercentEvery10Minutes:
  +10% a cada 10 minutos
• AllAtOnce:
  100% imediatamente

Pre/Post Traffic Hooks:
• Lambda functions para validação
• BeforeAllowTraffic: teste antes
• AfterAllowTraffic: teste depois
• Falha no hook = rollback automático

🎯 Para o exame: Blue/Green = rollback instantâneo (mais seguro, mais caro). Canary = teste com % pequeno antes. Immutable = novas instâncias (rollback rápido). Rolling = capacidade reduzida durante deploy.

AWS SAM (Serverless Application Model)

Framework para definir e deployar aplicações serverless. Extensão do CloudFormation.

SAM Templatetemplate.yaml
AWSTemplateFormatVersion: '2010-09-09'
Transform: AWS::Serverless-2016-10-31

Globals:
  Function:
    Timeout: 30
    Runtime: python3.11
    MemorySize: 256
    Environment:
      Variables:
        TABLE_NAME: !Ref MyTable

Resources:
  MyFunction:
    Type: AWS::Serverless::Function
    Properties:
      Handler: app.handler
      CodeUri: src/
      Events:
        ApiEvent:
          Type: Api
          Properties:
            Path: /items
            Method: get
      Policies:
        - DynamoDBCrudPolicy:
            TableName: !Ref MyTable

  MyTable:
    Type: AWS::Serverless::SimpleTable
    Properties:
      PrimaryKey:
        Name: id
        Type: String

  MyApi:
    Type: AWS::Serverless::Api
    Properties:
      StageName: prod
      Auth:
        DefaultAuthorizer: MyCognitoAuth
SAM CLIComandos
Desenvolvimento local:
$ sam init          # scaffold novo projeto
$ sam build         # compila e prepara artefatos
$ sam local invoke  # invoca Lambda localmente
$ sam local start-api  # API Gateway local
$ sam local start-lambda  # endpoint Lambda local

Deploy:
$ sam deploy --guided  # deploy interativo
$ sam deploy           # deploy com samconfig.toml

Outros:
$ sam validate    # valida template
$ sam logs        # tail de logs do CloudWatch
$ sam sync        # sync rápido (dev)

samconfig.toml:
[default.deploy.parameters]
stack_name = "my-app"
s3_bucket = "my-deploy-bucket"
region = "us-east-1"
capabilities = "CAPABILITY_IAM"
confirm_changeset = true

⚠️ Transform: AWS::Serverless-2016-10-31
   é obrigatório no template SAM

SAM Globals e Policy Templates

GlobalsHerança
Globals:
  Function:
    Runtime: python3.11
    Timeout: 30
    MemorySize: 256
    Tracing: Active
    Environment:
      Variables:
        STAGE: prod

• Aplica a TODAS as funções do template
• Função individual pode sobrescrever
• Reduz repetição no template
• Suporta: Function, Api, HttpApi, SimpleTable
Policy TemplatesPermissões
Policies simplificadas do SAM:
• DynamoDBCrudPolicy
• S3ReadPolicy / S3CrudPolicy
• SQSPollerPolicy
• SNSPublishMessagePolicy
• KMSDecryptPolicy
• LambdaInvokePolicy
• StepFunctionsExecutionPolicy
• CloudWatchPutMetricPolicy

Exemplo:
Policies:
  - DynamoDBCrudPolicy:
      TableName: !Ref MyTable
  - S3ReadPolicy:
      BucketName: !Ref MyBucket

⚠️ Muito mais simples que IAM policies manuais

🎯 Para o exame: SAM = extensão do CloudFormation para serverless. Transform é obrigatório. sam local para desenvolvimento local. Globals reduz repetição. Policy Templates simplificam IAM. sam build + sam deploy para CI/CD.

AWS CloudFormation

Infrastructure as Code — define e provisiona recursos AWS de forma declarativa.

Intrinsic Functions

Funções PrincipaisRef & GetAtt
!Ref LogicalName
• Retorna valor do recurso ou parâmetro
• Recurso: geralmente ID físico
• Parâmetro: valor do parâmetro

!GetAtt Resource.Attribute
• Retorna atributo específico do recurso
• Ex: !GetAtt MyBucket.Arn
• Ex: !GetAtt MyBucket.DomainName

!Sub "Hello ${AWS::StackName}"
• Substitui variáveis em strings
• Suporta pseudo-parâmetros

!Join [delimiter, [values]]
• Concatena strings com delimitador

!Select [index, [list]]
• Seleciona item de uma lista

!Split [delimiter, string]
• Divide string em lista
Condicionais & MappingLógica
Conditions:
  IsProd: !Equals [!Ref Env, "prod"]

Resources:
  ProdBucket:
    Type: AWS::S3::Bucket
    Condition: IsProd

!If [condition, true-value, false-value]
!Equals [value1, value2]
!Not [condition]
!And [conditions...]
!Or [conditions...]

Mappings:
  RegionMap:
    us-east-1:
      AMI: ami-12345
    eu-west-1:
      AMI: ami-67890

!FindInMap [MapName, Key1, Key2]
• Ex: !FindInMap [RegionMap, !Ref AWS::Region, AMI]

Pseudo-parâmetros:
• AWS::AccountId, AWS::Region
• AWS::StackName, AWS::StackId
• AWS::NoValue

Change Sets, Nested Stacks e Drift Detection

Change SetsPreview
• Preview de mudanças antes de aplicar
• Mostra: Add, Modify, Remove
• Não garante sucesso (apenas preview)
• Workflow:
  1. Criar change set
  2. Revisar mudanças
  3. Executar ou deletar

Replacement:
• True: recurso será recriado
• False: update in-place
• Conditional: depende do atributo

⚠️ Sempre usar change sets em produção
Nested StacksModularização
• Stack dentro de stack
• Reutilização de templates
• Cada nested stack = recurso AWS::CloudFormation::Stack

Resources:
  VPCStack:
    Type: AWS::CloudFormation::Stack
    Properties:
      TemplateURL: https://s3.../vpc.yaml
      Parameters:
        CIDR: "10.0.0.0/16"

Cross-Stack References:
• Export: Output com Export Name
• Import: !ImportValue ExportName
• Diferente de nested (compartilha entre stacks independentes)

⚠️ Nested = composição (lifecycle junto)
⚠️ Cross-stack = compartilhamento (lifecycle separado)
Drift DetectionCompliance
• Detecta mudanças manuais nos recursos
• Compara estado atual vs template
• Status: IN_SYNC, DRIFTED, NOT_CHECKED

Drift Status por recurso:
• MODIFIED: propriedades alteradas
• DELETED: recurso removido
• NOT_CHECKED: não verificado

Ações após detectar drift:
• Atualizar template para refletir mudanças
• Reverter mudanças manuais
• Import resource para gerenciar

⚠️ Nem todos os recursos suportam drift detection
⚠️ Não detecta drift em nested stacks automaticamente

🎯 Para o exame: !Ref retorna ID, !GetAtt retorna atributos. Change Sets para preview. Nested Stacks para modularização. Cross-Stack para compartilhar outputs. Drift Detection para compliance.

AWS Elastic Beanstalk

PaaS que gerencia infraestrutura automaticamente — deploy de aplicações web sem gerenciar servidores.

Plataformas & AmbientesConfiguração
Plataformas suportadas:
• Node.js, Python, Java, .NET, PHP, Ruby, Go
• Docker (single/multi-container)
• Custom platform (Packer)

Tipos de ambiente:
• Web Server Environment:
  - ELB + Auto Scaling + EC2
  - Para aplicações web (HTTP)
• Worker Environment:
  - SQS + Auto Scaling + EC2
  - Para processamento em background
  - Daemon processa mensagens da fila

Componentes:
• Application: container lógico
• Environment: instância da aplicação
• Application Version: código deployado
• Configuration: settings do ambiente
Deployment PoliciesDeploy
• All at once: rápido, com downtime
• Rolling: batches, capacidade reduzida
• Rolling with additional batch: sem redução
• Immutable: novas instâncias, rollback rápido
• Traffic splitting: canary testing
• Blue/Green: swap de environment URLs

Rollback:
• All at once: re-deploy versão anterior
• Rolling: re-deploy
• Immutable: terminar novas instâncias
• Blue/Green: swap URLs de volta

⚠️ Immutable e Blue/Green são os mais seguros
⚠️ Traffic splitting = canary nativo do Beanstalk
.ebextensionsCustomização
Diretório .ebextensions/ na raiz do source bundle:

.ebextensions/01-packages.config:
packages:
  yum:
    git: []
    nginx: []

.ebextensions/02-files.config:
files:
  "/etc/nginx/conf.d/proxy.conf":
    mode: "000644"
    content: |
      proxy_pass http://localhost:8080;

.ebextensions/03-commands.config:
container_commands:
  01_migrate:
    command: "python manage.py migrate"
    leader_only: true

Ordem de execução:
• Arquivos .config em ordem alfabética
• packages → sources → files → commands
• container_commands: após app deploy
• leader_only: apenas em 1 instância

🎯 Para o exame: .ebextensions para customizar ambiente. Worker environment para SQS processing. Immutable deployment para rollback rápido. leader_only para migrations. Docker suportado nativamente.

Amazon ECS e ECR

Orquestração de containers Docker na AWS com opções de compute gerenciado (Fargate) ou self-managed (EC2).

Task DefinitionsBlueprint
• JSON que define como rodar containers
• Imagem Docker, CPU, memória
• Port mappings, volumes
• Environment variables
• Logging configuration
• IAM roles

{
  "family": "my-app",
  "taskRoleArn": "arn:aws:iam::...",
  "executionRoleArn": "arn:aws:iam::...",
  "containerDefinitions": [{
    "name": "app",
    "image": "123456.dkr.ecr.us-east-1.amazonaws.com/my-app:latest",
    "cpu": 256,
    "memory": 512,
    "portMappings": [{"containerPort": 8080}],
    "logConfiguration": {
      "logDriver": "awslogs",
      "options": {
        "awslogs-group": "/ecs/my-app",
        "awslogs-region": "us-east-1"
      }
    }
  }]
}

Roles:
• Task Role: permissões do container (app)
• Execution Role: permissões do ECS agent (pull image, logs)
Fargate vs EC2Launch Type
Fargate (Serverless):
• Sem gerenciar instâncias EC2
• Paga por vCPU + memória por segundo
• Escala automaticamente
• Isolamento por task (segurança)
• Sem acesso ao host
• Ideal para: microservices, batch jobs

EC2 Launch Type:
• Você gerencia as instâncias EC2
• Mais controle (GPU, instance type)
• Pode ser mais barato em escala
• ECS Agent em cada instância
• Capacity Providers para Auto Scaling
• Ideal para: GPU, compliance, custo otimizado

ECS Services:
• Mantém N tasks rodando
• Load balancer integration (ALB/NLB)
• Auto Scaling (target tracking, step)
• Rolling update ou Blue/Green (CodeDeploy)
• Service discovery (Cloud Map)
Amazon ECRRegistry
Elastic Container Registry:
• Registry privado de Docker images
• Integração nativa com ECS, EKS, Lambda
• Criptografia at rest (KMS)
• Image scanning (vulnerabilidades)
• Cross-region e cross-account replication

Lifecycle Policies:
• Limpar imagens antigas automaticamente
• Por contagem ou por idade
• Manter apenas N imagens mais recentes

Comandos:
# Login
aws ecr get-login-password | \
  docker login --username AWS --password-stdin \
  123456.dkr.ecr.us-east-1.amazonaws.com

# Push
docker tag app:latest 123456.dkr.ecr.../app:latest
docker push 123456.dkr.ecr.../app:latest

# Immutable tags: previne overwrite de tags

🎯 Para o exame: Task Role = permissões da app. Execution Role = permissões do ECS agent. Fargate = serverless containers. ECR lifecycle policies para limpeza. ECS Service para manter tasks rodando com LB.
