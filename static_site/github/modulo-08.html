Seção 1

GitHub Projects — Gestão de Trabalho

O GitHub Projects é um sistema de gestão de projetos integrado ao repositório, conectando issues e PRs a quadros, tabelas e roadmaps.

📋 Quadros, Tabelas e Automações

Recursos do Projects (v2)

  • Views: Board (kanban), Table (planilha), Roadmap (linha do tempo)
  • Campos customizados: Status, Prioridade, Estimativa, Sprint, Iteration
  • Automações built-in: mover item para "Done" quando o PR é mesclado, adicionar issues novas automaticamente
  • Filtros e agrupamentos: por assignee, label, milestone, campo customizado

Gerenciando via GitHub CLI

# Listar projetos
gh project list --owner rscopim

# Adicionar uma issue a um projeto
gh project item-add 1 --owner rscopim --url https://github.com/rscopim/repo/issues/42

# Ver itens de um projeto
gh project item-list 1 --owner rscopim

💡 Fluxo típico com Projects

Colunas Backlog → To Do → In Progress → In Review → Done. Issues entram no Backlog, são priorizadas, movidas para To Do em cada sprint, e as automações movem para In Review quando um PR vinculado é aberto e para Done quando é mesclado. Tudo rastreável e transparente.

Seção 2

GitHub Pages — Hospedagem de Sites

O GitHub Pages hospeda sites estáticos gratuitamente direto do repositório — perfeito para documentação, portfólios e landing pages.

🌐 Publicando com Pages

# Opção 1: publicar de uma branch
# Settings → Pages → Source: Deploy from a branch
# Escolha a branch (ex: main) e a pasta (/ root ou /docs)
# Seu site fica em: https://SEU-USUARIO.github.io/REPO/

# Opção 2: publicar via GitHub Actions (recomendado)
# Settings → Pages → Source: GitHub Actions

Workflow de Deploy no Pages

name: Deploy Pages
on:
  push:
    branches: [main]

permissions:
  contents: read
  pages: write
  id-token: write

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    steps:
      - uses: actions/checkout@v4
      - uses: actions/configure-pages@v5
      - uses: actions/upload-pages-artifact@v3
        with:
          path: './dist'
      - id: deployment
        uses: actions/deploy-pages@v4

🔗 Domínio customizado

Em Settings → Pages → Custom domain, você aponta um domínio próprio (ex: docs.seusite.com) adicionando um registro CNAME/A no seu DNS. O GitHub provisiona HTTPS automaticamente via Let's Encrypt.

Seção 3

Branch Protection Rules

Proteger a branch principal impede merges perigosos e força boas práticas. É um dos controles mais importantes em times.

🛡️ Regras de Proteção

Configurar em Settings → Branches → Add branch protection rule

  • Require a pull request before merging: proíbe push direto na main
  • Require approvals: exige N aprovações (ex: 1 ou 2 reviewers)
  • Dismiss stale approvals: invalida aprovações se novos commits chegarem
  • Require status checks to pass: o CI (Actions) precisa passar antes do merge
  • Require branches to be up to date: a branch deve estar atualizada com a main
  • Require conversation resolution: todos os comentários resolvidos
  • Require signed commits: só commits assinados (GPG/SSH)
  • Include administrators: aplica as regras até para admins
  • Restrict who can push: limita quem pode mesclar

⚠️ Regra mínima recomendada

Para qualquer repositório com mais de uma pessoa: exija PR + pelo menos 1 aprovação + status checks (CI) passando. Isso sozinho previne a maioria dos acidentes em produção. Combine com o fluxo de branches do Módulo 06.

Seção 4

CODEOWNERS e Environments

Dois recursos que refinam a governança: revisão obrigatória por especialistas e ambientes de deploy com aprovação.

👤 CODEOWNERS — Revisão por Área

Arquivo .github/CODEOWNERS

# Sintaxe: <padrão> <owner(s)>
# Owners são solicitados automaticamente como reviewers em PRs
# que tocam os arquivos correspondentes.

# Owner padrão de todo o repositório
*                    @rscopim

# Time de backend revisa a pasta de API
/src/api/            @org/backend

# Especialista em infra revisa Terraform
/infra/              @rscopim @org/devops
*.tf                 @org/devops

# Docs podem ser revisados por qualquer um do time de docs
/docs/               @org/tech-writers

# Arquivos de CI exigem revisão do time de plataforma
/.github/workflows/  @org/plataforma

💡 CODEOWNERS + Branch Protection

Combinado com "Require review from Code Owners" nas branch protection rules, isso força que quem entende de cada área revise as mudanças relevantes — evitando que código de infra, por exemplo, seja mesclado sem o aval do time de DevOps.

🌍 Environments com Aprovação

# Settings → Environments → New environment (ex: production)
# Configure:
# - Required reviewers: pessoas que aprovam antes do deploy
# - Wait timer: espera N minutos antes de liberar
# - Deployment branches: só a main pode deployar aqui
# - Environment secrets: secrets exclusivos deste ambiente

# No workflow, referencie o environment:
jobs:
  deploy-prod:
    environment: production   # pausa aguardando aprovação
    runs-on: ubuntu-latest
    steps:
      - run: ./deploy.sh
Seção 5

Dependabot e Segurança de Dependências

Dependências desatualizadas são uma das maiores fontes de vulnerabilidades. O Dependabot automatiza atualizações e alertas.

🤖 Configurando o Dependabot

.github/dependabot.yml

version: 2
updates:
  # Atualizações de pacotes npm
  - package-ecosystem: "npm"
    directory: "/"
    schedule:
      interval: "weekly"
    open-pull-requests-limit: 5
    labels: ["dependencies"]

  # Atualizações do próprio GitHub Actions
  - package-ecosystem: "github-actions"
    directory: "/"
    schedule:
      interval: "monthly"

  # Terraform providers
  - package-ecosystem: "terraform"
    directory: "/infra"
    schedule:
      interval: "weekly"

🛡️ O que o Dependabot faz

  • Version updates: abre PRs atualizando dependências no schedule definido
  • Security updates: abre PRs urgentes quando uma CVE é descoberta
  • Alerts: notifica sobre vulnerabilidades conhecidas nas suas dependências
Seção 6

Code Scanning e Secret Scanning

A suíte de segurança do GitHub detecta vulnerabilidades no seu código e segredos vazados automaticamente.

🔍 Recursos de Segurança (aba Security)

RecursoO que faz
Code scanning (CodeQL)Analisa o código em busca de vulnerabilidades (SQL injection, XSS, etc.)
Secret scanningDetecta tokens, chaves e senhas commitados acidentalmente
Push protectionBloqueia o push que contém um segredo detectado
Dependency graphMapeia todas as dependências e suas versões
Security advisoriesPublicar/gerenciar avisos de segurança do seu projeto

Ativando CodeQL via workflow

# .github/workflows/codeql.yml
name: CodeQL
on:
  push:
    branches: [main]
  schedule:
    - cron: '0 3 * * 1'   # toda segunda às 3h

jobs:
  analyze:
    runs-on: ubuntu-latest
    permissions:
      security-events: write
    steps:
      - uses: actions/checkout@v4
      - uses: github/codeql-action/init@v3
        with:
          languages: javascript, python
      - uses: github/codeql-action/analyze@v3

⚠️ Se um segredo vazou

Remover o segredo em um novo commit NÃO basta — ele continua no histórico. Considere o segredo comprometido e rotacione-o imediatamente (gere uma nova chave/token e revogue o antigo). O secret scanning do GitHub ajuda a detectar, mas a rotação é responsabilidade sua.

Seção 7

Arquivos de Comunidade e Conclusão

Bons repositórios têm arquivos que orientam a comunidade e documentam o projeto. Vamos fechar a trilha com eles.

📄 Health Files do Repositório

ArquivoPropósito
README.mdApresentação do projeto (o mais importante)
LICENSEDefine os direitos de uso do código
CONTRIBUTING.mdComo contribuir (setup, padrões, fluxo)
CODE_OF_CONDUCT.mdRegras de convivência da comunidade
SECURITY.mdComo reportar vulnerabilidades
CHANGELOG.mdHistórico de mudanças por versão
.github/CODEOWNERSDonos de cada área do código

💡 Reuso via repositório .github

Um repositório especial chamado .github na sua conta/organização pode conter health files padrão (CONTRIBUTING, templates, CODE_OF_CONDUCT) que se aplicam a TODOS os repositórios que não os definem localmente. Ótimo para padronizar uma organização inteira.
