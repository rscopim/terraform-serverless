Automação e CI/CD com GitHub Actions

Automatizar testes, builds e deploys é o que transforma um repositório em uma máquina de entregar valor. Neste módulo você domina o GitHub Actions — workflows, jobs, triggers, secrets, matrizes — constrói pipelines de CI/CD reais e aprende a rodar validações locais com Git Hooks, Husky e lint-staged.

Seção 1

Conceitos de CI/CD

Antes das ferramentas, os conceitos. CI/CD é uma prática, não um produto.

🔄 CI, CD e CD

SiglaNomeO que é
CIContinuous IntegrationIntegrar código com frequência, validando automaticamente (build + testes) a cada push/PR
CDContinuous DeliveryManter o código sempre pronto para deploy; o deploy final é manual (1 clique)
CDContinuous DeploymentDeploy automático a cada mudança aprovada, sem intervenção humana

💡 Por que CI/CD importa

  • Pega bugs cedo (a cada PR, não só no fim)
  • Reduz o medo de fazer deploy (é automatizado e repetível)
  • Feedback rápido para quem escreveu o código
  • Libera tempo do time para o que importa
Seção 2

Anatomia de um GitHub Actions Workflow

Um workflow é um arquivo YAML em .github/workflows/. Vamos dissecar sua estrutura.

🧩 Estrutura Fundamental

.github/workflows/ci.yml

name: CI                       # nome do workflow

on:                            # QUANDO rodar (triggers)
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:                          # um workflow tem 1+ jobs
  testes:                      # id do job
    runs-on: ubuntu-latest     # máquina virtual (runner)
    steps:                     # sequência de passos
      - name: Checkout do código
        uses: actions/checkout@v4      # action reutilizável

      - name: Configura Node
        uses: actions/setup-node@v4
        with:
          node-version: '20'

      - name: Instala dependências
        run: npm ci             # comando shell

      - name: Roda os testes
        run: npm test
ConceitoDescrição
WorkflowProcesso automatizado (um arquivo .yml)
Event/TriggerO que dispara o workflow (push, PR, schedule, manual)
JobConjunto de steps que roda em um runner; jobs rodam em paralelo por padrão
StepUma tarefa: um comando (run) ou uma action (uses)
RunnerMáquina que executa o job (Ubuntu, Windows, macOS ou self-hosted)
ActionComponente reutilizável (ex: actions/checkout)
Seção 3

Triggers — Quando o Workflow Roda

O bloco on: define os eventos que disparam o workflow. Há muitas opções úteis.

⏰ Principais Triggers

on:
  # Em push para branches específicas
  push:
    branches: [main, develop]
    paths: ['src/**', 'package.json']   # só se esses arquivos mudarem
    tags: ['v*']                         # ou ao criar tags

  # Em Pull Requests
  pull_request:
    branches: [main]
    types: [opened, synchronize, reopened]

  # Agendado (cron) — ex: todo dia às 3h UTC
  schedule:
    - cron: '0 3 * * *'

  # Manual (botão "Run workflow" na aba Actions)
  workflow_dispatch:
    inputs:
      ambiente:
        description: 'Ambiente de deploy'
        required: true
        default: 'staging'

  # Chamado por outro workflow (reutilizável)
  workflow_call:
Seção 4

Jobs Avançados — Matrix, Dependências e Condicionais

Recursos que tornam os workflows poderosos e eficientes.

🔢 Matrix — Testar em Várias Versões

jobs:
  testes:
    runs-on: ${{ matrix.os }}
    strategy:
      matrix:
        os: [ubuntu-latest, windows-latest, macos-latest]
        node: [18, 20, 22]
    # Gera 3 x 3 = 9 combinações rodando em paralelo!
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node }}
      - run: npm ci && npm test

🔗 Dependências entre Jobs e Condicionais

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - run: echo "buildando..."

  deploy:
    needs: build           # só roda se 'build' passar
    runs-on: ubuntu-latest
    if: github.ref == 'refs/heads/main'   # só na main
    steps:
      - run: echo "deployando..."

  notificar:
    needs: [build, deploy]
    if: always()           # roda mesmo se algo falhar
    runs-on: ubuntu-latest
    steps:
      - run: echo "notificando resultado"
Seção 5

Secrets, Variáveis e Segurança

Pipelines precisam de credenciais (deploy, APIs) sem expô-las no código. GitHub Actions oferece secrets e boas práticas de segurança.

🔐 Usando Secrets

# Configurar em: Settings → Secrets and variables → Actions
# - Secrets: valores sensíveis (mascarados nos logs)
# - Variables: valores não sensíveis

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production      # exige aprovação (protection rules)
    steps:
      - name: Deploy
        env:
          API_TOKEN: ${{ secrets.API_TOKEN }}
          REGION: ${{ vars.AWS_REGION }}
        run: ./deploy.sh

🔒 OIDC — o padrão moderno (sem secrets estáticos)

# Em vez de guardar chaves AWS como secrets, use OIDC:
# o GitHub Actions assume uma IAM Role temporária. Zero segredos armazenados.

permissions:
  id-token: write     # necessário para OIDC
  contents: read

steps:
  - uses: aws-actions/configure-aws-credentials@v4
    with:
      role-to-assume: arn:aws:iam::123456789012:role/github-actions-deploy
      aws-region: us-east-1
  - run: aws s3 sync ./dist s3://meu-bucket

Este é exatamente o padrão usado nos projetos de referência: autenticação OIDC, sem chaves estáticas no repositório.

⚠️ Segurança em workflows

  • Fixe versões das actions por SHA ou tag confiável (evita supply chain attacks)
  • Use permissions: mínimo necessário (least privilege)
  • Cuidado com pull_request_target — roda com secrets em PRs de forks
  • Nunca ecoe secrets em echo ou logs
Seção 6

Pipeline CI/CD Completo

Vamos montar um pipeline real: lint + testes no CI, e deploy no CD.

🚀 Exemplo de Pipeline de Produção

.github/workflows/deploy.yml

name: CI/CD

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

permissions:
  id-token: write
  contents: read

jobs:
  ci:
    name: Lint & Testes
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'
      - run: npm ci
      - run: npm run lint
      - run: npm test
      - name: Upload cobertura
        uses: actions/upload-artifact@v4
        with:
          name: coverage
          path: coverage/

  deploy:
    name: Deploy Produção
    needs: ci
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    environment: production
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: ${{ secrets.AWS_ROLE_ARN }}
          aws-region: us-east-1
      - run: npm ci && npm run build
      - name: Sync para S3
        run: aws s3 sync ./dist s3://meu-site --delete
      - name: Invalida CloudFront
        run: aws cloudfront create-invalidation --distribution-id ${{ secrets.CF_ID }} --paths "/*"

Seção 7

Git Hooks, Husky e lint-staged

Nem toda automação precisa ser na nuvem. Git Hooks rodam validações localmente, antes mesmo do push — feedback instantâneo.

🪝 Git Hooks Nativos

# Hooks ficam em .git/hooks/ (não são versionados por padrão)
# Principais:
#   pre-commit  → antes de criar o commit (lint, testes rápidos)
#   commit-msg  → valida a mensagem de commit
#   pre-push    → antes do push (testes completos)

# Exemplo de .git/hooks/pre-commit (torne executável: chmod +x)
#!/bin/sh
echo "Rodando lint antes do commit..."
npm run lint || {
  echo "❌ Lint falhou. Commit abortado."
  exit 1
}

🐶 Husky + lint-staged

Como os hooks nativos não são versionados, o Husky resolve isso: versiona os hooks no repositório e os instala automaticamente. O lint-staged roda linters apenas nos arquivos em staging (rápido).

# Instalar
npm install --save-dev husky lint-staged
npx husky init

# .husky/pre-commit
npx lint-staged

# package.json
{
  "lint-staged": {
    "*.{js,ts}": ["eslint --fix", "prettier --write"],
    "*.{css,md}": ["prettier --write"]
  }
}

# .husky/commit-msg — validar Conventional Commits
npx --no -- commitlint --edit $1

# Agora, a cada commit:
# 1. lint-staged formata e corrige só os arquivos staged
# 2. commitlint valida a mensagem
# Feedback local ANTES de subir o código

💡 Hooks locais + CI = defesa em camadas

Hooks locais dão feedback rápido, mas podem ser pulados (--no-verify). Por isso, o CI no GitHub Actions é a barreira final e obrigatória: mesmo que alguém pule o hook local, o CI reprova o PR. Use os dois juntos.
