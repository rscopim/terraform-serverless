🐙 Git & GitHub — Módulo 05

Histórico e Reescrita

Um histórico limpo e legível é sinal de profissionalismo. Neste módulo você domina as ferramentas de reescrita do Git: rebase interativo para organizar commits, cherry-pick para transportar mudanças específicas, reset para desfazer e reflog para recuperar o que parecia perdido. Poder que exige responsabilidade — e você vai aprender a usá-lo com segurança.

Seção 1

Rebase — Reaplicando Commits

Rebase move ou "reaplica" uma sequência de commits sobre uma nova base. É a alternativa ao merge que produz um histórico linear, sem commits de merge.

📐 Rebase vs Merge

# Situação inicial:
#   C0 ─ C1 ─ C4 ◀── main
#          └─ C2 ─ C3 ◀── feature

# MERGE cria um commit de junção (C5):
#   C0 ─ C1 ─ C4 ─── C5 ◀── main
#          └─ C2 ─ C3 ─┘

# REBASE reaplica C2 e C3 depois de C4 (histórico linear):
#   C0 ─ C1 ─ C4 ─ C2' ─ C3' ◀── feature
# (C2' e C3' são NOVOS commits — hashes diferentes!)

git switch feature
git rebase main
# Agora feature está "em cima" da main mais recente
AspectoMergeRebase
HistóricoPreserva (com commits de merge)Linear (reescrito)
Hashes dos commitsMantidosAlterados (novos commits)
RastreabilidadeMostra quando as branches se uniramParece que tudo foi sequencial
Uso seguroSempreSó em branches não compartilhadas

⚠️ A Regra de Ouro do Rebase

Nunca faça rebase de commits que já foram enviados (push) e que outras pessoas podem ter baixado. Rebase reescreve o histórico criando novos commits — se outra pessoa tem os commits antigos, o histórico diverge e vira uma bagunça. Rebase é seguro apenas na sua branch local antes do primeiro push.

Seção 2

Rebase Interativo — Organizando Commits

O rebase interativo (-i) é uma das ferramentas mais poderosas do Git. Ele permite reordenar, juntar, editar, renomear e remover commits antes de finalizar seu trabalho.

🎛️ Comandos do Rebase Interativo

# Rebasear interativamente os últimos 4 commits
git rebase -i HEAD~4

# Abre um editor com a lista de commits e as ações disponíveis:
pick   a1b2c3 feat: adiciona login
pick   d4e5f6 fix: corrige typo
pick   g7h8i9 wip: teste
pick   j0k1l2 feat: adiciona logout

# Ações que você pode aplicar a cada linha:
# pick   (p) → mantém o commit como está
# reword (r) → mantém, mas edita a mensagem
# edit   (e) → pausa para você alterar o commit
# squash (s) → funde com o commit ANTERIOR (combina mensagens)
# fixup  (f) → funde com o anterior, DESCARTA a mensagem
# drop   (d) → remove o commit
# reorder    → só mude a ordem das linhas

Exemplo: Limpando uma Branch Antes do PR

# Antes: histórico bagunçado
pick   a1b2c3 feat: adiciona login
squash d4e5f6 fix: corrige typo do login
fixup  g7h8i9 wip: teste
reword j0k1l2 feat: adiciona logout

# Resultado: 2 commits limpos
#   - "feat: adiciona login" (com o typo e o wip incorporados)
#   - "feat: adiciona logout" (com mensagem reescrita)

# Histórico profissional, fácil de revisar e de reverter

💡 Casos de uso comuns

  • Squash de "wip": juntar vários commits de tentativa em um commit final coerente
  • Reword: corrigir mensagens antes de compartilhar
  • Reorder: agrupar commits relacionados
  • Drop: remover um commit experimental que não deu certo
Seção 3

Cherry-Pick — Transportando Commits

Cherry-pick aplica um commit específico de uma branch em outra, sem trazer todo o resto. Útil para levar um hotfix a múltiplas branches ou resgatar um commit isolado.

🍒 Usando Cherry-Pick

# Aplicar um commit específico na branch atual
git cherry-pick a1b2c3

# Aplicar vários commits
git cherry-pick a1b2c3 d4e5f6

# Aplicar um intervalo de commits
git cherry-pick a1b2c3..g7h8i9

# Cherry-pick SEM commitar (revisar antes)
git cherry-pick -n a1b2c3

# Se der conflito, resolva e continue
git cherry-pick --continue
git cherry-pick --abort      # ou aborte

🎯 Caso de uso: hotfix em duas versões

# Você corrigiu um bug crítico na main (commit abc123).
# A versão antiga (branch release/1.x) também precisa da correção:
git switch release/1.x
git cherry-pick abc123
git push
# A correção foi replicada sem trazer outras mudanças da main
Seção 4

Reset — Movendo o Ponteiro

Reset move a branch atual para um commit diferente. Suas três variações controlam o que acontece com o staging e o working directory — a fonte de muita confusão que vamos esclarecer.

🎚️ Os Três Modos de Reset

ModoMove HEADStagingWorking Dir
--soft✅MantémMantém
--mixed (padrão)✅ResetaMantém
--hard✅Reseta⚠️ Descarta
 
# SOFT: desfaz o commit, mas mantém tudo staged
# (ótimo para refazer o último commit com mudanças adicionais)
git reset --soft HEAD~1

# MIXED: desfaz o commit e tira do staging (mantém edições no disco)
git reset HEAD~1
git reset --mixed HEAD~1     # explícito

# HARD: desfaz o commit E descarta TODAS as mudanças (PERIGOSO)
git reset --hard HEAD~1

# Resetar para um commit específico
git reset --hard a1b2c3

# Descartar mudanças e igualar ao remoto
git reset --hard origin/main

⚠️ --hard apaga trabalho não commitado

O reset --hard descarta permanentemente as mudanças do working directory que não foram commitadas. Use com cautela. A boa notícia: commits "perdidos" por reset podem ser recuperados via reflog (próxima seção), mas mudanças nunca commitadas não têm volta.

Seção 5

Revert — Desfazendo com Segurança

Diferente do reset, o revert não apaga histórico. Ele cria um novo commit que desfaz as mudanças de um commit anterior — a forma segura de reverter algo que já foi compartilhado.

↩️ Usando Revert

# Reverter um commit específico (cria um NOVO commit de reversão)
git revert a1b2c3

# Reverter sem abrir editor de mensagem
git revert --no-edit a1b2c3

# Reverter vários commits
git revert HEAD~3..HEAD

# Reverter um commit de merge (precisa indicar o "mainline")
git revert -m 1 <hash-do-merge>

# Reverter sem commitar (agrupar em um commit só)
git revert -n a1b2c3 d4e5f6
git commit -m "revert: desfaz mudanças problemáticas"
CenárioUse
Commit já enviado / branch públicagit revert (seguro)
Commit apenas local, não compartilhadogit reset
Seção 6

Reflog — A Rede de Segurança

O reflog registra todos os movimentos do HEAD, mesmo os que "somem" do histórico normal. É o seu seguro contra desastres — quase nada é realmente perdido no Git.

🛟 Recuperando Commits Perdidos

# Ver o histórico de TODOS os movimentos do HEAD
git reflog
# a1b2c3 HEAD@{0}: reset: moving to HEAD~1
# d4e5f6 HEAD@{1}: commit: feat: funcionalidade importante
# g7h8i9 HEAD@{2}: checkout: moving from main to feature

# Ops! Fiz reset --hard e perdi um commit. Recuperar:
git reset --hard HEAD@{1}
# ou recriar uma branch a partir do commit perdido:
git switch -c recuperada d4e5f6

# Recuperar uma branch deletada (encontre o último commit dela no reflog)
git reflog
git switch -c branch-recuperada <hash>

💡 Por que o reflog salva vidas

Mesmo depois de um reset --hard, rebase mal feito ou branch deletada, os commits continuam no repositório por ~90 dias (até o garbage collection). O reflog é o mapa para encontrá-los de volta. Sempre que "perder" algo no Git, seu primeiro reflexo deve ser git reflog.

Seção 7

Exercício Prático e Resumo

Pratique um squash de commits com rebase interativo — a habilidade que mais impressiona em code reviews.

🧪 Limpando uma Branch com Squash

# 1. Criar uma branch com histórico "sujo"
git switch -c feature/calculadora
echo "def soma(): pass" > calc.py
git add . && git commit -m "wip inicio"
echo "def soma(a,b): return a+b" > calc.py
git commit -am "corrige soma"
echo "# calculadora" > calc.py
git commit -am "typo"

# 2. Ver o histórico bagunçado
git log --oneline    # 3 commits confusos

# 3. Squash tudo em 1 commit limpo
git rebase -i HEAD~3
# No editor: deixe 'pick' no primeiro, 'squash' (ou 's') nos outros 2
# Depois escreva uma mensagem final:
#   "feat: adiciona função de soma na calculadora"

# 4. Verificar o resultado
git log --oneline    # agora só 1 commit limpo!

# 5. Se algo der errado, o reflog te salva:
git reflog

🎯 Resumo do Módulo 05

Você domina agora as ferramentas de reescrita: rebase (linear vs merge) e rebase interativo (squash, reword, reorder, drop), cherry-pick (transportar commits), reset (soft/mixed/hard e seus efeitos), revert (desfazer com segurança em branches públicas) e reflog (recuperar o que parecia perdido). Lembre-se da regra de ouro: reescreva apenas o que ainda não foi compartilhado. No Módulo 06, organizamos tudo isso em fluxos de trabalho profissionais.
