Seção 1

Fork e o Modelo de Contribuição

Há dois modelos de colaboração no GitHub: o modelo de fork (open source, contribuidores externos) e o modelo de branch compartilhada (times com acesso de escrita). Entender os dois é essencial.

🍴 O que é um Fork

Um fork é uma cópia de um repositório na sua própria conta do GitHub. Você usa forks quando quer contribuir com um projeto no qual não tem permissão de escrita — típico de projetos open source. Você faz mudanças no seu fork e propõe que elas sejam integradas ao original via Pull Request.

Fluxo de Fork (Contribuição Open Source)

# 1. No GitHub, clique em "Fork" no repositório original
#    Isso cria github.com/SEU-USUARIO/projeto

# 2. Clone o SEU fork
git clone git@github.com:seu-usuario/projeto.git
cd projeto

# 3. Adicione o repositório ORIGINAL como "upstream"
git remote add upstream git@github.com:dono-original/projeto.git
git remote -v
# origin    → seu fork (push aqui)
# upstream  → original (pull das novidades daqui)

# 4. Mantenha seu fork sincronizado com o original
git fetch upstream
git switch main
git merge upstream/main
git push origin main

# 5. Crie uma branch para sua contribuição
git switch -c fix/corrige-typo-readme

👥 Modelo de Branch Compartilhada

Em times onde todos têm acesso de escrita ao repositório, não se usa fork. Cada pessoa cria branches diretamente no repositório central e abre PRs a partir delas. É o fluxo mais comum em empresas.

AspectoForkBranch compartilhada
Quem usaContribuidores externos / open sourceTimes com acesso de escrita
Onde ficam as branchesNo seu forkNo repositório central
Remotesorigin (fork) + upstream (original)apenas origin
Seção 2

Pull Requests — O Coração da Colaboração

O Pull Request (PR) é a proposta de integrar as mudanças de uma branch em outra. É onde acontece a revisão de código, a discussão e os testes automatizados antes do merge.

🔃 Abrindo um Pull Request

Fluxo Completo de um PR

# 1. Trabalhe na sua branch e faça push
git switch -c feature/nova-funcionalidade
# ... commits ...
git push -u origin feature/nova-funcionalidade

# 2. No GitHub, aparece um botão "Compare & pull request"
#    OU vá em Pull requests → New pull request

# 3. Configure o PR:
#    base: main    ←  compare: feature/nova-funcionalidade
#    (integrar 'compare' DENTRO de 'base')

# 4. Preencha título e descrição, adicione reviewers, labels

# Usando o GitHub CLI (gh):
gh pr create --base main --head feature/nova-funcionalidade \
  --title "feat: nova funcionalidade" \
  --body "Descrição do que foi feito e como testar."

# Ver PRs abertos
gh pr list

# Ver detalhes de um PR
gh pr view 42

✍️ Anatomia de uma boa descrição de PR

  • O quê: resumo das mudanças
  • Por quê: qual problema resolve / qual issue fecha
  • Como testar: passos para o revisor validar
  • Screenshots (se for UI)
  • Palavras-chave que fecham issues: Closes #123, Fixes #45

🔀 Estratégias de Merge de PR

Ao aprovar um PR, o GitHub oferece três formas de integrá-lo:

EstratégiaO que fazQuando usar
Merge commitCria commit de merge preservando todos os commitsQuer histórico completo da branch
Squash and mergeJunta todos os commits do PR em um sóHistórico limpo, 1 commit por feature (mais popular)
Rebase and mergeAplica os commits linearmente sem merge commitHistórico linear sem commits de merge
Seção 3

Code Review — Revisão de Código

A revisão de código melhora a qualidade, espalha conhecimento no time e pega bugs cedo. Saber revisar e ser revisado com maturidade é uma habilidade profissional valiosa.

🔎 Revisando um PR

# Baixar o PR de alguém para testar localmente
gh pr checkout 42
# ... testa, roda, valida ...

# Estados de revisão no GitHub:
# - Comment  → comentários sem aprovar/rejeitar
# - Approve  → aprova as mudanças
# - Request changes → pede alterações antes do merge

# Comentar em linhas específicas: clique no + ao lado da linha no diff
# Sugerir código diretamente (suggestion):
# ```suggestion
# const nome = user.name.trim();
# ```
# O autor pode aceitar a sugestão com 1 clique

✅ Boas práticas ao revisar

  • Seja respeitoso e específico — critique o código, não a pessoa
  • Explique o porquê das sugestões
  • Diferencie o que é bloqueante do que é preferência ("nit:")
  • Elogie boas soluções — review não é só apontar erros
  • Aprove quando estiver bom; não segure o PR por perfeccionismo

✅ Boas práticas ao ser revisado

  • Mantenha PRs pequenos (mais fáceis de revisar)
  • Responda a todos os comentários
  • Não leve críticas para o pessoal
  • Explique decisões de design quando necessário
Seção 4

Issues — Rastreando Trabalho

Issues são o sistema de rastreamento de tarefas, bugs e ideias do GitHub. Bem usadas, tornam o projeto organizado e transparente.

🐛 Criando e Organizando Issues

# Via GitHub CLI
gh issue create --title "Bug: login falha com e-mail maiúsculo" \
  --body "Passos para reproduzir..." \
  --label bug --assignee @me

# Listar issues
gh issue list --label bug --state open

# Fechar uma issue
gh issue close 15

# Referenciar issues em commits/PRs (fecha automaticamente ao mergear):
#   git commit -m "fix: normaliza e-mail no login. Closes #15"
# Palavras que fecham: close, closes, closed, fix, fixes, fixed, resolve...

🏷️ Labels, Milestones e Assignees

RecursoPara que serve
LabelsCategorizar: bug, enhancement, documentation, good first issue
MilestonesAgrupar issues por entrega/versão (ex: "v2.0", "Sprint 5")
AssigneesQuem é responsável pela issue
ProjectsQuadro kanban (veremos no Módulo 08)

Templates de Issue e PR

Templates padronizam a informação que contribuidores fornecem, economizando tempo e melhorando a qualidade das issues e PRs.

📋 Criando Templates

Template de Pull Request

## Descrição
<!-- O que este PR faz? -->

## Tipo de mudança
- [ ] Bug fix
- [ ] Nova feature
- [ ] Breaking change
- [ ] Documentação

## Como testar

- [ ] Código segue o style guide
- [ ] Testes adicionados/atualizados

Seção 7

Exercício Prático e Resumo

Simule uma contribuição completa, do fork ao PR aprovado.

🧪 Sua Primeira Contribuição Open Source

# 1. Fork um repositório com "good first issue" no GitHub
# 2. Clone seu fork e configure upstream
git clone git@github.com:seu-usuario/projeto.git
cd projeto
git remote add upstream git@github.com:original/projeto.git

# 3. Sincronize e crie a branch
git fetch upstream && git switch main && git merge upstream/main
git switch -c docs/corrige-instrucoes-instalacao

# 4. Faça a mudança, commite e envie
git commit -am "docs: corrige comando de instalação no README"
git push -u origin docs/corrige-instrucoes-instalacao

# 5. Abra o PR contra o repositório original
gh pr create --base main --title "docs: corrige instalação" \
  --body "Corrige o comando que estava desatualizado. Closes #7"

# 6. Responda aos comentários da revisão até a aprovação e merge 🎉
