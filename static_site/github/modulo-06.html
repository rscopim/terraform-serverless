🐙 Git & GitHub — Módulo 06

Fluxos de Trabalho Profissionais

Comandos são só ferramentas — o que diferencia times maduros é a disciplina do fluxo de trabalho. Aqui você compara Git Flow, GitHub Flow e Trunk-Based Development, aprende a versionar releases com tags e SemVer, e adota Conventional Commits para gerar changelogs automáticos. É a ponte entre "saber git" e "trabalhar como engenheiro sênior".

Seção 1

GitHub Flow — Simples e Eficaz

O GitHub Flow é o fluxo mais usado hoje em times ágeis e produtos web. Simples, baseado em branches curtas e deploy contínuo a partir da main.

🌊 Como Funciona o GitHub Flow

# A regra central: a branch 'main' está SEMPRE pronta para deploy.

# 1. Crie uma branch a partir da main
git switch main && git pull
git switch -c feature/nova-funcionalidade

# 2. Faça commits pequenos e frequentes
git commit -am "feat: implementa parte 1"

# 3. Abra um Pull Request cedo (mesmo incompleto = draft)
git push -u origin feature/nova-funcionalidade

# 4. Discussão, review e CI automático rodam no PR

# 5. Após aprovação, merge na main

# 6. Deploy automático da main (CI/CD)

# 7. Delete a branch

✅ Quando usar GitHub Flow

  • Produtos web / SaaS com deploy contínuo
  • Times que entregam várias vezes por dia
  • Quando não há necessidade de manter várias versões em paralelo
Seção 2

Git Flow — Estruturado para Releases

O Git Flow é mais elaborado, com branches dedicadas para desenvolvimento, releases e hotfixes. Adequado a produtos com ciclos de release formais e versões mantidas em paralelo.

🌳 As Branches do Git Flow

BranchPropósitoNasce deIntegra em
mainCódigo em produção (tags de versão)——
developIntegração do próximo releasemain—
feature/*Novas funcionalidadesdevelopdevelop
release/*Preparação de um releasedevelopmain + develop
hotfix/*Correção urgente em produçãomainmain + develop
 
# Iniciar uma feature
git switch develop && git switch -c feature/pagamento
# ... trabalho ... depois merge em develop

# Preparar um release
git switch -c release/1.2.0 develop
# ... ajustes finais, bump de versão ...
git switch main && git merge release/1.2.0
git tag -a v1.2.0 -m "Release 1.2.0"
git switch develop && git merge release/1.2.0

# Hotfix urgente
git switch -c hotfix/1.2.1 main
# ... corrige ...
git switch main && git merge hotfix/1.2.1 && git tag v1.2.1
git switch develop && git merge hotfix/1.2.1

⚠️ Git Flow pode ser complexo demais

Para produtos web com entrega contínua, o Git Flow costuma ser burocrático demais. Ele faz sentido para software versionado (bibliotecas, apps desktop/mobile, sistemas com múltiplas versões em suporte). Escolha o fluxo pela necessidade real, não por moda.

Seção 3

Trunk-Based Development

Abordagem favorecida por times de alta performance (DevOps/DORA): todos integram na main (trunk) frequentemente, com branches de vida muito curta e feature flags.

🌲 Princípios do Trunk-Based

Características

  • Branches curtíssimas (horas a 1-2 dias), integradas rápido na main
  • Feature flags para esconder código incompleto em produção
  • CI/CD robusto — testes automáticos garantem que a main nunca quebra
  • Commits pequenos e frequentes reduzem conflitos ao máximo
# Feature flag: código novo entra na main "desligado"
if feature_flags.esta_ativa("novo_checkout"):
    usar_novo_checkout()
else:
    usar_checkout_antigo()

# Assim você faz merge de código incompleto sem impactar usuários,
# e ativa a feature quando estiver pronta — sem branch de longa duração.
FluxoComplexidadeIdeal para
GitHub FlowBaixaWeb/SaaS, times ágeis
Git FlowAltaSoftware versionado, releases formais
Trunk-BasedMédia (exige CI forte)Alta performance, deploy contínuo
Seção 4

Tags e Releases

Tags marcam pontos importantes no histórico — tipicamente versões. Releases no GitHub adicionam notas, binários e changelog a uma tag.

🏷️ Trabalhando com Tags

# Tag anotada (recomendada — guarda autor, data e mensagem)
git tag -a v1.0.0 -m "Primeira versão estável"

# Tag leve (apenas um ponteiro, sem metadados)
git tag v1.0.0-beta

# Taggear um commit antigo específico
git tag -a v0.9.0 a1b2c3 -m "Versão beta"

# Listar tags
git tag
git tag -l "v1.*"       # filtrar

# Ver detalhes de uma tag
git show v1.0.0

# Enviar tags para o GitHub (não vão com git push normal!)
git push origin v1.0.0
git push origin --tags     # todas as tags

# Deletar tag
git tag -d v1.0.0                  # local
git push origin --delete v1.0.0    # remota

📦 GitHub Releases

No GitHub, vá em Releases → Draft a new release, escolha uma tag, adicione título, notas e anexe binários. O GitHub gera automaticamente um changelog a partir dos PRs mesclados desde a última release ("Generate release notes"). Via CLI: gh release create v1.0.0 --generate-notes.

Seção 5

Versionamento Semântico (SemVer)

SemVer é o padrão de numeração de versões mais adotado. Ele comunica, só pelo número, o impacto de uma atualização.

🔢 O Formato MAJOR.MINOR.PATCH

          v  2  .  4  .  1
              │     │     │
              │     │     └── PATCH: correções de bug (compatível)
              │     └──────── MINOR: novas features (compatível)
              └────────────── MAJOR: mudanças que QUEBRAM compatibilidade
MudançaIncrementaExemplo
Correção de bug (sem quebrar API)PATCH1.2.3 → 1.2.4
Nova feature compatívelMINOR (zera PATCH)1.2.4 → 1.3.0
Mudança incompatível (breaking)MAJOR (zera MINOR e PATCH)1.3.0 → 2.0.0

💡 Sufixos de pré-lançamento

Versões instáveis usam sufixos: 1.0.0-alpha, 1.0.0-beta.2, 1.0.0-rc.1 (release candidate). A versão 0.x.y indica desenvolvimento inicial, onde a API ainda pode mudar a qualquer momento.

Seção 6

Conventional Commits

Uma convenção de mensagens de commit que padroniza a comunicação e permite gerar changelogs e versões SemVer automaticamente.

📝 A Especificação

# Formato:
#   <tipo>[escopo opcional]: <descrição>
#
#   [corpo opcional]
#
#   [rodapé(s) opcional(is)]

# Exemplos:
feat: adiciona login com Google
fix: corrige cálculo de frete para o Nordeste
docs: atualiza instruções de instalação
refactor(auth): extrai validação para módulo separado
perf: reduz consultas ao banco no dashboard
test: adiciona testes para o serviço de e-mail
chore: atualiza dependências

# Breaking change (gera MAJOR no SemVer):
feat!: remove suporte à API v1
# ou no rodapé:
feat: nova API de pagamentos

BREAKING CHANGE: o endpoint /pay foi removido, use /payments
TipoSignificadoImpacto SemVer
featNova funcionalidadeMINOR
fixCorreção de bugPATCH
docsDocumentação—
styleFormatação (sem mudar lógica)—
refactorRefatoração—
perfMelhoria de performancePATCH
testTestes—
choreManutenção/build—
feat! / BREAKING CHANGEQuebra compatibilidadeMAJOR

🤖 Automação a partir dos commits

Ferramentas como semantic-release e standard-version leem seus Conventional Commits e automaticamente: calculam a próxima versão SemVer, geram o CHANGELOG, criam a tag e publicam a release. Adotar a convenção destrava toda essa automação.

Seção 7

Escolhendo seu Fluxo e Resumo

Não existe fluxo "certo" universal — existe o fluxo adequado ao seu contexto. Veja como decidir.

🧭 Guia de Decisão

Perguntas para escolher o fluxo

  • Faz deploy contínuo? → GitHub Flow ou Trunk-Based
  • Mantém várias versões em suporte? → Git Flow
  • Time pequeno e ágil? → GitHub Flow
  • Tem CI/CD maduro e quer máxima velocidade? → Trunk-Based com feature flags
  • É uma biblioteca publicada? → SemVer + Conventional Commits + releases automáticas

🎯 Resumo do Módulo 06

Você conhece os principais fluxos de trabalho (GitHub Flow, Git Flow, Trunk-Based) e sabe escolher pelo contexto. Domina tags e GitHub Releases, entende Versionamento Semântico (MAJOR.MINOR.PATCH) e adota Conventional Commits para comunicação padronizada e automação de changelog/versão. Este é o vocabulário de times profissionais. No Módulo 07, automatizamos tudo isso com GitHub Actions e CI/CD.
