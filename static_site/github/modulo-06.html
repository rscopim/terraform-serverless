Fluxos Profissionais: Git Flow, Tags e Conventional Commits

Git Flow, GitHub Flow, Tags, Conventional Commits, SemVer. Estratégias de branching usadas por equipes profissionais.

1. Git Flow vs GitHub Flow

Git FlowFluxo

Modelo robusto para projetos com releases planejadas.

# Branches permanentes:
# main     → código em produção
# develop  → integração de features

# Branches temporárias:
# feature/* → novas funcionalidades
# release/* → preparação de release
# hotfix/*  → correções urgentes em produção

# Fluxo:
git checkout develop
git checkout -b feature/pagamento
# ... desenvolve ...
git checkout develop
git merge --no-ff feature/pagamento

# Release:
git checkout -b release/1.2.0 develop
# ... ajustes finais, bump version ...
git checkout main
git merge --no-ff release/1.2.0
git tag -a v1.2.0 -m "Release 1.2.0"
git checkout develop
git merge --no-ff release/1.2.0
GitHub FlowFluxo

Modelo simplificado — ideal para deploy contínuo.

# Apenas 1 branch permanente: main (sempre deployável)

# Fluxo:
# 1. Crie branch a partir de main
git checkout -b feature/dark-mode

# 2. Faça commits incrementais
git commit -m "feat: adiciona toggle de tema"
git commit -m "feat: implementa CSS dark mode"

# 3. Abra Pull Request cedo (Draft PR)
git push -u origin feature/dark-mode
# → Abra PR no GitHub

# 4. Code Review + CI passa

# 5. Merge na main (squash ou merge commit)

# 6. Deploy automático após merge

# Quando usar cada um:
# Git Flow → releases planejadas, múltiplas versões
# GitHub Flow → deploy contínuo, SaaS, projetos ágeis

2. Tags e Versionamento

git tagRelease

Marca pontos específicos no histórico (releases).

# Tag anotada (recomendada)
git tag -a v1.0.0 -m "Primeira release"

# Tag leve
git tag v1.0.0-beta

# Listar tags
git tag -l "v1.*"

# Push tags para remoto
git push origin v1.0.0
git push origin --tags    # todas

# Deletar tag
git tag -d v1.0.0
git push origin --delete v1.0.0
Conventional CommitsPadrão

Padrão de mensagens para changelog automático.

# Formato:
# tipo(escopo): descrição

feat: adiciona autenticação OAuth
feat(api): implementa endpoint /users
fix: corrige validação de email
fix(auth): token não expira corretamente
docs: atualiza README com exemplos
style: formata código com prettier
refactor: extrai lógica para service
test: adiciona testes para UserService
chore: atualiza dependências
ci: adiciona step de lint no pipeline

# Breaking change:
feat!: remove suporte a Node 14
# ou
feat: migra para ESM
BREAKING CHANGE: require() não funciona mais

3. Semantic Versioning (SemVer)

MAJOR.MINOR.PATCH — Exemplo: v2.1.3 
MAJOR (2) → Breaking changes (incompatível com anterior)
MINOR (1) → Nova funcionalidade (compatível)
PATCH (3) → Correção de bug (compatível)

Exemplos:
v1.0.0 → v1.0.1  (fix: corrige bug)
v1.0.1 → v1.1.0  (feat: nova feature)
v1.1.0 → v2.0.0  (feat!: breaking change)
