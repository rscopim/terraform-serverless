Seção 1

ping — Testando Conectividade

O comando mais fundamental de diagnóstico de rede. Verifica se um host está alcançável e mede o tempo de resposta usando o protocolo ICMP.

1.1 — O que é o ping?

O ping é uma ferramenta de diagnóstico que utiliza o protocolo ICMP (Internet Control Message Protocol) para verificar a conectividade entre dois hosts na rede. Ele funciona enviando pacotes ICMP Echo Request para o destino e aguardando pacotes ICMP Echo Reply como resposta.

O nome "ping" vem da analogia com o sonar de submarinos — um pulso é enviado e espera-se o eco de volta. Se o eco retorna, o alvo está lá. Se não retorna, algo está bloqueando a comunicação.

O ping opera na Camada 3 (Rede) do modelo OSI, o que significa que ele testa a conectividade IP sem se preocupar com portas ou serviços específicos. Um ping bem-sucedido garante que existe rota IP entre origem e destino, mas não garante que um serviço específico (como HTTP na porta 80) esteja funcionando.

💡 ICMP — O Protocolo por trás do ping

ICMP (RFC 792) é um protocolo auxiliar do IP usado para enviar mensagens de controle e erro. Além do ping (Echo Request/Reply), o ICMP é responsável por mensagens como "Destination Unreachable", "Time Exceeded" (usado pelo traceroute) e "Redirect". O ICMP não usa portas TCP/UDP — ele opera diretamente sobre o IP.

1.2 — Sintaxe Básica

📋 Sintaxe do ping

# Sintaxe geral
ping [opções] <destino>

# Exemplos básicos
ping google.com              # Ping por hostname (resolve DNS primeiro)
ping 8.8.8.8                 # Ping por IP (sem resolução DNS)
ping 192.168.1.1             # Ping no gateway local
ping localhost               # Ping em si mesmo (127.0.0.1)
ping ::1                     # Ping IPv6 loopback

1.4 — Flags Comuns do ping

📋 Flags mais utilizadas

# -c (count) — Define número de pacotes a enviar (Linux/Mac)
ping -c 4 google.com          # Envia exatamente 4 pacotes e para

# -t (Windows) — Ping contínuo até Ctrl+C
ping -t google.com             # Windows: ping infinito

# -n (Windows) — Define número de pacotes
ping -n 10 google.com          # Windows: envia 10 pacotes

# -i (interval) — Intervalo entre pacotes em segundos (Linux)
ping -i 0.2 google.com         # Envia a cada 200ms (requer root para <0.2)
ping -i 5 google.com           # Envia a cada 5 segundos (monitoramento)

# -s (size) — Tamanho do payload ICMP em bytes
ping -s 1472 google.com        # Testa MTU (1472 + 28 bytes cabeçalho = 1500 MTU)
ping -s 65507 google.com       # Payload máximo (antigo "ping of death")

# -W / -w (timeout) — Tempo máximo de espera por resposta
ping -W 2 192.168.1.100        # Linux: espera max 2 segundos por resposta
ping -w 5 192.168.1.100        # Linux: tempo total máximo de execução

# -f (flood) — Envia pacotes na velocidade máxima (requer root)
sudo ping -f -c 1000 192.168.1.1  # Stress test local (CUIDADO!)

# -I (interface) — Especifica interface de saída
ping -I eth0 8.8.8.8           # Força saída pela interface eth0

# -4 / -6 — Força IPv4 ou IPv6
ping -4 google.com             # Força resolução/ping IPv4
ping -6 google.com             # Força resolução/ping IPv6

# -D — Mostra timestamp em cada linha (Linux)
ping -D google.com             # Útil para correlacionar com logs

# -q — Modo quiet (só mostra estatísticas finais)
ping -q -c 100 google.com     # Útil em scripts

1.5 — Troubleshooting com ping

O ping é a primeira ferramenta a ser utilizada quando há suspeita de problemas de conectividade. A técnica recomendada é testar de dentro para fora (do mais próximo ao mais distante):

🔧 Metodologia de Diagnóstico com ping

# PASSO 1: Testar a interface local (loopback)
ping -c 2 127.0.0.1
# Se falhar: Stack TCP/IP do SO está com problema

# PASSO 2: Testar o gateway padrão (roteador local)
ping -c 2 192.168.1.1
# Se falhar: Problema na rede local (cabo, Wi-Fi, switch)

# PASSO 3: Testar um IP externo conhecido
ping -c 2 8.8.8.8
# Se falhar: Problema no link de Internet ou roteamento

# PASSO 4: Testar resolução DNS
ping -c 2 google.com
# Se IP funciona mas hostname falha: Problema de DNS

# PASSO 5: Testar o destino final específico
ping -c 5 meu-servidor.empresa.com
# Se falhar: Problema específico com o destino

⚠️ Cenários Comuns de Falha

# Cenário 1: Destination Host Unreachable
$ ping 192.168.1.200
From 192.168.1.1 icmp_seq=1 Destination Host Unreachable
# Significado: O roteador não encontrou o host na rede local (ARP falhou)
# Causa provável: Host desligado ou IP errado na mesma subnet

# Cenário 2: Request Timed Out (sem resposta)
$ ping 10.0.5.100
--- 10.0.5.100 ping statistics ---
5 packets transmitted, 0 received, 100% packet loss
# Significado: Pacotes enviados mas nenhuma resposta recebida
# Causas: Firewall bloqueando ICMP, host fora do ar, rota inexistente

# Cenário 3: Packet loss intermitente
$ ping -c 20 servidor.empresa.com
20 packets transmitted, 16 received, 20% packet loss
# Significado: Conexão instável — alguns pacotes se perdem
# Causas: Link congestionado, cabo danificado, interferência Wi-Fi

# Cenário 4: Latência alta/variável
64 bytes from server: icmp_seq=1 ttl=64 time=1.2 ms
64 bytes from server: icmp_seq=2 ttl=64 time=245.8 ms
64 bytes from server: icmp_seq=3 ttl=64 time=2.1 ms
64 bytes from server: icmp_seq=4 ttl=64 time=189.3 ms
# Significado: Jitter alto — latência variando muito
# Causas: Congestionamento, QoS inadequado, link saturado

# Cenário 5: TTL Exceeded
$ ping 172.16.0.50
From 10.0.0.1 icmp_seq=1 Time to live exceeded
# Significado: Loop de roteamento — pacote ficou circulando
# Causa: Configuração errada de rotas (routing loop)

⚠️ Limitações do ping

Muitos firewalls e servidores bloqueiam ICMP por política de segurança. Um ping que falha não significa necessariamente que o host está fora do ar — pode significar apenas que ICMP está bloqueado. Exemplo clássico: o Windows Firewall por padrão bloqueia ping de entrada. Servidores corporativos frequentemente desabilitam resposta a ICMP. Sempre combine ping com outras ferramentas (telnet, curl, nmap) para confirmar.

Seção 2

traceroute / tracert — Mapeando o Caminho

Descubra exatamente por quais roteadores seus pacotes passam até chegar ao destino, identificando gargalos e pontos de falha no caminho.

2.1 — Como o traceroute Funciona

O traceroute (Linux/Mac) ou tracert (Windows) é uma ferramenta que revela o caminho completo que um pacote percorre da origem até o destino, mostrando cada roteador (hop) intermediário e o tempo de resposta em cada salto.

O funcionamento é engenhoso: ele explora o campo TTL (Time To Live) do cabeçalho IP. Cada roteador que processa um pacote decrementa o TTL em 1. Quando o TTL chega a 0, o roteador descarta o pacote e envia uma mensagem ICMP Time Exceeded de volta à origem, revelando sua identidade (IP).

🔧 Mecanismo do traceroute — Passo a Passo

# O traceroute envia pacotes com TTL incrementalmente crescente:

Pacote 1: TTL=1
  → Chega ao 1° roteador → TTL decrementado para 0
  → Roteador 1 descarta e envia "ICMP Time Exceeded" → Revelado!

Pacote 2: TTL=2
  → Passa pelo 1° roteador (TTL=1) → Chega ao 2° roteador → TTL=0
  → Roteador 2 descarta e envia "ICMP Time Exceeded" → Revelado!

Pacote 3: TTL=3
  → Passa pelo 1° (TTL=2) → 2° (TTL=1) → Chega ao 3° → TTL=0
  → Roteador 3 descarta e envia "ICMP Time Exceeded" → Revelado!

  ... continua até o destino final responder ...

Pacote N: TTL=N (suficiente para alcançar o destino)
  → Destino recebe o pacote e responde normalmente
  → Traceroute completo!

# Diagrama:
Origem ──[TTL=1]──▶ R1 ──✗ (Time Exceeded → revela R1)
Origem ──[TTL=2]──▶ R1 ──▶ R2 ──✗ (Time Exceeded → revela R2)
Origem ──[TTL=3]──▶ R1 ──▶ R2 ──▶ R3 ──✗ (Time Exceeded → revela R3)
Origem ──[TTL=4]──▶ R1 ──▶ R2 ──▶ R3 ──▶ Destino ✓ (ICMP Echo Reply)

💡 Diferenças entre Implementações

Linux traceroute: Por padrão usa pacotes UDP em portas altas (33434+). Pode ser configurado para usar ICMP (-I) ou TCP (-T).
Windows tracert: Usa ICMP Echo Request (como o ping).
Implicação: Se um firewall bloqueia UDP mas permite ICMP, o traceroute do Linux pode falhar enquanto o tracert do Windows funciona. Use traceroute -I no Linux para comportamento similar ao Windows.

2.3 — Flags e Variações do traceroute

📋 Opções comuns do traceroute

# Linux — traceroute
traceroute google.com              # Padrão: UDP probes
traceroute -I google.com           # Usar ICMP (como tracert do Windows)
traceroute -T google.com           # Usar TCP SYN (atravessa mais firewalls)
traceroute -T -p 443 google.com   # TCP na porta 443 (HTTPS)
traceroute -n google.com           # Não resolver DNS (mais rápido)
traceroute -m 20 google.com       # Máximo de 20 hops (padrão: 30)
traceroute -w 3 google.com        # Timeout de 3 segundos por probe
traceroute -q 1 google.com        # Apenas 1 probe por hop (mais rápido)

# Windows — tracert
tracert google.com                 # Padrão: ICMP
tracert -d google.com              # Não resolver DNS
tracert -h 20 google.com          # Máximo de 20 hops
tracert -w 2000 google.com        # Timeout de 2000ms por probe

# mtr — Ferramenta moderna que combina ping + traceroute
mtr google.com                     # Interface interativa em tempo real
mtr -r -c 100 google.com         # Relatório após 100 ciclos
mtr --tcp -P 443 google.com      # Usar TCP porta 443
mtr -n google.com                  # Sem resolução DNS

⚠️ Cuidado ao Interpretar Perda em Hops Intermediários

Muitos roteadores dão baixa prioridade para responder ICMP Time Exceeded (rate limiting). Isso pode mostrar "perda" em um hop intermediário que na verdade está funcionando perfeitamente. A regra de ouro: se a perda não continua nos hops seguintes, provavelmente é rate limiting e não perda real. Só considere um problema real se a perda persistir em todos os hops subsequentes.

2.4 — Encontrando Gargalos

O traceroute é essencial para identificar onde um problema de rede está ocorrendo. Aqui estão as técnicas para encontrar gargalos:

🎯 Sinais de Gargalo

1. Salto de latência que persiste — aumento de 10ms para 150ms que continua alto em todos os hops seguintes

2. Perda de pacotes que persiste — se hop 5 tem 20% de perda E hops 6-8 também, o problema é no hop 5

3. Jitter alto (StDev grande) — indica congestionamento/saturação naquele link

4. Timeouts completos a partir de um ponto — indica bloqueio ou falha

🎯 Falsos Positivos

1. Perda em um hop que não se repete depois — rate limiting, ignorar

2. Latência alta em um hop mas baixa no seguinte — roteador lento para responder ICMP, não é gargalo real

3. Asteriscos isolados — roteador configurado para não responder, tráfego passa normalmente

4. Salto geográfico (SP→NY) — latência é física, não é "problema"

Seção 3

nslookup / dig — Consultas DNS

Ferramentas para consultar o Sistema de Nomes de Domínio (DNS), resolver hostnames para IPs e diagnosticar problemas de resolução de nomes.

3.1 — O que são nslookup e dig?

O DNS (Domain Name System) é o "catálogo telefônico" da Internet — traduz nomes legíveis (como google.com) para endereços IP (como 142.250.79.46). Quando a resolução DNS falha, nenhum serviço baseado em nome funciona, mesmo que a rede IP esteja perfeita.

nslookup (Name Server Lookup) é uma ferramenta disponível em todos os SOs (Windows, Linux, Mac). É mais simples e interativa, ideal para consultas rápidas.

dig (Domain Information Groper) é a ferramenta preferida por profissionais em ambientes Linux/Unix. Oferece saída mais detalhada e completa, com informações sobre autoridade, tempo de resposta, e flags do protocolo DNS.

💡 nslookup vs dig — Qual Usar?

nslookup: Use para consultas rápidas e simples, especialmente em Windows. Está sendo gradualmente substituído pelo dig em ambientes profissionais.
dig: Use para diagnósticos detalhados, scripts de automação e quando precisa de informações completas sobre a resposta DNS (flags, seções authority/additional, TTL dos registros). É a ferramenta padrão para administradores DNS.

3.5 — Troubleshooting DNS

🔧 Diagnóstico de Problemas DNS

# Problema: "Site não abre" — Primeiro verificar se é DNS
$ ping meusite.com.br
ping: meusite.com.br: Name or service not known
# ↑ DNS não resolveu! Vamos investigar:

# 1. Verificar se o DNS configurado está respondendo
$ dig @192.168.1.1 google.com +short
142.250.79.46
# ✓ DNS local funciona para outros domínios

# 2. Consultar o domínio problemático
$ dig meusite.com.br
;; ->>HEADER<<- opcode: QUERY, status: NXDOMAIN
# ↑ NXDOMAIN = domínio não existe (expirou? erro de digitação?)

# 3. Testar com DNS público (eliminar problema no DNS local)
$ dig @8.8.8.8 meusite.com.br
# Se funciona no 8.8.8.8 mas não no local: problema no DNS local/cache

# 4. Verificar propagação (domínio recém-criado/alterado)
$ dig +short @8.8.8.8 novo-site.com.br
$ dig +short @1.1.1.1 novo-site.com.br
# Se resultados diferentes: propagação DNS ainda em andamento (até 48h)

# 5. Verificar TTL restante de um registro
$ dig google.com | grep -A1 "ANSWER SECTION"
google.com.             241     IN      A       142.250.79.46
#                       ↑ TTL=241 segundos até o cache expirar

# 6. Flush do cache DNS local
# Windows:
ipconfig /flushdns

# Linux (systemd-resolved):
sudo systemd-resolve --flush-caches

# macOS:
sudo dscacheutil -flushcache; sudo killall -HUP mDNSResponder

⚠️ "Non-authoritative answer" — O que significa?

Quando você vê "Non-authoritative answer" no nslookup (ou sem flag aa no dig), significa que a resposta veio de um cache DNS e não diretamente do servidor autoritativo do domínio. Isso é normal e esperado — o sistema DNS depende de cache para funcionar em escala. Uma resposta "authoritative" viria diretamente do NS do domínio (ex: ns1.google.com para google.com).

Seção 4

netstat / ss — Conexões e Portas

Ferramentas para listar conexões de rede ativas, portas em escuta e identificar quais processos estão usando cada porta. Essenciais para segurança e troubleshooting de serviços.

4.1 — netstat vs ss

O netstat (Network Statistics) é a ferramenta clássica presente em todos os sistemas operacionais há décadas. Mostra conexões de rede, tabelas de roteamento, estatísticas de interface e muito mais.

O ss (Socket Statistics) é o substituto moderno do netstat em sistemas Linux. É significativamente mais rápido (especialmente em servidores com milhares de conexões) e fornece informações mais detalhadas sobre o estado dos sockets. Em distribuições Linux modernas, o ss é preferido — o netstat faz parte do pacote net-tools que está sendo descontinuado.

📊 netstat — Vantagens

• Disponível em todos os SOs (Windows, Linux, Mac)

• Interface familiar e bem documentada

• Flags similares entre plataformas

• Mostra rotas e estatísticas de interface

📊 ss — Vantagens

• Muito mais rápido (usa netlink ao invés de /proc)

• Mostra mais informações (timers, memória, etc.)

• Filtros avançados embutidos

• Ativamente mantido (netstat está depreciado)

4.2 — Estados de Conexão TCP

Para interpretar a saída do netstat/ss, é essencial entender os estados TCP:

📋 Estados TCP e seus Significados

# Estados TCP principais que você verá no netstat/ss:

LISTEN        → Porta aberta aguardando conexões (servidor pronto)
ESTABLISHED   → Conexão ativa e transmitindo dados
SYN_SENT      → Cliente enviou SYN, aguardando SYN-ACK (tentando conectar)
SYN_RECV      → Servidor recebeu SYN, enviou SYN-ACK, aguardando ACK final
TIME_WAIT     → Conexão fechada, aguardando pacotes retardatários (normal!)
CLOSE_WAIT    → Lado remoto fechou, aguardando aplicação local fechar
FIN_WAIT1     → Aplicação local iniciou fechamento, enviou FIN
FIN_WAIT2     → Recebeu ACK do FIN, aguardando FIN do remoto
CLOSING       → Ambos os lados enviaram FIN simultaneamente
LAST_ACK      → Aguardando ACK final antes de liberar o socket

# Diagrama simplificado do ciclo de vida TCP:
#
# Cliente                          Servidor
#    │                                │
#    │──── SYN ────────────────▶│     │  (SYN_SENT)
#    │                          │     │  (SYN_RECV)
#    │◀─── SYN-ACK ────────────│     │
#    │                                │
#    │──── ACK ────────────────▶│     │  (ESTABLISHED)
#    │                                │
#    │◀════ Dados ════════════▶│     │  (ESTABLISHED)
#    │                                │
#    │──── FIN ────────────────▶│     │  (FIN_WAIT1 → FIN_WAIT2)
#    │◀─── ACK ────────────────│     │  (CLOSE_WAIT)
#    │◀─── FIN ────────────────│     │  (LAST_ACK)
#    │──── ACK ────────────────▶│     │  (TIME_WAIT → CLOSED)
#    │                                │  (CLOSED)

💡 TIME_WAIT — Não é um Problema!

Ver muitas conexões em TIME_WAIT é normal em servidores web ocupados. O TIME_WAIT dura 2×MSL (Maximum Segment Lifetime, geralmente 60 segundos) e serve para garantir que pacotes retardatários não confundam novas conexões. Só é problema se esgotar as portas efêmeras disponíveis (65535 - portas reservadas ≈ 28000 portas disponíveis).

Visualize e gerencie interfaces de rede, endereços IP, endereços MAC, MTU e estado das interfaces. O ip é o comando moderno que substituiu o ifconfig.

5.1 — ifconfig vs ip — A Transição

O ifconfig (interface configuration) é o comando clássico Unix/Linux para configurar interfaces de rede. Assim como o netstat, faz parte do pacote net-tools que está sendo descontinuado em distribuições Linux modernas.

O ip (do pacote iproute2) é o substituto moderno, mais poderoso e consistente. Ele agrupa funcionalidades que antes estavam espalhadas em vários comandos (ifconfig, route, arp, netstat) em um único utilitário.

Tarefa ifconfig (legado) ip (moderno)
Ver interfaces ifconfig ip addr show ou ip a
Ver interface específica ifconfig eth0 ip addr show dev eth0
Atribuir IP ifconfig eth0 192.168.1.10/24 ip addr add 192.168.1.10/24 dev eth0
Remover IP ifconfig eth0 0.0.0.0 ip addr del 192.168.1.10/24 dev eth0
Ativar interface ifconfig eth0 up ip link set eth0 up
Desativar interface ifconfig eth0 down ip link set eth0 down
Ver tabela de rotas route -n ip route show ou ip r
Adicionar rota route add -net 10.0.0.0/8 gw 192.168.1.1 ip route add 10.0.0.0/8 via 192.168.1.1
Ver tabela ARP arp -a ip neigh show ou ip n
Alterar MTU ifconfig eth0 mtu 9000 ip link set eth0 mtu 9000

Seção 6

nmap — Scanner de Rede

A ferramenta definitiva para descoberta de hosts, varredura de portas e auditoria de segurança. Poderosa e versátil, é indispensável para profissionais de segurança e administradores de rede.

6.1 — O que é o nmap?

O nmap (Network Mapper) é um scanner de rede open-source criado por Gordon "Fyodor" Lyon. É a ferramenta mais popular do mundo para:

🎯 Capacidades do nmap

• Descoberta de hosts: Quais máquinas estão online na rede

• Varredura de portas: Quais serviços estão rodando em cada host

• Detecção de versão: Qual software e versão em cada porta

• Detecção de SO: Identifica o sistema operacional remoto

• Scripts NSE: Automação de testes de segurança específicos

⚖️ Aspectos Legais e Éticos

• Redes próprias: Totalmente legal e recomendado

• Com autorização: Legal (pentest contratado com escopo definido)

• Sem autorização: ILEGAL em muitas jurisdições (invasão de privacidade)

• Em produção: Cuidado — scans agressivos podem derrubar serviços frágeis

• Regra de ouro: Só escaneie o que você tem permissão para escanear

6.3 — Varredura de Portas

📋 Tipos de Scan e Exemplos

# ═══════════════════════════════════════════════════
# SCANS BÁSICOS
# ═══════════════════════════════════════════════════

# Scan padrão (top 1000 portas TCP)
$ nmap 192.168.1.50
PORT     STATE SERVICE
22/tcp   open  ssh
80/tcp   open  http
443/tcp  open  https
3306/tcp open  mysql

# Scan de todas as 65535 portas TCP
$ nmap -p- 192.168.1.50

# Scan de portas específicas
$ nmap -p 22,80,443,8080 192.168.1.50

# Scan de range de portas
$ nmap -p 1-1024 192.168.1.50

# Scan de portas UDP (mais lento — UDP não confirma recebimento)
$ nmap -sU 192.168.1.50

# Scan TCP + UDP combinado
$ nmap -sS -sU -p T:22,80,443,U:53,161 192.168.1.50

# ═══════════════════════════════════════════════════
# TÉCNICAS DE SCAN (-s)
# ═══════════════════════════════════════════════════

# -sS (SYN Scan — "Half-open") — O mais comum e discreto
$ sudo nmap -sS 192.168.1.50
# Envia SYN, recebe SYN-ACK (porta aberta) ou RST (fechada)
# Não completa o handshake → mais difícil de detectar em logs
# Requer root/admin (raw sockets)

# -sT (TCP Connect) — Completa o handshake
$ nmap -sT 192.168.1.50
# Mais lento e mais visível, mas não requer root
# Aparece nos logs do servidor como conexão completa

# -sV (Version Detection) — Identifica serviço e versão
$ nmap -sV 192.168.1.50
PORT     STATE SERVICE  VERSION
22/tcp   open  ssh      OpenSSH 8.9p1 Ubuntu 3ubuntu0.4
80/tcp   open  http     nginx 1.24.0
443/tcp  open  ssl/http nginx 1.24.0
3306/tcp open  mysql    MySQL 8.0.35

# -O (OS Detection) — Identifica sistema operacional
$ sudo nmap -O 192.168.1.50
Running: Linux 5.X
OS details: Linux 5.15 - 5.19
Network Distance: 1 hop

# Scan agressivo (OS + Version + Scripts + Traceroute)
$ sudo nmap -A 192.168.1.50

# ═══════════════════════════════════════════════════
# ESTADOS DE PORTA NO NMAP
# ═══════════════════════════════════════════════════
# open     → Porta aceitando conexões (serviço ativo)
# closed   → Porta acessível mas sem serviço (responde RST)
# filtered → Firewall bloqueando (sem resposta ou ICMP unreachable)
# open|filtered → Não foi possível determinar (comum em UDP scan)

6.4 — Scans Comuns no Dia a Dia

🔧 Receitas Práticas com nmap

# Auditoria rápida de um servidor (o que está exposto?)
$ sudo nmap -sS -sV -O --top-ports 100 192.168.1.50

# Verificar se uma porta específica está aberta (rápido)
$ nmap -p 443 --open 192.168.1.50
PORT    STATE SERVICE
443/tcp open  https

# Encontrar todos os servidores web na rede
$ nmap -sS -p 80,443,8080,8443 --open 192.168.1.0/24

# Encontrar todos os servidores SSH na rede
$ nmap -sS -p 22 --open 10.0.0.0/24

# Scan silencioso (evasão básica de IDS)
$ sudo nmap -sS -T2 --randomize-hosts 192.168.1.0/24
# -T2 = velocidade "polite" (mais lento, menos detectável)
# Escala: -T0 (paranoid) → -T5 (insane)

# Salvar resultado em arquivo
$ nmap -sV -oN resultado.txt 192.168.1.50      # Formato normal
$ nmap -sV -oX resultado.xml 192.168.1.50      # Formato XML
$ nmap -sV -oA resultado 192.168.1.50          # Todos os formatos

# Scan de vulnerabilidades com scripts NSE
$ nmap --script vuln 192.168.1.50
$ nmap --script ssl-heartbleed -p 443 192.168.1.50
$ nmap --script http-title -p 80,443 192.168.1.0/24

⚠️ Implicações de Segurança do nmap

O nmap é uma faca de dois gumes: é essencial para administradores verificarem a segurança de suas redes, mas também é a primeira ferramenta que um atacante usaria para reconhecimento. Implicações: (1) Sistemas IDS/IPS podem alertar ou bloquear scans; (2) Muitos provedores cloud (AWS, Azure) exigem autorização prévia para realizar scans; (3) Portas abertas desnecessárias devem ser fechadas imediatamente após descoberta; (4) Atualize serviços cuja versão apresente vulnerabilidades conhecidas (CVEs).

Seção 7

tcpdump / Wireshark — Captura de Pacotes

As ferramentas definitivas para análise profunda de tráfego de rede. Quando todos os outros comandos não bastam, a captura de pacotes revela exatamente o que está acontecendo no fio.

7.1 — tcpdump vs Wireshark — Quando Usar Cada Um

A captura de pacotes (packet capture/sniffing) é o nível mais profundo de diagnóstico de rede. Permite ver cada byte que trafega na interface, incluindo cabeçalhos de protocolos, payloads e timing preciso.

🖥️ tcpdump

Tipo: Linha de comando (CLI)

Onde: Linux/Mac (nativamente), Windows (via WinDump/Npcap)

Quando usar:

• Servidores sem interface gráfica (SSH)

• Captura rápida em produção

• Scripts automatizados

• Capturar e salvar para análise posterior

• Ambientes de container/Kubernetes

🦈 Wireshark

Tipo: Interface gráfica (GUI)

Onde: Windows, Linux, Mac

Quando usar:

• Análise detalhada de protocolos

• Visualização de conversações (follow stream)

• Decodificação complexa (TLS, HTTP/2, gRPC)

• Ensino e aprendizado de protocolos

• Análise forense de tráfego

💡 Fluxo de Trabalho Profissional

O workflow mais comum em produção: (1) Capturar com tcpdump no servidor remoto via SSH, salvando em arquivo .pcap; (2) Transferir o arquivo para sua estação de trabalho; (3) Analisar com Wireshark usando toda a riqueza da interface gráfica. Isso combina o melhor dos dois mundos — captura leve em produção e análise detalhada no desktop.

7.2 — tcpdump — Captura via Linha de Comando

📋 Sintaxe e Exemplos do tcpdump

# Sintaxe geral:
# tcpdump [opções] [expressão de filtro]

# ═══════════════════════════════════════════════════
# CAPTURAS BÁSICAS
# ═══════════════════════════════════════════════════

# Capturar todo o tráfego na interface padrão
$ sudo tcpdump
# Ctrl+C para parar

# Capturar em interface específica
$ sudo tcpdump -i eth0
$ sudo tcpdump -i any          # Todas as interfaces

# Limitar número de pacotes capturados
$ sudo tcpdump -c 100          # Captura 100 pacotes e para

# Não resolver DNS (mais rápido, IPs puros)
$ sudo tcpdump -n

# Mostrar conteúdo do pacote em hex e ASCII
$ sudo tcpdump -X

# Verbose (mais detalhes nos cabeçalhos)
$ sudo tcpdump -v              # Verbose
$ sudo tcpdump -vv             # Muito verbose
$ sudo tcpdump -vvv            # Máximo detalhe

# ═══════════════════════════════════════════════════
# FILTROS POR HOST
# ═══════════════════════════════════════════════════

# Tráfego de/para um host específico
$ sudo tcpdump host 192.168.1.50

# Apenas tráfego ORIGINADO do host
$ sudo tcpdump src host 192.168.1.50

# Apenas tráfego DESTINADO ao host
$ sudo tcpdump dst host 192.168.1.50

# Tráfego entre dois hosts específicos
$ sudo tcpdump host 192.168.1.10 and host 192.168.1.50

# ═══════════════════════════════════════════════════
# FILTROS POR PORTA
# ═══════════════════════════════════════════════════

# Tráfego na porta 80 (HTTP)
$ sudo tcpdump port 80

# Tráfego na porta 443 (HTTPS)
$ sudo tcpdump port 443

# Múltiplas portas
$ sudo tcpdump port 80 or port 443

# Range de portas
$ sudo tcpdump portrange 8000-9000

# Porta de destino específica
$ sudo tcpdump dst port 3306       # Conexões ao MySQL

# ═══════════════════════════════════════════════════
# FILTROS POR PROTOCOLO
# ═══════════════════════════════════════════════════

# Apenas tráfego TCP
$ sudo tcpdump tcp

# Apenas tráfego UDP
$ sudo tcpdump udp

# Apenas tráfego ICMP (ping)
$ sudo tcpdump icmp

# Apenas tráfego ARP
$ sudo tcpdump arp

# Apenas pacotes DNS (porta 53)
$ sudo tcpdump port 53

# ═══════════════════════════════════════════════════
# FILTROS COMBINADOS
# ═══════════════════════════════════════════════════

# TCP na porta 80 de/para um host

$ sudo tcpdump 'tcp[tcpflags] == tcp-syn'

# Pacotes RST (conexões rejeitadas/resetadas)
$ sudo tcpdump 'tcp[tcpflags] & (tcp-rst) != 0'

7.3 — Salvando e Lendo Capturas

📋 Trabalhando com Arquivos .pcap

# Salvar captura em arquivo .pcap (para análise posterior no Wireshark)
$ sudo tcpdump -i eth0 -w captura.pcap

# Salvar com limite de tamanho (rotação de arquivo)
$ sudo tcpdump -i eth0 -w captura.pcap -C 100
# -C 100 = cria novo arquivo a cada 100MB (captura.pcap, captura.pcap1, etc.)

# Salvar com limite de tempo
$ sudo tcpdump -i eth0 -w captura.pcap -G 3600 -W 24
# -G 3600 = novo arquivo a cada hora
# -W 24 = máximo 24 arquivos (24 horas de captura)

# Ler arquivo .pcap salvo
$ tcpdump -r captura.pcap

# Ler com filtro (analisar apenas parte da captura)
$ tcpdump -r captura.pcap port 443
$ tcpdump -r captura.pcap host 10.0.0.5

# Ler mostrando timestamps legíveis
$ tcpdump -r captura.pcap -tttt

# Captura em produção (receita recomendada):
$ sudo tcpdump -i eth0 -n -s 0 -w /tmp/debug-$(date +%Y%m%d-%H%M%S).pcap \
    port 443 and host 10.0.0.5 -c 10000
# -n = sem DNS
# -s 0 = capturar pacote completo (não truncar)
# -c 10000 = parar após 10000 pacotes
# Depois: scp /tmp/debug-*.pcap usuario@desktop:/tmp/

$ sudo tcpdump -n -c 3 tcp and port 80 and host 192.168.1.50

    Content-Length: 1234

⚠️ Captura de Pacotes e Privacidade

A captura de pacotes pode expor informações sensíveis: credenciais em protocolos não criptografados (HTTP, FTP, Telnet, SMTP sem TLS), tokens de API, cookies de sessão, dados pessoais. Regras importantes: (1) Capture apenas o necessário para o diagnóstico; (2) Delete capturas após a análise; (3) Nunca capture em redes que você não administra sem autorização; (4) Em redes com HTTPS, o payload é criptografado (você verá apenas os cabeçalhos TCP/TLS); (5) Informe a equipe quando realizar capturas em produção.

Exercício 1 — Servidor Web Inacessível

📋 Cenário

# SITUAÇÃO:
# Você é administrador de rede e recebe um chamado:
# "O site interno da empresa (intranet.empresa.local) não está abrindo!"
#
# Informações disponíveis:
# - Servidor web: 10.0.1.50 (porta 80 e 443)
# - DNS interno: 10.0.1.10
# - Gateway da sua rede: 192.168.1.1
# - Seu IP: 192.168.1.100
#
# TAREFA: Use os comandos de diagnóstico para identificar o problema.
# Siga a metodologia "de dentro para fora".

✅ Solução — Passo a Passo

# PASSO 1: Verificar conectividade básica (stack TCP/IP local)
$ ping -c 2 127.0.0.1
PING 127.0.0.1: 2 packets transmitted, 2 received, 0% packet loss
# ✓ Stack local OK

# PASSO 2: Verificar gateway
$ ping -c 2 192.168.1.1
PING 192.168.1.1: 2 packets transmitted, 2 received, 0% packet loss
# ✓ Rede local OK, gateway acessível

# PASSO 3: Verificar se o servidor responde por IP
$ ping -c 4 10.0.1.50
PING 10.0.1.50: 4 packets transmitted, 4 received, 0% packet loss
# ✓ Servidor está online e acessível por IP

# PASSO 4: Verificar resolução DNS
$ nslookup intranet.empresa.local 10.0.1.10
Server:     10.0.1.10
Address:    10.0.1.10#53

** server can't find intranet.empresa.local: NXDOMAIN
# ✗ DNS NÃO RESOLVE o nome! Esse é o problema!

# PASSO 5: Confirmar que o serviço web está rodando
$ nmap -p 80,443 10.0.1.50
PORT    STATE SERVICE
80/tcp  open  http
443/tcp open  https
# ✓ Serviço web está rodando

# DIAGNÓSTICO FINAL:
# O servidor web está online e funcionando (porta 80/443 aberta).
# O problema é DNS — o registro "intranet.empresa.local" não existe
# no servidor DNS 10.0.1.10.
#
# SOLUÇÃO: Criar/corrigir o registro A no servidor DNS:
# intranet.empresa.local → 10.0.1.50
#
# WORKAROUND IMEDIATO: Usuário pode acessar por IP: http://10.0.1.50

Exercício 2 — Latência Alta em Aplicação

📋 Cenário

# SITUAÇÃO:
# Usuários reclamam que o sistema ERP (erp.empresa.com) está
# "muito lento" desde ontem. O servidor está em um data center
# externo (IP: 203.0.113.50).
#
# Informações:
# - ERP Server: 203.0.113.50 (porta 8443)

Exercício 3 — Porta Misteriosa Aberta

📋 Cenário

# SITUAÇÃO:
# Durante uma auditoria de segurança de rotina, você precisa verificar
# quais portas estão abertas no servidor de produção (192.168.1.50)
# e identificar um serviço suspeito rodando em uma porta não-padrão.
#
# O servidor deveria ter APENAS:
# - SSH (22)
# - HTTP (80)
# - HTTPS (443)
# - PostgreSQL (5432) — apenas local (127.0.0.1)
#
# TAREFA: Identifique portas abertas indevidas e o processo responsável.

✅ Solução — Passo a Passo

# PASSO 1: Scan completo do servidor (da sua máquina)
$ sudo nmap -sS -sV -p- 192.168.1.50
PORT      STATE SERVICE    VERSION
22/tcp    open  ssh        OpenSSH 8.9p1 Ubuntu 3ubuntu0.4
80/tcp    open  http       nginx 1.24.0
443/tcp   open  ssl/http   nginx 1.24.0
4444/tcp  open  krb524?                    ← SUSPEITO!
5432/tcp  open  postgresql PostgreSQL 15.4

# PROBLEMAS DETECTADOS:
# 1. Porta 4444 aberta — NÃO está na lista de serviços autorizados!
# 2. PostgreSQL (5432) acessível externamente — deveria ser só 127.0.0.1!

# PASSO 2: No servidor — identificar o processo na porta 4444
$ ss -tlnp | grep :4444
tcp  LISTEN  0  5  0.0.0.0:4444  0.0.0.0:*  users:(("nc",pid=31337,fd=4))
# → netcat (nc) rodando como listener na porta 4444!
# PID 31337 — número de "elite" frequentemente associado a backdoors

# PASSO 3: Investigar o processo suspeito
$ ps aux | grep 31337
nobody  31337  0.0  0.1  2000  500 ?  S  Jan10  0:00  nc -lvp 4444 -e /bin/bash
# CRÍTICO! É um netcat com shell reverso — BACKDOOR CONFIRMADO!
# -l = listen, -v = verbose, -p 4444 = porta, -e /bin/bash = executa shell

# PASSO 4: Verificar PostgreSQL escutando em interface errada
$ ss -tlnp | grep :5432
tcp  LISTEN  0  128  0.0.0.0:5432  0.0.0.0:*  users:(("postgres",pid=1234,fd=6))
# Escutando em 0.0.0.0 (todas interfaces) — deveria ser 127.0.0.1!

# AÇÕES IMEDIATAS:
# 1. Matar o backdoor:
$ sudo kill -9 31337

# 2. Bloquear porta 4444 no firewall:
$ sudo iptables -A INPUT -p tcp --dport 4444 -j DROP

# 3. Corrigir PostgreSQL (/etc/postgresql/15/main/postgresql.conf):
#    listen_addresses = 'localhost'    # Era '*'
$ sudo systemctl restart postgresql

# 4. Investigar como o backdoor foi instalado:
$ last                            # Últimos logins
$ cat /var/log/auth.log | grep "Accepted"  # Logins SSH
$ find / -newer /etc/passwd -name "*.sh"   # Scripts recentes

# 5. Notificar equipe de segurança para incident response completo

Exercício 4 — Problema de Comunicação entre Containers

📋 Cenário

# SITUAÇÃO:
# Você tem uma aplicação em Docker Compose com 3 containers:
# - frontend (nginx) na porta 3000
# - backend (Node.js API) na porta 8080
# - database (PostgreSQL) na porta 5432
#
# O frontend consegue acessar o backend, mas o backend NÃO consegue
# conectar ao database. Erro: "Connection refused to db:5432"
#
# Docker network: app-network (bridge)
# Nomes dos containers: app-frontend, app-backend, app-database
#
# TAREFA: Diagnostique o problema de comunicação entre containers.

✅ Solução — Passo a Passo

# PASSO 1: Verificar se todos os containers estão rodando
$ docker ps
CONTAINER ID  IMAGE    COMMAND               STATUS          PORTS         NAMES
a1b2c3d4e5f6  nginx    "nginx -g..."         Up 5 minutes    0.0.0.0:3000→80  app-frontend
f6e5d4c3b2a1  node     "node server.js"      Up 5 minutes    8080/tcp      app-backend
1a2b3c4d5e6f  postgres "docker-entrypoint…"  Up 2 minutes    5432/tcp      app-database

# ✓ Todos rodando

# PASSO 2: Verificar se os containers estão na mesma rede
$ docker network inspect app-network | grep -A 3 "Containers"
# Verificar se app-database está listado na rede

# PASSO 3: Testar DNS interno do Docker (de dentro do backend)
$ docker exec app-backend nslookup app-database
Server:    127.0.0.11
Address:   127.0.0.11#53

Name:   app-database
Address: 172.18.0.4
# ✓ DNS resolve corretamente

# PASSO 4: Testar conectividade IP (ping)
$ docker exec app-backend ping -c 3 app-database
PING app-database (172.18.0.4): 3 packets transmitted, 3 received, 0% loss
# ✓ Conectividade IP OK

# PASSO 5: Testar se a porta 5432 está acessível
$ docker exec app-backend sh -c 'nc -zv app-database 5432'
app-database (172.18.0.4:5432): Connection refused
# ✗ A porta está RECUSANDO conexão!

# PASSO 6: Verificar se PostgreSQL está escutando dentro do container
$ docker exec app-database ss -tlnp | grep 5432
tcp  LISTEN  0  128  127.0.0.1:5432  0.0.0.0:*  users:(("postgres",pid=1,fd=3))
# ← ENCONTRADO! PostgreSQL escutando apenas em 127.0.0.1 (localhost)!
# Precisa escutar em 0.0.0.0 para aceitar conexões de outros containers

# DIAGNÓSTICO FINAL:
# O PostgreSQL está configurado para aceitar conexões apenas de localhost
# (127.0.0.1), mas o backend está em outro container (outro IP: 172.18.0.x).
# 
# SOLUÇÃO: No docker-compose.yml ou postgresql.conf:
#
# Opção A — docker-compose.yml (variável de ambiente):
#   environment:
#     - POSTGRES_HOST_AUTH_METHOD=md5
#   command: ["postgres", "-c", "listen_addresses=*"]
#
# Opção B — postgresql.conf dentro do container:
#   listen_addresses = '*'
#
# E em pg_hba.conf, adicionar:
#   host  all  all  172.18.0.0/16  md5
#
# Após alteração:
$ docker restart app-database

# VERIFICAÇÃO:
$ docker exec app-backend sh -c 'nc -zv app-database 5432'
app-database (172.18.0.4:5432): Connection succeeded!
# ✓ Problema resolvido!
