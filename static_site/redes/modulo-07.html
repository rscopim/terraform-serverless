Seção 1

Fundamentos de Segurança de Redes

Compreenda os conceitos fundamentais que sustentam toda a disciplina de segurança de redes: a tríade CIA, defesa em profundidade, panorama de ameaças, vetores de ataque comuns e os frameworks de políticas de segurança que orientam decisões técnicas.

1.1 — A Tríade CIA (Confidencialidade, Integridade e Disponibilidade)

A Tríade CIA é o modelo fundamental que orienta toda política e implementação de segurança da informação. Cada decisão de segurança deve equilibrar estes três pilares:

🔒 Confidencialidade (Confidentiality)

Garantir que a informação seja acessível apenas para aqueles autorizados a visualizá-la. Em redes, isso se traduz em:

  • Criptografia de dados em trânsito (TLS, IPSec, SSH)
  • Controle de acesso (ACLs, firewalls, autenticação)
  • Segmentação de rede (VLANs, sub-redes isoladas)
  • VPNs para comunicação privada sobre redes públicas
  • Classificação de dados e need-to-know

Ameaças típicas: Sniffing, Man-in-the-Middle, acesso não autorizado, shoulder surfing, engenharia social.

✅ Integridade (Integrity)

Garantir que a informação não seja alterada de forma não autorizada durante transmissão ou armazenamento. Em redes:

  • Hashing (SHA-256, MD5) para verificação de integridade
  • Assinaturas digitais para autenticação de origem
  • Protocolos seguros (HTTPS, SFTP, SNMPv3)
  • Checksums em cabeçalhos de protocolos (TCP, IP)
  • Controle de versão e auditoria de mudanças

Ameaças típicas: Modificação em trânsito, injeção de pacotes, DNS poisoning, ARP spoofing.

🟢 Disponibilidade (Availability)

Garantir que sistemas e dados estejam acessíveis quando necessário por usuários autorizados. Em infraestrutura de redes, disponibilidade significa:

  • Redundância: Links duplos, HSRP/VRRP, clusters de firewalls, múltiplos ISPs
  • Resiliência: STP (previne loops), OSPF (reconvergência rápida), load balancing
  • Proteção contra DoS/DDoS: Rate limiting, scrubbing centers, CDNs
  • Backup e recuperação: Configurações de backup, failover automático
  • Monitoramento: SNMP, NetFlow, alertas de indisponibilidade
  • Capacity planning: Dimensionamento adequado para picos de tráfego

Ameaças típicas: DDoS, falha de hardware, desastres naturais, ataques de ransomware, misconfiguration.

💡 Equilíbrio da Tríade CIA

Na prática, os três pilares frequentemente entram em conflito. Exemplo: criptografar absolutamente tudo (alta confidencialidade) pode impactar a performance e a disponibilidade. Um sistema extremamente restritivo (alta integridade) pode dificultar o acesso legítimo. O papel do profissional de segurança é encontrar o equilíbrio adequado para cada contexto de negócio, considerando o apetite de risco da organização.

1.2 — Defesa em Profundidade (Defense in Depth)

A defesa em profundidade é uma estratégia de segurança que implementa múltiplas camadas de proteção, de modo que se uma camada for comprometida, as demais continuam protegendo os ativos. Inspirada em táticas militares, essa abordagem reconhece que nenhuma medida isolada é infalível.

Princípios-chave da defesa em profundidade:

  • Diversidade de mecanismos: Use tecnologias diferentes em cada camada (não apenas firewalls de um mesmo fabricante)
  • Redundância: Se uma camada falhar, a próxima deve ser capaz de detectar e bloquear a ameaça
  • Princípio do menor privilégio: Cada componente tem acesso apenas ao mínimo necessário
  • Monitoramento contínuo: Visibilidade em todas as camadas para detecção rápida
  • Resposta a incidentes: Planos documentados para cada cenário de comprometimento

1.3 — Panorama de Ameaças (Threat Landscape)

O cenário de ameaças evolui constantemente. Profissionais de segurança de redes devem compreender os principais atores de ameaça e suas motivações:

Ator de Ameaça Motivação Recursos Exemplos de Ataques
Script Kiddies Diversão, notoriedade, vandalismo Baixos — usam ferramentas prontas Defacement, DDoS com botnets alugadas, exploits públicos
Hacktivistas Ideologia política/social Moderados — comunidades organizadas DDoS coordenado, vazamento de dados, defacement

1.4 — Vetores de Ataque Comuns em Redes

Os vetores de ataque são os caminhos pelos quais ameaças podem comprometer uma rede:

  • Perímetro de Internet: Exploração de serviços expostos (servidores web, email, VPN), ataques DDoS, scanning de portas
  • Email/Phishing: Links maliciosos, anexos com malware, Business Email Compromise (BEC)
  • Rede Wireless: Rogue APs, Evil Twin, ataques de desautenticação, WPA cracking
  • Rede Local (LAN): ARP spoofing, VLAN hopping, MAC flooding, DHCP starvation
  • Supply Chain: Comprometimento de fornecedores de software/hardware, atualizações maliciosas
  • Acesso Físico: USB drops, rubber ducky, evil maid attacks, shoulder surfing
  • Dispositivos IoT: Senhas padrão, firmware desatualizado, protocolos inseguros
  • Cloud Misconfiguration: S3 buckets públicos, Security Groups permissivos, APIs sem autenticação

1.5 — Políticas de Segurança e Frameworks

A segurança efetiva começa com políticas bem definidas, não com tecnologia. Os principais frameworks e padrões incluem:

📋 Frameworks de Segurança

  • NIST Cybersecurity Framework: Identify, Protect, Detect, Respond, Recover
  • ISO 27001/27002: Sistema de Gestão de Segurança da Informação (SGSI)
  • CIS Controls: 18 controles prioritários baseados em ataques reais
  • COBIT: Governança de TI e alinhamento com o negócio
  • PCI-DSS: Padrão para proteção de dados de cartão de crédito
  • LGPD/GDPR: Legislação de proteção de dados pessoais

📋 Políticas Essenciais de Rede

  • Política de Uso Aceitável (AUP): Define o uso permitido da rede
  • Política de Senhas: Complexidade, expiração, MFA
  • Política de Acesso Remoto: VPN obrigatória, dispositivos permitidos
  • Política de Firewall: Default deny, regras de exceção documentadas
  • Plano de Resposta a Incidentes: Passos, responsáveis, comunicação
  • Política de Backup: RPO, RTO, testes periódicos

⚠️ Segurança sem Política é Caos

Implementar firewalls e IDS sem uma política de segurança documentada é como instalar fechaduras sem decidir quem recebe as chaves. A política define o que proteger, contra quem, com qual nível de risco aceitável — a tecnologia é apenas a implementação dessas decisões. Sempre comece com uma avaliação de risco (Risk Assessment) antes de definir controles técnicos.

Seção 2

Tipos de Ameaças e Ataques de Rede

Conheça em detalhes as categorias de ataques mais comuns em redes corporativas: reconhecimento, acesso, negação de serviço, interceptação, engenharia social e malware. Compreender os ataques é o primeiro passo para construir defesas eficazes.

2.1 — Ataques de Reconhecimento (Reconnaissance)

Ataques de reconhecimento são a fase inicial de um ataque mais complexo. O objetivo é coletar informações sobre a rede-alvo sem causar danos diretos — mas fornecendo dados para ataques subsequentes.

📋 Técnicas de Reconhecimento e Ferramentas


# ══════════════════════════════════════════════════════════════
# RECONHECIMENTO PASSIVO (sem interagir diretamente com o alvo)
# ══════════════════════════════════════════════════════════════

# WHOIS — informações de registro de domínio
$ whois empresa-alvo.com.br
# Retorna: proprietário, NS, contatos, datas de registro

# DNS Lookup — descobrir servidores e IPs
$ dig empresa-alvo.com.br ANY
$ nslookup -type=MX empresa-alvo.com.br
# Retorna: registros A, MX, NS, TXT, CNAME

# Google Dorking — informações indexadas
# site:empresa-alvo.com.br filetype:pdf
# intitle:"index of" site:empresa-alvo.com.br

# Shodan / Censys — dispositivos expostos na internet
# https://shodan.io/search?query=org:"Empresa Alvo"

# ══════════════════════════════════════════════════════════════
# RECONHECIMENTO ATIVO (interação direta com o alvo)
# ══════════════════════════════════════════════════════════════

# Port Scanning com Nmap — descobrir serviços ativos
$ nmap -sS -sV -O -p 1-65535 192.168.1.0/24
# -sS = SYN scan (stealth)
# -sV = detecção de versão de serviço
# -O  = detecção de sistema operacional
# -p  = range de portas

# Scan de portas comuns (rápido)
$ nmap -F 10.0.0.1
# Resultado típico:
# PORT     STATE  SERVICE
# 22/tcp   open   ssh
# 80/tcp   open   http
# 443/tcp  open   https
# 3389/tcp closed ms-wrd-rdp

# SNMP Sweep — coletar informações via SNMP
$ snmpwalk -v2c -c public 192.168.1.1
# Se community string padrão não foi alterada, retorna:
# interfaces, rotas, tabela ARP, config do dispositivo

# Banner Grabbing — identificar softwares/versões
$ nc -v 192.168.1.10 80
# HEAD / HTTP/1.0
# → Server: Apache/2.4.52 (Ubuntu)

# Ping Sweep — descobrir hosts ativos
$ nmap -sn 192.168.1.0/24
# Envia ICMP echo + TCP SYN 443 + TCP ACK 80

⚠️ Defesas contra Reconhecimento

Prevenção: Desabilitar respostas ICMP desnecessárias, usar SNMP v3 com autenticação, não expor serviços desnecessários, configurar firewalls para drop (não reject) em portas fechadas, usar rate limiting em respostas DNS.

Detecção: IDS com assinaturas para port scan, monitoramento de logs de firewall para múltiplas conexões rejeitadas do mesmo IP, alertas para SNMP queries de IPs desconhecidos.

2.2 — Ataques de Acesso (Access Attacks)

Ataques de acesso visam obter acesso não autorizado a sistemas, dados ou privilégios. Exploram vulnerabilidades em autenticação, autorização ou confiança entre sistemas.

Tipo de Ataque Descrição Contramedida
Brute Force Tenta todas as combinações possíveis de senha até encontrar a correta Lockout após N tentativas, MFA, senhas longas, rate limiting
Dictionary Attack Usa lista de senhas comuns (rockyou.txt, wordlists customizadas) Políticas de complexidade, proibir senhas comuns, MFA
Credential Stuffing Usa credenciais vazadas de outros breaches em múltiplos serviços MFA, monitorar Have I Been Pwned, alertas de login anômalo
Pass-the-Hash Usa hash NTLM capturado para autenticar sem conhecer a senha Credential Guard, LAPS, segmentação de admin, Kerberos
Trust Exploitation Explora relações de confiança entre sistemas (trust entre domínios, ssh keys) Princípio do menor privilégio, revisão de trusts, auditoria regular
Port Redirection Redireciona tráfego legítimo para um sistema controlado pelo atacante Monitoramento de rotas, DNSSEC, certificados TLS
Privilege Escalation Eleva privilégios de usuário comum para administrador explorando vulnerabilidades Patching, RBAC, separação de privilégios, monitoramento de sudo

2.3 — Ataques de Negação de Serviço (DoS/DDoS)

Ataques de Negação de Serviço (DoS) visam tornar um serviço ou rede indisponível para usuários legítimos, consumindo recursos (banda, CPU, memória, conexões) até a exaustão. Quando originados de múltiplas fontes simultaneamente, são chamados de DDoS (Distributed Denial of Service).

🔴 Ataques Volumétricos

Saturar a largura de banda do alvo com volume massivo de tráfego:

  • UDP Flood: Envia pacotes UDP em massa para portas aleatórias
  • ICMP Flood (Ping Flood): Milhões de echo requests simultâneos
  • DNS Amplification: Queries DNS com IP de origem spoofado (resposta 50-100x maior que a query)
  • NTP Amplification: Monlist command amplifica tráfego 556x
  • Memcached Amplification: Fator de amplificação de até 51.000x

Volume típico: 100 Gbps a 3+ Tbps

🟡 Ataques de Protocolo

Explorar fraquezas em protocolos de rede para exaurir recursos de dispositivos:

  • SYN Flood: Envia SYN sem completar o handshake, esgota a tabela de conexões TCP
  • Ping of Death: Pacotes ICMP malformados maiores que 65.535 bytes
  • Smurf Attack: Ping para broadcast com IP origem spoofado
  • Fragmentation Attack: Fragmentos sobrepostos que crasham o stack TCP/IP
  • TCP Reset Attack: RST packets spoofados para derrubar conexões existentes

Impacto: Exaustão de tabelas de estado em firewalls e servidores

📋 SYN Flood — Anatomia do Ataque


  ATAQUE SYN FLOOD — Como funciona:

  Atacante                         Servidor Alvo
     │                                  │
     │──── SYN (IP falso: 1.1.1.1) ───→│  Servidor aloca recursos
     │──── SYN (IP falso: 2.2.2.2) ───→│  para cada half-open connection
     │──── SYN (IP falso: 3.3.3.3) ───→│
     │──── SYN (IP falso: 4.4.4.4) ───→│  Tabela de conexões
     │──── SYN (IP falso: 5.5.5.5) ───→│  vai enchendo...
     │          ... milhares ...         │
     │──── SYN (IP falso: N.N.N.N) ───→│  TABELA CHEIA!
     │                                  │
     │                                  │  ✗ Novas conexões legítimas
     │                                  │    são REJEITADAS
     │                                  │
  ←─────── SYN-ACK (para IPs falsos) ──│  Respostas vão para IPs
                                           spoofados (nunca respondem)

  DEFESAS:
  ┌──────────────────────────────────────────────────────────────┐
  │ • SYN Cookies: não aloca recursos até receber ACK final     │
  │ • Reduzir SYN-RECEIVED timeout (de 75s para 10-20s)         │
  │ • Aumentar backlog queue (net.ipv4.tcp_max_syn_backlog)      │
  │ • Rate limiting de SYN por IP de origem                      │
  │ • Hardware anti-DDoS (Arbor, CloudFlare Spectrum)            │
  │ • Firewall stateful com SYN proxy                            │
  └──────────────────────────────────────────────────────────────┘

2.4 — Ataques Man-in-the-Middle (MitM)

Em um ataque Man-in-the-Middle, o atacante se posiciona entre dois endpoints de comunicação, interceptando e potencialmente modificando o tráfego sem que as partes percebam.

📋 ARP Spoofing — Ataque MitM em Redes Locais


  CENÁRIO NORMAL:
  PC-Vítima (192.168.1.10)  ←──→  Gateway (192.168.1.1)
  ARP Cache: 192.168.1.1 = AA:BB:CC:DD:EE:01 (MAC real do gateway)

  ATAQUE ARP SPOOFING:
  ┌─────────────────────────────────────────────────────────────────────┐
  │                                                                     │
  │  Atacante (192.168.1.50, MAC: FF:FF:FF:00:00:01)                   │
  │                                                                     │
  │  1. Envia ARP Reply gratuitous para a VÍTIMA:                       │
  │     "192.168.1.1 está em FF:FF:FF:00:00:01" (MAC do atacante!)     │
  │                                                                     │
  │  2. Envia ARP Reply gratuitous para o GATEWAY:                      │
  │     "192.168.1.10 está em FF:FF:FF:00:00:01" (MAC do atacante!)    │
  │                                                                     │
  │  RESULTADO:                                                         │
  │  Vítima → Atacante → Gateway (encaminha para manter conectividade)  │
  │  Gateway → Atacante → Vítima (intercepta tráfego de retorno)        │
  │                                                                     │
  │  O atacante agora vê TODO o tráfego entre vítima e gateway!         │
  └─────────────────────────────────────────────────────────────────────┘

  FERRAMENTAS DO ATACANTE:
  $ arpspoof -i eth0 -t 192.168.1.10 192.168.1.1   # Envenena a vítima
  $ arpspoof -i eth0 -t 192.168.1.1 192.168.1.10   # Envenena o gateway
  $ echo 1 > /proc/sys/net/ipv4/ip_forward          # Ativa forwarding

  DEFESAS:
  • Dynamic ARP Inspection (DAI) no switch
  • DHCP Snooping (cria binding table IP↔MAC confiável)
  • Entradas ARP estáticas para gateway (impraticável em larga escala)
  • 802.1X (autentica dispositivos na porta)
  • Criptografia end-to-end (HTTPS, SSH) — não previne MitM, mas protege dados

💡 DNS Poisoning (DNS Spoofing)

Outro ataque MitM poderoso é o DNS Poisoning, onde o atacante compromete as respostas DNS para redirecionar vítimas a servidores maliciosos. Pode ser feito por: envenenamento do cache DNS de um resolver, modificação de respostas DNS em trânsito (via ARP spoofing), ou comprometimento direto de servidores DNS autoritativos. Defesas: DNSSEC (assinaturas criptográficas em registros DNS), DoH/DoT (DNS over HTTPS/TLS), monitoramento de alterações DNS.

2.5 — Engenharia Social

A engenharia social explora a psicologia humana — é frequentemente o vetor de ataque mais eficaz, pois bypassa todas as defesas técnicas ao manipular pessoas:

  • Phishing: Emails/mensagens que simulam comunicação legítima para obter credenciais ou instalar malware
  • Spear Phishing: Phishing direcionado a indivíduos específicos com personalização detalhada
  • Whaling: Spear phishing dirigido a executivos C-level
  • Vishing: Engenharia social por telefone (Voice phishing)
  • Smishing: Phishing via SMS
  • Pretexting: Criar cenário falso para obter informações (ex: "sou do TI, preciso sua senha para manutenção")
  • Baiting: Deixar USB infectados em locais estratégicos
  • Tailgating/Piggybacking: Seguir funcionário autorizado para entrar em área restrita
  • Quid Pro Quo: Oferecer algo em troca de informação (ex: "suporte técnico gratuito")

⚠️ O Fator Humano

Estudos mostram que 82% dos breaches envolvem o fator humano (Verizon DBIR 2022). A melhor defesa técnica é inútil se um funcionário clicar em um link de phishing e fornecer credenciais VPN. Contramedidas: Security Awareness Training regular, simulações de phishing, cultura de segurança, processos de verificação para solicitações sensíveis, e MFA como rede de segurança mesmo quando credenciais são comprometidas.

2.6 — Tipos de Malware

ACLs (Access Control Lists) — Cisco IOS

Domine as Access Control Lists, o mecanismo fundamental de filtragem de tráfego em roteadores e switches Cisco. Aprenda a criar, posicionar e verificar ACLs padrão, estendidas e nomeadas para controlar o fluxo de dados na rede.

3.1 — Conceitos Fundamentais de ACLs

Uma ACL (Access Control List) é uma lista sequencial de instruções (ACE — Access Control Entries) que permitem ou negam tráfego com base em critérios definidos. São processadas de cima para baixo (top-down), e a primeira regra que corresponde ao pacote é aplicada — as demais são ignoradas.

💡 Regras Fundamentais de ACLs

  • Processamento top-down: Regras são avaliadas na ordem em que aparecem
  • First match wins: O primeiro match determina a ação (permit/deny)
  • Implicit deny all: Existe um "deny any" implícito no final de toda ACL
  • Uma ACL por interface, por direção, por protocolo: Máximo de 1 ACL in + 1 ACL out por interface
  • Direção: "in" filtra tráfego entrando na interface, "out" filtra tráfego saindo
  • Não filtra tráfego originado no próprio roteador: ACLs aplicam-se a tráfego de passagem (transit)

📋 Fluxo de Processamento de ACL


  Pacote chega na interface ──→ ACL aplicada na direção "in"?

                              SIM       │        NÃO
                               │        │         │
                               ▼        │         ▼
                    ┌──────────────────┐ │   Pacote é processado
                    │ Avalia Regra 1   │ │   normalmente (routing)
                    │ Match?           │ │
                    │  SIM → Ação      │ │
                    │  NÃO → Próxima   │ │

                    │ Avalia Regra 2   │ │

                    ├──────────────────┤ │

3.2 — Wildcard Masks

ACLs Cisco utilizam wildcard masks (máscara curinga) em vez de subnet masks. A wildcard mask é o inverso lógico da máscara de sub-rede: bits 0 significam "deve corresponder exatamente" e bits 1 significam "qualquer valor é aceito".

Objetivo Endereço IP Wildcard Mask Significado
Host único 192.168.1.10 0.0.0.0 Todos os bits devem corresponder (host exato)
Sub-rede /24 192.168.1.0 0.0.0.255 Primeiros 24 bits fixos, últimos 8 livres
Sub-rede /16 172.16.0.0 0.0.255.255 Primeiros 16 bits fixos, últimos 16 livres
Sub-rede /28 10.0.0.16 0.0.0.15 Primeiros 28 bits fixos, últimos 4 livres (16 hosts)
Qualquer IP 0.0.0.0 255.255.255.255 Nenhum bit precisa corresponder (any)
Faixa ímpar (3º octeto) 192.168.1.0 0.0.254.255 Corresponde a redes com 3º octeto ímpar

💡 Atalhos de Wildcard

host 192.168.1.10 = 192.168.1.10 0.0.0.0 (um host específico)
any = 0.0.0.0 255.255.255.255 (qualquer endereço)
Fórmula: Wildcard = 255.255.255.255 - Subnet Mask. Ex: /24 → 255.255.255.0 → Wildcard = 0.0.0.255

3.3 — ACLs Padrão (Standard ACLs)

ACLs padrão filtram tráfego baseado apenas no endereço IP de origem. São identificadas por números de 1 a 99 (e 1300-1999 na faixa expandida). Por filtrarem apenas por origem, devem ser posicionadas o mais próximo possível do destino.

📋 Configuração de ACL Padrão Numerada


! ══════════════════════════════════════════════════════════════
! CENÁRIO: Bloquear a rede 192.168.10.0/24 de acessar
!          o servidor na rede 192.168.30.0/24
!          Permitir todo o restante do tráfego
! ══════════════════════════════════════════════════════════════

! Passo 1: Criar a ACL padrão (modo de configuração global)
Router(config)# access-list 10 deny 192.168.10.0 0.0.0.255
Router(config)# access-list 10 permit any

! Passo 2: Aplicar na interface mais PRÓXIMA DO DESTINO
! (interface que conecta à rede 192.168.30.0/24)
Router(config)# interface GigabitEthernet 0/2
Router(config-if)# ip access-group 10 out

! ══════════════════════════════════════════════════════════════
! EXEMPLO 2: Permitir apenas o host 10.0.0.5 a acessar a rede
! ══════════════════════════════════════════════════════════════
Router(config)# access-list 20 permit host 10.0.0.5
! (implicit deny any - bloqueia todo o resto)

Router(config)# interface GigabitEthernet 0/1
Router(config-if)# ip access-group 20 out

! ══════════════════════════════════════════════════════════════
! EXEMPLO 3: Restringir acesso ao VTY (Telnet/SSH)
! Apenas a rede de gerência 172.16.1.0/24 pode acessar
! ══════════════════════════════════════════════════════════════
Router(config)# access-list 5 permit 172.16.1.0 0.0.0.255
Router(config)# line vty 0 4
Router(config-line)# access-class 5 in

3.4 — ACLs Estendidas (Extended ACLs)

ACLs estendidas oferecem filtragem granular baseada em IP de origem, IP de destino, protocolo, porta de origem e porta de destino. São identificadas por números de 100 a 199 (e 2000-2699 na faixa expandida). Por serem específicas, devem ser posicionadas o mais próximo possível da origem do tráfego.

📋 Sintaxe de ACL Estendida


! SINTAXE COMPLETA:
! access-list {100-199} {permit|deny} {protocolo} {origem} {wildcard}
!   [operador porta] {destino} {wildcard} [operador porta] [log]
!
! Protocolos: ip, tcp, udp, icmp, eigrp, ospf, gre, ahp, esp
! Operadores: eq (=), gt (>), lt (<), neq (≠), range (faixa)

! ══════════════════════════════════════════════════════════════
! CENÁRIO CORPORATIVO COMPLETO:
! Rede de Servidores: 10.0.1.0/24
! Rede de Usuários: 192.168.10.0/24
! Rede de Visitantes: 192.168.50.0/24
! Internet: qualquer
! ══════════════════════════════════════════════════════════════

! Permitir usuários acessarem HTTP/HTTPS nos servidores
Router(config)# access-list 110 permit tcp 192.168.10.0 0.0.0.255 10.0.1.0 0.0.0.255 eq 80
Router(config)# access-list 110 permit tcp 192.168.10.0 0.0.0.255 10.0.1.0 0.0.0.255 eq 443

! Permitir usuários acessarem SSH no servidor de gerência (10.0.1.10)
Router(config)# access-list 110 permit tcp 192.168.10.0 0.0.0.255 host 10.0.1.10 eq 22

! Permitir DNS (UDP 53) para o servidor DNS interno (10.0.1.2)
Router(config)# access-list 110 permit udp 192.168.10.0 0.0.0.255 host 10.0.1.2 eq 53

! Permitir ICMP (ping) da rede de usuários para servidores (diagnóstico)
Router(config)# access-list 110 permit icmp 192.168.10.0 0.0.0.255 10.0.1.0 0.0.0.255

! BLOQUEAR visitantes de acessar servidores internos
Router(config)# access-list 110 deny ip 192.168.50.0 0.0.0.255 10.0.1.0 0.0.0.255 log

! Permitir visitantes acessarem apenas Internet (HTTP/HTTPS/DNS)
Router(config)# access-list 110 permit tcp 192.168.50.0 0.0.0.255 any eq 80
Router(config)# access-list 110 permit tcp 192.168.50.0 0.0.0.255 any eq 443
Router(config)# access-list 110 permit udp 192.168.50.0 0.0.0.255 any eq 53

! Negar todo o restante (explícito para log)
Router(config)# access-list 110 deny ip any any log

! Aplicar na interface PRÓXIMA DA ORIGEM (extended = perto da origem)
Router(config)# interface GigabitEthernet 0/0
Router(config-if)# ip access-group 110 in

ACLs nomeadas oferecem vantagens significativas sobre as numeradas: nomes descritivos, possibilidade de editar regras individuais (inserir/remover sem recriar), e sem limitação de quantidade.

📋 ACLs Nomeadas — Configuração e Edição

3.6 — Posicionamento de ACLs e Verificação

O posicionamento correto de ACLs é crucial para eficiência e funcionalidade:

📍 Regras de Posicionamento

  • ACL Padrão → Próximo ao DESTINO
    Por filtrar apenas por origem, se colocada perto da origem, bloquearia o tráfego para TODOS os destinos, não apenas o desejado
  • ACL Estendida → Próximo à ORIGEM
    Por ser específica (origem+destino+porta), pode bloquear apenas o tráfego indesejado sem afetar outras comunicações. Também evita tráfego desnecessário na rede

🔍 Comandos de Verificação

  • show access-lists — Mostra todas as ACLs e contadores de match
  • show access-lists 110 — Mostra ACL específica
  • show ip interface g0/0 — Mostra ACLs aplicadas na interface
  • show running-config | include access — Localiza ACLs na config
  • clear access-list counters — Zera contadores para troubleshooting

📋 Troubleshooting de ACLs — Verificação Completa


! Verificar quais ACLs existem e quantos pacotes cada regra processou
Router# show access-lists
Extended IP access list 110
    10 permit tcp 192.168.10.0 0.0.0.255 10.0.1.0 0.0.0.255 eq www (1523 matches)
    20 permit tcp 192.168.10.0 0.0.0.255 10.0.1.0 0.0.0.255 eq 443 (8921 matches)
    30 permit tcp 192.168.10.0 0.0.0.255 host 10.0.1.10 eq 22 (47 matches)
    40 deny ip any any log (312 matches)  ← Pacotes bloqueados!

! Verificar em qual interface a ACL está aplicada
Router# show ip interface GigabitEthernet 0/0
  GigabitEthernet0/0 is up, line protocol is up
    Inbound access list is 110         ← ACL 110 aplicada na entrada
    Outgoing access list is not set    ← Nenhuma ACL na saída

! Verificar se há ACL bloqueando tráfego (olhar logs)
Router# show logging | include ACL
*Mar  1 12:00:01: %SEC-6-IPACCESSLOGP: list 110 denied tcp
  192.168.50.5(49231) -> 10.0.1.1(22), 1 packet

! DICA: Usar "log" no final das regras deny para registrar bloqueios
! access-list 110 deny ip any any log

⚠️ Erros Comuns com ACLs

  • Esquecer o "permit any" no final: O implicit deny bloqueia TODO o tráfego restante
  • Ordem incorreta das regras: Regras mais específicas devem vir ANTES das genéricas
  • Wildcard mask errada: 0.0.0.255 ≠ 255.255.255.0 (são inversos!)
  • ACL aplicada na direção errada: "in" e "out" são relativos à interface do roteador
  • ACL padrão perto da origem: Bloqueia tráfego para todos os destinos, não apenas o desejado
  • Não considerar tráfego de retorno: Se bloquear a ida, a volta também será bloqueada em ACLs estendidas (use established ou ACL reflexiva)

Firewalls — Conceitos e Tipos

Compreenda a evolução dos firewalls desde packet filters simples até NGFWs modernos. Aprenda as diferenças entre firewalls stateless e stateful, proxies, WAFs, a arquitetura DMZ e como selecionar a tecnologia adequada para cada cenário.

4.1 — O que é um Firewall e sua Evolução

Um firewall é um dispositivo ou software de segurança que monitora e controla o tráfego de rede com base em regras de segurança predefinidas. Atua como uma barreira entre redes confiáveis (internas) e não confiáveis (Internet), decidindo qual tráfego pode passar e qual deve ser bloqueado.

📋 Evolução dos Firewalls


  EVOLUÇÃO HISTÓRICA DOS FIREWALLS:

  ┌─────────────────────────────────────────────────────────────────────────┐
  │ 1ª Geração (1988) — PACKET FILTERING                                   │
  │ • Filtra pacotes individualmente por IP/porta                          │
  │ • Stateless — não rastreia conexões                                    │
  │ • Rápido, mas facilmente burlado                                       │

  ├─────────────────────────────────────────────────────────────────────────┤
  │ 2ª Geração (1989-1994) — STATEFUL INSPECTION                           │
  │ • Rastreia estado de conexões TCP/UDP                                  │
  │ • Tabela de estados (connection tracking)                              │
  │ • Permite tráfego de retorno automaticamente                           │
  │ • Ex: Cisco ASA, Check Point FW-1, iptables com conntrack              │
  ├─────────────────────────────────────────────────────────────────────────┤
  │ 3ª Geração (1991-2000) — APPLICATION LAYER GATEWAY (PROXY)             │
  │ • Inspeciona payload de aplicação (Layer 7)                            │
  │ • Pode entender HTTP, FTP, SMTP, DNS                                   │
  │ • Mais lento (processa todo o payload)                                 │

  ├─────────────────────────────────────────────────────────────────────────┤
  │ 4ª Geração (2004-2010) — UTM (Unified Threat Management)               │
  │ • Combina firewall + IDS/IPS + antivírus + VPN + filtro web           │

  ├─────────────────────────────────────────────────────────────────────────┤
  │ 5ª Geração (2010+) — NGFW (Next-Generation Firewall)                   │
  │ • Deep Packet Inspection (DPI)                                         │
  │ • Application awareness (identifica apps independente de porta)        │
  │ • User identity integration (LDAP/AD)                                  │
  │ • Threat Intelligence feeds                                            │
  │ • Sandboxing para análise de malware                                   │
  │ • SSL/TLS inspection                                                   │
  │ • Ex: Palo Alto PA-series, Cisco Firepower, Fortinet FortiGate 7.x    │
  └─────────────────────────────────────────────────────────────────────────┘

4.2 — Firewall Packet Filtering (Stateless)

O firewall de filtragem de pacotes (1ª geração) examina cada pacote individualmente, sem considerar o contexto de conexões anteriores. Decide com base em:

  • Endereço IP de origem e destino
  • Porta de origem e destino (TCP/UDP)
  • Protocolo (TCP, UDP, ICMP)
  • Interface de entrada/saída
  • Flags TCP (SYN, ACK, FIN, RST)

✅ Vantagens

  • Alta performance (processamento simples)
  • Baixa latência
  • Transparente para aplicações
  • Baixo custo (disponível em roteadores)
  • Escalável para alto throughput

❌ Desvantagens

  • Não rastreia estado de conexões
  • Vulnerável a IP spoofing
  • Não inspeciona payload (Layer 7)
  • Regras complexas para tráfego de retorno
  • Não detecta ataques de aplicação (SQL injection, XSS)
  • Facilmente burlado com fragmentação

4.3 — Firewall Stateful Inspection

O firewall stateful mantém uma tabela de estados (state table/connection table) que rastreia cada conexão ativa. Pacotes de retorno são permitidos automaticamente se pertencerem a uma conexão previamente autorizada.

📋 Stateful vs Stateless — Exemplo Prático


  CENÁRIO: Host interno (192.168.1.10) acessa servidor web externo (8.8.8.8:80)

  ═══════════════════════════════════════════════════════════════════════════
  FIREWALL STATELESS (ACL simples):
  ═══════════════════════════════════════════════════════════════════════════

  Regra OUTBOUND: permit tcp 192.168.1.0/24 any eq 80     ← OK, pacote sai

  Regra INBOUND para tráfego de RETORNO:
  permit tcp any eq 80 192.168.1.0/24 gt 1023              ← Necessário!
  (permite qualquer origem porta 80 para interno porta alta)

  PROBLEMA: Atacante pode enviar pacotes com source port 80 e entrar!
  Precisa adicionar: permit tcp any eq 80 192.168.1.0/24 gt 1023 established
  (verifica flag ACK — mas ainda vulnerável a ACK scan)

  ═══════════════════════════════════════════════════════════════════════════
  FIREWALL STATEFUL:
  ═══════════════════════════════════════════════════════════════════════════

  Regra OUTBOUND: permit tcp 192.168.1.0/24 any eq 80     ← Pacote sai

  STATE TABLE (criada automaticamente):
  ┌──────────────────────────────────────────────────────────────────────┐
  │ Source IP    │ Src Port │ Dest IP   │ Dst Port │ State      │ Timer │
  │ 192.168.1.10│ 49152    │ 8.8.8.8   │ 80       │ ESTABLISHED│ 3600s │
  └──────────────────────────────────────────────────────────────────────┘

  Tráfego de retorno: 8.8.8.8:80 → 192.168.1.10:49152
  → Firewall consulta state table → Encontra match → PERMITE automaticamente
  → NÃO precisa de regra inbound explícita!

  Pacote de atacante: 6.6.6.6:80 → 192.168.1.10:49152
  → Firewall consulta state table → NÃO encontra match → BLOQUEIA!

💡 Vantagem Principal do Stateful

O firewall stateful simplifica drasticamente as regras: você precisa apenas definir regras para tráfego de saída (outbound). Todo tráfego de retorno legítimo é permitido automaticamente com base na tabela de estados. Isso elimina a necessidade de regras inbound permissivas que poderiam ser exploradas por atacantes.

4.4 — Application Layer Firewall (Proxy/WAF)

Firewalls de camada de aplicação (Layer 7) inspecionam o conteúdo real dos pacotes, entendendo protocolos de aplicação como HTTP, FTP, SMTP e DNS. Podem detectar e bloquear ataques que passariam despercebidos por firewalls de camada 3/4.

🔄 Proxy Firewall

Atua como intermediário: o cliente conecta ao proxy, que faz uma nova conexão ao servidor. Nunca há conexão direta.

  • Quebra a conexão em duas (client↔proxy e proxy↔server)
  • Pode cachear conteúdo (melhora performance)
  • Inspeciona e modifica payload
  • Oculta a topologia interna
  • Pode exigir autenticação do usuário
  • Exemplos: Squid, Blue Coat, Zscaler

🛡️ WAF (Web Application Firewall)

Firewall especializado em proteger aplicações web contra ataques de Layer 7:

  • SQL Injection (SQLi) — bloqueio de queries maliciosas
  • Cross-Site Scripting (XSS) — sanitização de scripts
  • Cross-Site Request Forgery (CSRF)
  • Directory Traversal (../../etc/passwd)
  • Command Injection
  • OWASP Top 10 protection
  • Exemplos: AWS WAF, Cloudflare WAF, ModSecurity, F5 ASM

4.5 — Next-Generation Firewalls (NGFW)

NGFWs combinam as capacidades de firewalls tradicionais com funcionalidades avançadas de inspeção e inteligência:

  • Deep Packet Inspection (DPI): Inspeciona payload completo em tempo real, não apenas cabeçalhos
  • Application Awareness: Identifica aplicações (Facebook, BitTorrent, Zoom) independente da porta usada
  • User Identity: Integra com AD/LDAP para criar políticas por usuário/grupo, não apenas por IP
  • IPS Integrado: Detecção e prevenção de intrusão inline
  • SSL/TLS Decryption: Descriptografa tráfego HTTPS para inspeção (com implicações de privacidade)
  • Threat Intelligence: Feeds de IOC (Indicators of Compromise) atualizados em tempo real
  • Sandboxing: Executa arquivos suspeitos em ambiente isolado para análise de malware zero-day
  • URL Filtering: Bloqueio por categoria de site (gambling, malware, adult)
  • DNS Security: Bloqueia resolução de domínios maliciosos

💡 Principais Fabricantes de NGFW

Palo Alto Networks (PA-series): Líder em Application-ID e User-ID. Cisco Firepower/FTD: Integra Snort IPS e AMP (Advanced Malware Protection). Fortinet FortiGate: Excelente custo-benefício com processadores ASIC dedicados (SPU). Check Point: Forte em gerenciamento centralizado (SmartConsole). Juniper SRX: Forte em ambientes de service provider.

4.6 — Arquitetura DMZ (Demilitarized Zone)

A DMZ é uma sub-rede intermediária entre a rede interna (confiável) e a Internet (não confiável). Hospeda serviços que precisam ser acessíveis externamente (web, email, DNS público) sem expor a rede interna.

📋 Arquitetura DMZ com Firewall Dual-Homed


  ══════════════════════════════════════════════════════════════════════════
  ARQUITETURA DMZ — MODELO CLÁSSICO (Firewall com 3 interfaces)
  ══════════════════════════════════════════════════════════════════════════

                         INTERNET
                            │
                            │ (interface OUTSIDE)
                    ┌───────┴───────┐
                    │               │

5.2 — Zone-Based Policy Firewall (ZBF) — Cisco IOS

O Zone-Based Policy Firewall (ZBF) é o modelo moderno de firewall no Cisco IOS, substituindo o antigo CBAC. Interfaces são atribuídas a zonas, e políticas são definidas entre pares de zonas.

📋 Configuração ZBF — Exemplo Completo


! ══════════════════════════════════════════════════════════════
! PASSO 1: Criar as zonas de segurança
! ══════════════════════════════════════════════════════════════
Router(config)# zone security INSIDE
Router(config-sec-zone)# description Rede interna corporativa
Router(config-sec-zone)# exit

Router(config)# zone security OUTSIDE
Router(config-sec-zone)# description Internet e redes externas
Router(config-sec-zone)# exit

Router(config)# zone security DMZ
Router(config-sec-zone)# description Servidores publicos
Router(config-sec-zone)# exit

! ══════════════════════════════════════════════════════════════
! PASSO 2: Criar class-maps (classificar o tráfego)
! ══════════════════════════════════════════════════════════════
Router(config)# class-map type inspect match-any INSIDE-TO-OUTSIDE-CLASS
Router(config-cmap)# match protocol http
Router(config-cmap)# match protocol https
Router(config-cmap)# match protocol dns
Router(config-cmap)# match protocol icmp
Router(config-cmap)# exit

Router(config)# class-map type inspect match-any OUTSIDE-TO-DMZ-CLASS
Router(config-cmap)# match protocol http
Router(config-cmap)# match protocol https
Router(config-cmap)# match protocol smtp
Router(config-cmap)# exit

! ══════════════════════════════════════════════════════════════
! PASSO 3: Criar policy-maps (definir ações)
! ══════════════════════════════════════════════════════════════
Router(config)# policy-map type inspect INSIDE-TO-OUTSIDE-POLICY
Router(config-pmap)# class type inspect INSIDE-TO-OUTSIDE-CLASS
Router(config-pmap-c)# inspect
Router(config-pmap-c)# exit
Router(config-pmap)# class class-default
Router(config-pmap-c)# drop log
Router(config-pmap-c)# exit

Router(config)# policy-map type inspect OUTSIDE-TO-DMZ-POLICY
Router(config-pmap)# class type inspect OUTSIDE-TO-DMZ-CLASS
Router(config-pmap-c)# inspect
Router(config-pmap-c)# exit
Router(config-pmap)# class class-default
Router(config-pmap-c)# drop log
Router(config-pmap-c)# exit

! ══════════════════════════════════════════════════════════════
! PASSO 4: Criar zone-pairs e aplicar políticas
! ══════════════════════════════════════════════════════════════
Router(config)# zone-pair security INSIDE-TO-OUTSIDE source INSIDE destination OUTSIDE
Router(config-sec-zone-pair)# service-policy type inspect INSIDE-TO-OUTSIDE-POLICY
Router(config-sec-zone-pair)# exit

Router(config)# zone-pair security OUTSIDE-TO-DMZ source OUTSIDE destination DMZ
Router(config-sec-zone-pair)# service-policy type inspect OUTSIDE-TO-DMZ-POLICY
Router(config-sec-zone-pair)# exit

! ══════════════════════════════════════════════════════════════
! PASSO 5: Atribuir interfaces às zonas
! ══════════════════════════════════════════════════════════════
Router(config)# interface GigabitEthernet 0/0
Router(config-if)# zone-member security INSIDE
Router(config-if)# exit

Router(config)# interface GigabitEthernet 0/1
Router(config-if)# zone-member security OUTSIDE
Router(config-if)# exit

Router(config)# interface GigabitEthernet 0/2
Router(config-if)# zone-member security DMZ
Router(config-if)# exit

⚠️ Regras Importantes do ZBF

  • Tráfego entre interfaces na mesma zona é permitido por padrão
  • Tráfego entre interfaces em zonas diferentes é bloqueado por padrão (até criar zone-pair com política)
  • Interface sem zona atribuída só pode se comunicar com outras interfaces sem zona
  • O tráfego para/do próprio roteador (self zone) requer configuração separada

5.3 — Ordenamento de Regras e Boas Práticas

A ordem das regras em um firewall é crítica — regras são processadas de cima para baixo (top-down), e a primeira correspondência determina a ação:

📋 Ordenamento Recomendado de Regras de Firewall


  ═══════════════════════════════════════════════════════════════
  ORDEM RECOMENDADA DE REGRAS (de cima para baixo):
  ═══════════════════════════════════════════════════════════════

  1. REGRAS DE EMERGÊNCIA / BLOCK LIST
     → IPs de atacantes conhecidos, threat intelligence feeds
     → deny ip host 45.33.32.156 any log  (IP malicioso)

  2. REGRAS DE ALLOW LIST PARA SERVIÇOS CRÍTICOS
     → Garantir que tráfego crítico nunca seja bloqueado acidentalmente
     → permit tcp host 10.0.1.5 host 10.0.1.1 eq 22  (admin → SSH)

  3. REGRAS ANTI-SPOOFING
     → Bloquear pacotes com IP de origem impossível na interface
     → deny ip 192.168.0.0/16 any (na interface OUTSIDE)
     → deny ip 10.0.0.0/8 any (na interface OUTSIDE)
     → deny ip 127.0.0.0/8 any (na interface OUTSIDE)

  4. REGRAS DE NEGÓCIOS (mais específicas primeiro)
     → permit tcp 192.168.10.0/24 10.0.1.0/24 eq 443
     → permit tcp 192.168.20.0/24 10.0.1.0/24 eq 80
     → permit tcp 192.168.20.0/24 10.0.1.0/24 eq 443

  5. REGRAS GERAIS DE SAÍDA
     → permit tcp 192.168.0.0/16 any eq 80
     → permit tcp 192.168.0.0/16 any eq 443
     → permit udp 192.168.0.0/16 any eq 53

  6. DENY EXPLÍCITO FINAL (com log)
     → deny ip any any log
     → Torna o implicit deny visível nos logs para troubleshooting
  ═══════════════════════════════════════════════════════════════

💡 Boas Práticas para Políticas de Firewall

  • Default Deny (Whitelist): Bloquear tudo por padrão e permitir apenas o necessário — NUNCA default allow
  • Princípio do Menor Privilégio: Cada regra permite apenas o mínimo necessário (IP+porta específicos)
  • Documentação: Cada regra deve ter comentário explicando propósito, responsável e data de criação
  • Revisão periódica: Auditar regras trimestralmente — remover regras obsoletas
  • Teste antes de produção: Implementar mudanças em janela de manutenção com rollback planejado
  • Logging: Ativar log em regras deny e em regras críticas de permit
  • Change Management: Toda alteração de firewall passa por processo formal de aprovação
  • Regras bidirecionais: Considerar tanto o fluxo de ida quanto o de retorno

5.4 — iptables/nftables — Firewall Linux

Em servidores Linux, o iptables (legado) e nftables (moderno) são os firewalls stateful mais utilizados. Exemplos práticos:

📋 iptables — Configuração de Servidor Web


# ══════════════════════════════════════════════════════════════
# CENÁRIO: Servidor web Linux — permitir apenas SSH, HTTP, HTTPS
# ══════════════════════════════════════════════════════════════

# Definir política padrão como DROP (default deny)
sudo iptables -P INPUT DROP
sudo iptables -P FORWARD DROP
sudo iptables -P OUTPUT ACCEPT

# Permitir tráfego loopback (localhost)
sudo iptables -A INPUT -i lo -j ACCEPT

# Permitir conexões ESTABELECIDAS e RELACIONADAS (stateful)
sudo iptables -A INPUT -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT

# Permitir SSH apenas da rede de gerência
sudo iptables -A INPUT -p tcp -s 172.16.1.0/24 --dport 22 -j ACCEPT

# Permitir HTTP e HTTPS de qualquer origem
sudo iptables -A INPUT -p tcp --dport 80 -j ACCEPT
sudo iptables -A INPUT -p tcp --dport 443 -j ACCEPT

# Permitir ICMP (ping) com rate limit
sudo iptables -A INPUT -p icmp --icmp-type echo-request -m limit --limit 1/s -j ACCEPT

# Log de pacotes rejeitados (últimas regras antes do DROP implícito)
sudo iptables -A INPUT -j LOG --log-prefix "IPTables-Dropped: " --log-level 4

# Salvar regras persistentemente
sudo iptables-save > /etc/iptables/rules.v4

# ══════════════════════════════════════════════════════════════
# PROTEÇÕES ADICIONAIS
# ══════════════════════════════════════════════════════════════

# Proteção contra SYN flood
sudo iptables -A INPUT -p tcp --syn -m limit --limit 10/s --limit-burst 20 -j ACCEPT
sudo iptables -A INPUT -p tcp --syn -j DROP

# Bloquear pacotes inválidos
sudo iptables -A INPUT -m conntrack --ctstate INVALID -j DROP

# Proteção contra port scanning (rate limit de novas conexões)
sudo iptables -A INPUT -p tcp -m conntrack --ctstate NEW -m limit --limit 60/s --limit-burst 20 -j ACCEPT
sudo iptables -A INPUT -p tcp -m conntrack --ctstate NEW -j DROP

IPSec e VPNs

Domine os conceitos e a arquitetura de VPNs (Virtual Private Networks): tipos de VPN, o framework IPSec com seus protocolos AH e ESP, fases IKE, algoritmos de criptografia, modos de operação e implementações em ambientes corporativos e cloud.

6.1 — Conceitos Fundamentais de VPN

Uma VPN (Virtual Private Network) cria um túnel criptografado sobre uma rede pública (Internet), permitindo comunicação segura como se os endpoints estivessem na mesma rede privada. Principais benefícios:

  • Confidencialidade: Dados são criptografados — sniffing captura apenas dados ilegíveis
  • Integridade: Hashing garante que pacotes não foram alterados em trânsito
  • Autenticação: Endpoints verificam a identidade um do outro antes de estabelecer o túnel
  • Anti-replay: Números de sequência previnem ataques de repetição

🔗 Site-to-Site VPN

Conecta duas redes inteiras (escritórios) permanentemente pela Internet:

  • Túnel entre gateways VPN (roteadores/firewalls)
  • Transparente para os usuários finais
  • Sempre ativo (persistent tunnel)
  • Protocolos: IPSec, GRE over IPSec
  • Exemplo: Matriz SP ↔ Filial RJ via Internet

👤 Remote Access VPN

Conecta um usuário individual à rede corporativa:

  • Cliente VPN no dispositivo do usuário
  • Estabelecido sob demanda (dial-up)
  • Split tunneling (tráfego corporativo via VPN, Internet direto) ou full tunnel
  • Protocolos: SSL/TLS VPN, IPSec com XAUTH
  • Exemplo: Home office → Rede corporativa

6.3 — IKE (Internet Key Exchange) — Fases 1 e 2

O IKE é o protocolo responsável por negociar e estabelecer as Security Associations (SAs) do IPSec. Opera em duas fases distintas:

📋 IKE Phase 1 e Phase 2 — Processo Detalhado


  ══════════════════════════════════════════════════════════════════════
  IKE PHASE 1 — Estabelecer IKE SA (canal seguro de gerenciamento)
  ══════════════════════════════════════════════════════════════════════

  Objetivo: Autenticar os peers e criar um canal seguro para Phase 2

  Negociação (ambos os lados devem concordar em):
  ┌────────────────────────────────────────────────────┐
  │ 1. Algoritmo de criptografia: AES-256             │
  │ 2. Algoritmo de hash: SHA-256                      │
  │ 3. Método de autenticação: PSK ou Certificado     │
  │ 4. Grupo Diffie-Hellman: Group 14 (2048-bit)      │
  │ 5. Lifetime do SA: 86400 segundos (24h)           │
  └────────────────────────────────────────────────────┘

  Modos de Phase 1:
  • Main Mode (6 mensagens): Mais seguro, protege identidade dos peers
  • Aggressive Mode (3 mensagens): Mais rápido, mas expõe identidade

  Resultado: IKE SA (ISAKMP SA) estabelecida — canal seguro bidirecional

  ══════════════════════════════════════════════════════════════════════
  IKE PHASE 2 — Estabelecer IPSec SAs (túneis de dados)
  ══════════════════════════════════════════════════════════════════════

  Objetivo: Negociar parâmetros do túnel IPSec para dados de usuário

  Negociação (protegida pelo canal IKE Phase 1):
  ┌────────────────────────────────────────────────────┐
  │ 1. Protocolo IPSec: ESP (ou AH)                   │
  │ 2. Algoritmo de criptografia: AES-256             │
  │ 3. Algoritmo de hash: SHA-256                      │
  │ 4. Modo: Tunnel (ou Transport)                     │
  │ 5. Lifetime: 3600 segundos (1h) ou 4.608.000 KB   │
  │ 6. PFS (Perfect Forward Secrecy): DH Group 14     │
  │ 7. Interesting traffic: ACL define qual tráfego    │
  │    deve ser criptografado                          │
  └────────────────────────────────────────────────────┘

  Modo: Quick Mode (3 mensagens)

  Resultado: 2 IPSec SAs unidirecionais (uma para cada direção)

  ══════════════════════════════════════════════════════════════════════
  FLUXO COMPLETO:
  ══════════════════════════════════════════════════════════════════════

  Peer A                                              Peer B

💡 Perfect Forward Secrecy (PFS)

PFS garante que, se a chave de uma sessão for comprometida, sessões anteriores e futuras permanecem seguras. Funciona gerando novas chaves DH para cada Phase 2, em vez de derivar da Phase 1. Sempre habilite PFS em VPNs corporativas — o overhead de CPU é mínimo em hardware moderno e a proteção é significativa.

Segurança Wireless (Wi-Fi)

Compreenda a evolução dos protocolos de segurança wireless de WEP a WPA3, métodos de autenticação, ameaças específicas de redes sem fio e as melhores práticas para proteger infraestrutura Wi-Fi corporativa.

7.1 — Evolução dos Protocolos de Segurança Wireless

A segurança wireless evoluiu drasticamente desde os primeiros padrões, motivada por vulnerabilidades descobertas em cada geração:

Protocolo Ano Criptografia Autenticação Segurança Status
WEP 1999 RC4 (40/104-bit) Shared Key ou Open Quebrado em minutos (aircrack-ng) ❌ Depreciado — NUNCA usar
WPA 2003 TKIP (RC4 aprimorado) PSK ou 802.1X Vulnerável (TKIP fraco) ⚠️ Legado — evitar
WPA2 2004 AES-CCMP (128-bit) PSK ou 802.1X (Enterprise) Seguro (KRACK patch disponível) ✅ Ainda amplamente usado
WPA3 2018 AES-GCMP (128/192-bit) SAE (Dragonfly) ou 802.1X Forward secrecy, resistente a offline dictionary attacks ✅ Recomendado (mais recente)

⚠️ WEP é Trivialmente Quebrável

O WEP utiliza IVs (Initialization Vectors) de apenas 24 bits, causando repetições estatísticas. Com ferramentas como aircrack-ng, um atacante pode quebrar a chave WEP capturando apenas 40.000-85.000 pacotes (2-5 minutos de captura em rede ativa). Se você encontrar redes WEP em auditoria, a migração para WPA2/WPA3 deve ser prioridade imediata.

7.2 — Autenticação Wireless: PSK vs Enterprise (802.1X)

🔑 WPA2/WPA3 Personal (PSK)

  • Usa Pre-Shared Key (senha compartilhada)
  • Todos os usuários usam a mesma senha
  • Simples de configurar
  • Adequado para redes domésticas/pequenas
  • Problemas:
    • Sem controle individual de usuários
    • Se um dispositivo for comprometido, toda a rede está exposta
    • Difícil revogar acesso sem trocar a senha de todos
    • Vulnerável a offline dictionary attack (WPA2-PSK)

🏢 WPA2/WPA3 Enterprise (802.1X)

  • Cada usuário autentica individualmente (username/password ou certificado)
  • Requer servidor RADIUS (FreeRADIUS, NPS, Cisco ISE)
  • Métodos EAP: PEAP, EAP-TLS, EAP-TTLS
  • Chave de criptografia única por sessão/usuário
  • Vantagens:
    • Revogação individual de acesso
    • Auditoria por usuário
    • Integra com Active Directory/LDAP
    • Cada sessão usa chaves diferentes (sem risco de dictionary attack offline)
    • Pode atribuir VLAN dinâmica por grupo/usuário

Seção 8

IDS/IPS — Detecção e Prevenção de Intrusões

Compreenda as diferenças entre IDS e IPS, métodos de detecção (assinatura e anomalia), modos de deployment (inline vs passivo), soluções populares e integração com SIEM para resposta eficaz a incidentes.

8.1 — IDS vs IPS: Diferenças Fundamentais

Embora frequentemente mencionados juntos, IDS e IPS têm papéis distintos na arquitetura de segurança:

🔍 IDS (Intrusion Detection System)

Detecta e alerta sobre atividades maliciosas, mas não bloqueia o tráfego:

  • Opera em modo passivo (cópia do tráfego via SPAN/TAP)
  • Não está no caminho do tráfego (out-of-band)
  • Gera alertas para SOC/SIEM
  • Zero impacto na latência e throughput
  • Sem risco de bloquear tráfego legítimo (false positive)
  • Útil para monitoramento e forense
  • Limitação: ataque já ocorreu quando alerta é gerado

🛡️ IPS (Intrusion Prevention System)

Detecta e bloqueia atividades maliciosas em tempo real:

  • Opera em modo inline (no caminho do tráfego)
  • Pode drop, reset ou modify pacotes maliciosos
  • Prevenção ativa — ataque é bloqueado antes de alcançar o alvo
  • Adiciona latência (inspeção de cada pacote)
  • Risco: false positives podem bloquear tráfego legítimo
  • Requer tunning cuidadoso de regras
  • Deve ter fail-open/fail-close configurado

8.2 — Métodos de Detecção

📝 Detecção por Assinatura (Signature-Based)

Compara o tráfego contra um banco de dados de padrões conhecidos de ataques:

  • Como funciona: Pattern matching — busca sequências de bytes, padrões de cabeçalhos ou comportamentos conhecidos no tráfego
  • Vantagem: Alta precisão para ataques conhecidos, baixa taxa de false positives
  • Limitação: Não detecta ataques novos (zero-day) — precisa de atualização constante de assinaturas
  • Analogia: Como antivírus — reconhece assinaturas de malware já catalogados
  • Exemplos de regras Snort: Detectar SQL injection, shellcode, exploit específico

📊 Detecção por Anomalia (Anomaly-Based)

Estabelece baseline do tráfego "normal" e alerta sobre desvios significativos:

  • Como funciona: Machine Learning/estatística cria perfil de comportamento normal; tráfego que desvia significativamente é alertado
  • Vantagem: Pode detectar ataques desconhecidos (zero-day) e ameaças internas
  • Limitação: Alta taxa de false positives inicialmente, requer período de treinamento (baselining)
  • Parâmetros monitorados: Volume de tráfego, horários de acesso, protocolos usados, tamanho de pacotes, destinos acessados
  • Exemplos: Cisco Stealthwatch, Darktrace, Vectra AI

💡 Abordagem Híbrida é Ideal

A melhor prática é combinar assinatura + anomalia: assinaturas detectam ataques conhecidos com alta precisão, enquanto anomalia identifica atividades suspeitas que podem indicar ameaças novas. Soluções modernas como Cisco Firepower e Suricata suportam ambos os métodos nativamente.

8.3 — HIDS vs NIDS

Característica NIDS (Network-based) HIDS (Host-based)
Onde opera Monitora tráfego de rede (wire) Monitora atividade do host (OS, filesystem, logs)
Deployment SPAN port, TAP, ou inline no switch/firewall Agente instalado em cada host
Visibilidade Todo tráfego do segmento de rede Atividade detalhada daquele host específico
Tráfego criptografado Limitado (não vê payload em HTTPS sem decryption) Pode ver dados após descriptografia no host
Detecta ataques internos Sim (se tráfego passa pelo sensor) Sim (monitora ações no host local)
Impacto no host Zero (não instala nada nos hosts) Consome CPU/RAM do host
Escalabilidade Um sensor cobre todo o segmento Precisa de agente em cada host
Exemplos Snort, Suricata, Zeek (Bro) OSSEC, Wazuh, Tripwire, CrowdStrike Falcon

8.5 — Tuning, False Positives e Integração SIEM

O maior desafio operacional de IDS/IPS é o tuning — ajustar sensibilidade para minimizar falsos positivos sem perder detecções reais:

  • False Positive: Alerta gerado para tráfego legítimo (ex: ferramenta de vulnerability scan interna disparando alertas)
  • False Negative: Ataque real que não é detectado (mais perigoso, mas menos visível)
  • True Positive: Ataque real corretamente detectado
  • True Negative: Tráfego legítimo corretamente não alertado

💡 Integração com SIEM

IDS/IPS geram volume massivo de alertas. A integração com um SIEM (Security Information and Event Management) como Splunk, QRadar, Azure Sentinel, Elastic SIEM ou Wazuh é essencial para: correlação de eventos (alertas IDS + logs de firewall + autenticação = detecção de cadeia de ataque), priorização baseada em contexto (alerta de exploit em servidor vulnerável vs em servidor patcheado), dashboards de visibilidade, e automação de resposta (SOAR — Security Orchestration, Automation and Response).

Segurança em Cloud (AWS/Azure)

Domine os controles de segurança de rede em ambientes cloud: Security Groups, Network ACLs, WAF, proteção DDoS, serviços de detecção de ameaças, modelo Zero Trust e melhores práticas para arquiteturas seguras em nuvem.

9.1 — Security Groups (AWS) e NSG (Azure)

Security Groups são firewalls stateful de nível de instância/interface que controlam tráfego de entrada e saída:

☁️ AWS Security Groups

  • Nível: ENI (Elastic Network Interface) — por instância
  • Tipo: Stateful — tráfego de retorno permitido automaticamente
  • Default: Deny all inbound, Allow all outbound
  • Regras: Apenas ALLOW (não há regras DENY explícitas)
  • Referência cruzada: Pode referenciar outro SG como source/destination
  • Limite: 5 SGs por ENI (padrão), 60 regras por SG
  • Avaliação: Todas as regras são avaliadas (não top-down)

☁️ Azure NSG (Network Security Group)

  • Nível: NIC ou Subnet
  • Tipo: Stateful — tráfego de retorno permitido automaticamente
  • Default: Regras padrão (deny inbound internet, allow inbound VNet, allow outbound)
  • Regras: ALLOW e DENY com prioridade numérica (100-4096)
  • Processamento: Ordem de prioridade (menor número = maior prioridade)
  • ASG: Application Security Groups para agrupar VMs por função
  • Flow Logs: NSG Flow Logs para auditoria e análise

📋 AWS Security Group — Exemplo Terraform


# ══════════════════════════════════════════════════════════════
# Security Group para servidor web com acesso restrito
# ══════════════════════════════════════════════════════════════

resource "aws_security_group" "web_server" {
  name        = "web-server-sg"
  description = "Security Group para servidor web"
  vpc_id      = aws_vpc.main.id

  # Ingress: permitir HTTP/HTTPS de qualquer lugar
  ingress {
    description = "HTTP from Internet"
    from_port   = 80
    to_port     = 80
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }

  ingress {
    description = "HTTPS from Internet"
    from_port   = 443
    to_port     = 443
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }

  # Ingress: SSH apenas da rede de gerência
  ingress {
    description     = "SSH from management"
    from_port       = 22
    to_port         = 22
    protocol        = "tcp"
    security_groups = [aws_security_group.bastion.id]  # Referência cruzada!
  }

  # Egress: permitir todo tráfego de saída
  egress {
    description = "All outbound traffic"
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }

  tags = {
    Name        = "web-server-sg"
    Environment = "production"
  }
}

# Security Group para banco de dados (acesso apenas do web server)
resource "aws_security_group" "database" {
  name        = "database-sg"
  description = "Security Group para RDS"
  vpc_id      = aws_vpc.main.id

  ingress {
    description     = "MySQL from web servers only"
    from_port       = 3306
    to_port         = 3306
    protocol        = "tcp"
    security_groups = [aws_security_group.web_server.id]  # Apenas web servers!
  }

  # Sem regras de egress = nega todo outbound (exceto retorno stateful)
  tags = {
    Name = "database-sg"
  }
}

9.2 — Network ACLs (AWS) — Stateless

Diferente dos Security Groups (stateful), as Network ACLs (NACLs) na AWS são firewalls stateless de nível de sub-rede:

Característica Security Group Network ACL (NACL)
Nível Instância (ENI) Sub-rede
Stateful/Stateless Stateful (retorno automático) Stateless (regras explícitas para retorno)
Tipos de regra Apenas ALLOW ALLOW e DENY
Processamento Todas as regras avaliadas Top-down (first match wins)
Default Deny all inbound Allow all (NACL padrão)
Associação Múltiplos SGs por instância 1 NACL por sub-rede

💡 Defesa em Profundidade na AWS

Use NACL + Security Group juntos para defesa em profundidade: NACL bloqueia IPs/ranges maliciosos conhecidos no nível de sub-rede (primeira camada), enquanto Security Groups controlam acesso granular por instância (segunda camada). 9.5 — Zero Trust Networking em Cloud

O modelo Zero Trust ("nunca confie, sempre verifique") é especialmente relevante em cloud, onde o perímetro tradicional não existe:

💡 Princípios Zero Trust para Redes Cloud

  • Verify Explicitly: Autenticação e autorização em cada requisição (não assume confiança por estar "dentro" da rede)
  • Least Privilege Access: Acesso mínimo necessário, por tempo limitado (just-in-time)
  • Assume Breach: Design como se a rede já estivesse comprometida — microsegmentação, criptografia end-to-end
  • Microsegmentação: Cada workload em seu próprio Security Group/NSG restritivo
  • Identity-based access: Políticas baseadas em identidade do workload (IAM Roles, Service Accounts), não em IP
  • mTLS (Mutual TLS): Criptografia e autenticação mútua entre todos os serviços (service mesh: Istio, App Mesh)
  • Continuous verification: Monitoramento contínuo de postura, detecção de drift

Criptografia e PKI

Compreenda os fundamentos de criptografia aplicada à segurança de redes: algoritmos simétricos e assimétricos, certificados digitais, infraestrutura de chave pública (PKI), o handshake TLS/SSL e a validação de certificados que protege a comunicação na Internet moderna.

10.1 — Criptografia Simétrica vs Assimétrica

A criptografia é a base de toda comunicação segura em redes. Existem dois paradigmas fundamentais:

🔑 Criptografia Simétrica

A mesma chave é usada para criptografar e descriptografar:

  • Velocidade: Muito rápida (100-1000x mais que assimétrica)
  • Uso: Criptografia de dados em bulk (arquivos, tráfego de rede)
  • Problema: Como compartilhar a chave com segurança? (key distribution problem)
  • Algoritmos:
    • AES (Advanced Encryption Standard): 128, 192 ou 256 bits — padrão atual
    • ChaCha20: Alternativa moderna ao AES (usado em TLS, WireGuard)
    • 3DES: 168 bits — legado, evitar (lento)
    • RC4: Stream cipher — QUEBRADO, nunca usar

🔐 Criptografia Assimétrica

Usa par de chaves: pública (compartilhada) e privada (secreta):

  • Velocidade: Lenta (operações matemáticas complexas)
  • Uso: Key exchange, assinatura digital, autenticação
  • Vantagem: Resolve o problema de distribuição de chaves
  • Algoritmos:
    • RSA: 2048-4096 bits — mais tradicional, baseado em fatoração
    • ECDSA/ECDH: 256-384 bits — curvas elípticas, mais eficiente
    • Ed25519: Assinatura digital moderna (SSH, TLS)
    • X25519: Key exchange moderno (TLS 1.3, WireGuard)

10.2 — Hashing (Funções de Resumo)

Hashing produz um resumo de tamanho fixo (digest) a partir de dados de qualquer tamanho. Não é criptografia (é unidirecional — não pode ser "descriptografado"):

Algoritmo Tamanho do Digest Segurança Uso em Redes
MD5 128 bits (32 hex chars) ❌ QUEBRADO — colisões triviais Legado (OSPF MD5 auth), NÃO usar para segurança
SHA-1 160 bits (40 hex chars) ⚠️ Depreciado — colisões demonstradas (SHAttered 2017) Legado, em processo de descontinuação
SHA-256 256 bits (64 hex chars) ✅ Seguro — padrão atual TLS, IPSec, certificados, integridade de firmware
SHA-384/512 384/512 bits ✅ Seguro — alta segurança Ambientes que exigem máxima segurança
HMAC Depende do hash base ✅ Hash com chave (autenticação + integridade) IPSec, TLS MAC, API authentication

⚠️ Hash ≠ Criptografia

Hashing é unidirecional — dado o digest, é computacionalmente impossível recuperar os dados originais. É usado para verificar integridade (o arquivo/pacote foi alterado?), não para esconder informações. Em segurança de redes, hashing é fundamental em: autenticação de protocolos de roteamento (OSPF, BGP com SHA-256), verificação de integridade em IPSec (HMAC-SHA-256), e assinaturas digitais.

10.5 — Let's Encrypt e Certificados Automatizados

Let's Encrypt revolucionou a adoção de HTTPS ao oferecer certificados DV gratuitos e automatizados via protocolo ACME:

  • Gratuito: Sem custo para emissão ou renovação
  • Automatizado: Protocolo ACME permite emissão/renovação sem intervenção humana
  • Validade: 90 dias (força automação, limita exposição de chave comprometida)
  • Validação: Domain Validation (DV) via HTTP-01 ou DNS-01 challenge
  • Clientes ACME: Certbot, acme.sh, Caddy (automático), Traefik
  • Em cloud: AWS Certificate Manager (ACM), Azure Key Vault Certificates

11.3 — Princípios de Segurança Operacional

📋 Princípio do Menor Privilégio

  • Usuários e sistemas recebem apenas as permissões mínimas necessárias
  • Contas de administrador separadas de contas de uso diário
  • Acesso just-in-time (JIT): privilégios elevados apenas quando necessário
  • Revisão trimestral de acessos (access review/recertification)
  • Revogar imediatamente acessos de funcionários desligados
  • Firewall rules: permit apenas portas/IPs específicos necessários

📋 Patch Management

  • Inventário de todos os dispositivos e versões de software
  • Monitorar CVEs relevantes (NVD, vendor advisories)
  • Classificar patches por criticidade (CVSS score)
  • Testar patches em ambiente staging antes de produção
  • Janela de manutenção definida para aplicação de patches
  • Patches críticos (CVSS 9+): aplicar em 24-72h
  • Patches altos (CVSS 7-8.9): aplicar em 7-14 dias
  • Automatizar onde possível (WSUS, Ansible, SSM Patch Manager)

11.4 — Auditoria e Monitoramento Contínuo

Segurança não é um estado, é um processo contínuo. Monitore, audite e melhore constantemente:

💡 Atividades de Monitoramento Essenciais

  • ✅ Log centralizado: Todos os dispositivos enviando syslog para SIEM (retenção mínima 90 dias)
  • ✅ Alertas automatizados: Regras de correlação para detecção de padrões suspeitos
  • ✅ Vulnerability scanning: Scans regulares (semanal) com Nessus, Qualys ou OpenVAS
  • ✅ Penetration testing: Testes de penetração anuais por equipe externa qualificada
  • ✅ Configuration auditing: Verificar compliance de configuração (CIS Benchmarks)
  • ✅ Network baseline: Conhecer o tráfego "normal" para identificar anomalias
  • ✅ Access review: Revisar trimestralmente quem tem acesso a quê
  • ✅ Backup verification: Testar restore mensalmente (backup não testado = sem backup)
  • ✅ Incident drills: Simulações de incidentes para testar processo de resposta

Exercício 2 — Identificação de Ataques

Cenário: Você está monitorando a rede e observa os seguintes comportamentos nos logs do firewall e IDS. Identifique o tipo de ataque em cada caso:

  1. Milhares de pacotes SYN de IPs diferentes para a porta 80 do seu servidor web, sem nenhum ACK de retorno
  2. Um host interno (192.168.1.50) está enviando ARP replies não solicitados informando que o IP do gateway (192.168.1.1) está no MAC desse host
  3. Tráfego DNS saindo da rede para um servidor externo desconhecido, com queries para subdomínios muito longos e aleatórios de um mesmo domínio
  4. Múltiplas tentativas de login SSH em sequência rápida (10.000 tentativas em 5 minutos) com usernames diferentes vindas do mesmo IP
  5. Um Access Point com o mesmo SSID da rede corporativa aparece com sinal mais forte, mas com BSSID diferente
💡 Resposta

Identificação dos Ataques

  1. DDoS — SYN Flood: Múltiplos IPs enviando SYN sem completar o handshake TCP (half-open connections) visando esgotar a tabela de conexões do servidor. Os IPs diferentes indicam que é um ataque distribuído (DDoS) — possivelmente de uma botnet. Defesa: SYN cookies, rate limiting, AWS Shield/CloudFlare.
  2. ARP Spoofing (Man-in-the-Middle): O host está enviando gratuitous ARP replies para se posicionar entre as vítimas e o gateway, interceptando todo o tráfego da VLAN. Defesa: Dynamic ARP Inspection (DAI), DHCP Snooping, 802.1X.
  3. DNS Tunneling (Exfiltração de Dados): Dados estão sendo codificados nos subdomínios de queries DNS para exfiltrar informações (bypass de firewall, pois DNS geralmente é permitido). Exemplo: aGVsbG8gd29ybGQ.evil-domain.com. Defesa: Monitorar queries DNS anormais, bloquear DNS externo (forçar DNS interno), DNS security (Cisco Umbrella, DNS firewall).
  4. Brute Force / Credential Stuffing: Ataque de força bruta contra SSH tentando múltiplas combinações de usuário/senha. Se os usernames são de listas conhecidas, pode ser credential stuffing. Defesa: Fail2ban, ACL restritiva no SSH, autenticação por chave apenas, MFA, rate limiting.
  5. Evil Twin Attack: Um Access Point falso está imitando a rede corporativa com SSID idêntico, mas com BSSID (MAC do AP) diferente. Clientes podem se conectar ao AP falso pensando ser legítimo. Defesa: 802.1X com validação de certificado do servidor, WIDS/WIPS para detectar rogue APs, educação de usuários.

Exercício 4 — VPN IPSec — Conceitos

Perguntas teóricas sobre IPSec:

  1. Qual a diferença entre AH e ESP? Qual é recomendado e por quê?
  2. Por que o AH é incompatível com NAT?
  3. Explique a diferença entre Tunnel Mode e Transport Mode. Em que cenário cada um é usado?
  4. O que é PFS (Perfect Forward Secrecy) e por que é importante?
  5. Quais são as duas fases do IKE e qual o objetivo de cada uma?
💡 Resposta

Respostas sobre IPSec

  1. AH vs ESP: O AH (Authentication Header) fornece apenas integridade e autenticação (sem criptografia). O ESP (Encapsulating Security Payload) fornece confidencialidade (criptografia) + integridade + autenticação. ESP é recomendado porque fornece todas as proteções de AH MAIS criptografia. AH é usado apenas em casos raros onde criptografia não é necessária mas proteção do header IP original é (ex: compliance que exige não-repúdio do header).
  2. AH e NAT: O AH calcula o hash de integridade incluindo o header IP (incluindo endereços de origem/destino). Quando um dispositivo NAT altera o endereço IP do pacote, o hash se torna inválido e o pacote é descartado pelo receptor. O ESP não tem esse problema porque seu hash não inclui o header IP externo, e com NAT-T (NAT Traversal) encapsula pacotes ESP em UDP 4500.
  3. Tunnel vs Transport Mode: Tunnel Mode encapsula o pacote IP original INTEIRO dentro de um novo pacote com novos headers, ocultando os IPs originais — usado em VPN site-to-site (gateway-to-gateway). Transport Mode protege apenas o payload do pacote IP, mantendo os headers originais visíveis — usado em comunicação host-to-host (ex: dentro de um túnel L2TP).
  4. PFS: Perfect Forward Secrecy garante que a compromissão de uma chave de longo prazo (PSK ou private key) não compromete sessões passadas ou futuras. Funciona gerando novas chaves DH efêmeras para cada Phase 2, em vez de derivar da chave da Phase 1. Se um atacante obtiver a chave de uma sessão, não pode descriptografar outras sessões.
  5. Fases IKE: Phase 1 (Main/Aggressive Mode): Autentica os peers e estabelece um canal seguro (IKE SA) para proteger a negociação subsequente. Negocia criptografia, hash, DH group, authentication method. Phase 2 (Quick Mode): Usando o canal seguro da Phase 1, negocia os parâmetros do túnel IPSec real (ESP/AH, criptografia, hash, lifetime) e cria as IPSec SAs para tráfego de dados.

Rule 4: permit tcp 10.0.0.5 any eq 3306

Problemas Identificados

  1. Regra 5 (permit ip any any) — CRÍTICO: Permite TODO o tráfego de qualquer origem para qualquer destino. Isso invalida completamente o propósito do firewall. Deve ser removida e substituída por regras específicas. Possivelmente deveria ser a política de deny padrão no final.

  3. Regra 3 (permit udp any any eq 53) — RISCO: Permite DNS de QUALQUER origem para QUALQUER destino. Deveria restringir para fontes internas e apenas servidores DNS confiáveis como destino (ex: permit udp 192.168.0.0/16 host 10.0.0.2 eq 53). DNS aberto facilita DNS tunneling e exfiltração.

Exercício 7 — Criptografia e Certificados

Perguntas:

  1. Um usuário reporta um aviso de "certificado inválido" ao acessar um site interno. Liste pelo menos 5 possíveis causas.
  2. Qual a diferença entre criptografia simétrica e assimétrica? Por que TLS usa ambas?
  3. Explique por que MD5 e SHA-1 não devem mais ser usados para segurança. O que deve ser usado em seu lugar?
💡 Resposta

Respostas sobre Criptografia

  1. Causas de "certificado inválido":
    • Certificado expirado: O campo notAfter está no passado (certificado venceu)
    • CN/SAN mismatch: O hostname acessado não corresponde ao Common Name ou Subject Alternative Name no certificado
    • CA não confiável: Certificado emitido por CA interna cujo root não está instalado no trust store do navegador
    • Certificado revogado: O certificado foi revogado (presente na CRL ou resposta OCSP = revoked)
    • Chain incompleta: O servidor não está enviando o intermediate certificate, impedindo a validação da cadeia
    • Data/hora incorreta no cliente: Relógio do computador errado faz parecer que certificado expirou ou ainda não é válido (notBefore)
    • Self-signed certificate: Certificado auto-assinado (não emitido por CA confiável)
    • MitM em progresso: Um proxy/firewall está interceptando a conexão TLS com certificado próprio
  2. Simétrica vs Assimétrica: Criptografia simétrica usa a mesma chave para encrypt/decrypt (rápida, mas precisa compartilhar chave). Assimétrica usa par de chaves pública/privada (resolve key distribution, mas é lenta). O TLS usa ambas (criptografia híbrida): assimétrica para trocar com segurança uma chave simétrica de sessão (key exchange via ECDHE), depois simétrica para criptografar os dados rapidamente (AES-256-GCM). Combina segurança da assimétrica com performance da simétrica.
  3. MD5/SHA-1 depreciados: MD5 tem colisões triviais conhecidas desde 2004 — é possível criar dois documentos diferentes com o mesmo hash. SHA-1 teve colisões demonstradas publicamente em 2017 (ataque SHAttered do Google). Ambos não garantem integridade pois um atacante pode modificar dados e manter o mesmo hash. Usar: SHA-256 (SHA-2 família) como mínimo para qualquer aplicação de segurança (certificados, assinaturas, HMAC). Para máxima segurança: SHA-384 ou SHA-512.

Exercício 9 — iptables — Servidor de Aplicação

Cenário: Você tem um servidor Linux que hospeda uma aplicação web (porta 8080), um banco Redis (porta 6379) e precisa de SSH para gerenciamento. O servidor está na rede 10.0.2.0/24. A rede de gerência é 10.0.1.0/24. Os application servers que acessam Redis estão na mesma subnet.

Tarefa: Escreva as regras iptables completas seguindo a política de default deny.

💡 Resposta

Regras iptables — Servidor de Aplicação


#!/bin/bash
# Script de configuração iptables — Servidor de Aplicação

# Limpar regras existentes
iptables -F
iptables -X
iptables -Z

# Definir política padrão: DROP (default deny)
iptables -P INPUT DROP
iptables -P FORWARD DROP
iptables -P OUTPUT ACCEPT    # Saída liberada (pode restringir se necessário)

# Permitir loopback (comunicação local)
iptables -A INPUT -i lo -j ACCEPT
iptables -A OUTPUT -o lo -j ACCEPT

# Permitir conexões já estabelecidas e relacionadas (stateful)
iptables -A INPUT -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT

# SSH apenas da rede de gerência (10.0.1.0/24)
iptables -A INPUT -p tcp -s 10.0.1.0/24 --dport 22 -j ACCEPT

# Aplicação web (porta 8080) — acessível de qualquer rede interna
iptables -A INPUT -p tcp -s 10.0.0.0/16 --dport 8080 -j ACCEPT

# Redis (porta 6379) — apenas da mesma subnet (app servers)
iptables -A INPUT -p tcp -s 10.0.2.0/24 --dport 6379 -j ACCEPT

# ICMP (ping) — permitir para diagnóstico, com rate limit
iptables -A INPUT -p icmp --icmp-type echo-request \
  -m limit --limit 5/s --limit-burst 10 -j ACCEPT

# Proteção contra SYN flood
iptables -A INPUT -p tcp --syn -m limit --limit 25/s --limit-burst 50 -j ACCEPT
iptables -A INPUT -p tcp --syn -j DROP

# Bloquear pacotes inválidos
iptables -A INPUT -m conntrack --ctstate INVALID -j DROP

# Logar pacotes dropped (para troubleshooting)
iptables -A INPUT -j LOG --log-prefix "[DROPPED] " --log-level 4

# Salvar regras
iptables-save > /etc/iptables/rules.v4

echo "Regras iptables aplicadas com sucesso!"

Verificação: sudo iptables -L -n -v para ver regras e contadores. Testar de cada rede para confirmar que apenas o tráfego autorizado passa.

Análise e Resposta ao Incidente

  1. Análise Inicial — Provável comprometimento:

    Os indicadores sugerem um breach ativo com exfiltração de dados em andamento:

    • O user IAM 'deploy-prod' foi comprometido (acesso de Tor = atacante usando anonimização)
    • O atacante provavelmente usou credenciais comprometidas para acessar a instância EC2
    • O spike de CPU no RDS sugere que o atacante está executando queries pesadas (dump de dados)
    • O tráfego de saída na porta 443 é provavelmente exfiltração de dados para um servidor C2 disfarçada como HTTPS
    • Os bloqueios do WAF indicam que o atacante tentou SQL injection via web (possivelmente vetor inicial), mas o sucesso veio via credenciais IAM comprometidas (API calls)
    • Timeline provável: SQL injection tentou (bloqueado pelo WAF) → atacante usou credenciais IAM roubadas → acessou EC2 → pivotou para RDS → exfiltrando dados
  2. Primeiras 5 ações de contenção (em ordem):
    1. Desabilitar a access key do IAM user 'deploy-prod' — interrompe acesso do atacante imediatamente
    2. Isolar a instância EC2 i-0abc123 — trocar Security Group para um SG vazio (sem inbound/outbound) para parar exfiltração sem destruir evidências
    3. Revogar todas as sessões ativas do IAM user — invalidar temporary credentials com política inline de deny
    4. Bloquear IPs do Tor exit node no WAF/NACL — impedir re-entrada do atacante
    5. Restringir acesso ao RDS — modificar SG do RDS para aceitar apenas do app tier legítimo (remover acesso da EC2 comprometida)
  3. Evidências para preservar ANTES de remediar:
    • Snapshot do volume EBS da EC2 comprometida (imagem forense)
    • Memory dump da EC2 (se possível, antes de isolar)
    • CloudTrail logs (todas as API calls do user comprometido)
    • VPC Flow Logs (IPs de destino da exfiltração)
    • WAF logs completos (padrões de ataque, IPs de origem)
    • RDS audit logs / slow query logs (queries executadas pelo atacante)
    • CloudWatch Logs da aplicação no período do incidente
    • DNS query logs (possível DNS tunneling ou resolução de domínios C2)

    Importante: NUNCA terminate/delete a instância comprometida antes de coletar evidências. O isolamento via Security Group preserva o estado enquanto contém a ameaça.
