Modelo OSI e TCP/IP

Neste módulo você dominará os dois principais modelos de referência em redes: o Modelo OSI (7 camadas) e o Modelo TCP/IP (4 camadas). Entender como os dados são organizados em camadas é a chave para diagnosticar problemas, configurar equipamentos e projetar redes robustas.

Seção 1

Por que Modelos em Camadas?

Antes de mergulhar nas camadas do OSI e TCP/IP, entenda por que dividir a comunicação em camadas é tão poderoso e por que essa abordagem revolucionou as redes de computadores.

1.1 — O Problema Sem Camadas

Imagine construir um sistema de comunicação sem nenhuma organização em camadas. Você teria que resolver todos os problemas de uma vez: como converter dados em sinais elétricos, como detectar erros, como encontrar rotas, como garantir entrega, como formatar dados para aplicações — tudo em um único bloco monolítico de código.

Nos primórdios das redes (anos 1960-70), cada fabricante criava sua própria solução proprietária e monolítica. Redes IBM (SNA) não conversavam com redes DEC (DECnet), que não conversavam com redes Honeywell. Era como se cada país tivesse seu próprio sistema postal com regras completamente diferentes e incompatíveis.

A solução? Dividir para conquistar — separar o problema complexo da comunicação em rede em camadas menores, bem definidas e independentes. Cada camada resolve um aspecto específico do problema e oferece serviços à camada superior.

1.2 — Analogia: Linha de Montagem Industrial

A melhor analogia para modelos em camadas é uma linha de montagem de uma fábrica de automóveis. Em vez de um único operário montar o carro inteiro (impossível de escalar), a produção é dividida em etapas especializadas:

🏭 Linha de Montagem (Analogia)

Estação 1: Monta o chassi (estrutura base)

Estação 2: Instala o motor (potência)

Estação 3: Coloca a carroceria (proteção)

Estação 4: Faz a pintura (acabamento)

Estação 5: Instala o interior (conforto)

Estação 6: Controle de qualidade (verificação)

🌐 Modelo em Camadas (Rede)

Camada 1: Transmite bits (sinais físicos)

Camada 2: Organiza frames (acesso ao meio)

Camada 3: Roteia pacotes (endereçamento lógico)

Camada 4: Garante entrega (transporte confiável)

Camada 5-6: Gerencia sessão e formato

Camada 7: Interface com usuário (aplicação)

Assim como na fábrica, cada estação (camada) é especialista no que faz, não precisa saber como as outras estações funcionam internamente, e pode ser atualizada independentemente sem parar toda a linha.

1.3 — Conceitos Fundamentais da Arquitetura em Camadas

🧩 Abstração

Cada camada esconde sua complexidade interna e expõe apenas uma interface simples para a camada acima. Quando você acessa um site, não precisa saber se está usando fibra óptica ou Wi-Fi — a camada de aplicação (HTTP) funciona igual em ambos os casos. A camada física é "abstraída".

📦 Modularidade

Assim como blocos LEGO, cada camada é um módulo independente. Você pode trocar a camada física (substituir cabo por Wi-Fi) sem alterar absolutamente nada nas camadas superiores. A aplicação nem percebe a mudança. Isso permite evolução tecnológica sem redesenhar tudo.

🔌 Interoperabilidade

Com interfaces padronizadas entre camadas, equipamentos de fabricantes diferentes podem trabalhar juntos. Um switch Cisco conversa com um servidor Dell que roda Linux e envia dados para um iPhone — todos usando os mesmos padrões de camada.

🛠️ Facilidade de Troubleshooting

Se a rede para de funcionar, você pode testar camada por camada de baixo para cima: "O cabo está conectado? (L1) O MAC está OK? (L2) O IP responde a ping? (L3) A porta TCP está aberta? (L4) O HTTP retorna 200? (L7)". Isso isola o problema rapidamente.

💡 Na Prática — Cloud e DevOps

No mundo cloud, a abstração em camadas é levada ao extremo: quando você usa um AWS Application Load Balancer, está operando na Camada 7 — a AWS cuida de todas as camadas abaixo (hardware, rede, transporte) para você. Da mesma forma, containers Docker abstraem o SO e a infraestrutura abaixo. Entender as camadas ajuda a escolher o serviço cloud certo para cada necessidade.

⚠️ Conceito Importante: Comunicação Lógica vs Física

Duas máquinas conversando via HTTP parecem estar trocando dados diretamente na Camada 7. Mas fisicamente, os dados descem todas as camadas no emissor (7→1), viajam pelo meio físico, e sobem todas as camadas no receptor (1→7). A comunicação direta entre camadas pares é apenas lógica (conceitual) — os dados sempre passam pelas camadas intermediárias. Esse processo se chama encapsulamento.

Seção 2

Modelo OSI — 7 Camadas

O modelo Open Systems Interconnection (OSI) foi criado pela ISO em 1984 como referência teórica universal. Possui 7 camadas, cada uma com responsabilidades bem definidas. Vamos explorar cada uma em profundidade.

2.1 — Visão Geral do Modelo OSI

O modelo OSI (Open Systems Interconnection) foi desenvolvido pela ISO (International Organization for Standardization) entre 1977 e 1984. Seu objetivo era criar um modelo de referência universal que permitisse a qualquer fabricante desenvolver equipamentos e softwares de rede que pudessem interoperar.

2.2 — Camada 1: Física (Physical Layer)

A camada mais baixa do modelo OSI lida com a transmissão bruta de bits sobre um meio físico. Ela não se preocupa com o significado dos dados — apenas com a conversão entre bits (0s e 1s) e sinais (elétricos, ópticos ou eletromagnéticos).

⚡ Função Principal

Transmitir bits individuais de um nó ao próximo nó através de um meio de transmissão físico.

PDU: Bit (stream de bits)

Endereçamento: Nenhum (apenas sinais)

Dispositivos: Hubs, repetidores, cabos, conectores, transceivers

🔧 Responsabilidades

• Definição de voltagens e temporização dos sinais

• Tipo de conector e pinagem (RJ-45, LC, SC)

• Taxa de transmissão (bit rate): 10 Mbps, 1 Gbps, etc.

• Modo de transmissão: simplex, half-duplex, full-duplex

• Topologia física: bus, estrela, anel

• Codificação de linha (Manchester, 4B/5B, 8B/10B)

💡 Diagnóstico na Camada 1

Problemas de Camada 1 são os mais comuns e os primeiros a verificar: cabo desconectado, cabo danificado, porta do switch com LED apagado, interferência eletromagnética, conector mal crimpado. A famosa frase de troubleshooting: "Você verificou se o cabo está conectado?" é literalmente um diagnóstico de Camada 1.

2.3 — Camada 2: Enlace de Dados (Data Link Layer)

A Camada 2 é responsável pela comunicação nó a nó — ou seja, entre dois dispositivos diretamente conectados no mesmo segmento de rede. Ela organiza os bits da Camada 1 em unidades lógicas chamadas frames e adiciona endereçamento físico (MAC).

🔗 Função Principal

Transferência confiável de frames entre dois nós adjacentes na mesma rede local.

PDU: Frame (quadro)

Endereçamento: MAC Address (48 bits, ex: AA:BB:CC:DD:EE:FF)

Dispositivos: Switches, bridges, placas de rede (NIC)

🔧 Responsabilidades

• Enquadramento (framing): delimitar onde começa e termina cada frame

• Endereçamento físico: MAC de origem e destino

• Controle de acesso ao meio (MAC): quem pode transmitir e quando

• Detecção de erros: CRC (Cyclic Redundancy Check) no trailer

• Controle de fluxo: evitar que receptor lento seja sobrecarregado

⚠️ MAC Address vs IP Address

O MAC address (Camada 2) é gravado no hardware da placa de rede pelo fabricante e identifica o dispositivo localmente. O IP address (Camada 3) é configurado por software e identifica o dispositivo logicamente na rede. O MAC funciona apenas no segmento local — quando um pacote cruza um roteador, os MACs de origem e destino mudam (são trocados pelo roteador), mas os IPs permanecem os mesmos.

2.4 — Camada 3: Rede (Network Layer)

A Camada 3 é responsável pelo endereçamento lógico e pelo roteamento — ou seja, encontrar o melhor caminho para um pacote viajar da origem ao destino, mesmo passando por múltiplas redes intermediárias.

🗺️ Função Principal

Roteamento de pacotes da origem ao destino final através de múltiplas redes.

PDU: Pacote (Packet)

Endereçamento: IP Address (IPv4: 32 bits / IPv6: 128 bits)

Dispositivos: Roteadores (routers), switches L3

🔧 Responsabilidades

• Endereçamento lógico: atribuir IPs únicos aos dispositivos

• Roteamento: determinar o melhor caminho (OSPF, BGP, RIP)

• Fragmentação: dividir pacotes grandes se necessário

• Controle de congestionamento

• Tradução de endereços (NAT)

• QoS (Quality of Service): priorização de tráfego

💡 Camada 3 na Cloud (AWS)

Na AWS, a VPC (Virtual Private Cloud) é essencialmente uma rede de Camada 3. Você define CIDR blocks (faixas de IP), cria sub-redes, configura route tables e internet gateways — tudo conceitos de Camada 3. Security Groups filtram por IP e porta (L3/L4). Entender roteamento é fundamental para arquitetar VPCs corretamente.

2.5 — Camada 4: Transporte (Transport Layer)

A Camada 4 é responsável pela comunicação fim a fim (end-to-end) entre processos em hosts diferentes. Enquanto a Camada 3 roteia pacotes entre máquinas, a Camada 4 entrega dados ao processo correto dentro da máquina (usando portas).

🚚 Função Principal

Entrega confiável (ou não) de dados entre processos em hosts distintos.

PDU: Segmento (TCP) ou Datagrama (UDP)

Endereçamento: Portas (0-65535)

Protocolos: TCP, UDP, SCTP, QUIC

🔧 Responsabilidades

• Segmentação e remontagem de dados

• Multiplexação por portas (múltiplas apps no mesmo host)

• Controle de fluxo (sliding window)

• Controle de congestionamento (TCP)

• Entrega ordenada e sem duplicatas (TCP)

• Detecção de erros (checksum)

Característica TCP (Transmission Control Protocol) UDP (User Datagram Protocol)
Conexão Orientado a conexão (3-way handshake) Sem conexão (connectionless)
Confiabilidade Garantida (ACKs, retransmissão) Não garantida (best-effort)
Ordenação Dados entregues em ordem (sequence numbers) Sem garantia de ordem
Velocidade Mais lento (overhead de controle) Mais rápido (mínimo overhead)
Controle de Fluxo Sim (sliding window) Não

Uso Típico HTTP, HTTPS, FTP, SMTP, SSH DNS, DHCP, VoIP, streaming, gaming

💡 TCP vs UDP — Quando Usar Cada Um?

Use TCP quando precisa que todos os dados cheguem corretamente e em ordem (web, email, transferência de arquivos). Use UDP quando velocidade importa mais que perfeição — em streaming de vídeo, se um frame se perde, é melhor seguir em frente do que parar e retransmitir (isso causaria "travamento"). DNS também usa UDP porque as consultas são pequenas e rápidas — se não responder, basta perguntar de novo.

2.6 — Camada 5: Sessão (Session Layer)

A Camada 5 gerencia sessões de comunicação entre aplicações. Uma sessão é um diálogo ordenado entre dois processos — ela controla quem fala quando, permite checkpoints para retomar transferências e garante que conexões sejam abertas e fechadas de forma organizada.

🤝 Função Principal

Estabelecer, gerenciar e encerrar sessões entre aplicações.

PDU: Dados (Data)

Protocolos: NetBIOS, RPC, PPTP, L2TP, SIP

Conceito-chave: Controle de diálogo

🔧 Responsabilidades

• Abertura e fechamento de sessões

• Sincronização (checkpoints para recuperação)

• Controle de diálogo: full-duplex, half-duplex, simplex

• Gerenciamento de tokens (quem pode transmitir)

• Recuperação de sessão em caso de falha

💡 Exemplo Prático de Sessão

Quando você faz upload de um arquivo grande (ex: 2 GB) e a conexão cai no meio, um protocolo com suporte a sessão pode retomar de onde parou em vez de começar do zero. Isso é possível graças aos checkpoints (pontos de sincronização) que a Camada 5 insere periodicamente. Sem sessão, todo o progresso seria perdido.

2.7 — Camada 6: Apresentação (Presentation Layer)

A Camada 6 cuida da sintaxe e semântica das informações trocadas. Ela garante que dados produzidos por uma aplicação em um sistema possam ser lidos por uma aplicação em outro sistema, independentemente da representação interna.

🎨 Função Principal

Tradução, criptografia e compressão de dados para a camada de aplicação.

PDU: Dados (Data)

Protocolos/Padrões: SSL/TLS, JPEG, MPEG, GIF, ASCII, Unicode, XML, JSON

Conceito-chave: Formatação e tradução

🔧 Responsabilidades

• Tradução de formatos (ASCII ↔ EBCDIC, UTF-8 ↔ UTF-16)

• Criptografia/Descriptografia (SSL/TLS)

• Compressão/Descompressão (reduzir tamanho dos dados)

• Serialização (converter objetos em bytes)

• Codificação de mídia (JPEG, MP3, H.264)

⚠️ Camadas 5 e 6 na Prática

No mundo real, as funções das Camadas 5 e 6 geralmente são absorvidas pela Camada 7 (aplicação) ou por bibliotecas do sistema. Por exemplo, TLS (criptografia) tecnicamente seria Camada 6, mas na prática é implementado como uma biblioteca entre TCP (L4) e HTTP (L7). É por isso que o modelo TCP/IP não possui essas camadas separadas — ele unifica tudo em "Aplicação". Ainda assim, o OSI é útil como modelo de referência conceitual.

2.8 — Camada 7: Aplicação (Application Layer)

A Camada 7 é a camada mais próxima do usuário final. Ela fornece a interface entre a rede e as aplicações que o usuário utiliza. Não é a aplicação em si (o navegador, por exemplo), mas sim os protocolos que a aplicação usa para se comunicar.

📱 Função Principal

Fornecer serviços de rede diretamente aos processos de aplicação do usuário.

PDU: Dados/Mensagem (Data/Message)

Protocolos: HTTP, HTTPS, FTP, SMTP, POP3, IMAP, DNS, DHCP, SSH, Telnet, SNMP

Conceito-chave: Interface com o usuário

🔧 Responsabilidades

• Identificação de parceiros de comunicação

• Determinação de disponibilidade de recursos

• Sincronização de comunicação

• Autenticação e autorização

• Transferência de informações (arquivos, e-mails, páginas web)

• Resolução de nomes (DNS)

💡 Camada 7 e Load Balancers

Na AWS, o Application Load Balancer (ALB) opera na Camada 7 — ele pode tomar decisões de roteamento baseadas no conteúdo HTTP (URL path, headers, cookies). Já o Network Load Balancer (NLB) opera na Camada 4 — ele só vê IP e porta. Essa distinção é direta do modelo OSI e determina qual load balancer usar em cada cenário.

Seção 3

Modelo TCP/IP — 4 Camadas

O modelo TCP/IP é o modelo prático que realmente roda a Internet. Desenvolvido pelo DoD (Departamento de Defesa dos EUA) nos anos 1970, é mais simples que o OSI e reflete como os protocolos são implementados na prática.

3.1 — Origem e Filosofia do TCP/IP

O modelo TCP/IP nasceu antes do modelo OSI — foi desenvolvido por Vinton Cerf e Bob Kahn na DARPA (Defense Advanced Research Projects Agency) entre 1973-1983. Enquanto o OSI é um modelo teórico criado por comitê, o TCP/IP foi desenvolvido na prática, resolvendo problemas reais da ARPANET.

A filosofia do TCP/IP segue princípios pragmáticos:

🎯 Princípios do TCP/IP

End-to-End: Inteligência nas pontas, rede simples no meio

Robustez: "Seja liberal no que aceita, conservador no que envia" (Postel's Law)

Simplicidade: Menos camadas, implementação mais direta

Interoperabilidade: Funcionar em qualquer hardware/SO

Escalabilidade: Projetado para crescer (e cresceu para bilhões de hosts)

📊 TCP/IP vs OSI — Números

Camadas: 4 (vs 7 do OSI)

Documentação: RFCs (Request for Comments)

Organismo: IETF (Internet Engineering Task Force)

Adoção: 100% da Internet mundial

Implementações: Linux, Windows, macOS, iOS, Android

3.3 — Camada 1: Acesso à Rede (Network Access / Link Layer)

Esta camada combina as funções das Camadas 1 (Física) e 2 (Enlace) do modelo OSI. Ela é responsável por colocar os pacotes IP "no fio" — converter pacotes em frames e frames em sinais que viajam pelo meio físico.

🔌 Função

Transmitir dados no segmento local de rede, do host ao primeiro roteador (ou entre hosts no mesmo segmento).

Protocolos: Ethernet (802.3), Wi-Fi (802.11), PPP, ARP

Endereçamento: MAC address (hardware)

🔧 O que resolve

• Como bits viram sinais (codificação)

• Como delimitar frames (enquadramento)

• Como identificar vizinhos (MAC/ARP)

• Como lidar com colisões (CSMA/CD, CSMA/CA)

• Como detectar erros no segmento local (CRC)

💡 Por que o TCP/IP "simplifica" esta camada?

O modelo TCP/IP foi projetado para funcionar sobre qualquer tecnologia de rede local — Ethernet, Token Ring, FDDI, ATM, Wi-Fi, celular. Por isso, ele não detalha a camada de acesso à rede: "não importa como o pacote chega ao próximo hop, desde que chegue". Essa flexibilidade é o que permite que IP rode tanto sobre fibra óptica submarina quanto sobre satélite ou Bluetooth.

3.4 — Camada 2: Internet (Internet Layer)

Equivalente à Camada 3 do OSI. É o coração do modelo TCP/IP — o protocolo IP (Internet Protocol) opera aqui e é responsável por rotear pacotes da origem ao destino final, independentemente de quantas redes intermediárias existam.

🌐 Função

Endereçamento lógico e roteamento de pacotes entre redes distintas.

Protocolo Principal: IP (v4 e v6)

Protocolos Auxiliares: ICMP (diagnóstico), ARP (resolução MAC), IGMP (multicast)

🔧 Características do IP

• Connectionless: Cada pacote é independente

• Best-effort: Não garante entrega (L4 cuida disso)

• Roteável: Pacotes podem cruzar múltiplas redes

• Fragmentável: Pacotes grandes podem ser divididos

• Endereçamento hierárquico: Permite agregação de rotas

3.5 — Camada 3: Transporte (Transport Layer)

Idêntica à Camada 4 do OSI. Fornece comunicação fim a fim entre processos, com os mesmos dois protocolos principais: TCP (confiável) e UDP (rápido).

🚚 TCP no Modelo TCP/IP

Orientado a conexão: 3-way handshake antes de enviar dados

Confiável: Retransmissão automática de segmentos perdidos

Ordenado: Números de sequência garantem ordem correta

Controle de fluxo: Window size adapta velocidade

Controle de congestionamento: Slow start, congestion avoidance

⚡ UDP no Modelo TCP/IP

Sem conexão: Envia sem handshake (fire and forget)

Não confiável: Sem ACKs nem retransmissão

Não ordenado: Datagramas podem chegar fora de ordem

Leve: Header de apenas 8 bytes

Rápido: Ideal para real-time (VoIP, games, streaming)

3.6 — Camada 4: Aplicação (Application Layer)

No modelo TCP/IP, a camada de Aplicação unifica as Camadas 5, 6 e 7 do OSI em uma única camada. Aqui residem todos os protocolos que interagem diretamente com o software do usuário.

📱 Protocolos de Aplicação TCP/IP

Web: HTTP/1.1, HTTP/2, HTTP/3, HTTPS (TLS)

E-mail: SMTP (envio), POP3/IMAP (recebimento)

Transferência: FTP, SFTP, SCP, TFTP

Resolução: DNS (nomes → IPs)

Configuração: DHCP (IPs automáticos), NTP (tempo)

Acesso remoto: SSH, Telnet, RDP

Gerenciamento: SNMP, Syslog, NETCONF

🔐 TLS/SSL na Aplicação TCP/IP

No modelo OSI, criptografia seria Camada 6 (Apresentação). No TCP/IP, TLS é tratado como parte da camada de Aplicação — mais especificamente, ele se situa entre a aplicação (HTTP) e o transporte (TCP), criando um "sub-layer" de segurança.

Stack completa HTTPS:

HTTP → TLS → TCP → IP → Ethernet

Isso resulta no que chamamos de HTTPS = HTTP over TLS over TCP.

💡 HTTP/3 e QUIC — A Evolução

O protocolo HTTP/3 (2022) revolucionou ao abandonar TCP em favor de QUIC (baseado em UDP). QUIC implementa confiabilidade e criptografia diretamente, eliminando o overhead do TCP handshake + TLS handshake. O resultado? Conexões são estabelecidas com 0-RTT (zero round trips), drasticamente mais rápido que TCP+TLS (que requer 3+ round trips). Isso mostra como o modelo em camadas permite inovação radical mantendo compatibilidade.

Seção 5

Encapsulamento e Desencapsulamento

Entenda como os dados são "embalados" camada por camada ao descer o modelo (envio) e "desembalados" ao subir (recepção). Este processo é fundamental para entender como redes funcionam na prática.

5.1 — O que é Encapsulamento?

Encapsulamento é o processo pelo qual cada camada adiciona seu próprio cabeçalho (header) — e às vezes um trailer — aos dados recebidos da camada superior. É como colocar uma carta dentro de um envelope, depois esse envelope dentro de outro envelope, e assim por diante.

Cada cabeçalho adicionado contém informações de controle específicas daquela camada: endereços, números de sequência, checksums, flags, etc. Quando o dado chega ao destino, cada camada remove seu respectivo cabeçalho (desencapsulamento) e passa o conteúdo para a camada acima.

⬆️ No Servidor Web (Desencapsulamento)

L1 (Física): NIC recebe sinais, reconstrói bits

⚠️ O que Acontece no Meio? (Roteadores)

Cada roteador no caminho faz desencapsulamento parcial: ele remove o header de Camada 2, lê o header de Camada 3 (IP destino) para decidir a rota, e re-encapsula com um novo header de Camada 2 (novos MACs) para o próximo hop. Os headers de Camada 3+ permanecem intactos. É por isso que dizemos que roteadores operam na Camada 3 — eles só precisam "ler" até essa camada.

6.3 — Overhead de Encapsulamento

Cada camada adiciona bytes de controle (overhead). Para dados úteis (payload) viajarem pela rede, eles precisam carregar todos esses cabeçalhos consigo. Vamos calcular:

📊 Cálculo de Overhead Típico

Ethernet Header: 14 bytes

IP Header: 20 bytes

TCP Header: 20 bytes

FCS (CRC): 4 bytes

Total de overhead: 58 bytes

MTU Ethernet: 1500 bytes (payload máximo)

MSS TCP: 1460 bytes (1500 - 20 IP - 20 TCP)

📈 Eficiência

Com payload máximo (1460 bytes):

Eficiência = 1460/1518 = 96.2%

Com payload pequeno (100 bytes):

Eficiência = 100/158 = 63.3%

Conclusão: Pacotes pequenos têm muito overhead relativo. É por isso que o TCP usa o algoritmo de Nagle para agrupar dados pequenos!

💡 MTU e Fragmentação

MTU (Maximum Transmission Unit) é o tamanho máximo de um pacote que pode ser transmitido sem fragmentação. Na Ethernet padrão, o MTU é 1500 bytes. Se um pacote for maior que o MTU do link, ele precisa ser fragmentado (dividido em pedaços menores). Fragmentação reduz a performance e deve ser evitada — por isso, o TCP descobre o menor MTU do caminho (Path MTU Discovery) e ajusta o tamanho dos segmentos.

QUIC Sobre UDP Multiplexação sem head-of-line blocking, 0-RTT, criptografia integrada HTTP/3, Google services, YouTube, Chrome

7.3 — Protocolos da Camada de Rede (L3)

Protocolo Função Detalhes
IPv4 Endereçamento e roteamento (32 bits) Formato: 192.168.1.1. Suporta ~4.3 bilhões de endereços. Amplamente utilizado com NAT
IPv6 Endereçamento e roteamento (128 bits) Formato: 2001:db8::1. Suporta 3.4×10³⁸ endereços. Sem necessidade de NAT. Header simplificado
ICMP Mensagens de controle e erro Usado por ping (Echo Request/Reply) e traceroute. Reporta erros: host unreachable, TTL exceeded
ICMPv6 ICMP para IPv6 Inclui Neighbor Discovery (substitui ARP), Path MTU Discovery, Router Solicitation/Advertisement
IPSec Segurança na camada de rede Criptografia e autenticação de pacotes IP. Base de VPNs site-to-site. Modos: Transport e Tunnel
OSPF Roteamento dinâmico (intra-AS) Link-state, convergência rápida, suporta VLSM e CIDR. Usa áreas para escalabilidade
BGP Roteamento dinâmico (inter-AS) Protocolo da Internet. Conecta ISPs e grandes redes (AS). Path-vector, baseado em políticas

7.4 — Protocolos da Camada de Enlace (L2)

Protocolo/Tecnologia Padrão Função Detalhes
Ethernet IEEE 802.3 LAN cabeada Padrão dominante em redes locais. 10 Mbps → 400 Gbps. CSMA/CD (legado). Full-duplex com switches
Wi-Fi IEEE 802.11 (a/b/g/n/ac/ax) LAN sem fio CSMA/CA para evitar colisões. Frequências: 2.4 GHz, 5 GHz, 6 GHz. Criptografia: WPA3
ARP RFC 826 Resolução IP → MAC Broadcast "Quem tem IP X?". Resposta unicast com MAC. Tabela ARP em cache. Vulnerável a ARP Spoofing
PPP RFC 1661 Links ponto-a-ponto Usado em conexões DSL (PPPoE), links WAN seriais. Autenticação (PAP/CHAP), compressão
STP IEEE 802.1D Prevenção de loops Spanning Tree Protocol. Desabilita links redundantes para evitar broadcast storms. RSTP (802.1w) é mais rápido
VLAN IEEE 802.1Q Segmentação lógica Divide switch em múltiplas redes lógicas. Tag de 4 bytes no frame. Até 4094 VLANs. Trunk entre switches

Exercício 1 — Identificação de Camadas

Para cada cenário abaixo, identifique em qual camada do modelo OSI o problema ou ação está ocorrendo. Justifique sua resposta.

📋 Cenários

A) O LED da porta do switch está apagado após conectar o cabo.

B) O comando ping 8.8.8.8 retorna "Destination Host Unreachable".

C) O navegador exibe "ERR_SSL_PROTOCOL_ERROR" ao acessar um site HTTPS.

D) Um download via FTP para no meio e não retoma — ao reconectar, recomeça do zero.

E) Dois computadores no mesmo switch não se comunicam, mas o cabo está OK e os LEDs acendem.

F) O comando curl http://api.exemplo.com/users retorna HTTP 503 Service Unavailable.

🔍 Ver Resposta do Exercício 1

Respostas:

A) Camada 1 (Física) — LED apagado indica problema físico: cabo danificado, mal crimpado, conector quebrado, ou porta do switch com defeito. Sem sinal elétrico/óptico = problema L1.

B) Camada 3 (Rede) — "Destination Host Unreachable" é uma mensagem ICMP indicando que o roteador não encontrou rota para o destino. Problema de roteamento/endereçamento IP = L3.

C) Camada 6 (Apresentação) / Camada 5-7 no TCP/IP — SSL/TLS é um protocolo de apresentação (criptografia). Erro de protocolo SSL indica incompatibilidade de versão ou certificado inválido.

D) Camada 5 (Sessão) — A sessão não manteve checkpoints/pontos de sincronização. Sem gerenciamento de sessão adequado, não há como retomar de onde parou.

E) Camada 2 (Enlace) — LEDs OK (L1 funcionando). Possíveis causas L2: VLANs diferentes, endereços MAC duplicados, port security bloqueando, ou STP colocando porta em blocking.

F) Camada 7 (Aplicação) — HTTP 503 é uma resposta do servidor web (aplicação). O servidor está up mas indisponível (manutenção, overload). Todas as camadas inferiores funcionam (a resposta chegou!).

Exercício 2 — Encapsulamento Passo a Passo

Você está em um computador com IP 192.168.1.50 e MAC AA:BB:CC:11:22:33. Seu gateway é 192.168.1.1 com MAC DD:EE:FF:44:55:66. Você quer acessar http://93.184.216.34 (servidor web externo).

Descreva o encapsulamento completo do pacote, preenchendo os campos de cada cabeçalho.

🔍 Ver Resposta do Exercício 2

Encapsulamento Completo:

Camada 7 (Aplicação):

Dados = "GET / HTTP/1.1\r\nHost: 93.184.216.34\r\n\r\n"

Camada 4 (Transporte — TCP):

• Porta Origem: 49152 (efêmera, aleatória entre 49152-65535)

• Porta Destino: 80 (HTTP)

• Seq: número de sequência inicial (ISN do handshake)

• Flags: PSH, ACK (push data, acknowledge)

Camada 3 (Rede — IPv4):

• IP Origem: 192.168.1.50

• IP Destino: 93.184.216.34

• TTL: 128 (Windows default) ou 64 (Linux default)

• Protocol: 6 (TCP)

Camada 2 (Enlace — Ethernet):

• MAC Origem: AA:BB:CC:11:22:33 (seu computador)

• MAC Destino: DD:EE:FF:44:55:66 (gateway! NÃO o servidor final)

• EtherType: 0x0800 (IPv4)

• FCS: CRC-32 calculado sobre todo o frame

Ponto crucial: O MAC destino é do GATEWAY (roteador), não do servidor final! O roteador vai trocar os MACs a cada hop, mas os IPs permanecem os mesmos até o destino.

Exercício 3 — TCP vs UDP: Escolha o Protocolo

Para cada aplicação abaixo, indique se deve usar TCP ou UDP e justifique com base nas características de cada protocolo.

📋 Aplicações

A) Sistema de videoconferência em tempo real (Zoom/Meet)

B) Transferência bancária online (internet banking)

C) Jogo multiplayer online (FPS com 64 jogadores)

D) Download de atualização de sistema operacional (4 GB)

E) Sensor IoT enviando temperatura a cada 5 segundos

F) Consulta DNS para resolver "cloudtrilhas.com"

🔍 Ver Resposta do Exercício 3

Respostas:

A) UDP — Videoconferência prioriza tempo real. Se um frame de vídeo se perde, é melhor mostrar o próximo do que pausar para retransmitir (causaria lag). Latência baixa > perfeição.

B) TCP — Transação financeira exige 100% de confiabilidade. Cada byte deve chegar correto e em ordem. Perder ou corromper dados em uma transferência bancária seria catastrófico.

C) UDP — Games FPS precisam de latência mínima. Posição de jogadores muda 60x/segundo — um pacote perdido é irrelevante pois o próximo já traz a posição atualizada.

D) TCP — Download de arquivo grande precisa ser 100% íntegro. Um bit errado pode corromper todo o instalador. TCP garante entrega completa, ordenada e sem erros.

E) UDP — Sensor IoT envia leituras frequentes. Se uma leitura se perde, a próxima chega em 5s. O overhead do TCP (handshake + ACKs) seria desnecessário para dados tão pequenos e frequentes.

F) UDP — Consultas DNS são pequenas (< 512 bytes) e rápidas. Se não responder, o cliente simplesmente pergunta de novo. TCP seria overhead desnecessário para uma pergunta/resposta tão simples.

Exercício 4 — Mapeamento OSI ↔ TCP/IP e Troubleshooting

Você é administrador de rede e recebe o seguinte chamado: "Usuários do escritório não conseguem acessar o site interno http://intranet.empresa.local, mas conseguem acessar sites externos como google.com normalmente."

Faça um diagnóstico estruturado usando as camadas do modelo OSI (de baixo para cima) e identifique as possíveis causas em cada camada.

🔍 Ver Resposta do Exercício 4

Diagnóstico Estruturado:

Camada 1 (Física): DESCARTADA — Se acessam Google, a conectividade física está OK. Cabos, switches e links funcionam.

Camada 2 (Enlace): DESCARTADA — Se há comunicação com a Internet, frames estão sendo enviados/recebidos corretamente no segmento local.

Camada 3 (Rede): POSSÍVEL — O servidor da intranet pode estar em uma sub-rede diferente com rota faltando. Verificar: ping [IP-do-servidor-intranet]. Se ping funcionar com IP direto, descarte L3.

Camada 4 (Transporte): POSSÍVEL — A porta 80 do servidor pode estar fechada (serviço parado). Verificar: telnet intranet.empresa.local 80 ou Test-NetConnection.

Camada 5 (Sessão): MENOS PROVÁVEL — Problemas de sessão são raros em HTTP simples.

Camada 6 (Apresentação): MENOS PROVÁVEL — Não é HTTPS, então não há TLS envolvido.

Camada 7 (Aplicação): MUITO PROVÁVEL — O nome "intranet.empresa.local" pode não estar resolvendo em DNS! Sites externos usam DNS público (8.8.8.8) que funciona, mas o DNS interno (que resolve .local) pode estar fora do ar. Verificar: nslookup intranet.empresa.local.

Diagnóstico mais provável: Problema de DNS interno (Camada 7/Aplicação). O servidor DNS corporativo que resolve nomes internos (.local) está offline ou mal configurado, mas o DNS para nomes públicos funciona via DNS externo.
