DNS — Fundamentos e Arquitetura

O Domain Name System (DNS) é um dos serviços mais críticos da Internet. Sem ele, seria necessário memorizar endereços IP numéricos para acessar qualquer recurso. Compreenda a arquitetura hierárquica distribuída, o processo de resolução e os tipos de registros que formam a base do DNS.

1.1 — O que é DNS e Por que Ele Existe

O Domain Name System (DNS) é um sistema de banco de dados distribuído e hierárquico que traduz nomes de domínio legíveis por humanos (como www.cloudtrilhas.com.br) em endereços IP numéricos (como 192.0.2.45 ou 2001:db8::1) que os computadores utilizam para se comunicar.

Imagine a Internet sem DNS: para acessar o Google, você precisaria digitar 142.250.218.68 no navegador. Para cada site, um endereço IP diferente para memorizar. O DNS funciona como a "lista telefônica" da Internet — você fornece o nome, e ele retorna o número (endereço IP).

💡 Dados sobre o DNS Global

  • Volume de consultas: Estima-se mais de 1 trilhão de consultas DNS por dia globalmente
  • Tempo de resposta típico: 20-120 ms para consultas não cacheadas; <1 ms para cache local
  • Protocolo: UDP porta 53 (consultas normais) e TCP porta 53 (transferências de zona e respostas >512 bytes)
  • RFC principal: RFC 1034 (conceitos) e RFC 1035 (implementação), publicadas em 1987
  • Criticidade: Se o DNS parar, praticamente toda a Internet para — email, web, APIs, cloud, tudo depende de resolução de nomes

O DNS resolve vários problemas fundamentais:

  • Usabilidade: Humanos lembram de nomes, não de números IP
  • Abstração: Um nome pode apontar para IPs diferentes ao longo do tempo (migração de servidores)
  • Balanceamento de carga: Um nome pode resolver para múltiplos IPs (round-robin DNS)
  • Redundância: Se um IP falha, o DNS pode direcionar para outro
  • Organização: A estrutura hierárquica permite gestão descentralizada (cada organização gerencia seus domínios)
  • Serviços auxiliares: Além de traduzir nomes→IPs, o DNS armazena informações sobre servidores de email (MX), aliases (CNAME), verificação (TXT/SPF/DKIM) e muito mais

1.2 — Estrutura Hierárquica do DNS

O DNS é organizado em uma estrutura de árvore invertida, com o "raiz" no topo. Cada nível da hierarquia é chamado de domínio, e os nomes são lidos da direita para a esquerda (do mais geral para o mais específico):

  • New gTLD: .cloud, .app, .dev, .io, .tech, .ai

Cada nível da hierarquia é gerenciado por entidades diferentes:

  • Root (.): Gerenciado por 13 conjuntos de root servers operados por 12 organizações independentes (ICANN, Verisign, NASA, etc.)
  • TLD (.com, .br): Gerenciados por registries designados (Verisign para .com, NIC.br para .br)
  • Domínios registrados: Gerenciados pelos proprietários através de registrars (GoDaddy, Registro.br, Cloudflare Registrar)
  • Subdomínios: Gerenciados livremente pelo proprietário do domínio

1.3 — Processo de Resolução DNS (Passo a Passo)

Quando você digita www.cloudtrilhas.com.br no navegador, uma sequência complexa de consultas ocorre para descobrir o endereço IP correspondente. Existem dois modos de resolução:

🔄 Resolução Recursiva

O cliente envia uma consulta ao resolver recursivo (geralmente o DNS do ISP ou um público como 8.8.8.8). Este resolver assume a responsabilidade de encontrar a resposta completa, fazendo quantas consultas iterativas forem necessárias aos servidores autoritativos. O cliente recebe a resposta final pronta.

Analogia: Você pede a um bibliotecário para encontrar um livro — ele vai de estante em estante até achá-lo e te entrega.

➡️ Resolução Iterativa

O servidor DNS não resolve a consulta completamente, mas retorna uma referência (referral) para o próximo servidor na hierarquia que pode ter a resposta. O cliente (ou resolver recursivo) deve seguir cada referência manualmente.

Analogia: Você pergunta onde fica um livro e recebem: "Tente no setor C". No setor C: "Tente na prateleira 7". E assim por diante.

1.4 — Tipos de Registros DNS

O DNS armazena diversos tipos de registros (Resource Records — RRs), cada um com uma função específica. Conhecer os principais tipos é fundamental para administrar domínios e troubleshooting:

Tipo Nome Completo Função Exemplo
A Address (IPv4) Mapeia nome → endereço IPv4 www IN A 192.0.2.45
AAAA Address (IPv6) Mapeia nome → endereço IPv6 www IN AAAA 2001:db8::1
CNAME Canonical Name Cria alias (aponta um nome para outro nome) blog IN CNAME www.cloudtrilhas.com.br.
MX Mail Exchanger Define servidores de email do domínio (com prioridade) @ IN MX 10 mail.cloudtrilhas.com.br.
NS Name Server Define os servidores DNS autoritativos para a zona @ IN NS ns1.cloudtrilhas.com.br.
PTR Pointer Resolução reversa (IP → nome). Usado em zonas .arpa 45.2.0.192.in-addr.arpa. IN PTR www.cloudtrilhas.com.br.
TXT Text Texto livre — usado para SPF, DKIM, verificação de domínio @ IN TXT "v=spf1 include:_spf.google.com ~all"
SOA Start of Authority Metadados da zona (NS primário, email admin, serial, timers) @ IN SOA ns1.exemplo.com. admin.exemplo.com. (2024010101 3600 900 604800 86400)
SRV Service Localiza serviços específicos (porta, peso, prioridade) _sip._tcp IN SRV 10 60 5060 sipserver.exemplo.com.
CAA Certification Authority Authorization Define quais CAs podem emitir certificados para o domínio @ IN CAA 0 issue "letsencrypt.org"

⚠️ Regras Importantes sobre CNAME

  • Um CNAME não pode coexistir com outros registros para o mesmo nome (exceto DNSSEC)
  • O apex do domínio (ex: cloudtrilhas.com.br sem www) não deve ter CNAME — use registros A/AAAA ou ALIAS/ANAME (extensão não-padrão)
  • CNAMEs criam uma cadeia de resolução adicional (hop extra), impactando levemente a latência
  • Em cloud, use Alias Records (Route 53) ou CNAME flattening (Cloudflare) para o apex

1.5 — Servidores DNS: Autoritativos vs Recursivos

É fundamental distinguir os dois tipos principais de servidores DNS:

🏛️ Servidor Autoritativo

  • Possui a "verdade" sobre uma zona DNS específica
  • Responde consultas com dados que ele POSSUI (não consulta outros servidores)
  • Tipos: Primário (master) e Secundário (slave)
  • Flag aa (Authoritative Answer) ativa na resposta
  • Exemplos: ns1.cloudtrilhas.com.br, ns-cloud-a1.googledomains.com
  • Gerenciado pelo proprietário do domínio

🔄 Servidor Recursivo (Resolver)

  • Não possui dados próprios — busca respostas consultando outros servidores
  • Realiza o trabalho pesado de resolução para os clientes
  • Mantém cache para acelerar futuras consultas
  • Flag ra (Recursion Available) ativa na resposta
  • Exemplos: 8.8.8.8 (Google), 1.1.1.1 (Cloudflare), DNS do ISP
  • Gerenciado pelo ISP ou provedor de DNS público

1.6 — DNS Caching e TTL

O caching é o mecanismo que torna o DNS eficiente. Sem cache, cada consulta exigiria percorrer toda a hierarquia (root → TLD → autoritativo), gerando latência e carga nos servidores. O TTL (Time To Live) controla por quanto tempo uma resposta DNS pode ficar em cache:

TTL Duração Uso Recomendado Trade-off
60 segundos 1 minuto Failover rápido, DNS dinâmico, load balancing Mais consultas ao autoritativo, mais carga
300 segundos 5 minutos Serviços que mudam frequentemente, pré-migração Bom equilíbrio para serviços ativos
3600 segundos 1 hora Registros moderadamente estáveis (padrão comum) Equilíbrio entre performance e atualização
86400 segundos 24 horas Registros muito estáveis (MX, NS) Alta performance de cache, mudanças demoram a propagar
604800 segundos 7 dias Registros que praticamente nunca mudam Máxima eficiência de cache, quase impossível mudar rapidamente

💡 Dica Prática: Reduzir TTL Antes de Migrações

Antes de migrar um serviço (mudar o IP de um registro A), reduza o TTL para 60-300 segundos com 48-72 horas de antecedência. Assim, quando você fizer a mudança, os caches ao redor do mundo expirarão rapidamente e buscarão o novo IP. Após a migração ser confirmada estável, retorne o TTL ao valor normal.

2.3 — Zonas DNS: Forward e Reverse

Uma zona DNS é uma porção do espaço de nomes DNS que é administrada por uma entidade específica. Existem dois tipos principais:

➡️ Zona Forward (Direta)

  • Traduz nomes → endereços IP
  • É o tipo mais comum de zona
  • Contém registros A, AAAA, CNAME, MX, etc.
  • Exemplo: zona cloudtrilhas.com.br
  • Arquivo: db.cloudtrilhas.com.br

⬅️ Zona Reverse (Reversa)

  • Traduz endereços IP → nomes
  • Essencial para email (verificação anti-spam)
  • Contém registros PTR
  • Usa domínio especial .in-addr.arpa (IPv4) ou .ip6.arpa (IPv6)
  • IP escrito ao contrário: 192.0.2.x → 2.0.192.in-addr.arpa

2.4 — Formato de Arquivo de Zona (Zone File)

O arquivo de zona é um arquivo texto que contém os registros DNS de uma zona específica. Segue o formato definido na RFC 1035:

📋 Exemplo Completo de Arquivo de Zona Forward


; ═══════════════════════════════════════════════════════════════
; Arquivo de zona: /etc/bind/zones/db.cloudtrilhas.com.br
; Domínio: cloudtrilhas.com.br
; ═══════════════════════════════════════════════════════════════

; ─── TTL padrão para registros sem TTL explícito ───

2.5 — Tipos de Servidores DNS

Em uma infraestrutura DNS, diferentes servidores desempenham papéis distintos:

Tipo Função Possui Dados Próprios? Quando Usar
Primário (Master) Fonte original dos dados da zona; aceita atualizações Sim — arquivo de zona editável Sempre necessário para cada zona
Secundário (Slave) Cópia read-only do primário; obtém dados via transferência de zona (AXFR/IXFR) Sim — cópia sincronizada Redundância e distribuição geográfica
Caching-Only Apenas faz consultas recursivas e armazena em cache; não possui zonas Não — apenas cache Aceleração local, filiais remotas
Forwarder Encaminha consultas para outro servidor ao invés de resolver diretamente Não — repassa consultas Concentrar consultas (firewall), usar DNS externo como upstream
Stub Contém apenas registros NS e glue records de uma zona (não transfere tudo) Parcial — apenas NS Referência a zonas delegadas sem overhead de transferência completa

2.6 — Split-Brain DNS (DNS Dividido)

O Split-Brain DNS (também chamado Split-Horizon ou Split DNS) é uma configuração onde o mesmo domínio retorna respostas diferentes dependendo de onde a consulta se origina (rede interna vs Internet):

📋 Conceito de Split-Brain DNS

  │                     SPLIT-BRAIN DNS                                  │
  ├─────────────────────────────────────────────────────────────────────┤
  │                                                                     │
  │  Consulta INTERNA (rede corporativa 10.0.0.0/8):                    │
  │  ─────────────────────────────────────────────────                  │
  │  app.empresa.com → 10.1.2.100 (IP interno direto)                  │
  │  intranet.empresa.com → 10.1.3.50                                  │
  │  mail.empresa.com → 10.1.2.25                                      │
  │  secret.empresa.com → 10.1.5.200 (EXISTE internamente)             │
  │                                                                     │
  │  Consulta EXTERNA (Internet):                                       │
  │  ─────────────────────────────                                      │
  │  app.empresa.com → 203.0.113.45 (IP público / Load Balancer)       │
  │  intranet.empresa.com → NXDOMAIN (NÃO EXISTE externamente)         │
  │  mail.empresa.com → 203.0.113.25                                   │
  │  secret.empresa.com → NXDOMAIN (NÃO EXISTE externamente)           │
  │                                                                     │
  │  Benefícios:                                                        │
  │  • Clientes internos acessam diretamente (sem hairpin NAT)          │
  │  • Serviços internos ficam invisíveis para a Internet               │
  │  • Reduz latência para acesso interno                               │
  │  • Aumenta segurança (menos exposição)                              │
  │                                                                     │
  └─────────────────────────────────────────────────────────────────────┘

💡 Implementação em Ambientes Cloud

Em AWS, o split-brain DNS é implementado com Private Hosted Zones no Route 53 (resolvido apenas dentro da VPC) combinadas com Public Hosted Zones (resolvido pela Internet). Em Azure, utiliza-se Azure Private DNS zones associadas a VNets. O mesmo domínio pode ter zonas pública e privada coexistindo, e o resolver escolhe baseado na origem da consulta.

Seção 3

DNS — Segurança e Problemas

O DNS foi projetado na década de 1980, quando a segurança não era prioridade. Conheça as vulnerabilidades exploradas por atacantes, as soluções modernas (DNSSEC, DoH, DoT) e as melhores práticas para proteger sua infraestrutura DNS.

3.1 — DNS Cache Poisoning (Envenenamento de Cache)

O cache poisoning é um dos ataques mais perigosos contra o DNS. O atacante injeta registros falsos no cache de um resolver recursivo, fazendo com que todos os clientes desse resolver sejam direcionados para IPs maliciosos:

📋 Como Funciona o Cache Poisoning


  ┌─────────────────────────────────────────────────────────────────────────┐
  │                   ATAQUE: DNS CACHE POISONING                           │
  ├─────────────────────────────────────────────────────────────────────────┤
  │                                                                         │
  │  1. Cliente consulta: "Qual o IP de banco.com.br?"                      │
  │     Cliente → Resolver recursivo (8.8.8.8)                              │
  │                                                                         │
  │  2. Resolver consulta o autoritativo de banco.com.br                    │
  │     Resolver → ns1.banco.com.br: "IP de www.banco.com.br?"             │
  │                                                                         │
  │  3. ATACANTE envia resposta FALSA antes do servidor legítimo:           │
  │     Resposta forjada: "www.banco.com.br = 198.51.100.666"              │
  │     (IP do servidor do atacante com site phishing)                      │
  │                                                                         │
  │  4. Se o resolver aceitar a resposta falsa:                             │
  │     → Cache poisoned: banco.com.br = IP malicioso                       │
  │     → TODOS os clientes deste resolver vão para o site falso           │
  │     → Pelo TTL inteiro (pode ser horas!)                                │
  │                                                                         │
  │  Para ter sucesso, o atacante precisa:                                  │
  │  • Acertar o Transaction ID (16 bits = 65536 possibilidades)            │
  │  • Acertar a source port (se for fixa/previsível = fácil!)              │
  │  • Responder antes do servidor legítimo                                 │
  │                                                                         │
  │  ══ Ataque Kaminsky (2008) ══                                           │
  │  Dan Kaminsky demonstrou que era possível envenenar QUALQUER            │
  │  domínio, não apenas o consultado, explorando referrals.                │
  │  Isso acelerou a adoção de source port randomization.                   │
  └─────────────────────────────────────────────────────────────────────────┘

⚠️ Contramedidas contra Cache Poisoning

  • Source Port Randomization: Usar portas aleatórias para consultas (aumenta entropia)
  • Transaction ID Randomization: IDs de transação aleatórios (padrão moderno)
  • DNSSEC: Validação criptográfica das respostas (solução definitiva)
  • 0x20 Encoding: Randomizar maiúsculas/minúsculas no nome consultado como verificação adicional
  • Limitar recursão: Aceitar consultas recursivas apenas de clientes autorizados

3.2 — DNS Amplification DDoS

O DNS Amplification é um ataque de negação de serviço distribuído (DDoS) que explora servidores DNS abertos para amplificar o tráfego direcionado à vítima:

📋 Mecânica do Ataque DNS Amplification


  ┌─────────────────────────────────────────────────────────────────────────┐
  │              ATAQUE: DNS AMPLIFICATION DDoS                              │
  ├─────────────────────────────────────────────────────────────────────────┤
  │                                                                         │
  │  Atacante                DNS Resolvers Abertos            Vítima        │
  │  (botnet)                (milhares na Internet)           (alvo)        │
  │                                                                         │
  │  ┌──────┐    Consulta com IP SPOOFADO     ┌──────────┐                 │
  │  │      │──────────────────────────────────│ Resolver │                 │
  │  │      │  dig ANY isc.org @resolver1      │   #1     │                 │
  │  │      │  (source IP = IP da vítima)      └────┬─────┘                 │
  │  │      │                                       │                       │
  │  │ Bot  │    Consulta com IP SPOOFADO     ┌─────▼────┐    Resposta     │
  │  │ net  │──────────────────────────────────│ Resolver │    ENORME      │
  │  │      │                                  │   #2     │────────────┐   │
  │  │      │                                  └──────────┘            │   │
  │  │      │    Consulta com IP SPOOFADO     ┌──────────┐             │   │
  │  │      │──────────────────────────────────│ Resolver │      ┌─────▼─┐ │
  │  │      │                                  │   #N     │──────│VÍTIMA │ │
  │  └──────┘                                  └──────────┘      └───────┘ │
  │                                                                         │
  │  Fator de Amplificação:                                                 │
  │  • Consulta enviada: ~60 bytes (UDP)                                    │
  │  • Resposta recebida pela vítima: ~3000-4000 bytes                      │
  │  • Amplificação: 50-70x !!                                              │
  │  • 1 Gbps de consultas = 50-70 Gbps na vítima                          │
  │                                                                         │
  │  Por que funciona:                                                      │
  │  • UDP não tem handshake (fácil spoofar IP de origem)                   │
  │  • Consultas tipo ANY/TXT retornam respostas muito grandes              │
  │  • Milhares de resolvers abertos na Internet                            │
  └─────────────────────────────────────────────────────────────────────────┘

💡 Proteções contra DNS Amplification

  • Response Rate Limiting (RRL): Limitar respostas repetitivas para o mesmo destino
  • BCP 38/RFC 2827: ISPs devem implementar filtro de IP source (anti-spoofing)
  • Desabilitar recursão aberta: Resolvers não devem aceitar consultas de qualquer IP
  • Bloquear consultas ANY: Muitos servidores modernos rejeitam ou minimizam respostas ANY
  • Anycast DNS: Distribuir a carga do ataque entre múltiplos pontos de presença

3.3 — DNSSEC (DNS Security Extensions)

O DNSSEC adiciona autenticação criptográfica ao DNS, permitindo que resolvers validem se uma resposta é autêntica (veio do servidor autoritativo correto) e não foi alterada em trânsito. Não criptografa as consultas — apenas garante integridade e autenticidade.

📋 Cadeia de Confiança DNSSEC


  ┌─────────────────────────────────────────────────────────────────────────┐
  │                     CADEIA DE CONFIANÇA DNSSEC                          │
  ├─────────────────────────────────────────────────────────────────────────┤
  │                                                                         │
  │  Conceitos-chave:                                                       │
  │  • KSK (Key Signing Key): Chave "mestre" que assina as chaves          │
  │  • ZSK (Zone Signing Key): Chave que assina os registros da zona       │
  │  • RRSIG: Assinatura digital de um registro (ou conjunto)               │
  │  • DNSKEY: Chave pública publicada no DNS                               │
  │  • DS (Delegation Signer): Hash da KSK filho, publicado no pai         │
  │  • NSEC/NSEC3: Prova de inexistência (domínio não existe)              │
  │                                                                         │
  │  Cadeia de Validação:                                                   │
  │  ═══════════════════                                                    │
  │                                                                         │
  │  Root (.)  ──→ Possui KSK da raiz (trust anchor pré-configurado)       │
  │     │              Assina DS record do .br                              │
  │     ▼                                                                   │
  │  .br TLD   ──→ DS record valida KSK do .br                             │
  │     │              .br assina DS record do cloudtrilhas.com.br          │
  │     ▼                                                                   │
  │  cloudtrilhas.com.br ──→ DS record valida KSK do domínio               │
  │     │                         ZSK assina todos os registros             │
  │     ▼                                                                   │
  │  www.cloudtrilhas.com.br ──→ RRSIG valida o registro A                 │
  │                                                                         │
  │  Resultado: O resolver pode PROVAR matematicamente que                  │
  │  "www.cloudtrilhas.com.br = 192.0.2.45" é uma resposta autêntica       │
  │  vinda do administrador legítimo do domínio.                            │
  └─────────────────────────────────────────────────────────────────────────┘

# Consultar com validação DNSSEC

;; flags: qr rd ra ad;    ← flag "ad" = Authenticated Data (DNSSEC validado!)

;; ANSWER SECTION:

cloudtrilhas.com.br.    3600    IN    RRSIG  A 13 3 3600 20240215000000 20240115000000 12345 cloudtrilhas.com.br. (assinatura...)

# Consultar DNSKEY (chaves públicas da zona)
$ dig cloudtrilhas.com.br DNSKEY +short
257 3 13 (KSK pública — flags 257 = KSK)
256 3 13 (ZSK pública — flags 256 = ZSK)

# Consultar DS record (no pai)
$ dig cloudtrilhas.com.br DS +short
12345 13 2 (hash SHA-256 da KSK)

# Verificar cadeia completa
$ dig +sigchase +trusted-key=/etc/trusted-key.key www.cloudtrilhas.com.br A

3.4 — DNS over HTTPS (DoH) e DNS over TLS (DoT)

Enquanto o DNSSEC garante autenticidade, ele não criptografa as consultas — qualquer observador na rede pode ver quais domínios você está consultando. DoH e DoT resolvem este problema de privacidade:

Característica DNS Tradicional DoT (DNS over TLS) DoH (DNS over HTTPS)
Porta UDP/TCP 53 TCP 853 TCP 443 (HTTPS padrão)
Criptografia Nenhuma (texto claro) TLS 1.2/1.3 TLS 1.2/1.3 (via HTTPS)
Visibilidade na rede Consultas visíveis para qualquer observador Conteúdo criptografado; porta 853 identifica como DNS Indistinguível de tráfego HTTPS normal
Bloqueio por firewall Fácil (bloquear porta 53) Possível (bloquear porta 853) Muito difícil (misturado com tráfego web)
Privacidade Zero — ISP vê todas as consultas Alta — ISP não vê conteúdo, mas sabe que é DNS Máxima — ISP não distingue do tráfego web
Performance Menor latência (UDP, sem handshake) Overhead de TLS handshake Overhead de TLS + HTTP/2
URLs N/A N/A (conexão TCP direta) https://dns.google/dns-query, https://cloudflare-dns.com/dns-query

3.5 — DNS Tunneling

O DNS Tunneling é uma técnica que encapsula tráfego não-DNS (dados, comandos C2, exfiltração) dentro de consultas e respostas DNS. Como o DNS quase sempre é permitido em firewalls, atacantes usam isso para exfiltrar dados ou manter comunicação com malware:

📋 Como Funciona o DNS Tunneling


  ┌─────────────────────────────────────────────────────────────────────────┐
  │                      DNS TUNNELING                                       │
  ├─────────────────────────────────────────────────────────────────────────┤
  │                                                                         │
  │  Máquina infectada              Servidor C2 do atacante                 │
  │  (dentro da rede)               (controla domínio malicioso.com)        │
  │                                                                         │
  │  Dados a exfiltrar: "senha_do_banco=abc123"                             │
  │                                                                         │
  │  1. Malware codifica dados em Base32/Base64:                            │
  │     → "c2VuaGFfZG9fYmFuY289YWJjMTIz"                                   │
  │                                                                         │
  │  2. Envia como consulta DNS (parece legítimo!):                         │
  │     → TXT c2VuaGFfZG9fYmFuY289YWJjMTIz.data.malicioso.com              │
  │                                                                         │
  │  3. Firewall permite (é "apenas" DNS na porta 53)                       │
  │                                                                         │
  │  4. Servidor autoritativo de malicioso.com recebe e decodifica:         │
  │     → "senha_do_banco=abc123" — dados exfiltrados!                      │
  │                                                                         │
  │  Indicadores de DNS Tunneling:                                          │
  │  • Subdomínios muito longos (>50 caracteres)                            │
  │  • Alto volume de consultas TXT ou NULL                                 │
  │  • Padrões Base32/Base64 em nomes de domínio                            │
  │  • Volume anômalo de DNS para domínios desconhecidos                    │
  │  • Respostas DNS grandes (>512 bytes frequentemente)                    │
  │                                                                         │
  │  Ferramentas conhecidas: iodine, dnscat2, dns2tcp                       │
  └─────────────────────────────────────────────────────────────────────────┘

💡 Melhores Práticas de Segurança DNS

  • Implementar DNSSEC em todos os domínios que você gerencia
  • Usar resolvers validadores que verificam DNSSEC (Google 8.8.8.8, Cloudflare 1.1.1.1)
  • Monitorar logs DNS para padrões anômalos (volume, tamanho, entropia)
  • Restringir recursão apenas a clientes internos autorizados
  • Manter software atualizado (BIND, Unbound, Windows DNS)
  • Implementar Response Rate Limiting (RRL) contra amplificação
  • Usar DNS Sinkhole para bloquear domínios maliciosos conhecidos
  • Separar funções — resolver recursivo e autoritativo em servidores diferentes
  • Configurar CAA records para controlar emissão de certificados
  • Habilitar DoH/DoT para proteger privacidade dos clientes

DNS em Cloud

4.1 — AWS Route 53

O Amazon Route 53 é o serviço de DNS gerenciado da AWS. Oferece registro de domínios, DNS autoritativo e health checks integrados. O nome "Route 53" é uma referência à porta UDP/TCP 53 usada pelo DNS:

Simple Retorna um ou mais IPs sem lógica adicional Sites simples com um único recurso
Weighted Distribui tráfego proporcionalmente entre recursos (ex: 70%/30%) Blue/green deployment, testes A/B, migração gradual
Latency-based Direciona para a região AWS com menor latência para o cliente Aplicações multi-região, experiência de baixa latência
Failover Direciona para recurso primário; se health check falhar, vai para secundário Disaster recovery, alta disponibilidade ativo-passivo

Geoproximity Direciona baseado na distância geográfica com bias configurável Distribuição geográfica com controle fino (Traffic Flow)
Multivalue Answer Retorna múltiplos IPs saudáveis (até 8), com health check por IP Load balancing simples em DNS com health check
IP-based Direciona baseado no bloco CIDR de origem do cliente Otimização por ISP, roteamento por rede de origem

  • Auto-registration: VMs registram DNS automaticamente
  • Resolução cross-VNet (link zona a múltiplas VNets)
  • Suporta forward e reverse zones privadas
  • Ideal para nomes internos sem exposição à Internet
  • Integra com Azure Private Endpoints
  • Não requer servidor DNS customizado

Seção 5

DHCP — Fundamentos

O Dynamic Host Configuration Protocol (DHCP) automatiza a atribuição de endereços IP e parâmetros de rede aos dispositivos. Sem DHCP, cada dispositivo precisaria ser configurado manualmente — impraticável em redes com centenas ou milhares de hosts.

5.1 — O que é DHCP e Por que é Essencial

O DHCP (Dynamic Host Configuration Protocol), definido na RFC 2131, é um protocolo cliente-servidor que fornece automaticamente:

  • Endereço IP — atribuído de um pool pré-configurado (scope)
  • Máscara de sub-rede — define o tamanho da rede local
  • Default gateway — roteador para sair da rede local
  • Servidores DNS — para resolução de nomes
  • Nome de domínio — sufixo DNS (ex: empresa.local)
  • Servidor NTP — sincronização de relógio
  • Muitos outros parâmetros — definidos pelas DHCP Options (RFC 2132)

💡 DHCP em Números

  • Protocolo: UDP (não confiável, sem conexão)
  • Porta do servidor: UDP 67
  • Porta do cliente: UDP 68
  • RFC principal: RFC 2131 (DHCPv4), RFC 8415 (DHCPv6)
  • Alternativa em IPv6: SLAAC (Stateless Address Autoconfiguration) — RFC 4862
  • Onipresença: Praticamente toda rede (doméstica, corporativa, data center) usa DHCP

Sem DHCP, administradores precisariam:

  1. Configurar manualmente IP, máscara, gateway e DNS em cada dispositivo
  2. Manter planilhas de controle para evitar conflitos de IP
  3. Reconfigurar cada dispositivo quando parâmetros mudassem
  4. Visitar fisicamente cada máquina para mudanças de rede

Em uma rede corporativa com 5.000 dispositivos, isso seria humanamente impossível de gerenciar.

5.2 — O Processo DORA (Discover, Offer, Request, Acknowledge)

A obtenção de um endereço IP via DHCP segue um processo de 4 mensagens conhecido como DORA. Este processo usa broadcasts nas etapas iniciais (pois o cliente ainda não tem IP):

📋 Processo DORA — Detalhamento Completo


  ┌─────────────────────────────────────────────────────────────────────────┐
  │                    PROCESSO DORA (4 MENSAGENS)                           │
  ├─────────────────────────────────────────────────────────────────────────┤
  │                                                                         │
  │  Cliente (sem IP)                              Servidor DHCP            │
  │  IP: 0.0.0.0                                   IP: 192.168.1.1         │
  │  MAC: AA:BB:CC:DD:EE:01                        Pool: 192.168.1.100-200 │
  │                                                                         │
  │  ═══ PASSO 1: DHCP DISCOVER (Broadcast) ═══                            │
  │                                                                         │
  │  Cliente → Broadcast (255.255.255.255):                                 │
  │  "Há algum servidor DHCP nesta rede? Preciso de um IP!"                 │
  │                                                                         │
  │  • Source IP: 0.0.0.0                                                   │
  │  • Dest IP: 255.255.255.255                                             │
  │  • Source MAC: AA:BB:CC:DD:EE:01                                        │
  │  • Dest MAC: FF:FF:FF:FF:FF:FF                                          │
  │  • Source Port: UDP 68 | Dest Port: UDP 67                              │
  │  • Transaction ID: 0x3903F326 (identificador único)                     │
  │                                                                         │
  │  ═══ PASSO 2: DHCP OFFER (Broadcast ou Unicast) ═══                    │
  │                                                                         │
  │  Servidor → Cliente:                                                    │
  │  "Posso oferecer 192.168.1.150, com lease de 8 horas"                   │
  │                                                                         │
  │  • Offered IP: 192.168.1.150                                            │
  │  • Subnet Mask: 255.255.255.0                                           │
  │  • Default Gateway: 192.168.1.1                                         │
  │  • DNS Servers: 8.8.8.8, 8.8.4.4                                       │
  │  • Lease Time: 28800 seconds (8 hours)                                  │
  │  • DHCP Server ID: 192.168.1.1                                          │
  │                                                                         │
  │  (Se houver múltiplos servidores DHCP, cada um pode enviar um Offer)    │
  │                                                                         │
  │  ═══ PASSO 3: DHCP REQUEST (Broadcast) ═══                             │
  │                                                                         │
  │  Cliente → Broadcast:                                                   │
  │  "Aceito o IP 192.168.1.150 do servidor 192.168.1.1"                    │
  │                                                                         │
  │  • Ainda em broadcast (para que outros servidores saibam que            │
  │    suas ofertas foram rejeitadas)                                       │
  │  • Requested IP: 192.168.1.150                                          │
  │  • Server Identifier: 192.168.1.1                                       │
  │                                                                         │
  │  ═══ PASSO 4: DHCP ACK (Unicast ou Broadcast) ═══                      │
  │                                                                         │
  │  Servidor → Cliente:                                                    │
  │  "Confirmado! 192.168.1.150 é seu por 8 horas. Aqui estão              │
  │   todos os parâmetros de rede."                                         │
  │                                                                         │
  │  • Confirma todos os parâmetros (IP, mask, gateway, DNS...)             │
  │  • Cliente configura sua interface de rede                              │
  │  • Cliente pode agora comunicar normalmente na rede                     │
  │                                                                         │
  │  ═══ POSSÍVEL: DHCP NAK (Negative Acknowledgment) ═══                  │
  │                                                                         │
  │  Se o IP solicitado não está mais disponível ou é inválido:             │
  │  Servidor → Cliente: "Negado! O IP não está disponível."                │
  │  → Cliente reinicia o processo com novo DISCOVER                        │
  └─────────────────────────────────────────────────────────────────────────┘

5.5 — Scope, Reservação e Exclusão

A configuração DHCP organiza-se em torno de três conceitos fundamentais:

📦 Scope (Escopo)

Define o pool de endereços IP que o servidor pode atribuir. Inclui a faixa de IPs, máscara, gateway, DNS e lease time.

Exemplo: Scope "Rede-Usuarios"
Range: 192.168.10.100 - 192.168.10.250
Mask: 255.255.255.0
Gateway: 192.168.10.1
Lease: 8 horas

📌 Reservação (Reservation)

Associa um endereço IP fixo a um MAC address específico. O dispositivo sempre recebe o mesmo IP via DHCP. Combina a conveniência do DHCP com a previsibilidade de IP estático.

Uso: Servidores, impressoras, câmeras IP, telefones VoIP — dispositivos que precisam de IP previsível mas ainda se beneficiam de configuração centralizada.

⚠️ Exclusão (Exclusion Range)

Define IPs dentro do range do scope que NÃO devem ser atribuídos pelo DHCP. Usado para reservar IPs para dispositivos com configuração estática (roteadores, servidores legados, equipamentos de rede). Exemplo: excluir 192.168.10.1-192.168.10.99 para infraestrutura de rede.

5.6 — Considerações sobre Lease Time

A escolha do lease time impacta diretamente a operação da rede:

Lease Time Cenário Ideal Vantagem Desvantagem
30 min - 2h Wi-Fi público, cafeterias, hotéis, conferências IPs reciclados rapidamente para muitos usuários transitórios Renovações frequentes, mais tráfego DHCP
4h - 8h Escritório corporativo (horário comercial) Bom equilíbrio: IPs liberados à noite quando PCs desligam Pool pode esgotar em redes muito densas
24h - 7 dias Redes residenciais, dispositivos semi-fixos Menos tráfego DHCP, IPs mais estáveis IPs de dispositivos desconectados ficam "presos" por mais tempo
30+ dias Redes com poucos dispositivos e muito espaço de endereçamento Mínimo overhead de DHCP IPs desperdiçados por longo tempo após desconexão

6.2 — DHCP Relay Agent (ip helper-address)

O DHCP usa broadcasts, que não atravessam roteadores. Quando o servidor DHCP está em outra sub-rede, é necessário um DHCP Relay Agent que converte o broadcast do cliente em unicast direcionado ao servidor:

📋 DHCP Relay — Conceito e Configuração


  ┌─────────────────────────────────────────────────────────────────────────┐
  │                      DHCP RELAY AGENT                                    │
  ├─────────────────────────────────────────────────────────────────────────┤
  │                                                                         │
  │  VLAN 10 (Usuários)          Roteador/L3 Switch        Servidor DHCP   │
  │  192.168.10.0/24             (Relay Agent)              192.168.1.50    │
  │                                                                         │
  │  ┌──────────┐               ┌──────────────┐          ┌───────────┐   │
  │  │  Cliente  │──Broadcast──►│ Interface     │──Unicast─►│   DHCP    │   │
  │  │  (0.0.0.0)│  DISCOVER    │ VLAN 10      │  DISCOVER │  Server   │   │
  │  │           │              │ 192.168.10.1  │  (com     │           │   │
  │  └──────────┘              │              │  giaddr)  └───────────┘   │
  │                             │              │                           │
  │  O Relay:                   │  Adiciona:   │                           │
  │  1. Intercepta broadcast    │  giaddr =    │  Servidor usa giaddr     │
  │     na interface local      │  192.168.10.1│  para saber de qual      │
  │  2. Insere "giaddr" (IP     │              │  sub-rede veio o pedido  │
  │     da interface local)     └──────────────┘  e selecionar o pool     │
  │  3. Encaminha via unicast                      correto.                │
  │     ao servidor DHCP                                                   │
  │  4. Recebe resposta unicast                                            │
  │  5. Retransmite como                                                   │
  │     broadcast na VLAN local                                            │
  └─────────────────────────────────────────────────────────────────────────┘

  ═══ Configuração Cisco IOS ═══

  ! Na interface da VLAN dos clientes (onde chegam os broadcasts)
  Router(config)# interface vlan 10
  Router(config-if)# ip address 192.168.10.1 255.255.255.0
  Router(config-if)# ip helper-address 192.168.1.50
  !                   ↑ IP do servidor DHCP
  Router(config-if)# exit

  ! Para múltiplos servidores DHCP (redundância)
  Router(config-if)# ip helper-address 192.168.1.50
  Router(config-if)# ip helper-address 192.168.1.51

  ! NOTA: ip helper-address encaminha por padrão estes protocolos:
  ! UDP 67/68 (DHCP), UDP 69 (TFTP), UDP 37 (Time), UDP 49 (TACACS),
  ! UDP 53 (DNS), UDP 137/138 (NetBIOS), UDP 161 (SNMP)
  ! Para restringir apenas DHCP:
  Router(config)# no ip forward-protocol udp 69
  Router(config)# no ip forward-protocol udp 37
  (etc.)

# /etc/dhcp/dhcpd.conf — Servidor DHCP Linux
# ═══════════════════════════════════════════════════════

# Configurações globais
authoritative;                          # Este servidor é autoritativo para estas sub-redes
default-lease-time 28800;               # 8 horas (padrão)

log-facility local7;                    # Logging via syslog

    option routers 192.168.10.1;               # Default gateway
    option domain-name-servers 10.0.0.5, 8.8.8.8;
    option domain-name "usuarios.empresa.local";
    default-lease-time 28800;                  # 8 horas
    max-lease-time 43200;                      # 12 horas máximo
}

subnet 192.168.20.0 netmask 255.255.255.0 {
    range 192.168.20.50 192.168.20.100;
    option routers 192.168.20.1;

}

# ─── Sub-rede: Wi-Fi Visitantes (VLAN 30) ───

6.4 — DHCP Failover (Alta Disponibilidade)

Em ambientes de produção, um único servidor DHCP é um ponto único de falha. Se ele cair, clientes não conseguem obter ou renovar IPs. Existem algumas abordagens para HA:

🔄 Split-Scope (80/20 Rule)

  • Dois servidores DHCP com o mesmo scope
  • Servidor A: 80% dos IPs (range .100-.250)
  • Servidor B: 20% dos IPs (range .251-.290)
  • Ambos configurados como ip helper-address
  • Simples, sem sincronização entre servidores
  • Risco: IPs duplicados se ambos atendem (mitigado por conflito detection)

🤝 DHCP Failover (ISC/Windows)

  • Dois servidores sincronizam leases entre si
  • Um é Primary, outro é Secondary
  • Pool compartilhado, sem divisão manual
  • Se Primary falha, Secondary assume 100%
  • Windows Server: built-in failover com Hot Standby ou Load Balance
  • ISC DHCP: failover peer configuration

DHCP — Segurança e Problemas

O protocolo DHCP não possui mecanismos nativos de autenticação — qualquer dispositivo pode se anunciar como servidor DHCP ou solicitar todos os IPs disponíveis. Conheça os ataques comuns e as defesas implementadas em switches modernos.

7.1 — Rogue DHCP Server (Servidor DHCP Malicioso)

Um rogue DHCP server é um servidor DHCP não autorizado na rede. Pode ser intencional (ataque) ou acidental (funcionário conectou roteador doméstico com DHCP ativado). O impacto é severo:

7.2 — DHCP Starvation Attack (Exaustão de Pool)

No ataque de DHCP Starvation, o atacante envia milhares de mensagens DHCP DISCOVER com MACs aleatórios, esgotando todo o pool de endereços disponíveis. Clientes legítimos não conseguem obter IP:

📋 DHCP Starvation — Mecânica


  Atacante usa ferramenta como "Yersinia" ou "DHCPig":

  1. Gera MACs aleatórios: AA:11:22:33:44:01, AA:11:22:33:44:02, ...
  2. Envia DISCOVER com cada MAC → servidor responde OFFER
  3. Envia REQUEST aceitando cada OFFER → servidor confirma ACK
  4. Repete até esgotar todo o pool (ex: 200 IPs em segundos)

  Resultado:
  • Pool DHCP 100% esgotado
  • Clientes legítimos recebem "no DHCP offers received"
  • Denial of Service para toda a rede

  Frequentemente combinado com Rogue DHCP:
  • Passo 1: Starvation esgota o servidor legítimo
  • Passo 2: Rogue DHCP começa a responder no lugar
  • Clientes agora recebem configuração maliciosa do rogue

7.3 — DHCP Snooping (Defesa Principal)

O DHCP Snooping é o mecanismo de segurança implementado em switches gerenciáveis que protege contra servidores DHCP maliciosos e ataques de starvation. Funciona classificando portas como trusted ou untrusted:

📋 DHCP Snooping — Configuração Cisco


! ═══════════════════════════════════════════════════════
! DHCP SNOOPING — Proteção contra Rogue DHCP
! ═══════════════════════════════════════════════════════

! Passo 1: Habilitar DHCP Snooping globalmente

! Passo 2: Habilitar nas VLANs que deseja proteger
Switch(config)# ip dhcp snooping vlan 10,20,30

! Passo 3: Configurar portas TRUSTED (onde está o servidor DHCP legítimo)

Switch(config-if)# description "Uplink para servidor DHCP"
Switch(config-if)# ip dhcp snooping trust
Switch(config-if)# exit

! Passo 4: Portas de acesso (PCs) ficam UNTRUSTED por padrão
! Mensagens DHCP OFFER/ACK vindas de portas untrusted são BLOQUEADAS
Switch(config)# interface range FastEthernet0/1-48
Switch(config-if-range)# description "Portas de acesso - usuarios"
Switch(config-if-range)# no ip dhcp snooping trust

💡 DHCP Snooping Binding Table

O DHCP Snooping constrói uma tabela de binding (associação) observando tráfego DHCP legítimo. Essa tabela mapeia: MAC → IP → VLAN → Porta → Lease. É a base para outros recursos de segurança como IP Source Guard (bloqueia pacotes com IP que não corresponde ao lease) e Dynamic ARP Inspection (valida ARP contra a binding table).

7.5 — DHCP em Ambientes Cloud

Em nuvem pública, o DHCP funciona de forma diferente — é gerenciado integralmente pelo provedor, sem possibilidade de executar servidor DHCP customizado:

  • VMs recebem IP do pool da subnet via DHCP

  • Gateway é sempre .1 da sub-rede
  • IPs são "reservados" no nível da plataforma (não há DORA tradicional visível)
  • Lease "infinito" (enquanto VM existir)
  • Suporte a custom DNS via VNet settings

NAT — Revisão Avançada e Cenários Complexos

Além do NAT básico (Static, Dynamic, PAT) abordado em módulos anteriores, existem cenários avançados que todo engenheiro de rede precisa dominar: NAT hairpinning, CGNAT, NAT traversal, impacto em protocolos e a transição IPv4/IPv6 via NAT64.

8.1 — Revisão Rápida: Tipos de NAT

Antes de avançar para cenários complexos, recapitulemos os três tipos fundamentais de NAT:

Tipo Mapeamento Caso de Uso Configuração Cisco
Static NAT 1 IP interno ↔ 1 IP externo (fixo, permanente) Servidores que precisam ser acessados externamente (web, email) ip nat inside source static 10.0.0.5 203.0.113.5
Dynamic NAT Pool interno → Pool externo (1:1, sob demanda) Grupo de hosts que precisa de IPs públicos dedicados temporariamente ip nat inside source list 1 pool NOME
PAT (NAT Overload) Múltiplos IPs internos → 1 IP externo (diferenciado por porta) Acesso à Internet para toda a rede via 1 IP público (o mais comum) ip nat inside source list 1 interface G0/1 overload

8.2 — NAT Hairpinning (NAT Loopback)

O NAT Hairpinning ocorre quando um host interno tenta acessar outro host interno usando o endereço IP público (externo) do servidor. O tráfego "sai" pelo NAT e precisa "voltar" para a mesma rede interna:

📋 NAT Hairpinning — O Problema


  ┌─────────────────────────────────────────────────────────────────────────┐
  │                    NAT HAIRPINNING (Loopback)                            │
  ├─────────────────────────────────────────────────────────────────────────┤
  │                                                                         │
  │  Rede Interna 10.0.0.0/24                                               │
  │                                                                         │
  │  ┌──────────┐                    ┌──────────────┐                       │
  │  │  PC-A     │                    │  Web Server   │                       │
  │  │  10.0.0.10│                    │  10.0.0.50    │                       │
  │  └─────┬────┘                    │  NAT→203.0.113.5│                     │
  │        │                          └───────┬────────┘                     │
  │        │                                  │                              │
  │        └──────────┐       ┌───────────────┘                              │
  │                   ▼       ▼                                              │
  │             ┌─────────────────┐                                          │
  │             │    ROTEADOR       │                                          │
  │             │    (NAT device)   │                                          │
  │             │    inside: 10.0.0.1│                                         │
  │             │    outside: 203.0.113.1│                                     │
  │             └─────────────────┘                                          │
  │                                                                         │
  │  PC-A quer acessar: http://203.0.113.5 (o IP PÚBLICO do web server)     │
  │                                                                         │
  │  PROBLEMA sem hairpin NAT:                                               │
  │  1. PC-A envia pacote para 203.0.113.5                                  │
  │  2. Roteador faz NAT de destino: 203.0.113.5 → 10.0.0.50               │
  │  3. Resposta do server: src=10.0.0.50, dst=10.0.0.10                    │
  │  4. PC-A recebe resposta de 10.0.0.50, mas esperava de 203.0.113.5     │
  │  5. PC-A DESCARTA o pacote (source mismatch!) → conexão FALHA          │
  │                                                                         │
  │  SOLUÇÃO: Hairpin NAT (roteador faz NAT de source E destination)        │
  │  - Traduz destino: 203.0.113.5 → 10.0.0.50                             │
  │  - Traduz fonte: 10.0.0.10 → 10.0.0.1 (IP do roteador)                │
  │  - Resposta volta pelo roteador → NAT reverso funciona                  │
  │                                                                         │
  │  ALTERNATIVA MELHOR: Split-Brain DNS                                    │
  │  - DNS interno resolve app.empresa.com → 10.0.0.50 (IP interno direto) │
  │  - DNS externo resolve app.empresa.com → 203.0.113.5 (IP público)      │
  │  - Sem NAT hairpin necessário!                                          │
  └─────────────────────────────────────────────────────────────────────────┘

8.3 — Carrier-Grade NAT (CGNAT / NAT444)

Com a exaustão de endereços IPv4 públicos, ISPs passaram a implementar um segundo nível de NAT entre o cliente e a Internet — o CGNAT (Carrier-Grade NAT), também conhecido como NAT444 ou Large Scale NAT (LSN):

  │  (privado)        (privado ISP)              (público compartilhado!)    │
  │                                                                         │
  │  Faixa reservada para CGNAT: 100.64.0.0/10 (RFC 6598)                  │

  │                                                                         │

  │  • Impossibilidade de hospedar servidores                               │
  │                                                                         │
  │  No Brasil: muito comum em ISPs de banda larga (economia de IPv4)       │
  │  Solução definitiva: migração para IPv6 (endereços ilimitados)          │
  └─────────────────────────────────────────────────────────────────────────┘

8.4 — NAT Traversal (STUN, TURN, ICE)

Muitas aplicações modernas (VoIP, videoconferência, jogos P2P) precisam estabelecer conexões diretas entre dois clientes, ambos atrás de NAT. Protocolos de NAT Traversal resolvem esse problema:

Protocolo Nome Completo Função Quando Funciona
STUN Session Traversal Utilities for NAT Cliente descobre seu IP público e tipo de NAT consultando servidor STUN NAT tipo Cone (Full, Restricted, Port-Restricted). Falha em Symmetric NAT
TURN Traversal Using Relays around NAT Servidor relay que retransmite tráfego entre os dois clientes Sempre funciona (fallback). Maior latência e custo (relay no meio)
ICE Interactive Connectivity Establishment Framework que tenta múltiplos métodos (direto → STUN → TURN) e escolhe o melhor Sempre (combina todas as técnicas e seleciona a mais eficiente)

💡 NAT Traversal no WebRTC

O WebRTC (usado em Google Meet, Zoom web, Discord no navegador) utiliza o framework ICE obrigatoriamente. Cada peer coleta "candidates" (IPs e portas locais, reflexivos via STUN, e relay via TURN) e testa conectividade. Em ~85% dos casos, STUN é suficiente. Os 15% restantes (symmetric NAT/firewall restritivo) requerem TURN relay, que adiciona ~50-100ms de latência.

8.5 — Impacto do NAT em Protocolos

O NAT "quebra" o princípio end-to-end da Internet. Vários protocolos foram projetados antes do NAT existir e têm problemas quando atravessam dispositivos NAT:

Protocolo Problema com NAT Solução
FTP (Ativo) Servidor tenta conectar de volta ao cliente em porta negociada (impossível através de NAT) FTP Passivo (PASV), ALG no NAT, ou SFTP/SCP
SIP (VoIP) Endereço IP interno no corpo SDP; RTP em portas dinâmicas não mapeadas SIP ALG, STUN, Session Border Controller (SBC), ou VPN
IPSec (AH) AH assina todo o cabeçalho IP (incluindo endereços). NAT modifica → assinatura inválida NAT-T (NAT Traversal): encapsula ESP em UDP 4500
IPSec (ESP) ESP não tem porta (protocolo IP 50). PAT precisa de portas para multiplexar NAT-T (encapsulamento UDP)
H.323 (Vídeo) Múltiplos canais dinâmicos com IPs embutidos nos payloads H.323 ALG ou Session Border Controller
PPTP Usa GRE (protocolo IP 47) sem portas. Múltiplos clientes PPTP atrás de mesmo NAT conflitam PPTP ALG, ou migrar para L2TP/IPSec ou OpenVPN

8.6 — NAT ALG (Application Layer Gateway)

Um NAT ALG é um componente do dispositivo NAT que inspeciona protocolos de camada de aplicação e modifica os endereços IP embutidos nos payloads para que funcionem através do NAT:

⚠️ Cuidado com ALGs

ALGs frequentemente causam mais problemas do que resolvem em redes modernas. O SIP ALG, em particular, é notório por corromper cabeçalhos SIP e quebrar VoIP. Recomendação: Desabilite SIP ALG em roteadores/firewalls e use Session Border Controllers (SBC) dedicados ou configure o VoIP para usar STUN/TURN com portas definidas. Em Cisco IOS: no ip nat service sip.

8.7 — Double NAT e Soluções

O Double NAT ocorre quando existem dois dispositivos fazendo NAT no caminho (ex: roteador do ISP + roteador do cliente). Causa problemas similares ao CGNAT mas em escala doméstica/SMB:

  • Problema: Port forwarding no roteador interno não funciona (ISP NAT bloqueia conexões de entrada)
  • Problema: VPNs podem falhar (especialmente IPSec sem NAT-T)
  • Problema: Jogos online, UPnP e protocos P2P com dificuldades

Soluções:

  1. Colocar o modem/roteador do ISP em modo bridge (apenas modem, sem NAT)
  2. Configurar DMZ no roteador do ISP apontando para o roteador interno
  3. Solicitar IP público fixo ao ISP (elimina o NAT do ISP)
  4. Usar IPv6 (endereçamento end-to-end sem NAT)

Seção 9

VPN — Tipos e Protocolos

Virtual Private Networks (VPNs) criam túneis criptografados sobre redes públicas, permitindo comunicação segura entre sites remotos ou usuários móveis. Domine os protocolos IPSec, OpenVPN, WireGuard e as arquiteturas de VPN modernas.

9.1 — Visão Geral e Casos de Uso

Uma VPN (Virtual Private Network) é uma tecnologia que cria um canal de comunicação seguro (túnel criptografado) sobre uma infraestrutura de rede não confiável (tipicamente a Internet). Os principais casos de uso incluem:

  • Site-to-Site VPN: Conecta duas redes corporativas através da Internet (filial ↔ matriz). Roteadores/firewalls em cada ponta estabelecem o túnel permanente
  • Remote Access VPN: Permite que funcionários remotos acessem a rede corporativa de qualquer lugar (home office, viagem). Cliente VPN no laptop/celular
  • Extranet VPN: Conecta redes de parceiros comerciais com acesso limitado a recursos específicos
  • Bypass de censura/geolocalização: Usuários individuais mascarando localização (uso pessoal)
  • Proteção em redes públicas: Criptografia de tráfego em Wi-Fi de aeroportos, cafés, hotéis

💡 VPN — Propriedades de Segurança

  • Confidencialidade: Dados criptografados (AES-256, ChaCha20) — ininteligíveis para interceptadores
  • Integridade: Dados verificados contra alteração (HMAC-SHA256, Poly1305)
  • Autenticação: Identidade dos peers verificada (certificados, PSK, tokens)
  • Anti-replay: Pacotes duplicados/reordenados são detectados e descartados

9.2 — Site-to-Site VPN (IPSec)

9.3 — IPSec em Detalhe (IKE, ESP, AH)

O IPSec (IP Security) é um framework de protocolos que oferece segurança na camada de rede (Layer 3). Composto por:

🔑 IKE (Internet Key Exchange)

  • Função: Negociação de parâmetros e troca de chaves
  • IKEv1: 2 fases (Main/Aggressive Mode + Quick Mode)
  • IKEv2: Mais eficiente (4 mensagens), suporta MOBIKE, EAP
  • Porta: UDP 500 (ou UDP 4500 com NAT-T)
  • Fase 1: Autentica peers, estabelece IKE SA (ISAKMP SA)
  • Fase 2: Negocia IPSec SA (parâmetros de criptografia do túnel)
  • Autenticação: PSK (Pre-Shared Key) ou Certificados digitais (PKI)

🔒 ESP e AH

  • ESP (Encapsulating Security Payload):
  • — Protocolo IP 50
  • — Criptografia + Integridade + Anti-replay
  • — Modo Tunnel: encapsula pacote inteiro (novo header IP)
  • — Modo Transport: apenas payload criptografado (header IP original)
  • AH (Authentication Header):
  • — Protocolo IP 51
  • — Apenas integridade e autenticação (SEM criptografia)
  • — Incompatível com NAT (assina header IP incluindo endereços)
  • — Raramente usado hoje (ESP faz tudo que AH faz + criptografia)

📋 Parâmetros de Negociação IPSec


  ═══ IKE Phase 1 (IKE SA / ISAKMP SA) ═══
  Ambos os peers precisam concordar em:
  • Algoritmo de criptografia: AES-128, AES-256, 3DES (legado)
  • Algoritmo de hash/integridade: SHA-256, SHA-384, SHA-512, MD5 (inseguro)
  • Grupo Diffie-Hellman: Grupo 14 (2048-bit), 19 (ECP-256), 20 (ECP-384), 21 (ECP-521)
  • Método de autenticação: PSK ou RSA Certificates
  • Lifetime: 86400 segundos (24h) típico

  ═══ IKE Phase 2 (IPSec SA) ═══
  • Algoritmo de criptografia: AES-256-GCM (recomendado), AES-256-CBC
  • Algoritmo de integridade: SHA-256-HMAC, SHA-384-HMAC (ou integrado no GCM)
  • Protocolo: ESP (quase sempre) ou AH
  • Modo: Tunnel (site-to-site) ou Transport (host-to-host)
  • PFS (Perfect Forward Secrecy): Sim — novo DH a cada rekey
  • Lifetime: 3600 segundos (1h) ou por volume de dados (ex: 4GB)
  • Proxy IDs / Traffic Selectors: quais redes passam pelo túnel

  ═══ Algoritmos Recomendados (2024) ═══
  EVITAR: 3DES, MD5, SHA-1, DH Grupo 1/2/5 (inseguros/deprecated)
  USAR: AES-256-GCM, SHA-256+, DH Grupo 14+ ou ECDH (19/20/21)

9.6 — MPLS VPN e SD-WAN (Visão Geral)

Para redes corporativas de grande porte, existem tecnologias de VPN gerenciadas por operadoras e soluções modernas de WAN:

🏢 MPLS VPN

  • L3VPN (VPN de Camada 3): Operadora roteia pacotes IP entre sites do cliente. Usa VRF (Virtual Routing and Forwarding) para isolar tráfego entre clientes. Protocolos: MP-BGP + MPLS labels
  • L2VPN (VPN de Camada 2): Extensão de LAN entre sites (VPLS, EVPN). Transparente: frames Ethernet entre sites como se fossem a mesma LAN
  • Vantagens: SLA garantido, QoS, baixa latência, sem necessidade de criptografia (rede privada do ISP)
  • Desvantagens: Custo MUITO alto, dependência do ISP, provisioning lento (semanas), difícil escalar globalmente

🌐 SD-WAN

  • Conceito: Software-Defined WAN — abstrai a camada de transporte (MPLS, Internet, 4G/5G) com overlay inteligente
  • Funcionalidades: Seleção dinâmica de caminho, QoS por aplicação, balanceamento de links, zero-touch provisioning
  • Vantagens: Usa links Internet baratos, visibilidade por aplicação, deploy em minutos, gerenciamento centralizado
  • Vendors: Cisco Viptela, VMware VeloCloud, Fortinet, Palo Alto Prisma SD-WAN, Silver Peak (Aruba)
  • Tendência: Substituindo MPLS em muitas organizações (custo 50-80% menor)

Outros Serviços de Rede Essenciais

Além de DNS, DHCP, NAT e VPN, diversas aplicações e protocolos de apoio são fundamentais para o funcionamento e gerenciamento de redes. Conheça NTP, SNMP, Syslog, protocolos de transferência de arquivos, web e autenticação.

11.1 — NTP (Network Time Protocol)

O NTP sincroniza os relógios de todos os dispositivos na rede com fontes de tempo precisas. Pode parecer trivial, mas a sincronização de tempo é crítica para:

  • Segurança: Certificados TLS, Kerberos (tolerância 5min), tokens TOTP, DNSSEC
  • Logs e auditoria: Correlação de eventos entre dispositivos (se timestamps divergem, investigação forense é impossível)
  • Protocolos distribuídos: Replicação de banco de dados, consensus (Raft/Paxos), causalidade
  • Transações financeiras: Regulamentações exigem timestamps precisos (MiFID II: 100μs)
  • Backups: Incremental backup depende de timestamps de modificação de arquivos

📋 NTP — Conceitos e Configuração


  ═══ Hierarquia NTP (Stratum) ═══
  Stratum 0: Relógios de referência (GPS, relógio atômico) — não na rede
  Stratum 1: Servidores conectados diretamente a Stratum 0 (altíssima precisão)
  Stratum 2: Sincronizados com Stratum 1 (servidores públicos NTP)
  Stratum 3: Sincronizados com Stratum 2 (servidores NTP corporativos)
  ... até Stratum 15 (máximo)
  Stratum 16: Não sincronizado (insane/unreachable)

  ═══ Portas e Protocolo ═══
  • UDP 123
  • Precisão típica: 1-10ms via Internet, <1ms em LAN

  ═══ Configuração Linux (/etc/ntp.conf ou chrony) ═══
  # Usando Chrony (recomendado para Linux moderno)
  $ sudo apt install chrony
  $ cat /etc/chrony/chrony.conf
  # Servidores NTP brasileiros (NIC.br)
  server a.ntp.br iburst
  server b.ntp.br iburst
  server c.ntp.br iburst
  # Pool global como fallback
  pool pool.ntp.org iburst maxsources 4

  $ chronyc tracking          # Ver status de sincronização
  $ chronyc sources -v        # Ver fontes NTP e qualidade

  ═══ Configuração Cisco IOS ═══
  Router(config)# ntp server 200.160.0.8         ! a.ntp.br
  Router(config)# ntp server 200.189.40.8        ! b.ntp.br
  Router(config)# clock timezone BRT -3
  Router# show ntp status
  Router# show ntp associations

  ═══ AWS — Time Sync Service ═══
  • Amazon Time Sync: 169.254.169.123 (acessível de qualquer EC2)
  • Chrony pré-configurado em Amazon Linux 2
  • Stratum 1 (GPS + relógio atômico em cada região)
  • Protocolo NTP na porta UDP 123 via link-local

  ═══ Componentes SNMP ═══
  • Manager (NMS): Software que monitora (Zabbix, Nagios, PRTG, Datadog)
  • Agent: Processo no dispositivo monitorado que responde consultas
  • MIB (Management Information Base): "dicionário" de OIDs que o agent conhece

  ═══ Operações ═══
  • GET: Manager solicita valor de um OID específico
  • GET-NEXT: Manager solicita próximo OID na árvore MIB
  • GET-BULK (v2c+): Manager solicita múltiplos OIDs de uma vez
  • SET: Manager altera valor de um OID (configuração remota)
  • TRAP: Agent envia notificação NÃO SOLICITADA ao Manager (evento/alarme!)
  • INFORM (v2c+): Como TRAP, mas com confirmação (ACK do manager)

  ═══ Portas ═══
  • UDP 161: Consultas (GET/SET) — Manager → Agent
  • UDP 162: Traps/Informs — Agent → Manager

  ═══ OIDs Comuns (exemplos) ═══
  • 1.3.6.1.2.1.1.1.0 — sysDescr (descrição do sistema)
  • 1.3.6.1.2.1.1.3.0 — sysUpTime (tempo desde último reboot)
  • 1.3.6.1.2.1.2.2.1.10 — ifInOctets (bytes recebidos na interface)
  • 1.3.6.1.2.1.2.2.1.16 — ifOutOctets (bytes enviados na interface)
  • 1.3.6.1.4.1.9.9.109.1.1.1.1.6 — cpmCPUTotal5minRev (CPU 5min Cisco)

  ═══ Configuração Cisco IOS (SNMPv3 — seguro) ═══
  Router(config)# snmp-server group MONITOR v3 priv
  Router(config)# snmp-server user admin MONITOR v3 auth sha MyAuthPass priv aes 128 MyPrivPass
  Router(config)# snmp-server host 10.0.0.100 version 3 priv admin
  Router(config)# snmp-server enable traps

  ═══ Teste com snmpwalk (Linux) ═══
  $ snmpwalk -v3 -l authPriv -u admin -a SHA -A MyAuthPass -x AES -X MyPrivPass 192.168.1.1 system

11.5 — Protocolos de Email

Os protocolos de email formam um ecossistema com funções distintas:

📤 SMTP (Envio)

  • Função: Envio e relay de emails entre servidores
  • Portas: 25 (relay entre servers), 587 (submission com AUTH), 465 (SMTPS legado)
  • Segurança: STARTTLS (upgrade para TLS) na porta 587
  • Direção: Cliente → Servidor → Servidor destino

📥 IMAP / POP3 (Recebimento)

  • IMAP (143/993): Mensagens ficam no servidor, sincronizadas entre dispositivos. Pastas, flags, busca server-side
  • POP3 (110/995): Baixa mensagens para o cliente e remove do servidor (modelo antigo)
  • Recomendação: IMAP é o padrão moderno (multi-device)
  • Segurança: IMAPS (993) e POP3S (995) com TLS

11.6 — RADIUS e TACACS+ (AAA)

Protocolos de AAA (Authentication, Authorization, Accounting) centralizam o controle de acesso a dispositivos de rede e serviços:

Característica RADIUS TACACS+
Desenvolvido por IETF (RFC 2865/2866) Cisco (proprietário, mas amplamente adotado)
Protocolo UDP 1812 (auth) / 1813 (accounting) TCP 49
Criptografia Apenas a senha é criptografada Payload INTEIRO é criptografado
AAA Authentication + Authorization combinados em um pacote Authentication, Authorization e Accounting SEPARADOS (granular)
Autorização Tudo-ou-nada (perfil completo retornado na autenticação) Por comando (pode autorizar comandos individualmente)
Uso principal Acesso à rede: Wi-Fi (802.1X), VPN, dial-up Administração de dispositivos: login em routers/switches
Exemplos de servidores FreeRADIUS, Microsoft NPS, Cisco ISE Cisco ISE, TACACS+ daemon, Cisco ACS (legado)

💡 Quando usar cada protocolo

RADIUS é ideal para autenticação de acesso à rede (802.1X em switches/Wi-Fi, VPN remote access, autenticação de usuários em geral). TACACS+ é ideal para controle de acesso administrativo a equipamentos de rede (quem pode executar quais comandos em quais roteadores/switches). Em muitos ambientes enterprise, ambos coexistem: RADIUS para acesso de usuários à rede + TACACS+ para administradores de rede.

Exercício 1 — Resolução DNS

Um usuário reporta que não consegue acessar www.empresa.com.br pelo navegador, mas consegue acessar o mesmo servidor pelo IP 192.0.2.100. O comando nslookup www.empresa.com.br retorna "DNS request timed out". Quais são as possíveis causas e como você faria o troubleshooting?

💡 Resposta

Diagnóstico e Troubleshooting

Análise: O fato de o acesso por IP funcionar mas por nome não, confirma que o problema é exclusivamente DNS (rede está OK).

Possíveis causas:

  1. Servidor DNS inacessível: O servidor DNS configurado no cliente pode estar down ou inalcançável
  2. Firewall bloqueando UDP/TCP 53: Tráfego DNS pode estar sendo filtrado
  3. Servidor DNS sobrecarregado: Timeout por excesso de consultas
  4. Configuração DNS incorreta no cliente: IP do servidor DNS errado

Passos de troubleshooting:

  1. ipconfig /all (Windows) ou cat /etc/resolv.conf (Linux) — verificar DNS configurado
  2. ping 8.8.8.8 — testar conectividade geral
  3. nslookup www.empresa.com.br 8.8.8.8 — testar com DNS alternativo
  4. nslookup www.empresa.com.br 1.1.1.1 — testar com outro DNS público
  5. Se DNS alternativo funcionar → problema no DNS primário configurado
  6. Se nenhum DNS funcionar → firewall bloqueando porta 53
  7. traceroute/tracert para o IP do servidor DNS
  8. Verificar Windows DNS Client Service (services.msc)

Exercício 2 — DHCP Troubleshooting

Em uma rede corporativa, alguns computadores na VLAN 20 (192.168.20.0/24) recebem endereços IP na faixa 169.254.x.x (APIPA). O servidor DHCP está na VLAN 1 (10.0.1.0/24) e funciona corretamente para clientes na VLAN 1. O que pode estar errado e como resolver?

💡 Resposta

Diagnóstico

169.254.x.x (APIPA) indica que o cliente enviou DHCP Discover mas NÃO recebeu nenhum Offer. Como o servidor funciona na VLAN 1 mas não na VLAN 20:

Causa mais provável: Falta do DHCP Relay Agent (ip helper-address) na interface do roteador/L3 switch para a VLAN 20.

Por quê: O DHCP Discover é broadcast e não atravessa roteadores. Como o servidor DHCP está em outra VLAN/sub-rede, é necessário um relay para encaminhar as mensagens DHCP.

Solução:

Switch(config)# interface vlan 20
Switch(config-if)# ip helper-address 10.0.1.50
!                   ↑ IP do servidor DHCP na VLAN 1

Verificações adicionais:

  • Verificar se o servidor DHCP tem um scope configurado para 192.168.20.0/24
  • Confirmar que há rota de retorno do servidor DHCP para a VLAN 20
  • Verificar ACLs que possam bloquear UDP 67/68
  • show ip dhcp relay statistics — ver se relay está recebendo/encaminhando

Exercício 3 — NAT e Conectividade

Uma empresa tem a seguinte configuração: rede interna 10.0.0.0/24, roteador com PAT configurado usando IP público 200.100.50.1. Um servidor web interno (10.0.0.80) possui NAT estático para 200.100.50.80. Funcionários internos reportam que não conseguem acessar o site da empresa usando o URL público (http://200.100.50.80). O que está acontecendo e quais são as soluções?

💡 Resposta

Problema: NAT Hairpinning

Este é um caso clássico de NAT Hairpinning (NAT Loopback). Quando um host interno (10.0.0.x) tenta acessar outro host interno pelo IP público (200.100.50.80):

  1. PC (10.0.0.10) envia pacote para 200.100.50.80
  2. Roteador faz DNAT: destino muda para 10.0.0.80
  3. Servidor responde diretamente ao PC (10.0.0.10) com source 10.0.0.80
  4. PC esperava resposta de 200.100.50.80, recebe de 10.0.0.80 → DESCARTA

Soluções (da melhor para a pior):

  1. Split-Brain DNS (MELHOR): DNS interno resolve empresa.com → 10.0.0.80 (direto). DNS externo resolve → 200.100.50.80
  2. Hairpin NAT no roteador: Configurar o roteador para fazer NAT de source E destination quando o tráfego é inside→inside via IP público
  3. NAT Loopback: Cisco: ip nat inside source static 10.0.0.80 200.100.50.80 + rota adequada
  4. Hosts file: Adicionar entrada em /etc/hosts (não escalável)

Exercício 4 — VPN Design

Uma empresa com sede em São Paulo precisa conectar 3 filiais (Rio, BH, Curitiba) à VPC AWS na região us-east-1. Requisitos: tolerância a falhas, roteamento dinâmico, capacidade de comunicação entre filiais (mesh parcial). Qual arquitetura VPN você recomendaria na AWS e por quê?

💡 Resposta

Arquitetura Recomendada: Transit Gateway com VPN

Solução: AWS Transit Gateway (TGW) com VPN Site-to-Site para cada filial.

Justificativa:

  • Transit Gateway funciona como hub central — cada filial precisa de apenas 1 conexão VPN
  • TGW suporta roteamento transitivo: Rio pode falar com BH via TGW (sem VPN direta)
  • Cada VPN tem 2 túneis (HA automática com DPD failover)
  • BGP para roteamento dinâmico — failover automático, anúncio de rotas sem configuração manual
  • Route tables no TGW para segmentação (se necessário isolar filiais)

Arquitetura:

SP (matriz) ──VPN──┐
Rio (filial) ──VPN──┤── Transit Gateway ──→ VPC (us-east-1)
BH (filial) ───VPN──┤
Curitiba ──────VPN──┘

Roteamento: BGP (ASN privado por filial)
Failover: automático (2 túneis por VPN + BGP reconvergência)

Alternativa com melhor performance: Direct Connect (se o budget permitir) com VPN como backup.

Exercício 5 — Registros DNS

Você precisa configurar o DNS para o domínio minhaempresa.com.br com os seguintes requisitos: (a) site principal em CloudFront (d123.cloudfront.net), (b) email via Google Workspace, (c) subdomínio api apontando para um ALB, (d) verificação SPF, (e) registro CAA permitindo apenas Let's Encrypt. Quais registros DNS você criaria?

💡 Resposta

Configuração DNS Completa

; ─── Apex e WWW (CloudFront) ───
@       IN  ALIAS   d123.cloudfront.net.        ; Route 53 Alias Record (apex)
www     IN  CNAME   d123.cloudfront.net.        ; CNAME para www

; ─── API (Application Load Balancer) ───
api     IN  ALIAS   my-alb-123.us-east-1.elb.amazonaws.com.  ; Alias para ALB

; ─── Email (Google Workspace) ───
@       IN  MX  1   aspmx.l.google.com.
@       IN  MX  5   alt1.aspmx.l.google.com.
@       IN  MX  5   alt2.aspmx.l.google.com.
@       IN  MX  10  alt3.aspmx.l.google.com.
@       IN  MX  10  alt4.aspmx.l.google.com.

; ─── SPF (autorização de envio de email) ───
@       IN  TXT     "v=spf1 include:_spf.google.com ~all"

; ─── DMARC ───
_dmarc  IN  TXT     "v=DMARC1; p=quarantine; rua=mailto:dmarc@minhaempresa.com.br"

; ─── CAA (apenas Let's Encrypt pode emitir certificados) ───
@       IN  CAA 0 issue "letsencrypt.org"
@       IN  CAA 0 iodef "mailto:security@minhaempresa.com.br"

Notas:

  • ALIAS/ANAME é usado no apex porque CNAME não é permitido no apex do domínio
  • No Route 53, use Alias Records (gratuitos para recursos AWS)
  • SPF deve incluir _spf.google.com para Google Workspace
  • CAA com issue "letsencrypt.org" restringe emissão de certificados

Exercício 6 — DHCP Snooping

Em um switch Cisco 2960 com 48 portas, as portas 1-44 conectam PCs de usuários (VLAN 10), as portas 45-46 são uplinks para o switch core (onde está o servidor DHCP), e as portas 47-48 são para access points Wi-Fi. Configure DHCP Snooping para proteger contra rogue DHCP servers. Quais portas devem ser trusted?

💡 Resposta

Configuração DHCP Snooping

! Habilitar DHCP Snooping
Switch(config)# ip dhcp snooping
Switch(config)# ip dhcp snooping vlan 10

! Portas TRUSTED: apenas uplinks (onde o DHCP legítimo está)
! Portas 45-46 são trusted (path para o servidor DHCP)
Switch(config)# interface range GigabitEthernet0/45-46
Switch(config-if-range)# ip dhcp snooping trust
Switch(config-if-range)# exit

! Portas UNTRUSTED: todas as portas de acesso (PCs e APs)
! Portas 1-44 (PCs) e 47-48 (APs) — untrusted por padrão
Switch(config)# interface range FastEthernet0/1-44
Switch(config-if-range)# ip dhcp snooping limit rate 10
Switch(config-if-range)# exit

Switch(config)# interface range FastEthernet0/47-48
Switch(config-if-range)# ip dhcp snooping limit rate 50
!                         ↑ Rate maior para APs (múltiplos clientes Wi-Fi)
Switch(config-if-range)# exit

! Verificação
Switch# show ip dhcp snooping
Switch# show ip dhcp snooping binding

Explicação:

  • Trusted: Apenas portas 45-46 (uplinks) — porque o servidor DHCP legítimo está acessível por esses uplinks
  • Untrusted: Portas 1-44 (PCs) e 47-48 (APs) — qualquer DHCP Offer/ACK vindo dessas portas será bloqueado
  • Rate limit de 10 para PCs (normais não geram mais que 1-2 DHCP/seg)
  • Rate limit de 50 para APs (servem múltiplos clientes Wi-Fi simultâneos)

Exercício 7 — CGNAT e IPv6

Um cliente reporta que não consegue hospedar um servidor de jogo em casa (port forwarding configurado no roteador doméstico não funciona). Ao verificar o IP WAN do roteador, ele mostra 100.72.45.210. Explique o problema e as possíveis soluções.

💡 Resposta

Problema: CGNAT (Carrier-Grade NAT)

Diagnóstico: O IP WAN 100.72.45.210 está na faixa 100.64.0.0/10 (100.64.0.0 — 100.127.255.255), que é reservada para CGNAT pela RFC 6598. Isso significa que o ISP está usando NAT na infraestrutura dele (double NAT).

Por que port forwarding não funciona:

  1. O roteador doméstico faz port forward para o PC (NAT 1 — funciona)
  2. MAS o IP 100.72.45.210 não é público — é privado do ISP
  3. O ISP faz outro NAT (NAT 2) compartilhando um IP público entre muitos clientes
  4. Conexões de entrada da Internet não chegam ao cliente (ISP não faz port forward)

Soluções:

  1. Solicitar IP público ao ISP: Alguns ISPs oferecem IP público fixo (pode ter custo adicional)
  2. Usar IPv6: Se o ISP oferece IPv6, cada dispositivo tem IP público global (sem NAT). Configurar o servidor com IPv6
  3. VPN com relay: Usar um VPS com IP público como relay (ex: WireGuard tunnel)
  4. Serviços de tunneling: Cloudflare Tunnel, ngrok, pagekite (relay público gratuito/barato)
  5. UPnP via IGD do ISP: Alguns CGNAT suportam PCP (Port Control Protocol) — raro
  6. Trocar de ISP: Escolher um que forneça IP público nativo

Exercício 8 — VPN Cloud

Sua empresa está migrando para AWS e precisa de conectividade híbrida. O requisito é: 2 Gbps de throughput consistente, latência abaixo de 50ms para a região sa-east-1 (São Paulo), e os dados não podem trafegar pela Internet pública por compliance. Qual serviço AWS você recomendaria e por quê? Uma VPN Site-to-Site atenderia?

💡 Resposta

Recomendação: AWS Direct Connect

Por que VPN Site-to-Site NÃO atende:

  • Throughput máximo por túnel VPN: ~1.25 Gbps (abaixo dos 2 Gbps necessários)
  • Latência via Internet é variável (não garante <50ms consistentemente)
  • Dados trafegam pela Internet pública (falha no requisito de compliance)

Por que Direct Connect atende todos os requisitos:

  • Throughput: Porta dedicada de 1 Gbps ou 10 Gbps (2x 1G para 2 Gbps com ECMP via TGW)
  • Latência: Conexão dedicada, consistente e previsível (<5ms em datacenters próximos ao PoP AWS São Paulo)
  • Compliance: Tráfego NUNCA passa pela Internet pública — vai por fibra dedicada entre datacenter e AWS
  • HA: 2 conexões DX em locations diferentes para SLA 99.99%

Complemento recomendado: VPN Site-to-Site como backup/failover do Direct Connect (menor custo que DX redundante completo, mas com tráfego pela Internet em caso de falha do DX).

Opção com criptografia: Se necessário criptografar dados mesmo no DX: configurar VPN IPSec SOBRE o Direct Connect (MACsec também disponível para 10/100 Gbps).

Exercício 9 — DNS Security

O time de segurança detectou que várias máquinas na rede estão fazendo consultas DNS com subdomínios muito longos e com aparência de dados codificados em Base64 (ex: dGhpcyBpcyBhIHRlc3Q.exfil.attacker.com). O volume de consultas DNS para este domínio é anormalmente alto. O que provavelmente está acontecendo e como responder?

💡 Resposta

Diagnóstico: DNS Tunneling / Exfiltração de Dados

O que está acontecendo: As máquinas estão infectadas com malware que usa DNS Tunneling para exfiltrar dados. Os dados são codificados (Base64/Base32) e enviados como subdomínios de um domínio controlado pelo atacante.

Indicadores de comprometimento (IoC):

  • Subdomínios com mais de 50 caracteres e padrão Base64
  • Volume anômalo de consultas para um único domínio desconhecido
  • Consultas do tipo TXT ou NULL (podem carregar mais dados na resposta)
  • Alta entropia nos labels do subdomínio (dados aleatórios = alta entropia)

Resposta ao incidente:

  1. Bloquear imediatamente o domínio attacker.com no DNS resolver/firewall (DNS sinkhole)
  2. Identificar máquinas infectadas via logs DNS (quais IPs estão consultando o domínio)
  3. Isolar máquinas comprometidas da rede (quarentena VLAN ou desconectar)
  4. Investigar o malware nas máquinas (antivírus, EDR, análise forense)
  5. Implementar controles preventivos:
    • DNS firewall/RPZ (Response Policy Zone) com feeds de threat intelligence
    • Monitoramento de anomalias DNS (ferramentas SIEM com regras de detecção)
    • Bloquear DNS direto (forçar todo DNS pelo proxy/resolver interno)
    • Limitar tamanho de consultas DNS no firewall

Exercício 10 — WireGuard vs IPSec

Sua startup precisa implementar VPN para 50 funcionários remotos acessarem a infraestrutura na AWS. O time é pequeno, o orçamento é limitado, e a prioridade é simplicidade e performance. Compare WireGuard vs AWS Client VPN (OpenVPN-based) para este cenário. Qual você recomendaria?

Análise Comparativa para o Cenário
