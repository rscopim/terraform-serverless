Migração e Modernização (20%)

Estratégias de migração (6 Rs), serviços de migração, transferência de dados e modernização de workloads para a nuvem AWS.

6 Rs de Migração

Estratégias para migrar workloads para a nuvem, ordenadas por complexidade crescente:

EstratégiaDescriçãoEsforçoQuando Usar
Rehost (Lift & Shift)Mover para a nuvem sem modificações. Mesmo OS, mesmo app.BaixoMigração rápida, deadline apertado, apps legados
Replatform (Lift & Reshape)Pequenas otimizações sem mudar a arquitetura core. Ex: migrar DB para RDS.Médio-BaixoGanhos rápidos sem refactoring completo
Repurchase (Drop & Shop)Substituir por SaaS. Ex: CRM on-prem → Salesforce.MédioSoftware comercial com equivalente SaaS melhor
Refactor (Re-architect)Redesenhar a aplicação para ser cloud-native (microserviços, serverless).AltoNecessidade de escala, agilidade, features cloud-native
RetireDesligar aplicações que não são mais necessárias.BaixoApps redundantes, sem uso, ou substituídos
Retain (Revisit)Manter on-premises por enquanto. Migrar depois.NenhumCompliance, dependências complexas, não pronto
RehostLift & Shift
Ferramentas:
• AWS Application Migration Service (MGN)
  → Replicação contínua de servidores
  → Cutover com mínimo downtime
  → Suporta Windows e Linux
• VM Import/Export
• CloudEndure Migration (predecessor do MGN)

Processo:
1. Instalar agente no servidor source
2. Replicação contínua para AWS
3. Test instances (validação)
4. Cutover (migração final)
5. Desligar source

Vantagens:
• Mais rápido de executar
• Menor risco (sem mudanças no app)
• Pode otimizar depois (replatform/refactor)
ReplatformLift & Reshape
Exemplos comuns:
• MySQL on-prem → Amazon RDS MySQL
• Self-managed Redis → ElastiCache
• Apache on EC2 → Elastic Beanstalk
• Monolith on EC2 → ECS (containerizar)
• Cron jobs → EventBridge + Lambda

Benefícios sem refactoring completo:
• Managed services (menos operação)
• Auto-scaling, backups automáticos
• Multi-AZ (alta disponibilidade)
• Patching automático

Quando escolher:
• App funciona bem mas infra é pesada
• Quer benefícios de managed services
• Não tem tempo/budget para refactor completo
RefactorRe-architect
Padrões de modernização:
• Monolith → Microserviços
• Synchronous → Event-driven (SQS, SNS, EventBridge)
• Relational → Purpose-built databases
• Batch → Real-time streaming (Kinesis)
• On-prem storage → S3 data lake

Tecnologias cloud-native:
• Containers: ECS/EKS + Fargate
• Serverless: Lambda + API Gateway + DynamoDB
• Event-driven: EventBridge + Step Functions
• CI/CD: CodePipeline + CodeBuild + CodeDeploy

Quando escolher:
• Necessidade de escala massiva
• Time-to-market é prioridade
• Custos operacionais muito altos
• Features que só existem na cloud

Serviços de Migração

AWS Migration HubCentral

Painel centralizado para rastrear o progresso de migrações de múltiplas ferramentas.

Funcionalidades:
• Dashboard unificado de migração
• Rastreia progresso de múltiplas ferramentas
• Integra com: MGN, DMS, Application Discovery
• Strategy Recommendations: sugere estratégia (6 Rs)
• Refactor Spaces: gerencia refactoring incremental

Migration Hub Orchestrator:
• Workflows pré-definidos para migração
• Templates para SAP, SQL Server, etc.
• Automação de steps comuns
Application Discovery ServiceDescoberta

Descobre servidores on-premises, dependências e padrões de uso para planejar migração.

Modos:
• Agentless (via VMware vCenter):
  → Informações básicas: CPU, memória, disco, rede
  → Sem instalar nada nos servidores
  → Bom para inventário inicial

• Agent-based:
  → Informações detalhadas + dependências
  → Processos rodando, conexões de rede
  → Mapa de dependências entre servidores
  → Necessário para planejamento detalhado

Integração:
• Migration Hub (visualização)
• Athena (queries nos dados coletados)
• QuickSight (dashboards de inventário)
AWS DMSDatabase Migration

Migra bancos de dados para AWS com mínimo downtime. Suporta migrações homogêneas e heterogêneas.

Tipos de migração:
• Homogênea: MySQL → RDS MySQL (mesmo engine)
• Heterogênea: Oracle → Aurora PostgreSQL (diferente)
  → Requer SCT (Schema Conversion Tool) primeiro

Modos:
• Full Load: copia todos os dados uma vez
• CDC (Change Data Capture): replicação contínua
• Full Load + CDC: copia tudo + mantém sincronizado

Características:
• Replication Instance: EC2 que executa a migração
• Source e Target endpoints
• Suporta: Oracle, SQL Server, MySQL, PostgreSQL,
  MongoDB, DynamoDB, S3, Redshift, Kinesis
• Multi-AZ para alta disponibilidade

AWS SCT (Schema Conversion Tool):
• Converte schema entre engines diferentes
• Identifica incompatibilidades
• Gera relatório de assessment
• Converte stored procedures, views, triggers

Transferência de Dados

AWS DataSyncTransferência

Transferência de dados automatizada e acelerada entre on-premises e AWS (ou entre serviços AWS).

Características:
• Até 10x mais rápido que ferramentas open-source
• Agente on-premises (VM ou EC2)
• Criptografia em trânsito (TLS)
• Verificação de integridade automática
• Scheduling (transferências periódicas)
• Bandwidth throttling

Origens/Destinos:
• NFS, SMB, HDFS, self-managed object storage
• S3, EFS, FSx (Windows, Lustre, ONTAP, OpenZFS)
• Transferência entre serviços AWS (S3 → EFS)

Quando usar:
• Migração de dados para AWS
• Replicação periódica (backup)
• Transferência entre regiões/contas
• Mover dados entre storage services

vs Storage Gateway:
• DataSync: transferência/migração (mover dados)
• Storage Gateway: acesso híbrido contínuo (usar dados)
AWS Transfer FamilyProtocolos

Transferência de arquivos gerenciada via SFTP, FTPS, FTP e AS2 diretamente para S3 ou EFS.

Protocolos suportados:
• SFTP (SSH File Transfer Protocol)
• FTPS (FTP over SSL)
• FTP (File Transfer Protocol)
• AS2 (Applicability Statement 2)

Características:
• Endpoint público ou VPC
• Autenticação: service-managed, AD, custom (Lambda)
• Integra com S3 e EFS como backend
• IP estático (Elastic IP)
• Managed workflows (post-upload processing)

Quando usar:
• Parceiros/clientes enviam arquivos via SFTP
• Substituir servidor SFTP on-premises
• Compliance requer protocolos específicos
• B2B file exchange (AS2 para EDI)
AWS Snow FamilyOffline

Dispositivos físicos para transferência massiva de dados quando a rede não é viável.

Dispositivos:
┌─────────────────────────────────────────────────┐
│ Snowcone       │ 8 TB (HDD) ou 14 TB (SSD)     │
│                │ Portátil, edge computing        │
│                │ DataSync agent integrado        │
├─────────────────────────────────────────────────┤
│ Snowball Edge  │ Storage Optimized: 80 TB       │
│                │ Compute Optimized: 42 TB + GPU  │
│                │ Edge computing (EC2, Lambda)    │
├─────────────────────────────────────────────────┤
│ Snowmobile     │ 100 PB (caminhão)              │
│                │ Para migrações >10 PB          │
│                │ Segurança física extrema        │
└─────────────────────────────────────────────────┘

Regra de decisão:
• <10 TB ou boa conectividade → DataSync/Internet
• 10 TB - 10 PB → Snowball Edge
• >10 PB → Snowmobile
• Edge computing remoto → Snowcone/Snowball Edge

Processo:
1. Solicitar dispositivo no console
2. AWS envia o dispositivo
3. Copiar dados para o dispositivo
4. Enviar de volta para AWS
5. AWS carrega dados no S3
Direct Connect para MigraçãoRede Dedicada
Quando usar DX para migração:
• Transferência contínua de grandes volumes
• Latência consistente necessária
• Migração de longa duração (meses)
• Workloads híbridos permanentes

Combinação com outros serviços:
• DX + DataSync: transferência acelerada via DX
• DX + DMS: migração de banco via conexão dedicada
• DX + Storage Gateway: acesso híbrido contínuo

Limitações para migração:
• Lead time: semanas a meses para provisionar
• Custo fixo mensal (porta + transferência)
• Não resolve migração inicial urgente
  → Use VPN como bridge temporária
  → Snow Family para bulk data inicial
  → DX para operação contínua depois

Modernização

ContainerizaçãoContainers
Estratégia de containerização:
1. Containerizar monolith (lift & shift para container)
2. Extrair serviços gradualmente
3. Migrar para orquestrador (ECS/EKS)
4. Adotar Fargate (serverless containers)

AWS App2Container:
• Ferramenta que containeriza apps Java/.NET
• Analisa dependências automaticamente
• Gera Dockerfile e task definitions
• Cria pipeline CI/CD

AWS Copilot:
• CLI para deploy de containers no ECS/Fargate
• Abstrai complexidade de ECS
• Environments, services, pipelines

Padrão Strangler Fig:
• Migrar funcionalidades incrementalmente
• Novo código em microserviços
• Roteamento gradual (API Gateway, ALB)
• Monolith diminui até ser desligado
ServerlessModernização
Padrão serverless completo:
• API: API Gateway + Lambda
• Data: DynamoDB ou Aurora Serverless
• Auth: Cognito
• Storage: S3
• Events: EventBridge + Step Functions
• Messaging: SQS + SNS

Benefícios:
• Zero gerenciamento de servidores
• Escala automática (0 → milhões)
• Paga apenas por uso
• Alta disponibilidade built-in

Quando modernizar para serverless:
• APIs com tráfego variável
• Event processing
• Scheduled tasks (cron)
• Data processing pipelines
• Microserviços com baixo tráfego
Decomposição de MicroserviçosArquitetura
Padrões de decomposição:
• Por domínio de negócio (DDD - Bounded Contexts)
• Por subdomain (core, supporting, generic)
• Por verbo/ação (checkout, inventory, shipping)

Comunicação entre serviços:
• Síncrona: REST/gRPC (API Gateway, ALB)
• Assíncrona: eventos (SQS, SNS, EventBridge)
• Orquestração: Step Functions (workflow central)
• Coreografia: cada serviço reage a eventos

Padrões importantes:
• Saga Pattern: transações distribuídas
  → Orquestração (Step Functions)
  → Coreografia (eventos + compensação)
• CQRS: separar leitura de escrita
• Event Sourcing: estado como sequência de eventos
• Circuit Breaker: evitar cascading failures

Service Mesh (App Mesh):
• Comunicação service-to-service
• Observabilidade, retry, circuit breaker
• mTLS entre serviços

🎯 Para o exame: "Migrar com mínimo downtime" → DMS com CDC + MGN. "Transferir petabytes" → Snow Family. "Migrar servidores" → Application Migration Service (MGN). "Descobrir dependências" → Application Discovery Service. "Modernizar monolith" → Strangler Fig + containers/serverless.
