Otimização de Custos

Modelos de Compra EC2Pricing

Escolher o modelo correto de compra pode reduzir custos em até 72%.

On-Demand:
• Paga por hora/segundo
• Sem compromisso
• Quando: workloads imprevisíveis, curta duração

Reserved Instances (RI):
• 1 ou 3 anos de compromisso
• Até 72% de desconto
• Standard RI: tipo fixo, pode vender no Marketplace
• Convertible RI: pode trocar tipo (menor desconto)
• Quando: workloads estáveis e previsíveis

Savings Plans:
• Compromisso de $/hora por 1 ou 3 anos
• Compute SP: qualquer região, família, OS, tenancy
• EC2 Instance SP: família específica em uma região
• Mais flexível que RI
• Quando: preferir flexibilidade sobre RI

Spot Instances:
• Até 90% de desconto
• Pode ser interrompido (2 min aviso)
• Quando: batch, CI/CD, tolerante a falha

Dedicated Hosts:
• Servidor físico dedicado
• Quando: compliance, licenças por socket/core
Right-Sizing & LifecycleOtimização
AWS Compute Optimizer:
• Analisa utilização de EC2, EBS, Lambda, ECS
• Recomenda instance types ideais
• Baseado em ML (14 dias de métricas)
• Identifica over-provisioned e under-provisioned

Right-Sizing:
• Reduzir instance type se CPU/memória <40%
• Considerar Graviton (ARM) — até 40% melhor preço/performance
• Usar T instances (burstable) para workloads variáveis

S3 Lifecycle Policies:
• Standard → Standard-IA (30+ dias)
• Standard-IA → Glacier Instant (90+ dias)
• Glacier → Deep Archive (180+ dias)
• Expiration: deletar após N dias
• S3 Intelligent-Tiering: automático

Outras otimizações:
• EBS: gp3 vs gp2 (gp3 é mais barato e configurável)
• NAT Gateway: considerar VPC endpoints para S3/DynamoDB
• Data transfer: usar CloudFront, VPC endpoints, mesma AZ
• Idle resources: ELBs sem targets, EIPs não associados

Otimização de Performance

CloudFrontCDN

CDN global que cacheia conteúdo em edge locations para reduzir latência.

Otimizações:
• Cache Policy: controle granular de cache keys
• Origin Request Policy: headers enviados à origin
• Cache behaviors: diferentes configs por path pattern
• Lambda@Edge / CloudFront Functions:
  → Manipular request/response na edge
  → A/B testing, URL rewrite, auth

Performance:
• Compressão automática (gzip, Brotli)
• HTTP/2 e HTTP/3 (QUIC)
• Origin Shield: camada extra de cache
• Regional Edge Caches: entre edge e origin

Segurança:
• OAC (Origin Access Control) para S3
• WAF integration
• Geo-restriction
• Field-level encryption
• Signed URLs / Signed Cookies
Caching StrategiesLatência
ElastiCache (Redis/Memcached):
• Cache de queries de banco de dados
• Session store
• Leaderboards, rate limiting

DAX (DynamoDB Accelerator):
• Cache transparente para DynamoDB
• Microsegundos de latência
• API-compatible (drop-in replacement)

API Gateway Caching:
• Cache de respostas da API
• TTL configurável (300s default)
• Invalidação por header ou flush

CloudFront Caching:
• Conteúdo estático e dinâmico
• TTL por behavior
• Invalidation para forçar refresh

Padrão de decisão:
• DB reads pesados → ElastiCache/DAX
• API responses → API Gateway cache
• Assets/páginas → CloudFront
• Session data → ElastiCache Redis
Read Replicas & Connection PoolingDatabase
Read Replicas:
• RDS: até 15 replicas (Aurora), 5 (outros engines)
• Offload de leitura do primary
• Cross-region replicas para DR e latência
• Promoção para standalone em caso de falha

Aurora Reader Endpoint:
• Load balancing automático entre replicas
• Connection string única para todas as replicas

RDS Proxy:
• Connection pooling gerenciado
• Reduz conexões ao banco (Lambda → RDS)
• Failover mais rápido (66% menos tempo)
• IAM authentication
• Quando: Lambda + RDS (evita connection exhaustion)

Global Accelerator para DB:
• Não aplicável diretamente
• Use Aurora Global Database para multi-região
• Route 53 latency-based para read replicas regionais

Excelência Operacional

Infrastructure as CodeIaC
AWS CloudFormation:
• Templates declarativos (YAML/JSON)
• Stacks: unidade de deploy
• StackSets: deploy multi-conta/multi-região
• Drift Detection: detecta mudanças manuais
• Change Sets: preview de mudanças

AWS CDK (Cloud Development Kit):
• IaC em linguagens de programação
• TypeScript, Python, Java, C#, Go
• Compila para CloudFormation
• Constructs: abstrações reutilizáveis
• Quando: equipes de desenvolvimento preferem código

Terraform:
• Multi-cloud, HCL
• State management
• Quando: multi-cloud ou preferência da equipe

Melhores práticas:
• Versionamento em Git
• CI/CD para infraestrutura
• Ambientes separados (dev/staging/prod)
• Módulos reutilizáveis
• Drift detection periódico
Systems ManagerOperações
Componentes principais:
• Session Manager: acesso SSH sem abrir porta 22
• Patch Manager: patching automatizado
• Parameter Store: configurações e secrets
• Run Command: executar comandos em frota
• Automation: runbooks para tarefas operacionais
• State Manager: configuração desejada
• Inventory: inventário de software/hardware

Automation Runbooks:
• Documentos que definem ações automatizadas
• Aprovação manual opcional
• Integra com EventBridge para triggers
• Exemplos: restart instance, create AMI, remediate Config

OpsCenter:
• Visão centralizada de issues operacionais
• OpsItems: tickets de operação
• Integra com CloudWatch, Config, CloudFormation
• Runbooks para resolução
Config Rules & Auto-RemediationCompliance
AWS Config Rules:
• Avaliam compliance de recursos continuamente
• Managed Rules: 300+ regras pré-definidas
• Custom Rules: Lambda functions
• Organization Rules: aplicar em todas as contas

Auto-Remediation:
• Config Rule detecta non-compliance
• Trigger automático de SSM Automation
• Exemplos:
  → SG aberto → fechar porta
  → S3 sem encryption → habilitar
  → EBS sem backup → criar snapshot
  → Instance sem tag → adicionar tag

Conformance Packs:
• Conjunto de Config Rules + Remediations
• Templates pré-definidos (PCI-DSS, HIPAA, etc.)
• Deploy via Organizations (multi-conta)

Fluxo:
Config Rule (detecta) → SSM Automation (remedia)
                      → EventBridge (notifica)
                      → Security Hub (agrega)

Confiabilidade

Multi-AZ & Multi-RegionHA
Multi-AZ (Alta Disponibilidade):
• RDS Multi-AZ: failover automático (standby síncrono)
• Aurora: 6 cópias em 3 AZs, failover <30s
• ELB: distribui tráfego entre AZs
• ASG: instâncias em múltiplas AZs
• S3: replicação automática em 3+ AZs
• EFS: multi-AZ por padrão

Multi-Region (DR + Latência):
• Aurora Global Database: <1s replication lag
• DynamoDB Global Tables: active-active multi-region
• S3 Cross-Region Replication (CRR)
• CloudFront: cache global
• Route 53: latency-based / failover routing
• API Gateway: regional endpoints por região

Decisão:
• HA dentro de uma região → Multi-AZ
• DR ou latência global → Multi-Region
• Ambos para máxima resiliência
Route 53 FailoverDNS
Routing Policies:
• Simple: um registro, um destino
• Weighted: distribuir % entre destinos
• Latency: rota para região mais próxima
• Failover: primary/secondary com health check
• Geolocation: rota por localização do usuário
• Geoproximity: rota por proximidade (com bias)
• Multivalue: múltiplos IPs com health check

Health Checks:
• Endpoint: HTTP/HTTPS/TCP para IP ou domínio
• Calculated: combina múltiplos health checks (AND/OR)
• CloudWatch Alarm: baseado em métrica

Failover Pattern:
• Primary: região principal (health check ativo)
• Secondary: região DR (ativado quando primary falha)
• Failover automático em ~30-60 segundos
• Pode combinar com Global Accelerator
Chaos EngineeringResiliência
AWS Fault Injection Simulator (FIS):
• Serviço gerenciado para chaos engineering
• Injeta falhas controladas em recursos AWS
• Experiment templates: definem ações e targets
• Stop conditions: limites de segurança

Tipos de experimentos:
• EC2: terminate instances, stress CPU/memory
• ECS: stop tasks, drain container instances
• EKS: terminate pods, inject network latency
• RDS: failover, reboot
• Network: packet loss, latency injection

Melhores práticas:
• Comece em ambientes não-produtivos
• Defina hipóteses antes do experimento
• Monitore métricas durante o teste
• Stop conditions para limitar blast radius
• Game Days: exercícios regulares de DR

Objetivo:
• Validar que sistemas se recuperam de falhas
• Encontrar pontos fracos antes que causem outages
• Construir confiança na resiliência da arquitetura

🎯 Para o exame: "Otimizar custos" → Reserved/Savings Plans + right-sizing + lifecycle policies. "Melhorar performance" → caching (CloudFront, ElastiCache, DAX) + read replicas. "Reduzir esforço operacional" → serviços gerenciados + automação (SSM, Config auto-remediation). "Aumentar resiliência" → multi-AZ + health checks + chaos engineering.
