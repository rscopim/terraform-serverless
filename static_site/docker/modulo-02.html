Fundamentos

O que é uma Imagem Docker?

Uma imagem Docker é um pacote imutável, leve e autocontido que contém tudo necessário para executar uma aplicação: código, runtime, bibliotecas, variáveis de ambiente e configurações.

Analogia: A Receita vs O Prato

Para entender imagens Docker, pense em uma receita de bolo:

Imagem Docker = ReceitaAnalogia

A imagem é como uma receita completa e congelada — contém todas as instruções e ingredientes necessários. Ela não muda. Você pode distribuir cópias para qualquer pessoa, e o resultado será sempre o mesmo.

Container = Prato ProntoAnalogia

O container é o prato sendo preparado/consumido — é a receita em execução. Cada vez que você "faz a receita", cria um novo prato independente. Você pode ter vários pratos da mesma receita simultaneamente.

💡 Conceito fundamental: Uma imagem é imutável (read-only). Quando você executa uma imagem, Docker cria um container com uma camada de escrita no topo. Qualquer modificação feita no container acontece apenas nessa camada — a imagem original permanece intacta.

Sistema de Camadas (Layers) — O Coração das Imagens

Imagens Docker não são um único arquivo monolítico. Elas são compostas por camadas empilhadas, onde cada camada representa uma mudança no filesystem. Isso é o que torna Docker tão eficiente.

Anatomia de uma imagem em camadasDiagrama
┌─────────────────────────────────────────────────────────────┐
│          CONTAINER (camada de escrita - efêmera)            │
│  Logs, arquivos temporários, dados de sessão               │
├─────────────────────────────────────────────────────────────┤  ← Tudo acima é R/W
│  Layer 6: COPY . /app/              [2.1 MB]  ← Seu código │
├─────────────────────────────────────────────────────────────┤
│  Layer 5: RUN pip install -r req..  [45 MB]   ← Deps       │
├─────────────────────────────────────────────────────────────┤
│  Layer 4: COPY requirements.txt .   [1 KB]    ← Arquivo    │
├─────────────────────────────────────────────────────────────┤
│  Layer 3: WORKDIR /app              [0 B]     ← Metadata   │
├─────────────────────────────────────────────────────────────┤
│  Layer 2: RUN apt-get install ...   [15 MB]   ← Pacotes SO │
├─────────────────────────────────────────────────────────────┤
│  Layer 1: FROM python:3.12-slim     [120 MB]  ← Base        │
└─────────────────────────────────────────────────────────────┘
                    Todas as layers são READ-ONLY

Total da imagem: ~182 MB (soma das camadas)
10 containers rodando = 182 MB + (10 × poucos KB da camada RW)
⚡ Por que camadas são geniais?
  • Compartilhamento: Se 10 imagens usam python:3.12-slim como base, o disco armazena essa camada uma única vez
  • Cache de build: Ao reconstruir uma imagem, Docker reutiliza camadas que não mudaram — builds são muito mais rápidos
  • Downloads eficientes: Ao fazer pull de uma imagem, Docker baixa apenas as camadas que você ainda não possui
  • Versionamento implícito: Cada camada tem um hash SHA256 — integridade garantida

Como o Cache de Build Funciona

O cache é um dos conceitos mais importantes para builds eficientes. Docker verifica cada instrução do Dockerfile de cima para baixo e, para cada uma, decide: "posso reutilizar o resultado anterior?"

Regras do CacheImportante
# Docker verifica o cache seguindo estas regras:

1. Se a instrução anterior usou cache → verifica se esta também pode usar
2. Para RUN: compara o TEXTO do comando (string exata)
3. Para COPY/ADD: compara o CHECKSUM dos arquivos copiados
4. Se UMA camada invalida o cache → TODAS as camadas seguintes são reconstruídas

# Exemplo prático — POR QUE a ordem importa:

# ❌ RUIM: qualquer mudança no código invalida o pip install
COPY . /app/                  ← Muda a cada commit (invalida cache)
RUN pip install -r requirements.txt  ← Reinstala TUDO toda vez

# ✅ BOM: só reinstala quando requirements.txt muda
COPY requirements.txt .       ← Só muda quando adiciona dependência
RUN pip install -r requirements.txt  ← Cache válido na maioria dos builds
COPY . /app/                  ← Código muda sempre, mas deps já estão prontas
💡 Regra de ouro: Coloque instruções que mudam com menos frequência primeiro (SO, dependências) e instruções que mudam frequentemente por último (código-fonte). Isso maximiza o aproveitamento do cache.

Image ID vs Tag vs Digest — Identificadores

Uma imagem pode ser identificada de três formas diferentes:

Image ID (SHA256)Hash

Identificador único gerado a partir do conteúdo da imagem. Qualquer mudança gera um ID diferente. É o identificador mais confiável.

# Image ID (abreviado para 12 chars):
sha256:a1b2c3d4e5f6...

# Usar pelo ID:
docker run a1b2c3d4e5f6
docker rmi sha256:a1b2c3...
Tag (nome:versão)Label

Nome legível dado à imagem. É um "ponteiro" que pode mudar — a tag latest aponta para imagens diferentes ao longo do tempo. Tags são mutáveis!

# Formato: registry/repositório:tag
nginx:1.25.3
python:3.12-slim
meuuser/minha-app:v2.1.0
ghcr.io/org/api:latest

# Se não especificar tag, assume :latest
docker pull nginx  # = docker pull nginx:latest
Digest (SHA256 do manifest)Imutável

Hash do manifesto da imagem no registry. Diferente do Image ID local, o digest identifica a imagem de forma imutável e globalmente única no registry.

# Digest = garantia de que é EXATAMENTE aquela imagem
nginx@sha256:abc123def456...

# Usar em produção para pinagem segura:
docker pull nginx@sha256:abc123...

# Ver digest de uma imagem:
docker inspect --format='{{.RepoDigests}}' nginx
⚠️ Cuidado com :latest em produção! 
# Hoje:   nginx:latest → nginx@sha256:aaa111...  (versão 1.25.3)
# Amanhã: nginx:latest → nginx@sha256:bbb222...  (versão 1.25.4)

# Em produção, SEMPRE use tags específicas ou digests:
✅ nginx:1.25.3
✅ nginx@sha256:abc123def456...
❌ nginx:latest  ← Pode mudar sem aviso!

docker pull — Baixar imagens de um Registry

Busca imagens de um registry (Docker Hub por padrão) e armazena localmente:

docker pullDownload
# Pull básico (do Docker Hub):
docker pull nginx
docker pull nginx:1.25.3
docker pull python:3.12-slim

# Pull com digest (imutável):
docker pull nginx@sha256:abc123...

# Pull de registry privado:
docker pull ghcr.io/minha-org/api:v2.0
docker pull 123456789.dkr.ecr.us-east-1.amazonaws.com/app:latest
docker pull registry.gitlab.com/user/project:main

# Pull de todas as tags (raramente necessário):
docker pull --all-tags nginx
Como o pull funcionaInterno
# Quando você executa docker pull nginx:1.25

1. Docker resolve nginx → docker.io/library/nginx:1.25
2. Contata o registry (Docker Hub)
3. Baixa o manifest (lista de layers)
4. Para cada layer:
   - Se já existe localmente → SKIP ✓
   - Se não existe → download
5. Verifica integridade (SHA256)
6. Armazena no storage local

# É por isso que o 2º pull de imagem similar é rápido:
docker pull python:3.12       # 1.01GB — lento
docker pull python:3.12-slim  # Apenas layers diferentes — rápido!

docker tag — Renomear e versionar imagens

Cria um novo nome/tag que aponta para a mesma imagem (não duplica dados):

# Sintaxe: docker tag IMAGEM_ORIGEM NOVO_NOME:TAG

# Adicionar tag de versão:
docker tag minha-app:latest minha-app:v1.0.0
docker tag minha-app:latest minha-app:v1.0
docker tag minha-app:latest minha-app:v1

# Preparar para push em registry:

# Tag com informações do ambiente:

# Verificar — ambas apontam para o mesmo Image ID:

💡 Boas práticas de tagging: Use Semantic Versioning (v1.2.3), inclua tags múltiplas (v1, v1.2, v1.2.3) e adicione o SHA do commit para rastreabilidade. Em CI/CD, nunca use apenas :latest.

Dockerfile

Dockerfile — Todas as Instruções

O Dockerfile é a receita que define como construir uma imagem Docker. Cada instrução cria uma camada na imagem final. Domine cada uma delas.

FROM — Imagem Base

Toda imagem começa com FROM. Define a imagem base sobre a qual você constrói. É a primeira instrução obrigatória do Dockerfile.

FROMBase
# Sintaxe:
FROM imagem:tag
FROM imagem@digest
FROM imagem:tag AS nome_do_stage

# Exemplos comuns:
FROM ubuntu:22.04
FROM python:3.12-slim
FROM node:20-alpine
FROM golang:1.22 AS builder
FROM scratch  # Imagem vazia — para binários estáticos

# Com plataforma específica:
FROM --platform=linux/amd64 python:3.12-slim
FROM --platform=linux/arm64 node:20-alpine
Escolhendo a imagem baseDecisão
# Variantes comuns:
python:3.12        → Debian full (1.0GB) — dev/debug
python:3.12-slim   → Debian minimal (150MB) — produção
python:3.12-alpine → Alpine Linux (50MB) — mínimo

# Trade-offs:
# Full   = mais pacotes, mais fácil, mais pesada
# Slim   = equilíbrio ideal para 90% dos casos
# Alpine = mínima, mas pode ter incompatibilidades
#          (musl vs glibc — cuidado com Python/Node)

# Regra para produção:
✅ Use -slim como padrão
✅ Use -alpine se tiver certeza de compatibilidade
❌ Nunca use :latest em produção
❌ Evite full exceto para debugging

RUN — Executar Comandos

RUN executa comandos durante o build da imagem. Cada RUN cria uma nova camada. Usado para instalar pacotes, configurar o ambiente, compilar código.

Formas de usoSintaxe
# Shell form (usa /bin/sh -c):
RUN apt-get update
RUN pip install flask

# Exec form (sem shell — mais preciso):
RUN ["apt-get", "update"]
RUN ["pip", "install", "flask"]

# Multi-line com \ (legibilidade):
RUN apt-get update && \
    apt-get install -y \
      curl \
      wget \
      vim && \
    rm -rf /var/lib/apt/lists/*
Boas práticas de RUNImportante
# ❌ RUIM: cada RUN = nova camada + cache ineficiente
RUN apt-get update
RUN apt-get install -y curl
RUN apt-get install -y wget
RUN rm -rf /var/lib/apt/lists/*
# = 4 camadas, cache do apt não é limpo na mesma layer!

# ✅ BOM: encadeie com && em um único RUN
RUN apt-get update && \
    apt-get install -y --no-install-recommends \
      curl \
      wget && \
    rm -rf /var/lib/apt/lists/*
# = 1 camada, limpeza efetiva, imagem menor

# 💡 --no-install-recommends evita pacotes sugeridos
# 💡 rm -rf /var/lib/apt/lists/* limpa o cache do apt
# 💡 Ambos DEVEM estar no mesmo RUN para ter efeito
⚠️ Por que a limpeza deve estar no mesmo RUN? Cada RUN cria uma layer imutável. Se você instala pacotes em um RUN e limpa em outro, a layer anterior ainda contém os arquivos! A remoção cria uma "whiteout" na nova layer, mas o tamanho total da imagem não diminui.

COPY vs ADD — Copiar Arquivos

Ambos copiam arquivos do contexto de build para a imagem, mas com diferenças importantes:

COPYRecomendado
# Copia arquivos/diretórios do host para a imagem
# Simples, previsível, transparente

COPY requirements.txt .
COPY src/ /app/src/
COPY package.json package-lock.json ./
COPY --chown=appuser:appuser . /app/

# Com multi-stage (copiar do outro stage):
COPY --from=builder /app/dist /usr/share/nginx/html
COPY --from=0 /go/bin/app /app

# Wildcards:
COPY *.py /app/
COPY config*.yml /etc/app/
ADDExtras
# Faz tudo que COPY faz, MAIS:
# 1. Descompacta arquivos tar automaticamente
# 2. Aceita URLs como fonte

ADD app.tar.gz /app/       # Descompacta automaticamente!
ADD https://example.com/file.txt /app/  # Download de URL

# ⚠️ Problemas com ADD:
# → URL não usa cache de build
# → Comportamento implícito (descompacta sem pedir)
# → Menos previsível em code review

# Quando usar ADD:
# → APENAS quando precisa descompactar tar local
# → Para URLs, prefira: RUN curl -o ... ou RUN wget

# Regra: USE COPY a menos que precise
# das features extras do ADD

WORKDIR — Diretório de Trabalho

Define o diretório padrão para as instruções subsequentes (RUN, COPY, CMD, ENTRYPOINT). Se não existir, é criado automaticamente.

WORKDIRDiretório
# Definir diretório de trabalho:
WORKDIR /app

# A partir daqui, tudo é relativo a /app:
COPY . .          # = COPY . /app/
RUN npm install   # Executa em /app
CMD ["node", "server.js"]  # Executa em /app

# Pode usar múltiplos WORKDIR:
WORKDIR /app
WORKDIR src        # Agora em /app/src
WORKDIR ../config  # Agora em /app/config

# ❌ RUIM: usar cd em RUN (não persiste entre layers!)
RUN cd /app && npm install   # Funciona, mas é feio
RUN npm start                # Volta para / !

# ✅ BOM: usar WORKDIR
WORKDIR /app
RUN npm install
RUN npm start     # Ainda em /app ✓

# 💡 WORKDIR aceita variáveis de ambiente:
ENV APP_HOME=/opt/myapp
WORKDIR $APP_HOME

ENV vs ARG — Variáveis de Ambiente vs Build Arguments

Ambos definem variáveis, mas com escopo e persistência diferentes:

ENVRuntime
# ENV persiste na imagem final e nos containers

# Definir variáveis de ambiente:
ENV NODE_ENV=production
ENV PORT=8080
ENV APP_VERSION=2.1.0

# Múltiplas em uma linha:
ENV NODE_ENV=production \
    PORT=8080 \
    APP_VERSION=2.1.0

# Usando em instruções posteriores:
ENV INSTALL_DIR=/opt/app
WORKDIR $INSTALL_DIR
RUN echo "Instalando em $INSTALL_DIR"

# Disponível em RUNTIME (dentro do container):
docker run minha-app
# → process.env.NODE_ENV = "production"
# → process.env.PORT = "8080"

# Override no docker run:
docker run -e PORT=9090 minha-app
ARGBuild-time
# ARG só existe durante o build — NÃO vai para a imagem

# Definir build argument:
ARG PYTHON_VERSION=3.12
ARG BUILD_DATE
ARG GIT_SHA

# Usar durante o build:
FROM python:${PYTHON_VERSION}-slim
ARG BUILD_DATE
LABEL build-date=$BUILD_DATE

# Passar valor no build:
docker build \
  --build-arg PYTHON_VERSION=3.11 \
  --build-arg BUILD_DATE=$(date -I) \
  --build-arg GIT_SHA=$(git rev-parse HEAD) \
  -t minha-app .

# ⚠️ ARG antes do FROM tem escopo especial:
ARG BASE_IMAGE=python:3.12
FROM ${BASE_IMAGE}
# Após FROM, esse ARG não existe mais!
# Precisa redeclarar se quiser usar:
ARG BASE_IMAGE

EXPOSE — Documentar Portas

EXPOSE é apenas documentação. Não abre nem publica portas. Informa quais portas o container escuta.

EXPOSEDocumentação
# Documentar portas que a aplicação usa:
EXPOSE 8080

CMD vs ENTRYPOINT — O Comando Principal

Ambos definem o que executar quando o container inicia, mas com comportamentos fundamentalmente diferentes:

CMDPadrão
# CMD define o comando PADRÃO — pode ser sobrescrito

# Exec form (recomendado):
CMD ["python", "app.py"]
CMD ["node", "server.js"]
CMD ["nginx", "-g", "daemon off;"]

# Shell form (usa /bin/sh -c):
CMD python app.py
CMD node server.js

# CMD é SUBSTITUÍDO por argumentos do docker run:
# Dockerfile: CMD ["python", "app.py"]
docker run minha-app              # Executa: python app.py
docker run minha-app bash         # Executa: bash (CMD ignorado!)
docker run minha-app python test.py  # Executa: python test.py

# Apenas o ÚLTIMO CMD vale:
CMD ["echo", "primeiro"]
CMD ["echo", "segundo"]   # ← Só este executa
ENTRYPOINTFixo
# ENTRYPOINT define o comando FIXO — não é substituído

# Exec form (recomendado):
ENTRYPOINT ["python"]
ENTRYPOINT ["java", "-jar", "app.jar"]

# Com ENTRYPOINT, argumentos do docker run são ADICIONADOS:
# Dockerfile: ENTRYPOINT ["python"]
docker run minha-app app.py       # Executa: python app.py
docker run minha-app -c "print(1)"  # Executa: python -c "print(1)"

# ENTRYPOINT + CMD = Padrão com override parcial:
ENTRYPOINT ["python"]
CMD ["app.py"]
# docker run minha-app         → python app.py
# docker run minha-app test.py → python test.py
#                                 (CMD substituído, ENTRYPOINT mantido)

# Para sobrescrever ENTRYPOINT no run:
docker run --entrypoint bash minha-app
CenárioCMDENTRYPOINTENTRYPOINT + CMD

docker run app XExecuta X (CMD ignorado)ENTRYPOINT XENTRYPOINT + X (CMD substituído)

💡 Exec form vs Shell form: 
# Exec form: ["executable", "arg1", "arg2"]
CMD ["node", "server.js"]
# → PID 1 = node (recebe signals corretamente, graceful shutdown)

# Shell form: command arg1 arg2
CMD node server.js
# → PID 1 = /bin/sh -c "node server.js"
# → node é filho do sh (NÃO recebe SIGTERM diretamente!)
# → Container pode não fazer graceful shutdown!

# SEMPRE use exec form em produção!

USER — Segurança de Processos

Define qual usuário executa as instruções subsequentes e o container em runtime. Nunca rode containers como root em produção.

USERSegurança
# Criar usuário e mudar contexto:

    useradd -r -g appuser -d /app -s /sbin/nologin appuser

# Dar permissões antes de mudar de usuário:

# ou:

# Mudar para o novo usuário (tudo abaixo roda como appuser):

# Verificar no container:
# $ whoami → appuser
# $ id → uid=1000(appuser) gid=1000(appuser)

# Por que NÃO rodar como root em produção:
# 1. Se um atacante escapar do container, terá root no host
# 2. Principle of Least Privilege (PoLP)
# 3. Muitos registries/orquestradores exigem (ex: OpenShift)
# 4. Compliance e auditoria

HEALTHCHECKSaúde

# 0 = healthy
# 1 = unhealthy

VOLUME — Pontos de Montagem

Declara que um diretório deve ser tratado como volume (dados persistentes que sobrevivem ao container):

VOLUMEPersistência
# Declarar volumes:
VOLUME /data
VOLUME /var/log/app
VOLUME ["/data", "/var/log/app"]

# O que VOLUME faz:
# 1. Cria um ponto de montagem no path especificado
# 2. Dados escritos ali são armazenados FORA do container layer
# 3. Sobrevivem ao docker rm (se usado named volume)
# 4. Não são incluídos em docker commit

# ⚠️ Cuidado: VOLUME no Dockerfile cria um ANONYMOUS volume
# Se você não montar explicitamente, Docker cria um volume sem nome
# que é difícil de gerenciar. Prefira:

# No Dockerfile:
VOLUME /data

# No docker run (melhor controle):
docker run -v meus-dados:/data minha-app       # Named volume
docker run -v /host/path:/data minha-app       # Bind mount

# 💡 Em geral, é melhor NÃO usar VOLUME no Dockerfile
# e deixar o operador decidir no docker run ou compose.
# VOLUME no Dockerfile impede que layers posteriores modifiquem o path!
Build Context

.dockerignore — Controlando o Contexto de Build

O arquivo .dockerignore define quais arquivos e diretórios NÃO devem ser enviados para o Docker daemon durante o build. É essencial para segurança, performance e tamanho da imagem.

O que é o Build Context?

Quando você executa docker build ., o Docker envia todo o conteúdo do diretório (o "contexto") para o daemon. Sem .dockerignore, isso inclui tudo — node_modules, .git, arquivos de teste, secrets...

O problema sem .dockerignoreProblema
# Sem .dockerignore — o que acontece:
$ docker build -t minha-app .
Sending build context to Docker daemon  2.1GB  ← 😱

# O que foi enviado:
node_modules/     → 500MB (será reinstalado pelo npm install!)
.git/             → 800MB (histórico completo do git)
dist/             → 50MB  (será reconstruído no build!)
*.log             → 100MB (logs desnecessários)
.env              → 1KB   (⚠️ SECRETS EXPOSTOS!)
tests/            → 20MB  (não precisa em produção)

# Com .dockerignore:
$ docker build -t minha-app .
Sending build context to Docker daemon  5.2MB  ← ✅

# Benefícios:
# → Build 100x mais rápido (menos dados para enviar)
# → Imagem menor (COPY . não inclui lixo)
# → Segurança (secrets não vazam para a imagem)
# → Cache mais eficiente (menos invalidação)

Avançado

Multi-Stage Build

A técnica mais poderosa para criar imagens mínimas de produção. Separe o ambiente de build do ambiente de runtime e reduza suas imagens de GBs para MBs.

O Problema: Imagens Enormes com Toolchain de Build

Para compilar uma aplicação, você precisa de ferramentas (compilador, SDK, dependências de build). Mas em produção, só precisa do binário/artefato final. Sem multi-stage, tudo vai para a imagem:

Sem Multi-Stage — O problemaProblema
# ❌ Dockerfile SEM multi-stage (Go):
FROM golang:1.22              # 800MB de SDK + ferramentas
WORKDIR /app
COPY . .
RUN go build -o server .     # Compila o binário (15MB)
CMD ["./server"]

# Resultado: imagem de ~815MB
# Contém: Go SDK, compilador, código-fonte, ferramentas de build
# Tudo desnecessário em produção!
# Superfície de ataque ENORME

# ❌ Dockerfile SEM multi-stage (Node.js):
FROM node:20                  # 1.1GB
WORKDIR /app
COPY package*.json ./
RUN npm install               # Inclui devDependencies!
COPY . .
RUN npm run build             # Gera /app/dist
CMD ["node", "dist/server.js"]

# Resultado: ~1.3GB
# Contém: Node completo, código fonte, devDependencies, TypeScript compiler...

A Solução: Multi-Stage Build

Use múltiplos FROM no mesmo Dockerfile. Cada FROM inicia um "stage". O stage final contém apenas o necessário para rodar a aplicação:

Conceito visualDiagrama
┌─────────────────────────────────────────────────────────────┐
│  STAGE 1: "builder"                                          │
│  FROM golang:1.22 AS builder                                 │
│                                                              │
│  Contém: SDK, compilador, código-fonte, deps de build        │
│  Faz: compila o código → gera binário                        │
│  Tamanho: ~800MB                                             │
│  ❌ NÃO vai para a imagem final                              │
├──────────────────────────┬──────────────────────────────────┤
│                          │ COPY --from=builder               │
│                          ▼ (copia só o binário)              │
├─────────────────────────────────────────────────────────────┤
│  STAGE 2: "runtime" (IMAGEM FINAL)                           │
│  FROM alpine:3.19                                            │
│                                                              │
│  Contém: SO mínimo + binário compilado                       │
│  Tamanho: ~15MB ✅                                           │
│  → Vai para produção                                         │
└─────────────────────────────────────────────────────────────┘

# De 800MB para 15MB — redução de 98%!

Exemplo: Go (compilado)

Multi-stage para GoExemplo
# ==================== STAGE 1: Build ====================
FROM golang:1.22-alpine AS builder

WORKDIR /build

# Cache de dependências (muda pouco)
COPY go.mod go.sum ./
RUN go mod download

# Código-fonte (muda frequentemente)
COPY . .

# Compilar binário estático (sem dependências de runtime)
RUN CGO_ENABLED=0 GOOS=linux GOARCH=amd64 \
    go build -ldflags="-w -s" -o /app/server ./cmd/server

# ==================== STAGE 2: Runtime ====================
FROM alpine:3.19

# Certificados SSL (para HTTPS)
RUN apk --no-cache add ca-certificates

# Usuário não-root
RUN adduser -D -H appuser
USER appuser

WORKDIR /app

# Copiar APENAS o binário do stage de build
COPY --from=builder /app/server .

EXPOSE 8080
HEALTHCHECK --interval=30s --timeout=5s \
  CMD wget --no-verbose --tries=1 --spider http://localhost:8080/health || exit 1

CMD ["./server"]

# Resultado:
# Stage 1 (builder): ~800MB — descartado
# Stage 2 (final):   ~15MB  — vai para produção ✅

Performance

Otimização de Imagens — Boas Práticas de Mercado

Aprenda as técnicas que times de engenharia em empresas como Google, Netflix e Spotify usam para criar imagens Docker eficientes, seguras e rápidas de construir.

1. Ordem das Instruções — Cache Optimization

A regra mais importante: coloque o que muda menos primeiro. Quando uma camada invalida o cache, todas as camadas seguintes são reconstruídas.

❌ Ordem ruimAnti-pattern
# Qualquer mudança no código (COPY .)
# invalida TUDO abaixo — inclusive npm install!

FROM node:20-alpine
WORKDIR /app
COPY . .                    ← Muda a cada commit
RUN npm install             ← Reinstala SEMPRE
EXPOSE 3000
CMD ["node", "server.js"]

# Build time: ~2 minutos toda vez
# Deps são reinstaladas em cada build 😫
✅ Ordem otimizadaBest Practice
# Separa dependências do código
# npm install usa cache na maioria dos builds!

FROM node:20-alpine
WORKDIR /app
COPY package.json package-lock.json ./  ← Muda raramente
RUN npm ci                              ← Cache válido!
COPY . .                                ← Muda sempre (ok, é a última)
EXPOSE 3000
CMD ["node", "server.js"]

# Build time: ~10 segundos (quando só código muda)
# Deps usam cache — só reinstala quando package.json muda ✅
💡 Ordem ideal de instruções: 
1. FROM (imagem base)
2. Instalar pacotes do SO (apt-get)         ← Muda quase nunca
3. Copiar arquivos de lock/requirements      ← Muda quando adiciona dep
4. Instalar dependências da linguagem        ← Cache muito valioso
5. Copiar código-fonte                       ← Muda a cada commit
6. Build/compilação
7. CMD/ENTRYPOINT

2. Combinar RUN com && — Reduzir Camadas

Cada RUN cria uma layer. Combine comandos relacionados para reduzir o número de layers e garantir que limpezas sejam efetivas:

❌ Múltiplos RUNAnti-pattern
# 4 layers — limpeza na layer 4 NÃO remove
# o cache da layer 1!
RUN apt-get update
RUN apt-get install -y curl wget
RUN apt-get install -y git
RUN rm -rf /var/lib/apt/lists/*

# Tamanho: ~150MB (cache ainda na layer 1)
✅ RUN único com &&Best Practice
# 1 layer — limpeza efetiva!
RUN apt-get update && \
    apt-get install -y --no-install-recommends \
      curl \
      wget \
      git && \
    rm -rf /var/lib/apt/lists/*

# Tamanho: ~80MB (cache removido na mesma layer)

RUN apk add --no-cache --virtual .build-deps \

    apk del .build-deps

Node.js Express — Multi-stage com TypeScript

Dockerfile — Node.js Express + TypeScriptProdução
# ============================================================
# Dockerfile para Node.js Express + TypeScript — Produção
# ============================================================

# Stage 1: Instalar TODAS deps + compilar TypeScript
FROM node:20-alpine AS builder

WORKDIR /app

# Copiar apenas arquivos de dependências (cache optimization)
COPY package.json package-lock.json tsconfig.json ./

# Instalar todas as deps (incluindo devDependencies para compilação)
RUN npm ci

# Copiar código-fonte TypeScript
COPY src/ ./src/

# Compilar TypeScript → JavaScript
RUN npm run build
# Resultado: /app/dist/ com JS puro

# ============================================================
# Stage 2: Deps de produção apenas
FROM node:20-alpine AS deps

WORKDIR /app

COPY package.json package-lock.json ./

# Instalar APENAS dependências de produção
RUN npm ci --only=production && \
    npm cache clean --force

# ============================================================
# Stage 3: Runtime mínimo
FROM node:20-alpine

# Metadata
LABEL org.opencontainers.image.title="Express API" \
      org.opencontainers.image.version="2.0.0"

# Segurança: dumb-init para PID 1 correto
RUN apk add --no-cache dumb-init

# Criar usuário não-root
RUN addgroup -S app && adduser -S app -G app

WORKDIR /app

# Copiar deps de produção do stage 2
COPY --from=deps --chown=app:app /app/node_modules ./node_modules

# Copiar código compilado do stage 1
COPY --from=builder --chown=app:app /app/dist ./dist

# Copiar package.json (necessário para node)
COPY --chown=app:app package.json ./

# Variáveis de ambiente
ENV NODE_ENV=production \
    PORT=3000

# Usuário não-root
USER app

EXPOSE 3000

HEALTHCHECK --interval=30s --timeout=5s --start-period=10s --retries=3 \
  CMD node -e "const http = require('http'); const options = { hostname: 'localhost', port: 3000, path: '/health', timeout: 4000 }; const req = http.request(options, (res) => { process.exit(res.statusCode === 200 ? 0 : 1); }); req.on('error', () => process.exit(1)); req.end();"

# dumb-init garante que signals (SIGTERM) sejam propagados corretamente
CMD ["dumb-init", "node", "dist/server.js"]
💡 Por que 3 stages?
  • Stage 1 (builder): Compila TypeScript — precisa de devDependencies (typescript, ts-node, types)
  • Stage 2 (deps): Instala apenas prodDependencies — sem typescript, sem types
  • Stage 3 (runtime): Junta código compilado + prodDeps — mínimo possível
  • dumb-init — Garante que SIGTERM é propagado corretamente (graceful shutdown)

Java Spring Boot — Multi-stage com Maven

Dockerfile — Java Spring Boot + MavenProdução
# ============================================================
# Dockerfile para Java Spring Boot — Produção
# ============================================================

# Stage 1: Build com Maven
FROM maven:3.9-eclipse-temurin-21 AS builder

WORKDIR /build

# Cache de dependências Maven (muda raramente)
COPY pom.xml .
RUN mvn dependency:go-offline -B
# ↑ Baixa TODAS as deps — cache válido até pom.xml mudar

# Código-fonte (muda frequentemente)
COPY src/ ./src/

# Compilar e empacotar (skip tests — rodam no CI separadamente)
RUN mvn package -DskipTests -B
# Resultado: /build/target/app.jar

# ============================================================
# Stage 2: Runtime com JRE (não JDK!)
FROM eclipse-temurin:21-jre-alpine

# Metadata
LABEL org.opencontainers.image.title="Spring Boot API" \
      org.opencontainers.image.version="3.0.0"

# Criar usuário não-root
RUN addgroup -S spring && adduser -S spring -G spring

WORKDIR /app

# Copiar apenas o JAR do stage de build (não o código-fonte, não o Maven!)
COPY --from=builder --chown=spring:spring /build/target/*.jar app.jar

# Variáveis JVM otimizadas para containers
ENV JAVA_OPTS="-XX:+UseContainerSupport \
               -XX:MaxRAMPercentage=75.0 \
               -XX:InitialRAMPercentage=50.0 \
               -Djava.security.egd=file:/dev/./urandom"

USER spring

EXPOSE 8080

HEALTHCHECK --interval=30s --timeout=10s --start-period=40s --retries=3 \
  CMD wget --no-verbose --tries=1 --spider http://localhost:8080/actuator/health || exit 1

# Exec form com shell expansion para JAVA_OPTS
ENTRYPOINT ["sh", "-c", "java $JAVA_OPTS -jar app.jar"]
💡 Decisões chave para Java:
  • eclipse-temurin:21-jre-alpine — JRE (não JDK!) em Alpine — de 700MB para 200MB
  • mvn dependency:go-offline — Baixa deps separadamente para cache eficiente
  • -XX:+UseContainerSupport — JVM respeita limites de memória do container
  • -XX:MaxRAMPercentage=75.0 — Heap usa 75% da RAM disponível (deixa 25% para non-heap)
  • start-period=40s — Java demora para iniciar (Spring Boot ~20-30s)
  • /actuator/health — Endpoint padrão do Spring Boot Actuator

DesafioIntermediário
# Crie um Dockerfile multi-stage para esta aplicação Go.

# main.go:
package main

import (
    "fmt"
    "log"
    "net/http"
    "os"
)

func healthHandler(w http.ResponseWriter, r *http.Request) {
    w.WriteHeader(http.StatusOK)
    fmt.Fprintf(w, `{"status":"healthy"}`)
}

func helloHandler(w http.ResponseWriter, r *http.Request) {
    name := os.Getenv("APP_NAME")
    if name == "" {
        name = "World"
    }
    fmt.Fprintf(w, "Hello, %s!", name)
}

func main() {
    http.HandleFunc("/health", healthHandler)
    http.HandleFunc("/", helloHandler)

    port := os.Getenv("PORT")
    if port == "" {
        port = "8080"
    }

    log.Printf("Server starting on port %s", port)
    log.Fatal(http.ListenAndServe(":"+port, nil))
}

# go.mod:
module hello-server
go 1.22

# REQUISITOS:
# 1. Stage 1: Compilar com golang:1.22-alpine
# 2. Binário estático (CGO_ENABLED=0)
# 3. Usar -ldflags="-w -s" para reduzir tamanho
# 4. Stage 2: Usar alpine:3.19 ou scratch
# 5. Certificados SSL (ca-certificates)
# 6. Usuário não-root
# 7. HEALTHCHECK
# 8. ENV para APP_NAME e PORT
💡 Solução: 
# Dockerfile (~12MB com alpine, ~7MB com scratch):
FROM golang:1.22-alpine AS builder
WORKDIR /build
COPY go.mod ./
# Se tivesse go.sum: COPY go.sum ./
# RUN go mod download
COPY main.go .
RUN CGO_ENABLED=0 GOOS=linux GOARCH=amd64 \
    go build -ldflags="-w -s" -o /app/server .

FROM alpine:3.19
RUN apk --no-cache add ca-certificates && \
    adduser -D -H appuser
WORKDIR /app
COPY --from=builder /app/server .
ENV APP_NAME="Docker Student" \
    PORT=8080
USER appuser
EXPOSE 8080
HEALTHCHECK --interval=30s --timeout=3s \
  CMD wget --no-verbose --tries=1 --spider http://localhost:8080/health || exit 1
CMD ["./server"]
