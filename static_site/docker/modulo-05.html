Docker Compose

Domine a orquestração de aplicações multi-container com Docker Compose: defina toda a sua stack em um único arquivo YAML, gerencie serviços, redes e volumes de forma declarativa, configure healthchecks e dependências, e suba ambientes completos com um único comando.

Fundamentos

O que é Docker Compose?

Docker Compose é a ferramenta que resolve o problema de gerenciar aplicações multi-container. Em vez de executar dezenas de comandos docker run com flags complexas, você define toda a stack em um único arquivo YAML e opera tudo com um comando.

O Problema: Gerenciar Múltiplos Containers Manualmente

Imagine que você precisa subir uma aplicação web com 4 serviços. Sem Compose, você faria assim:

Sem Docker Compose — A dor de cabeçaProblema
# 1. Criar a rede
docker network create minha-app

# 2. Criar volumes
docker volume create postgres-data
docker volume create redis-data

# 3. Subir PostgreSQL
docker run -d \
  --name postgres \
  --network minha-app \
  -v postgres-data:/var/lib/postgresql/data \
  -e POSTGRES_USER=app \
  -e POSTGRES_PASSWORD=senha123 \
  -e POSTGRES_DB=minha_app \
  --restart unless-stopped \
  postgres:16-alpine

# 4. Subir Redis
docker run -d \
  --name redis \
  --network minha-app \
  -v redis-data:/data \
  --restart unless-stopped \
  redis:7-alpine --appendonly yes

# 5. Subir a aplicação (esperando DB e Redis estarem prontos...)
docker run -d \
  --name app \
  --network minha-app \
  -e DATABASE_URL=postgresql://app:senha123@postgres:5432/minha_app \
  -e REDIS_URL=redis://redis:6379 \
  --restart unless-stopped \
  minha-app:latest

# 6. Subir Nginx (reverse proxy)
docker run -d \
  --name nginx \
  --network minha-app \
  -p 80:80 -p 443:443 \
  -v ./nginx.conf:/etc/nginx/nginx.conf:ro \
  --restart unless-stopped \
  nginx:alpine

# PROBLEMAS:
# ❌ 6+ comandos longos e propensos a erros de digitação
# ❌ Sem controle de ordem/dependência de startup
# ❌ Difícil de versionar (como guardar isso no Git?)
# ❌ Difícil de replicar (outro dev precisa rodar tudo de novo)
# ❌ Para destruir: docker stop + docker rm para CADA container
# ❌ Variáveis de ambiente espalhadas em vários comandos
# ❌ Se um container falhar, precisa lembrar o comando exato

A Solução: Docker Compose — Um Arquivo, Um Comando

Com Docker Compose, a mesma stack é definida em um arquivo docker-compose.yml e operada com um único comando:

Com Docker Compose — A solução eleganteSolução
# docker-compose.yml — TODA a stack em um arquivo:
services:
  postgres:
    image: postgres:16-alpine
    volumes:
      - postgres-data:/var/lib/postgresql/data
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: senha123
      POSTGRES_DB: minha_app
    restart: unless-stopped

  redis:
    image: redis:7-alpine
    volumes:
      - redis-data:/data
    command: redis-server --appendonly yes
    restart: unless-stopped

  app:
    build: .
    environment:
      DATABASE_URL: postgresql://app:senha123@postgres:5432/minha_app
      REDIS_URL: redis://redis:6379
    depends_on:
      - postgres
      - redis
    restart: unless-stopped

  nginx:
    image: nginx:alpine
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./nginx.conf:/etc/nginx/nginx.conf:ro
    depends_on:
      - app
    restart: unless-stopped

volumes:
  postgres-data:
  redis-data:

# SUBIR TUDO:
docker compose up -d

# DERRUBAR TUDO:
docker compose down

# VANTAGENS:
# ✅ Toda a stack em UM arquivo versionável (Git)
# ✅ Um comando para subir, um para derrubar
# ✅ Dependências declaradas (depends_on)
# ✅ Rede criada automaticamente
# ✅ Qualquer dev clona o repo e roda docker compose up
# ✅ Reproduzível e determinístico
# ✅ Fácil de modificar e manter
🔑 Resumo: Docker Compose transforma uma sequência complexa de comandos em um arquivo declarativo e versionável. É a diferença entre "executar instruções" e "declarar o estado desejado".

Estrutura do docker-compose.yml

O arquivo Compose é organizado em seções de nível superior (top-level keys) que definem todos os componentes da sua aplicação. Entender essa estrutura é fundamental para criar configurações corretas e eficientes.

A Chave "version" — Deprecada no Compose V2

Se você já viu arquivos Compose, provavelmente encontrou a chave version: no topo. No Compose V2, ela é ignorada:

version: — O que era e por que foi removidaDeprecado
# ════════════════════════════════════════════════════════════════
# A CHAVE "version:" NO COMPOSE
# ════════════════════════════════════════════════════════════════

# ANTIGAMENTE (Compose V1):
# A chave "version" indicava qual formato de arquivo usar:
version: "2.4"    # Formato 2.x (features de single-host)
version: "3.8"    # Formato 3.x (features de Swarm/deploy)

# PROBLEMA:
# → Confusão sobre qual versão usar (2.x vs 3.x)
# → Features disponíveis dependiam da version
# → Incompatibilidades entre formatos
# → Usuários não sabiam qual escolher

# HOJE (Compose V2 / Compose Specification):
# ✅ A chave "version" é OPCIONAL e IGNORADA
# ✅ Todas as features estão sempre disponíveis
# ✅ O formato é unificado (Compose Specification)

# ARQUIVO MODERNO (sem version):
services:
  app:
    image: node:20-alpine
    ports:
      - "3000:3000"

# ARQUIVO LEGADO (version ainda funciona, mas é ignorada):
version: "3.8"    # ← Ignorada pelo Compose V2
services:
  app:
    image: node:20-alpine
    ports:
      - "3000:3000"

# RECOMENDAÇÃO:
# → Remova "version:" de novos arquivos
# → Não precisa remover de arquivos existentes (funciona igual)
# → Foque apenas em: services, networks, volumes

Top-Level Keys — As 4 Seções Principais

Um arquivo Compose completo pode ter estas seções de nível superior:

Estrutura completa do docker-compose.ymlReferência
# ════════════════════════════════════════════════════════════════
# ESTRUTURA COMPLETA DO DOCKER-COMPOSE.YML
# ════════════════════════════════════════════════════════════════

# ┌─────────────────────────────────────────────────────────────┐
# │ name: (opcional)                                             │
# │ Define o nome do projeto (substitui o nome do diretório)     │
# └─────────────────────────────────────────────────────────────┘
name: minha-aplicacao

# ┌─────────────────────────────────────────────────────────────┐
# │ services: (OBRIGATÓRIO)                                      │
# │ Define os containers que compõem sua aplicação               │
# │ Cada service = 1 container (ou múltiplas réplicas)           │
# └─────────────────────────────────────────────────────────────┘
services:
  web:          # Nome do serviço (usado como hostname DNS)
    image: nginx:alpine
    ports:
      - "80:80"

  api:          # Outro serviço
    build: ./api
    ports:
      - "3000:3000"

  db:           # Banco de dados
    image: postgres:16
    volumes:
      - db-data:/var/lib/postgresql/data

# ┌─────────────────────────────────────────────────────────────┐
# │ networks: (OPCIONAL)                                         │
# │ Define redes customizadas                                    │
# │ Se omitido, uma rede "default" é criada automaticamente      │
# └─────────────────────────────────────────────────────────────┘
networks:
  frontend:
    driver: bridge
  backend:
    driver: bridge
    internal: true   # Sem acesso à internet

# ┌─────────────────────────────────────────────────────────────┐
# │ volumes: (OPCIONAL)                                          │
# │ Define named volumes para persistência                       │
# │ Volumes declarados aqui são gerenciados pelo Docker          │
# └─────────────────────────────────────────────────────────────┘
volumes:
  db-data:
    driver: local
  cache-data:

# ┌─────────────────────────────────────────────────────────────┐
# │ configs: (OPCIONAL, mais usado com Swarm)                    │
# │ Define configurações que podem ser montadas nos containers   │
# └─────────────────────────────────────────────────────────────┘
configs:
  nginx-config:
    file: ./nginx/nginx.conf

# ┌─────────────────────────────────────────────────────────────┐
# │ secrets: (OPCIONAL)                                          │
# │ Define secrets que são montados de forma segura              │
# └─────────────────────────────────────────────────────────────┘
secrets:
  db-password:
    file: ./secrets/db-password.txt

Arquivo Completo Comentado Linha por Linha

Vamos ver um arquivo Compose real e completo com cada linha explicada:

docker-compose.yml — Comentado completoExemplo Real
# ════════════════════════════════════════════════════════════════
# PROJETO: Aplicação Web com API, DB e Cache
# ════════════════════════════════════════════════════════════════

# Nome do projeto (opcional, senão usa o nome do diretório)
name: minha-webapp

# ────────────────────────────────────────────────────────────────
# SERVICES: define cada container da aplicação
# ────────────────────────────────────────────────────────────────
services:

  # ══════════════════════════════════════════════════════════════
  # SERVIÇO: api (aplicação principal)
  # ══════════════════════════════════════════════════════════════
  api:
    # Construir imagem a partir do Dockerfile local
    build:
      context: .              # Diretório de contexto para o build
      dockerfile: Dockerfile  # Nome do Dockerfile (padrão)
      args:                   # Build arguments
        NODE_ENV: production

    # Nome fixo do container (opcional, padrão: projeto-servico-1)
    container_name: webapp-api

    # Portas expostas: "HOST:CONTAINER"
    ports:
      - "3000:3000"           # API acessível na porta 3000 do host

    # Variáveis de ambiente
    environment:
      NODE_ENV: production
      DATABASE_URL: postgresql://app:${DB_PASSWORD}@db:5432/webapp
      REDIS_URL: redis://cache:6379

    # Volumes montados
    volumes:
      - ./uploads:/app/uploads          # Bind mount para uploads
      - app-logs:/app/logs              # Named volume para logs

    # Redes que este serviço pertence
    networks:
      - frontend       # Acessível pelo Nginx
      - backend        # Acessa DB e Redis

    # Dependências: esperar outros serviços
    depends_on:
      db:
        condition: service_healthy  # Espera DB estar saudável
      cache:
        condition: service_started  # Espera Redis iniciar

    # Política de restart
    restart: unless-stopped

    # Healthcheck para monitorar saúde
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:3000/health"]
      interval: 30s
      timeout: 10s
      retries: 3
      start_period: 40s

  # ══════════════════════════════════════════════════════════════
  # SERVIÇO: db (PostgreSQL)
  # ══════════════════════════════════════════════════════════════
  db:
    image: postgres:16-alpine   # Imagem do Docker Hub

    container_name: webapp-db

    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: ${DB_PASSWORD}   # Variável do .env
      POSTGRES_DB: webapp

    volumes:
      - db-data:/var/lib/postgresql/data        # Dados persistentes
      - ./postgres/init.sql:/docker-entrypoint-initdb.d/init.sql:ro

    networks:
      - backend               # Apenas rede interna

    restart: unless-stopped

    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d webapp"]
      interval: 10s
      timeout: 5s
      retries: 5

  # ══════════════════════════════════════════════════════════════
  # SERVIÇO: cache (Redis)
  # ══════════════════════════════════════════════════════════════
  cache:
    image: redis:7-alpine

    container_name: webapp-cache

    command: redis-server --appendonly yes --maxmemory 256mb

    volumes:
      - cache-data:/data

    networks:
      - backend

    restart: unless-stopped

    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 10s
      timeout: 5s
      retries: 3

  # ══════════════════════════════════════════════════════════════
  # SERVIÇO: nginx (reverse proxy)
  # ══════════════════════════════════════════════════════════════
  nginx:
    image: nginx:alpine

    container_name: webapp-nginx

    ports:
      - "80:80"
      - "443:443"

    volumes:
      - ./nginx/nginx.conf:/etc/nginx/nginx.conf:ro
      - ./nginx/certs:/etc/nginx/certs:ro

    networks:
      - frontend

    depends_on:
      api:
        condition: service_healthy

    restart: unless-stopped

# ────────────────────────────────────────────────────────────────
# NETWORKS: define as redes da aplicação
# ────────────────────────────────────────────────────────────────
networks:
  frontend:                  # Rede para tráfego externo
    driver: bridge
  backend:                   # Rede para serviços internos
    driver: bridge
    internal: true           # Sem acesso à internet (segurança!)

# ────────────────────────────────────────────────────────────────
# VOLUMES: define volumes nomeados para persistência
# ────────────────────────────────────────────────────────────────
volumes:
  db-data:                   # Dados do PostgreSQL
    driver: local
  cache-data:                # Dados do Redis
    driver: local
  app-logs:                  # Logs da aplicação
    driver: local
🔑 Observação: O ${DB_PASSWORD} é interpolado a partir de um arquivo .env no mesmo diretório. Compose lê automaticamente variáveis do .env — nunca coloque senhas diretamente no YAML!

# 2. Variável: COMPOSE_PROJECT_NAME=meu-projeto

Services

Services — Todas as Opções

A seção services é o coração do Compose. Cada service define um container (ou grupo de réplicas) com todas as suas configurações. Aqui estão todas as opções disponíveis com exemplos práticos.

image vs build — De Onde Vem a Imagem?

Todo service precisa de uma imagem. Você pode usar uma imagem pronta (image) ou construir uma a partir de um Dockerfile (build):

image — Usar imagem existentePull
# OPÇÃO 1: image (imagem pronta do registry)
# ═══════════════════════════════════════════

services:
  # Imagem oficial, tag latest (não recomendado)
  redis:
    image: redis

  # Imagem com tag específica (recomendado!)
  postgres:
    image: postgres:16-alpine

  # Imagem de registry privado
  api:
    image: registry.empresa.com/api:v2.1.0

  # Imagem do GitHub Container Registry
  app:
    image: ghcr.io/usuario/app:latest

  # Imagem do AWS ECR
  backend:
    image: 123456789.dkr.ecr.us-east-1.amazonaws.com/api:prod

# REGRA: sempre use tag específica em produção!
# ❌ image: nginx          (latest implícito)
# ❌ image: nginx:latest   (muda sem aviso)
# ✅ image: nginx:1.25-alpine  (determinístico)
build — Construir do DockerfileBuild
# OPÇÃO 2: build (construir a imagem localmente)
# ═══════════════════════════════════════════════

services:
  # Forma simples: path para o contexto de build
  app:
    build: .
    # Equivalente a: docker build .

  # Forma completa: todas as opções
  api:
    build:
      context: ./backend         # Diretório de contexto
      dockerfile: Dockerfile.prod # Dockerfile customizado
      args:                       # Build arguments
        NODE_ENV: production
        API_VERSION: "2.1.0"
      target: production          # Multi-stage target
      cache_from:                 # Cache de build
        - registry.io/api:cache
      labels:                     # Labels na imagem
        com.empresa.version: "2.1"
      platforms:                  # Multi-platform
        - linux/amd64
        - linux/arm64

  # COMBINAR image + build:
  # Constrói E dá nome/tag à imagem
  webapp:
    build: .
    image: minha-empresa/webapp:dev
    # Resultado: imagem construída E taggeada

      - "3000"

      # Bind em IP específico
      - "127.0.0.1:8080:80"

      # Range de portas
      - "8000-8010:8000-8010"

      # Formato longo (mais explícito):
      - target: 80        # Porta no container
        published: 8080   # Porta no host
        protocol: tcp     # tcp ou udp
        host_ip: 0.0.0.0  # IP de bind
expose vs portsDiferença
# DIFERENÇA: expose vs ports
# ═══════════════════════════════════════

# expose: torna a porta acessível APENAS
# para outros containers na mesma rede.
# NÃO publica no host!
services:
  api:
    build: .
    expose:
      - "3000"    # Outros containers acessam :3000
                  # Host NÃO acessa!

  # ports: publica no HOST (acessível externamente)
  nginx:
    image: nginx
    ports:
      - "80:80"   # Host E containers acessam

# QUANDO USAR CADA UM:
#
# expose: serviços internos que NÃO devem
#         ser acessados de fora
#   → Banco de dados
#   → Cache (Redis)
#   → APIs internas (microserviços)
#
# ports: serviços que DEVEM ser acessíveis
#        do mundo externo
#   → Nginx/Load Balancer (entrada)
#   → API pública
#   → Painel admin (dev apenas)

# NOTA: na prática, containers na mesma
# rede já se comunicam em qualquer porta.
# "expose" é mais documentacional.

volumes — Bind Mounts e Named Volumes

volumes em services — Todas as formasPersistência
# volumes: montar dados no container
# ═══════════════════════════════════════════════════════════════

services:
  app:
    image: node:20-alpine
    volumes:
      # ── FORMATO CURTO ──────────────────────────────────────

      # Named volume (gerenciado pelo Docker):
      - app-data:/app/data

      # Bind mount (diretório do host):
      - ./src:/app/src

      # Bind mount read-only:
      - ./config/app.conf:/etc/app/app.conf:ro

      # Volume anônimo (sem nome, efêmero):
      - /app/node_modules

      # ── FORMATO LONGO (mais controle) ──────────────────────

      # Named volume com opções:
      - type: volume
        source: app-data        # Nome do volume
        target: /app/data       # Path no container

      # Bind mount com opções:
      - type: bind
        source: ./src           # Path no host (relativo)
        target: /app/src        # Path no container
        read_only: false

      # Bind mount read-only:
      - type: bind
        source: ./nginx.conf
        target: /etc/nginx/nginx.conf
        read_only: true

      # tmpfs (RAM, dados temporários):
      - type: tmpfs
        target: /app/tmp
        tmpfs:
          size: 100000000       # 100MB máximo

# ── DECLARAR NAMED VOLUMES NO TOP-LEVEL ──────────────────────
volumes:
  app-data:           # Deve ser declarado aqui se usado acima
    driver: local

depends_on — Ordem de Inicialização

O depends_on controla a ordem em que os serviços são iniciados. Com condition, você pode esperar que um serviço esteja realmente pronto (não apenas iniciado):

depends_on — Forma simplesOrdem
# depends_on SIMPLES:
# Garante que db e cache INICIAM antes da api
# MAS não espera estarem PRONTOS!

services:
  api:
    build: .
    depends_on:
      - db       # Inicia db primeiro
      - cache    # Inicia cache primeiro
    # api inicia DEPOIS de db e cache

  db:
    image: postgres:16

  cache:
    image: redis:7

# PROBLEMA:
# PostgreSQL pode demorar 5-10s para aceitar
# conexões. A api pode iniciar e FALHAR porque
# o db ainda não está pronto para queries.
#
# depends_on simples = ordem de START
# NÃO garante que o serviço está FUNCIONAL!
depends_on + conditionHealthcheck
# depends_on com CONDITION (recomendado!):
# Espera o serviço estar realmente PRONTO

services:
  api:
    build: .
    depends_on:
      db:
        condition: service_healthy
        # Espera db passar no healthcheck!
      cache:
        condition: service_healthy
        # Espera cache passar no healthcheck!
      migrations:
        condition: service_completed_successfully
        # Espera migrations terminar com exit 0!

  db:
    image: postgres:16
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app"]
      interval: 5s
      timeout: 3s
      retries: 5
      start_period: 10s

  cache:
    image: redis:7
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 3s
      retries: 3

  migrations:
    build: .
    command: npm run migrate
    # Roda e termina (exit 0 = sucesso)

# CONDITIONS DISPONÍVEIS:
# service_started    → iniciou (padrão)
# service_healthy    → healthcheck OK
# service_completed_successfully → exit 0
🔑 Melhor prática: Sempre use depends_on com condition: service_healthy em produção. Combine com healthcheck em cada serviço para garantir que as dependências estão realmente prontas antes de iniciar serviços dependentes.

restart — Política de Reinicialização

restart — Todas as opçõesResiliência
# restart: define o que acontece quando um container para/falha
# ═══════════════════════════════════════════════════════════════

services:
  # NO: nunca reinicia (padrão)
  dev-tool:
    image: dev-tool:latest
    restart: "no"
    # Container parou → fica parado
    # Uso: ferramentas de desenvolvimento, jobs one-shot

  # ALWAYS: sempre reinicia (mesmo se parado manualmente com docker stop)
  critical-service:
    image: monitoring:latest
    restart: always
    # Container parou → reinicia SEMPRE
    # Mesmo após docker stop → reinicia no boot do Docker
    # Uso: serviços que DEVEM estar sempre rodando

  # UNLESS-STOPPED: reinicia exceto se parado manualmente
  web-app:
    image: webapp:latest
    restart: unless-stopped
    # Container crashou → reinicia
    # docker stop → NÃO reinicia
    # Docker restart/reboot → reinicia (se não foi stopped)
    # Uso: aplicações de produção (mais comum!)

  # ON-FAILURE: reinicia apenas se saiu com erro (exit code ≠ 0)
  worker:
    image: worker:latest
    restart: on-failure
    # exit 0 (sucesso) → NÃO reinicia
    # exit 1+ (erro) → reinicia
    # Uso: workers, processadores de fila

# ┌────────────────────────────────────────────────────────────┐
# │ RESUMO:                                                     │
# │                                                             │
# │ Política          │ Crash │ docker stop │ Docker restart    │
# │ ──────────────────│───────│─────────────│─────────────────  │
# │ no                │  Não  │    Não      │    Não            │
# │ always            │  Sim  │    Sim      │    Sim            │
# │ unless-stopped    │  Sim  │    Não      │    Sim*           │
# │ on-failure        │  Sim  │    Não      │    Não            │
# │                                                             │
# │ * Se não foi stopped antes do Docker restart                │
# └────────────────────────────────────────────────────────────┘

# RECOMENDAÇÃO:
# Dev: restart: "no" (quer ver crashes)
# Prod: restart: unless-stopped (padrão seguro)

deploy — Configuração de deployRecursos
# deploy: configurações de deployment (réplicas, recursos)
# ═══════════════════════════════════════════════════════════════

services:
  api:
    image: minha-api:latest
    deploy:
      # Número de réplicas (instâncias do container):
      replicas: 3
      # Cria: api-1, api-2, api-3
      # ⚠️ Não use container_name com replicas > 1!

      # Limites de recursos (CPU e memória):
      resources:
        # LIMITS: máximo que o container pode usar
        limits:
          cpus: "1.0"          # Máximo 1 CPU core
          memory: 512M         # Máximo 512MB RAM
          # Container é KILLED se ultrapassar memory limit (OOM)

        # RESERVATIONS: mínimo garantido
        reservations:
          cpus: "0.25"         # Garantido 0.25 CPU
          memory: 128M         # Garantido 128MB RAM
          # Compose não agenda se host não tem esse mínimo disponível

      # Política de restart (alternativa ao restart: de top-level)
      restart_policy:
        condition: on-failure
        delay: 5s              # Espera entre restarts
        max_attempts: 3        # Máximo de tentativas
        window: 120s           # Janela de avaliação

      # Update config (para rolling updates)
      update_config:
        parallelism: 1         # Quantos containers atualizar por vez
        delay: 10s             # Delay entre batches
        order: start-first     # start-first ou stop-first

  # Worker com recursos limitados:
  worker:
    image: worker:latest
    deploy:
      replicas: 5
      resources:
        limits:
          cpus: "0.5"
          memory: 256M
        reservations:
          cpus: "0.1"
          memory: 64M

  # Database: 1 réplica, muita memória:
  db:
    image: postgres:16
    deploy:
      replicas: 1
      resources:
        limits:
          cpus: "2.0"
          memory: 2G
        reservations:
          cpus: "1.0"
          memory: 1G

Networks

Redes no Compose

O Docker Compose gerencia redes automaticamente, mas também permite configurações avançadas para cenários que exigem isolamento, IPs fixos, redes externas e aliases personalizados.

Rede Padrão — Criada Automaticamente

Quando você roda docker compose up, o Compose cria automaticamente uma rede bridge chamada <projeto>_default:

Rede default — Comportamento automáticoPadrão
# SEM definir "networks:" no compose, TODOS os services
# são colocados na mesma rede default automaticamente.

# Arquivo: ~/webapp/docker-compose.yml
services:
  api:
    image: node:20-alpine
    command: node server.js

  db:
    image: postgres:16

  redis:
    image: redis:7

# Ao rodar docker compose up:
# 1. Cria rede: webapp_default (bridge)
# 2. Conecta TODOS os services a essa rede
# 3. DNS automático: cada service é acessível pelo NOME

# Dentro do container "api":
#   ping db      → resolve para IP do postgres
#   ping redis   → resolve para IP do redis

# O NOME DO SERVICE = HOSTNAME DNS
# api pode conectar em: postgresql://db:5432/app
# api pode conectar em: redis://redis:6379

# Verificar rede criada:
docker network ls | grep webapp
# abcdef123456   webapp_default   bridge   local

# Inspecionar:
docker network inspect webapp_default
# → Mostra subnet, gateway, containers conectados

# IMPORTANTE: a rede default é REMOVIDA com docker compose down
docker compose down
# Removing network webapp_default
💡 Para a maioria dos casos: A rede default é suficiente. Só defina redes customizadas quando precisar de isolamento entre grupos de serviços (ex: frontend não deve acessar banco direto).

Redes Customizadas

Defina redes customizadas para segmentar sua aplicação e controlar quem pode se comunicar com quem:

Redes customizadas — IsolamentoSegurança
# REDES CUSTOMIZADAS: isolar grupos de serviços
# ═══════════════════════════════════════════════════════════════

services:
  # Nginx: apenas na rede frontend (ponto de entrada)
  nginx:
    image: nginx:alpine
    ports:
      - "80:80"
    networks:
      - frontend

  # API: em AMBAS as redes (ponte entre frontend e backend)
  api:
    build: .
    networks:
      - frontend     # Nginx acessa a API
      - backend      # API acessa o banco

  # Banco: apenas na rede backend (isolado!)
  db:
    image: postgres:16
    networks:
      - backend

  # Redis: apenas na rede backend
  redis:
    image: redis:7
    networks:
      - backend

# DEFINIÇÃO DAS REDES:
networks:
  frontend:
    driver: bridge
    # Rede para tráfego "público" (vindo do Nginx)

  backend:
    driver: bridge
    # Rede para serviços internos (DB, cache)

# ┌─────────────────────────────────────────────────────┐
# │ FRONTEND NETWORK                                     │
# │   nginx ←────→ api                                  │
# └─────────────────────────────────────────────────────┘
# ┌─────────────────────────────────────────────────────┐
# │ BACKEND NETWORK                                      │
# │   api ←────→ db                                     │
# │   api ←────→ redis                                  │
# └─────────────────────────────────────────────────────┘
#
# nginx → db:    ❌ BLOQUEADO (redes diferentes)
# nginx → redis: ❌ BLOQUEADO (redes diferentes)
# Usuário → db:  ❌ BLOQUEADO (sem ports publicados)
#
# SEGURANÇA: banco NUNCA é exposto diretamente!

# ✅ Bancos de dados (PostgreSQL, MySQL, MongoDB)
# ✅ Caches (Redis, Memcached)
# ✅ Message queues (RabbitMQ, Kafka)
# ✅ Serviços que processam dados sensíveis
# ✅ Qualquer serviço que NÃO precisa acessar internet

# docker compose exec db ping google.com
# → ping: bad address 'google.com'  (DNS falha)
# → connect: Network is unreachable

Volumes

Volumes no Compose

Volumes no Compose permitem persistir dados entre restarts, compartilhar arquivos entre host e containers, e manter configurações de forma declarativa. Entenda todas as opções disponíveis.

Named Volumes — Declarados no Top-Level

Named volumes são gerenciados pelo Docker e declarados na seção volumes: de nível superior. São a forma recomendada para persistir dados:

Named Volumes — Declaração e usoPersistência
# NAMED VOLUMES: gerenciados pelo Docker
# ═══════════════════════════════════════════════════════════════

services:
  db:
    image: postgres:16
    volumes:
      - db-data:/var/lib/postgresql/data    # Named volume

  redis:
    image: redis:7-alpine
    volumes:
      - redis-data:/data                    # Named volume

  app:
    build: .
    volumes:
      - app-uploads:/app/uploads            # Named volume
      - app-logs:/app/logs                  # Named volume

# DECLARAÇÃO TOP-LEVEL (obrigatória para named volumes):
volumes:
  # Forma simples (driver padrão: local):
  db-data:
  redis-data:
  app-uploads:
  app-logs:

  # Forma com opções:
  db-data:
    driver: local
    driver_opts:
      type: none
      device: /mnt/ssd/postgres-data     # Path específico no host
      o: bind
    labels:
      com.empresa.backup: "daily"
      com.empresa.retention: "30d"

  # Com nome customizado (diferente da key):
  cache:
    name: "production-redis-data"
    # Cria: production-redis-data (não projeto_cache)

# CICLO DE VIDA:
# docker compose up   → Cria volumes (se não existem)
# docker compose down → NÃO remove volumes (dados preservados!)
# docker compose down -v → REMOVE volumes (⚠️ PERDA DE DADOS!)

# VERIFICAR:
# docker volume ls | grep projeto
# docker volume inspect projeto_db-data
🔑 Regra de ouro: docker compose down preserva volumes. Use docker compose down -v apenas quando quiser destruir todos os dados (ex: reset de ambiente dev). Em produção, NUNCA use -v sem backup.

Bind Mounts — Diretórios do Host

Bind Mounts — Sincronizar com o hostDesenvolvimento
# BIND MOUNTS: mapear diretório/arquivo do host para o container
# ═══════════════════════════════════════════════════════════════

services:
  # Desenvolvimento com hot reload:
  app-dev:
    build: .
    volumes:
      # Código fonte (hot reload em dev):
      - ./src:/app/src

      # Configuração (read-only):
      - ./config/app.yml:/app/config/app.yml:ro

      # Evitar sobrescrever node_modules do container:
      - ./src:/app/src
      - /app/node_modules            # Volume anônimo (preserva)

    # Formato longo para mais controle:
    volumes:
      - type: bind
        source: ./src
        target: /app/src
        consistency: delegated    # Mac: melhor performance

      - type: bind
        source: ./nginx.conf
        target: /etc/nginx/nginx.conf
        read_only: true

# PATHS RELATIVOS:
# ./   → relativo ao diretório do docker-compose.yml
# ../  → um nível acima
# ~    → NÃO funciona no Compose! Use path absoluto ou ./

# BOAS PRÁTICAS PARA BIND MOUNTS:
# ✅ Use para código em desenvolvimento (hot reload)
# ✅ Use :ro para configs (read-only)
# ✅ Não use em produção (prefira named volumes ou COPY no Dockerfile)
# ✅ Cuidado com permissões (UID/GID do container vs host)

# PROBLEMA COMUM EM LINUX:
# Container cria arquivos como root → você não pode editar no host
# SOLUÇÃO: definir user no service
services:
  app:
    build: .
    user: "1000:1000"    # Mesmo UID/GID do seu usuário
    volumes:
      - ./src:/app/src

tmpfs — Volume em memória RAMPerformance
# tmpfs: monta diretório em memória (RAM)
# NÃO persiste entre restarts!
# ═══════════════════════════════════════════

services:
  # Formato curto (seção tmpfs):
  app:
    image: minha-app:latest
    tmpfs:
      - /app/tmp
      - /app/cache

  # Formato longo (na seção volumes):
  api:
    image: api:latest
    volumes:
      - type: tmpfs
        target: /app/tmp
        tmpfs:
          size: 104857600     # 100MB (em bytes)
          mode: 1777          # Permissões

  # Com limite de tamanho:
  worker:
    image: worker:latest
    tmpfs:
      - /tmp:size=50M

# QUANDO USAR tmpfs:
# ✅ Arquivos temporários que NÃO precisam persistir
# ✅ Cache em memória (muito rápido!)
# ✅ Secrets que não devem ir para disco
# ✅ Dados de sessão efêmeros
# ✅ Diretórios /tmp de alta performance

# VANTAGENS:
# → Mais rápido que filesystem (é RAM!)
# → Dados destruídos quando container para
# → Não gasta I/O de disco
# → Ideal para dados sensíveis temporários
Comandos

Comandos do docker compose

Todos os comandos essenciais para operar sua stack Compose no dia a dia — desde subir e derrubar serviços até monitorar logs, executar comandos e validar configurações.

docker compose up — Subir a Stack

docker compose up — Todas as variaçõesEssencial
# docker compose up: cria e inicia TODOS os serviços
# ═══════════════════════════════════════════════════════════════

# Subir em foreground (logs no terminal):
docker compose up

# Subir em background (detached):
docker compose up -d

# Subir apenas serviços específicos:
docker compose up -d api db
# Sobe api + db + dependências declaradas em depends_on

# Rebuild imagens antes de subir:
docker compose up -d --build
# Força docker build mesmo se imagem já existe

# Forçar recreate dos containers:
docker compose up -d --force-recreate
# Remove e recria containers (mesmo sem mudanças)
# Útil quando mudou env vars ou configurações

# Não recriar containers que não mudaram:
docker compose up -d --no-recreate
# Só cria containers NOVOS (não toca nos existentes)

# Remover containers órfãos (serviços removidos do YAML):
docker compose up -d --remove-orphans
# Se você removeu um service do YAML, o container antigo
# ainda existe. --remove-orphans limpa esses "fantasmas"

# Escalar um serviço:
docker compose up -d --scale worker=5
# Cria 5 instâncias do service "worker"

# Timeout para esperar containers:
docker compose up -d --timeout 60
# Espera até 60s para containers ficarem healthy

# COMBINAÇÃO COMUM PARA DEV:
docker compose up -d --build --remove-orphans

# COMBINAÇÃO COMUM PARA ATUALIZAR PRODUÇÃO:
docker compose up -d --build --force-recreate --remove-orphans

# O QUE docker compose up FAZ internamente:
# 1. Lê docker-compose.yml (e overrides)
# 2. Cria networks (se não existem)
# 3. Cria volumes (se não existem)
# 4. Puxa imagens (pull) se necessário
# 5. Constrói imagens (build) se configurado
# 6. Cria containers na ordem de depends_on
# 7. Inicia containers
# 8. Mostra logs (foreground) ou retorna (detached)

docker compose down — Derrubar a Stack

docker compose down — Todas as variaçõesEssencial
# docker compose down: para e REMOVE containers + rede
# ═══════════════════════════════════════════════════════════════

# Down básico (containers + rede default):
docker compose down
# ✅ Para todos os containers
# ✅ Remove todos os containers
# ✅ Remove redes criadas pelo Compose
# ❌ NÃO remove volumes (dados preservados!)
# ❌ NÃO remove imagens

# Down + remover volumes (⚠️ DADOS PERDIDOS!):
docker compose down -v
docker compose down --volumes
# Remove TUDO acima + named volumes
# ⚠️ CUIDADO: banco de dados, uploads, TUDO é apagado!

# Down + remover imagens:
docker compose down --rmi all
# Remove TUDO + todas as imagens usadas pelos serviços
# (tanto pulled quanto built)

docker compose down --rmi local
# Remove apenas imagens que foram BUILT localmente
# (não remove imagens pulled do registry)

# Down + remover órfãos:
docker compose down --remove-orphans
# Remove containers de serviços que não estão mais no YAML

# Down com timeout (espera containers pararem):
docker compose down --timeout 30
# Espera 30s antes de SIGKILL (padrão: 10s)

# COMBINAÇÃO "NUCLEAR" (reset total do ambiente):
docker compose down -v --rmi all --remove-orphans
# Remove TUDO: containers, volumes, imagens, redes, órfãos
# Ambiente volta ao estado "limpo"

# TABELA RESUMO:
# ┌────────────────────────────────────────────────┐
# │ Flag              │ Remove                      │
# │───────────────────│─────────────────────────────│
# │ (nenhuma)         │ Containers + Redes          │
# │ -v / --volumes    │ + Named volumes             │
# │ --rmi all         │ + Todas imagens             │
# │ --rmi local       │ + Imagens built localmente  │
# │ --remove-orphans  │ + Containers órfãos         │
# └────────────────────────────────────────────────┘
⚠️ CUIDADO: docker compose down -v destrói TODOS os dados armazenados em named volumes (bancos de dados, uploads, etc.). Use apenas quando quiser um reset completo. Em produção, SEMPRE faça backup antes!

Controle de ciclo de vidaOperações
# ═══════════════════════════════════════════════════════════════
# CONTROLE DO CICLO DE VIDA DOS CONTAINERS
# ═══════════════════════════════════════════════════════════════

# STOP: parar containers (sem remover)
docker compose stop            # Para todos
docker compose stop api        # Para apenas api
docker compose stop -t 30 api  # Timeout de 30s antes de SIGKILL

# START: iniciar containers parados
docker compose start           # Inicia todos os parados
docker compose start api       # Inicia apenas api

# RESTART: parar + iniciar
docker compose restart         # Restart de todos
docker compose restart api     # Restart apenas api
docker compose restart -t 20 api  # Timeout de 20s

# PAUSE / UNPAUSE: congelar processos (SIGSTOP/SIGCONT)
docker compose pause api       # Congela (CPU = 0, mas mantém memória)
docker compose unpause api     # Descongela

# RUN: executar comando em container NOVO (one-shot)
docker compose run api npm test
docker compose run api npm run migrate
docker compose run --rm api sh        # Remove container após sair
docker compose run -d worker process  # Run em background
docker compose run --no-deps api sh   # Sem subir dependências

# KILL: forçar parada (SIGKILL imediato)
docker compose kill            # Kill em todos
docker compose kill -s SIGTERM api  # Enviar signal específico

# DIFERENÇAS IMPORTANTES:
# ┌─────────────────────────────────────────────────────────┐
# │ stop/start  → Para/inicia containers existentes         │
# │ restart     → stop + start (mesmo container)            │
# │ down/up     → Remove + recria (container novo)          │
# │ run         → Cria container NOVO temporário            │
# │ exec        → Executa em container JÁ rodando          │

Uma API REST em Flask com banco PostgreSQL para persistência e Redis para cache/sessões:

Flask + PostgreSQL + Redis — docker-compose.ymlPython Stack
# ════════════════════════════════════════════════════════════════
# STACK: Flask API + PostgreSQL + Redis
# Ambiente: Produção (single-host)
# ════════════════════════════════════════════════════════════════

services:
  # ──────────────────────────────────────────────────────────────
  # API Flask (aplicação principal)
  # ──────────────────────────────────────────────────────────────
  api:
    build:
      context: .
      dockerfile: Dockerfile
      target: production           # Multi-stage: estágio de produção
    container_name: flask-api
    ports:
      - "8000:8000"
    environment:
      FLASK_ENV: production
      DATABASE_URL: postgresql://${DB_USER}:${DB_PASSWORD}@db:5432/${DB_NAME}
      REDIS_URL: redis://redis:6379/0
      SECRET_KEY: ${SECRET_KEY}
      LOG_LEVEL: info
    env_file:
      - .env.production
    volumes:
      - app-uploads:/app/uploads   # Uploads persistentes
      - app-logs:/app/logs         # Logs persistentes
    networks:
      - frontend
      - backend
    depends_on:
      db:
        condition: service_healthy
      redis:
        condition: service_healthy
    restart: unless-stopped
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:8000/health"]
      interval: 30s
      timeout: 10s
      retries: 3
      start_period: 30s
    deploy:
      resources:
        limits:
          cpus: "1.0"
          memory: 512M
        reservations:
          cpus: "0.25"
          memory: 128M

  # ──────────────────────────────────────────────────────────────
  # PostgreSQL (banco de dados principal)
  # ──────────────────────────────────────────────────────────────
  db:
    image: postgres:16-alpine
    container_name: flask-postgres
    environment:
      POSTGRES_USER: ${DB_USER}
      POSTGRES_PASSWORD: ${DB_PASSWORD}
      POSTGRES_DB: ${DB_NAME}
      PGDATA: /var/lib/postgresql/data/pgdata
    volumes:
      - postgres-data:/var/lib/postgresql/data
      - ./docker/postgres/init.sql:/docker-entrypoint-initdb.d/01-init.sql:ro
      - ./docker/postgres/backup:/backups
    networks:
      - backend
    restart: unless-stopped
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ${DB_USER} -d ${DB_NAME}"]
      interval: 10s
      timeout: 5s
      retries: 5
      start_period: 30s
    deploy:
      resources:
        limits:
          cpus: "2.0"
          memory: 1G
        reservations:
          cpus: "0.5"
          memory: 256M

  # ──────────────────────────────────────────────────────────────
  # Redis (cache + sessões + fila de tarefas)
  # ──────────────────────────────────────────────────────────────
  redis:
    image: redis:7-alpine
    container_name: flask-redis
    command: >
      redis-server
      --appendonly yes
      --maxmemory 256mb
      --maxmemory-policy allkeys-lru
      --requirepass ${REDIS_PASSWORD}
    volumes:
      - redis-data:/data
    networks:
      - backend
    restart: unless-stopped
    healthcheck:
      test: ["CMD", "redis-cli", "-a", "${REDIS_PASSWORD}", "ping"]
      interval: 10s
      timeout: 5s
      retries: 3
    deploy:

# + depends_on com condition: service_healthy
# ════════════════════════════════════════════════════════════════

    image: postgres:16-alpine

      interval: 5s
      timeout: 3s
      retries: 10
      start_period: 20s

    image: redis:7-alpine
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 3s
      retries: 5

  # CAMADA 2: Migrations (depende da infra)
  migrations:
    build: .
    command: npm run db:migrate
    depends_on:
      db:
        condition: service_healthy     # DB pronto para queries!
    restart: "no"                       # Roda uma vez e para

  api:
    build: .
    depends_on:
      db:
        condition: service_healthy
      redis:
        condition: service_healthy
      migrations:
        condition: service_completed_successfully  # Migrations OK!
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:3000/health"]
      interval: 15s
      timeout: 5s
      retries: 3
      start_period: 30s

  # CAMADA 4: Reverse Proxy (depende da app)
  nginx:
    image: nginx:alpine
    depends_on:
      api:
        condition: service_healthy     # API pronta para requests!

# ✅ Sem race conditions no startup
# ✅ Sem "connection refused" durante inicialização
# ✅ Migrations rodam ANTES da app iniciar
# ✅ Nginx só recebe tráfego quando API está pronta
# ✅ docker compose ps mostra status real (healthy/unhealthy)

Checklist de Boas Práticas

📋 Segurança

  • Use env_file para variáveis sensíveis
  • Adicione .env* ao .gitignore
  • Crie .env.example como template (commitado)
  • Use redes internal: true para DBs
  • Não exponha portas de bancos em produção
  • Use read_only: true para configs montadas
  • Defina deploy.resources.limits (evita OOM)

📋 Confiabilidade

  • Defina healthcheck em CADA serviço
  • Use depends_on com condition: service_healthy
  • Sempre use restart: unless-stopped em prod
  • Nomeie volumes (não use anônimos em prod)
  • Use tags fixas nas imagens (não :latest)
  • Defina start_period adequado nos healthchecks
  • Teste com docker compose config antes de deploy

📋 Organização

  • Use override files para separar dev/prod
  • Use profiles para ferramentas opcionais
  • Comente seções importantes do YAML
  • Agrupe services por camada (infra → app → proxy)
  • Use .dockerignore para builds menores
  • Prefira compose.yaml (formato novo)
  • Documente com README.md como subir o projeto

📋 Performance

  • Use multi-stage builds no Dockerfile
  • Use imagens -alpine (menores)
  • Configure maxmemory no Redis
  • Use tmpfs para dados temporários
  • Defina limites de CPU/memória com deploy
  • Use --parallel no build
  • Cache de build com cache_from

Exercício 2: Adicionar Nginx como Reverse Proxy

Exercício 2 — InstruçõesPrática
# ════════════════════════════════════════════════════════════════
# EXERCÍCIO 2: Adicionar Nginx como Reverse Proxy
# ════════════════════════════════════════════════════════════════
#
# OBJETIVO: Extender o exercício 1 adicionando Nginx
# na frente da API Flask como reverse proxy.
#
# REQUISITOS:
# 1. Novo service "nginx":
#    - Imagem: nginx:alpine
#    - Porta 80 no host (remover porta 5000 da api)
#    - Volume bind mount para nginx.conf
#    - Depende da API (condition: service_healthy)
#    - Healthcheck
#
# 2. Criar nginx.conf com:
#    - Proxy pass para http://api:5000
#    - Headers de proxy (X-Real-IP, X-Forwarded-For)
#    - Location /health para healthcheck do Nginx
#
# 3. Separar redes:
#    - "frontend": nginx + api
#    - "backend": api + db + redis
#    - Nginx NÃO deve acessar db/redis diretamente
#
# 4. API não deve ter porta exposta no host (apenas via Nginx)
#
# ARQUIVO nginx.conf:
cat > nginx/nginx.conf << 'EOF'
events {
    worker_connections 1024;
}

http {
    upstream flask_app {
        server api:5000;
    }

    server {
        listen 80;
        server_name _;

        location / {
            proxy_pass http://flask_app;
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $scheme;
            proxy_connect_timeout 30s;
            proxy_read_timeout 30s;
        }

        location /health {
            access_log off;
            return 200 "OK\n";
            add_header Content-Type text/plain;
        }
    }
}
EOF

# MODIFICAÇÕES NO docker-compose.yml:
# - Remover ports da api (apenas expose: "5000")
# - Adicionar service nginx com port 80
# - Criar 2 redes: frontend e backend
# - Api conectada a ambas
# - Nginx apenas em frontend
# - DB e Redis apenas em backend

# VALIDAÇÃO:
# ✅ curl localhost → resposta da API (via Nginx)
# ✅ curl localhost:5000 → connection refused (porta não exposta)
# ✅ docker compose exec nginx ping db → falha (redes separadas)
# ✅ docker compose exec api ping db → funciona

Exercício 4 — InstruçõesPrática
# ════════════════════════════════════════════════════════════════
# EXERCÍCIO 4: Implementar Healthcheck + Depends_on com Condition
# ════════════════════════════════════════════════════════════════
#
# OBJETIVO: Garantir que os serviços só iniciam quando suas
# dependências estão REALMENTE prontas (não apenas "rodando").
#
# CENÁRIO: API que precisa de migrations antes de iniciar
#
# REQUISITOS:
# 1. Service "db": healthcheck com pg_isready
#    - interval: 5s, timeout: 3s, retries: 10, start_period: 15s
#
# 2. Service "redis": healthcheck com redis-cli ping
#    - interval: 5s, timeout: 3s, retries: 5
#
# 3. Service "migrations" (roda UMA vez e para):
#    - Mesmo build que api
#    - Command: python manage.py migrate
#    - depends_on db: condition: service_healthy
#    - restart: "no" (não reiniciar após completar)
#
# 4. Service "seed" (popular dados iniciais):
#    - Mesmo build que api
#    - Command: python manage.py seed
#    - depends_on migrations: condition: service_completed_successfully
#    - restart: "no"
#
# 5. Service "api":
#    - depends_on:
#        db: condition: service_healthy
#        redis: condition: service_healthy
#        migrations: condition: service_completed_successfully
#    - Healthcheck: curl /health
#
# 6. Service "nginx":
#    - depends_on api: condition: service_healthy
#
# ORDEM ESPERADA DE STARTUP:
# 1. db + redis (paralelo, sem dependências)
# 2. migrations (após db healthy)
# 3. seed (após migrations completed)
# 4. api (após db healthy + redis healthy + migrations completed)
# 5. nginx (após api healthy)
#
# COMO OBSERVAR A ORDEM:
docker compose up
# (sem -d, para ver logs em tempo real)
# Você verá:
# ✓ db e redis iniciando
# ✓ "waiting for db to become healthy..."
# ✓ migrations rodando e completando
# ✓ api iniciando
# ✓ nginx iniciando por último

# TESTE DE FALHA:
# 1. Faça o migrations falhar (exit 1):
#    command: "exit 1"
# 2. Observe que api NÃO inicia
# 3. docker compose ps → migrations: exited (1)
# 4. api e nginx não aparecem como running

# VALIDAÇÃO:
# ✅ docker compose up mostra ordem correta de startup
# ✅ API só inicia DEPOIS de migrations completar com sucesso
# ✅ Nginx só inicia DEPOIS de API estar healthy
# ✅ Se DB falha no healthcheck, nada mais sobe
# ✅ docker compose ps mostra status (healthy) para todos
