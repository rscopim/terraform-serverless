Docker em Produção e CI/CD

Leve seus containers para produção com registries privados, pipelines CI/CD automatizados, Docker Swarm e estratégias de troubleshooting.

Registry Privado

docker login / push / pull registry

Autentique e publique imagens em registries privados (ECR, ACR, GCR, Docker Hub).

# Login no Docker Hub
docker login

# Login em registry privado (AWS ECR)
aws ecr get-login-password --region us-east-1 | \
  docker login --username AWS --password-stdin \
  123456789.dkr.ecr.us-east-1.amazonaws.com

# Tag para o registry
docker tag app:v1 \
  123456789.dkr.ecr.us-east-1.amazonaws.com/app:v1

# Push para o registry
docker push \
  123456789.dkr.ecr.us-east-1.amazonaws.com/app:v1

# Pull do registry
docker pull \
  123456789.dkr.ecr.us-east-1.amazonaws.com/app:v1
Estratégias de Tagging versionamento

Use tags semânticas para rastreabilidade e rollback.

# Semantic Versioning (recomendado)
docker tag app:latest registry/app:1.2.3
docker tag app:latest registry/app:1.2
docker tag app:latest registry/app:1

# Git SHA (rastreabilidade exata)
GIT_SHA=$(git rev-parse --short HEAD)
docker tag app:latest registry/app:${GIT_SHA}

# Data + Build number
docker tag app:latest registry/app:2024.01.15-42

# Combinação (melhor prática)
docker tag app:latest registry/app:1.2.3
docker tag app:latest registry/app:1.2.3-abc1234
docker tag app:latest registry/app:latest

# ⚠️ NUNCA use apenas :latest em produção!

Docker Compose para Produção

docker-compose.prod.yml produção

Compose otimizado para produção com imagens do registry, healthchecks e limites de recursos.

services:
  api:
    image: 123456789.dkr.ecr.us-east-1.amazonaws.com/app:1.2.3
    restart: unless-stopped
    deploy:
      resources:
        limits:
          cpus: "1.0"
          memory: 512M
        reservations:
          cpus: "0.25"
          memory: 128M
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:4000/health"]
      interval: 30s
      timeout: 10s
      retries: 3
      start_period: 40s
    logging:
      driver: json-file
      options:
        max-size: "10m"
        max-file: "5"
    environment:
      - NODE_ENV=production
    ports:
      - "4000:4000"

  db:
    image: postgres:16-alpine
    restart: always
    volumes:
      - pgdata:/var/lib/postgresql/data
    deploy:
      resources:
        limits:
          memory: 1G
    logging:
      driver: json-file
      options:
        max-size: "20m"
        max-file: "10"

volumes:
  pgdata:

Logging em Produção

Logging Drivers observabilidade

Configure drivers de log para centralizar e gerenciar logs em produção.

# json-file (padrão) — com rotação
docker run -d \
  --log-driver json-file \
  --log-opt max-size=10m \
  --log-opt max-file=5 \
  app:v1

# syslog — enviar para servidor syslog
docker run -d \
  --log-driver syslog \
  --log-opt syslog-address=tcp://logserver:514 \
  --log-opt tag="{{.Name}}" \
  app:v1

# fluentd — agregação com Fluentd/Fluent Bit
docker run -d \
  --log-driver fluentd \
  --log-opt fluentd-address=localhost:24224 \
  --log-opt tag="docker.{{.Name}}" \
  app:v1

# awslogs — direto para CloudWatch
docker run -d \
  --log-driver awslogs \
  --log-opt awslogs-region=us-east-1 \
  --log-opt awslogs-group=/ecs/app \
  --log-opt awslogs-stream-prefix=prod \
  app:v1

CI/CD com GitHub Actions

.github/workflows/docker.yml CI/CD

Pipeline completo: build, scan, push para registry com cache otimizado.

name: Docker Build & Push

on:
  push:
    branches: [main]
    tags: ["v*"]
  pull_request:
    branches: [main]

env:
  REGISTRY: ghcr.io
  IMAGE_NAME: ${{ github.repository }}

jobs:
  build-and-push:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write

    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Set up Docker Buildx
        uses: docker/setup-buildx-action@v3

      - name: Login to Container Registry
        uses: docker/login-action@v3
        with:
          registry: ${{ env.REGISTRY }}
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Extract metadata (tags, labels)
        id: meta
        uses: docker/metadata-action@v5
        with:
          images: ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}
          tags: |
            type=semver,pattern={{version}}
            type=semver,pattern={{major}}.{{minor}}
            type=sha,prefix=
            type=ref,event=branch

      - name: Build and Push
        uses: docker/build-push-action@v5
        with:
          context: .
          push: ${{ github.event_name != 'pull_request' }}
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          cache-from: type=gha
          cache-to: type=gha,mode=max

CI/CD com GitLab CI

.gitlab-ci.yml CI/CD

Pipeline GitLab com build, test e deploy para registry.

stages:
  - build
  - test
  - deploy

variables:
  IMAGE_TAG: $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA
  IMAGE_LATEST: $CI_REGISTRY_IMAGE:latest

build:
  stage: build
  image: docker:24
  services:
    - docker:24-dind
  before_script:
    - docker login -u $CI_REGISTRY_USER -p $CI_REGISTRY_PASSWORD $CI_REGISTRY
  script:
    - docker build --cache-from $IMAGE_LATEST -t $IMAGE_TAG -t $IMAGE_LATEST .
    - docker push $IMAGE_TAG
    - docker push $IMAGE_LATEST
  only:
    - main
    - tags

test:
  stage: test
  image: $IMAGE_TAG
  script:
    - npm run test
  needs: [build]

scan:
  stage: test
  image: aquasec/trivy:latest
  script:
    - trivy image --exit-code 1 --severity HIGH,CRITICAL $IMAGE_TAG
  needs: [build]
  allow_failure: true

deploy:
  stage: deploy
  image: docker:24
  services:
    - docker:24-dind
  script:
    - docker login -u $CI_REGISTRY_USER -p $CI_REGISTRY_PASSWORD $CI_REGISTRY
    - docker pull $IMAGE_TAG
    - docker tag $IMAGE_TAG $CI_REGISTRY_IMAGE:production
    - docker push $CI_REGISTRY_IMAGE:production
  only:
    - tags
  when: manual

Docker Swarm

Inicialização e Nodes cluster

Configure um cluster Swarm para orquestração nativa do Docker.

# Inicializar Swarm (no manager)
docker swarm init --advertise-addr 192.168.1.10

# Token para workers se juntarem
docker swarm join-token worker

# Listar nodes do cluster
docker node ls

# Promover worker a manager
docker node promote worker-01

# Remover node do cluster
docker node rm worker-02
Services deploy

Crie e gerencie serviços distribuídos no cluster.

# Criar serviço com réplicas
docker service create \
  --name api \
  --replicas 3 \
  --publish 8080:4000 \
  --env NODE_ENV=production \
  registry/app:1.2.3

# Listar serviços
docker service ls

# Ver tasks (containers) do serviço
docker service ps api

# Escalar réplicas
docker service scale api=5

# Logs do serviço
docker service logs -f api
Updates e Rollback deploy

Rolling updates e rollback automático em caso de falha.

# Update da imagem (rolling update)
docker service update \
  --image registry/app:1.3.0 \
  --update-parallelism 1 \
  --update-delay 10s \
  --update-failure-action rollback \
  api

# Rollback manual
docker service rollback api

# Remover serviço
docker service rm api
Stacks deploy

Deploy de aplicações completas via compose file no Swarm.

# Deploy stack a partir de compose file
docker stack deploy -c docker-compose.yml myapp

# Listar stacks
docker stack ls

# Serviços da stack
docker stack services myapp

# Tasks da stack
docker stack ps myapp

# Remover stack
docker stack rm myapp

Cleanup e Manutenção

Comandos de Limpeza manutenção

Mantenha o ambiente limpo removendo recursos não utilizados.

# Ver uso de disco
docker system df

# Limpar containers parados
docker container prune

# Limpar imagens sem tag (dangling)
docker image prune

# Limpar imagens não utilizadas por nenhum container
docker image prune -a

# Limpar volumes órfãos
docker volume prune

# Limpar redes não utilizadas
docker network prune

# Limpar build cache
docker builder prune

# NUCLEAR: limpar TUDO não utilizado + volumes
docker system prune -a --volumes
# ⚠️ Cuidado: remove dados persistentes!

Troubleshooting

Container Crashando debug

Diagnostique containers que reiniciam ou falham ao iniciar.

# Ver logs do container que crashou
docker logs --tail 100 meu-app
docker logs --since 5m meu-app

# Inspecionar exit code
docker inspect meu-app --format='{{.State.ExitCode}}'
# ExitCode 137 = OOM Killed (falta memória)
# ExitCode 1   = Erro da aplicação
# ExitCode 0   = Saiu normalmente

# Ver estado detalhado
docker inspect meu-app --format='{{json .State}}' | jq

# Eventos do daemon
docker events --filter container=meu-app

# Ver se foi OOM killed
docker inspect meu-app --format='{{.State.OOMKilled}}'
Debug de Rede debug

Diagnostique problemas de conectividade entre containers.

# Container de debug na mesma rede
docker run --rm -it --network app_default \
  nicolaka/netshoot sh

# Testar DNS interno
nslookup api
nslookup db

# Testar conectividade
ping api
curl -v http://api:4000/health

# Inspecionar rede
docker network inspect app_default

# Ver portas mapeadas
docker port meu-app
Health Status debug

Verifique o status de saúde dos containers.

# Ver health status
docker inspect meu-app \
  --format='{{.State.Health.Status}}'
# healthy | unhealthy | starting

# Histórico de health checks
docker inspect meu-app \
  --format='{{json .State.Health}}' | jq

# Filtrar containers unhealthy
docker ps --filter health=unhealthy

# Ver logs do healthcheck
docker inspect meu-app \
  --format='{{range .State.Health.Log}}{{.Output}}{{end}}'
Inspect com jq debug

Use jq para extrair informações específicas do inspect.

# IP do container
docker inspect meu-app | \
  jq -r '.[0].NetworkSettings.IPAddress'

# Variáveis de ambiente
docker inspect meu-app | \
  jq '.[0].Config.Env'

# Mounts/Volumes
docker inspect meu-app | \
  jq '.[0].Mounts'

# Port bindings
docker inspect meu-app | \
  jq '.[0].NetworkSettings.Ports'

# Restart count
docker inspect meu-app | \
  jq '.[0].RestartCount'
