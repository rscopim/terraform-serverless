Realidade

Containers em Produção — Realidade

Docker em produção é muito diferente de desenvolvimento local. Aqui você precisa pensar em disponibilidade, observabilidade, escalabilidade e recuperação. A primeira decisão é: Docker sozinho ou com orquestrador?

Docker Sozinho vs Orquestradores

Não existe resposta única. A escolha depende da complexidade, escala e equipe disponível:

Docker Compose em ProduçãoSimples
# DOCKER COMPOSE EM PRODUÇÃO
# ════════════════════════════════════════
#
# QUANDO USAR:
# ✅ 1 servidor (single-host)
# ✅ Poucos services (< 10)
# ✅ Tráfego previsível
# ✅ Equipe pequena (1-5 devs)
# ✅ Startups, projetos pessoais, MVPs
# ✅ Aplicações internas
#
# VANTAGENS:
# • Simples de operar
# • Curva de aprendizado baixa
# • restart: unless-stopped = auto-recovery
# • docker compose pull + up = deploy
# • Funciona em qualquer VPS de $5/mês
#
# LIMITAÇÕES:
# ❌ Sem auto-scaling
# ❌ Sem rolling updates nativos (downtime)
# ❌ Single point of failure (1 host)
# ❌ Sem service discovery avançado
# ❌ Sem self-healing sofisticado
#
# CENÁRIO IDEAL:
# • Blog/site com 1000-50000 visitas/dia
# • API interna com poucos endpoints
# • SaaS em estágio inicial
# • Microserviços em fase de validação
#
# DEPLOY TÍPICO:
ssh server "cd /app && \
  docker compose pull && \
  docker compose up -d"
Kubernetes / Swarm em ProduçãoEscala
# ORQUESTRADORES EM PRODUÇÃO
# ════════════════════════════════════════
#
# QUANDO USAR ORQUESTRADOR:
# ✅ Multi-host (cluster)
# ✅ Alta disponibilidade (HA) necessária
# ✅ Auto-scaling (horizontal)
# ✅ Rolling updates sem downtime
# ✅ Muitos services (10+)
# ✅ Equipe com expertise DevOps
#
# OPÇÕES:
#
# 1. DOCKER SWARM (simples)
# • Integrado ao Docker CLI
# • Fácil migração de Compose
# • Bom para equipes pequenas
# • Menos features que K8s
#
# 2. KUBERNETES (enterprise)
# • Padrão da indústria
# • Ecossistema enorme
# • Auto-scaling, self-healing
# • Curva de aprendizado ALTA
# • Precisa de equipe dedicada
#
# 3. MANAGED K8s (cloud)
# • EKS (AWS), GKE (GCP), AKS (Azure)
# • Control plane gerenciado
# • Mais caro, menos ops
#
# DECISÃO:
# < 5 services + 1 host → Compose
# 5-20 services OU HA → Swarm
# > 20 services + escala → Kubernetes
# Enterprise + budget → Managed K8s
🔑 Regra prática: Comece com Docker Compose em produção. Migre para Swarm quando precisar de HA ou rolling updates. Migre para Kubernetes quando Swarm não for suficiente. Não comece por K8s — a complexidade operacional é enorme para equipes pequenas.

Logging

Logging

Em produção, logs são seu principal mecanismo de debug. Docker captura stdout/stderr de cada container. O desafio é coletar, agregar e pesquisar logs de dezenas de containers de forma eficiente.

Logging Drivers do Docker

Docker suporta múltiplos drivers de logging que determinam para onde os logs vão:

json-file (padrão)Default
# JSON-FILE — Driver padrão
# ════════════════════════════════════════
#
# COMO FUNCIONA:
# Docker grava stdout/stderr em arquivos JSON
# em /var/lib/docker/containers/{id}/{id}-json.log
#
# CONFIGURAR NO COMPOSE:
services:
  api:
    image: minha-api
    logging:
      driver: json-file
      options:
        max-size: "10m"    # Rotaciona em 10MB
        max-file: "5"      # Mantém 5 arquivos
        compress: "true"   # Comprime rotacionados
        tag: "{{.Name}}"   # Tag no log

# ⚠️ SEM LIMITES = DISCO CHEIO:
# Sem max-size, logs crescem INFINITAMENTE
# Container de alto tráfego = disco cheio em dias!

# CONFIGURAR GLOBALMENTE:
# /etc/docker/daemon.json
{
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "10m",
    "max-file": "3"
  }
}
# Reiniciar: systemctl restart docker

# ACESSAR LOGS:
docker logs container --tail 100
docker logs container --since 1h
docker logs container -f  # Follow
Drivers para centralizaçãoProdução
# DRIVERS PARA LOGGING CENTRALIZADO
# ════════════════════════════════════════

# 1. SYSLOG — Enviar para syslog server
services:
  api:
    logging:
      driver: syslog
      options:
        syslog-address: "udp://logserver:514"
        tag: "api-{{.Name}}"

# 2. FLUENTD — Coletor flexível
services:
  api:
    logging:
      driver: fluentd
      options:
        fluentd-address: "localhost:24224"
        tag: "docker.api"
        fluentd-async: "true"

# 3. GELF — Para Graylog
services:
  api:
    logging:
      driver: gelf
      options:
        gelf-address: "udp://graylog:12201"
        tag: "api"

# 4. AWSLOGS — Para CloudWatch
services:
  api:
    logging:
      driver: awslogs
      options:
        awslogs-region: us-east-1
        awslogs-group: /docker/api
        awslogs-stream: "{{.Name}}"

# QUAL USAR:
# • Dev/staging: json-file + max-size
# • Prod simples: json-file + Promtail/Loki
# • Prod enterprise: fluentd + ELK
# • AWS: awslogs (integrado)
# • Multi-cloud: fluentd/vector + S3

Logging Centralizado com Loki + Grafana

A stack Grafana Loki é a alternativa leve ao ELK para logging centralizado:

Stack Loki completa com Docker ComposeImplementação
# STACK DE LOGGING: Promtail + Loki + Grafana
# ════════════════════════════════════════════════════════════════
#
# ARQUITETURA:
# Containers → stdout → Docker json-file → Promtail → Loki → Grafana
#
# docker-compose.logging.yml:
services:
  loki:
    image: grafana/loki:2.9.0
    ports:
      - "3100:3100"
    volumes:
      - loki-data:/loki
    command: -config.file=/etc/loki/local-config.yaml
    networks:
      - monitoring

  promtail:
    image: grafana/promtail:2.9.0
    volumes:
      - /var/log:/var/log:ro
      - /var/lib/docker/containers:/var/lib/docker/containers:ro
      - ./promtail-config.yml:/etc/promtail/config.yml:ro
    command: -config.file=/etc/promtail/config.yml
    networks:
      - monitoring
    depends_on:
      - loki

    ports:
      - "3000:3000"
    environment:
      GF_SECURITY_ADMIN_PASSWORD: ${GRAFANA_PASSWORD}
    volumes:
      - grafana-data:/var/lib/grafana
    networks:
      - monitoring
    depends_on:
      - loki

networks:
  monitoring:
    driver: bridge

volumes:
  loki-data:
  grafana-data:

💡 Loki vs ELK: Loki é significativamente mais leve e barato que ELK (Elasticsearch + Logstash + Kibana). Loki indexa apenas labels (metadata), não o conteúdo dos logs, consumindo 10x menos recursos. Para a maioria dos projetos, Loki é a escolha certa.

Healthchecks em Produção

Healthchecks determinam se um container está pronto para receber tráfego:

Healthchecks — Padrões e configuraçãoDisponibilidade
# HEALTHCHECKS EM PRODUÇÃO
# ════════════════════════════════════════════════════════════════

# TIPOS DE HEALTHCHECK:
#
# 1. LIVENESS — "O container está vivo?"
#    Verifica se o processo está respondendo.
#    Se falhar: restart do container.
#
# 2. READINESS — "O container está pronto para tráfego?"
#    Verifica se pode receber requisições.
#    Se falhar: remove do load balancer (não mata).
#
# 3. STARTUP — "O container já inicializou?"
#    Dá tempo para apps lentas iniciarem.
#    Se falhar: restart após N tentativas.

# PADRÕES POR TIPO DE SERVIÇO:
# ─────────────────────────────────────────────────────────────

# API REST / Web:
healthcheck:
  test: ["CMD", "wget", "--spider", "-q", "http://localhost:3000/health"]
  interval: 30s
  timeout: 5s
  retries: 3
  start_period: 30s

# PostgreSQL:
healthcheck:
  test: ["CMD-SHELL", "pg_isready -U postgres -d mydb"]
  interval: 10s
  timeout: 5s
  retries: 5

# Redis:
healthcheck:
  test: ["CMD", "redis-cli", "ping"]
  interval: 10s
  timeout: 3s
  retries: 3

# MongoDB:
healthcheck:
  test: ["CMD", "mongosh", "--eval", "db.adminCommand('ping')"]
  interval: 15s
  timeout: 5s
  retries: 3

# RabbitMQ:
healthcheck:
  test: ["CMD", "rabbitmq-diagnostics", "check_running"]
  interval: 30s
  timeout: 10s
  retries: 3

# Nginx (proxy):
healthcheck:
  test: ["CMD", "nginx", "-t"]
  interval: 30s
  timeout: 5s
  retries: 3

# ENDPOINT /health — O QUE VERIFICAR:
# {
#   "status": "healthy",
#   "checks": {
#     "database": "connected",
#     "redis": "connected",
#     "disk_space": "ok",
#     "memory": "ok"
#   },
#   "version": "1.5.2",
#   "uptime": "2d 5h 30m"
# }

# DICAS:
# • start_period: tempo para app inicializar (evita false positive)
# • interval: NÃO muito baixo (consome recursos)
# • retries: 3 é bom padrão (evita flap)
# • timeout: menor que interval
# • NUNCA ignore healthcheck em produção!
CI/CD

CI/CD com Docker

Docker torna CI/CD mais confiável: builds reproduzíveis, ambientes de teste idênticos à produção, e deploys atômicos com rollback fácil. Veja como integrar Docker no seu pipeline.

Build no CI — Multi-platform e Cache

Construir imagens no CI requer atenção a cache, multi-platform e segurança:

GitHub Actions — Docker buildGitHub
# .github/workflows/docker.yml
# ════════════════════════════════════════
name: Docker Build & Push

on:
  push:
    branches: [main]
    tags: ['v*']
  pull_request:
    branches: [main]

env:
  REGISTRY: ghcr.io
  IMAGE_NAME: ${{ github.repository }}

jobs:
  build:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write

    steps:
    - uses: actions/checkout@v4

    - name: Set up Docker Buildx
      uses: docker/setup-buildx-action@v3

    - name: Login to Registry
      uses: docker/login-action@v3
      with:
        registry: ${{ env.REGISTRY }}
        username: ${{ github.actor }}
        password: ${{ secrets.GITHUB_TOKEN }}

    - name: Extract metadata
      id: meta
      uses: docker/metadata-action@v5
      with:
        images: ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}
        tags: |
          type=semver,pattern={{version}}
          type=sha,prefix=

    - name: Build and Push
      uses: docker/build-push-action@v5
      with:
        context: .
        push: ${{ github.event_name != 'pull_request' }}
        tags: ${{ steps.meta.outputs.tags }}
        labels: ${{ steps.meta.outputs.labels }}
        cache-from: type=gha
        cache-to: type=gha,mode=max
Pipeline completo com scanSeguro
# PIPELINE COMPLETO COM SEGURANÇA
# ════════════════════════════════════════

    # (continuação do job anterior)

    - name: Scan vulnerabilities
      uses: aquasecurity/trivy-action@master
      with:
        image-ref: ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:sha-${{ github.sha }}
        format: 'sarif'
        output: 'trivy-results.sarif'
        severity: 'CRITICAL,HIGH'

    - name: Upload scan results
      uses: github/codeql-action/upload-sarif@v3
      with:
        sarif_file: 'trivy-results.sarif'

    - name: Fail on critical CVEs
      uses: aquasecurity/trivy-action@master
      with:
        image-ref: ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:sha-${{ github.sha }}
        exit-code: '1'
        severity: 'CRITICAL'

  deploy:
    needs: build
    runs-on: ubuntu-latest
    if: github.ref == 'refs/heads/main'
    steps:
    - name: Deploy to production
      uses: appleboy/ssh-action@v1
      with:
        host: ${{ secrets.PROD_HOST }}
        username: deploy
        key: ${{ secrets.SSH_KEY }}
        script: |
          cd /app
          docker compose pull
          docker compose up -d --remove-orphans
          docker image prune -f

# RESULTADO DO PIPELINE:
# 1. Build com cache (rápido)
# 2. Push para registry
# 3. Scan de CVEs (falha se CRITICAL)
# 4. Deploy automático para prod
# 5. Limpeza de imagens antigas

Estratégias de Tagging

Como taguear imagens de forma que facilite deploys e rollbacks:

Estratégias de tag para imagensEstratégia
# ESTRATÉGIAS DE TAGGING
# ════════════════════════════════════════════════════════════════

# 1. SEMANTIC VERSIONING (recomendado para releases):
minha-app:1.5.2          # Versão exata
minha-app:1.5            # Latest patch da minor
minha-app:1              # Latest minor da major
minha-app:latest         # ⚠️ Apenas para dev

# 2. GIT SHA (recomendado para CI/CD):
minha-app:sha-abc1234    # Commit exato → rastreável
minha-app:main-abc1234   # Branch + commit

# 3. BUILD NUMBER:
minha-app:build-456      # Número do build no CI
minha-app:pipeline-789   # ID do pipeline

# 4. DATE-BASED:
minha-app:2024-01-15     # Data do build
minha-app:20240115-1     # Data + sequência

# ESTRATÉGIA RECOMENDADA PARA PRODUÇÃO:
# ──────────────────────────────────────
# Taguear com MÚLTIPLAS tags no mesmo build:
docker buildx build \
  -t minha-app:1.5.2 \
  -t minha-app:1.5 \
  -t minha-app:sha-$(git rev-parse --short HEAD) \
  -t minha-app:latest \
  --push .

# ROLLBACK:
# Sabe a versão anterior? → docker compose com tag antiga
# Não sabe? → Use o sha do commit anterior

# docker-compose.prod.yml:
services:
  api:
    image: ghcr.io/org/api:${APP_VERSION:-latest}
# Deploy: APP_VERSION=1.5.2 docker compose up -d
# Rollback: APP_VERSION=1.5.1 docker compose up -d
Swarm

Docker Swarm (Overview)

Docker Swarm é o orquestrador nativo do Docker. É significativamente mais simples que Kubernetes e ideal para equipes que precisam de HA e rolling updates sem a complexidade do K8s.

Conceitos Fundamentais do Swarm

Swarm — Arquitetura e conceitosConceitos
# DOCKER SWARM — CONCEITOS
# ════════════════════════════════════════
#
# ARQUITETURA:
# ┌────────────────────────────────────┐
# │         SWARM CLUSTER              │
# │                                    │
# │  ┌─────────┐  ┌─────────┐         │
# │  │ Manager │  │ Manager │ (Raft)   │
# │  │  (líder)│  │(follower)│         │
# │  └────┬────┘  └────┬────┘         │
# │       │             │              │
# │  ┌────┴────┐  ┌────┴────┐         │
# │  │ Worker  │  │ Worker  │         │
# │  │ node 1  │  │ node 2  │         │
# │  └─────────┘  └─────────┘         │
# └────────────────────────────────────┘
#
# CONCEITOS:
# • Node: máquina no cluster (manager/worker)
# • Service: definição do que rodar (imagem, replicas)
# • Task: instância de um container rodando
# • Stack: grupo de services (como compose)
# • Overlay network: rede entre hosts
#
# INICIALIZAR SWARM:
docker swarm init --advertise-addr 192.168.1.10
# → Gera token para workers entrarem

# ADICIONAR WORKER:
docker swarm join --token SWMTKN-1-xxx 192.168.1.10:2377

# VER NODES:
docker node ls
# ID   HOSTNAME   STATUS  AVAILABILITY  MANAGER
# *    manager1   Ready   Active        Leader
#      worker1    Ready   Active
#      worker2    Ready   Active
Services, Replicas e UpdatesOperação
# SERVICES NO SWARM
# ════════════════════════════════════════

# CRIAR SERVICE COM RÉPLICAS:
docker service create \
  --name api \
  --replicas 3 \
  --publish 80:3000 \
  --update-delay 10s \
  --update-parallelism 1 \
  --rollback-parallelism 1 \
  --rollback-monitor 30s \
  minha-api:1.0

# VER SERVICES:
docker service ls
# ID    NAME  REPLICAS  IMAGE
# abc   api   3/3       minha-api:1.0

# VER TASKS (containers):
docker service ps api
# Mostra em qual node cada réplica roda

# ROLLING UPDATE (zero downtime):
docker service update \
  --image minha-api:1.1 \
  api
# Atualiza 1 container por vez
# Espera 10s entre cada um
# Se falhar, faz rollback automático!

# ROLLBACK MANUAL:
docker service rollback api

# SCALE:
docker service scale api=5
# Agora são 5 réplicas distribuídas

# SECRETS NO SWARM:
echo "senha123" | docker secret create db_pass -
docker service update \
  --secret-add db_pass \
  api

# DEPLOY VIA STACK (compose file):
docker stack deploy -c docker-compose.yml myapp
docker stack services myapp
docker stack rm myapp
💡 Quando usar Swarm: Se você precisa de 2-5 servidores com HA, rolling updates e service discovery, Swarm é perfeito. A migração de Docker Compose para Swarm é trivial (mesmo arquivo YAML + seção deploy:). Se precisa de auto-scaling, políticas avançadas ou tem 50+ services, migre para Kubernetes.
Kubernetes

Preparação para Kubernetes

Kubernetes é o próximo passo depois do Docker. Entender como Docker se conecta ao K8s ajuda na transição e nas decisões arquiteturais que você toma agora.

Como Docker se Conecta ao Kubernetes

Docker → containerd → K8sArquitetura
# EVOLUÇÃO: DOCKER → KUBERNETES
# ════════════════════════════════════════
#
# ANTIGAMENTE (K8s < 1.24):
# K8s usava Docker como container runtime

#
# HOJE (K8s >= 1.24):
# K8s usa containerd DIRETAMENTE
# kubectl → kubelet → CRI → containerd
#
# O QUE MUDOU:
# • dockershim foi REMOVIDO do K8s
# • Docker NÃO é mais necessário nos nodes
# • containerd roda containers diretamente

# É a API padrão que K8s usa para:
# • Criar/deletar containers
# • Pull de imagens
# • Gerenciar lifecycle
#
# RUNTIMES COMPATÍVEIS COM CRI:
# • containerd (padrão, usado pelo Docker)
# • CRI-O (Red Hat/OpenShift)
# • gVisor (sandbox, mais seguro)
# • Kata Containers (micro-VMs)
#
# CONCLUSÃO:
# Tudo que você aprende com Docker
# (Dockerfile, images, compose patterns)
# se aplica diretamente em K8s!
# A diferença é COMO você faz o deploy

Performance

Performance em Produção

Containers em produção precisam de resource limits, storage drivers otimizados e logging controlado. Sem limites, um container com memory leak pode derrubar todo o host.

Resource Limits — CPU e Memória

SEMPRE defina limites de recursos em produção. Um container sem limites pode consumir TUDO do host:

Memory LimitsRAM
# MEMORY LIMITS
# ════════════════════════════════════════

# Docker run:
docker run -d \
  --memory=512m \
  --memory-swap=512m \
  --memory-reservation=256m \
  minha-app

# Docker Compose:
services:
  api:
    image: minha-api
    deploy:
      resources:
        limits:
          memory: 512M    # Máximo absoluto
        reservations:
          memory: 256M    # Garantido

# O QUE ACONTECE SEM LIMITE:
# Container com memory leak → consome toda RAM
# → Linux OOM Killer mata processos
# → Pode matar outros containers ou o Docker!

# O QUE ACONTECE COM LIMITE:
# Container excede 512M → OOM Kill APENAS dele
# → Docker reinicia (restart: unless-stopped)
# → Outros containers não são afetados

# MONITORAR USO:
docker stats --no-stream
# CONTAINER  CPU%  MEM USAGE/LIMIT  NET I/O
# api        5%    287MB/512MB       10MB/5MB

# DICAS:
# • memory-swap = memory → Sem swap (melhor perf)
# • reservation → Mínimo garantido pelo scheduler
# • Monitore por 1 semana antes de definir limites
# • Alertar quando > 80% do limite
CPU LimitsCPU
# CPU LIMITS
# ════════════════════════════════════════

# Docker run:
docker run -d \
  --cpus=1.5 \
  --cpu-shares=1024 \
  minha-app

# Docker Compose:
services:
  api:
    image: minha-api
    deploy:
      resources:
        limits:
          cpus: "1.5"     # Máximo 1.5 cores
        reservations:
          cpus: "0.5"     # Garantido 0.5 core

# ENTENDENDO OS PARÂMETROS:
#
# --cpus=1.5
# → Pode usar no máximo 1.5 CPU cores
# → Em host com 4 cores: usa até 37.5%
#
# --cpu-shares=1024 (relativo)
# → Peso relativo quando há competição
# → Default: 1024
# → 512 = metade da prioridade
# → 2048 = dobro da prioridade
# → SÓ importa quando CPU está 100%
#
# --cpuset-cpus="0,1"
# → Pina container nos cores 0 e 1
# → Útil para workloads NUMA-aware

# COMBINAÇÃO RECOMENDADA PARA PRODUÇÃO:
services:
  api:
    deploy:
      resources:
        limits:
          memory: 512M
          cpus: "1.0"
        reservations:
          memory: 256M
          cpus: "0.25"

# DICA: Defina SEMPRE memory limit.
# CPU limit é menos crítico (não mata o host),
# mas evita que um container monopolize CPU.

  "max-concurrent-uploads": 5
}

DR

Disaster Recovery

O que acontece quando seu servidor morre? Quando o disco corrompe? Quando alguém deleta o volume do banco? Um plano de disaster recovery garante que você pode recuperar rapidamente.

Backup Strategy para Containers

Backup de VolumesDados
# BACKUP DE VOLUMES DOCKER
# ════════════════════════════════════════

# MÉTODO 1: Container temporário com tar
docker run --rm \
  -v meu-volume:/source:ro \
  -v $(pwd)/backups:/backup \
  alpine tar czf /backup/vol-$(date +%Y%m%d).tar.gz \
  -C /source .

# MÉTODO 2: Backup de PostgreSQL (dump)
docker exec postgres \
  pg_dump -U app -d mydb \
  | gzip > backup-$(date +%Y%m%d).sql.gz

# MÉTODO 3: Backup com docker compose
# backup.sh:
#!/bin/bash
BACKUP_DIR="/backups/$(date +%Y%m%d)"
mkdir -p $BACKUP_DIR

# Parar app (consistência)
docker compose stop api

# Backup do volume de dados
docker run --rm \
  -v myapp_db-data:/source:ro \
  -v $BACKUP_DIR:/backup \
  alpine tar czf /backup/db-data.tar.gz \
  -C /source .

# Backup do compose file e configs
cp docker-compose.yml $BACKUP_DIR/
cp -r configs/ $BACKUP_DIR/
cp .env $BACKUP_DIR/

# Restart
docker compose start api

echo "Backup concluído: $BACKUP_DIR"

# CRON para backup diário:
# 0 3 * * * /app/backup.sh >> /var/log/backup.log 2>&1

Checklist

Checklist de Produção

Antes de colocar sua stack Docker em produção, valide cada item desta lista. São 15 verificações que cobrem segurança, performance, observabilidade e resiliência.

Top 15 Items Antes de Ir para Produção

1. Resource Limits

TODOS os containers têm memory e cpus limits definidos. Sem exceção. Um container sem limite pode derrubar o host inteiro.

2. Healthchecks

Cada service tem healthcheck configurado com interval, timeout, retries e start_period adequados ao tempo de startup.

3. Logging Rotation

Log driver configurado com max-size e max-file. Sem rotation = disco cheio em dias de alto tráfego.

4. Restart Policy

Todos os services usam restart: unless-stopped ou restart: always. Containers devem se recuperar automaticamente.

5. Non-Root

Nenhum container roda como root. USER definido no Dockerfile ou via user: no compose. Validado com whoami.

6. Imagens Pinadas

Todas as imagens usam tag exata ou digest SHA256. Zero uso de :latest em produção. Builds são reproduzíveis.

7. Secrets Protegidos

Nenhuma senha ou token em variáveis de ambiente visíveis. Use Docker Secrets, Vault, ou secrets manager da cloud.

8. Scan de CVEs

Pipeline falha em CVEs CRITICAL. Scan executado em cada build. Imagens base atualizadas regularmente (mensal).

9. Backup Automatizado

Volumes de dados (DB, uploads) com backup diário automatizado. Restore testado pelo menos trimestralmente.

10. Monitoramento

Métricas de CPU, RAM, disco e rede coletadas. Dashboards configurados. Alertas para thresholds críticos.

11. Logging Centralizado

Logs de todos os containers agregados em sistema central (Loki, ELK, CloudWatch). Pesquisáveis e com retenção definida.

12. Network Isolation

Services internos (DB, cache) em redes internal: true. Apenas reverse proxy com porta exposta ao público.

13. CI/CD Pipeline

Deploy automatizado via pipeline. Sem SSH manual para produção. Rollback documentado e testado.

14. TLS/HTTPS

Todo tráfego externo via HTTPS. Certificados automáticos (Let's Encrypt via Traefik/Certbot). HSTS habilitado.

15. Documentação (Runbook)

Runbook com: como fazer deploy, rollback, restore de backup, troubleshooting comum, contatos de emergência.

Validação Rápida — Script de Verificação

Script de validação pré-produçãoAutomação
# ════════════════════════════════════════════════════════════════
# SCRIPT: Verificação pré-produção
# Salvar como: scripts/pre-prod-check.sh
# ════════════════════════════════════════════════════════════════
#!/bin/bash
set -e

echo "🔍 Verificação Pré-Produção Docker"
echo "════════════════════════════════════"
PASS=0; FAIL=0

check() {
  if eval "$2" > /dev/null 2>&1; then
    echo "  ✅ $1"; ((PASS++))
  else
    echo "  ❌ $1"; ((FAIL++))
  fi
}

echo ""
echo "📦 Containers:"
check "Todos rodando" "[ $(docker compose ps --status running -q | wc -l) -eq $(docker compose ps -q | wc -l) ]"
check "Todos healthy" "! docker compose ps | grep -q 'unhealthy'"
check "Nenhum como root" "! docker compose exec -T api whoami | grep -q root"

echo ""
echo "🔒 Segurança:"
check "Sem :latest" "! grep -q ':latest' docker-compose.yml"
check "Sem senhas em ENV" "! grep -qi 'password=' docker-compose.yml"
check "Rede interna existe" "grep -q 'internal: true' docker-compose.yml"

echo ""
echo "📊 Recursos:"
check "Memory limits definidos" "grep -q 'memory:' docker-compose.yml"
check "Log rotation configurado" "grep -q 'max-size' docker-compose.yml"
check "Healthcheck definido" "grep -q 'healthcheck:' docker-compose.yml"

echo ""
echo "💾 Backup:"
check "Script de backup existe" "[ -f scripts/backup.sh ]"
check "Último backup < 24h" "find /backups -name '*.tar.gz' -mtime -1 | grep -q ."

echo ""
echo "════════════════════════════════════"
echo "Resultado: ✅ $PASS passed, ❌ $FAIL failed"
[ $FAIL -eq 0 ] && echo "🎉 Pronto para produção!" || echo "⚠️ Corrija os itens acima antes do deploy."
exit $FAIL

# ════════════════════════════════════════════════════════════════
# EXERCÍCIO 1: LOGGING CENTRALIZADO COM LOKI + GRAFANA
# ════════════════════════════════════════════════════════════════

# CENÁRIO: Você tem 3 services (api, worker, nginx) e precisa
# centralizar os logs para pesquisa e alertas.

# REQUISITOS:
# 1. Stack de aplicação: api + worker + nginx
#    - api: Express.js que loga em JSON para stdout
#    - worker: processo background com logs

#    - Loki armazena e indexa
#    - Grafana visualiza com dashboards
#
# 3. Todos os services com logging rotation:
#    - max-size: 10m
#    - max-file: 3
#
# 4. Labels nos containers para filtrar no Grafana:
#    - app=minha-app
#    - environment=production
#    - service=api|worker|nginx

# PASSOS:
# 1. Criar docker-compose.yml com app stack
# 2. Criar docker-compose.logging.yml com Loki stack
# 3. Criar promtail-config.yml
# 4. Subir tudo: docker compose -f docker-compose.yml -f docker-compose.logging.yml up -d

# 6. Adicionar Loki como data source (http://loki:3100)
# 7. Criar dashboard com logs de cada service

# VALIDAÇÃO:
# ✅ Grafana mostra logs dos 3 services
# ✅ Filtro por service funciona ({service="api"})
# ✅ Filtro por tempo funciona (last 1h, 6h, 24h)

Exercício 2: Pipeline CI/CD Completo

Objetivo: Criar um pipeline que builda, testa, escaneia e deploya automaticamente.

Exercício 2 — CI/CD PipelinePrática
# ════════════════════════════════════════════════════════════════
# EXERCÍCIO 2: PIPELINE CI/CD COM DOCKER
# ════════════════════════════════════════════════════════════════

# CENÁRIO: Configurar pipeline completo no GitHub Actions
# que builda, testa, escaneia e deploya automaticamente.

# REQUISITOS DO PIPELINE:
# 1. Trigger: push na branch main + tags v*
# 2. Job "test":
#    - Rodar testes com docker compose (compose de teste)
#    - docker compose -f docker-compose.test.yml up --exit-code-from tests
#
# 3. Job "build" (depende de test):
#    - Build com Docker Buildx (multi-platform amd64+arm64)
#    - Cache com GitHub Actions cache
#    - Tag com semver + sha
#    - Push para GitHub Container Registry (ghcr.io)
#
# 4. Job "scan" (depende de build):
#    - Trivy scan da imagem buildada
#    - Falhar em CRITICAL
#    - Upload SARIF para GitHub Security
#
# 5. Job "deploy" (depende de scan, apenas main):
#    - SSH para servidor de produção
#    - docker compose pull
#    - docker compose up -d
#    - Verificar healthcheck
#    - Notificar Slack (sucesso/falha)

# ARQUIVOS A CRIAR:
# .github/workflows/docker-ci.yml  ← Pipeline
# docker-compose.test.yml          ← Stack de teste
# docker-compose.prod.yml          ← Stack de produção
# Dockerfile                       ← Multi-stage build

# docker-compose.test.yml:
services:
  tests:
    build:
      context: .
      target: test    # Stage de teste no Dockerfile
    depends_on:
      db:
        condition: service_healthy
    environment:
      DATABASE_URL: postgresql://test:test@db:5432/testdb

  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: test
      POSTGRES_PASSWORD: test
      POSTGRES_DB: testdb
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U test"]
      interval: 5s
      timeout: 3s
      retries: 5

# VALIDAÇÃO:
# ✅ Push na main dispara pipeline automaticamente
# ✅ Testes rodam em containers isolados
# ✅ Build usa cache (2a execução mais rápida)
# ✅ Scan de CVEs bloqueia deploy se CRITICAL
# ✅ Deploy automático após scan passar
# ✅ Rollback funciona (mudar tag no compose + redeploy)

Exercício 3: Deploy com Rolling Update

Objetivo: Implementar deploy sem downtime usando Docker Swarm ou script customizado.

Exercício 3 — Rolling UpdatePrática
# ════════════════════════════════════════════════════════════════
# EXERCÍCIO 3: DEPLOY COM ROLLING UPDATE (ZERO DOWNTIME)
# ════════════════════════════════════════════════════════════════

# CENÁRIO: Deploy de nova versão sem que usuários percebam.
# Escolha uma das abordagens:

# ── OPÇÃO A: Docker Swarm Rolling Update ─────────────────────

# 1. Inicializar Swarm:
docker swarm init

# 2. Deploy da stack:
docker stack deploy -c docker-compose.yml myapp

# 3. docker-compose.yml com deploy config:
services:
  api:
    image: minha-api:1.0
    deploy:
      replicas: 3
      update_config:
        parallelism: 1        # 1 container por vez
        delay: 10s            # Espera 10s entre cada
        failure_action: rollback
        monitor: 30s          # Monitora 30s após update
        max_failure_ratio: 0.3
      rollback_config:
        parallelism: 1
        delay: 5s
    healthcheck:
      test: ["CMD", "wget", "-q", "--spider", "http://localhost:3000/health"]
      interval: 10s
      timeout: 5s
      retries: 3

# 4. Rolling update:
docker service update --image minha-api:1.1 myapp_api
# Observe: 1 réplica atualizada por vez, com 10s entre cada

# ── OPÇÃO B: Script de Rolling Update (sem Swarm) ────────────

# Para Docker Compose single-host:
# blue-green-deploy.sh:
#!/bin/bash
NEW_IMAGE=$1
SERVICE="api"
COMPOSE_FILE="docker-compose.yml"

echo "🚀 Deploying $NEW_IMAGE..."

# 1. Pull nova imagem
docker compose pull $SERVICE

# 2. Scale up (2 instâncias: old + new)
docker compose up -d --no-deps --scale $SERVICE=2 $SERVICE

# 3. Esperar novo container ficar healthy
echo "Aguardando healthcheck..."
sleep 30

# 4. Verificar se novo está healthy
if docker compose ps $SERVICE | grep -q "healthy"; then
  echo "✅ Novo container healthy"
  # 5. Scale down para 1 (remove o antigo)
  docker compose up -d --no-deps --scale $SERVICE=1 $SERVICE
  echo "🎉 Deploy concluído!"
else
  echo "❌ Novo container unhealthy - rollback!"
  docker compose up -d --no-deps --scale $SERVICE=1 $SERVICE
  exit 1
fi

# VALIDAÇÃO:
# ✅ Durante o deploy, o service continua respondendo
# ✅ curl em loop mostra 0 erros durante update
# ✅ Se novo container falha healthcheck, rollback automático
# ✅ Após deploy, apenas containers da versão nova estão rodando
# ✅ docker service ps (Swarm) mostra histórico de updates
