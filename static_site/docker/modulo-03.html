Fundamentos

O Problema da Persistência

Containers são efêmeros por natureza. Quando você remove um container, todos os dados armazenados dentro dele desaparecem para sempre. Entender esse comportamento é o primeiro passo para gerenciar dados corretamente.

Containers são Efêmeros — O que isso significa?

A filosofia do Docker é que containers devem ser descartáveis. Você pode parar, destruir e recriar um container a qualquer momento sem preocupação. Mas isso cria um problema crítico: onde ficam os dados?

Demonstração: dados perdidos ao remover containerPrática
# 1. Criar um container e gravar um arquivo dentro dele
docker run -d --name meu-app ubuntu:22.04 sleep 3600

# 2. Entrar no container e criar dados
docker exec meu-app bash -c "echo 'Dados importantes!' > /dados.txt"
docker exec meu-app cat /dados.txt
# Saída: Dados importantes!

# 3. Parar e remover o container
docker stop meu-app
docker rm meu-app

# 4. Recriar o container com o mesmo nome
docker run -d --name meu-app ubuntu:22.04 sleep 3600

# 5. Tentar ler o arquivo...
docker exec meu-app cat /dados.txt
# Saída: cat: /dados.txt: No such file or directory
# ❌ DADOS PERDIDOS PARA SEMPRE!

# 6. Limpar
docker stop meu-app && docker rm meu-app
⚠️ Isso não é um bug — é uma feature! Containers efêmeros permitem:
  • Deploys limpos: Cada deploy começa do zero, sem "lixo" acumulado
  • Escalabilidade: Criar e destruir instâncias rapidamente
  • Reprodutibilidade: Mesmo container, mesmo comportamento, sempre
  • Isolamento: Problemas em um container não contaminam outros
O desafio é: como manter dados persistentes em um mundo efêmero?

A Camada de Escrita do Container

Quando Docker cria um container a partir de uma imagem, ele adiciona uma camada de escrita (writable layer) no topo das camadas read-only da imagem. Todo dado criado ou modificado pelo container vai para essa camada.

Anatomia do filesystem de um containerDiagrama
┌─────────────────────────────────────────────────────────────────┐
│         CAMADA DE ESCRITA (Writable Layer) — EFÊMERA           │
│                                                                 │
│  • Todos os arquivos criados pelo container vão aqui            │
│  • Modificações em arquivos da imagem usam Copy-on-Write (CoW)  │
│  • REMOVIDA quando o container é removido (docker rm)           │
│  • Tamanho cresce conforme o container gera dados               │
│  • Específica deste container — não compartilhada               │
├─────────────────────────────────────────────────────────────────┤
│         CAMADAS DA IMAGEM (Read-Only Layers) — PERMANENTES      │
│                                                                 │
│  Layer 4: COPY app.py /app/           [código]                  │
│  Layer 3: RUN pip install flask       [dependências]            │
│  Layer 2: RUN apt-get install python  [runtime]                 │
│  Layer 1: FROM ubuntu:22.04           [SO base]                 │
│                                                                 │
│  • Compartilhadas entre TODOS os containers desta imagem        │
│  • Imutáveis — nunca são modificadas                            │
│  • Permanecem no disco até a imagem ser removida                │
└─────────────────────────────────────────────────────────────────┘

Quando container modifica um arquivo da imagem:
  1. Docker COPIA o arquivo para a camada de escrita (CoW)
  2. Modificação acontece na cópia
  3. Original na camada da imagem permanece intacto

Copy-on-Write (CoW) — Como funciona

O mecanismo Copy-on-Write é o que permite que múltiplos containers compartilhem as mesmas camadas de imagem com eficiência:

Leitura — sem cópiaEficiente
# Quando um container LÊ um arquivo:
# → Docker busca nas camadas de cima para baixo
# → Encontra na camada da imagem
# → Serve o arquivo diretamente (sem cópia)
# → Múltiplos containers leem o mesmo arquivo

# Exemplo: 10 containers nginx
# Todos leem /etc/nginx/nginx.conf
# da MESMA camada da imagem = economia de disco
Escrita — cópia necessáriaCoW
# Quando um container MODIFICA um arquivo:
# → Docker COPIA o arquivo para a writable layer
# → Modificação acontece na cópia
# → Próximas leituras veem a versão modificada
# → Outros containers não são afetados

# Exemplo:
docker exec container1 bash -c \
  "echo 'custom' > /etc/nginx/nginx.conf"
# Container1: vê versão modificada (da writable layer)
# Container2: vê versão original (da imagem)
💡 Impacto no desempenho: A primeira escrita em um arquivo grande tem overhead (precisa copiar). Por isso, para dados que mudam frequentemente (bancos de dados, logs, uploads), usamos volumes — que bypassa completamente o mecanismo CoW.

Armazenamento

Tipos de Armazenamento no Docker

Docker oferece três mecanismos para persistir dados fora da camada de escrita do container. Cada um tem características, vantagens e casos de uso distintos. Entender quando usar cada um é essencial.

Visão Geral dos Três Tipos

Docker oferece três formas de armazenar dados fora do ciclo de vida do container:

Volumes (Named Volumes)Recomendado

Gerenciados pelo Docker. Armazenados em um diretório especial do Docker no host (/var/lib/docker/volumes/). O Docker controla o ciclo de vida, permissões e localização.

# Criar e usar:
docker volume create meus-dados
docker run -v meus-dados:/app/data nginx

# Características:
✅ Gerenciado pelo Docker
✅ Portável entre hosts
✅ Funciona em Linux, Mac, Windows
✅ Suporta volume drivers (NFS, cloud)
✅ Backup fácil
✅ Pode ser compartilhado entre containers
Bind MountsDesenvolvimento

Mapeamento direto do host. Um diretório ou arquivo do host é montado diretamente dentro do container. Qualquer caminho do filesystem do host pode ser usado.

# Criar e usar:
docker run -v /home/user/projeto:/app nginx
docker run -v $(pwd):/app node:20

# Características:
✅ Acesso direto aos arquivos do host
✅ Ideal para desenvolvimento (hot-reload)
✅ Performance nativa no Linux
⚠️ Dependente da estrutura do host
⚠️ Problemas de permissão (uid/gid)
⚠️ Risco de segurança se mal configurado
tmpfs MountsMemória RAM

Armazenamento em memória. Dados existem apenas na RAM do host. Nunca são escritos em disco e desaparecem quando o container para.

# Criar e usar:
docker run --tmpfs /app/cache nginx
docker run --mount type=tmpfs,dst=/secrets nginx

# Características:
✅ Velocidade máxima (RAM)
✅ Dados sensíveis nunca vão ao disco
✅ Ideal para cache temporário
⚠️ Limitado pela RAM disponível
⚠️ Dados perdidos ao parar container
⚠️ Não pode ser compartilhado entre containers

Sintaxe: -v vs --mount

Docker oferece duas formas de montar armazenamento. A sintaxe --mount é mais explícita e recomendada para cenários complexos:

-v (--volume) — Sintaxe curtaClássica
# Volume nomeado:
docker run -v meu-vol:/app/data nginx

# Bind mount:
docker run -v /host/path:/container/path nginx
docker run -v $(pwd):/app nginx

# Read-only:
docker run -v meu-vol:/app/data:ro nginx

# Formato:
# -v [nome_ou_path_host]:[path_container]:[opções]

# ⚠️ Comportamento ambíguo:
# Se o path começa com / ou ./ → bind mount
# Se é apenas um nome → volume nomeado
docker run -v dados:/app/data   # ← Volume "dados"
docker run -v ./dados:/app/data # ← Bind mount ./dados
--mount — Sintaxe explícitaRecomendada
# Volume nomeado:
docker run --mount \
  type=volume,source=meu-vol,target=/app/data \
  nginx

# Bind mount:
docker run --mount \
  type=bind,source=/host/path,target=/container/path \
  nginx

# tmpfs:
docker run --mount \
  type=tmpfs,target=/app/cache,tmpfs-size=100m \
  nginx

# Read-only:
docker run --mount \
  type=volume,source=meu-vol,target=/app/data,readonly \
  nginx

# ✅ Vantagens do --mount:
# → Explícito sobre o tipo (volume, bind, tmpfs)
# → Erro claro se path não existe (bind mount)
# → Mais opções (tmpfs-size, volume-driver, etc.)
# → Recomendado pela documentação oficial
💡 Diferença importante: Com -v, se o path do host não existe em um bind mount, Docker cria o diretório automaticamente (pode causar bugs silenciosos). Com --mount type=bind, Docker retorna um erro se o path não existe — comportamento mais seguro.
Volumes

Volumes (Named Volumes) — Guia Completo

Volumes são o mecanismo preferido para persistir dados gerados e usados por containers Docker. São completamente gerenciados pelo Docker e funcionam consistentemente em qualquer plataforma.

Montando Volumes em Containers

A principal utilidade de volumes é montá-los dentro de containers para que os dados persistam além do ciclo de vida do container:

Montagem com -v e --mountPrática
# FORMA 1: -v (volume flag — sintaxe curta)
docker run -d \
  --name postgres-db \
  -v pgdata:/var/lib/postgresql/data \
  -e POSTGRES_PASSWORD=secret123 \
  postgres:16

# FORMA 2: --mount (sintaxe explícita — recomendada)
docker run -d \
  --name postgres-db \
  --mount type=volume,source=pgdata,target=/var/lib/postgresql/data \
  -e POSTGRES_PASSWORD=secret123 \
  postgres:16

# Volume read-only (container não pode escrever):
docker run -d \
  --name web \
  -v config-vol:/etc/nginx/conf.d:ro \
  nginx:1.25

# Ou com --mount:
docker run -d \
  --name web \
  --mount type=volume,source=config-vol,target=/etc/nginx/conf.d,readonly \
  nginx:1.25

# Volume criado automaticamente se não existir:
docker run -v novo-volume:/data nginx
# Docker cria "novo-volume" automaticamente na primeira vez

Demonstração: Volumes sobrevivem ao container

A prova definitiva de que volumes persistem dados mesmo após a remoção do container:

Dados persistem entre containersDemonstração
# 1. Criar um volume
docker volume create demo-persistencia

# 2. Criar container e gravar dados no volume
docker run --rm \
  -v demo-persistencia:/dados \
  ubuntu:22.04 \
  bash -c "echo 'Criado em: $(date)' > /dados/registro.txt && \
           echo 'Informação importante' >> /dados/registro.txt && \
           echo '--- Dados gravados! ---'"

# Saída: --- Dados gravados! ---
# Container foi removido automaticamente (--rm)

# 3. Verificar que o volume ainda existe:
docker volume ls | grep demo-persistencia
# local     demo-persistencia  ✓

# 4. Criar NOVO container e ler os dados do MESMO volume:
docker run --rm \
  -v demo-persistencia:/dados \
  alpine:3.19 \
  cat /dados/registro.txt

# Saída:
# Criado em: Mon Jan 15 10:30:00 UTC 2024
# Informação importante

# ✅ DADOS PERSISTIRAM! Mesmo usando imagem diferente (alpine vs ubuntu)!

# 5. Limpar:
docker volume rm demo-persistencia
⚡ Pontos-chave demonstrados:
  • O container foi removido (--rm), mas os dados permaneceram no volume
  • Um container completamente diferente (alpine) conseguiu ler os dados
  • O volume é independente do container — vive no host, gerenciado pelo Docker
  • Volumes não dependem da imagem — qualquer container pode montar qualquer volume

Compartilhando Volumes entre Containers

Volumes podem ser montados simultaneamente em múltiplos containers, permitindo compartilhamento de dados:

Múltiplos containers, mesmo volumeCompartilhamento
# Cenário: app que gera logs + container que processa logs

# 1. Criar volume compartilhado:
docker volume create logs-compartilhados

# 2. Container 1: Aplicação que gera logs
docker run -d \
  --name app-producer \
  -v logs-compartilhados:/var/log/app \
  alpine:3.19 \
  sh -c "while true; do echo \"[$(date)] Evento processado\" >> /var/log/app/events.log; sleep 2; done"

# 3. Container 2: Processador de logs (lê do mesmo volume)
docker run -d \
  --name log-processor \
  -v logs-compartilhados:/logs:ro \
  alpine:3.19 \
  sh -c "tail -f /logs/events.log"

# 4. Verificar que o processador recebe os logs:
docker logs log-processor
# [Mon Jan 15 10:30:00 UTC 2024] Evento processado
# [Mon Jan 15 10:30:02 UTC 2024] Evento processado
# ...

# 5. Container 3: Backup periódico (também lê o volume)
docker run --rm \
  -v logs-compartilhados:/source:ro \
  -v $(pwd):/backup \
  alpine:3.19 \
  tar czf /backup/logs-backup.tar.gz -C /source .

# ✅ Três containers acessando o mesmo volume!

# Limpar:
docker stop app-producer log-processor
docker rm app-producer log-processor
docker volume rm logs-compartilhados
💡 Cuidado com concorrência: Quando múltiplos containers escrevem no mesmo volume, podem ocorrer conflitos. Use :ro (read-only) para leitores, e garanta que apenas um container escreve, ou use mecanismos de lock no nível da aplicação.

Volume Drivers — Além do Armazenamento Local

Por padrão, volumes usam o driver local (filesystem do host). Mas volume drivers permitem armazenar dados em NFS, cloud storage, clusters distribuídos e mais:

Driver local com NFSRede

docker volume create \
  --driver local \
  --opt type=nfs \
  --opt o=addr=192.168.1.100,rw,nfsvers=4 \
  --opt device=:/export/shared \
  volume-nfs

# Usar como qualquer outro volume:
docker run -d \
  -v volume-nfs:/app/shared \
  nginx

# Cenário: cluster Docker Swarm
# Todos os nós acessam o mesmo NFS
# → Dados disponíveis em qualquer nó

Backup e Restore de Volumes

Volumes não têm backup automático. Você precisa implementar estratégias de backup usando containers auxiliares:

Backup de volumeImportante
# Estratégia: container temporário monta o volume
# e cria um arquivo tar

# Backup completo:
docker run --rm \
  -v pgdata:/source:ro \
  -v $(pwd)/backups:/backup \
  alpine:3.19 \
  tar czf /backup/pgdata-$(date +%Y%m%d-%H%M%S).tar.gz \
    -C /source .

# Resultado: ./backups/pgdata-20240115-103000.tar.gz

# Backup com compressão xz (menor):
docker run --rm \
  -v pgdata:/source:ro \
  -v $(pwd)/backups:/backup \
  alpine:3.19 \
  sh -c "tar cf - -C /source . | xz > /backup/pgdata.tar.xz"

# Listar conteúdo do backup:
tar -tzf backups/pgdata-20240115-103000.tar.gz | head
Restore de volumeRecuperação
# 1. Criar volume de destino (ou usar existente):
docker volume create pgdata-restored

# 2. Restaurar do backup:
docker run --rm \
  -v pgdata-restored:/target \
  -v $(pwd)/backups:/backup:ro \
  alpine:3.19 \
  sh -c "cd /target && tar xzf /backup/pgdata-20240115-103000.tar.gz"

# 3. Usar o volume restaurado:
docker run -d \
  --name postgres-recovered \
  -v pgdata-restored:/var/lib/postgresql/data \
  -e POSTGRES_PASSWORD=secret123 \
  postgres:16

# 4. Verificar que dados estão lá:
docker exec postgres-recovered \
  psql -U postgres -c "SELECT count(*) FROM users;"

# ✅ Dados recuperados com sucesso!

Bind Mounts

Bind Mounts — Mapeamento Direto do Host

Bind mounts permitem montar qualquer arquivo ou diretório do host diretamente dentro do container. São a ferramenta principal para ambientes de desenvolvimento, mas exigem cuidado em produção.

Como Bind Mounts Funcionam

Um bind mount cria um "espelho" — o container vê exatamente o mesmo conteúdo que está no path do host, em tempo real:

Bind mount básicoPrática
# Sintaxe com -v (path absoluto do host):
docker run -d \
  --name web-dev \
  -v /home/user/meu-site:/usr/share/nginx/html \
  -p 8080:80 \
  nginx:1.25

# Sintaxe com $(pwd) — diretório atual:
docker run -d \
  --name web-dev \
  -v $(pwd)/src:/usr/share/nginx/html \
  -p 8080:80 \
  nginx:1.25

# Sintaxe com --mount (mais explícita):
docker run -d \
  --name web-dev \
  --mount type=bind,source=$(pwd)/src,target=/usr/share/nginx/html \
  -p 8080:80 \
  nginx:1.25

# ⚠️ DIFERENÇA IMPORTANTE com -v:
# Se $(pwd)/src NÃO EXISTE:
#   -v      → Docker CRIA o diretório (vazio) silenciosamente
#   --mount → Docker retorna ERRO (mais seguro!)

# Montar arquivo individual (não só diretório):
docker run -d \
  -v $(pwd)/nginx.conf:/etc/nginx/nginx.conf:ro \
  nginx:1.25

Permissões e Problemas de UID/GID

Um dos maiores problemas com bind mounts é a diferença de permissões entre host e container. O processo dentro do container pode rodar como um usuário diferente do seu usuário no host:

O problema de permissõesTroubleshooting
# Cenário problemático:
# Seu usuário no host: uid=1000, gid=1000
# Processo no container: uid=0 (root) ou uid=999 (postgres)

# Container cria arquivo como root:
docker run --rm -v $(pwd)/data:/data alpine:3.19 touch /data/arquivo.txt
ls -la data/arquivo.txt
# -rw-r--r-- 1 root root 0 Jan 15 10:30 data/arquivo.txt
# ❌ Você (uid=1000) pode ter problemas para editar!

# SOLUÇÃO 1: Rodar container com seu UID:
docker run --rm \
  -v $(pwd)/data:/data \
  --user $(id -u):$(id -g) \
  alpine:3.19 \
  touch /data/arquivo.txt

ls -la data/arquivo.txt
# -rw-r--r-- 1 user user 0 Jan 15 10:30 data/arquivo.txt ✅

# SOLUÇÃO 2: No Dockerfile, criar usuário com mesmo UID:
# Dockerfile:
# FROM node:20
# RUN groupadd -g 1000 appgroup && \
#     useradd -u 1000 -g appgroup -m appuser
# USER appuser

# SOLUÇÃO 3: fixuid (ferramenta para ajuste automático):
# Ajusta UID/GID no entrypoint do container

# SOLUÇÃO 4: Permissões adequadas no host:
chmod 777 data/   # ⚠️ Não ideal para produção
chmod g+w data/ && chgrp docker data/  # Melhor
💡 Em Docker Desktop (Mac/Windows): O problema de UID/GID é menos frequente porque Docker Desktop faz tradução automática de permissões entre o host e a VM Linux. Em Linux nativo, é o cenário mais comum de frustração com bind mounts.

Read-Only Bind Mounts

Quando o container só precisa LER dados do host (configs, certificados, etc.), monte como read-only para segurança:

Montagem read-onlySegurança
# Com -v (adicionar :ro no final):
docker run -d \
  -v $(pwd)/nginx.conf:/etc/nginx/nginx.conf:ro \
  -v $(pwd)/certs:/etc/ssl/certs:ro \
  nginx:1.25

# Com --mount (readonly flag):
docker run -d \
  --mount type=bind,source=$(pwd)/config,target=/app/config,readonly \
  minha-app:latest

# Container tenta escrever:
docker exec container1 touch /etc/nginx/nginx.conf
# touch: /etc/nginx/nginx.conf: Read-only file system
# ✅ Proteção funcionando!

# Cenários para read-only:
# → Arquivos de configuração
# → Certificados TLS/SSL
# → Chaves públicas
# → Dados de referência que não mudam
# → Código-fonte em containers de teste
Filesystem inteiro read-onlyHardening
# Container com TODO o filesystem read-only:
docker run -d \
  --read-only \
  --name secure-app \
  -v app-logs:/var/log \
  --tmpfs /tmp \
  --tmpfs /run \
  minha-app:latest

# --read-only: ninguém escreve na writable layer
# -v app-logs:/var/log: logs vão para volume (persiste)
# --tmpfs /tmp: diretório temporário em RAM
# --tmpfs /run: PID files em RAM

# ✅ Benefícios:
# → Atacante não pode modificar binários
# → Não pode instalar malware
# → Não pode alterar configurações
# → Container é verdadeiramente imutável

# ⚠️ Pode quebrar apps que escrevem em paths inesperados
# Teste bem antes de aplicar!

Segurança: Cuidado com o que você monta

Bind mounts podem ser um risco de segurança significativo se mal configurados. O container ganha acesso direto ao filesystem do host:

Riscos de segurança⚠️ Atenção
# ❌ NUNCA faça isso — acesso total ao host:
docker run -v /:/host ubuntu bash
# Container pode ler/escrever QUALQUER arquivo do host!
# Incluindo /etc/shadow, /etc/passwd, SSH keys...

# ❌ Montar Docker socket — equivale a acesso root no host:
docker run -v /var/run/docker.sock:/var/run/docker.sock docker
# Container pode criar outros containers, acessar volumes, etc.
# Use APENAS para ferramentas de CI/CD e monitoramento confiáveis

# ❌ Montar diretórios sensíveis:
docker run -v /etc:/etc ubuntu          # Configurações do sistema
docker run -v ~/.ssh:/root/.ssh ubuntu  # Chaves SSH
docker run -v /root:/root ubuntu        # Home do root

# ✅ BOAS PRÁTICAS:
# → Monte apenas o diretório mínimo necessário
# → Use :ro sempre que possível
# → Nunca monte / (raiz) ou /etc
# → Em produção, prefira volumes nomeados
# → Use --read-only no container quando possível
# → Audite bind mounts em docker-compose.yml de terceiros
⚠️ Regra de segurança: Trate bind mounts como você trata sudo — use apenas quando necessário, com o mínimo de permissão possível, e sempre questione por que o acesso é necessário.

tmpfs

tmpfs Mounts — Armazenamento em Memória

tmpfs mounts armazenam dados exclusivamente na memória RAM do host. Os dados nunca são escritos em disco e desaparecem completamente quando o container para. Ideal para dados sensíveis e cache de alta performance.

Como tmpfs Funciona

Um tmpfs mount cria um filesystem em memória dentro do container. É o tipo de armazenamento mais rápido (RAM) e mais volátil (sem persistência):

--tmpfs (sintaxe simples)Rápido
# Montar tmpfs em /app/cache:
docker run -d \
  --name fast-cache \
  --tmpfs /app/cache \
  nginx:1.25

# Com opções (tamanho e permissões):
docker run -d \
  --name secure-app \
  --tmpfs /tmp:rw,noexec,nosuid,size=100m \
  minha-app:latest

# Opções disponíveis:
# rw/ro      → leitura+escrita ou somente leitura
# noexec     → não permite execução de binários
# nosuid     → ignora bit SUID
# size=XXm   → limite de tamanho em MB
# mode=1777  → permissões do diretório

# Verificar que é tmpfs:
docker exec fast-cache df -h /app/cache
# Filesystem  Size  Used  Avail  Use%  Mounted on
# tmpfs       64M   0     64M    0%    /app/cache
--mount type=tmpfsExplícito
# Sintaxe --mount (mais opções):
docker run -d \
  --name secure-app \
  --mount type=tmpfs,target=/app/secrets,tmpfs-size=50m,tmpfs-mode=0700 \
  minha-app:latest

# Múltiplos tmpfs no mesmo container:
docker run -d \
  --name multi-tmpfs \
  --mount type=tmpfs,target=/tmp,tmpfs-size=200m \
  --mount type=tmpfs,target=/run,tmpfs-size=10m \
  --mount type=tmpfs,target=/app/cache,tmpfs-size=500m \
  minha-app:latest

# tmpfs-size: limite em bytes (aceita sufixos k, m, g)
# tmpfs-mode: permissões Unix (octal)

# Sem limite de tamanho (usa toda RAM disponível):
docker run -d \
  --mount type=tmpfs,target=/cache \
  minha-app:latest
# ⚠️ Cuidado: pode consumir toda a RAM!

Limitações do tmpfs

O que você precisa saberLimitações
# Limitações do tmpfs:

1. NÃO PERSISTE — dados perdidos ao parar container
   docker stop meu-container  → dados tmpfs = GONE

2. NÃO COMPARTILHÁVEL — apenas um container pode usar
   # Cada container tem seu próprio tmpfs independente
   # Diferente de volumes, não pode ser montado em múltiplos containers

3. CONSOME RAM do host
   # Se tmpfs-size=2g e container usa 2g, são 2g a MENOS de RAM para o host
   # OOM Killer pode matar processos se RAM acabar

4. APENAS LINUX
   # Em Docker Desktop (Mac/Windows), tmpfs funciona na VM Linux
   # Não no host real — mas o efeito prático é o mesmo

5. NÃO APARECE em 'docker volume ls'
   # tmpfs não é um "volume" — é um mount especial
   # Não tem backup, não tem inspect

# Verificar uso de tmpfs em um container:
docker inspect --format='{{.HostConfig.Tmpfs}}' meu-container
# ou
docker inspect meu-container | grep -A5 "Tmpfs"

Persistência para Bancos de Dados

Bancos de dados em containers são o caso de uso mais crítico para volumes. Sem persistência adequada, você perde todos os dados ao reiniciar. Veja como configurar corretamente os bancos mais populares.

docker stop postgres-prod && docker rm postgres-prod

Backup

Estratégias de Backup

Volumes persistem dados, mas NÃO são backup. Se o disco falha, o volume vai junto. Implementar uma estratégia de backup robusta é essencial para dados críticos em produção.

Backup de Volume com Container Auxiliar

A técnica mais comum e confiável: usar um container temporário que monta o volume e cria um arquivo compactado:

Padrão de backup com container auxiliarRecomendado
# BACKUP GENÉRICO DE QUALQUER VOLUME:

# Sintaxe geral:
docker run --rm \
  -v NOME_DO_VOLUME:/source:ro \
  -v /caminho/backups:/backup \
  alpine:3.19 \
  tar czf /backup/NOME-$(date +%Y%m%d-%H%M%S).tar.gz -C /source .

# Exemplo real — backup do PostgreSQL:
docker run --rm \
  -v pgdata:/source:ro \
  -v /opt/backups/postgres:/backup \
  alpine:3.19 \
  tar czf /backup/pgdata-$(date +%Y%m%d-%H%M%S).tar.gz -C /source .

# Exemplo — backup do MongoDB:
docker run --rm \
  -v mongo-data:/source:ro \
  -v /opt/backups/mongo:/backup \
  alpine:3.19 \
  tar czf /backup/mongo-$(date +%Y%m%d-%H%M%S).tar.gz -C /source .

# Exemplo — backup com compressão xz (menor, mais lento):
docker run --rm \
  -v pgdata:/source:ro \
  -v /opt/backups:/backup \
  alpine:3.19 \
  sh -c "apk add --no-cache xz && tar cf - -C /source . | xz -9 > /backup/pgdata-$(date +%Y%m%d).tar.xz"

# IMPORTANTE: Para bancos de dados em produção, prefira
# ferramentas nativas (pg_dump, mysqldump, mongodump)
# ao invés de backup raw dos arquivos do volume!

Backup Nativo de Bancos de Dados

Para bancos de dados, o backup dos dados em formato nativo é mais seguro e portável do que copiar os arquivos brutos do volume:

  pg_dump -U app_user -d minha_aplicacao \

Backup Automatizado com Cron + Container

Em produção, backups devem ser automáticos. Combine cron jobs com containers para criar backups periódicos:

Cron no hostAutomação
# Script de backup: /opt/scripts/backup-postgres.sh
#!/bin/bash
set -e

BACKUP_DIR="/opt/backups/postgres"
TIMESTAMP=$(date +%Y%m%d-%H%M%S)
RETENTION_DAYS=7

# Criar diretório se não existe
mkdir -p ${BACKUP_DIR}

# Backup via pg_dump
docker exec postgres-prod \
  pg_dump -U app_user -d minha_aplicacao \
  --format=custom \
  > ${BACKUP_DIR}/backup-${TIMESTAMP}.dump

# Comprimir
gzip ${BACKUP_DIR}/backup-${TIMESTAMP}.dump

# Limpar backups antigos
find ${BACKUP_DIR} -name "*.dump.gz" \
  -mtime +${RETENTION_DAYS} -delete

echo "[$(date)] Backup concluído: backup-${TIMESTAMP}.dump.gz"

# Adicionar ao crontab:
# crontab -e
# 0 2 * * * /opt/scripts/backup-postgres.sh >> /var/log/backup.log 2>&1
# (Executa todo dia às 2h da manhã)
Container de backup dedicadoElegante
# Dockerfile para container de backup:
# FROM alpine:3.19
# RUN apk add --no-cache postgresql16-client gzip
# COPY backup.sh /usr/local/bin/backup.sh
# RUN chmod +x /usr/local/bin/backup.sh
# ENTRYPOINT ["crond", "-f", "-l", "2"]

# Ou usar imagem pronta com cron:
docker run -d \
  --name backup-scheduler \
  --network backend-net \
  -v backups:/backups \
  -e PGHOST=postgres-prod \
  -e PGUSER=app_user \
  -e PGPASSWORD=senha_segura_123 \
  -e PGDATABASE=minha_aplicacao \
  alpine:3.19 \
  sh -c '
    apk add --no-cache postgresql16-client gzip &&
    echo "0 */6 * * * pg_dump -Fc > /backups/pg-\$(date +\%Y\%m\%d-\%H\%M).dump" \
      | crontab - &&
    crond -f -l 2
  '

# Resultado: backup a cada 6 horas automaticamente

# Verificar cron está funcionando:
docker exec backup-scheduler crontab -l
docker exec backup-scheduler ls -la /backups/
⚠️ Lembre-se: Backup não é backup até que você tenha testado o restore! Agende testes periódicos de restauração para garantir que seus backups são válidos. Um backup corrompido ou incompleto é pior que nenhum backup (dá falsa segurança).
Boas Práticas

Boas Práticas de Mercado

Após entender os mecanismos de persistência, veja as práticas adotadas por empresas e equipes maduras para gerenciar dados em containers de forma segura, organizada e escalável.

Regra #1: Nunca armazene dados importantes na camada de escrita

A camada de escrita do container é efêmera por design. Qualquer dado ali será perdido ao remover o container:

Onde dados devem e não devem ficarFundamental
# ❌ ERRADO — dados na writable layer:
docker run -d --name postgres postgres:16
# Dados em /var/lib/postgresql/data → writable layer
# docker rm postgres → DADOS PERDIDOS!

# ❌ ERRADO — logs importantes sem volume:
docker run -d --name app minha-app:latest
# Logs em /var/log/app → writable layer
# docker rm app → LOGS PERDIDOS!

# ❌ ERRADO — uploads de usuário sem volume:
docker run -d --name web minha-web:latest
# Uploads em /app/uploads → writable layer
# docker rm web → UPLOADS PERDIDOS!

# ✅ CORRETO — tudo com volume:
docker run -d \
  --name postgres \
  -v pgdata:/var/lib/postgresql/data \
  postgres:16

docker run -d \
  --name app \
  -v app-logs:/var/log/app \
  -v app-uploads:/app/uploads \
  minha-app:latest

# REGRA: Se o dado importa → Volume
# Camada de escrita é apenas para dados temporários descartáveis

Regra #2: Volumes nomeados em produção (não bind mounts)

Por que volumes > bind mounts em prodProdução
# Volumes nomeados são melhores para produção:

✅ 1. Portabilidade
   Volume funciona igual em Linux, Mac, Windows
   Bind mount depende de paths específicos do host

✅ 2. Gerenciamento pelo Docker
   docker volume ls/inspect/rm/prune
   Bind mount: gerenciamento manual

✅ 3. Performance consistente
   Volumes têm performance nativa em qualquer OS
   Bind mounts são lentos no Mac/Windows

✅ 4. Segurança
   Volumes ficam em /var/lib/docker/volumes/
   Bind mounts expõem paths arbitrários do host

✅ 5. Volume drivers
   Volumes suportam NFS, cloud storage, etc.
   Bind mounts: apenas filesystem local

✅ 6. Sem problemas de permissão
   Docker gerencia permissões internamente
   Bind mounts: conflitos de uid/gid frequentes
Quando bind mounts são aceitáveisExceções
# Bind mounts são OK para:

💻 1. Desenvolvimento local
   -v $(pwd)/src:/app/src  (hot-reload)

📄 2. Arquivos de configuração read-only
   -v ./nginx.conf:/etc/nginx/nginx.conf:ro
   -v ./prometheus.yml:/etc/prometheus/prometheus.yml:ro

🔐 3. Certificados/secrets do host
   -v /etc/letsencrypt:/certs:ro

📊 4. Diretórios de log do host (centralização)
   -v /var/log/containers:/var/log/app

🔧 5. Docker socket (ferramentas de CI/CD)
   -v /var/run/docker.sock:/var/run/docker.sock
   ⚠️ Com muita cautela!

# Padrão recomendado em produção:
# DADOS → Volume nomeado
# CONFIG → Bind mount read-only (ou ConfigMap no K8s)
# SECRETS → Docker secrets (ou Vault)

Regra #3: Separar dados de aplicação de configuração

Não misture dados persistentes com arquivos de configuração no mesmo volume. Separe por responsabilidade:

Separação de responsabilidadesOrganização
# ❌ RUIM — tudo junto:
docker run -d \
  -v app-tudo:/app \
  minha-app:latest
# Mistura: código + config + dados + logs no mesmo volume

# ✅ BOM — separado por responsabilidade:
docker run -d \
  --name minha-app \
  -v app-data:/app/data \
  -v app-uploads:/app/uploads \
  -v app-logs:/var/log/app \
  -v $(pwd)/config/app.yml:/app/config/app.yml:ro \
  --tmpfs /tmp \
  minha-app:latest

# Estrutura clara:
# /app/data/     → Volume: dados persistentes da aplicação
# /app/uploads/  → Volume: arquivos enviados por usuários
# /var/log/app/  → Volume: logs (pode ser rotacionado)
# /app/config/   → Bind mount RO: configuração (versionada no git)
# /tmp/          → tmpfs: temporários (rápido, não persiste)

# Benefícios:
# → Backup seletivo (apenas volumes de dados)
# → Config versionada no git (não no volume)
# → Logs podem ter política de retenção diferente
# → Temporários nunca ocupam disco

#!/bin/bash
THRESHOLD_GB=10
for vol in $(docker volume ls -q); do
  SIZE=$(sudo du -s /var/lib/docker/volumes/${vol}/_data/ 2>/dev/null | awk '{print $1}')
  SIZE_GB=$((SIZE / 1048576))
  if [ ${SIZE_GB} -gt ${THRESHOLD_GB} ]; then
    echo "⚠️ ALERTA: Volume '${vol}' tem ${SIZE_GB}GB (limite: ${THRESHOLD_GB}GB)"
  fi
done

#    - Monta o MESMO volume em /dados (read-only)

Exercício 3: Backup e Restore de um Volume

Objetivo: Praticar o workflow completo de backup e restore usando container auxiliar.

DesafioExercício 3
# TAREFAS:
# 1. Crie um volume "dados-importantes" com alguns arquivos
# 2. Faça backup do volume para um arquivo .tar.gz no host
# 3. Remova o volume original (simular desastre)
# 4. Crie um novo volume "dados-restaurados"
# 5. Restaure o backup no novo volume
# 6. Verifique que os dados estão intactos
# 7. Limpe tudo
SoluçãoResposta
# 1. Criar volume e popular com dados:
docker volume create dados-importantes

docker run --rm \
  -v dados-importantes:/data \
  alpine:3.19 \
  sh -c '
    mkdir -p /data/documentos /data/imagens
    echo "Relatório financeiro Q4 2024" > /data/documentos/relatorio.txt
    echo "Lista de clientes VIP" > /data/documentos/clientes.txt
    echo "PNG_FAKE_DATA_LOGO" > /data/imagens/logo.png
    echo "Configuração do sistema" > /data/config.yml
    echo "=== Conteúdo criado ==="
    find /data -type f
  '

# 2. Fazer BACKUP:
mkdir -p ./backups

docker run --rm \
  -v dados-importantes:/source:ro \
  -v $(pwd)/backups:/backup \
  alpine:3.19 \
  tar czf /backup/dados-importantes-backup.tar.gz -C /source .

echo "Backup criado: $(ls -lh ./backups/dados-importantes-backup.tar.gz)"

# 3. SIMULAR DESASTRE — remover volume original:
docker volume rm dados-importantes
echo "Volume original REMOVIDO! 💥"

# 4. Criar novo volume para restore:
docker volume create dados-restaurados

# 5. RESTAURAR backup:
docker run --rm \
  -v dados-restaurados:/target \
  -v $(pwd)/backups:/backup:ro \
  alpine:3.19 \
  sh -c "cd /target && tar xzf /backup/dados-importantes-backup.tar.gz"

echo "Restore concluído!"

# 6. Verificar dados restaurados:
docker run --rm \
  -v dados-restaurados:/data:ro \
  alpine:3.19 \
  sh -c '
    echo "=== Arquivos restaurados ==="
    find /data -type f
    echo ""
    echo "=== Conteúdo dos documentos ==="
    cat /data/documentos/relatorio.txt
    cat /data/documentos/clientes.txt
    cat /data/config.yml
  '
# ✅ Todos os arquivos e conteúdos restaurados!

# 7. Limpar:
docker volume rm dados-restaurados
rm -rf ./backups/dados-importantes-backup.tar.gz

Exercício 4: Development Setup com Bind Mount (Hot-Reload)

Objetivo: Configurar um ambiente de desenvolvimento com hot-reload usando bind mounts — a experiência mais comum do dia a dia.

DesafioExercício 4
# TAREFAS:
# 1. Crie uma pasta "meu-site" com um arquivo index.html básico
# 2. Inicie um container Nginx com bind mount dessa pasta
# 3. Acesse http://localhost:8080 e veja o site
# 4. Edite o index.html NO HOST (sem tocar no container)
# 5. Atualize o browser — a mudança deve aparecer INSTANTANEAMENTE
# 6. Demonstre que isso funciona para hot-reload
# 7. Limpe tudo
SoluçãoResposta
# 1. Criar estrutura do projeto:
mkdir -p meu-site

cat > meu-site/index.html <<'EOF'
<!DOCTYPE html>
<html>
<head>
  <title>Meu Site Docker</title>
  <style>
    body { font-family: Arial; text-align: center; padding: 50px; background: #1a1a2e; color: #eee; }
    h1 { color: #00d4aa; }
  </style>
</head>
<body>
  <h1>Versão 1.0</h1>
  <p>Este site está rodando em um container Docker!</p>
  <p>Edite este arquivo no host e atualize o browser.</p>
</body>
</html>
EOF

# 2. Iniciar Nginx com bind mount:
docker run -d \
  --name web-hotreload \
  -v $(pwd)/meu-site:/usr/share/nginx/html:ro \
  -p 8080:80 \
  nginx:1.25-alpine

# 3. Testar:
echo "Acesse: http://localhost:8080"
curl -s http://localhost:8080 | grep "h1"
# <h1>Versão 1.0</h1>

# 4. Editar NO HOST (simular desenvolvimento):
sed -i 's/Versão 1.0/Versão 2.0 - Hot Reload!/g' meu-site/index.html
# Ou abra no VS Code e edite manualmente

# 5. Verificar mudança INSTANTÂNEA (sem reiniciar container!):
curl -s http://localhost:8080 | grep "h1"
# <h1>Versão 2.0 - Hot Reload!</h1>
# ✅ Mudança refletida instantaneamente!

# O container NÃO foi reiniciado — Nginx serve o arquivo
# diretamente do bind mount, que é o mesmo arquivo do host!

# 6. Mais uma edição para provar:
echo '<p style="color:yellow">Adicionado em tempo real!</p>' >> meu-site/index.html
curl -s http://localhost:8080 | grep "tempo real"
# <p style="color:yellow">Adicionado em tempo real!</p> ✅

# 7. Limpar:
docker stop web-hotreload && docker rm web-hotreload
rm -rf meu-site

# 💡 Este é o padrão para desenvolvimento com Docker:
# Edite no host → Container reflete → Browser atualiza
# Funciona para: React, Vue, Angular, Flask, Django, Express, etc.
