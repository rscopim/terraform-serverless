Fundamentos

Networking no Docker — Visão Geral

Containers precisam se comunicar — com outros containers, com o host e com o mundo externo. O Docker implementa um modelo de networking robusto e flexível que permite isolar, conectar e publicar serviços de forma controlada.

Por que Containers Precisam de Rede?

Em aplicações modernas, um único container raramente opera sozinho. Uma aplicação típica envolve múltiplos serviços que precisam se comunicar:

🔑 Princípio fundamental: O Docker permite que você controle exatamente QUEM pode falar com QUEM. Containers na mesma rede se comunicam livremente; containers em redes diferentes são isolados por padrão. Isso é segurança por design.

Container Network Model (CNM)

O Docker implementa o Container Network Model (CNM) — uma especificação que define como networking funciona para containers. O CNM tem três componentes fundamentais:

Network SandboxIsolamento
# NETWORK SANDBOX
# ═══════════════════════════════════
# É o ambiente de rede ISOLADO de cada container.
# Contém:
#   • Interface(s) de rede virtual (veth)
#   • Tabela de rotas própria
#   • Configuração DNS própria (/etc/resolv.conf)
#   • Regras de firewall (iptables)
#
# Implementado via Linux Network Namespaces
#
# Analogia: cada container tem seu próprio
# "computador virtual" com placa de rede,
# tabela de rotas e DNS independentes.
#
# Verificar namespace de rede:
docker exec meu-container cat /etc/resolv.conf
docker exec meu-container ip addr
docker exec meu-container ip route
EndpointConexão
# ENDPOINT
# ═══════════════════════════════════
# É a "porta de entrada" que conecta um
# container (Sandbox) a uma rede (Network).
#
# Implementado como um par de interfaces
# virtuais (veth pair):
#   • Uma ponta dentro do container (eth0)
#   • Outra ponta na bridge do host (vethXXX)
#
# Um container pode ter MÚLTIPLOS endpoints
# (conectado a várias redes simultaneamente)
#
# Analogia: o cabo de rede que liga o
# computador ao switch. Cada cabo é um endpoint.
#
# Ver endpoints de um container:
docker inspect --format \
  '{{json .NetworkSettings.Networks}}' \
  meu-container | jq
NetworkInfraestrutura
# NETWORK
# ═══════════════════════════════════════════════════════════════
# É a infraestrutura de conectividade que agrupa endpoints.
# Containers no mesmo Network podem se comunicar diretamente.
#
# Implementada como:
#   • Bridge virtual (Linux bridge) para redes bridge
#   • Overlay network (VXLAN) para redes multi-host
#   • Conexão direta ao host para rede host
#
# Características:
#   • Tem seu próprio subnet (ex: 172.18.0.0/16)
#   • Pode ter servidor DNS embutido
#   • Isola tráfego de outras networks
#   • Pode ter políticas de acesso
#
# Analogia: o switch/VLAN que conecta múltiplos computadores.
# Quem está no mesmo switch pode se comunicar.
# Quem está em switches diferentes não pode (sem roteamento).
#
# Listar networks:
docker network ls

Networks Padrão do Docker

Quando você instala o Docker, três redes são criadas automaticamente:

# → Todo container sem --network especificado entra aqui
# → Subnet padrão: 172.17.0.0/16

# → Containers se comunicam por IP (NÃO por nome!)

# → Container usa a rede do host diretamente
# → Sem isolamento de rede
# → Sem port mapping (porta do container = porta do host)

# NONE:
# → Container sem qualquer interface de rede
# → Totalmente isolado
# → Apenas interface loopback (lo)
💡 Importante: A rede bridge padrão (docker0) tem uma limitação séria: containers NÃO conseguem se encontrar pelo nome. Para DNS automático, você precisa criar uma rede bridge customizada. Veremos isso em detalhes na Seção 3.
Drivers

Tipos de Rede (Network Drivers)

O Docker suporta múltiplos drivers de rede, cada um projetado para cenários específicos. Escolher o driver correto é fundamental para performance, segurança e funcionalidade da sua aplicação.

Bridge — Rede Privada Interna (Padrão)

O driver bridge cria uma rede privada interna no host. Containers conectados à mesma bridge podem se comunicar entre si. É o driver padrão e o mais utilizado para containers em um único host.

Bridge — Como funcionaPadrão
# DRIVER: bridge
# ═══════════════════════════════════
#
# COMO FUNCIONA:
# 1. Docker cria uma Linux bridge (switch virtual)
# 2. Cada container recebe um veth pair:
#    - Uma ponta no container (eth0)
#    - Outra ponta na bridge (vethXXXXX)
# 3. Bridge faz switching L2 entre containers
# 4. NAT/masquerade permite acesso à internet
#
# CARACTERÍSTICAS:
# ✅ Isolamento de rede por padrão
# ✅ DNS automático (user-defined bridges)
# ✅ Port mapping para acesso externo (-p)
# ✅ Múltiplas bridges = segmentação
# ✅ Funciona em qualquer OS
#
# LIMITAÇÕES:
# ⚠️ Apenas containers no MESMO host
# ⚠️ Bridge padrão não tem DNS por nome
# ⚠️ Performance ligeiramente menor que host

# Criar container na bridge padrão:
docker run -d --name web nginx

# Criar em bridge customizada:
docker network create minha-rede
docker run -d --name web --network minha-rede nginx

Host — Compartilha Rede do Host

O driver host remove completamente o isolamento de rede entre o container e o host. O container usa diretamente a stack de rede do host (mesmos interfaces, IPs, portas).

Host — Como funcionaPerformance
# DRIVER: host
# ═══════════════════════════════════
#
# COMO FUNCIONA:
# 1. Container NÃO recebe namespace de rede próprio
# 2. Container usa diretamente as interfaces do host
# 3. Sem NAT, sem bridge, sem overhead
# 4. Porta do container = porta do host
#
# CARACTERÍSTICAS:
# ✅ Performance máxima de rede
# ✅ Sem overhead de NAT/bridge
# ✅ Latência mínima
# ✅ Ideal para network-intensive apps
#
# LIMITAÇÕES:
# ⚠️ SEM isolamento de rede
# ⚠️ Conflito de portas com host/outros containers
# ⚠️ Port mapping (-p) NÃO funciona (ignorado)
# ⚠️ Funciona APENAS em Linux (Mac/Win usa VM)
# ⚠️ Menor segurança

# Usar rede host:
docker run -d --network host nginx
# Nginx escuta na porta 80 do HOST diretamente

# Verificar: container vê interfaces do host
docker run --network host --rm alpine ip addr
# Mostra eth0, wlan0, etc. do HOST
Host — Quando usarCasos de uso
# QUANDO USAR host:
#
# 1. Load Balancers de alta performance
#    → HAProxy, Nginx como LB, Traefik
#    → Evita double-NAT
#
# 2. Aplicações que precisam ver tráfego raw
#    → Network monitoring (Wireshark, tcpdump)
#    → IDS/IPS (Snort, Suricata)
#
# 3. Serviços que usam muitas portas dinâmicas
#    → FTP (portas passivas)
#    → SIP/VoIP
#
# 4. Performance crítica (microsegundos importam)
#    → Trading systems
#    → Gaming servers
#
# QUANDO NÃO USAR:
# ✗ Aplicações web normais (use bridge)
# ✗ Quando precisa rodar múltiplas instâncias
# ✗ Quando segurança é prioridade
# ✗ Em Mac/Windows (não funciona como esperado)

# Exemplo: Prometheus + Node Exporter
docker run -d --network host \
  --name node-exporter \
  prom/node-exporter

None — Sem Rede

O driver none desabilita toda a conectividade de rede do container. O container fica completamente isolado — não pode enviar nem receber pacotes (exceto loopback).

None — Container sem redeIsolamento
# DRIVER: none
# ═══════════════════════════════════
#
# COMO FUNCIONA:
# 1. Container recebe namespace de rede VAZIO
# 2. Apenas interface loopback (lo, 127.0.0.1)
# 3. Sem conectividade com host ou outros containers
# 4. Sem acesso à internet
#
# CARACTERÍSTICAS:
# ✅ Isolamento total de rede
# ✅ Segurança máxima
# ✅ Nenhuma superfície de ataque de rede
#
# CASOS DE USO:
# • Processamento batch (não precisa de rede)
# • Geração de relatórios/PDFs
# • Criptografia/assinatura de documentos
# • Testes que devem ser offline
# • Containers com dados sensíveis

# Usar rede none:
docker run --network none --rm alpine ip addr
# 1: lo:   ← Apenas loopback!
#     inet 127.0.0.1/8

# Sem acesso externo:
docker run --network none --rm alpine ping 8.8.8.8
# ping: sendto: Network unreachable
None — Exemplo práticoSegurança
# Cenário: processar dados sensíveis sem risco de vazamento
#
# Arquivo no host é montado via volume,
# processado SEM REDE, resultado salvo no volume.

# 1. Container sem rede processando dados sensíveis:
docker run --network none \
  -v dados-entrada:/input:ro \
  -v dados-saida:/output \
  minha-app-processamento

# O container:
# ✅ Lê dados do volume /input
# ✅ Processa (criptografa, gera relatório, etc.)
# ✅ Salva resultado em /output
# ❌ NÃO PODE enviar dados para fora (sem rede!)

# 2. Geração de PDF isolada:
docker run --network none \
  -v ./relatorios:/data \
  weasyprint \
  /data/template.html /data/output.pdf

# 3. Compilação segura (build sandbox):
docker run --network none \
  -v ./src:/src:ro \
  -v ./build:/output \
  gcc:latest \
  gcc /src/main.c -o /output/app

Overlay — Multi-Host (Swarm/Kubernetes)

O driver overlay permite comunicação entre containers em hosts diferentes. Cria uma rede virtual (VXLAN) que encapsula pacotes entre os nós de um cluster.

Overlay — Rede multi-hostCluster
# DRIVER: overlay
# ═══════════════════════════════════
#
# COMO FUNCIONA:
# 1. Usa VXLAN para encapsular tráfego L2 sobre L3
# 2. Containers em hosts diferentes parecem estar
#    na mesma rede local
# 3. Requer Docker Swarm ou orquestrador
# 4. Controle plane distribuído (gossip protocol)
#
# CARACTERÍSTICAS:
# ✅ Comunicação multi-host transparente
# ✅ Criptografia opcional (--opt encrypted)
# ✅ Service discovery integrado
# ✅ Load balancing (routing mesh)
#
# LIMITAÇÕES:
# ⚠️ Requer Swarm mode ou orquestrador
# ⚠️ Overhead de encapsulamento VXLAN
# ⚠️ Mais complexo de troubleshootar
# ⚠️ Latência maior que bridge local

# Requer Swarm inicializado:
docker swarm init

# Criar overlay network:
docker network create \
  --driver overlay \
  --subnet 10.0.0.0/24 \
  --opt encrypted \
  rede-overlay

# Deploy de serviço na overlay:
docker service create \
  --name api --network rede-overlay \
  --replicas 3 minha-api:latest

Macvlan — IP Real na Rede Física

O driver macvlan atribui um endereço MAC real e um IP da rede física do host ao container. O container aparece como um dispositivo físico na rede local.

Macvlan — IP na rede físicaAvançado
# DRIVER: macvlan
# ═══════════════════════════════════
#
# COMO FUNCIONA:
# 1. Container recebe MAC address próprio
# 2. Container recebe IP da rede LAN do host
# 3. Aparece como dispositivo físico na rede
# 4. Switch físico "vê" o container diretamente
#
# CARACTERÍSTICAS:
# ✅ Container com IP "real" na LAN
# ✅ Sem NAT — comunicação direta
# ✅ Performance muito alta
# ✅ Ideal para migração de apps legadas
#
# LIMITAÇÕES:
# ⚠️ Requer modo promíscuo na interface
# ⚠️ Limite de MACs por porta no switch
# ⚠️ Container ↔ Host NÃO se comunicam (!)
# ⚠️ Não funciona em clouds (AWS, Azure)
# ⚠️ Configuração de rede mais complexa

# Criar rede macvlan:
docker network create -d macvlan \
  --subnet=192.168.1.0/24 \
  --gateway=192.168.1.1 \
  -o parent=eth0 \
  rede-macvlan

# Container com IP da LAN:
docker run -d --network rede-macvlan \
  --ip 192.168.1.200 \
  --name servidor-legado nginx

# Agora na LAN: ping 192.168.1.200 → responde!
Macvlan — Quando usarCasos de uso
# QUANDO USAR macvlan:
#
# 1. Migração de apps legadas
#    → App espera IP fixo na LAN
#    → Não pode usar NAT/port mapping
#    → Ex: sistemas ERP, impressoras de rede
#
# 2. Aplicações que precisam de IP real
#    → Serviços DHCP (precisa estar na LAN)
#    → DNS autoritativo para a LAN
#    → Servidores NFS/SMB
#
# 3. Integração com infraestrutura existente
#    → Container precisa ser "visto" na LAN
#    → Firewalls baseados em IP da LAN
#    → VLANs existentes
#
# MODOS:
# • bridge (padrão): containers na mesma VLAN
# • 802.1q trunk: containers em VLANs diferentes

# Macvlan com VLAN tagging:
docker network create -d macvlan \
  --subnet=10.10.10.0/24 \
  --gateway=10.10.10.1 \
  -o parent=eth0.100 \
  rede-vlan100

# parent=eth0.100 → VLAN 100 no eth0

Bridge

Bridge Network — Guia Completo

A rede bridge é o driver mais utilizado no Docker. Entender a diferença entre a bridge padrão e bridges customizadas é crucial para configurar comunicação correta entre containers com DNS automático e isolamento adequado.

Bridge Padrão (docker0) vs User-Defined Bridge

Docker oferece duas categorias de bridge network. A diferença entre elas é enorme em termos de funcionalidade:

Bridge Padrão (docker0)Limitada
# BRIDGE PADRÃO (docker0)
# ═══════════════════════════════════
# É a rede "bridge" que existe por padrão.
# Todo container sem --network usa esta rede.

# Características:
# ❌ SEM DNS automático por nome
# ❌ Todos os containers juntos (sem isolamento)
# ❌ Precisa usar --link (deprecado) ou IP fixo
# ❌ Não pode desconectar container em runtime
# ⚠️ Compartilhada por TODOS os containers

# Demonstração — DNS NÃO funciona:
docker run -d --name app1 alpine sleep 3600
docker run -d --name app2 alpine sleep 3600

# Tentar comunicar por nome:
docker exec app1 ping app2
# ping: bad address 'app2'  ← ❌ NÃO RESOLVE!

docker inspect -f '{{.NetworkSettings.IPAddress}}' app2

docker exec app1 ping 172.17.0.3
# PING 172.17.0.3: 64 bytes ← ✅ funciona

docker stop app2 && docker rm app2

docker stop app1 app2 && docker rm app1 app2
User-Defined BridgeRecomendada
# USER-DEFINED BRIDGE (Customizada)
# ═══════════════════════════════════
# Rede criada por você com docker network create.
# SEMPRE use esta em vez da padrão!

# Características:
# ✅ DNS automático por nome de container
# ✅ Isolamento (só containers da rede se veem)
# ✅ Conectar/desconectar em runtime
# ✅ Configuração customizável (subnet, gateway)
# ✅ Melhor isolamento entre projetos

# Demonstração — DNS FUNCIONA:
docker network create minha-rede

docker run -d --name app1 --network minha-rede \
  alpine sleep 3600
docker run -d --name app2 --network minha-rede \

# PING app2 (172.18.0.3): 64 bytes ← ✅ FUNCIONA!

docker exec app2 ping app1
# PING app1 (172.18.0.2): 64 bytes ← ✅ FUNCIONA!

# DNS resolve automaticamente!

Criando Redes Customizadas — docker network create

O comando docker network create permite criar redes com controle total sobre a configuração:

Criação básica e com opçõesCriar
# Criação simples (Docker escolhe subnet):
docker network create app-network
# Docker atribui subnet automaticamente
# (172.18.0.0/16, 172.19.0.0/16, etc.)

# Criação com subnet específico:
docker network create \
  --subnet 10.0.1.0/24 \
  --gateway 10.0.1.1 \
  backend-network

# Criação com range de IPs:
docker network create \
  --subnet 10.0.2.0/24 \
  --ip-range 10.0.2.128/25 \
  --gateway 10.0.2.1 \
  frontend-network
# Containers recebem IPs entre 10.0.2.128 e 10.0.2.255

# Com labels para organização:
docker network create \
  --label projeto=ecommerce \
  --label ambiente=production \
  --label team=backend \
  ecommerce-internal

# Com opções avançadas do driver:
docker network create \
  --driver bridge \
  --opt com.docker.network.bridge.name=br-custom \
  --opt com.docker.network.bridge.enable_icc=true \
  --opt com.docker.network.bridge.enable_ip_masquerade=true \
  custom-bridge
Opções avançadas de configuraçãoAvançado
# Rede interna (sem acesso à internet):
docker network create \
  --internal \
  --subnet 10.0.99.0/24 \

# Containers nesta rede NÃO acessam internet
# Ideal para bancos de dados

# Verificar:
docker run --rm --network rede-interna alpine \
  ping -c 1 8.8.8.8
# ping: sendto: Network unreachable ← sem internet

# Rede com IPv6:
docker network create \
  --ipv6 \
  --subnet 172.20.0.0/16 \
  --subnet 2001:db8::/64 \
  rede-dualstack

# Rede com MTU customizado:
docker network create \
  --opt com.docker.network.driver.mtu=9000 \
  rede-jumbo-frames

# Desabilitar ICC (Inter-Container Communication):
docker network create \

# Apenas via port mapping publicado

# enable_icc: comunicação entre containers (true/false)

DNS Interno — Containers se Encontram pelo Nome

O DNS embutido do Docker é um dos recursos mais poderosos das redes customizadas. Ele permite que containers se descubram automaticamente pelo nome, sem precisar conhecer IPs:

Como o DNS interno funcionaDNS
# O Docker roda um servidor DNS embutido em 127.0.0.11
# Ele resolve automaticamente:
#   • Nome do container → IP do container
#   • Network aliases → IP do container
#   • Service names (em Swarm) → IPs dos containers

# Verificar DNS resolver no container:
docker run --rm --network app-net alpine cat /etc/resolv.conf
# nameserver 127.0.0.11    ← DNS embutido do Docker
# ndots:0

# RESOLUÇÃO POR NOME DE CONTAINER:
docker network create demo-net

docker run -d --name webserver --network demo-net nginx
docker run -d --name appserver --network demo-net alpine sleep 3600

docker exec appserver nslookup webserver
# Server:    127.0.0.11
# Address:   127.0.0.11:53
#
# Non-authoritative answer:
# Name: webserver
# Address: 172.20.0.2

docker exec appserver ping -c 2 webserver
# PING webserver (172.20.0.2): 56 data bytes
# 64 bytes from 172.20.0.2: seq=0 ttl=64 time=0.123 ms

# RESOLUÇÃO POR ALIAS:
docker run -d --name postgres-master \
  --network demo-net \
  --network-alias db \
  --network-alias postgres \
  postgres:16

# Qualquer um destes nomes funciona:
docker exec appserver ping postgres-master  # ✅ nome do container
docker exec appserver ping db               # ✅ alias
docker exec appserver ping postgres         # ✅ alias

# MÚLTIPLOS CONTAINERS COM MESMO ALIAS (round-robin DNS):
docker run -d --name api-1 --network demo-net --network-alias api alpine sleep 3600
docker run -d --name api-2 --network demo-net --network-alias api alpine sleep 3600
docker run -d --name api-3 --network demo-net --network-alias api alpine sleep 3600

# DNS retorna múltiplos IPs (load balancing básico):
docker exec appserver nslookup api
# Name: api  Address: 172.20.0.5
# Name: api  Address: 172.20.0.6
# Name: api  Address: 172.20.0.7

# Limpar:
docker stop webserver appserver postgres-master api-1 api-2 api-3
docker rm webserver appserver postgres-master api-1 api-2 api-3
docker network rm demo-net
💡 Dica profissional: Use nomes descritivos para containers e aliases para que o DNS reflita a arquitetura. Ex: --name postgres-primary --network-alias db. Assim, sua aplicação conecta em db:5432 e você pode trocar o banco sem alterar o código.

Comunicação

Comunicação entre Containers

Conectar containers entre si é uma das tarefas mais comuns no Docker. Vamos explorar os métodos disponíveis, entender por que --link é deprecado e dominar o padrão correto com user-defined bridges e DNS automático.

--link (Deprecado — NÃO USAR)

O --link foi a primeira solução do Docker para comunicação entre containers. Está deprecado desde Docker 1.9 e não deve ser usado em nenhum cenário novo:

--link — Por que NÃO usar❌ Deprecado
# ❌ NÃO FAÇA ISSO (código legado):
docker run -d --name db postgres:16
docker run -d --name app --link db:database myapp

# O --link fazia:
# 1. Adicionava entrada no /etc/hosts do container
# 2. Injetava variáveis de ambiente com dados do linked
# 3. Permitia comunicação na bridge padrão

# PROBLEMAS do --link:
# ❌ Só funciona na bridge padrão
# ❌ Unidirecional (app→db, mas db não vê app)
# ❌ Variáveis de ambiente expostas (inseguro)
# ❌ Não funciona entre hosts (não escala)
# ❌ Não dinâmico (precisa recriar para mudar)
# ❌ Será REMOVIDO em versões futuras do Docker
# ❌ Não funciona com Docker Compose v3+

# Se você vir --link em tutoriais/projetos:
# → É um sinal de que o tutorial está DESATUALIZADO
# → Substitua por user-defined bridge network
Migração: --link → network✅ Correto
# ═══════════════════════════════════
# ANTES (deprecado):
# ═══════════════════════════════════
docker run -d --name db postgres:16
docker run -d --name app \
  --link db:database myapp
# app conecta em "database:5432"

# ═══════════════════════════════════
# DEPOIS (correto):
# ═══════════════════════════════════
docker network create app-net

docker run -d --name db \
  --network app-net \
  --network-alias database \
  postgres:16

docker run -d --name app \
  --network app-net \
  myapp
# app conecta em "database:5432" ← MESMO código!
# OU conecta em "db:5432" (nome do container)

# VANTAGENS da migração:
# ✅ Bidirecional (app↔db)
# ✅ DNS automático
# ✅ Isolamento por rede
# ✅ Conectar/desconectar em runtime
# ✅ Funciona com Compose, Swarm, etc.
# ✅ Múltiplos aliases

User-Defined Bridge com DNS — Método Correto

O padrão recomendado para comunicação entre containers é criar uma rede bridge customizada. O DNS automático resolve nomes de containers para seus IPs dinamicamente:

Padrão correto: App + Banco na mesma redeBest Practice
# ═══════════════════════════════════════════════════════════════
# CENÁRIO: Aplicação Node.js + PostgreSQL + Redis
# ═══════════════════════════════════════════════════════════════

# 1. Criar a rede para o projeto:
docker network create --subnet 172.25.0.0/16 projeto-ecommerce

# 2. Iniciar o PostgreSQL:
docker run -d \
  --name postgres \
  --network projeto-ecommerce \
  --network-alias db \
  -e POSTGRES_USER=app \
  -e POSTGRES_PASSWORD=secret123 \
  -e POSTGRES_DB=ecommerce \
  -v pgdata:/var/lib/postgresql/data \
  postgres:16

# 3. Iniciar o Redis:
docker run -d \
  --name redis \
  --network projeto-ecommerce \
  --network-alias cache \
  -v redisdata:/data \
  redis:7-alpine redis-server --appendonly yes

# 4. Iniciar a aplicação Node.js:
docker run -d \
  --name api \
  --network projeto-ecommerce \
  -e DATABASE_URL=postgresql://app:secret123@db:5432/ecommerce \
  -e REDIS_URL=redis://cache:6379 \
  -p 3000:3000 \
  minha-api:latest

# ═══════════════════════════════════════════════════════════════
# COMUNICAÇÃO (tudo via DNS):
#
# api → db:5432     (PostgreSQL) ← alias do container postgres
# api → cache:6379  (Redis)      ← alias do container redis
# api → postgres:5432            ← nome do container (também funciona)
# api → redis:6379               ← nome do container (também funciona)
#
# Externo → api:3000             ← port mapping para acesso do usuário
# Externo → db:5432              ← ❌ NÃO exposto (sem -p)! SEGURO!
# Externo → redis:6379           ← ❌ NÃO exposto (sem -p)! SEGURO!
# ═══════════════════════════════════════════════════════════════

# 5. Verificar comunicação:
docker exec api ping -c 1 db       # ✅ resolve para IP do postgres
docker exec api ping -c 1 cache    # ✅ resolve para IP do redis
docker exec api ping -c 1 redis    # ✅ resolve (nome do container)

# 6. Verificar DNS:
docker exec api nslookup db
# Name: db  Address: 172.25.0.2

docker exec api nslookup cache
# Name: cache  Address: 172.25.0.3

Uma das grandes vantagens das user-defined bridges é poder conectar e desconectar containers de redes sem parar ou recriar o container:

Port Mapping (Publicação de Portas)

Por padrão, containers não são acessíveis de fora do host. Para expor serviços para o mundo externo (ou para o host), é necessário mapear portas do container para portas do host. Isso é o "port mapping" ou "port publishing".

Conceito: Por que Port Mapping é Necessário?

Container isolado vs Container publicadoConceito
═══════════════════════════════════════════════════════════════════════
SEM PORT MAPPING (padrão):
═══════════════════════════════════════════════════════════════════════

  Usuário (browser)                    Container (Nginx :80)
       │                                     │
       └──── http://localhost:80 ────────── ❌ Connection refused
                                              │
  O container escuta na porta 80,             │
  mas na interface INTERNA da bridge.         │
  O host NÃO roteia tráfego para lá.         │

═══════════════════════════════════════════════════════════════════════
COM PORT MAPPING (-p 8080:80):
═══════════════════════════════════════════════════════════════════════

  Usuário (browser)          iptables/NAT          Container (Nginx :80)
       │                         │                       │
       └── http://localhost:8080 ──▶ DNAT ──▶ 172.17.0.2:80
                                 │                       │
  Docker cria regra iptables:    │                       │

   host vai para porta 80       │                       │

docker run -d -p 8080:80 nginx
# Acesso: http://localhost:8080

docker run -d -p 80:80 nginx
# Acesso: http://localhost:80

docker run -d \
  -p 80:80 \

docker run -d -p 3000:80 nginx

docker run -d -p 8081:80 --name site1 nginx
docker run -d -p 8082:80 --name site2 nginx
docker run -d -p 8083:80 --name site3 nginx

# site2: http://localhost:8082
# site3: http://localhost:8083

# 8080/tcp -> 0.0.0.0:32772

# ⚠️ IMPORTANTE:
# EXPOSE no Dockerfile é apenas DOCUMENTAÇÃO!
# Não publica a porta automaticamente no run.
# Você precisa de -p ou -P para publicar.
#
# EXPOSE 80 → informa que o app usa porta 80
# -p 8080:80 → realmente publica a porta
# -P → publica todas as EXPOSE com portas aleatórias

# Quando usar -P:
# • Desenvolvimento rápido
# • Quando não importa qual porta do host
# • Testes automatizados

Bind em Interface Específica

Por padrão, -p faz bind em todas as interfaces (0.0.0.0), tornando o container acessível de qualquer IP do host. Você pode restringir a uma interface específica para maior segurança:

Bind por interfaceSegurança
# PADRÃO: bind em todas as interfaces (0.0.0.0)
docker run -d -p 8080:80 nginx
# Equivalente a:
docker run -d -p 0.0.0.0:8080:80 nginx
# Acessível de: localhost, LAN, internet (se exposto)

# ═══════════════════════════════════
# RESTRITO: apenas localhost (loopback)
# ═══════════════════════════════════
docker run -d -p 127.0.0.1:8080:80 nginx
# Acessível APENAS de: localhost
# NÃO acessível da LAN ou internet!

# QUANDO USAR 127.0.0.1:
# • Serviços que só devem ser acessados localmente
# • Bancos de dados em desenvolvimento
# • Admin panels, dashboards internos
# • Reverse proxy é o ponto de entrada público

# Exemplo: DB acessível só localmente:
docker run -d \
  -p 127.0.0.1:5432:5432 \
  postgres:16
# Só apps no mesmo host acessam o DB

# ═══════════════════════════════════
# RESTRITO: interface específica
# ═══════════════════════════════════
docker run -d -p 192.168.1.100:8080:80 nginx
# Acessível APENAS via IP 192.168.1.100
# Útil em servidores com múltiplas interfaces
IPv6 e ranges de portasAvançado
# ═══════════════════════════════════
# IPv6:
# ═══════════════════════════════════
docker run -d -p [::1]:8080:80 nginx
# Bind em localhost IPv6

docker run -d -p [::]:8080:80 nginx
# Bind em todas interfaces IPv6

# ═══════════════════════════════════
# Range de portas:
# ═══════════════════════════════════
docker run -d -p 8080-8083:80-83 nginx
# Mapeia:
#   host:8080 → container:80
#   host:8081 → container:81
#   host:8082 → container:82
#   host:8083 → container:83

# ═══════════════════════════════════
# Combinações comuns:
# ═══════════════════════════════════

# Web público + admin privado:
docker run -d \
  -p 80:80 \
  -p 127.0.0.1:9090:9090 \
  my-app
# Porta 80: acessível de qualquer lugar
# Porta 9090: apenas localhost (admin)

# Múltiplas interfaces:
docker run -d \
  -p 192.168.1.100:80:80 \
  -p 10.0.0.1:80:80 \
  nginx
# Acessível nas duas redes internas
# Mas NÃO na interface pública

TCP vs UDP

Por padrão, port mapping usa TCP. Para serviços que usam UDP (DNS, jogos, streaming), você precisa especificar explicitamente:

Especificando protocolo TCP/UDPProtocolo
# PADRÃO: TCP (não precisa especificar)
docker run -d -p 8080:80 nginx           # TCP implícito
docker run -d -p 8080:80/tcp nginx       # TCP explícito (mesmo resultado)

# UDP: precisa especificar
docker run -d -p 53:53/udp bind9         # DNS (UDP)
docker run -d -p 514:514/udp syslog      # Syslog (UDP)

# TCP + UDP na mesma porta:
docker run -d \
  -p 53:53/tcp \
  -p 53:53/udp \
  bind9
# DNS usa ambos os protocolos

# Cenários comuns com UDP:
# • DNS: porta 53 (TCP + UDP)
# • DHCP: porta 67-68 (UDP)
# • SNMP: porta 161-162 (UDP)
# • Syslog: porta 514 (UDP)
# • Gaming servers: portas variáveis (UDP)
# • VoIP/SIP: porta 5060 (UDP)
# • QUIC/HTTP3: porta 443 (UDP)

# Exemplo: servidor de jogo
docker run -d \
  -p 27015:27015/tcp \
  -p 27015:27015/udp \
  -p 27020:27020/udp \
  gameserver

# Verificar protocolo nas portas:
docker port meu-container
# 53/tcp -> 0.0.0.0:53
# 53/udp -> 0.0.0.0:53
# 80/tcp -> 0.0.0.0:8080
⚠️ Segurança com port mapping: Quando você publica uma porta com -p, Docker adiciona regras no iptables que bypassam o firewall do host (UFW, firewalld). Mesmo que UFW bloqueie a porta, Docker a expõe! Para evitar isso, sempre use 127.0.0.1:PORT:PORT para serviços internos, ou configure DOCKER_IPTABLES=false e gerencie manualmente.
Avançado

Host Network e None Network — Detalhado

Além do bridge, os drivers host e none atendem cenários específicos onde performance máxima ou isolamento total são necessários. Vamos explorar cada um em profundidade com casos de uso reais.

Host Network — Container usa Rede do Host Diretamente

Com --network host, o container não recebe namespace de rede próprio. Ele compartilha diretamente a stack de rede do host — mesmas interfaces, mesmos IPs, mesmas portas:

Host network — ComportamentoSem NAT
# Container com rede host:
docker run -d --network host --name web nginx

# Nginx escuta diretamente na porta 80 do HOST:
curl http://localhost:80
# ✅ Funciona! Sem port mapping.

# -p É IGNORADO com host network:
docker run -d --network host -p 9090:80 nginx
# WARNING: Published ports are discarded when
# using host network mode
# Nginx ainda escuta na :80 do host

# Container vê interfaces do host:
docker run --rm --network host alpine ip addr
# 1: lo: 
# 2: eth0:  ... inet 192.168.1.100/24
# 3: wlan0:  ... inet 192.168.1.101/24
# (mesmas interfaces que "ip addr" no host!)

# Container vê as mesmas portas:
docker run --rm --network host alpine netstat -tlnp
# (mostra TODAS as portas abertas do host)

# ⚠️ CONFLITO DE PORTAS:
docker run -d --network host --name web1 nginx
docker run -d --network host --name web2 nginx
# ❌ web2 falha: porta 80 já em uso!
# (Nginx do web1 já ocupa porta 80 do host)
Host network — PerformanceBenchmark
# ═══════════════════════════════════
# BENCHMARK: Bridge vs Host
# ═══════════════════════════════════

# Bridge (com NAT):
# Pacote: Container → veth → bridge → iptables → eth0
# Overhead: ~5-10% latência adicional
# Throughput: ~95% da rede nativa

# Host (sem NAT):
# Pacote: Container → eth0 (direto!)
# Overhead: ~0% (nativo)
# Throughput: ~100% da rede nativa

# ═══════════════════════════════════
# QUANDO USAR HOST NETWORK:
# ═══════════════════════════════════

# 1. Load Balancers (Nginx, HAProxy, Traefik):
docker run -d --network host \
  --name traefik \
  traefik:v2.10 \
  --entryPoints.web.address=:80 \
  --entryPoints.websecure.address=:443

# 2. Monitoring que precisa ver tráfego do host:
docker run -d --network host \
  --name prometheus \
  prom/prometheus

# 3. Service Mesh sidecars:
docker run -d --network host \
  --name envoy-proxy \
  envoyproxy/envoy

# 4. Network tools:
docker run -it --rm --network host \
  nicolaka/netshoot \
  tcpdump -i eth0 port 80
💡 Nota sobre Mac/Windows: Em macOS e Windows, Docker roda dentro de uma VM Linux. --network host conecta o container à rede da VM, não do Mac/Windows. Portanto, host networking funciona de forma diferente (e menos útil) fora do Linux.

None Network — Container Totalmente Isolado

Com --network none, o container recebe um namespace de rede vazio. Apenas a interface loopback (127.0.0.1) existe. Nenhuma comunicação externa é possível:

None network — Isolamento totalSegurança
# Container completamente sem rede:
docker run --rm --network none alpine ip addr
# 1: lo: 
#     inet 127.0.0.1/8
# NADA MAIS! Sem eth0, sem conectividade.

# Sem acesso à internet:
docker run --rm --network none alpine \
  wget -T 3 http://google.com
# wget: bad address 'google.com'

# Sem acesso a outros containers:
docker run --rm --network none alpine \
  ping -c 1 172.17.0.2
# PING 172.17.0.2: sendto: Network unreachable

# Apenas loopback funciona:
docker run --rm --network none alpine \
  ping -c 1 127.0.0.1
# 64 bytes from 127.0.0.1: seq=0 ttl=64 ✅

# ═══════════════════════════════════
# COMO TROCAR DADOS SEM REDE?
# ═══════════════════════════════════
# Use VOLUMES! Dados entram/saem via filesystem:
docker run --network none \
  -v ./input:/data/input:ro \
  -v ./output:/data/output \
  my-secure-processor

# Dados em ./input → processados → resultado em ./output
# Tudo sem qualquer acesso à rede!
None network — Casos de uso reaisPrática
# ═══════════════════════════════════
# CASO 1: Processamento de dados sensíveis
# ═══════════════════════════════════
# Dados de cartão de crédito, CPF, etc.
# Container processa sem risco de vazamento:
docker run --network none \
  -v dados-sensiveis:/input:ro \
  -v resultado:/output \
  processador-pci-dss

# ═══════════════════════════════════
# CASO 2: Build/compilação segura
# ═══════════════════════════════════
# Compilar código sem acesso à rede
# (previne supply-chain attacks):
docker run --network none \
  -v ./src:/src:ro \
  -v ./artifacts:/dist \
  rust:1.75 cargo build --release

# ═══════════════════════════════════
# CASO 3: Geração de documentos/PDFs
# ═══════════════════════════════════
docker run --network none \
  -v ./templates:/templates:ro \
  -v ./output:/output \
  pandoc/latex \
  /templates/relatorio.md -o /output/relatorio.pdf

# ═══════════════════════════════════
# CASO 4: Testes unitários isolados
# ═══════════════════════════════════
# Garantir que testes não dependem de rede:
docker run --network none \
  -v ./projeto:/app \
  node:20 npm test

# Se algum teste falhar = dependência de rede
# (indica teste mal escrito)

Arquitetura

Cenários Práticos de Arquitetura de Rede

Vamos explorar cenários reais de como organizar redes Docker para aplicações em produção. Cada cenário demonstra como usar múltiplas redes para implementar segmentação, isolamento e segurança.

Exemplo 1: Frontend + Backend + Database (3 Redes Separadas)

Uma aplicação web clássica com três camadas, cada uma em sua própria rede. O backend serve como ponte entre frontend e database:

Arquitetura 3-tier com redes isoladasProdução

# CENÁRIO: E-commerce com 3 camadas de rede
# ═══════════════════════════════════════════════════════════════
#
# REGRAS DE SEGURANÇA:
# • Frontend NÃO acessa banco diretamente
# • Database NÃO é exposto externamente
# • Backend é a única ponte entre as camadas
# • Apenas o Frontend/Nginx é acessível de fora
#
# ═══════════════════════════════════════════════════════════════

#
# ┌─────────────────────────────────────────────────────────────────┐

# │  │   ┌────────────────────────────────▼──────┐            │     │

Boas Práticas de Arquitetura de Rede

✅ Faça

  • Crie redes separadas por responsabilidade
  • Use --internal para redes de dados
  • Exponha apenas o mínimo necessário com -p
  • Use network aliases para desacoplar nomes
  • Documente a topologia de rede do projeto
  • Use labels para organizar redes
  • Bind em 127.0.0.1 para serviços internos

❌ Não Faça

  • Colocar todos os containers na mesma rede
  • Usar a bridge padrão (docker0)
  • Expor portas de banco/cache externamente
  • Usar --link (deprecado)
  • Hardcodar IPs (use DNS)
  • Usar --network host sem necessidade real
  • Ignorar firewall/iptables com Docker

Troubleshooting de Rede

Problemas de rede são os mais comuns em ambientes Docker. Saber diagnosticar rapidamente por que containers não se comunicam, por que portas não respondem ou por que não há acesso à internet pode economizar horas de frustração.

Problema 1: Container Não Consegue Acessar Internet

Diagnóstico: sem acesso à internetFix
# SINTOMA: container não baixa pacotes, não resolve DNS externo
docker exec meu-container ping 8.8.8.8
# ping: sendto: Network unreachable

# ═══════════════════════════════════════════════════════════════
# CHECKLIST DE DIAGNÓSTICO:
# ═══════════════════════════════════════════════════════════════

# 1. Verificar se a rede é --internal:
docker network inspect minha-rede --format '{{.Internal}}'
# Se "true" → rede é interna, sem internet por design!
# Solução: usar outra rede ou remover --internal

# 2. Verificar IP forwarding no host:
cat /proc/sys/net/ipv4/ip_forward
# Deve ser "1". Se "0":
sudo sysctl -w net.ipv4.ip_forward=1
# Persistir: echo "net.ipv4.ip_forward = 1" >> /etc/sysctl.conf

# 3. Verificar regras iptables (NAT/masquerade):
sudo iptables -t nat -L POSTROUTING -n -v
# Deve ter regra MASQUERADE para subnet do Docker

# 4. Verificar DNS dentro do container:
docker exec meu-container cat /etc/resolv.conf
# Deve ter: nameserver 127.0.0.11

# Testar resolução DNS:
docker exec meu-container nslookup google.com
# Se falhar: problema de DNS

# 5. Verificar conectividade por IP (bypass DNS):
docker exec meu-container ping -c 1 8.8.8.8
# Se ping por IP funciona mas DNS não → problema apenas de DNS

# 6. Verificar se o daemon Docker tem DNS configurado:
cat /etc/docker/daemon.json
# Adicionar se necessário:
# { "dns": ["8.8.8.8", "8.8.4.4"] }
# Reiniciar: sudo systemctl restart docker

# 7. Verificar se host tem internet:
ping -c 1 8.8.8.8  # no host
# Se host não tem internet, container também não terá

# 8. Verificar se bridge está UP:
ip link show docker0
# Deve estar: state UP

Problema 2: Containers Não se Comunicam entre Si

Diagnóstico: containers não se alcançamFix
# SINTOMA: docker exec app ping db → falha
# ═══════════════════════════════════════════════════════════════

# 1. VERIFICAR SE ESTÃO NA MESMA REDE:
docker inspect app --format '{{range $k,$v := .NetworkSettings.Networks}}{{$k}} {{end}}'
# Resultado: frontend-net

docker inspect db --format '{{range $k,$v := .NetworkSettings.Networks}}{{$k}} {{end}}'
# Resultado: backend-net

# ❌ PROBLEMA: estão em redes DIFERENTES!
# SOLUÇÃO: colocar na mesma rede:
docker network connect backend-net app
# ou criar rede compartilhada

# 2. VERIFICAR SE ESTÁ USANDO BRIDGE PADRÃO (sem DNS):
docker inspect app --format '{{range $k,$v := .NetworkSettings.Networks}}{{$k}} {{end}}'
# Resultado: bridge

# ❌ PROBLEMA: bridge padrão NÃO tem DNS por nome!
# SOLUÇÃO: criar rede customizada:
docker network create app-net
docker network connect app-net app
docker network connect app-net db
docker network disconnect bridge app
docker network disconnect bridge db

# 3. TESTAR CONECTIVIDADE POR IP (confirmar que rede funciona):
docker inspect db -f '{{.NetworkSettings.Networks.app_net.IPAddress}}'
# 172.18.0.3

docker exec app ping -c 1 172.18.0.3
# Se funciona por IP mas não por nome → problema de DNS
# Se não funciona nem por IP → problema de rede/rota

# 4. VERIFICAR DNS:
docker exec app nslookup db
# Se "** server can't find db" → container não está na mesma rede

# 5. VERIFICAR SE ICC ESTÁ DESABILITADO:
docker network inspect app-net --format '{{.Options}}'
# Se "com.docker.network.bridge.enable_icc:false" → comunicação bloqueada!
# Solução: recriar rede sem essa opção

# 6. VERIFICAR SE O CONTAINER DE DESTINO ESTÁ RODANDO:
docker ps --filter name=db
# Se não aparece → container está parado!

Problema 3: Porta Não Acessível de Fora

Diagnóstico: porta não responde externamenteFix
# SINTOMA: curl http://SERVIDOR:8080 → Connection refused (de outra máquina)
# Mas funciona localmente: curl http://localhost:8080 ✅
# ═══════════════════════════════════════════════════════════════

# 1. VERIFICAR PORT MAPPING:
docker port meu-container
# 80/tcp -> 0.0.0.0:8080  ← OK, publicado em todas interfaces
# 80/tcp -> 127.0.0.1:8080 ← PROBLEMA! Só acessível localmente!

# SOLUÇÃO se bind em 127.0.0.1:
docker stop meu-container && docker rm meu-container
docker run -d -p 0.0.0.0:8080:80 meu-container
# ou simplesmente: -p 8080:80 (default é 0.0.0.0)

# 2. VERIFICAR SE O APP ESCUTA NO ENDEREÇO CORRETO:
docker exec meu-container netstat -tlnp
# Se app escuta em 127.0.0.1:80 → só aceita conexões locais!
# Precisa escutar em 0.0.0.0:80

# Exemplo: Flask/Node precisa bind em 0.0.0.0:
# Flask: app.run(host='0.0.0.0', port=80)  ← correto
# Flask: app.run(host='127.0.0.1', port=80) ← só localhost
# Node: app.listen(80, '0.0.0.0')  ← correto

# 3. VERIFICAR FIREWALL DO HOST:
sudo ufw status
# Se ativo, a porta pode estar bloqueada
# ⚠️ MAS Docker geralmente bypassa UFW via iptables!

# Verificar iptables:
sudo iptables -L -n | grep 8080
# Deve ter regra ACCEPT para a porta

# 4. VERIFICAR SE CONTAINER ESTÁ RODANDO:
docker ps --filter name=meu-container
# Se não aparece → container caiu! Ver logs:
docker logs meu-container

# 5. VERIFICAR HEALTH DO SERVIÇO DENTRO DO CONTAINER:
docker exec meu-container curl -s http://localhost:80
# Se falha aqui → o serviço dentro do container tem problema

# 6. VERIFICAR SE OUTRO PROCESSO USA A PORTA:
sudo ss -tlnp | grep 8080
# Se outro processo ocupa a porta no host → conflito!

docker network create app-stack

docker run -d \

curl http://localhost:6379 2>&1

docker run -it --rm \
  --name app-node \
  --network app-stack \

    npm init -y > /dev/null 2>&1
    npm install ioredis --silent

    # Script que conecta no Redis via DNS
    node -e "
      const Redis = require(\"ioredis\");
      const redis = new Redis({ host: \"cache\", port: 6379 });

      async function main() {

        await redis.set(\"usuario:1\", JSON.stringify({
          nome: \"Maria Silva\",
          email: \"maria@email.com\"
        }));
        console.log(\"✅ Dados gravados no Redis\");

        const dados = await redis.get(\"usuario:1\");

        const visitas = await redis.get(\"visitas\");

        // Info do servidor
        const info = await redis.info(\"server\");

        await redis.quit();
      }
      main().catch(console.error);
    "
  '

#
# TOPOLOGIA:
# [Nginx] ←front-net→ [API] ←back-net→ [PostgreSQL]
#
# TENTE RESOLVER ANTES DE VER A SOLUÇÃO!

Solução do Exercício 3Solução

# SOLUÇÃO COMPLETA:

# 1. Criar as redes:
docker network create front-net
docker network create --internal back-net

# 2. Iniciar PostgreSQL (apenas back-net):
docker run -d \
  --name postgres \
  --network back-net \
  --network-alias db \
  -e POSTGRES_PASSWORD=secret \

# 3. Iniciar a API (inicialmente em front-net):
docker run -d \
  --name api \
  --network front-net \
  --network-alias backend \
  alpine sleep 3600

docker network connect back-net api

# 4. Iniciar Nginx (apenas front-net):
docker run -d \
  --name nginx \
  --network front-net \
  -p 8080:80 \
  nginx:alpine

# ═══════════════════════════════════════════════════════════════
# COMPROVAÇÃO DE ISOLAMENTO:
# ═══════════════════════════════════════════════════════════════

docker exec nginx ping -c 1 backend
# PING backend (172.18.0.3): 64 bytes from 172.18.0.3 ✅

docker exec nginx ping -c 1 -W 2 db

docker exec api ping -c 1 db

docker exec api ping -c 1 nginx
# PING nginx (172.18.0.2): 64 bytes from 172.18.0.2 ✅

docker exec postgres ping -c 1 -W 2 8.8.8.8

docker exec api ping -c 1 8.8.8.8

#   Nginx  → API: ✅    | Nginx  → DB: ❌

docker stop nginx api postgres
docker rm nginx api postgres
docker network rm front-net back-net

# ═══════════════════════════════════════════════════════════════
# CENÁRIO: Alguém configurou os containers abaixo, mas a

# Você precisa encontrar o problema e corrigir.
# ═══════════════════════════════════════════════════════════════
#
# SETUP (rode estes comandos para criar o cenário com problema):

docker network create rede-app

docker run -d --name webapp \

# Banco na rede-dados:
docker run -d --name database \
  --network rede-dados \
  --network-alias db \
  redis:7-alpine

# SINTOMA:
docker exec webapp ping -c 1 -W 2 db
# ping: bad address 'db'  ← NÃO FUNCIONA!

docker exec webapp ping -c 1 -W 2 database
# ping: bad address 'database'  ← NÃO FUNCIONA!

# ═══════════════════════════════════════════════════════════════
# SUA MISSÃO:
# 1. Diagnosticar por que não funciona
# 2. Corrigir o problema (sem recriar os containers)
# 3. Comprovar que a comunicação funciona após fix
# ═══════════════════════════════════════════════════════════════
#
# TENTE RESOLVER ANTES DE VER A SOLUÇÃO!
# ═══════════════════════════════════════════════════════════════
Solução do Exercício 4Solução
# ═══════════════════════════════════════════════════════════════
# DIAGNÓSTICO:
# ═══════════════════════════════════════════════════════════════

docker inspect webapp --format \
  '{{range $k,$v := .NetworkSettings.Networks}}{{$k}}: {{$v.IPAddress}} {{end}}'
