Configuração: Conta, SSH e Ambiente

Antes de versionar código, configure seu ambiente corretamente. Uma boa configuração evita problemas futuros com autenticação e identidade.

1. Configuração Inicial do Git

git configEssencial

Define identidade e preferências globais do Git.

# Identidade (obrigatório)
git config --global user.name "Seu Nome"
git config --global user.email "seu@email.com"

# Preferências úteis
git config --global init.defaultBranch main
git config --global core.editor "code --wait"
git config --global pull.rebase true

# Verificar configurações
git config --list
git config --global --list

2. Chave SSH e Autenticação

ssh-keygenAutenticação

Gera par de chaves para autenticação sem senha no GitHub.

# Gerar chave SSH (Ed25519 recomendado)
ssh-keygen -t ed25519 -C "seu@email.com"

# Iniciar o ssh-agent
eval "$(ssh-agent -s)"
ssh-add ~/.ssh/id_ed25519

# Copiar chave pública para adicionar no GitHub
cat ~/.ssh/id_ed25519.pub

# Testar conexão
ssh -T git@github.com
# Hi usuario! You've successfully authenticated

Fundamentos: Repositório, Commits e Remoto

O fluxo básico do Git: inicializar, rastrear mudanças, criar snapshots e sincronizar com o GitHub.

3. Criando e Clonando Repositórios

git initCriar

Inicializa um repositório Git local.

mkdir meu-projeto
cd meu-projeto
git init
# Initialized empty Git repository
git cloneCriar

Clona um repositório remoto para sua máquina.

# Via SSH (recomendado)
git clone git@github.com:user/repo.git

# Via HTTPS
git clone https://github.com/user/repo.git

# Clone com nome customizado
git clone git@github.com:user/repo.git meu-dir

4. Fluxo Básico: add → commit → push

Os 3 estados do Git: 
Working Directory → Staging Area → Repository
   (modificado)      (preparado)     (commitado)
      git add →      git commit →    git push →  Remote
git statusEssencial

Mostra o estado atual dos arquivos.

git status
# On branch main
# Changes not staged for commit:
#   modified: index.html
# Untracked files:
#   style.css

git status -s  # formato curto
# M  index.html
# ?? style.css
git addStaging

Adiciona arquivos à staging area.

git add arquivo.txt       # arquivo específico
git add .                 # tudo no diretório
git add *.js              # por extensão
git add -p                # interativo (por hunks)

# Remover do staging (sem perder mudanças)
git restore --staged arquivo.txt
git commitEssencial

Cria um snapshot das mudanças no staging.

git commit -m "feat: adiciona navbar"
git commit -am "fix: corrige typo"  # add + commit
git commit --amend  # edita último commit

# Boas práticas de mensagem:
# tipo: descrição curta (max 72 chars)
# feat: | fix: | docs: | refactor: | test:
git logHistórico

Visualiza o histórico de commits.

git log                    # completo
git log --oneline          # resumido
git log --oneline --graph  # com branches
git log -5                 # últimos 5
git log --author="João"    # por autor
git log --since="2024-01-01"

5. Sincronização com Remoto

git remoteRemoto

Gerencia conexões com repositórios remotos.

git remote add origin git@github.com:user/repo.git
git remote -v              # lista remotos
git remote rename origin upstream
git remote remove upstream
git pushEnviar

Envia commits locais para o remoto.

git push origin main
git push -u origin main    # define upstream
git push                   # após -u, basta isso
git push --force-with-lease # force seguro
git pullReceber

Baixa e integra mudanças do remoto.

git pull                   # fetch + merge
git pull --rebase          # fetch + rebase
git pull origin main       # branch específica
git fetchReceber

Baixa mudanças sem integrar (mais seguro).

git fetch origin
git fetch --all            # todos os remotos
git log origin/main..main  # ver diferenças
# Depois: git merge origin/main

Módulo 02

Branches: Ramificação e Merge

Branches permitem trabalhar em funcionalidades isoladas sem afetar o código principal. É o coração do trabalho em equipe.

1. Criando e Navegando entre Branches

git branch / checkout / switchEssencial

Gerencia branches locais e remotas.

# Listar branches
git branch              # locais
git branch -a           # locais + remotas
git branch -v           # com último commit

# Criar branch
git branch feature/login
git checkout -b feature/login    # cria e muda
git switch -c feature/login      # forma moderna

# Mudar de branch
git checkout main
git switch main

# Deletar branch
git branch -d feature/login      # seguro (merged)
git branch -D feature/login      # forçado
git push origin --delete feature/login  # remota
Convenções de nomes: feature/ nova funcionalidade, fix/ ou bugfix/ correção, hotfix/ correção urgente em produção, release/ preparação de release, chore/ tarefas de manutenção.

2. Merge e Estratégias

git mergeIntegração

Integra mudanças de uma branch em outra.

# Merge da feature na main
git checkout main
git merge feature/login

# Merge com commit explícito
git merge --no-ff feature/login

# Abortar merge com conflito
git merge --abort
git stashUtilidade

Salva mudanças temporariamente sem commit.

# Guardar mudanças
git stash
git stash push -m "WIP: navbar"

# Listar e recuperar
git stash list
git stash pop           # aplica e remove
git stash apply stash@{0}  # aplica sem remover

# Limpar
git stash drop stash@{0}
git stash clear
git diffComparação

Mostra diferenças entre estados.

git diff                   # working vs staging
git diff --staged          # staging vs commit
git diff main..feature     # entre branches
git diff HEAD~3            # últimos 3 commits
git diff --stat            # resumo
Estratégias de MergeConceito

Entenda quando usar cada tipo.

# Fast-forward (padrão quando possível)
# Histórico linear, sem commit de merge
git merge feature  # se main não avançou

# No fast-forward (preserva histórico)
git merge --no-ff feature
# Cria commit de merge sempre

# Squash (compacta commits)
git merge --squash feature
git commit -m "feat: login completo"

Módulo 04

Resolução de Conflitos

Conflitos acontecem quando duas pessoas editam o mesmo trecho. Saber resolvê-los é essencial para trabalho em equipe.

5. Entendendo e Resolvendo Conflitos

Conflito de MergeEssencial

Anatomia de um conflito e como resolver.

# Quando o Git não consegue resolver automaticamente:
<<<<<<< HEAD
const titulo = "Versão da branch atual";
=======
const titulo = "Versão da branch incoming";
>>>>>>> feature/nova-funcionalidade

# Resolução:
# 1. Edite o arquivo — escolha uma versão ou combine
const titulo = "Versão final combinada";

# 2. Remova os marcadores (<<<<, ====, >>>>)

# 3. Adicione e commite
git add arquivo-resolvido.js
git commit -m "fix: resolve conflito no título"

# Ferramentas visuais:
git mergetool              # abre ferramenta configurada
# VS Code: aceitar current/incoming/both
Prevenir ConflitosDica

Boas práticas para minimizar conflitos.

# 1. Pull frequente
git pull --rebase origin main

# 2. Branches curtas (1-3 dias)

# 3. Comunicação com o time

# 4. Arquivos pequenos e focados

# 5. Rebase antes de abrir PR
git checkout feature
git rebase main
# Resolve conflitos uma vez só
Abortar e RecomeçarSegurança

Quando a resolução fica complexa demais.

# Abortar merge em andamento
git merge --abort

# Abortar rebase em andamento
git rebase --abort

# Voltar ao estado anterior
git reset --hard HEAD

# Ver estado antes do conflito
git stash
git log --oneline --graph
Módulo 05

Histórico e Reescrita: Rebase, Cherry-pick e Reflog

Ferramentas avançadas para manipular o histórico de commits. Use com cuidado em branches compartilhadas.

1. Git Rebase

git rebaseAvançado

Reaplica commits sobre outra base. Cria histórico linear e limpo.

# Rebase simples — atualiza feature com main
git checkout feature/login
git rebase main
# Seus commits são reaplicados sobre o topo da main

# Rebase interativo — editar/squash/reorder commits
git rebase -i HEAD~5
# pick abc1234 feat: adiciona form
# squash def5678 fix: ajusta validação
# reword ghi9012 docs: atualiza README
# drop jkl3456 WIP: teste temporário

# Continuar após resolver conflito
git rebase --continue

# Abortar rebase
git rebase --abort
⚠️ Regra de Ouro: Nunca faça rebase em branches públicas/compartilhadas. Rebase reescreve o histórico — use apenas em branches locais ou pessoais.

2. Cherry-pick e Reflog

git cherry-pickAvançado

Aplica um commit específico em outra branch.

# Aplicar commit específico
git cherry-pick abc1234

# Aplicar múltiplos commits
git cherry-pick abc1234 def5678

# Aplicar sem commitar (só staging)
git cherry-pick --no-commit abc1234

# Caso de uso: hotfix
git checkout main
git cherry-pick fix-commit-hash
# Aplica a correção sem trazer toda a branch
git reflogRecuperação

Histórico de TODAS as ações — sua rede de segurança.

# Ver histórico completo de movimentos
git reflog
# abc1234 HEAD@{0}: commit: feat: login
# def5678 HEAD@{1}: checkout: main → feature
# ghi9012 HEAD@{2}: reset: moving to HEAD~1

# Recuperar commit "perdido"
git checkout HEAD@{2}
git branch recuperada HEAD@{2}

# Recuperar após reset --hard
git reflog
git reset --hard HEAD@{1}

# Reflog expira em 90 dias (padrão)
git resetReescrita

Move o HEAD para outro commit. Cuidado com --hard!

# Soft — mantém mudanças no staging
git reset --soft HEAD~1

# Mixed (padrão) — mantém no working dir
git reset HEAD~1

# Hard — DESCARTA tudo (perigoso!)
git reset --hard HEAD~1

# Desfazer último commit (mantendo mudanças)
git reset --soft HEAD~1
# Agora pode re-commitar diferente
git revertSeguro

Cria novo commit que desfaz outro. Seguro para branches públicas.

# Reverter um commit (cria novo commit)
git revert abc1234

# Reverter sem commitar automaticamente
git revert --no-commit abc1234

# Reverter merge commit
git revert -m 1 merge-commit-hash

# Diferença de reset:
# reset: apaga histórico (perigoso)
# revert: adiciona ao histórico (seguro)
Módulo 06

Fluxos Profissionais: Git Flow, Tags e Conventional Commits

Estratégias de branching usadas por equipes profissionais. Escolha o fluxo certo para seu projeto.

3. Git Flow vs GitHub Flow

Git FlowFluxo

Modelo robusto para projetos com releases planejadas.

# Branches permanentes:
# main     → código em produção
# develop  → integração de features

# Branches temporárias:
# feature/* → novas funcionalidades
# release/* → preparação de release
# hotfix/*  → correções urgentes em produção

# Fluxo:
git checkout develop
git checkout -b feature/pagamento
# ... desenvolve ...
git checkout develop
git merge --no-ff feature/pagamento

# Release:
git checkout -b release/1.2.0 develop
# ... ajustes finais, bump version ...
git checkout main
git merge --no-ff release/1.2.0
git tag -a v1.2.0 -m "Release 1.2.0"
git checkout develop
git merge --no-ff release/1.2.0
GitHub FlowFluxo

Modelo simplificado — ideal para deploy contínuo.

# Apenas 1 branch permanente: main (sempre deployável)

# Fluxo:
# 1. Crie branch a partir de main
git checkout -b feature/dark-mode

# 2. Faça commits incrementais
git commit -m "feat: adiciona toggle de tema"
git commit -m "feat: implementa CSS dark mode"

# 3. Abra Pull Request cedo (Draft PR)
git push -u origin feature/dark-mode
# → Abra PR no GitHub

# 4. Code Review + CI passa

# 5. Merge na main (squash ou merge commit)

# 6. Deploy automático após merge

# Quando usar cada um:
# Git Flow → releases planejadas, múltiplas versões
# GitHub Flow → deploy contínuo, SaaS, projetos ágeis

4. Tags e Versionamento

git tagRelease

Marca pontos específicos no histórico (releases).

# Tag anotada (recomendada)
git tag -a v1.0.0 -m "Primeira release"

# Tag leve
git tag v1.0.0-beta

# Listar tags
git tag -l "v1.*"

# Push tags para remoto
git push origin v1.0.0
git push origin --tags    # todas

# Deletar tag
git tag -d v1.0.0
git push origin --delete v1.0.0
Conventional CommitsPadrão

Padrão de mensagens para changelog automático.

# Formato:
# tipo(escopo): descrição

feat: adiciona autenticação OAuth
feat(api): implementa endpoint /users
fix: corrige validação de email
fix(auth): token não expira corretamente
docs: atualiza README com exemplos
style: formata código com prettier
refactor: extrai lógica para service
test: adiciona testes para UserService
chore: atualiza dependências
ci: adiciona step de lint no pipeline

# Breaking change:
feat!: remove suporte a Node 14
# ou
feat: migra para ESM
BREAKING CHANGE: require() não funciona mais

5. Semantic Versioning (SemVer)

MAJOR.MINOR.PATCH — Exemplo: v2.1.3 
MAJOR (2) → Breaking changes (incompatível com anterior)
MINOR (1) → Nova funcionalidade (compatível)
PATCH (3) → Correção de bug (compatível)

Exemplos:
v1.0.0 → v1.0.1  (fix: corrige bug)
v1.0.1 → v1.1.0  (feat: nova feature)
v1.1.0 → v2.0.0  (feat!: breaking change)
Módulo 07

Automação: GitHub Actions, CI/CD e Hooks

Automatize testes, builds e deploys diretamente no GitHub. GitHub Actions é a plataforma de CI/CD integrada ao repositório.

1. GitHub Actions — Fundamentos

Workflow YAMLCI/CD

Arquivo de workflow em .github/workflows/.

# .github/workflows/ci.yml
name: CI Pipeline

on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'

      - name: Install dependencies
        run: npm ci

      - name: Run linter
        run: npm run lint

      - name: Run tests
        run: npm test

      - name: Build
        run: npm run build
Deploy WorkflowCD

Exemplo de deploy automático para AWS S3 + CloudFront.

# .github/workflows/deploy.yml
name: Deploy to Production

on:
  push:
    branches: [main]

permissions:
  id-token: write
  contents: read

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production
    steps:
      - uses: actions/checkout@v4

      - name: Configure AWS Credentials (OIDC)
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789:role/github-actions
          aws-region: us-east-1

      - name: Sync to S3
        run: aws s3 sync ./dist s3://meu-bucket --delete

      - name: Invalidate CloudFront
        run: |
          aws cloudfront create-invalidation \
            --distribution-id ${{ secrets.CF_DISTRIBUTION_ID }} \
            --paths "/*"

2. Terraform CI com GitHub Actions

Terraform PipelineIaC
# .github/workflows/terraform.yml
name: Terraform CI

  pull_request:

          AWS_SECRET_ACCESS_KEY: ${{ secrets.AWS_SECRET_ACCESS_KEY }}

3. Git Hooks

Hooks LocaisAutomação

Scripts executados automaticamente em eventos Git.

# .git/hooks/pre-commit
#!/bin/bash
echo "Rodando lint antes do commit..."
npm run lint
if [ $? -ne 0 ]; then
  echo "❌ Lint falhou! Corrija antes de commitar."
  exit 1
fi

# .git/hooks/commit-msg
#!/bin/bash
MSG=$(cat "$1")
PATTERN="^(feat|fix|docs|style|refactor|test|chore)(\(.+\))?: .+"
if ! echo "$MSG" | grep -qE "$PATTERN"; then
  echo "❌ Mensagem fora do padrão Conventional Commits"
  exit 1
fi

4. Branch Protection Rules

Branch ProtectionSegurança

Proteja branches importantes contra push direto e merges sem review.

# Settings → Branches → Add rule
# Branch name pattern: main

# Regras recomendadas:
✅ Require a pull request before merging
  ✅ Require approvals (mínimo 1)
  ✅ Dismiss stale pull request approvals
✅ Require status checks to pass
  ✅ Require branches to be up to date
  → Selecione: CI Pipeline, Tests
✅ Require conversation resolution
✅ Require signed commits (opcional)
✅ Do not allow bypassing the above settings

# Resultado: ninguém faz push direto na main
# Todo código passa por PR + CI + Review
