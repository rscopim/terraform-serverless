Design de Arquiteturas de Alta Performance

EC2, EBS, S3, CloudFront, Global Accelerator, ElastiCache, DynamoDB, Lambda, containers e streaming. Este domínio representa 24% do exame.

1. EC2 — Compute

Instance FamiliesTipos
Famílias de instâncias (mnemônico):

General Purpose (M, T):
• M6i, M7g — workloads balanceados
• T3, T4g — burstable (créditos CPU)

Compute Optimized (C):
• C6i, C7g — batch, ML inference, gaming, HPC

Memory Optimized (R, X, z):
• R6i — caches, in-memory DBs
• X2idn — SAP HANA, grandes datasets
• z1d — alta frequência de clock

Storage Optimized (I, D, H):
• I4i — alto IOPS (databases)
• D3 — data warehousing, HDFS
• H1 — throughput sequencial

Accelerated Computing (P, G, Inf, Trn):
• P5 — ML training (GPU NVIDIA)
• G5 — graphics, video encoding
• Inf2 — ML inference (Inferentia)
• Trn1 — ML training (Trainium)
Placement GroupsPosicionamento
Cluster:
• Instâncias no MESMO rack/AZ
• Menor latência possível (10 Gbps entre instâncias)
• Risco: se rack falha, todas falham
• Uso: HPC, big data jobs, low-latency apps

Spread:
• Instâncias em hardware DIFERENTE
• Máximo 7 instâncias por AZ por grupo
• Minimiza risco de falha correlacionada
• Uso: aplicações críticas, HA

Partition:
• Grupos de instâncias em partições isoladas
• Cada partição em rack diferente
• Até 7 partições por AZ
• Uso: HDFS, HBase, Cassandra, Kafka

Enhanced Networking (ENA):
• Até 100 Gbps
• Menor latência, maior PPS
• Sem custo adicional
• Requer driver ENA na AMI

3. S3 — Performance

Transfer AccelerationUpload
S3 Transfer Acceleration:
• Usa edge locations da CloudFront para upload
• Dados viajam pela rede backbone da AWS
• 50-500% mais rápido para uploads distantes
• Endpoint: bucketname.s3-accelerate.amazonaws.com
• Custo adicional por GB transferido

Quando usar:
• Uploads de regiões distantes do bucket
• Transferências intercontinentais
• Clientes distribuídos globalmente

Multipart Upload:
• OBRIGATÓRIO para objetos > 5GB
• Recomendado para > 100MB
• Upload paralelo de partes
• Retry de partes individuais (sem recomeçar tudo)
• Abort incomplete uploads (lifecycle rule)
S3 Performance LimitsEscala
Limites por prefixo:
• 3.500 PUT/COPY/POST/DELETE por segundo
• 5.500 GET/HEAD por segundo
• Por prefixo! Mais prefixos = mais throughput

Otimização de prefixos:
• Distribuir objetos em múltiplos prefixos
• Ex: /images/2024/01/, /images/2024/02/
• Cada prefixo tem seus próprios limites

S3 Select / Glacier Select:
• Filtrar dados com SQL no lado do servidor
• Retorna apenas dados necessários
• Reduz transferência de dados em até 400%
• Reduz custo de transferência

Byte-Range Fetches:
• Download paralelo de partes do objeto
• Acelera downloads grandes
• Retry de ranges específicos

4. CloudFront — CDN

Origins e BehaviorsConfig
Origins (fontes de conteúdo):
• S3 Bucket (com OAC para acesso privado)
• ALB / EC2 (custom origin)
• API Gateway
• MediaStore / MediaPackage

Behaviors (regras de roteamento):
• Path pattern: /images/*, /api/*, /static/*
• Cada behavior → origin específico
• Cache policy por behavior
• Viewer protocol policy (HTTP→HTTPS redirect)

OAC (Origin Access Control):
• Substitui OAI (legacy)
• S3 bucket pode ser privado
• Apenas CloudFront acessa o bucket
• Suporta SSE-KMS
• Mais seguro que OAI
Cache PoliciesPerformance
Cache Key:
• Define o que diferencia objetos no cache
• Headers, query strings, cookies incluídos
• Menos itens no cache key = melhor hit ratio

TTL (Time to Live):
• Min TTL, Max TTL, Default TTL
• Cache-Control headers do origin
• Invalidation para forçar refresh (custo)

Cache Policies (managed):
• CachingOptimized — máximo cache
• CachingDisabled — sem cache (proxy)
• Custom — controle granular

Origin Request Policy:
• O que enviar ao origin (separado do cache key)
• Pode enviar headers sem afetar cache

Lambda@Edge / CloudFront Functions:
• Código na edge para manipular requests/responses
• CloudFront Functions: leve, viewer events
• Lambda@Edge: mais poder, origin events

5. AWS Global Accelerator

Global Accelerator vs CloudFrontComparação
Global Accelerator:
• 2 IPs estáticos anycast globais
• Tráfego entra na edge e viaja pela rede AWS (backbone)
• Melhora performance para TCP/UDP (não apenas HTTP)
• Health checks e failover automático entre regiões
• Sem cache — todo tráfego vai ao origin
• Casos: gaming, IoT, VoIP, APIs não-HTTP

CloudFront:
• CDN com cache na edge
• Otimizado para conteúdo HTTP/HTTPS
• Cache reduz carga no origin
• Ideal para conteúdo estático e dinâmico cacheable

Quando usar Global Accelerator:
• Precisa de IP estático (whitelisting)
• Protocolo não-HTTP (TCP/UDP)
• Failover instantâneo entre regiões
• Não precisa de cache, precisa de routing otimizado
• Gaming multiplayer, financial trading

6. ElastiCache

Redis vs MemcachedComparação
Redis:
• Estruturas de dados ricas (strings, lists, sets, hashes)
• Persistência (snapshots, AOF)
• Replicação (Multi-AZ com failover automático)
• Cluster mode (sharding)
• Pub/Sub, Lua scripting
• Backup e restore
• Encryption at rest e in transit

Memcached:
• Simples key-value
• Multi-threaded (melhor para multi-core)
• Sem persistência
• Sem replicação nativa
• Sem backup
• Auto-discovery de nodes

Escolha:
• Redis → persistência, HA, estruturas complexas
• Memcached → cache simples, multi-threaded
Caching StrategiesPadrões
Lazy Loading (Cache-Aside):
• App verifica cache primeiro
• Cache miss → busca no DB → grava no cache
• Dados podem ficar stale
• Apenas dados requisitados são cacheados

Write-Through:
• App escreve no cache E no DB simultaneamente
• Cache sempre atualizado
• Maior latência de escrita
• Dados nunca ficam stale

TTL (Time to Live):
• Expira dados após tempo definido
• Combina com Lazy Loading
• Balanceia freshness vs performance

Session Store:
• Armazenar sessões de usuário no Redis
• Alternativa a sticky sessions
• Compartilhado entre todas as instâncias
• TTL para expirar sessões inativas

7. DynamoDB

Partition Key DesignModelagem
Partition Key (PK):
• Determina em qual partição o item é armazenado
• DEVE ter alta cardinalidade (muitos valores únicos)
• Distribuição uniforme = melhor performance

Boas PKs: user_id, order_id, device_id
Más PKs: status, date, country (hot partition)

Sort Key (SK):
• Ordena itens dentro da mesma partição
• Permite range queries (begins_with, between)
• Composite key: PK + SK = item único

Padrões de design:
• Single-table design (múltiplas entidades)
• PK: USER#123, SK: ORDER#456
• PK: USER#123, SK: PROFILE
• Overloading de atributos
GSI e DAXPerformance
Global Secondary Index (GSI):
• Nova partition key + optional sort key
• Projeção de atributos (ALL, KEYS_ONLY, INCLUDE)
• Capacidade provisionada separada
• Eventually consistent reads apenas
• Até 20 GSIs por tabela

Local Secondary Index (LSI):
• Mesma partition key, sort key diferente
• Deve ser criado na criação da tabela
• Strongly consistent reads possível
• Até 5 LSIs por tabela

DynamoDB Accelerator (DAX):
• Cache in-memory para DynamoDB
• Microsegundos de latência (vs ms)
• Compatível com API DynamoDB (drop-in)
• Write-through cache
• Ideal para read-heavy workloads
• Cluster Multi-AZ

8. Lambda, ECS/EKS e Kinesis

Lambda PerformanceServerless
Concurrency:
• Default: 1.000 concurrent executions/region
• Reserved concurrency: garante para função
• Provisioned concurrency: elimina cold starts

Memory (128MB - 10GB):
• Mais memória = mais CPU proporcional
• 1.769 MB = 1 vCPU completo
• Otimizar: AWS Lambda Power Tuning

Layers:
• Bibliotecas compartilhadas entre funções
• Até 5 layers por função
• Reduz tamanho do deployment package
• Versionadas independentemente

Limites:
• Timeout: máximo 15 minutos
• Payload: 6MB (sync), 256KB (async)
• /tmp storage: 512MB - 10GB
• Deployment package: 50MB (zip), 250MB (unzipped)
ECS/EKS e KinesisContainers/Stream
ECS (Elastic Container Service):
• EC2 launch type: gerencia instâncias
• Fargate launch type: serverless containers
• Task definitions, services, clusters
• ALB integration (dynamic port mapping)

EKS (Elastic Kubernetes Service):
• Kubernetes gerenciado
• Nodes: EC2 ou Fargate
• Para equipes com expertise em K8s
• Portabilidade multi-cloud

Kinesis Data Streams:
• Streaming de dados em tempo real
• Shards: unidade de capacidade
  (1 MB/s in, 2 MB/s out por shard)
• Retention: 24h (default) até 365 dias
• Consumers: Lambda, KCL, Kinesis Analytics

Kinesis Data Firehose:
• Delivery stream (near real-time)
• Destinos: S3, Redshift, OpenSearch, Splunk
• Transformação com Lambda
• Sem gerenciamento de shards (auto-scaling)

🎯 Para o exame: Lambda = até 15 min, serverless. ECS Fargate = containers serverless. Kinesis Streams = real-time processing. Kinesis Firehose = delivery para S3/Redshift (near real-time, sem gerenciamento).
