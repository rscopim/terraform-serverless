🏛️ Solutions Architect — Domínio 02

Design de Arquiteturas Resilientes

Alta disponibilidade, Auto Scaling, Load Balancing, Route 53, replicação, bancos de dados e estratégias de DR. Este domínio representa 26% do exame.

1. Alta Disponibilidade (High Availability)

Multi-AZRegional
Availability Zones (AZs):
• Data centers isolados dentro de uma região
• Conectados por rede de baixa latência
• Falha de uma AZ não afeta outras

Padrão Multi-AZ:
• Distribuir recursos em 2+ AZs
• ALB roteia entre AZs automaticamente
• Auto Scaling lança em múltiplas AZs
• RDS Multi-AZ: standby síncrono em outra AZ

Serviços inerentemente Multi-AZ:
• S3 (replicação automática em 3+ AZs)
• DynamoDB (replicação em 3 AZs)
• ELB (distribui entre AZs)
• Lambda (executa em múltiplas AZs)
Multi-RegionGlobal
Quando usar Multi-Region:
• DR com RPO/RTO muito baixos
• Latência global (usuários em vários continentes)
• Compliance (dados em região específica)

Serviços Multi-Region:
• Route 53 (DNS global, failover)
• CloudFront (CDN global)
• S3 Cross-Region Replication
• DynamoDB Global Tables
• Aurora Global Database
• AWS Global Accelerator

Considerações:
• Custo significativamente maior
• Complexidade operacional
• Data sovereignty e compliance
• Consistência eventual entre regiões

2. Auto Scaling

Scaling PoliciesPolíticas
Target Tracking (recomendado):
• Define métrica alvo (ex: CPU = 50%)
• ASG ajusta automaticamente para manter o target
• Simples e eficiente para maioria dos casos

Step Scaling:
• Define steps baseados em alarmes CloudWatch
• Ex: CPU > 70% → +2 instâncias
      CPU > 90% → +4 instâncias
• Mais controle granular

Simple Scaling:
• Uma ação por alarme
• Cooldown period entre ações
• Menos usado (prefer target tracking)

Scheduled Scaling:
• Escala em horários pré-definidos
• Ex: +10 instâncias às 8h, -10 às 20h
• Para padrões de carga previsíveis
ASG ConfigurationConfig
Launch Template:
• AMI, instance type, key pair, SGs
• User data (bootstrap scripts)
• Suporta múltiplos instance types
• Versioning (v1, v2, Latest)

ASG Settings:
• Min / Max / Desired capacity
• Health check type: EC2 ou ELB
• Health check grace period
• Cooldown period (default 300s)
• Termination policies

Lifecycle Hooks:
• Pending:Wait → executar ações antes de InService
• Terminating:Wait → executar antes de terminar
• Útil para: drain connections, backup logs

Instance Refresh:
• Rolling update de instâncias
• Min healthy percentage
• Útil para deploy de nova AMI

🎯 Para o exame: Target Tracking é a política recomendada. Launch Template > Launch Configuration (deprecated). Health check ELB é mais preciso que EC2. Lifecycle hooks para ações pré/pós scaling.

Health ChecksMonitoramento
Configurações:
• Protocol: HTTP, HTTPS, TCP
• Path: /health (endpoint dedicado)
• Interval: 5-300s (default 30s)
• Threshold: healthy/unhealthy count
• Timeout: tempo máximo de resposta

Comportamento:
• Target unhealthy → para de receber tráfego
• Target healthy novamente → volta a receber
• Cross-zone load balancing distribui uniformemente

💡 Sempre criar endpoint /health dedicado
   que verifica dependências (DB, cache)
Sticky SessionsAfinidade
Application-based (ALB):
• Cookie customizado ou gerado pelo ALB
• Duração configurável
• Útil para sessões stateful

Problemas com sticky sessions:
• Distribuição desigual de carga
• Dificulta scaling
• Se instância falha, sessão é perdida

Alternativas (preferíveis):
• Sessões em ElastiCache (Redis)
• Sessões em DynamoDB
• JWT tokens (stateless)
• Cookies client-side criptografados

💡 Exame: se perguntam sobre "manter sessão"
   → ElastiCache/DynamoDB > sticky sessions

5. S3 — Replicação e Versionamento

ReplicationCópia
Cross-Region Replication (CRR):
• Replica objetos para bucket em outra região
• Casos: DR, compliance, latência
• Requer versioning habilitado em ambos

Same-Region Replication (SRR):
• Replica dentro da mesma região
• Casos: agregação de logs, compliance,
  replicação entre contas na mesma região

Regras:
• Versioning OBRIGATÓRIO (source e destination)
• Pode replicar para outra conta AWS
• Objetos existentes NÃO são replicados (apenas novos)
  → Use S3 Batch Replication para existentes
• Delete markers podem ser replicados (opcional)
• Não há replicação em cadeia (A→B→C não funciona)
VersioningHistórico
S3 Versioning:
• Mantém todas as versões de um objeto
• Protege contra deleção acidental
• Uma vez habilitado, não pode ser desabilitado
  (apenas suspenso)

Delete Marker:
• DELETE em objeto versionado cria delete marker
• Objeto "desaparece" mas versões anteriores existem
• Para restaurar: deletar o delete marker

MFA Delete:
• Requer MFA para deletar versões permanentemente
• Proteção extra contra deleção maliciosa
• Apenas root account pode habilitar

Lifecycle + Versioning:
• Mover versões antigas para classes mais baratas
• Expirar versões antigas após X dias
• Limpar incomplete multipart uploads

6. RDS, Aurora e Bancos de Dados

RDS Multi-AZHA
Multi-AZ Deployment:
• Standby síncrono em outra AZ
• Failover automático (1-2 minutos)
• Mesmo endpoint DNS (sem mudança na app)
• NÃO é para read scaling (standby não aceita reads)

Read Replicas:
• Replicação ASSÍNCRONA
• Até 5 read replicas por DB
• Podem estar em outra AZ ou região
• Endpoint próprio (app precisa apontar)
• Podem ser promovidas a standalone DB
• Cross-region para DR

Multi-AZ vs Read Replica:
• Multi-AZ = HA (failover automático)
• Read Replica = Performance (read scaling)
• Podem ser combinados!
Amazon AuroraManaged
Aurora vs RDS:
• 5x performance do MySQL, 3x do PostgreSQL
• Storage auto-scaling (10GB → 128TB)
• 6 cópias dos dados em 3 AZs
• Self-healing storage

Aurora Replicas:
• Até 15 read replicas (vs 5 no RDS)
• Failover automático para replica (< 30s)
• Reader endpoint (load balance entre replicas)

Aurora Serverless:
• Auto-scaling de compute (ACUs)
• Escala para zero quando ocioso
• Pay-per-use
• Bom para: workloads intermitentes, dev/test

Aurora Global Database:
• Replicação cross-region (< 1s lag)
• Até 5 secondary regions
• RPO < 1s, RTO < 1 minuto
• Promoted region em caso de DR

7. Estratégias de Disaster Recovery

EstratégiaRTORPOCustoDescrição
Backup & RestoreHorasHoras💰Backups em S3/outra região. Restaura quando necessário. Mais barato, mais lento.
Pilot Light10s minMinutos💰💰Core mínimo rodando (DB replicado). Escala compute quando necessário.
Warm StandbyMinutosSegundos💰💰💰Versão reduzida da produção rodando. Scale up quando ativado.
Active-Active (Multi-site)~0~0💰💰💰💰Full production em 2+ regiões. Tráfego distribuído. Mais caro, mais rápido.
AWS BackupCentralizado
Serviço centralizado de backup:
• Suporta: EC2, EBS, RDS, Aurora, DynamoDB, EFS, S3, FSx
• Backup Plans: schedule, retention, lifecycle
• Cross-region e cross-account backup
• Vault Lock: WORM (Write Once Read Many) para compliance
• Point-in-time recovery para serviços suportados

Boas práticas:
• Backup automático com retention policies
• Cross-region para DR
• Testar restore regularmente
• Vault Lock para proteção contra ransomware
• Tags para organização e compliance

🎯 Para o exame: Backup/Restore = mais barato, maior RTO. Active-Active = mais caro, menor RTO. Pilot Light = DB replicado + compute sob demanda. RPO = quanto dado posso perder. RTO = quanto tempo posso ficar offline.
