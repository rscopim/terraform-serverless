🏛️ Solutions Architect — Domínio 01

Design de Arquiteturas Seguras

IAM, VPC, criptografia, serviços de segurança, Organizations e governança. Este domínio representa 30% do exame.

1. IAM — Identity and Access Management

Policies e Permissões

Identity-based PoliciesUsuário/Role
Tipos de policies:
• AWS Managed — criadas e mantidas pela AWS
• Customer Managed — criadas pelo cliente (reusáveis)
• Inline — embutidas diretamente no usuário/grupo/role

Avaliação de permissões:
1. Deny explícito → SEMPRE nega
2. Allow explícito → permite (se não há deny)
3. Deny implícito → padrão (sem policy = sem acesso)

Princípio do menor privilégio:
• Conceder apenas permissões necessárias
• Usar conditions para restringir (IP, MFA, horário)
• Revisar com IAM Access Analyzer
Resource-based PoliciesRecurso
Aplicadas diretamente ao recurso:
• S3 Bucket Policies
• SQS Queue Policies
• KMS Key Policies
• Lambda Resource Policies

Diferença-chave:
• Identity-based: "O que este usuário pode fazer?"
• Resource-based: "Quem pode acessar este recurso?"

Cross-account:
• Resource-based permite acesso cross-account
  sem assumir role (Principal de outra conta)
• Útil para compartilhar S3, KMS, SQS entre contas

IAM Roles e Cross-Account Access

IAM RolesTemporário
Roles fornecem credenciais temporárias (STS):
• Não têm credenciais permanentes
• Assumidas por usuários, serviços ou contas externas

Casos de uso:
• EC2 Instance Profile (role para EC2)
• Lambda Execution Role
• Cross-account access
• Federation (SAML, OIDC)

Trust Policy:
• Define QUEM pode assumir a role
• Permissions Policy define O QUE a role pode fazer
Cross-Account AccessMulti-conta
Padrão para acesso entre contas AWS:

1. Conta B cria Role com Trust Policy
   → Principal: arn:aws:iam::CONTA-A:root

2. Conta A concede sts:AssumeRole para a role da Conta B

3. Usuário na Conta A assume a role da Conta B
   → Recebe credenciais temporárias

Alternativas:
• Resource-based policies (S3, KMS)
• AWS Resource Access Manager (RAM)
• Organizations + SCPs para governança

🎯 Para o exame: IAM Roles são SEMPRE preferíveis a access keys. Cross-account = Role + Trust Policy. MFA deve ser exigido para ações sensíveis. IAM Access Analyzer identifica recursos compartilhados externamente.

2. VPC — Virtual Private Cloud

Subnets e Roteamento

SubnetsRede
Subnet Pública:
• Route table com rota para Internet Gateway (IGW)
• Recursos com IP público acessam internet
• Ex: ALB, NAT Gateway, Bastion Host

Subnet Privada:
• Sem rota direta para IGW
• Acesso à internet via NAT Gateway (em subnet pública)
• Ex: EC2 de aplicação, RDS, ElastiCache

Boas práticas:
• Mínimo 2 AZs para alta disponibilidade
• Subnets separadas por tier (web, app, data)
• CIDR planning para evitar conflitos
VPC EndpointsPrivado
Acesso a serviços AWS sem passar pela internet:

Interface Endpoint (PrivateLink):
• ENI na subnet com IP privado
• Suporta: S3, DynamoDB, SQS, SNS, KMS, etc.
• Security Groups aplicáveis
• Custo por hora + dados transferidos

Gateway Endpoint (gratuito):
• Entrada na route table
• Apenas S3 e DynamoDB
• Sem custo adicional
• Preferível para S3/DynamoDB

💡 Gateway Endpoint para S3/DynamoDB
   Interface Endpoint para demais serviços

NACLs vs Security Groups

Security GroupsStateful
• Nível de instância (ENI)
• STATEFUL — retorno automático permitido
• Apenas regras ALLOW (sem deny explícito)
• Avalia TODAS as regras antes de decidir
• Pode referenciar outro SG como source

Exemplo:
• SG-Web: permite 80/443 de 0.0.0.0/0
• SG-App: permite 8080 de SG-Web
• SG-DB: permite 3306 de SG-App
NACLsStateless
• Nível de subnet
• STATELESS — precisa regra de entrada E saída
• Regras ALLOW e DENY
• Avalia regras em ORDEM numérica (primeira match)
• Default NACL permite tudo

Quando usar NACLs:
• Bloquear IPs específicos (deny)
• Camada extra de defesa
• Compliance requirements

⚠️ Ephemeral ports (1024-65535) devem ser
   permitidos na saída para respostas

Conectividade

VPC Peering1:1
• Conexão direta entre 2 VPCs
• Mesmo ou diferente account/region
• NÃO transitivo (A↔B, B↔C ≠ A↔C)
• CIDRs não podem se sobrepor
• Precisa atualizar route tables em ambos lados

Limitações:
• Não escala para muitas VPCs
• Cada par precisa de peering separado
• Para muitas VPCs → Transit Gateway
Transit GatewayHub
• Hub central para conectar múltiplas VPCs
• Suporta VPN e Direct Connect
• TRANSITIVO — todas VPCs se comunicam via hub
• Cross-region peering entre TGWs
• Route tables para controle granular

Casos de uso:
• Muitas VPCs (>3) precisam se comunicar
• Arquitetura hub-and-spoke
• Shared services VPC
• Conectividade híbrida centralizada

🎯 Para o exame: SG = stateful (só allow) | NACL = stateless (allow + deny). VPC Peering = não transitivo. Transit Gateway = transitivo, hub central. VPC Endpoints eliminam necessidade de NAT/IGW para serviços AWS.

3. Criptografia e Proteção de Dados

AWS KMSChaves
Key Management Service:

Tipos de chaves:
• AWS Managed Keys — criadas/gerenciadas pela AWS
  (aws/s3, aws/ebs, aws/rds)
• Customer Managed Keys (CMK) — controle total
  (rotação, policies, auditoria)
• AWS Owned Keys — usadas internamente pela AWS

Envelope Encryption:
1. KMS gera Data Key (plaintext + encrypted)
2. Data Key criptografa os dados
3. Plaintext key é descartada da memória
4. Encrypted data key armazenada junto aos dados

Rotação automática:
• AWS Managed: a cada 1 ano (automático)
• Customer Managed: configurável (anual)
Encryption at RestArmazenamento
S3 Encryption:
• SSE-S3: chave gerenciada pela AWS (padrão)
• SSE-KMS: chave KMS (auditoria via CloudTrail)
• SSE-C: chave fornecida pelo cliente
• Client-side: criptografa antes de enviar

EBS Encryption:
• AES-256 via KMS
• Snapshots de volumes encrypted são encrypted
• Volumes criados de snapshots encrypted são encrypted
• Não é possível remover encryption de volume existente

RDS Encryption:
• Ativada na criação (não pode ativar depois)
• Read replicas herdam encryption
• Snapshots de DB encrypted são encrypted
• Para criptografar DB existente:
  snapshot → copy com encryption → restore

🎯 Para o exame: SSE-KMS permite auditoria via CloudTrail. Envelope Encryption para dados grandes. Para criptografar RDS existente: snapshot → copy encrypted → restore. S3 default encryption = SSE-S3.

5. AWS Organizations e Governança

OrganizationsMulti-conta
Estrutura hierárquica:
• Root → OUs (Organizational Units) → Accounts
• Consolidated Billing (fatura única)
• Volume discounts compartilhados

SCPs (Service Control Policies):
• Definem LIMITE MÁXIMO de permissões
• NÃO concedem permissões (apenas restringem)
• Aplicadas a OUs ou contas
• Não afetam a Management Account
• Herança hierárquica (OU pai → OU filho)

Exemplo SCP — bloquear regiões:
{
  "Effect": "Deny",
  "Action": "*",
  "Resource": "*",
  "Condition": {
    "StringNotEquals": {
      "aws:RequestedRegion": ["us-east-1","sa-east-1"]
    }
  }
}
AWS SSO / Identity CenterAcesso
AWS IAM Identity Center (ex-SSO):
• Single Sign-On para múltiplas contas AWS
• Integra com Active Directory, Okta, Azure AD
• Permission Sets definem acesso por conta
• Um login → acesso a várias contas/apps

Fluxo:
1. Usuário autentica no Identity Center
2. Seleciona conta e permission set
3. Recebe credenciais temporárias (STS)

Vantagens:
• Gerenciamento centralizado de acesso
• Auditoria unificada
• Sem necessidade de IAM users por conta
• Suporta SAML 2.0 e OIDC

💡 Identity Center é a recomendação AWS
   para gerenciar acesso multi-conta
CloudTrail + ConfigAuditoria
CloudTrail:
• Registra TODAS as API calls (Management Events por padrão)
• Data Events (S3 object-level, Lambda invocations) — custo adicional
• Multi-region trail recomendado
• Integração com CloudWatch Logs para alertas
• Organization Trail para todas as contas

AWS Config:
• Avalia configurações contra regras
• Config Rules: managed (AWS) ou custom (Lambda)
• Remediation automática com SSM Automation
• Aggregator para visão multi-conta/multi-região
• Exemplos: s3-bucket-public-read-prohibited, encrypted-volumes, required-tags
