Permissões

Sistema de Permissões Linux

O Linux possui um sistema de permissões poderoso e elegante que controla quem pode ler, escrever e executar cada arquivo e diretório. Entender permissões é fundamental para segurança, deploy de aplicações e administração de servidores.

Modelo rwx — A base de tudo

Cada arquivo e diretório no Linux possui três conjuntos de permissões, cada um com três bits:

r — Read (Leitura)4

Arquivo: Permite ler o conteúdo do arquivo (cat, less, head).

Diretório: Permite listar o conteúdo do diretório (ls).

w — Write (Escrita)2

Arquivo: Permite modificar ou apagar o conteúdo do arquivo.

Diretório: Permite criar, renomear ou deletar arquivos dentro dele.

x — Execute (Execução)1

Arquivo: Permite executar o arquivo como programa ou script.

Diretório: Permite entrar no diretório (cd) e acessar seus arquivos.

⚠️ Atenção com diretórios: As permissões funcionam de forma diferente para diretórios! Um diretório sem x é inacessível (não pode fazer cd nele), mesmo que tenha r. Um diretório sem r mas com x permite acessar arquivos se souber o nome, mas não listar.

Os três níveis de permissão (UGO)

As permissões são aplicadas em três níveis, definindo quem pode fazer o quê:

u — User (Dono)Owner

O usuário que criou o arquivo (ou a quem foi atribuído com chown). Tem o primeiro conjunto de permissões.

g — Group (Grupo)Group

Todos os usuários que pertencem ao grupo associado ao arquivo. Segundo conjunto de permissões.

o — Others (Outros)World

Todos os demais usuários do sistema que não são o dono nem pertencem ao grupo. Terceiro conjunto.

Permissões Especiais: SUID, SGID e Sticky Bit

Além do rwx básico, existem três permissões especiais que controlam comportamentos avançados:

SUID (Set User ID)4000

Quando executado, o processo roda com as permissões do dono do arquivo, não do usuário que executou.

# Exemplo clássico: passwd
$ ls -l /usr/bin/passwd
-rwsr-xr-x 1 root root 68208 ...
#   ^
# 's' no lugar de 'x' do dono = SUID ativo

# Por que? passwd precisa escrever em /etc/shadow
# que é de propriedade do root. SUID permite que
# qualquer usuário execute passwd como root.

# Definir SUID:
chmod u+s programa
chmod 4755 programa

# PERIGO: SUID em scripts ou binários inseguros
# é uma vulnerabilidade grave de segurança!
SGID (Set Group ID)2000

Em arquivo: Executa com permissões do grupo do arquivo. Em diretório: Novos arquivos herdam o grupo do diretório.

# Em diretório (mais comum):
$ ls -ld /var/www/projeto
drwxrwsr-x 2 root devops 4096 ...
#      ^
# 's' no lugar de 'x' do grupo = SGID

# Todo arquivo criado dentro herda grupo "devops"
# Sem SGID: arquivo herdaria grupo primário do usuário
touch /var/www/projeto/novo.txt
ls -l /var/www/projeto/novo.txt
# -rw-r--r-- 1 joao devops ... novo.txt
#                    ^^^^^^ herdou do diretório!

# Definir SGID:
chmod g+s diretorio/
chmod 2775 diretorio/
Sticky Bit1000

Em diretórios com sticky bit, apenas o dono do arquivo (ou root) pode deletar/renomear seus próprios arquivos — mesmo que outros tenham permissão de escrita no diretório.

# Exemplo clássico: /tmp
$ ls -ld /tmp
drwxrwxrwt 15 root root 4096 ...
#        ^
# 't' no lugar de 'x' de others = Sticky Bit

# Todos podem criar arquivos em /tmp (rwx para others)
# Mas cada usuário só pode deletar SEUS próprios arquivos
# Sem sticky bit, qualquer um poderia deletar arquivos de outros

# Definir Sticky Bit:
chmod +t diretorio/
chmod 1777 diretorio/

# Cenário prático: diretório compartilhado de upload
mkdir /srv/uploads
chmod 1777 /srv/uploads
# Todos podem fazer upload, ninguém deleta arquivo dos outros
💡 Resumo das permissões especiais (octal): 
# Octal com 4 dígitos: [especial][user][group][others]
4755  →  SUID + rwxr-xr-x      (s no user)
2775  →  SGID + rwxrwxr-x      (s no group)
1777  →  Sticky + rwxrwxrwx    (t no others)
6755  →  SUID+SGID + rwxr-xr-x (s no user E group)

# Letras maiúsculas indicam ERRO (bit especial sem x correspondente):
# 'S' = SUID definido mas sem x no user (inútil)
# 'S' = SGID definido mas sem x no group (inútil)
# 'T' = Sticky definido mas sem x no others (inútil)

chmod — Alterar Permissões

O comando chmod (change mode) altera as permissões de arquivos e diretórios. Ele aceita duas notações: simbólica (mais legível) e octal (mais rápida). Dominar ambas é essencial.

Modo Simbólico — Legível e flexível

A notação simbólica usa letras para especificar quem, qual operação e qual permissão:

Sintaxe: chmod [quem][operação][permissão] arquivoSimbólico
# QUEM:
# u = user (dono)
# g = group (grupo)
# o = others (outros)
# a = all (todos = u+g+o)

# OPERAÇÃO:
# + = adicionar permissão
# - = remover permissão
# = = definir exatamente (remove outras)

# PERMISSÃO:
# r = read    w = write    x = execute
# s = SUID/SGID    t = sticky bit

# ═══════════════════════════════════════════════════
# EXEMPLOS PRÁTICOS:
# ═══════════════════════════════════════════════════

# Adicionar permissão de execução para o dono
chmod u+x script.sh
# Antes: -rw-r--r--  →  Depois: -rwxr--r--

# Remover escrita do grupo e outros
chmod go-w arquivo.txt
# Antes: -rw-rw-rw-  →  Depois: -rw-r--r--

# Definir permissão exata para outros (apenas leitura)
chmod o=r arquivo.txt
# Antes: -rwxrwxrwx  →  Depois: -rwxrwxr--

# Adicionar leitura para todos
chmod a+r documento.pdf
# Antes: -rw-------  →  Depois: -rw-r--r--

# Remover todas as permissões de outros
chmod o= confidencial.txt
# Antes: -rw-r--r--  →  Depois: -rw-r-----

# Múltiplas operações separadas por vírgula
chmod u+x,g+rx,o-rwx deploy.sh
# Antes: -rw-r--r--  →  Depois: -rwxr-x---

# Definir permissões exatas para todos os níveis
chmod u=rwx,g=rx,o= app.sh
# Resultado: -rwxr-x---

# Adicionar SUID
chmod u+s /usr/local/bin/programa
# Resultado: -rwsr-xr-x

# Adicionar SGID a diretório
chmod g+s /var/www/projeto/
# Resultado: drwxrwsr-x

# Adicionar Sticky Bit
chmod +t /srv/shared/
# Resultado: drwxrwxrwt

Modo Octal — Rápido e direto

A notação octal define todas as permissões de uma vez com 3 ou 4 dígitos:

Sintaxe: chmod [octal] arquivoOctal
# ═══════════════════════════════════════════════════
# PERMISSÕES MAIS USADAS NO DIA A DIA:
# ═══════════════════════════════════════════════════

# 755 — Diretórios e scripts executáveis
chmod 755 deploy.sh
# -rwxr-xr-x  (dono: tudo, grupo/outros: ler+executar)

# 644 — Arquivos regulares (configs, HTML, código)
chmod 644 index.html
# -rw-r--r--  (dono: ler+escrever, grupo/outros: ler)

# 700 — Diretórios privados
chmod 700 ~/.ssh
# drwx------  (apenas o dono pode acessar)

# 600 — Arquivos sensíveis (chaves, senhas)
chmod 600 ~/.ssh/id_rsa
chmod 600 .env
# -rw-------  (apenas o dono pode ler e escrever)

# 400 — Arquivos read-only sensíveis
chmod 400 chave-aws.pem
# -r--------  (apenas o dono pode ler, nem escrever)

# 775 — Diretórios de grupo (equipe compartilha)
chmod 775 /var/www/projeto
# drwxrwxr-x  (dono+grupo: tudo, outros: ler+executar)

# 664 — Arquivos compartilhados com grupo
chmod 664 documento.txt
# -rw-rw-r--  (dono+grupo: ler+escrever, outros: ler)

# 750 — Diretório de aplicação (grupo pode ler)
chmod 750 /opt/app
# drwxr-x---  (dono: tudo, grupo: ler+exec, outros: nada)

# 640 — Configs com dados sensíveis (grupo pode ler)
chmod 640 /etc/app/database.yml
# -rw-r-----  (dono: ler+escrever, grupo: ler, outros: nada)

# Com permissões especiais (4 dígitos):
chmod 4755 /usr/local/bin/app   # SUID
chmod 2775 /var/www/projeto     # SGID
chmod 1777 /tmp                 # Sticky

chmod -R — Recursivo

A flag -R aplica permissões recursivamente a todos os arquivos e subdiretórios:

Aplicação recursiva — CuidadosRecursivo
# Aplicar 755 a tudo recursivamente
chmod -R 755 /var/www/site/
# ⚠️ PROBLEMA: arquivos ficam com +x (executáveis) desnecessariamente!

# SOLUÇÃO CORRETA: separar diretórios de arquivos com find
# Diretórios: 755 (precisam de x para serem acessados)
find /var/www/site -type d -exec chmod 755 {} \;

# Arquivos: 644 (não precisam de x, apenas ler)
find /var/www/site -type f -exec chmod 644 {} \;

# Scripts: apenas os .sh ganham execução
find /var/www/site -type f -name "*.sh" -exec chmod 755 {} \;

# Alternativa mais rápida com find + xargs:
find /var/www/site -type d | xargs chmod 755
find /var/www/site -type f | xargs chmod 644

# chmod -R com simbólico (mais seguro):
# Adicionar execução em diretórios sem afetar arquivos
chmod -R a+X /var/www/site/
# X (maiúsculo) = adiciona x APENAS em diretórios e arquivos que JÁ têm x
⚠️ Regra de ouro: Nunca use chmod -R 777 em produção. Isso é a primeira coisa que um invasor procura. Se algo "não funciona" e a solução sugerida na internet é chmod 777, o problema real está em outro lugar (ownership ou configuração de serviço).

Ownership

chown e chgrp — Alterar Dono e Grupo

Permissões definem o que pode ser feito; ownership define quem é afetado por cada nível de permissão. Alterar o dono e grupo de arquivos é essencial em deploys, configuração de serviços e compartilhamento entre equipes.

chown — Alterar dono e/ou grupo

chown (change owner) modifica o proprietário e opcionalmente o grupo de um arquivo ou diretório. Requer root/sudo.

Sintaxe: chown [opções] [dono][:grupo] arquivo(s)Proprietário
# ═══════════════════════════════════════════════════
# FORMAS DE USO DO CHOWN:
# ═══════════════════════════════════════════════════

# Mudar apenas o dono:
sudo chown joao arquivo.txt
# Antes: -rw-r--r-- 1 root root  →  Depois: -rw-r--r-- 1 joao root

# Mudar dono E grupo (separador ':' ou '.'):
sudo chown joao:devops arquivo.txt
# Antes: -rw-r--r-- 1 root root  →  Depois: -rw-r--r-- 1 joao devops

sudo chown joao.devops arquivo.txt   # mesmo efeito com '.'

# Mudar apenas o grupo (: antes do grupo, sem user):
sudo chown :www-data arquivo.txt
# Antes: -rw-r--r-- 1 joao root  →  Depois: -rw-r--r-- 1 joao www-data

# Mudar dono e definir grupo como grupo primário do novo dono:
sudo chown joao: arquivo.txt
# Se grupo primário de joao é "joao":
# Antes: -rw-r--r-- 1 root root  →  Depois: -rw-r--r-- 1 joao joao

chown -R — Recursivo para diretórios

Aplicação recursiva em diretórios inteirosRecursivo
# Mudar dono de todo o diretório e seu conteúdo:
sudo chown -R www-data:www-data /var/www/site/

# Verbose (-v): mostra cada arquivo alterado
sudo chown -Rv deploy:devops /opt/app/
# changed '/opt/app/' from root:root to deploy:devops
# changed '/opt/app/main.py' from root:root to deploy:devops
# changed '/opt/app/config.yml' from root:root to deploy:devops

# Preservar grupo dos subdiretórios existentes, mudar só dono:
sudo chown -R deploy /opt/app/
# Apenas o user muda, group fica como estava

# --reference: copiar ownership de outro arquivo
sudo chown --reference=/var/www/site/index.html novo-arquivo.html
# novo-arquivo.html terá o mesmo dono e grupo de index.html

# Combinação com find para ser seletivo:
# Mudar dono apenas dos diretórios:
find /var/www -type d -exec sudo chown root:www-data {} \;

# Mudar dono apenas dos arquivos .py:
find /opt/app -name "*.py" -exec sudo chown deploy:devops {} \;

chgrp — Alterar apenas o grupo

chgrp (change group) é um atalho para mudar apenas o grupo, sem alterar o dono:

Sintaxe: chgrp [opções] grupo arquivo(s)Grupo
# Mudar grupo de um arquivo:
sudo chgrp devops deploy.sh
# Antes: -rwxr-x--- 1 deploy root  →  Depois: -rwxr-x--- 1 deploy devops

# Mudar grupo recursivamente:
sudo chgrp -R www-data /var/www/uploads/

# Verbose:
sudo chgrp -Rv devops /srv/projeto/
# changed group of '/srv/projeto/' from root to devops
# changed group of '/srv/projeto/app.py' from root to devops

# Usando referência:
sudo chgrp --reference=/var/www/site /var/www/novo-site

# Nota: chgrp é equivalente a "chown :grupo arquivo"
# Mas chgrp pode ser usado sem sudo se o usuário
# pertence ao grupo de destino (depende da distro).

Usuários e Grupos

Linux é um sistema multiusuário desde sua concepção. Gerenciar usuários e grupos é fundamental para segurança, controle de acesso e administração de servidores. Cada processo roda como um usuário, cada arquivo pertence a um dono e grupo.

Arquivos fundamentais — /etc/passwd, /etc/shadow, /etc/group

Toda informação sobre usuários e grupos é armazenada em três arquivos de texto plano:

su e sudo — Elevação de privilégios

Existem duas formas de executar comandos como outro usuário:

su — Switch User (mudar de usuário)su
# Mudar para root (pede senha do ROOT):
su -
# Password: [senha do root]
# Agora é root! (#)

# Mudar para outro usuário:
su - maria
# Password: [senha da maria]

# O '-' carrega o ambiente completo do usuário:
su - joao    # login shell (carrega .bashrc, PATH, etc)
su joao      # sem '-' = shell simples (herda ambiente atual)

# Executar um comando como outro usuário:
su - deploy -c "cd /opt/app && ./restart.sh"

# Problemas com su:
# 1. Precisa compartilhar senha do root/usuário
# 2. Não há log de quem fez o quê
# 3. Acesso "tudo ou nada"
# 4. Difícil auditar
sudo — Superuser Do (recomendado)sudo
# Executar comando como root (pede SUA senha):
sudo apt update
# [sudo] password for joao: [sua senha]

# Abrir shell root:
sudo -i     # login shell como root
sudo -s     # shell simples como root

# Executar como outro usuário:
sudo -u deploy ./restart.sh
sudo -u www-data touch /var/www/test.html

# Vantagens do sudo sobre su:
# 1. Usa SUA senha (não compartilha root)
# 2. Tudo é logado em /var/log/auth.log
# 3. Permissões granulares (sudoers)
# 4. Pode dar acesso a comandos específicos
# 5. Timeout (não fica como root para sempre)

# Editar sudoers (SEMPRE usar visudo!):
sudo visudo
# Nunca edite /etc/sudoers diretamente!
# visudo valida a sintaxe antes de salvar.

Processos

Gerenciamento de Processos

Tudo que roda no Linux é um processo — desde o kernel até seu editor de texto. Entender como visualizar, controlar e terminar processos é essencial para administrar servidores, debugar problemas de performance e gerenciar aplicações em produção.

O que é um Processo?

Um processo é uma instância de um programa em execução. Cada processo tem:

PID — Process IDIdentidade

Número único que identifica o processo. O primeiro processo (init/systemd) tem PID 1. Todo novo processo recebe um PID sequencial.

# Ver PID do shell atual:
echo $$
# 12345

# PID do último processo em background:
echo $!
# 12400
PPID — Parent Process IDPai

PID do processo que criou este processo (processo pai). Forma uma árvore de processos com PID 1 na raiz.

# Ver árvore de processos:
pstree -p
# systemd(1)─┬─sshd(850)───sshd(12300)───bash(12345)
#             ├─nginx(900)─┬─nginx(901)
#             │            └─nginx(902)
#             └─postgres(950)───postgres(951)
Estados de um ProcessoEstado

Cada processo está em um estado que define seu comportamento atual:

# Estados possíveis (coluna STAT no ps):
R = Running    (executando ou pronto)
S = Sleeping   (aguardando evento/I/O)
D = Disk sleep (I/O ininterruptível)
T = Stopped    (parado, Ctrl+Z)
Z = Zombie     (finalizado, pai não leu)
I = Idle       (kernel thread idle)

# Modificadores:
< = alta prioridade (nice negativo)
N = baixa prioridade (nice positivo)
s = líder de sessão
l = multi-threaded
+ = foreground process group

kill, killall, pkill — Enviar sinais a processos

No Linux, processos são controlados através de sinais. O mais comum é pedir que um processo termine, mas existem muitos sinais com diferentes significados:

Sinais mais importantesSinais
# ═══════════════════════════════════════════════════
# SINAIS FUNDAMENTAIS:
# ═══════════════════════════════════════════════════

# SIGTERM (15) — Terminação educada (padrão)
# O processo recebe o sinal e pode fazer cleanup:
# - Fechar conexões de banco
# - Salvar estado
# - Liberar recursos
# - Terminar gracefully
kill 12400          # envia SIGTERM (padrão)
kill -15 12400      # explícito: SIGTERM
kill -SIGTERM 12400 # por nome

# O kernel mata o processo instantaneamente.
# O processo NÃO pode capturar, ignorar ou fazer cleanup.
# USE APENAS como último recurso!
kill -9 12400       # SIGKILL
kill -KILL 12400    # por nome

# SIGHUP (1) — Hangup (recarregar config)
# Muitos daemons interpretam como "recarregue sua configuração"
kill -HUP 900       # nginx recarrega config
kill -1 900         # mesmo efeito

# SIGSTOP (19) — Pausar processo (irrecusável)
kill -STOP 12400    # congela o processo
kill -CONT 12400    # descongela (continua)

# SIGINT (2) — Interrupção (equivale a Ctrl+C)

# TABELA COMPLETA DE SINAIS ÚTEIS:
# ═══════════════════════════════════════════════════
# Sinal    Número   Ação               Capturável?
# SIGHUP     1      Recarregar/terminar   Sim
# SIGINT     2      Interromper (Ctrl+C)  Sim
# SIGQUIT    3      Quit + core dump      Sim
# SIGKILL    9      Matar imediatamente   NÃO
# SIGTERM   15      Terminar educado      Sim
# SIGSTOP   19      Pausar                NÃO

# 1. Tente SIGTERM primeiro:

Foreground vs Background — Controle de Jobs

O shell pode rodar processos em primeiro plano (foreground) ou segundo plano (background):

# FOREGROUND: Processo ocupa o terminal
# Você não pode digitar outros comandos enquanto roda

# Rodar em foreground (padrão):
./backup.sh              # terminal fica bloqueado até terminar

# O terminal fica livre para outros comandos

bg                       # retoma em background
# [1]+ ./processo-longo.sh &

# Mover processo de background para foreground:
fg                       # traz o último job para foreground
fg %1                    # traz job número 1 para foreground

# ═══════════════════════════════════════════════════

# ═══════════════════════════════════════════════════

# %1    = job número 1
# %+    = job mais recente (mesmo que %%)

nohup e disown — Sobreviver ao logout

Processos em background normalmente morrem quando você fecha o terminal (SIGHUP). Use nohup ou disown para mantê-los rodando:

nohup — No HangupPersistente

# Output vai para nohup.out por padrão

nohup ./processo-longo.sh &
# [1] 12600
# nohup: ignoring input and appending output to 'nohup.out'

# Redirecionar output para arquivo específico:
nohup ./backup.sh > /var/log/backup.log 2>&1 &

# Descartar output completamente:
nohup ./daemon.sh > /dev/null 2>&1 &

# Verificar se está rodando:
ps aux | grep processo-longo
# joao 12600 ... ./processo-longo.sh

# Agora pode fechar o terminal!
# O processo continua rodando.

# Ver output:
tail -f nohup.out
disown — Desassociar do shellDesassociar
# disown remove o job da tabela do shell
# O processo não recebe SIGHUP no logout

# Cenário: esqueceu o nohup!
./processo-longo.sh      # já está rodando...
# Ctrl+Z                 # suspende
bg                       # retoma em background
disown                   # desassocia do shell
# Agora pode fechar o terminal!

# disown com job específico:
disown %1                # desassocia job 1
disown %2                # desassocia job 2
disown -a                # desassocia TODOS os jobs

# disown -h (não remove da tabela, apenas ignora SIGHUP):
disown -h %1

# Diferença nohup vs disown:
# nohup = usar ANTES de iniciar (preventivo)
# disown = usar DEPOIS de iniciar (remediar)

# Para processos de longa duração, considere:
# - tmux / screen (melhor opção!)
# - systemd service
# - supervisord

Prioridade

Prioridade de Processos — nice e renice

O kernel Linux distribui tempo de CPU entre processos usando um sistema de prioridades. Você pode influenciar essa distribuição com os comandos nice e renice, garantindo que processos críticos tenham preferência sobre tarefas menos urgentes.

Entendendo Nice Values

O "niceness" (gentileza) de um processo determina sua prioridade de agendamento. Quanto mais "gentil" (nice), mais cede CPU para outros:

Escala de nice: -20 a 19Escala
# ═══════════════════════════════════════════════════
# ESCALA DE NICE VALUES:
# ═══════════════════════════════════════════════════

# -20 ─── ALTA prioridade (menos "gentil" — exige mais CPU)
# -10 ─── Prioridade alta
#   0 ─── Padrão (default para todos os processos)
#  10 ─── Prioridade baixa
#  19 ─── BAIXA prioridade (mais "gentil" — cede CPU)

# Regras:
# 1. Qualquer usuário pode AUMENTAR nice (0→19, reduzir prioridade)
# 2. Apenas root pode DIMINUIR nice (0→-20, aumentar prioridade)
# 3. Processos de sistema geralmente rodam com nice 0 ou negativo
# 4. Tarefas de manutenção devem usar nice alto (10-19)

# Ver nice value de processos:
ps -eo pid,ni,user,cmd | head -20
#   PID  NI USER     CMD
#     1   0 root     /sbin/init
#   850   0 root     sshd
# 12400   0 joao     node app.js
# 12500  19 joao     /usr/bin/updatedb

# No top/htop: coluna NI (Nice)

nice — Iniciar processo com prioridade específica

Iniciar processos com nice definidonice
# Sintaxe: nice -n [valor] comando

# Iniciar backup com baixa prioridade (não atrapalha produção):
nice -n 19 tar czf /backup/site.tar.gz /var/www/
# O backup usa CPU apenas quando ninguém mais precisa

# Iniciar processo com prioridade padrão (nice 0):
nice ./app.sh
# nice sem -n usa 10 por padrão!

# Iniciar com prioridade explícita:
nice -n 10 ./processar-relatorios.sh
nice -n 15 find / -name "*.log" -mtime +30 -delete

# Alta prioridade (requer root):
sudo nice -n -10 ./processo-critico.sh
sudo nice -n -20 ./real-time-processor

# Cenário: compilação pesada sem afetar produção
nice -n 19 make -j$(nproc)
# Usa todos os cores, mas com prioridade mínima

# Cenário: indexação do locate (já usa nice internamente)
nice -n 19 updatedb

renice — Alterar prioridade de processo em execução

Mudar prioridade de processos ativosrenice
# Sintaxe: renice [prioridade] -p PID

# Reduzir prioridade de um processo que está consumindo CPU:
renice 10 -p 12400
# 12400 (process ID) old priority 0, new priority 10

# Aumentar prioridade (requer root):
sudo renice -5 -p 12400
# 12400 (process ID) old priority 10, new priority -5

# Mudar prioridade de TODOS os processos de um usuário:
sudo renice 15 -u joao
# Todos os processos de joao ficam com nice 15

# Mudar prioridade de um grupo:
sudo renice 10 -g devops

# Cenário prático — Processo travando o servidor:
# 1. Identificar o processo pesado:
top     # → vejo que PID 5500 está usando 95% de CPU

# 2. Reduzir prioridade imediatamente:
sudo renice 19 -p 5500
# Sistema volta a responder enquanto o processo continua rodando

# 3. Ou renice pelo htop:
# Selecione o processo → F7 (nice +1) ou F8 (nice -1)

I/O

Redirecionamento de I/O (Introdução)

Todo processo no Linux possui três canais de comunicação padrão: stdin, stdout e stderr. Redirecionar esses canais é uma das habilidades mais poderosas do shell — permite conectar programas, salvar saídas, filtrar erros e automatizar tarefas complexas.

Os três canais padrão (File Descriptors)

Quando qualquer processo inicia, ele automaticamente recebe três "canais" de comunicação:

stdin (FD 0) — Entrada padrãoInput

De onde o processo lê dados de entrada. Por padrão, é o teclado.

# Exemplos de stdin:
cat                  # espera input do teclado
read variavel        # lê uma linha do teclado
grep "erro"          # sem arquivo, lê do stdin

# Redirecionar stdin de arquivo:
cat < arquivo.txt    # lê de arquivo, não teclado
sort < dados.txt     # sort lê de dados.txt
stdout (FD 1) — Saída padrãoOutput

Para onde o processo envia sua saída normal. Por padrão, é o terminal.

# Exemplos de stdout:
echo "hello"         # imprime no terminal
ls -la               # lista no terminal
cat arquivo.txt      # conteúdo no terminal

# Redirecionar stdout para arquivo:
echo "hello" > arquivo.txt
ls -la > listagem.txt
cat /etc/passwd > backup-passwd.txt
stderr (FD 2) — Saída de erroErro

Para onde o processo envia mensagens de erro e diagnóstico. Por padrão, é o terminal (mesmo destino que stdout, mas canal separado).

# Exemplos de stderr:
ls /diretorio-inexistente       # "No such file or directory" vai para stderr
cat arquivo-que-nao-existe      # erro vai para stderr
grep "texto" /sem-permissao     # "Permission denied" vai para stderr

# Por que separar stdout de stderr?
# Permite tratar saída normal e erros de forma diferente:
ls /var /inexistente > saida.txt 2> erros.txt
# stdout (listagem de /var) → saida.txt
# stderr (erro do /inexistente) → erros.txt

# No terminal parece tudo junto, mas são canais diferentes!
Diagrama de fluxo de I/ODiagrama
                    ┌─────────────────────┐
  ┌─────────┐       │                     │       ┌──────────────┐
  │ Teclado │──────▶│  stdin (FD 0)       │       │              │
  │ Arquivo │──────▶│                     │──────▶│ Terminal     │
  │ Pipe    │──────▶│     PROCESSO        │       │ Arquivo      │
  └─────────┘       │                     │──────▶│ Pipe         │
                    │  stdout (FD 1) ─────│──────▶│ /dev/null    │
                    │  stderr (FD 2) ─────│──────▶│              │
                    │                     │       └──────────────┘
                    └─────────────────────┘

  Redirecionamento permite mudar de onde vem (stdin)
  e para onde vai (stdout/stderr) de qualquer processo.

Operadores de Redirecionamento

> — Redirecionar stdout (sobrescrever)Sobrescrever
# Envia stdout para arquivo (CRIA ou SOBRESCREVE):
echo "Linha 1" > arquivo.txt
# arquivo.txt agora contém: "Linha 1"

echo "Linha 2" > arquivo.txt
# arquivo.txt agora contém: "Linha 2"
# ⚠️ "Linha 1" foi PERDIDA!

# Outros exemplos:
ls -la /etc > listagem.txt
date > timestamp.txt
whoami > usuario.txt
cat /etc/passwd > backup-passwd.txt
ps aux > processos.txt

# Criar arquivo vazio:
> arquivo-vazio.txt
# Equivale a: truncate -s 0 arquivo-vazio.txt
>> — Redirecionar stdout (append)Append
# Envia stdout para arquivo (ADICIONA ao final):
echo "Linha 1" > log.txt     # cria com "Linha 1"
echo "Linha 2" >> log.txt    # adiciona "Linha 2"
echo "Linha 3" >> log.txt    # adiciona "Linha 3"

# log.txt agora contém:
# Linha 1
# Linha 2
# Linha 3

# Cenário: construir arquivo incrementalmente
echo "=== Relatório $(date) ===" > relatorio.txt
echo "" >> relatorio.txt
echo "Processos:" >> relatorio.txt
ps aux >> relatorio.txt
echo "" >> relatorio.txt
echo "Disco:" >> relatorio.txt
df -h >> relatorio.txt

# Cenário: log com timestamp
echo "[$(date)] Deploy iniciado" >> /var/log/deploy.log
echo "[$(date)] Deploy finalizado" >> /var/log/deploy.log
2> — Redirecionar stderrErros
# Enviar APENAS erros para arquivo:
find / -name "*.conf" 2> erros.txt
# Resultado no terminal: lista dos .conf encontrados
# erros.txt: "Permission denied" e outros erros

# Descartar erros completamente:
find / -name "*.conf" 2> /dev/null
# Mostra apenas resultados, sem mensagens de erro

# Append de erros:
comando_falho 2>> /var/log/erros.log

# Cenário: script que ignora erros:
rm arquivo-inexistente 2> /dev/null
# Não mostra erro, não interrompe o script

# Separar stdout e stderr em arquivos diferentes:
./meu-script.sh > output.log 2> error.log
# output.log = saída normal
# error.log = apenas erros
2>&1 — Combinar stderr com stdoutCombinar
# Enviar stdout E stderr para o MESMO destino:
./script.sh > tudo.log 2>&1
# stdout → tudo.log
# stderr → vai para onde stdout está → tudo.log

# ⚠️ ORDEM IMPORTA:
# CORRETO: > arquivo 2>&1
./script.sh > log.txt 2>&1     # ✅ ambos vão para log.txt

# ERRADO: 2>&1 > arquivo
./script.sh 2>&1 > log.txt     # ❌ stderr vai pro terminal!
# Porque 2>&1 aponta stderr para onde stdout ESTÁ (terminal)
# Depois > muda stdout para arquivo, mas stderr não acompanha

# Sintaxe moderna (bash 4+):
./script.sh &> tudo.log        # equivale a > tudo.log 2>&1
./script.sh &>> tudo.log       # append de ambos

# Cenário: cron job (capturar toda saída):
0 2 * * * /opt/backup.sh > /var/log/backup.log 2>&1

# Cenário: verificar se comando funciona:
which terraform > /dev/null 2>&1 && echo "Instalado" || echo "Não encontrado"

/dev/null — O buraco negro do Linux

/dev/null — Descartar qualquer saídaDescarte
# /dev/null é um "arquivo" especial que:
# - Aceita qualquer input (descarta tudo)
# - Quando lido, retorna EOF imediatamente

# ═══════════════════════════════════════════════════
# USOS COMUNS:
# ═══════════════════════════════════════════════════

# 1. Silenciar stdout (só ver erros):
apt update > /dev/null
# Mostra apenas erros no terminal

# 2. Silenciar stderr (só ver saída normal):
find / -name "*.log" 2>/dev/null
# Mostra resultados sem "Permission denied"

# 3. Silenciar TUDO (rodar silenciosamente):
./script.sh > /dev/null 2>&1
# Nenhuma saída no terminal (útil em cron)

# 4. Verificar se comando existe (sem output):
which docker > /dev/null 2>&1
if [ $? -eq 0 ]; then
    echo "Docker instalado"
fi

# 5. Esvaziar arquivo sem deletar:
cat /dev/null > /var/log/app.log
# ou simplesmente: > /var/log/app.log
# Arquivo fica com 0 bytes (preserva permissões e inode)

# 6. Gerar "nada" como input:
cat /dev/null | command   # stdin vazio

# 7. Descarte em scripts de deploy:
git pull > /dev/null 2>&1 || { echo "ERRO: git pull falhou"; exit 1; }

# Outro arquivo especial útil:
# /dev/zero — fonte infinita de bytes zero
# /dev/random — fonte de dados aleatórios
# /dev/urandom — fonte rápida de dados pseudo-aleatórios

📋 Resumo dos operadores de redirecionamento: 
comando > arquivo      # stdout → arquivo (sobrescreve)
comando >> arquivo     # stdout → arquivo (append)
comando 2> arquivo     # stderr → arquivo (sobrescreve)
comando 2>> arquivo    # stderr → arquivo (append)
comando &> arquivo     # stdout+stderr → arquivo (sobrescreve)
comando &>> arquivo    # stdout+stderr → arquivo (append)
comando > arq 2>&1     # stdout+stderr → arquivo (compatível)
comando < arquivo      # stdin ← arquivo
comando <<< "string"   # stdin ← string (here string)
comando > /dev/null    # descartar stdout
comando 2> /dev/null   # descartar stderr
comando &> /dev/null   # descartar tudo

Exercício 2: Configurar Permissões de Projeto (Dev + Ops)

Cenário: Configure a estrutura de um projeto web onde:

  • O time de desenvolvimento ("devteam") pode ler e escrever código
  • O time de operações ("ops") pode ler código e executar scripts de deploy
  • O servidor web (www-data) pode apenas ler arquivos estáticos
  • Novos arquivos criados por qualquer dev devem herdar o grupo "devteam"
  • Ninguém de fora dos times pode acessar o projeto
Ver Solução
Solução completaSolução
# 1. Criar grupos:
sudo groupadd devteam
sudo groupadd ops

# 2. Criar estrutura de diretórios:
sudo mkdir -p /srv/projeto/{src,public,scripts,logs}

# 3. Configurar ownership com SGID para herança de grupo:
sudo chown -R root:devteam /srv/projeto
sudo chmod 2770 /srv/projeto        # SGID + rwxrwx---
sudo chmod 2770 /srv/projeto/src    # devs escrevem aqui

# 4. Diretório público (www-data pode ler):
sudo chown root:www-data /srv/projeto/public
sudo chmod 2755 /srv/projeto/public  # SGID + rwxr-xr-x

# 5. Scripts de deploy (ops pode executar):
sudo chown root:ops /srv/projeto/scripts
sudo chmod 2750 /srv/projeto/scripts  # SGID + rwxr-x---

# 6. Logs (ops e devs podem ler):
sudo chown root:devteam /srv/projeto/logs
sudo chmod 2770 /srv/projeto/logs

# 7. Adicionar ops ao grupo devteam para ler código:
sudo usermod -aG devteam operador1

# 8. Permissões de arquivos dentro:
find /srv/projeto/src -type f -exec chmod 660 {} \;
find /srv/projeto/public -type f -exec chmod 644 {} \;
find /srv/projeto/scripts -type f -name "*.sh" -exec chmod 750 {} \;

# 9. Verificação:
ls -la /srv/projeto/
# drwxrws--- 6 root devteam  4096 ... .
# drwxrws--- 2 root devteam  4096 ... src
# drwxr-sr-x 2 root www-data 4096 ... public
# drwxr-s--- 2 root ops      4096 ... scripts
# drwxrws--- 2 root devteam  4096 ... logs

# Teste: dev cria arquivo, grupo é herdado:
su - joao
touch /srv/projeto/src/novo.py
ls -l /srv/projeto/src/novo.py
# -rw-rw---- 1 joao devteam ... novo.py  ✓ grupo herdado!

Exercício 3: Gerenciar Processos (Encontrar, Background, Matar)

Cenário: Um servidor está com problemas de performance. Você precisa:

  • Identificar os 5 processos que mais consomem CPU
  • Encontrar todos os processos do usuário "deploy"
  • Um processo Python está travado — encontre e termine-o gracefully
  • Inicie um monitoramento de logs em background que sobreviva ao logout
  • Reduza a prioridade de um processo de backup que está impactando a aplicação
Ver Solução
Solução completaSolução
# 1. Top 5 processos por CPU:
ps aux --sort=-%cpu | head -6
# (head -6 porque a primeira linha é o cabeçalho)

# Alternativa:
ps -eo pid,user,%cpu,%mem,cmd --sort=-%cpu | head -6

# 2. Processos do usuário "deploy":
ps -u deploy -f
# ou
ps aux | grep "^deploy"

# 3. Encontrar e matar processo Python travado:
# Encontrar:
pgrep -a python
# 15200 python3 process_data.py (este está travado)

# Verificar detalhes:
ps -fp 15200
# UID  PID  PPID  C STIME TTY  TIME     CMD
# deploy 15200 1  0 08:00 ?  02:30:00 python3 process_data.py

# Terminar gracefully (SIGTERM):
kill 15200

# Esperar 10 segundos:
sleep 10

# Verificar se morreu:
ps -p 15200 > /dev/null 2>&1 && echo "Ainda vivo" || echo "Morto"

# Se ainda vivo, forçar:
kill -9 15200

# 4. Monitoramento em background que sobrevive ao logout:
nohup tail -f /var/log/app/production.log > /tmp/monitor-output.log 2>&1 &
# Ou melhor, com timestamp:
nohup sh -c 'tail -f /var/log/app/production.log | while read line; do echo "[$(date +%H:%M:%S)] $line"; done' > /tmp/monitor.log 2>&1 &

# Verificar:
jobs -l
ps aux | grep "tail -f"

# 5. Reduzir prioridade do backup:
# Encontrar processo de backup:
pgrep -a backup
# 18000 /bin/bash /opt/scripts/backup.sh

# Reduzir prioridade:
renice 19 -p 18000
# 18000 (process ID) old priority 0, new priority 19

# Também reduzir I/O priority:
sudo ionice -c3 -p 18000

# Verificar:
ps -o pid,ni,cmd -p 18000
#   PID  NI CMD
# 18000  19 /bin/bash /opt/scripts/backup.sh  ✓

Exercício 4: Redirecionamento de Logs

Cenário: Você precisa configurar o logging de uma aplicação:

  • Executar um script de health check que salva stdout em success.log e stderr em errors.log
  • Criar um script de monitoramento que descarta stdout mas salva erros
  • Combinar logs de múltiplos serviços em um único arquivo com timestamp
  • Esvaziar um log que cresceu demais sem deletar o arquivo
Ver Solução
Solução completaSolução
# 1. Health check com stdout e stderr separados:
/opt/scripts/health-check.sh > /var/log/health/success.log 2> /var/log/health/errors.log

# Com append (para cron job que roda a cada minuto):
/opt/scripts/health-check.sh >> /var/log/health/success.log 2>> /var/log/health/errors.log

# Em cron:
# */1 * * * * /opt/scripts/health-check.sh >> /var/log/health/success.log 2>> /var/log/health/errors.log

# 2. Monitoramento que descarta stdout mas salva erros:
/opt/scripts/monitor-services.sh > /dev/null 2>> /var/log/monitor-errors.log

# Com timestamp em cada erro:
/opt/scripts/monitor-services.sh > /dev/null 2>&1 | \
  while read line; do echo "[$(date '+%F %T')] $line"; done >> /var/log/monitor-errors.log

# Alternativa mais simples:
/opt/scripts/monitor-services.sh > /dev/null 2>> >(while read l; do echo "$(date +%F_%T) $l"; done >> /var/log/monitor-errors.log)

# 3. Combinar logs de múltiplos serviços:
{
  echo "=== NGINX ===" 
  tail -5 /var/log/nginx/error.log 2>/dev/null
  echo ""
  echo "=== APP ===" 
  tail -5 /var/log/app/production.log 2>/dev/null
  echo ""
  echo "=== DATABASE ===" 
  tail -5 /var/log/postgresql/postgresql-main.log 2>/dev/null
} > /tmp/combined-status-$(date +%Y%m%d_%H%M%S).log

# Script de coleta com timestamp:
#!/bin/bash
LOG="/var/log/services-combined.log"
echo "[$(date)] === Coleta de logs ===" >> $LOG
echo "[$(date)] --- Nginx ---" >> $LOG
tail -20 /var/log/nginx/error.log >> $LOG 2>&1
echo "[$(date)] --- App ---" >> $LOG
tail -20 /var/log/app/error.log >> $LOG 2>&1
echo "[$(date)] === Fim ===" >> $LOG

# 4. Esvaziar log sem deletar (preserva inode, permissões, ownership):
# Método 1 — Mais usado:
> /var/log/app/huge-log.log

# Método 2 — Explícito:
cat /dev/null > /var/log/app/huge-log.log

# Método 3 — Com truncate:
truncate -s 0 /var/log/app/huge-log.log

# Método 4 — Manter últimas 1000 linhas:
tail -1000 /var/log/app/huge-log.log > /tmp/temp-log.txt
cat /tmp/temp-log.txt > /var/log/app/huge-log.log
rm /tmp/temp-log.txt

# Verificar resultado:
ls -l /var/log/app/huge-log.log
# -rw-r--r-- 1 app app 0 Jan 15 15:00 huge-log.log
# Tamanho zerado, mas arquivo preservado!
