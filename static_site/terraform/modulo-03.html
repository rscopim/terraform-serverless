1. Locals — Tags e Valores Computados

O bloco locals permite definir valores intermediários que simplificam seu código, eliminam repetição e criam uma camada de abstração entre variáveis brutas e recursos. Pense neles como "variáveis privadas" do seu módulo.

1.1 O que são Locals?

No Terraform, variable é a porta de entrada de dados (vem de fora). local é um valor computado internamente — não pode ser definido pelo usuário, apenas pelo código. É o lugar perfeito para transformações, concatenações e valores derivados.

🏭 Analogia — A Linha de Montagem:

Imagine uma fábrica: as variables são as matérias-primas que chegam de fornecedores externos (inputs). Os locals são as peças intermediárias fabricadas internamente — combinando matérias-primas para criar componentes prontos para uso. Os resources são os produtos finais montados com essas peças.

Locals vs Variables — Quando usar cada umConceito
# ═══════════════════════════════════════════════════════════════
# VARIABLES — Inputs do módulo (configuráveis pelo usuário)
# Pertencem à INTERFACE PÚBLICA do módulo
# ═══════════════════════════════════════════════════════════════
variable "environment" {
  description = "Ambiente de deploy (dev, staging, prod)"
  type        = string
  default     = "dev"
}

variable "project" {
  description = "Nome do projeto"
  type        = string
}

variable "region" {
  description = "Região AWS"
  type        = string
  default     = "us-east-1"
}

# ═══════════════════════════════════════════════════════════════
# LOCALS — Valores computados internamente (privados ao módulo)
# NÃO podem ser sobrescritos de fora
# ═══════════════════════════════════════════════════════════════
locals {
  # Valor derivado (concatenação de inputs)
  name_prefix = "${var.project}-${var.environment}"

  # Lógica condicional
  is_production = var.environment == "prod"

  # Mapa computado a partir de inputs
  instance_type = local.is_production ? "t3.large" : "t3.micro"

  # Tags reutilizáveis (DRY principle)
  common_tags = {
    Project     = var.project
    Environment = var.environment
    ManagedBy   = "terraform"
    Team        = "platform"
  }
}

1.2 Princípio DRY com Locals

O princípio DRY (Don't Repeat Yourself) é fundamental em qualquer código. Com locals, você define um valor UMA vez e referencia em dezenas de recursos. Se precisar mudar, altera em um único lugar.

DRY com Locals — Antes vs DepoisRefatoração
# ═══════════════════════════════════════════════════════════════
# ❌ ANTES (sem locals) — Repetição em todo lugar
# Se o formato do nome mudar, precisa alterar em 15+ recursos!
# ═══════════════════════════════════════════════════════════════
resource "aws_security_group" "web" {
  name = "myapp-prod-web-sg"  # Repetindo projeto + env + tipo
  tags = {
    Project     = "myapp"       # Repetindo
    Environment = "prod"        # Repetindo
    ManagedBy   = "terraform"   # Repetindo
  }
}

resource "aws_instance" "web" {
  tags = {
    Name        = "myapp-prod-web-server"  # Repetindo padrão
    Project     = "myapp"                  # Repetindo
    Environment = "prod"                   # Repetindo
    ManagedBy   = "terraform"              # Repetindo
  }
}

# ═══════════════════════════════════════════════════════════════
# ✅ DEPOIS (com locals) — Zero repetição, fácil manutenção
# ═══════════════════════════════════════════════════════════════
locals {
  name_prefix = "${var.project}-${var.environment}"

  common_tags = {
    Project     = var.project
    Environment = var.environment
    ManagedBy   = "terraform"
    Team        = var.team
    CostCenter  = var.cost_center
  }
}

resource "aws_security_group" "web" {
  name = "${local.name_prefix}-web-sg"
  tags = merge(local.common_tags, { Name = "${local.name_prefix}-web-sg" })
}

resource "aws_instance" "web" {
  tags = merge(local.common_tags, { Name = "${local.name_prefix}-web-server" })
}

# Resultado: se mudar var.project ou var.environment,
# TODOS os recursos são atualizados automaticamente!

1.3 Locals Avançados — Transformações e Lógica

Locals não são apenas para strings simples. Você pode usar funções, condicionais, loops e até data sources dentro deles:

Locals Avançados — Computações ComplexasAvançado
# ═══════════════════════════════════════════════════════════════
# Locals com lógica complexa para um projeto real
# ═══════════════════════════════════════════════════════════════
locals {
  # ─── Informações da conta ─────────────────────────────────────
  account_id = data.aws_caller_identity.current.account_id
  region     = data.aws_region.current.name

  # ─── Lógica condicional ───────────────────────────────────────
  is_production  = var.environment == "prod"
  is_development = var.environment == "dev"

  # ─── Sizing baseado no ambiente ───────────────────────────────
  db_instance_class = local.is_production ? "db.r6g.large" : "db.t3.micro"
  db_multi_az       = local.is_production ? true : false
  db_backup_days    = local.is_production ? 35 : 7

  # ─── CIDR blocks computados ───────────────────────────────────
  vpc_cidr = "10.${var.environment == "prod" ? 0 : 1}.0.0/16"

  public_subnets = [
    for i, az in data.aws_availability_zones.available.names :
    cidrsubnet(local.vpc_cidr, 8, i)
  ]

  private_subnets = [
    for i, az in data.aws_availability_zones.available.names :
    cidrsubnet(local.vpc_cidr, 8, i + 100)
  ]

  # ─── Tags computadas com timestamp ───────────────────────────
  common_tags = merge(
    {
      Project     = var.project
      Environment = var.environment
      ManagedBy   = "terraform"
      Region      = local.region
      AccountId   = local.account_id
    },
    var.extra_tags  # Tags adicionais passadas como variável
  )

  # ─── Naming conventions ───────────────────────────────────────
  resource_name = "${var.project}-${var.environment}-${local.region}"
}
⚠️ Cuidado com Locals Excessivos:

Não crie locals para TUDO. Se um valor é usado apenas uma vez, não precisa de local. Use locals quando: (1) o valor é usado em 2+ recursos, (2) há lógica/transformação envolvida, ou (3) melhora a legibilidade significativamente.

2. IAM — Identity and Access Management

IAM é o sistema nervoso de segurança da AWS. Controla QUEM pode fazer O QUÊ em QUAIS recursos. Sem IAM bem configurado, sua infraestrutura é uma casa com todas as portas abertas.

2.1 Conceitos Fundamentais do IAM

Antes de criar policies com Terraform, é essencial entender profundamente como IAM funciona. Vamos usar uma analogia completa.

🏢 Analogia — O Prédio Corporativo:

Imagine a AWS como um enorme prédio corporativo com centenas de salas (serviços). O IAM é o sistema de segurança desse prédio:

  • Users = Funcionários com crachá pessoal (pessoas reais)
  • Groups = Departamentos (Marketing, TI, Financeiro) — permissões em lote
  • Roles = Crachás temporários para visitantes ou robôs (serviços AWS)
  • Policies = Regras escritas no crachá ("pode entrar na sala 301, mas só para ler documentos")
  • Principal = Qualquer entidade que pode autenticar (user, role, account, service)

2.2 Princípio de Menor Privilégio (Least Privilege)

A regra de ouro do IAM: conceda apenas as permissões mínimas necessárias para realizar uma tarefa. Nunca use * em produção sem justificativa documentada.

Evolução de uma Policy — Do Pior ao MelhorBoas Práticas
# ═══════════════════════════════════════════════════════════════
# ❌ NÍVEL 1 — Admin (NUNCA em produção para serviços)
# Dá acesso a TUDO. Se comprometido, atacante controla a conta inteira.
# ═══════════════════════════════════════════════════════════════
{
  "Effect": "Allow",
  "Action": "*",
  "Resource": "*"
}

# ═══════════════════════════════════════════════════════════════
# ⚠️ NÍVEL 2 — Serviço amplo (ainda ruim)
# Limita ao serviço S3, mas permite TUDO no S3 (delete, create bucket...)
# ═══════════════════════════════════════════════════════════════
{
  "Effect": "Allow",
  "Action": "s3:*",
  "Resource": "*"
}

# ═══════════════════════════════════════════════════════════════
# ✅ NÍVEL 3 — Ação específica + recurso específico (CORRETO)
# Só pode ler objetos de UM bucket específico. Nada mais.
# ═══════════════════════════════════════════════════════════════
{
  "Effect": "Allow",
  "Action": [
    "s3:GetObject",
    "s3:ListBucket"
  ],
  "Resource": [
    "arn:aws:s3:::meu-bucket-app",
    "arn:aws:s3:::meu-bucket-app/*"
  ]
}

# ═══════════════════════════════════════════════════════════════
# 🏆 NÍVEL 4 — Com conditions (EXCELENTE)
# Mesmo nível 3, mas só funciona se a request vier de uma VPC específica
# ═══════════════════════════════════════════════════════════════
{
  "Effect": "Allow",
  "Action": ["s3:GetObject"],
  "Resource": ["arn:aws:s3:::meu-bucket-app/*"],
  "Condition": {
    "StringEquals": {
      "aws:SourceVpc": "vpc-0abc123def456"
    }
  }
}

2.3 Estrutura de um Policy Document

Toda IAM Policy segue a mesma estrutura JSON. Entender cada campo é essencial para criar policies corretas:

Anatomia Completa de um Policy DocumentReferência
{
  "Version": "2012-10-17",          // Sempre use esta versão (mais recente)
  "Statement": [
    {
      // ─── SID (Statement ID) ─────────────────────────────────
      // Identificador opcional, mas recomendado para legibilidade
      "Sid": "AllowS3ReadAccess",

      // ─── EFFECT ─────────────────────────────────────────────
      // "Allow" = Permitir  |  "Deny" = Negar (Deny SEMPRE vence)
      "Effect": "Allow",

      // ─── PRINCIPAL ──────────────────────────────────────────
      // QUEM pode executar (só em resource-based policies)
      // Em identity-based policies, o principal é implícito (quem tem a policy)
      // "Principal": {"Service": "lambda.amazonaws.com"},
      // "Principal": {"AWS": "arn:aws:iam::123456789012:role/MyRole"},
      // "Principal": "*",  ← Qualquer um (CUIDADO!)

      // ─── ACTION ─────────────────────────────────────────────
      // O QUE pode fazer (API calls específicas)
      "Action": [
        "s3:GetObject",           // Ler objetos
        "s3:PutObject",           // Escrever objetos
        "s3:ListBucket",          // Listar conteúdo do bucket
        "s3:DeleteObject"         // Deletar objetos
      ],
      // Wildcards: "s3:Get*" = todas as ações Get do S3
      // "s3:*" = TODAS as ações do S3 (evitar!)

      // ─── RESOURCE ───────────────────────────────────────────
      // EM QUAIS recursos (ARNs específicos)
      "Resource": [
        "arn:aws:s3:::meu-bucket",      // O bucket em si (para ListBucket)
        "arn:aws:s3:::meu-bucket/*"     // Objetos dentro (para Get/Put/Delete)
      ],
      // "*" = todos os recursos (evitar em produção!)

      // ─── CONDITION ──────────────────────────────────────────
      // Condições extras (opcional, mas poderoso)
      "Condition": {
        "StringEquals": {
          "s3:prefix": ["uploads/", "reports/"]   // Só essas pastas
        },
        "IpAddress": {
          "aws:SourceIp": "10.0.0.0/8"           // Só da rede interna
        },
        "Bool": {
          "aws:SecureTransport": "true"           // Só via HTTPS
        }
      }
    }
  ]
}
📋 Regras de Avaliação de Policies:
  • Deny Explícito SEMPRE vence sobre Allow (em qualquer policy)
  • Sem permissão = Deny implícito (tudo é negado por padrão)
  • Múltiplas policies são avaliadas juntas (union de Allows, intersection com Denys)
  • Resource-based + Identity-based = ambas precisam Allow (exceto mesmo account)

3. IAM Roles e Policies com Terraform

Agora vamos traduzir os conceitos IAM em código Terraform. Cada recurso tem um papel específico na cadeia de confiança e permissões.

3.1 Trust Relationship — Quem pode "vestir" a Role

Uma IAM Role é como um crachá de visitante. Antes de alguém usá-lo, precisa existir uma trust relationship (política de confiança) que define QUEM pode assumir essa role.

Trust Relationship — Diagrama de FluxoConceitual

# FLUXO DE ASSUME ROLE:
#
#   ┌──────────┐      "Posso usar      ┌──────────────┐
#   │ SERVIÇO  │  ──────essa role?────▶ │   IAM ROLE   │
#   │ (Lambda) │                        │──────────────│
#   └──────────┘                        │ Trust Policy │
#                                       │ (assume_role)│
#        ▲                              └──────┬───────┘
#        │                                     │
#        │  ✅ "Sim, Lambda está               │
#        │     na trust policy"                 ▼
#        │                              ┌──────────────┐

#        └──── recebe credenciais ──────│   POLICIES   │

3.2 aws_iam_role — Criando uma Role

O recurso aws_iam_role cria a role e define sua trust policy (quem pode assumir). É o primeiro passo.

aws_iam_role — Role para LambdaTerraform
# ═══════════════════════════════════════════════════════════════
# IAM Role que pode ser assumida pelo serviço Lambda
# ═══════════════════════════════════════════════════════════════
resource "aws_iam_role" "lambda_execution" {
  name = "${local.name_prefix}-lambda-exec-role"

  # Trust Policy — Define QUEM pode assumir esta role
  # Neste caso: o serviço Lambda da AWS
  assume_role_policy = jsonencode({
    Version = "2012-10-17"
    Statement = [
      {
        Sid    = "AllowLambdaAssume"
        Effect = "Allow"
        Principal = {
          Service = "lambda.amazonaws.com"  # Serviço Lambda
        }
        Action = "sts:AssumeRole"
      }
    ]
  })

  # Tags para organização
  tags = merge(local.common_tags, {
    Name = "${local.name_prefix}-lambda-exec-role"
    Role = "lambda-execution"
  })
}

# ═══════════════════════════════════════════════════════════════
# IAM Role para EC2 (Instance Profile)
# ═══════════════════════════════════════════════════════════════
resource "aws_iam_role" "ec2_app" {
  name = "${local.name_prefix}-ec2-app-role"

  assume_role_policy = jsonencode({
    Version = "2012-10-17"
    Statement = [
      {
        Sid    = "AllowEC2Assume"
        Effect = "Allow"
        Principal = {
          Service = "ec2.amazonaws.com"  # Serviço EC2
        }
        Action = "sts:AssumeRole"
      }
    ]
  })

  tags = merge(local.common_tags, {
    Name = "${local.name_prefix}-ec2-app-role"
  })
}

3.3 aws_iam_policy — Definindo Permissões

Depois de criar a role, precisamos definir O QUE ela pode fazer. Isso é feito com aws_iam_policy:

aws_iam_policy — Policies CustomizadasTerraform
# ═══════════════════════════════════════════════════════════════
# Policy customizada — Lambda pode ler S3 e escrever logs
# ═══════════════════════════════════════════════════════════════
resource "aws_iam_policy" "lambda_s3_logs" {
  name        = "${local.name_prefix}-lambda-s3-logs"
  description = "Permite Lambda ler S3 e escrever CloudWatch Logs"
  path        = "/app/"  # Organiza policies em "pastas" no IAM

  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [
      {
        Sid    = "CloudWatchLogs"
        Effect = "Allow"
        Action = [
          "logs:CreateLogGroup",
          "logs:CreateLogStream",
          "logs:PutLogEvents"
        ]
        Resource = "arn:aws:logs:${local.region}:${local.account_id}:*"
      },
      {
        Sid    = "S3ReadOnly"
        Effect = "Allow"
        Action = [
          "s3:GetObject",
          "s3:ListBucket"
        ]
        Resource = [
          aws_s3_bucket.app_data.arn,
          "${aws_s3_bucket.app_data.arn}/*"
        ]
      }
    ]
  })

  tags = merge(local.common_tags, {
    Name = "${local.name_prefix}-lambda-s3-logs"
  })
}

# ═══════════════════════════════════════════════════════════════
# Policy para EC2 — Acessar Secrets Manager e SSM
# ═══════════════════════════════════════════════════════════════
resource "aws_iam_policy" "ec2_secrets_access" {
  name        = "${local.name_prefix}-ec2-secrets"
  description = "Permite EC2 ler segredos da aplicação"

  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [
      {
        Sid    = "ReadAppSecrets"
        Effect = "Allow"
        Action = [
          "secretsmanager:GetSecretValue",
          "secretsmanager:DescribeSecret"
        ]
        Resource = [
          "arn:aws:secretsmanager:${local.region}:${local.account_id}:secret:${local.name_prefix}/*"
        ]
      },
      {
        Sid    = "ReadSSMParameters"
        Effect = "Allow"
        Action = [
          "ssm:GetParameter",
          "ssm:GetParameters",
          "ssm:GetParametersByPath"
        ]
        Resource = [
          "arn:aws:ssm:${local.region}:${local.account_id}:parameter/${var.project}/${var.environment}/*"
        ]
      }
    ]
  })

  tags = local.common_tags
}

3.5 aws_iam_instance_profile — IAM para EC2

EC2 instances não usam roles diretamente. Elas precisam de um Instance Profile — um "wrapper" que permite à instância assumir a role:

Instance Profile — Ponte entre EC2 e IAM RoleTerraform
# ═══════════════════════════════════════════════════════════════
# Instance Profile é o "adaptador" entre EC2 e IAM Role
#
#   EC2 Instance ──▶ Instance Profile ──▶ IAM Role ──▶ Policies
#
# Sem Instance Profile, a EC2 NÃO consegue assumir a role!
# ═══════════════════════════════════════════════════════════════

Banco de Dados

5. RDS — Banco de Dados Relacional

O Amazon RDS (Relational Database Service) gerencia bancos de dados para você — patching, backups, failover, replicação. Você foca no schema e nas queries, a AWS cuida da infraestrutura.

5.1 O que é RDS e por que usar?

Instalar e manter um banco de dados em EC2 exige trabalho significativo: patching do OS e do DB, configurar backups, monitorar disco, gerenciar failover. O RDS automatiza tudo isso.

🏨 Analogia — Hotel vs Acampar:

Banco de dados em EC2 é como acampar: você monta a barraca, faz o fogo, busca água, limpa tudo. RDS é como um hotel: você chega, usa o quarto (banco), e o hotel cuida de limpeza (patching), café da manhã (backups), e segurança (monitoramento). Você paga um pouco mais, mas seu tempo vai para o que importa.

Segurança de Rede

7. Security Group para RDS

O Security Group do banco de dados é a primeira linha de defesa. Ele deve ser o mais restritivo possível: apenas a aplicação pode acessar o banco, e o banco NUNCA tem acesso à internet.

7.1 Princípio: Cross-Reference Security Groups

Em vez de liberar CIDRs (faixas de IP), referencie o Security Group da aplicação. Assim, qualquer instância que pertença ao SG da app automaticamente ganha acesso ao banco:

Arquitetura de SGs — App → DatabaseDiagrama
# ═══════════════════════════════════════════════════════════════
# CROSS-REFERENCE SECURITY GROUPS
# ═══════════════════════════════════════════════════════════════
#
#   Internet
#      │
#      ▼
#  ┌──────────────────────┐
#  │   ALB Security Group │  ← Aceita 80/443 de 0.0.0.0/0
#  │   (sg-alb-xxxxx)     │
#  └──────────┬───────────┘
#             │ porta 8080
#             ▼
#  ┌──────────────────────┐
#  │   App Security Group │  ← Aceita APENAS de sg-alb
#  │   (sg-app-xxxxx)     │
#  └──────────┬───────────┘
#             │ porta 5432
#             ▼
#  ┌──────────────────────┐
#  │    DB Security Group │  ← Aceita APENAS de sg-app
#  │   (sg-db-xxxxx)      │  ← SEM acesso à internet (sem egress 0.0.0.0/0)
#  └──────────────────────┘
#
# RESULTADO:
# • Atacante na internet NÃO acessa a app diretamente
# • App NÃO acessa o banco se não estiver no SG correto
# • Banco NÃO tem acesso à internet (nenhuma rota de saída)
# • Se escalar para 10 instâncias de app, TODAS acessam o DB
#   automaticamente (pertencem ao mesmo SG)
# ═══════════════════════════════════════════════════════════════

7.3 Rede Completa para RDS — Sem Acesso à Internet

O RDS deve viver em subnets privadas sem rota para internet. Aqui está a configuração de rede completa:

Route Table Privada — Sem Internet GatewayTerraform
# ═══════════════════════════════════════════════════════════════
# Route Table para subnets de banco de dados
# NENHUMA rota para Internet Gateway ou NAT Gateway!
# ═══════════════════════════════════════════════════════════════
resource "aws_route_table" "database" {
  vpc_id = aws_vpc.main.id

  # Sem nenhuma rota externa — apenas tráfego local da VPC
  # A rota local (10.0.0.0/16 → local) é adicionada automaticamente

  tags = merge(local.common_tags, {
    Name = "${local.name_prefix}-db-rt"
    Tier = "database"
  })
}

# Associar subnets de banco à route table isolada
resource "aws_route_table_association" "database" {
  count          = length(aws_subnet.database)
  subnet_id      = aws_subnet.database[count.index].id
  route_table_id = aws_route_table.database.id
}

# ═══════════════════════════════════════════════════════════════
# Network ACL extra (camada adicional de defesa)
# ═══════════════════════════════════════════════════════════════
resource "aws_network_acl" "database" {
  vpc_id     = aws_vpc.main.id
  subnet_ids = aws_subnet.database[*].id

  # Permitir PostgreSQL APENAS das subnets da app
  ingress {
    protocol   = "tcp"
    rule_no    = 100
    action     = "allow"
    cidr_block = "10.0.0.0/24"  # Subnet da app (ajustar conforme seu CIDR)
    from_port  = 5432
    to_port    = 5432
  }

  # Ephemeral ports para resposta
  egress {
    protocol   = "tcp"
    rule_no    = 100
    action     = "allow"
    cidr_block = "10.0.0.0/24"
    from_port  = 1024
    to_port    = 65535
  }

  # Deny explícito para todo o resto
  ingress {
    protocol   = "-1"
    rule_no    = 999
    action     = "deny"
    cidr_block = "0.0.0.0/0"
    from_port  = 0
    to_port    = 0
  }

  egress {
    protocol   = "-1"
    rule_no    = 999
    action     = "deny"
    cidr_block = "0.0.0.0/0"
    from_port  = 0
    to_port    = 0
  }

  tags = merge(local.common_tags, {
    Name = "${local.name_prefix}-db-nacl"
  })
}
⚠️ Defesa em Profundidade:

Segurança de banco de dados usa múltiplas camadas: (1) Subnet privada sem rota para internet, (2) Security Group restritivo, (3) Network ACL, (4) Senha forte com rotação, (5) SSL obrigatório, (6) deletion_protection. Se uma camada falhar, as outras ainda protegem o banco.

Segredos

8. Gerenciamento de Segredos

Senhas, API keys, tokens e certificados são os dados mais sensíveis da sua infraestrutura. Nunca devem estar em código, variáveis de ambiente estáticas ou repositórios Git. Vamos explorar as opções seguras.

8.1 Por que NUNCA Hardcode?

Colocar segredos diretamente no código (hardcode) é o erro mais perigoso que existe em infraestrutura:

O Desastre do Hardcode — Cenário RealPERIGO
# ═══════════════════════════════════════════════════════════════
# ❌ NUNCA FAÇA ISSO — Hardcode de segredos
# ═══════════════════════════════════════════════════════════════

# CENÁRIO: Dev coloca senha no código "temporariamente"
resource "aws_db_instance" "main" {
  username = "admin"
  password = "SuperSecreta123!"   # ← DESASTRE POTENCIAL
}

# O QUE ACONTECE:
# 1. Código vai para o Git (git add . → git push)
# 2. Mesmo se remover depois, fica no histórico do Git PARA SEMPRE
# 3. terraform.tfstate armazena o valor em PLAIN TEXT
# 4. Se state está em S3, qualquer pessoa com acesso ao bucket lê a senha
# 5. Bots escaneiam repositórios públicos em segundos buscando credentials
# 6. Resultado: banco comprometido, dados vazados, empresa na mídia
#
# IMPACTO REAL (casos documentados):
# • Uber (2016): Credenciais no GitHub → dados de 57M usuários
# • Capital One (2019): Credenciais IAM expostas → 100M registros
# • Samsung (2022): Credenciais hardcoded → código fonte vazado
#
# ═══════════════════════════════════════════════════════════════
# ✅ O QUE FAZER INSTEAD:
# ═══════════════════════════════════════════════════════════════
#
# Opção 1: AWS gerencia a senha
resource "aws_db_instance" "main" {
  manage_master_user_password = true  # AWS cria e rotaciona
}
#
# Opção 2: Referência ao Secrets Manager
resource "aws_db_instance" "main" {
  password = data.aws_secretsmanager_secret_version.db.secret_string
}
#
# Opção 3: Variable com sensitive = true (mínimo aceitável)
resource "aws_db_instance" "main" {
  password = var.db_password  # Passado via -var ou TF_VAR_
}

8.3 Método 1: Variables com sensitive = true

O método mais simples. O valor não aparece no terminal durante plan/apply, mas AINDA está no state file:

Variable Sensitive — Mínimo AceitávelBásico

# variables.tf — Definição com sensitive = true
# ═══════════════════════════════════════════════════════════════
variable "db_password" {
  description = "Senha master do banco de dados"
  type        = string
  sensitive   = true  # Oculta em plan/apply output

  validation {
    condition     = length(var.db_password) >= 16
    error_message = "Senha deve ter no mínimo 16 caracteres."
  }
}

variable "api_key" {
  description = "Chave da API externa"
  type        = string
  sensitive   = true
}

# ═══════════════════════════════════════════════════════════════
# COMO PASSAR O VALOR (sem colocar no código):
# ═══════════════════════════════════════════════════════════════

# Opção A: Variável de ambiente (CI/CD)
# export TF_VAR_db_password="MinhaSenh@Forte2024!"
# terraform apply

# Opção B: Flag -var (interativo)
# terraform apply -var="db_password=MinhaSenh@Forte2024!"

# Opção C: Arquivo .tfvars NÃO versionado
# terraform apply -var-file="secrets.tfvars"
#
# secrets.tfvars (NO .gitignore!):
# db_password = "MinhaSenh@Forte2024!"
# api_key     = "sk-1234567890abcdef"

# ═══════════════════════════════════════════════════════════════
# .gitignore OBRIGATÓRIO:
# ═══════════════════════════════════════════════════════════════
# *.tfvars       ← TODOS os .tfvars (ou pelo menos secrets.tfvars)
# .terraform/
# *.tfstate
# *.tfstate.backup
⚠️ Limitação de sensitive = true:

O atributo sensitive = true apenas oculta o valor no OUTPUT do terminal. O valor AINDA é armazenado em plain text no arquivo terraform.tfstate! Por isso, sempre use backend remoto (S3) com encriptação e controle de acesso rigoroso para o state file.

9. aws_secretsmanager_secret

AWS Secrets Manager é a solução enterprise para segredos: rotação automática, versionamento, auditoria via CloudTrail, e integração nativa com RDS, Redshift e DocumentDB.

9.1 Criar Segredos com Terraform

No Secrets Manager, a criação é feita em dois passos: (1) criar o "container" (secret), (2) criar o "conteúdo" (version):

Secrets Manager — Criar e PopularTerraform
# ═══════════════════════════════════════════════════════════════
# PASSO 1: Criar o Secret (container)
# ═══════════════════════════════════════════════════════════════
resource "aws_secretsmanager_secret" "db_credentials" {
  name        = "${local.name_prefix}/db/credentials"
  description = "Credenciais master do banco PostgreSQL"

  # Encriptação com KMS key customizada (recomendado)
  kms_key_id = aws_kms_key.secrets.arn

  # Dias para recuperação após deletar (proteção contra exclusão acidental)
  recovery_window_in_days = local.is_production ? 30 : 7

  # Forçar delete sem recovery (APENAS para dev/testes)
  # force_overwrite_replica_secret = true

  tags = merge(local.common_tags, {
    Name        = "${local.name_prefix}/db/credentials"
    AutoRotate  = "true"
    Application = var.project
  })
}

# ═══════════════════════════════════════════════════════════════
# PASSO 2: Popular com o valor (version)
# ═══════════════════════════════════════════════════════════════
resource "aws_secretsmanager_secret_version" "db_credentials" {
  secret_id = aws_secretsmanager_secret.db_credentials.id

  # Valor do segredo — formato JSON para múltiplos campos
  secret_string = jsonencode({
    username = aws_db_instance.main.username
    password = var.db_password
    engine   = "postgres"
    host     = aws_db_instance.main.address
    port     = aws_db_instance.main.port
    dbname   = aws_db_instance.main.db_name
    # URL completa para facilitar uso em aplicações

9.3 Rotação Automática de Segredos

A rotação automática é o grande diferencial do Secrets Manager em relação ao SSM Parameter Store. Uma Lambda rotaciona a senha periodicamente sem downtime:

Rotação Automática — Lambda + Secrets ManagerAvançado
# ═══════════════════════════════════════════════════════════════
# Rotação automática de senha do RDS
# A AWS fornece Lambdas prontas para RDS!
# ═══════════════════════════════════════════════════════════════

# Configurar rotação automática
resource "aws_secretsmanager_secret_rotation" "db_credentials" {
  secret_id           = aws_secretsmanager_secret.db_credentials.id
  rotation_lambda_arn = aws_lambda_function.secret_rotation.arn

  rotation_rules {
    # Rotacionar a cada 30 dias
    automatically_after_days = 30
    # schedule_expression = "rate(30 days)"  # Alternativa com cron
  }
}

# ═══════════════════════════════════════════════════════════════
# Lambda de rotação (AWS fornece templates prontos)
# ═══════════════════════════════════════════════════════════════
resource "aws_lambda_function" "secret_rotation" {
  function_name = "${local.name_prefix}-secret-rotation"
  description   = "Rotaciona senha do RDS PostgreSQL"

  # AWS mantém um repositório com rotation lambdas prontas
  # https://github.com/aws-samples/aws-secrets-manager-rotation-lambdas
  filename         = data.archive_file.rotation_lambda.output_path
  source_code_hash = data.archive_file.rotation_lambda.output_base64sha256
  handler          = "lambda_function.lambda_handler"
  runtime          = "python3.11"
  timeout          = 30

  role = aws_iam_role.rotation_lambda.arn

  # A Lambda precisa acessar o banco e o Secrets Manager
  vpc_config {
    subnet_ids         = aws_subnet.private[*].id
    security_group_ids = [aws_security_group.rotation_lambda.id]
  }

  environment {
    variables = {
      SECRETS_MANAGER_ENDPOINT = "https://secretsmanager.${local.region}.amazonaws.com"
    }
  }

  tags = local.common_tags
}

# Permissão para Secrets Manager invocar a Lambda
resource "aws_lambda_permission" "secrets_manager" {
  statement_id  = "AllowSecretsManagerInvoke"
  action        = "lambda:InvokeFunction"
  function_name = aws_lambda_function.secret_rotation.function_name
  principal     = "secretsmanager.amazonaws.com"
}

# ═══════════════════════════════════════════════════════════════
# FLUXO DA ROTAÇÃO:
#
#  Secrets Manager → Invoca Lambda → Lambda:
#    1. create_secret: Gera nova senha
#    2. set_secret: Atualiza no RDS (ALTER USER ... PASSWORD)
#    3. test_secret: Testa conexão com nova senha
#    4. finish_secret: Promove nova versão como AWSCURRENT
#
#  Se qualquer etapa falhar → rollback para senha anterior
#  Aplicações buscam AWSCURRENT → sempre pegam a senha válida
# ═══════════════════════════════════════════════════════════════
💡 Alternativa mais simples — manage_master_user_password:

Se seu objetivo é apenas rotacionar a senha do RDS, use manage_master_user_password = true no recurso aws_db_instance. A AWS cuida de TUDO: cria o secret, configura a Lambda de rotação e gerencia as versões. Você não precisa criar nada disso manualmente!

9.4 KMS Key para Encriptação de Segredos

Por padrão, Secrets Manager usa a key aws/secretsmanager. Para produção, crie uma KMS key dedicada com política de acesso restrita:

KMS Key Dedicada para SecretsTerraform
# ═══════════════════════════════════════════════════════════════
# KMS Key para encriptar segredos da aplicação
# ═══════════════════════════════════════════════════════════════
resource "aws_kms_key" "secrets" {
  description             = "KMS key para segredos do ${var.project}"
  deletion_window_in_days = 30
  enable_key_rotation     = true  # Rotação anual automática da key material

  # Policy da key — quem pode usar e administrar
  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [
      {
        Sid    = "EnableRootAccountFullAccess"
        Effect = "Allow"
        Principal = {
          AWS = "arn:aws:iam::${local.account_id}:root"
        }
        Action   = "kms:*"
        Resource = "*"
      },
      {
        Sid    = "AllowAppRolesToDecrypt"
        Effect = "Allow"
        Principal = {
          AWS = [
            aws_iam_role.ec2_app.arn,
            aws_iam_role.lambda_execution.arn,
            aws_iam_role.ecs_task_execution.arn
          ]
        }
        Action = [
          "kms:Decrypt",
          "kms:DescribeKey"
        ]
        Resource = "*"
      }
    ]
  })

  tags = merge(local.common_tags, {
    Name = "${local.name_prefix}-secrets-key"
  })
}

10. Outputs Sensíveis

Outputs no Terraform expõem valores para uso externo (outros módulos, CI/CD, humanos). Quando o valor é sensível, precisamos de cuidados extras para não vazar informações.

10.1 sensitive = true em Outputs

Assim como variáveis, outputs podem ser marcados como sensíveis. Isso oculta o valor no terminal mas mantém disponível programaticamente:

Outputs Sensíveis — Definição e AcessoTerraform
# ═══════════════════════════════════════════════════════════════
# outputs.tf — Outputs do módulo de banco de dados
# ═══════════════════════════════════════════════════════════════

# Output NÃO sensível — endpoint do banco (host:port)
output "db_endpoint" {
  description = "Endpoint do RDS PostgreSQL (host:port)"
  value       = aws_db_instance.main.endpoint
}

# Output NÃO sensível — apenas o hostname
output "db_host" {
  description = "Hostname do RDS (sem porta)"
  value       = aws_db_instance.main.address
}

# Output SENSÍVEL — connection string completa
output "db_connection_string" {
  description = "Connection string completa (contém senha)"
  value       = "postgresql://${aws_db_instance.main.username}:${var.db_password}@${aws_db_instance.main.endpoint}/${aws_db_instance.main.db_name}"
  sensitive   = true  # ← Oculto no terminal!
}

# Output SENSÍVEL — ARN do secret (pode ser usado por outros módulos)
output "db_secret_arn" {
  description = "ARN do secret com credenciais do banco"
  value       = aws_secretsmanager_secret.db_credentials.arn
  # Este não precisa ser sensitive pois é apenas um ARN (identificador)
  # Mas se preferir cautela extra:
  # sensitive = true
}

# Output SENSÍVEL — senha master
output "db_master_password" {
  description = "Senha master do banco (apenas para referência interna)"
  value       = var.db_password
  sensitive   = true
}

# ═══════════════════════════════════════════════════════════════
# O QUE ACONTECE NO TERMINAL:
# ═══════════════════════════════════════════════════════════════
#
# $ terraform output
# db_endpoint          = "myapp-prod-postgres.xxxx.us-east-1.rds.amazonaws.com:5432"
# db_host              = "myapp-prod-postgres.xxxx.us-east-1.rds.amazonaws.com"
# db_connection_string = <sensitive>   ← Oculto!
# db_master_password   = <sensitive>   ← Oculto!
# db_secret_arn        = "arn:aws:secretsmanager:us-east-1:123456:secret:myapp-prod/db/credentials-AbC123"
#
# ═══════════════════════════════════════════════════════════════
# COMO ACESSAR VALORES SENSÍVEIS:
# ═══════════════════════════════════════════════════════════════
#
# Opção 1: terraform output com -raw (mostra valor individual)
# $ terraform output -raw db_connection_string
# postgresql://admin:SenhaForte@host:5432/app_database
#
# Opção 2: terraform output -json (formato JSON, inclui sensíveis)
# $ terraform output -json | jq -r '.db_connection_string.value'
#
# Opção 3: Em CI/CD, redirecionar para variável de ambiente
# $ export DB_URL=$(terraform output -raw db_connection_string)
#
# ═══════════════════════════════════════════════════════════════

10.2 Passando Outputs Sensíveis entre Módulos

Quando módulos precisam compartilhar valores sensíveis, a cadeia de sensitive deve ser mantida em cada nível:

Propagação de Sensitive entre MódulosMódulos
# ═══════════════════════════════════════════════════════════════
# MÓDULO: modules/database/outputs.tf
# ═══════════════════════════════════════════════════════════════
output "connection_string" {
  description = "Connection string do banco"
  value       = "postgresql://${var.username}:${var.password}@${aws_db_instance.main.endpoint}/${var.db_name}"
  sensitive   = true  # Marcar como sensível no módulo filho
}

output "secret_arn" {
  description = "ARN do secret no Secrets Manager"
  value       = aws_secretsmanager_secret.credentials.arn
}

# ═══════════════════════════════════════════════════════════════
# ROOT: main.tf — Usando o módulo
# ═══════════════════════════════════════════════════════════════
module "database" {
  source = "./modules/database"

  environment = var.environment
  project     = var.project
  username    = "app_admin"
  password    = var.db_password  # Variable sensitive → módulo
  db_name     = "app_database"
}

# ═══════════════════════════════════════════════════════════════
# ROOT: Passando para outro módulo
# ═══════════════════════════════════════════════════════════════
module "application" {
  source = "./modules/application"

  # Output sensível do módulo database → input do módulo application
  db_connection_string = module.database.connection_string
  db_secret_arn        = module.database.secret_arn
}

# ═══════════════════════════════════════════════════════════════
# ROOT: outputs.tf — Expondo para fora
# ═══════════════════════════════════════════════════════════════
output "database_endpoint" {
  description = "Endpoint do banco (não sensível)"
  value       = module.database.endpoint  # Sem senha = ok
}

output "database_connection" {
  description = "Connection string (sensível)"
  value       = module.database.connection_string
  sensitive   = true  # DEVE manter sensitive ao propagar!
}

# ═══════════════════════════════════════════════════════════════
# REGRA: Se um output do módulo filho é sensitive,
# qualquer output do root que use esse valor TAMBÉM deve ser
# sensitive. Terraform EXIGE isso — dá erro se não marcar!
# ═══════════════════════════════════════════════════════════════

10.3 Padrão Recomendado: Passar ARN em vez de Valor

Em vez de passar senhas entre módulos, passe o ARN do secret. A aplicação busca o valor em runtime:

Padrão ARN — Mais Seguro que Passar ValoresBoas Práticas
# ═══════════════════════════════════════════════════════════════
# ❌ EVITAR: Passar a senha como string entre módulos
# (valor fica no state de TODOS os módulos que tocam nela)
# ═══════════════════════════════════════════════════════════════
module "app" {
  db_password = var.db_password  # Valor em plain text no state
}

# ═══════════════════════════════════════════════════════════════
# ✅ PREFERIR: Passar o ARN do secret — app busca em runtime
# (valor NÃO fica no Terraform state — apenas o identificador)
# ═══════════════════════════════════════════════════════════════
module "app" {
  db_secret_arn = module.database.secret_arn  # Apenas o ARN (referência)
}

# No módulo de aplicação, o ECS/Lambda usa o ARN para buscar:
resource "aws_ecs_task_definition" "app" {
  container_definitions = jsonencode([{
    secrets = [{
      name      = "DB_PASSWORD"
      valueFrom = "${var.db_secret_arn}:password::"  # Busca em runtime!
    }]
  }])
}

# VANTAGENS:
# 1. Senha NÃO está no Terraform state
# 2. Rotação funciona automaticamente (app sempre busca a versão atual)
# 3. Audit trail: CloudTrail registra cada acesso ao secret
# 4. Granularidade: IAM controla quem pode ler o secret
📋 Resumo — Hierarquia de Segurança para Segredos:
  1. Melhor: manage_master_user_password = true (AWS gerencia tudo)
  2. Muito bom: Secrets Manager + rotação + KMS dedicada
  3. Bom: SSM Parameter Store SecureString + IAM restritivo
  4. Aceitável: Variable sensitive + TF_VAR_ em CI/CD + state encriptado
  5. Inaceitável: Hardcode no código ou .tfvars versionado

Exercício 4 — GitHub Actions OIDC + Deploy Seguro

Objetivo: Configurar acesso OIDC para GitHub Actions deploy em S3 + CloudFront invalidation, sem usar access keys estáticas. Implementar restrição por repositório e branch.

Requisitos:

  • OIDC Provider para GitHub Actions
  • IAM Role com trust policy restritiva (org, repo, branch main apenas)
  • Policy com permissões mínimas: S3 PutObject/DeleteObject e CloudFront CreateInvalidation
  • Conditions usando StringEquals e StringLike
  • Output do Role ARN para uso no workflow YAML
  • Exemplo de workflow GitHub Actions que usa a role
▶ Ver solução
github-oidc.tfSolução
# ═══════════════════════════════════════════════════════════════

# ═══════════════════════════════════════════════════════════════

variable "github_org" {
  description = "Organização ou usuário GitHub"
  type        = string
}

variable "github_repo" {
  description = "Nome do repositório"
  type        = string
}

# ─── OIDC Provider ─────────────────────────────────────────────
resource "aws_iam_openid_connect_provider" "github" {
  url             = "https://token.actions.githubusercontent.com"
  client_id_list  = ["sts.amazonaws.com"]
  thumbprint_list = ["6938fd4d98bab03faadb97b34396831e3780aea1"]

  tags = merge(local.common_tags, { Name = "github-actions-oidc" })
}

# ─── IAM Role para GitHub Actions ─────────────────────────────
resource "aws_iam_role" "github_actions" {
  name = "${local.name_prefix}-github-actions-deploy"

  assume_role_policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Sid    = "AllowGitHubOIDC"
      Effect = "Allow"
      Principal = {
        Federated = aws_iam_openid_connect_provider.github.arn
      }
      Action = "sts:AssumeRoleWithWebIdentity"
      Condition = {
        StringEquals = {
          "token.actions.githubusercontent.com:aud" = "sts.amazonaws.com"
        }
        StringLike = {
          # SOMENTE branch main do repositório específico
          "token.actions.githubusercontent.com:sub" = "repo:${var.github_org}/${var.github_repo}:ref:refs/heads/main"
        }
      }
    }]
  })

  # Limitar duração da sessão (máximo 1 hora para deploy)
  max_session_duration = 3600

  tags = merge(local.common_tags, {
    Name    = "${local.name_prefix}-github-deploy"
    Purpose = "CI/CD"
  })
}

# ─── Deploy Policy ─────────────────────────────────────────────
resource "aws_iam_policy" "github_deploy" {
  name        = "${local.name_prefix}-github-deploy-policy"
  description = "Permite deploy de site estático via GitHub Actions"

  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [
      {
        Sid    = "S3SiteDeployment"
        Effect = "Allow"
        Action = [
          "s3:PutObject",
          "s3:DeleteObject",
          "s3:GetObject",
          "s3:ListBucket"
        ]
        Resource = [
          "arn:aws:s3:::${local.name_prefix}-site",
          "arn:aws:s3:::${local.name_prefix}-site/*"
        ]
      },
      {
        Sid    = "CloudFrontInvalidation"
        Effect = "Allow"
        Action = ["cloudfront:CreateInvalidation"]
        Resource = "arn:aws:cloudfront::${local.account_id}:distribution/*"
      }
    ]
  })

  tags = local.common_tags
}

resource "aws_iam_role_policy_attachment" "github_deploy" {
  role       = aws_iam_role.github_actions.name
  policy_arn = aws_iam_policy.github_deploy.arn
}
