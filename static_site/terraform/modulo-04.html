S3 Bucket — Configuração Segura

O S3 armazena objetos (arquivos, backups, assets). Configuramos versionamento, criptografia e bloqueio de acesso público seguindo as melhores práticas.

aws_s3_buckets3.tf

Cria o bucket base. No Terraform AWS Provider v4+, configurações são recursos separados.

resource "aws_s3_bucket" "app" {
  bucket = "${var.project_name}-${var.environment}-assets"

  tags = merge(local.common_tags, {
    Name = "${var.project_name}-${var.environment}-assets"
    Role = "storage"
  })
}
aws_s3_bucket_versioningVersionamento

Habilita versionamento para manter histórico de alterações e permitir recuperação.

resource "aws_s3_bucket_versioning" "app" {
  bucket = aws_s3_bucket.app.id

  versioning_configuration {
    status = "Enabled"
  }
}
aws_s3_bucket_server_side_encryption_configurationCriptografia

Criptografia at-rest com AES256 (SSE-S3). Todos os objetos são criptografados automaticamente.

resource "aws_s3_bucket_server_side_encryption_configuration" "app" {
  bucket = aws_s3_bucket.app.id

  rule {
    apply_server_side_encryption_by_default {
      sse_algorithm = "AES256"
    }
    bucket_key_enabled = true
  }
}
aws_s3_bucket_public_access_blockBloqueio Público

Bloqueia todo acesso público ao bucket — todas as 4 opções habilitadas.

resource "aws_s3_bucket_public_access_block" "app" {
  bucket = aws_s3_bucket.app.id

  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
}

S3 Lifecycle Rules — Otimização de Custos

Lifecycle Rules movem objetos automaticamente entre classes de armazenamento e expiram dados antigos, reduzindo custos significativamente.

aws_s3_bucket_lifecycle_configurationlifecycle.tf

Transições automáticas: Standard → Standard-IA (30d) → Glacier (90d) → Expiração (365d).

resource "aws_s3_bucket_lifecycle_configuration" "app" {
  bucket = aws_s3_bucket.app.id

  rule {
    id     = "transition-and-expire"
    status = "Enabled"

    transition {
      days          = 30
      storage_class = "STANDARD_IA"
    }

    transition {
      days          = 90
      storage_class = "GLACIER"
    }

    expiration {
      days = 365
    }

    noncurrent_version_expiration {
      noncurrent_days = 30
    }

    abort_incomplete_multipart_upload {
      days_after_initiation = 7
    }
  }
}

ClasseUsoCusto

STANDARD_IAAcesso infrequente$$$
GLACIERArquivo de longo prazo$$
DEEP_ARCHIVERaramente acessado$

IAM Role para EC2 — Acesso ao S3

Em vez de usar Access Keys na EC2, criamos uma IAM Role com Instance Profile. A EC2 assume a role automaticamente via metadata service.

aws_iam_roleiam.tf

Role com trust policy permitindo que o serviço EC2 assuma esta role.

resource "aws_iam_role" "ec2_s3_role" {
  name = "${var.project_name}-ec2-s3-role"

  assume_role_policy = jsonencode({
    Version = "2012-10-17"
    Statement = [
      {
        Action = "sts:AssumeRole"
        Effect = "Allow"
        Principal = {
          Service = "ec2.amazonaws.com"
        }
      }
    ]
  })

  tags = local.common_tags
}
aws_iam_role_policyPermissões S3

Policy inline com permissões específicas para o bucket da aplicação.

resource "aws_iam_role_policy" "ec2_s3_policy" {
  name = "${var.project_name}-ec2-s3-policy"
  role = aws_iam_role.ec2_s3_role.id

  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [
      {
        Effect = "Allow"
        Action = [
          "s3:GetObject",
          "s3:PutObject",
          "s3:ListBucket",
          "s3:DeleteObject"
        ]
        Resource = [
          aws_s3_bucket.app.arn,
          "${aws_s3_bucket.app.arn}/*"
        ]
      }
    ]
  })
}
aws_iam_instance_profileInstance Profile

O Instance Profile é o "wrapper" que conecta a IAM Role à instância EC2.

resource "aws_iam_instance_profile" "ec2_profile" {
  name = "${var.project_name}-ec2-profile"
  role = aws_iam_role.ec2_s3_role.name

  tags = local.common_tags
}

# Uso na EC2:
resource "aws_instance" "web" {
  # ... outras configurações ...
  iam_instance_profile = aws_iam_instance_profile.ec2_profile.name
}

Bucket Policy — Controle de Acesso

A Bucket Policy define regras de acesso no nível do bucket. Combinamos permissão para a EC2 Role com negação de transporte inseguro (HTTP).

aws_s3_bucket_policys3-policy.tf

Permite acesso da EC2 Role e nega requisições sem HTTPS (transporte inseguro).

resource "aws_s3_bucket_policy" "app" {
  bucket = aws_s3_bucket.app.id

  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [
      {
        Sid    = "AllowEC2RoleAccess"
        Effect = "Allow"
        Principal = {
          AWS = aws_iam_role.ec2_s3_role.arn
        }
        Action = [
          "s3:GetObject",
          "s3:PutObject",
          "s3:ListBucket"
        ]
        Resource = [
          aws_s3_bucket.app.arn,
          "${aws_s3_bucket.app.arn}/*"
        ]
      },
      {
        Sid       = "DenyInsecureTransport"
        Effect    = "Deny"
        Principal = "*"
        Action    = "s3:*"
        Resource = [
          aws_s3_bucket.app.arn,
          "${aws_s3_bucket.app.arn}/*"
        ]
        Condition = {
          Bool = {
            "aws:SecureTransport" = "false"
          }
        }
      }
    ]
  })
}

Comandos Avançados do Terraform

Comandos essenciais para gerenciar infraestrutura em cenários reais: planejamento, importação e workspaces.

terraform plan -outPlanejamento

Salva o plano em arquivo binário para aplicar exatamente o que foi revisado.

# Gerar plano e salvar em arquivo
terraform plan -out=plan.tfplan

# Aplicar exatamente o plano salvo (sem re-calcular)
terraform apply plan.tfplan
terraform output -jsonOutputs

Exporta outputs em formato JSON para integração com scripts e CI/CD.

# Ver todos os outputs em JSON
terraform output -json

# Output específico (sem aspas)
terraform output -raw db_endpoint

# Usar em scripts bash
DB_HOST=$(terraform output -raw db_endpoint)
echo "Conectando em: $DB_HOST"
terraform importImportação

Importa recursos existentes (criados manualmente) para o state do Terraform.

# Sintaxe: terraform import RECURSO_TF ID_AWS
terraform import aws_s3_bucket.app meu-bucket-existente

terraform import aws_db_instance.main meu-rds-identifier

terraform import aws_vpc.main vpc-0abc123def456

# Após importar, escreva o código .tf correspondente
# e execute terraform plan para verificar drift
terraform state mvState

Move recursos no state — útil ao refatorar código sem destruir infraestrutura.

# Renomear recurso no state
terraform state mv aws_instance.web aws_instance.app_server

# Mover para módulo
terraform state mv aws_s3_bucket.app module.storage.aws_s3_bucket.main

# Listar recursos no state
terraform state list

# Ver detalhes de um recurso
terraform state show aws_s3_bucket.app
terraform workspaceWorkspaces

Workspaces permitem múltiplos states no mesmo código — útil para ambientes dev/staging/prod.

# Criar novo workspace
terraform workspace new dev
terraform workspace new staging
terraform workspace new prod

# Listar workspaces
terraform workspace list

# Selecionar workspace
terraform workspace select dev

# Usar no código
locals {
  environment = terraform.workspace
}

resource "aws_instance" "web" {
  instance_type = terraform.workspace == "prod" ? "t3.medium" : "t3.micro"
}

Remote Backend — State Compartilhado

Em equipe ou CI/CD, o state deve ser armazenado remotamente com locking para evitar conflitos. O backend S3 + DynamoDB é o padrão na AWS.

terraform backend "s3"backend.tf

Configuração do backend remoto com criptografia e locking via DynamoDB.

terraform {
  backend "s3" {
    bucket         = "cloudtrilhas-terraform-state"
    key            = "vpc-ec2-rds-s3/terraform.tfstate"
    region         = "us-east-1"
    dynamodb_table = "terraform-state-lock"
    encrypt        = true
  }
}
Pré-requisitos do BackendSetup

O bucket S3 e a tabela DynamoDB devem existir ANTES de configurar o backend.

# Criar bucket para state (via AWS CLI ou console)
aws s3api create-bucket \
  --bucket cloudtrilhas-terraform-state \
  --region us-east-1

# Habilitar versionamento
aws s3api put-bucket-versioning \
  --bucket cloudtrilhas-terraform-state \
  --versioning-configuration Status=Enabled

# Criar tabela DynamoDB para locking
aws dynamodb create-table \
  --table-name terraform-state-lock \
  --attribute-definitions AttributeName=LockID,AttributeType=S \
  --key-schema AttributeName=LockID,KeyType=HASH \
  --billing-mode PAY_PER_REQUEST

# Após criar, inicialize o backend
terraform init -migrate-state

💡 Dica: O DynamoDB table usa LockID como partition key. Quando alguém executa terraform apply, um lock é criado impedindo execuções simultâneas.
