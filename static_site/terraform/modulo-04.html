Armazenamento

1. S3 Bucket — Armazenamento de Objetos

Entenda o serviço de armazenamento mais versátil da AWS: como ele funciona internamente, sua arquitetura, regras de nomenclatura e casos de uso reais em produção.

1.1 O que é o Amazon S3?

Amazon Simple Storage Service (S3) é um serviço de armazenamento de objetos que oferece escalabilidade, disponibilidade de dados, segurança e performance líderes de mercado. Lançado em 2006, foi um dos primeiros serviços da AWS e continua sendo o pilar central de inúmeras arquiteturas cloud.

O S3 armazena dados como objetos dentro de buckets. Diferente de um sistema de arquivos tradicional (hierárquico com pastas), o S3 é um flat namespace — as "pastas" que você vê no console são apenas prefixos nas chaves dos objetos.

☁️ Analogia — Google Drive Infinito:

Imagine um Google Drive sem limite de armazenamento, que nunca fica indisponível, aceita arquivos de qualquer tamanho (até 5TB), e cobra centavos por GB. Agora adicione controle de acesso granular, versionamento automático, replicação entre regiões, e eventos que disparam Lambdas quando um arquivo é carregado. Isso é o S3.

1.5 Versionamento de Objetos

O versionamento mantém múltiplas variantes de um objeto no mesmo bucket. Quando ativado, o S3 preserva todas as versões de um objeto — incluindo todas as escritas e até deleções.

📚 Analogia — Google Docs com Histórico:

Assim como o Google Docs mantém o histórico de todas as edições de um documento (e você pode voltar para qualquer versão anterior), o S3 com versionamento mantém todas as versões de cada arquivo. Se alguém sobrescreve ou deleta acidentalmente, basta restaurar a versão anterior.

Como Funciona o VersionamentoConceito
# Estado do objeto "relatorio.pdf" com versionamento ativo:

Versão 3 (ATUAL)  → Upload em 2024-06-15  │ 2.1 MB │ ID: abc123
Versão 2           → Upload em 2024-06-01  │ 1.8 MB │ ID: def456
Versão 1           → Upload em 2024-05-20  │ 1.2 MB │ ID: ghi789

# DELETE no objeto com versionamento ativo:
# NÃO remove o arquivo! Adiciona um "Delete Marker"

Delete Marker (ATUAL) → Criado em 2024-06-20 │ ID: jkl012
Versão 3               → Upload em 2024-06-15 │ ID: abc123  ← ainda existe!
Versão 2               → Upload em 2024-06-01 │ ID: def456
Versão 1               → Upload em 2024-05-20 │ ID: ghi789

# Para restaurar: remova o Delete Marker ou copie versão específica
⚠️ Cuidado com Custos de Versionamento:

Cada versão ocupa espaço e é cobrada. Se você tem um arquivo de 100MB que é atualizado diariamente, após 30 dias terá ~3GB armazenados (30 versões × 100MB). Combine versionamento com Lifecycle Rules para expirar versões antigas automaticamente.

Terraform + S3

2. S3 com Terraform

Aprenda a criar e configurar buckets S3 usando Terraform com o padrão moderno de recursos separados — a abordagem recomendada pela AWS e HashiCorp desde 2022.

2.1 Padrão Antigo vs Novo (Separate Resources)

Antes do Terraform AWS Provider v4.0 (2022), todas as configurações do S3 ficavam dentro de um único resource aws_s3_bucket. Agora, cada configuração é um recurso separado:

❌ Padrão Antigo (Depreciado)Evitar
# NÃO USE — vai gerar warnings
resource "aws_s3_bucket" "this" {
  bucket = "meu-bucket"
  acl    = "private"

  versioning {
    enabled = true
  }

  server_side_encryption_configuration {
    rule {
      apply_server_side_encryption_by_default {
        sse_algorithm = "AES256"
      }
    }
  }

  lifecycle_rule {
    enabled = true
    transition {
      days          = 30
      storage_class = "STANDARD_IA"
    }
  }
}
✅ Padrão Novo (Recursos Separados)Recomendado
# RECOMENDADO — cada config é um resource
resource "aws_s3_bucket" "this" {
  bucket = "meu-bucket"
  tags   = var.tags
}

resource "aws_s3_bucket_versioning" "this" {
  bucket = aws_s3_bucket.this.id
  versioning_configuration {
    status = "Enabled"
  }
}

resource "aws_s3_bucket_server_side_encryption_configuration" "this" {
  bucket = aws_s3_bucket.this.id
  rule {
    apply_server_side_encryption_by_default {
      sse_algorithm = "AES256"
    }
  }
}
💡 Por que recursos separados?
  • Granularidade: Pode alterar versionamento sem recriar o bucket inteiro
  • Menos conflitos: Equipes diferentes podem gerenciar aspectos diferentes
  • Lifecycle mais previsível: Cada configuração tem seu próprio ciclo de vida no state
  • Import facilitado: Pode importar configurações individualmente

2.2 Bucket Completo para Produção

Veja a configuração completa de um bucket S3 para produção seguindo boas práticas de segurança:

s3.tfProdução
# ╔══════════════════════════════════════════════════════════════╗
# ║  S3 BUCKET — CONFIGURAÇÃO COMPLETA PARA PRODUÇÃO           ║
# ╚══════════════════════════════════════════════════════════════╝

# ────────────────────────────────────────────────────────────────
# 1. BUCKET PRINCIPAL
# ────────────────────────────────────────────────────────────────
resource "aws_s3_bucket" "app_assets" {
  # Nome globalmente único — use convenção: {empresa}-{app}-{env}-{finalidade}
  bucket = "${var.project_name}-${var.environment}-assets"

  # Previne destruição acidental do bucket (proteção extra)
  # Remova este bloco APENAS se realmente precisar destruir
  force_destroy = false

  tags = merge(var.common_tags, {
    Name    = "${var.project_name}-${var.environment}-assets"
    Purpose = "Application static assets and uploads"
  })
}

# ────────────────────────────────────────────────────────────────
# 2. VERSIONAMENTO — Proteção contra sobrescrita/deleção acidental
# ────────────────────────────────────────────────────────────────
resource "aws_s3_bucket_versioning" "app_assets" {
  bucket = aws_s3_bucket.app_assets.id

  versioning_configuration {
    # "Enabled" | "Suspended" | "Disabled"
    # Uma vez habilitado, não pode ser completamente desabilitado
    # apenas "Suspended" (pausa, mas mantém versões existentes)
    status = "Enabled"
  }
}

# ────────────────────────────────────────────────────────────────
# 3. CRIPTOGRAFIA — Todos os objetos criptografados em repouso
# ────────────────────────────────────────────────────────────────
resource "aws_s3_bucket_server_side_encryption_configuration" "app_assets" {
  bucket = aws_s3_bucket.app_assets.id

  rule {
    # Aplica criptografia automaticamente a todos os objetos
    apply_server_side_encryption_by_default {
      # AES256 = SSE-S3 (gerenciado pela AWS, sem custo extra)
      # aws:kms = SSE-KMS (mais controle, audit via CloudTrail, custo por request)
      sse_algorithm = "AES256"
    }
    # Força que TODOS os objetos usem a criptografia configurada
    bucket_key_enabled = true
  }
}

# ────────────────────────────────────────────────────────────────
# 4. BLOQUEIO DE ACESSO PÚBLICO — Defesa em profundidade
# ────────────────────────────────────────────────────────────────
resource "aws_s3_bucket_public_access_block" "app_assets" {
  bucket = aws_s3_bucket.app_assets.id

  # Bloqueia ACLs públicas (não permite configurar objetos como públicos)
  block_public_acls = true

  # Bloqueia bucket policies que concedem acesso público
  block_public_policy = true

  # Ignora ACLs públicas existentes (override de segurança)
  ignore_public_acls = true

  # Restringe acesso público concedido por policies
  restrict_public_buckets = true
}

# ────────────────────────────────────────────────────────────────
# 5. OWNERSHIP CONTROLS — Desabilita ACLs (recomendado)
# ────────────────────────────────────────────────────────────────
resource "aws_s3_bucket_ownership_controls" "app_assets" {
  bucket = aws_s3_bucket.app_assets.id

  rule {
    # "BucketOwnerEnforced" = ACLs desabilitadas (recomendado AWS)
    # O dono do bucket é sempre o dono de todos os objetos
    object_ownership = "BucketOwnerEnforced"
  }
}

2.4 Upload de Objetos com Terraform

O Terraform pode fazer upload de objetos individuais para o S3 usando aws_s3_object:

aws_s3_objectUpload
# Upload de arquivo individual
resource "aws_s3_object" "index_html" {
  bucket       = aws_s3_bucket.app_assets.id
  key          = "index.html"
  source       = "${path.module}/files/index.html"
  content_type = "text/html"
  etag         = filemd5("${path.module}/files/index.html")

  # etag força re-upload quando o conteúdo muda
}

# Upload de conteúdo inline (útil para configs)
resource "aws_s3_object" "config_json" {
  bucket       = aws_s3_bucket.app_assets.id
  key          = "config/app-config.json"
  content_type = "application/json"

  content = jsonencode({
    api_endpoint = var.api_url
    environment  = var.environment
    version      = var.app_version
  })
}

# Upload de múltiplos arquivos com for_each
locals {
  static_files = {
    "css/style.css"   = "text/css"
    "js/app.js"       = "application/javascript"
    "images/logo.png" = "image/png"
  }
}

resource "aws_s3_object" "static_files" {
  for_each = local.static_files

  bucket       = aws_s3_bucket.app_assets.id
  key          = each.key
  source       = "${path.module}/static/${each.key}"
  content_type = each.value
  etag         = filemd5("${path.module}/static/${each.key}")
}
⚠️ Terraform NÃO é ideal para deploy de arquivos estáticos em massa:

Para sites com centenas de arquivos, use aws s3 sync no CI/CD pipeline em vez de aws_s3_object. O Terraform é ótimo para infraestrutura, mas o sync é mais eficiente para conteúdo que muda frequentemente.

Otimização de Custos

3. S3 Lifecycle Rules

Automatize a transição de objetos entre classes de armazenamento e a expiração de dados antigos para otimizar custos sem intervenção manual.

3.1 O que são Lifecycle Rules?

Lifecycle Rules são políticas que definem ações automáticas em objetos do S3 baseadas na idade ou em prefixos. O S3 avalia essas regras diariamente e executa as ações configuradas.

🔄 Analogia — Arquivo Morto do Escritório:

Em um escritório organizado, documentos recentes ficam na mesa (fácil acesso), depois de 30 dias vão para o arquivo da sala (acesso rápido mas não imediato), após 1 ano vão para o arquivo morto no subsolo (recuperação demora), e após 7 anos são destruídos. Lifecycle Rules fazem exatamente isso automaticamente no S3.

📊 Fluxo de Transição entre Classes:

3.2 Lifecycle Configuration com Terraform

Veja a implementação completa de lifecycle rules para diferentes cenários:

lifecycle.tfCompleto
# ╔══════════════════════════════════════════════════════════════╗
# ║  LIFECYCLE RULES — OTIMIZAÇÃO AUTOMÁTICA DE CUSTOS          ║
# ╚══════════════════════════════════════════════════════════════╝

resource "aws_s3_bucket_lifecycle_configuration" "app_assets" {
  bucket = aws_s3_bucket.app_assets.id

  # Depende do versionamento estar ativo (para regras de noncurrent)
  depends_on = [aws_s3_bucket_versioning.app_assets]

  # ──────────────────────────────────────────────────────────────
  # REGRA 1: Logs de aplicação — transição progressiva
  # ──────────────────────────────────────────────────────────────
  rule {
    id     = "logs-lifecycle"
    status = "Enabled"

    # Aplica apenas a objetos com prefixo "logs/"
    filter {
      prefix = "logs/"
    }

    # Após 30 dias → Standard-IA (acesso infrequente mas rápido)
    transition {
      days          = 30
      storage_class = "STANDARD_IA"
    }

    # Após 90 dias → Glacier Instant Retrieval
    transition {
      days          = 90
      storage_class = "GLACIER_IR"
    }

    # Após 365 dias → Glacier Deep Archive (mais barato possível)
    transition {
      days          = 365
      storage_class = "DEEP_ARCHIVE"
    }

    # Após 2555 dias (7 anos) → Deletar permanentemente
    # (Compliance: muitas regulações exigem retenção de 7 anos)
    expiration {
      days = 2555
    }

    # Versões anteriores: mover para Glacier após 30 dias
    noncurrent_version_transition {
      noncurrent_days = 30
      storage_class   = "GLACIER"
    }

    # Versões anteriores: deletar após 90 dias
    noncurrent_version_expiration {
      noncurrent_days = 90
    }
  }

  # ──────────────────────────────────────────────────────────────
  # REGRA 2: Uploads temporários — limpeza agressiva
  # ──────────────────────────────────────────────────────────────
  rule {
    id     = "temp-uploads-cleanup"
    status = "Enabled"

    filter {
      prefix = "tmp/"
    }

    # Deleta após 7 dias
    expiration {
      days = 7
    }
  }

  # ──────────────────────────────────────────────────────────────
  # REGRA 3: Limpar uploads multipart incompletos
  # ──────────────────────────────────────────────────────────────
  rule {
    id     = "abort-incomplete-multipart"
    status = "Enabled"

    filter {
      prefix = "" # Aplica a todo o bucket
    }

    # Aborta uploads multipart incompletos após 7 dias
    # (evita cobranças por partes orphãs)
    abort_incomplete_multipart_upload {
      days_after_initiation = 7
    }
  }

  # ──────────────────────────────────────────────────────────────
  # REGRA 4: Delete Markers expirados — limpeza de versionamento
  # ──────────────────────────────────────────────────────────────
  rule {
    id     = "cleanup-delete-markers"
    status = "Enabled"

    filter {
      prefix = ""
    }

    # Remove delete markers que não apontam para nenhuma versão
    expiration {
      expired_object_delete_marker = true
    }
  }
}

3.3 Regras de Transição — Restrições Importantes

Nem todas as transições são permitidas. O S3 impõe uma hierarquia:

De ↓ / Para → Standard-IA One Zone-IA Glacier IR Glacier Flex Deep Archive
Standard✅ 30+ dias✅ 30+ dias✅ 90+ dias✅ 90+ dias✅ 180+ dias
Standard-IA—✅✅✅✅
One Zone-IA❌—✅✅✅
Glacier IR❌❌—✅✅
Glacier Flex❌❌❌—✅
Deep Archive❌❌❌❌—
⚠️ Tamanho Mínimo e Dias Mínimos:
  • Objetos menores que 128KB não são transicionados para IA/Glacier (cobrados como 128KB)
  • Mínimo de 30 dias em Standard antes de transição para IA
  • Mínimo de 30 dias adicionais antes de transição para Glacier
  • Objetos em Glacier têm cobrança mínima de 90 dias (mesmo se deletados antes)
  • Deep Archive: cobrança mínima de 180 dias
Controle de Acesso

4. Bucket Policy e ACLs

Domine os mecanismos de controle de acesso do S3: quando usar IAM Policies, Bucket Policies ou ACLs, e como implementar cenários reais de produção.

4.1 IAM Policy vs Bucket Policy vs ACL

O S3 possui três mecanismos de controle de acesso que trabalham juntos. A decisão final é "negar por padrão, permitir apenas se TODOS concordam":

Mecanismo Anexado a Controla Quando Usar

4.2 Bucket Policy — CloudFront OAC

O cenário mais comum em produção: permitir que CloudFront acesse objetos do S3 via Origin Access Control (OAC), enquanto bloqueia acesso direto ao bucket:

bucket_policy_cloudfront.tfOAC
# ╔══════════════════════════════════════════════════════════════╗
# ║  BUCKET POLICY — CLOUDFRONT OAC (Origin Access Control)     ║
# ╚══════════════════════════════════════════════════════════════╝

resource "aws_s3_bucket_policy" "allow_cloudfront" {
  bucket = aws_s3_bucket.app_assets.id

  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [
      {
        Sid    = "AllowCloudFrontServicePrincipal"
        Effect = "Allow"
        Principal = {
          Service = "cloudfront.amazonaws.com"
        }
        Action   = "s3:GetObject"
        Resource = "${aws_s3_bucket.app_assets.arn}/*"
        Condition = {
          StringEquals = {
            # Restringe ao distribution específico (não qualquer CloudFront)
            "AWS:SourceArn" = aws_cloudfront_distribution.main.arn
          }
        }
      }
    ]
  })
}

# OAC — substitui o antigo OAI (Origin Access Identity)
resource "aws_cloudfront_origin_access_control" "s3_oac" {
  name                              = "${var.project_name}-oac"
  description                       = "OAC para bucket ${aws_s3_bucket.app_assets.id}"
  origin_access_control_origin_type = "s3"
  signing_behavior                  = "always"
  signing_protocol                  = "sigv4"
}

4.3 Bucket Policy — Cross-Account Access

Permitir que outra conta AWS acesse o bucket (cenário comum em organizações com múltiplas contas):

bucket_policy_cross_account.tfMulti-Account
# Cenário: Conta de Produção (111111111111) permite que
# Conta de Analytics (222222222222) leia dados para relatórios

resource "aws_s3_bucket_policy" "cross_account_read" {
  bucket = aws_s3_bucket.data_lake.id

  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [
      {
        Sid    = "AllowAnalyticsAccountRead"
        Effect = "Allow"
        Principal = {
          AWS = "arn:aws:iam::222222222222:root"
        }
        Action = [
          "s3:GetObject",
          "s3:ListBucket"
        ]
        Resource = [
          aws_s3_bucket.data_lake.arn,         # ListBucket no bucket
          "${aws_s3_bucket.data_lake.arn}/*"   # GetObject nos objetos
        ]
        Condition = {
          StringEquals = {
            # Restringe a prefixos específicos (não dá acesso total)
            "s3:prefix" = ["reports/", "aggregated/"]
          }
        }
      }
    ]
  })
}

4.4 Bucket Policy — Forçar HTTPS (Negar HTTP)

Best practice de segurança: negar qualquer acesso que não use TLS/HTTPS:

bucket_policy_enforce_tls.tfSegurança
# Nega QUALQUER operação feita sem HTTPS (HTTP puro)
resource "aws_s3_bucket_policy" "enforce_tls" {
  bucket = aws_s3_bucket.app_assets.id

  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [
      {
        Sid       = "DenyInsecureTransport"
        Effect    = "Deny"
        Principal = "*"
        Action    = "s3:*"
        Resource = [
          aws_s3_bucket.app_assets.arn,
          "${aws_s3_bucket.app_assets.arn}/*"
        ]
        Condition = {
          Bool = {
            "aws:SecureTransport" = "false"
          }
        }
      },
      {
        Sid       = "DenyOutdatedTLS"
        Effect    = "Deny"
        Principal = "*"
        Action    = "s3:*"
        Resource = [
          aws_s3_bucket.app_assets.arn,
          "${aws_s3_bucket.app_assets.arn}/*"
        ]
        Condition = {
          NumericLessThan = {
            "s3:TlsVersion" = 1.2  # Exige TLS 1.2+
          }
        }
      }
    ]
  })
}
⚠️ Bucket Policies — Cuidados:
  • Uma policy mal escrita pode travar você fora do bucket. Sempre inclua acesso para a role de administrador.
  • Use terraform plan para revisar changes em policies antes de aplicar.
  • Limite de tamanho: 20KB por bucket policy.
  • Combine múltiplos statements em uma única policy (não é possível ter múltiplas policies por bucket).

5. Remote State — Backend S3

Entenda por que o state local é perigoso em equipes, como configurar backend remoto no S3 com locking via DynamoDB, e boas práticas de segurança para o arquivo mais sensível do Terraform.

5.1 O Problema do State Local

Por padrão, o Terraform armazena o state em um arquivo local chamado terraform.tfstate. Em um time de uma pessoa, isso funciona. Em equipes, é um desastre:

🧭 Analogia — GPS Compartilhado:

O state é como o GPS do Terraform — ele sabe onde cada recurso está e como chegar lá. Se dois motoristas (desenvolvedores) usam GPSs diferentes (states locais desatualizados), cada um acha que está no caminho certo, mas acabam colidindo no mesmo destino. Remote state é como ter um GPS na nuvem que todos compartilham em tempo real.

Problema State Local Remote State (S3)
Colaboração❌ Cada dev tem seu state — conflitos garantidos✅ State único compartilhado
Locking❌ Dois applies simultâneos corrompem state✅ DynamoDB lock previne concorrência
Segurança❌ Secrets em plain text no disco local✅ Criptografado em repouso (SSE)
Backup❌ Se perder o arquivo, perde o mapeamento✅ Versionamento S3 = histórico
CI/CD❌ Pipeline não tem acesso ao state local✅ Pipeline acessa via IAM role
Auditoria❌ Sem log de quem acessou✅ CloudTrail registra acessos
⚠️ NUNCA comite terraform.tfstate no Git!

O state contém dados sensíveis em plain text: senhas de bancos, chaves de API, IPs internos. Sempre adicione ao .gitignore:

5.2 Configurando Backend S3

O backend S3 é o mais popular para equipes AWS. Combina S3 (armazenamento) + DynamoDB (locking) + KMS (criptografia):

backend.tfRemote State
# ╔══════════════════════════════════════════════════════════════╗
# ║  BACKEND S3 — REMOTE STATE COM LOCKING                      ║
# ╚══════════════════════════════════════════════════════════════╝

terraform {
  backend "s3" {
    # Bucket que armazena o state (deve existir ANTES do init)
    bucket = "cloudtrilhas-terraform-state"

    # Caminho do arquivo de state dentro do bucket
    # Use caminhos que identifiquem projeto/ambiente
    key = "projects/cloudtrilhas/prod/terraform.tfstate"

    # Região do bucket
    region = "us-east-1"

    # Tabela DynamoDB para state locking
    # Previne que dois applies rodem ao mesmo tempo
    dynamodb_table = "terraform-state-lock"

    # Criptografia do state em repouso
    encrypt = true

    # (Opcional) KMS key para criptografia customizada
    # kms_key_id = "arn:aws:kms:us-east-1:123456789012:key/xxx"

    # (Opcional) Assume role para acesso cross-account
    # role_arn = "arn:aws:iam::123456789012:role/TerraformStateAccess"
  }
}

# NOTA IMPORTANTE:
# O bloco backend NÃO suporta variáveis ou interpolações!
# Todos os valores devem ser hardcoded ou passados via -backend-config
💡 Passando configuração dinâmica via -backend-config: 
# Para evitar hardcoding, use arquivos de configuração por ambiente:

# backend-prod.hcl
bucket         = "cloudtrilhas-terraform-state"
key            = "projects/app/prod/terraform.tfstate"
region         = "us-east-1"
dynamodb_table = "terraform-state-lock"
encrypt        = true

# Inicialização com arquivo de config:
terraform init -backend-config=backend-prod.hcl

# Ou via CLI args individuais:
terraform init \
  -backend-config="bucket=cloudtrilhas-terraform-state" \
  -backend-config="key=projects/app/dev/terraform.tfstate"

5.3 Infraestrutura do Backend (Bootstrap)

O bucket de state e a tabela DynamoDB devem existir antes de configurar o backend. Isso cria um problema de "ovo e galinha" — resolvido com um projeto bootstrap separado:

bootstrap/main.tfBootstrap
# ╔══════════════════════════════════════════════════════════════╗
# ║  BOOTSTRAP — INFRAESTRUTURA PARA REMOTE STATE              ║
# ║  Execute PRIMEIRO com state local, depois migre             ║
# ╚══════════════════════════════════════════════════════════════╝

provider "aws" {
  region = "us-east-1"
}

# ────────────────────────────────────────────────────────────────
# BUCKET PARA ARMAZENAR O STATE
# ────────────────────────────────────────────────────────────────
resource "aws_s3_bucket" "terraform_state" {
  bucket = "cloudtrilhas-terraform-state"

  # CRÍTICO: Previne destruição acidental do bucket de state
  lifecycle {
    prevent_destroy = true
  }

  tags = {
    Name      = "Terraform State Storage"
    ManagedBy = "terraform-bootstrap"
    Critical  = "true"
  }
}

resource "aws_s3_bucket_versioning" "terraform_state" {
  bucket = aws_s3_bucket.terraform_state.id

  versioning_configuration {
    # OBRIGATÓRIO para state — permite rollback se state corromper
    status = "Enabled"
  }
}

resource "aws_s3_bucket_server_side_encryption_configuration" "terraform_state" {
  bucket = aws_s3_bucket.terraform_state.id

  rule {
    apply_server_side_encryption_by_default {
      sse_algorithm = "AES256"
    }
  }
}

resource "aws_s3_bucket_public_access_block" "terraform_state" {
  bucket = aws_s3_bucket.terraform_state.id

  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
}

# ────────────────────────────────────────────────────────────────
# DYNAMODB TABLE PARA STATE LOCKING
# ────────────────────────────────────────────────────────────────
resource "aws_dynamodb_table" "terraform_lock" {
  name         = "terraform-state-lock"
  billing_mode = "PAY_PER_REQUEST"  # Sem custo quando não em uso
  hash_key     = "LockID"           # Chave OBRIGATÓRIA — o Terraform usa esta key

  attribute {
    name = "LockID"
    type = "S"  # String
  }

  tags = {
    Name      = "Terraform State Lock"
    ManagedBy = "terraform-bootstrap"
  }
}

# ────────────────────────────────────────────────────────────────
# OUTPUTS — Use estes valores no backend dos outros projetos
# ────────────────────────────────────────────────────────────────
output "state_bucket_name" {
  value       = aws_s3_bucket.terraform_state.id
  description = "Nome do bucket para usar no backend"
}

output "lock_table_name" {
  value       = aws_dynamodb_table.terraform_lock.name
  description = "Nome da tabela DynamoDB para locking"
}

6.2 terraform state mv — Refatorar sem Destruir

Quando você renomeia um recurso no código, o Terraform interpreta como "destruir o antigo, criar novo". O state mv corrige o mapeamento:

Cenários de state mvRefatoração
# ══════════════════════════════════════════════════════════════════
# CENÁRIO 1: Renomear recurso
# ══════════════════════════════════════════════════════════════════

# ANTES: resource "aws_s3_bucket" "bucket" { ... }
# DEPOIS: resource "aws_s3_bucket" "app_assets" { ... }

# Sem state mv: Terraform quer destruir "bucket" e criar "app_assets" 😱
# Com state mv: Terraform entende que é o mesmo recurso com nome novo ✅

terraform state mv aws_s3_bucket.bucket aws_s3_bucket.app_assets

# ══════════════════════════════════════════════════════════════════
# CENÁRIO 2: Mover recurso para dentro de um módulo
# ══════════════════════════════════════════════════════════════════

# ANTES: recurso na raiz → resource "aws_vpc" "main"
# DEPOIS: dentro do módulo → module.networking.aws_vpc.main

terraform state mv aws_vpc.main module.networking.aws_vpc.main

# ══════════════════════════════════════════════════════════════════
# CENÁRIO 3: Extrair recurso de for_each para recurso individual
# ══════════════════════════════════════════════════════════════════

# ANTES: aws_subnet.private["us-east-1a"]
# DEPOIS: aws_subnet.private_1a

terraform state mv 'aws_subnet.private["us-east-1a"]' aws_subnet.private_1a

# ══════════════════════════════════════════════════════════════════
# CENÁRIO 4: Mover entre state files (projetos diferentes)
# ══════════════════════════════════════════════════════════════════

terraform state mv -state-out=../networking/terraform.tfstate \
  aws_vpc.main aws_vpc.main

O data source terraform_remote_state permite que um projeto Terraform leia outputs de outro projeto. Essencial para arquiteturas decompostas:

# PROJETO A: networking/ — Cria VPC e exporta outputs
# ══════════════════════════════════════════════════════════════════

output "vpc_id" {

  description = "Subnet group para RDS"

# PROJETO B: application/ — Lê outputs do networking
# ══════════════════════════════════════════════════════════════════

  config = {
    bucket = "cloudtrilhas-terraform-state"
    key    = "projects/networking/prod/terraform.tfstate"

  ami           = data.aws_ami.ubuntu.id
  instance_type = "t3.micro"

  # Referencia output do projeto networking
  subnet_id = data.terraform_remote_state.networking.outputs.private_subnet_ids[0]

  vpc_security_group_ids = [aws_security_group.app.id]

  tags = {
    Name = "app-server"
  }
}

  # ...
  db_subnet_group_name = data.terraform_remote_state.networking.outputs.database_subnet_group_name
}
⚠️ terraform_remote_state vs Data Sources Dedicados:

O terraform_remote_state cria acoplamento forte entre projetos. Alternativas mais flexíveis:

  • SSM Parameter Store: Escreva valores em SSM params e leia com aws_ssm_parameter
  • Data sources AWS: Use aws_vpc data source com tags para descobrir VPCs
  • Terraform Cloud: Workspaces com outputs compartilhados

Prefira terraform_remote_state apenas quando ambos os projetos são mantidos pela mesma equipe.

6.5 Workspaces — Isolamento de State

Workspaces permitem manter múltiplos states para o mesmo código (útil para ambientes):

Terraform WorkspacesAmbientes
# Listar workspaces
terraform workspace list
# * default

# Criar workspace para dev
terraform workspace new dev
# Created and switched to workspace "dev"!

# Criar workspace para prod
terraform workspace new prod

# Trocar entre workspaces
terraform workspace select dev

# No código, use terraform.workspace para condicionar:
resource "aws_instance" "app" {
  instance_type = terraform.workspace == "prod" ? "t3.large" : "t3.micro"

  tags = {
    Environment = terraform.workspace
  }
}

# No backend S3, cada workspace usa um key diferente:
# env:/dev/projects/app/terraform.tfstate
# env:/prod/projects/app/terraform.tfstate
⚠️ Workspaces vs Diretórios Separados:

Muitas equipes preferem diretórios separados (environments/dev/, environments/prod/) em vez de workspaces. Motivos:

  • Workspaces compartilham o mesmo código — difícil ter configs diferentes por ambiente
  • Diretórios separados permitem PRs independentes por ambiente
  • Mais fácil de entender para equipes novas
  • Workspaces são ótimos para ambientes efêmeros (feature branches, testing)

Entenda o conceito de módulos: por que existem, como funcionam, e por que são essenciais para escalar infraestrutura em equipes e organizações.

7.1 O que são Módulos?

Um módulo Terraform é simplesmente um diretório com arquivos .tf. Todo código Terraform que você já escreveu é tecnicamente um módulo (o "root module"). Módulos permitem encapsular, reutilizar e compor infraestrutura como blocos de LEGO.

🧱 Analogia — Blocos LEGO:

Imagine que você precisa construir 10 casas diferentes. Sem módulos, você define cada tijolo individualmente — 10 vezes. Com módulos, você cria um "bloco casa" parametrizável (cor, tamanho, número de andares) e simplesmente monta as 10 casas com parâmetros diferentes. Se descobrir um problema no design da casa, corrige uma vez e todas as 10 são atualizadas.

Conceitos Fundamentais de Módulos:

7.4 Escopo e Encapsulamento

Módulos criam um escopo isolado. Recursos dentro de um módulo não são diretamente acessíveis de fora — somente via outputs:

❌ Acesso Direto (Impossível)Erro
# Isto NÃO funciona!
# Não pode acessar recursos internos
# do módulo diretamente

resource "aws_instance" "app" {
  subnet_id = module.networking.aws_subnet.private.id
  #                             ^^^^^^^^^^^^^^^^
  # Error: Cannot access resources
  # inside a module directly
}
✅ Via Outputs (Correto)Interface
# O módulo EXPÕE via output:
# modules/vpc/outputs.tf
output "private_subnet_id" {
  value = aws_subnet.private.id
}

# O chamador USA o output:
resource "aws_instance" "app" {
  subnet_id = module.networking.private_subnet_id
  #           ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
  # Correto! Acessa via output do módulo
}

8. Criando Módulos Reutilizáveis

Construa um módulo VPC completo do zero: com variáveis validadas, outputs expressivos e design flexível para múltiplos ambientes.

8.1 Módulo VPC — variables.tf (Interface de Entrada)

As variáveis são a "API de entrada" do seu módulo. Boas variáveis tornam o módulo flexível mas seguro:

modules/vpc/variables.tfInputs
# ╔══════════════════════════════════════════════════════════════╗
# ║  VARIÁVEIS DO MÓDULO VPC — Interface de Entrada             ║
# ╚══════════════════════════════════════════════════════════════╝

variable "vpc_name" {
  description = "Nome da VPC (usado em tags e naming)"
  type        = string

  validation {
    condition     = length(var.vpc_name) >= 3 && length(var.vpc_name) <= 32
    error_message = "vpc_name deve ter entre 3 e 32 caracteres."
  }
}

variable "vpc_cidr" {
  description = "CIDR block para a VPC (ex: 10.0.0.0/16)"
  type        = string
  default     = "10.0.0.0/16"

  validation {
    condition     = can(cidrhost(var.vpc_cidr, 0))
    error_message = "vpc_cidr deve ser um CIDR válido (ex: 10.0.0.0/16)."
  }

  validation {
    condition     = tonumber(split("/", var.vpc_cidr)[1]) <= 24
    error_message = "CIDR deve ter máscara /24 ou menor (mais endereços)."
  }
}

variable "environment" {
  description = "Ambiente (afeta sizing e redundância)"
  type        = string

  validation {
    condition     = contains(["dev", "staging", "prod"], var.environment)
    error_message = "Ambiente deve ser: dev, staging ou prod."
  }
}

variable "availability_zones" {
  description = "Lista de AZs para distribuir subnets"
  type        = list(string)
  default     = ["us-east-1a", "us-east-1b", "us-east-1c"]

  validation {
    condition     = length(var.availability_zones) >= 2
    error_message = "Mínimo 2 AZs para alta disponibilidade."
  }
}

variable "enable_nat_gateway" {
  description = "Criar NAT Gateway para subnets privadas (custo: ~$32/mês por NAT)"
  type        = bool
  default     = true
}

variable "single_nat_gateway" {
  description = "Usar apenas 1 NAT Gateway (economia) vs 1 por AZ (HA)"
  type        = bool
  default     = false
}

variable "enable_dns_hostnames" {
  description = "Habilitar DNS hostnames na VPC"
  type        = bool
  default     = true
}

variable "tags" {
  description = "Tags adicionais para todos os recursos"
  type        = map(string)
  default     = {}
}

8.2 Módulo VPC — main.tf (Recursos)

O core do módulo com a lógica de criação dos recursos:

modules/vpc/main.tfCore
# ╔══════════════════════════════════════════════════════════════╗
# ║  MÓDULO VPC — RECURSOS PRINCIPAIS                           ║
# ╚══════════════════════════════════════════════════════════════╝

locals {
  # Calcula CIDRs para subnets automaticamente
  az_count        = length(var.availability_zones)
  public_subnets  = [for i in range(local.az_count) : cidrsubnet(var.vpc_cidr, 8, i)]
  private_subnets = [for i in range(local.az_count) : cidrsubnet(var.vpc_cidr, 8, i + local.az_count)]

  # Tags padrão para todos os recursos do módulo
  common_tags = merge(var.tags, {
    Environment = var.environment
    Module      = "vpc"
    ManagedBy   = "terraform"
  })

  # Quantos NAT Gateways criar
  nat_count = var.enable_nat_gateway ? (var.single_nat_gateway ? 1 : local.az_count) : 0
}

# ────────────────────────────────────────────────────────────────
# VPC
# ────────────────────────────────────────────────────────────────
resource "aws_vpc" "this" {
  cidr_block           = var.vpc_cidr
  enable_dns_hostnames = var.enable_dns_hostnames
  enable_dns_support   = true

  tags = merge(local.common_tags, {
    Name = "${var.vpc_name}-${var.environment}"
  })
}

# ────────────────────────────────────────────────────────────────
# INTERNET GATEWAY
# ────────────────────────────────────────────────────────────────
resource "aws_internet_gateway" "this" {
  vpc_id = aws_vpc.this.id

  tags = merge(local.common_tags, {
    Name = "${var.vpc_name}-${var.environment}-igw"
  })
}

# ────────────────────────────────────────────────────────────────
# SUBNETS PÚBLICAS
# ────────────────────────────────────────────────────────────────
resource "aws_subnet" "public" {
  count = local.az_count

  vpc_id                  = aws_vpc.this.id
  cidr_block              = local.public_subnets[count.index]
  availability_zone       = var.availability_zones[count.index]
  map_public_ip_on_launch = true

  tags = merge(local.common_tags, {
    Name = "${var.vpc_name}-${var.environment}-public-${var.availability_zones[count.index]}"
    Tier = "public"
  })
}

# ────────────────────────────────────────────────────────────────
# SUBNETS PRIVADAS
# ────────────────────────────────────────────────────────────────
resource "aws_subnet" "private" {
  count = local.az_count

  vpc_id            = aws_vpc.this.id
  cidr_block        = local.private_subnets[count.index]
  availability_zone = var.availability_zones[count.index]

  tags = merge(local.common_tags, {
    Name = "${var.vpc_name}-${var.environment}-private-${var.availability_zones[count.index]}"
    Tier = "private"
  })
}

# ────────────────────────────────────────────────────────────────
# NAT GATEWAY (Elastic IP + NAT)
# ────────────────────────────────────────────────────────────────
resource "aws_eip" "nat" {
  count  = local.nat_count
  domain = "vpc"

  tags = merge(local.common_tags, {
    Name = "${var.vpc_name}-${var.environment}-nat-eip-${count.index}"
  })
}

resource "aws_nat_gateway" "this" {
  count = local.nat_count

  allocation_id = aws_eip.nat[count.index].id
  subnet_id     = aws_subnet.public[count.index].id

  tags = merge(local.common_tags, {
    Name = "${var.vpc_name}-${var.environment}-nat-${count.index}"
  })

  depends_on = [aws_internet_gateway.this]
}

# ────────────────────────────────────────────────────────────────
# ROUTE TABLES
# ────────────────────────────────────────────────────────────────
resource "aws_route_table" "public" {
  vpc_id = aws_vpc.this.id

  route {
    cidr_block = "0.0.0.0/0"
    gateway_id = aws_internet_gateway.this.id
  }

  tags = merge(local.common_tags, {
    Name = "${var.vpc_name}-${var.environment}-public-rt"
  })
}

resource "aws_route_table_association" "public" {
  count = local.az_count

  subnet_id      = aws_subnet.public[count.index].id
  route_table_id = aws_route_table.public.id
}

resource "aws_route_table" "private" {
  count  = local.nat_count > 0 ? local.az_count : 0
  vpc_id = aws_vpc.this.id

  route {
    cidr_block     = "0.0.0.0/0"
    nat_gateway_id = aws_nat_gateway.this[var.single_nat_gateway ? 0 : count.index].id
  }

  tags = merge(local.common_tags, {
    Name = "${var.vpc_name}-${var.environment}-private-rt-${count.index}"
  })
}

resource "aws_route_table_association" "private" {
  count = local.nat_count > 0 ? local.az_count : 0

  subnet_id      = aws_subnet.private[count.index].id
  route_table_id = aws_route_table.private[count.index].id
}

8.4 Módulo VPC — versions.tf

Declare versões mínimas de providers e Terraform para garantir compatibilidade:

modules/vpc/versions.tfConstraints
terraform {
  # Versão mínima do Terraform para usar este módulo
  required_version = ">= 1.5.0"

  required_providers {
    aws = {
      source  = "hashicorp/aws"
      # Aceita qualquer patch da v5.x (ex: 5.0.0, 5.10.0, 5.99.0)
      version = ">= 5.0.0, < 6.0.0"
    }
  }
}

# NOTA: NÃO declare o bloco provider {} aqui!
# O provider é configurado no root module e passado implicitamente.

9.1 O Bloco module — Sintaxe Base

Para usar um módulo, declare um bloco module no seu root module:

# ║  CHAMADA DO MÓDULO VPC — AMBIENTE DE PRODUÇÃO               ║
# ╚══════════════════════════════════════════════════════════════╝

module "vpc_prod" {
  # Fonte do módulo (onde encontrar o código)
  source = "../../modules/vpc"

  # Inputs obrigatórios (variáveis sem default)
  vpc_name    = "cloudtrilhas"
  environment = "prod"

  # Inputs opcionais (sobrescrevendo defaults)
  vpc_cidr           = "10.0.0.0/16"
  availability_zones = ["us-east-1a", "us-east-1b", "us-east-1c"]
  enable_nat_gateway = true
  single_nat_gateway = false  # HA: um NAT por AZ em prod

  tags = {
    Project   = "cloudtrilhas"
    CostCenter = "engineering"
  }
}

# ──────────────────────────────────────────────────────────────
# ACESSANDO OUTPUTS DO MÓDULO
# ──────────────────────────────────────────────────────────────

# Use em outros recursos:
resource "aws_instance" "app" {
  ami           = data.aws_ami.ubuntu.id
  instance_type = "t3.large"
  subnet_id     = module.vpc_prod.private_subnet_ids[0]

  tags = {
    Name = "app-prod"
  }
}

# Use em outputs do root module:
output "vpc_id" {
  value = module.vpc_prod.vpc_id
}

output "nat_ips" {

9.3 Versionamento de Módulos

O controle de versão é crítico para módulos — especialmente em produção:

Version ConstraintsPinning
# ══════════════════════════════════════════════════════════════════
# CONSTRAINTS DE VERSÃO (mesmo formato de provider versions)
# ══════════════════════════════════════════════════════════════════

# Versão exata — mais seguro para produção
module "vpc" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "5.5.1"
}

# Aceita patches (~> pessimistic constraint)
module "vpc" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "~> 5.5"  # Aceita 5.5.x, não aceita 5.6.0
}

# Aceita minor versions
module "vpc" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "~> 5.0"  # Aceita 5.x.x, não aceita 6.0.0
}

# Range explícito
module "vpc" {
  source  = "terraform-aws-modules/vpc/aws"
  version = ">= 5.0.0, < 6.0.0"
}

# ══════════════════════════════════════════════════════════════════
# PARA MÓDULOS GIT: use ?ref= com tags semver
# ══════════════════════════════════════════════════════════════════
module "vpc" {
  source = "git::https://github.com/org/modules.git//vpc?ref=v2.1.0"
  # NUNCA use ref=main em produção! Sempre uma tag específica.
}
⚠️ Regra para Ambientes:
  • Produção: SEMPRE versão exata (version = "5.5.1") ou tag Git fixa
  • Staging: Pessimistic constraint (version = "~> 5.5") — testa patches antes de prod
  • Dev: Pode usar source local para desenvolvimento rápido

10.3 Como Avaliar um Módulo antes de Usar

Nem todo módulo no Registry é adequado para produção. Checklist de avaliação:

✅ Checklist para Avaliar Módulos:
  • Manutenção: Último commit há menos de 3 meses? Issues sendo respondidas?
  • Downloads: Módulos com milhões de downloads são mais battle-tested
  • Versão: Segue semver? Está em v1.0+ (estável)?
  • Documentação: Inputs/outputs documentados? Exemplos de uso?
  • Código: Leia o main.tf — entenda o que o módulo realmente cria
  • Licença: MIT/Apache 2.0 são seguras para uso comercial
  • Provider version: Compatível com a versão que você usa?
  • Breaking changes: CHANGELOG menciona breaking changes na versão atual?
⚠️ Riscos de Módulos da Comunidade:
  • Supply chain attack: Módulo pode ser atualizado com código malicioso
  • Abandono: Mantenedor pode abandonar o projeto
  • Over-engineering: Módulo pode criar mais recursos do que você precisa
  • Mitigação: Pin exato de versão, leia o código, fork se necessário

11.2 Autenticação OIDC — Zero Secrets Estáticos

OIDC (OpenID Connect) permite que GitHub Actions assuma uma IAM Role na AWS sem armazenar access keys como secrets. É a abordagem recomendada pela AWS e GitHub:

oidc.tf — Infraestrutura para OIDCSegurança
# ╔══════════════════════════════════════════════════════════════╗
# ║  GITHUB OIDC — AUTENTICAÇÃO SEM SECRETS                     ║
# ╚══════════════════════════════════════════════════════════════╝

# 1. Identity Provider — conecta GitHub à AWS
resource "aws_iam_openid_connect_provider" "github" {
  url = "https://token.actions.githubusercontent.com"

  # Audience esperada (padrão para GitHub Actions)
  client_id_list = ["sts.amazonaws.com"]

  # Thumbprint do certificado TLS do GitHub
  thumbprint_list = ["6938fd4d98bab03faadb97b34396831e3780aea1"]

  tags = {
    Name      = "GitHub Actions OIDC"
    ManagedBy = "terraform"
  }
}

# 2. IAM Role que o GitHub Actions vai assumir
resource "aws_iam_role" "github_actions" {
  name = "github-actions-terraform"

  assume_role_policy = jsonencode({
    Version = "2012-10-17"
    Statement = [
      {
        Effect = "Allow"
        Principal = {
          Federated = aws_iam_openid_connect_provider.github.arn
        }
        Action = "sts:AssumeRoleWithWebIdentity"
        Condition = {
          StringEquals = {
            # CRÍTICO: Restringe ao seu repositório específico!
            "token.actions.githubusercontent.com:aud" = "sts.amazonaws.com"
          }
          StringLike = {
            # Formato: repo:{owner}/{repo}:ref:refs/heads/{branch}
            "token.actions.githubusercontent.com:sub" = "repo:seu-org/seu-repo:*"
          }
        }
      }
    ]
  })

  tags = {
    Name      = "GitHub Actions Terraform Role"
    ManagedBy = "terraform"
  }
}

# 3. Policy com permissões necessárias para Terraform
resource "aws_iam_role_policy_attachment" "github_actions_admin" {
  role       = aws_iam_role.github_actions.name
  # Em produção, use policy customizada com least privilege!
  policy_arn = "arn:aws:iam::aws:policy/AdministratorAccess"
}

# 4. Output o ARN da role para usar no workflow
output "github_actions_role_arn" {
  value       = aws_iam_role.github_actions.arn
  description = "ARN da role para configurar no GitHub Actions workflow"
}

11.3 GitHub Actions Workflow — Completo

Workflow completo com validação em PR e apply em merge na main:

.github/workflows/terraform.ymlCI/CD
# ╔══════════════════════════════════════════════════════════════╗
# ║  GITHUB ACTIONS — TERRAFORM CI/CD PIPELINE                  ║
# ╚══════════════════════════════════════════════════════════════╝

name: "Terraform CI/CD"

on:
  push:
    branches: [main]
    paths: ["terraform/**"]  # Só roda se infra mudou
  pull_request:
    branches: [main]
    paths: ["terraform/**"]

# Permissões para OIDC funcionar
permissions:
  id-token: write   # Necessário para OIDC
  contents: read    # Leitura do repo
  pull-requests: write  # Comentar no PR

env:
  TF_VERSION: "1.7.0"
  AWS_REGION: "us-east-1"
  WORKING_DIR: "terraform/environments/prod"

jobs:
  # ──────────────────────────────────────────────────────────────
  # JOB 1: VALIDAÇÃO E PLAN (roda em TODO PR)
  # ──────────────────────────────────────────────────────────────
  plan:
    name: "Terraform Plan"
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: ${{ env.WORKING_DIR }}

    steps:
      - name: Checkout código
        uses: actions/checkout@v4

      - name: Setup Terraform
        uses: hashicorp/setup-terraform@v3
        with:
          terraform_version: ${{ env.TF_VERSION }}

      - name: Configurar AWS Credentials (OIDC)
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/github-actions-terraform
          aws-region: ${{ env.AWS_REGION }}

      - name: Terraform Format Check
        id: fmt
        run: terraform fmt -check -recursive
        continue-on-error: true

      - name: Terraform Init
        id: init
        run: terraform init -input=false

      - name: Terraform Validate
        id: validate
        run: terraform validate -no-color

      - name: Terraform Plan
        id: plan
        run: terraform plan -no-color -input=false -out=tfplan
        continue-on-error: true

      - name: Postar Plan no PR
        if: github.event_name == 'pull_request'
        uses: actions/github-script@v7
        with:
          github-token: ${{ secrets.GITHUB_TOKEN }}
          script: |
            const output = `### Terraform Plan 📋

            #### Format: \`${{ steps.fmt.outcome }}\`
            #### Init: \`${{ steps.init.outcome }}\`
            #### Validate: \`${{ steps.validate.outcome }}\`
            #### Plan: \`${{ steps.plan.outcome }}\`

            
Ver Plan Completo

            \`\`\`terraform
            ${{ steps.plan.outputs.stdout }}
            \`\`\`

            


            *Pushed by: @${{ github.actor }}*`;

            github.rest.issues.createComment({
              issue_number: context.issue.number,
              owner: context.repo.owner,
              repo: context.repo.repo,
              body: output
            });

      - name: Plan Status
        if: steps.plan.outcome == 'failure'
        run: exit 1

  # ──────────────────────────────────────────────────────────────
  # JOB 2: APPLY (só na main, após merge)
  # ──────────────────────────────────────────────────────────────
  apply:
    name: "Terraform Apply"
    runs-on: ubuntu-latest
    needs: plan
    if: github.ref == 'refs/heads/main' && github.event_name == 'push'

    # Environment com proteção (requer aprovação manual)
    environment:
      name: production
      url: https://console.aws.amazon.com

    defaults:
      run:
        working-directory: ${{ env.WORKING_DIR }}

    steps:
      - name: Checkout código
        uses: actions/checkout@v4

      - name: Setup Terraform
        uses: hashicorp/setup-terraform@v3
        with:
          terraform_version: ${{ env.TF_VERSION }}

      - name: Configurar AWS Credentials (OIDC)
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/github-actions-terraform
          aws-region: ${{ env.AWS_REGION }}

      - name: Terraform Init
        run: terraform init -input=false

      - name: Terraform Apply
        run: terraform apply -auto-approve -input=false

11.4 Environment Protection Rules

Configure proteções no GitHub para garantir que applies em produção passem por aprovação humana:

🛡️ Configuração de Proteção (GitHub Settings):
  1. Vá em Settings → Environments → New Environment → "production"
  2. Ative "Required reviewers" → adicione 1-2 aprovadores
  3. Ative "Wait timer" → 5 minutos (tempo para revisão final)
  4. (Opcional) "Deployment branches" → apenas "main"

Com isso, o job apply fica pausado até um reviewer aprovar no GitHub.

⚠️ Boas Práticas de CI/CD para Terraform:
  • Nunca use -auto-approve em PR: Apenas na main após merge aprovado
  • Pin todas as versões: Terraform, providers, Actions (use SHA em vez de tag)
  • State lock: DynamoDB garante que pipeline não conflita com outro
  • Separação de concerns: Um workflow por ambiente (dev, staging, prod)
  • Terraform plan artifact: Salve o plan file e use no apply para garantir que aplica exatamente o que foi revisado
  • Notificações: Configure Slack/Teams alerts para applies em produção

Exercício 1 — Bucket S3 com Lifecycle Rules

Objetivo: Criar um bucket S3 para armazenar logs de aplicação com lifecycle rules otimizadas para custo.

📋 Requisitos:
  • Bucket com nome no padrão: {projeto}-{env}-logs
  • Versionamento habilitado
  • Criptografia AES256
  • Bloqueio total de acesso público
  • Lifecycle: Standard → Standard-IA (30 dias) → Glacier (90 dias) → Delete (365 dias)
  • Versões anteriores: Glacier após 7 dias, delete após 30 dias
  • Limpar multipart uploads após 3 dias
💡 Ver Solução do Exercício 1

      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}

  region = var.aws_region
}

variable "aws_region" {
  default = "us-east-1"
}

variable "project" {
  default = "cloudtrilhas"
}

variable "environment" {
  default = "dev"
}

# BUCKET PRINCIPAL
# ────────────────────────────────────────────────────────────────

  bucket = "${var.project}-${var.environment}-logs"

  tags = {
    Name        = "${var.project}-${var.environment}-logs"
    Environment = var.environment
    Purpose     = "Application logs storage"
    ManagedBy   = "terraform"
  }
}

# ────────────────────────────────────────────────────────────────
# VERSIONAMENTO
# ────────────────────────────────────────────────────────────────
resource "aws_s3_bucket_versioning" "logs" {
  bucket = aws_s3_bucket.logs.id

  versioning_configuration {
    status = "Enabled"
  }
}

# ────────────────────────────────────────────────────────────────
# CRIPTOGRAFIA
# ────────────────────────────────────────────────────────────────
resource "aws_s3_bucket_server_side_encryption_configuration" "logs" {
  bucket = aws_s3_bucket.logs.id

  rule {
    apply_server_side_encryption_by_default {
      sse_algorithm = "AES256"
    }
    bucket_key_enabled = true
  }
}

# ────────────────────────────────────────────────────────────────
# BLOQUEIO DE ACESSO PÚBLICO
# ────────────────────────────────────────────────────────────────
resource "aws_s3_bucket_public_access_block" "logs" {
  bucket = aws_s3_bucket.logs.id

  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
}

# ────────────────────────────────────────────────────────────────
# LIFECYCLE RULES
# ────────────────────────────────────────────────────────────────
resource "aws_s3_bucket_lifecycle_configuration" "logs" {
  bucket = aws_s3_bucket.logs.id

  depends_on = [aws_s3_bucket_versioning.logs]

  # Regra para versões atuais
  rule {
    id     = "logs-transition"
    status = "Enabled"

    filter {
      prefix = ""
    }

    transition {
      days          = 30
      storage_class = "STANDARD_IA"
    }

    transition {
      days          = 90
      storage_class = "GLACIER"
    }

    expiration {
      days = 365
    }

    # Versões anteriores
    noncurrent_version_transition {
      noncurrent_days = 7
      storage_class   = "GLACIER"
    }

    noncurrent_version_expiration {
      noncurrent_days = 30
    }
  }

  # Limpeza de multipart uploads
  rule {
    id     = "abort-multipart"
    status = "Enabled"

    filter {
      prefix = ""
    }

    abort_incomplete_multipart_upload {
      days_after_initiation = 3
    }
  }
}

# ────────────────────────────────────────────────────────────────

# ────────────────────────────────────────────────────────────────

  value = aws_s3_bucket.logs.id
}

  value = aws_s3_bucket.logs.arn

Exercício 4 — Pipeline CI/CD Completo

Objetivo: Criar um workflow GitHub Actions para automatizar o ciclo Terraform com autenticação OIDC.

📋 Requisitos:
  • Workflow que roda em PR e push na main
  • Jobs separados: validate, plan, apply
  • Autenticação via OIDC (sem secrets AWS estáticos)
  • Plan postado como comentário no PR
  • Apply apenas na main com environment protection
  • Cache do .terraform para acelerar init
  • Notificação de sucesso/falha
💡 Ver Solução do Exercício 4
.github/workflows/terraform-complete.ymlSolução
name: "Terraform Complete Pipeline"

on:
  push:
    branches: [main]
    paths: ["terraform/**"]
  pull_request:
    branches: [main]
    paths: ["terraform/**"]

permissions:
  id-token: write
  contents: read
  pull-requests: write

env:
  TF_VERSION: "1.7.0"
  AWS_REGION: "us-east-1"
  WORKING_DIR: "terraform/environments/prod"
  TF_IN_AUTOMATION: "true"

jobs:
  validate:
    name: "Validate"
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: ${{ env.WORKING_DIR }}
    steps:
      - uses: actions/checkout@v4

      - uses: hashicorp/setup-terraform@v3
        with:
          terraform_version: ${{ env.TF_VERSION }}

      - name: Cache Terraform plugins
        uses: actions/cache@v4
        with:
          path: ${{ env.WORKING_DIR }}/.terraform
          key: terraform-${{ hashFiles('**/.terraform.lock.hcl') }}

      - name: Format Check
        run: terraform fmt -check -recursive -diff

      - name: Init (backend disabled for validate)
        run: terraform init -backend=false

      - name: Validate
        run: terraform validate

  plan:
    name: "Plan"
    runs-on: ubuntu-latest
    needs: validate
    defaults:
      run:
        working-directory: ${{ env.WORKING_DIR }}
    steps:
      - uses: actions/checkout@v4

      - uses: hashicorp/setup-terraform@v3
        with:
          terraform_version: ${{ env.TF_VERSION }}

      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: ${{ vars.AWS_ROLE_ARN }}
          aws-region: ${{ env.AWS_REGION }}

      - name: Init
        run: terraform init -input=false

      - name: Plan
        id: plan
        run: |
          terraform plan -no-color -input=false -detailed-exitcode -out=tfplan 2>&1 | tee plan_output.txt
        continue-on-error: true

      - name: Comment PR
        if: github.event_name == 'pull_request'
        uses: actions/github-script@v7
        with:
          script: |
            const fs = require('fs');
            const plan = fs.readFileSync('${{ env.WORKING_DIR }}/plan_output.txt', 'utf8');
            const truncated = plan.length > 60000 ? plan.substring(0, 60000) + '\n... (truncated)' : plan;
            await github.rest.issues.createComment({
              issue_number: context.issue.number,
              owner: context.repo.owner,
              repo: context.repo.repo,
              body: `### 📋 Terraform Plan\n\n
Ver Plan\n\n\`\`\`\n${truncated}\n\`\`\`\n
`
            });

      - name: Upload Plan
        uses: actions/upload-artifact@v4
        with:
          name: tfplan
          path: ${{ env.WORKING_DIR }}/tfplan

  apply:
    name: "Apply"
    runs-on: ubuntu-latest
    needs: plan
    if: github.ref == 'refs/heads/main' && github.event_name == 'push'
    environment: production
    defaults:
      run:
        working-directory: ${{ env.WORKING_DIR }}
    steps:
      - uses: actions/checkout@v4

      - uses: hashicorp/setup-terraform@v3
        with:
          terraform_version: ${{ env.TF_VERSION }}

      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: ${{ vars.AWS_ROLE_ARN }}
          aws-region: ${{ env.AWS_REGION }}

      - name: Init
        run: terraform init -input=false

      - name: Download Plan
        uses: actions/download-artifact@v4
        with:
          name: tfplan
          path: ${{ env.WORKING_DIR }}

      - name: Apply
        run: terraform apply -auto-approve -input=false tfplan
