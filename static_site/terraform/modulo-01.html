Conceitos Fundamentais

1. O que é Terraform?

Entenda Infrastructure as Code (IaC), por que o Terraform se tornou o padrão da indústria e como ele se compara com outras ferramentas do mercado.

1.1 Infrastructure as Code (IaC) — A Revolução

Antes da IaC, engenheiros configuravam servidores manualmente — clicando em consoles web, rodando comandos SSH um a um, documentando passos em wikis que ficavam desatualizadas em semanas. Esse processo era lento, propenso a erros e impossível de reproduzir de forma consistente.

Infrastructure as Code é o paradigma onde toda a infraestrutura é descrita em arquivos de código versionáveis, auditáveis e reproduzíveis. Assim como você versiona código da aplicação no Git, a infraestrutura também vive em repositórios.

🏗️ Analogia — A Planta do Edifício:

Imagine construir um prédio de 20 andares sem planta arquitetônica. Cada pedreiro faria do seu jeito, não haveria padrão, e se o prédio precisasse ser reconstruído em outro terreno, seria impossível replicá-lo. O Terraform é a planta arquitetônica da sua infraestrutura — descreve exatamente o que deve existir, onde, e como os componentes se conectam.

Benefícios Concretos da IaC:

Aspecto Manual (Console/CLI) Infrastructure as Code
Reprodutibilidade❌ Depende de documentação✅ 100% reproduzível
Versionamento❌ Sem histórico✅ Git com diff e blame
Code Review❌ Impossível✅ Pull Requests
Velocidade❌ Minutos/horas por recurso✅ Centenas de recursos em minutos
Consistência❌ Drift inevitável✅ Estado desejado garantido
Disaster Recovery❌ Reconstrução manual✅ terraform apply e pronto
Colaboração❌ "Quem mexeu nisso?"✅ Commits com autor e motivo

1.2 O que é Terraform Especificamente?

Terraform é uma ferramenta de IaC open-source criada pela HashiCorp em 2014. Escrita em Go, ela permite provisionar e gerenciar infraestrutura em qualquer cloud (AWS, Azure, GCP) e centenas de outros serviços (GitHub, Datadog, Kubernetes, etc.) usando uma linguagem declarativa chamada HCL (HashiCorp Configuration Language).

Conceito CentralDeclarativo
# Você declara O QUE quer — não COMO fazer
# Terraform calcula os passos necessários automaticamente

resource "aws_vpc" "main" {
  cidr_block           = "10.0.0.0/16"
  enable_dns_hostnames = true
  enable_dns_support   = true

  tags = {
    Name        = "vpc-producao"
    Environment = "production"
    ManagedBy   = "terraform"
  }
}

# Resultado: Terraform verifica o estado atual,
# compara com o desejado, e executa apenas as mudanças necessárias

Características Principais:

  • Multi-Cloud: Um único workflow para AWS, Azure, GCP, e 3000+ providers
  • Declarativo: Descreva o estado final desejado, não os passos
  • Idempotente: Rodar múltiplas vezes produz o mesmo resultado
  • Plano de Execução: Mostra exatamente o que será alterado antes de aplicar
  • Grafo de Dependências: Entende a ordem de criação/destruição automaticamente
  • State Management: Mantém um mapa entre código e recursos reais

1.3 Declarativo vs Imperativo

Essa distinção é fundamental para entender por que o Terraform funciona da forma que funciona.

Aspecto Imperativo (Ansible, Scripts) Declarativo (Terraform, CloudFormation)
Você descreveOS PASSOS para chegar ao resultadoO RESULTADO final desejado
Analogia"Vire à direita, ande 200m, vire à esquerda...""Quero estar no restaurante X"
IdempotênciaVocê precisa implementarBuilt-in (automática)
Drift DetectionDifícilNativo (plan mostra diferenças)
Exemplo"Crie a VPC, depois crie a subnet...""Deve existir uma VPC com esta subnet"
Imperativo (Shell Script)Passos
# Precisa verificar se já existe
# Precisa tratar erros em cada passo
# Rodar 2x pode causar duplicação

aws ec2 create-vpc --cidr-block 10.0.0.0/16
aws ec2 create-subnet --vpc-id $VPC_ID \
  --cidr-block 10.0.1.0/24
aws ec2 create-internet-gateway
aws ec2 attach-internet-gateway \
  --vpc-id $VPC_ID --igw-id $IGW_ID
Declarativo (Terraform)Estado
# Descreve o resultado final
# Terraform calcula o que precisa fazer
# Rodar 2x = "No changes needed"

resource "aws_vpc" "main" {
  cidr_block = "10.0.0.0/16"
}
resource "aws_subnet" "public" {
  vpc_id     = aws_vpc.main.id
  cidr_block = "10.0.1.0/24"
}
resource "aws_internet_gateway" "igw" {
  vpc_id = aws_vpc.main.id
}

  • Ecossistema: 3000+ providers no Terraform Registry — desde AWS até PagerDuty
  • Maturidade: 10+ anos de desenvolvimento, adoção massiva na indústria

Arquitetura Interna

2. Como o Terraform Funciona

Entenda a arquitetura interna do Terraform: providers, state file, o ciclo plan/apply e o grafo de dependências que torna tudo possível.

2.1 Arquitetura do Terraform

O Terraform possui uma arquitetura elegante baseada em três componentes principais:

🔧 Arquitetura em Camadas: 

┌─────────────────────────────────────────────────────────────┐
│                    TERRAFORM CORE                             │
│  (Binário Go — lê HCL, gera grafo, gerencia state)          │
├─────────────────────────────────────────────────────────────┤
│                    PROVIDER PLUGINS                           │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐   │
│  │   AWS    │  │  Azure   │  │   GCP    │  │  GitHub  │   │
│  │ Provider │  │ Provider │  │ Provider │  │ Provider │   │
│  └────┬─────┘  └────┬─────┘  └────┬─────┘  └────┬─────┘   │
├───────┼──────────────┼──────────────┼──────────────┼────────┤
│       ▼              ▼              ▼              ▼         │
│              CLOUD PROVIDER APIs                              │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐   │
│  │ AWS API  │  │Azure API │  │ GCP API  │  │GitHub API│   │
│  └──────────┘  └──────────┘  └──────────┘  └──────────┘   │
└─────────────────────────────────────────────────────────────┘

Componentes Explicados:

  • Terraform Core: O binário principal. Lê arquivos .tf, constrói o grafo de dependências, gerencia o state e orquestra os providers. Não sabe nada sobre AWS ou Azure — delega tudo aos providers.
  • Providers: Plugins que implementam a comunicação com APIs externas. O provider AWS, por exemplo, traduz resource "aws_vpc" em chamadas para a API EC2 da AWS.
  • State File: Arquivo JSON que mapeia seus recursos declarados no código para os recursos reais existentes na cloud. É o "cérebro" do Terraform.

2.2 O State File — O GPS do Terraform

O state é possivelmente o conceito mais importante (e mais incompreendido) do Terraform. Sem ele, o Terraform não saberia o que já existe na cloud.

🗺️ Analogia — GPS do Projeto:

Imagine que você está dirigindo para um destino (estado desejado). O state file é seu GPS — ele sabe exatamente onde você está agora (estado atual). O terraform plan é a rota calculada entre sua posição atual e o destino. Sem GPS, você não sabe onde está e não pode calcular o caminho.

⚠️ NUNCA faça isso com o State:
  • ❌ Editar manualmente o arquivo .tfstate
  • ❌ Deletar o state sem backup (você "perde" todos os recursos)
  • ❌ Armazenar state apenas localmente em projetos com equipe
  • ❌ Commitar o state no Git (pode conter secrets!)
  • ✅ Use remote backend (S3 + DynamoDB) para projetos reais

2.4 Grafo de Dependências

O Terraform constrói automaticamente um DAG (Directed Acyclic Graph) — um grafo direcionado sem ciclos — que determina a ordem de criação e destruição dos recursos.

📊 Exemplo de Grafo de Dependências: 

                    ┌─────────────┐
                    │   aws_vpc   │
                    │    main     │
                    └──────┬──────┘
                           │
              ┌────────────┼────────────┐
              ▼            ▼            ▼
      ┌──────────────┐ ┌──────────┐ ┌──────────────┐
      │ aws_subnet   │ │ aws_igw  │ │ aws_subnet   │
      │   public     │ │   main   │ │   private    │
      └──────┬───────┘ └────┬─────┘ └──────┬───────┘
              │              │              │
              ▼              ▼              ▼
      ┌──────────────┐ ┌──────────┐ ┌──────────────┐
      │ aws_route    │ │aws_nat_gw│ │ aws_route    │
      │ table_public │ │          │ │ table_private│
      └──────────────┘ └──────────┘ └──────────────┘

Ordem de CRIAÇÃO:  VPC → Subnets + IGW → Route Tables + NAT
Ordem de DESTRUIÇÃO: inversa (NAT → Subnets → VPC)

Referências implícitas criam dependências automáticas. Quando você escreve vpc_id = aws_vpc.main.id, o Terraform sabe que a subnet depende da VPC. Em casos raros onde não há referência direta, use depends_on.

3. Instalação e Configuração

Instale o Terraform no seu sistema operacional, configure credenciais AWS e use tfenv para gerenciar múltiplas versões.

3.1 Instalação no Linux (Ubuntu/Debian)

A HashiCorp mantém repositórios APT oficiais para distribuições baseadas em Debian:

Instalação via APT (Recomendado)Linux
# 1. Instalar dependências necessárias
sudo apt-get update && sudo apt-get install -y \
  gnupg \
  software-properties-common \
  curl

# 2. Adicionar a chave GPG da HashiCorp
curl -fsSL https://apt.releases.hashicorp.com/gpg | \
  sudo gpg --dearmor -o /usr/share/keyrings/hashicorp-archive-keyring.gpg

# 3. Adicionar o repositório oficial
echo "deb [signed-by=/usr/share/keyrings/hashicorp-archive-keyring.gpg] \
  https://apt.releases.hashicorp.com $(lsb_release -cs) main" | \
  sudo tee /etc/apt/sources.list.d/hashicorp.list

# 4. Instalar o Terraform
sudo apt-get update && sudo apt-get install terraform

# 5. Verificar a instalação
terraform -version
# Terraform v1.7.x on linux_amd64

3.4 tfenv — Gerenciador de Versões

Em projetos reais, diferentes repositórios podem exigir versões diferentes do Terraform. O tfenv resolve isso (similar ao nvm para Node.js ou pyenv para Python).

Instalação e Uso do tfenvVersões
# Instalar tfenv (Linux/macOS)
git clone https://github.com/tfutils/tfenv.git ~/.tfenv
echo 'export PATH="$HOME/.tfenv/bin:$PATH"' >> ~/.bashrc
source ~/.bashrc

# Listar versões disponíveis
tfenv list-remote

# Instalar versão específica
tfenv install 1.7.0
tfenv install 1.6.6

# Definir versão global (padrão)
tfenv use 1.7.0

# Definir versão por projeto (cria .terraform-version)
echo "1.7.0" > .terraform-version

# Listar versões instaladas
tfenv list
# * 1.7.0 (set by /home/user/projeto/.terraform-version)
#   1.6.6

# O tfenv lê .terraform-version automaticamente!
# Ao entrar na pasta do projeto, usa a versão correta
💡 Best Practice:

Sempre inclua um arquivo .terraform-version na raiz do seu projeto. Isso garante que toda a equipe use a mesma versão, evitando incompatibilidades de state e syntax.

4. Estrutura de Arquivos

Aprenda a convenção de nomes e organização de arquivos que a comunidade Terraform adota como padrão em projetos de produção.

4.1 Convenção de Arquivos

O Terraform lê todos os arquivos .tf de um diretório como se fossem um único arquivo. A separação em múltiplos arquivos é uma convenção para organização humana — o Terraform não se importa com nomes de arquivos.

📁 Estrutura Padrão de Projeto Terraform: 

terraform-vpc-project/
├── .terraform-version      # Versão do Terraform (tfenv)
├── .gitignore              # Ignorar .terraform/, *.tfstate, etc.
├── README.md               # Documentação do projeto
├── providers.tf            # Bloco terraform {} e provider {}
├── variables.tf            # Declaração de TODAS as variáveis
├── terraform.tfvars        # Valores das variáveis (não commitado)
├── main.tf                 # Recursos principais (VPC, Subnets)
├── outputs.tf              # Outputs do projeto
├── data.tf                 # Data sources (AMIs, AZs, etc.)
├── locals.tf               # Variáveis locais calculadas
└── versions.tf             # (alternativa) required_providers

Após terraform init:
├── .terraform/             # Providers baixados (não commitar!)
│   └── providers/
│       └── registry.terraform.io/
│           └── hashicorp/aws/5.31.0/
├── .terraform.lock.hcl     # Lock de versões (COMMITAR!)
└── terraform.tfstate       # State local (não commitar!)

│   └── prod/
│       ├── main.tf            # Chama módulos com valores prod
│       ├── terraform.tfvars   # Valores para prod
│       ├── providers.tf
│       └── backend.tf         # State no S3 (bucket-prod)

Essa estrutura permite que cada ambiente tenha seu próprio state isolado, enquanto os módulos garantem consistência na definição dos recursos.

Linguagem

5. HCL — HashiCorp Configuration Language

Domine a sintaxe da linguagem usada pelo Terraform: blocos, argumentos, expressões, tipos de dados, funções built-in e interpolação.

5.1 Anatomia de um Bloco HCL

HCL é uma linguagem declarativa projetada para ser legível por humanos e máquinas. Tudo em HCL é organizado em blocos.

Estrutura de um BlocoSintaxe
# Anatomia completa de um bloco HCL:
#
# TIPO    LABEL_1    LABEL_2    CORPO
# ↓       ↓          ↓          ↓
resource "aws_vpc"   "main"    {
  # ARGUMENTO = VALOR
  cidr_block = "10.0.0.0/16"    # string
  
  # ARGUMENTO = EXPRESSÃO
  enable_dns_hostnames = true    # boolean
  
  # BLOCO ANINHADO (sem =)
  tags = {                       # map
    Name        = "vpc-main"
    Environment = var.environment
    CreatedBy   = "terraform"
  }
}

# Tipos de blocos mais comuns:
# terraform {}      — Configuração do Terraform
# provider ""  {}   — Configuração de providers
# resource "" "" {} — Recursos a criar/gerenciar
# data "" "" {}     — Data sources (consultas)
# variable "" {}    — Variáveis de entrada
# output "" {}      — Valores de saída
# locals {}         — Variáveis locais
# module "" {}      — Chamada de módulos

5.2 Tipos de Dados

HCL suporta tipos primitivos e complexos (coleções):

Tipos Primitivos e ComplexosTipos
# ═══════════════════════════════════════════
# TIPOS PRIMITIVOS
# ═══════════════════════════════════════════

# string — texto entre aspas duplas

  type    = string
  default = "us-east-1"
}

# ═══════════════════════════════════════════

}

    cidr_block           = string

}

# tuple([]) — como list, mas cada posição tem tipo diferente
variable "rule" {
  type    = tuple([string, number, string])
  default = ["tcp", 443, "0.0.0.0/0"]
}

5.5 Loops e Iteração

HCL oferece mecanismos poderosos para criar múltiplos recursos ou transformar dados:

count, for_each, for expressionLoops
# ═══════════════════════════════════════════
# COUNT — criar N cópias de um recurso
# ═══════════════════════════════════════════
resource "aws_subnet" "public" {
  count             = 3   # Cria 3 subnets
  vpc_id            = aws_vpc.main.id
  cidr_block        = cidrsubnet(var.vpc_cidr, 8, count.index)
  availability_zone = data.aws_availability_zones.available.names[count.index]
  
  tags = {
    Name = "subnet-public-${count.index + 1}"
  }
}
# Acesso: aws_subnet.public[0].id, aws_subnet.public[1].id ...

# ═══════════════════════════════════════════
# FOR_EACH — criar recursos a partir de map/set
# ═══════════════════════════════════════════
variable "subnets" {
  default = {
    public-1  = { cidr = "10.0.1.0/24", az = "us-east-1a", public = true }
    public-2  = { cidr = "10.0.2.0/24", az = "us-east-1b", public = true }
    private-1 = { cidr = "10.0.10.0/24", az = "us-east-1a", public = false }
  }
}

resource "aws_subnet" "this" {
  for_each = var.subnets

  vpc_id                  = aws_vpc.main.id
  cidr_block              = each.value.cidr
  availability_zone       = each.value.az
  map_public_ip_on_launch = each.value.public

  tags = { Name = "subnet-${each.key}" }
}
# Acesso: aws_subnet.this["public-1"].id

# ═══════════════════════════════════════════
# FOR EXPRESSION — transformar coleções
# ═══════════════════════════════════════════
# Gerar lista de IDs
subnet_ids = [for s in aws_subnet.this : s.id]

# Gerar map filtrado
public_subnets = {
  for k, s in aws_subnet.this : k => s.id
  if s.map_public_ip_on_launch == true
}

# Transformar lista em outra lista
upper_names = [for name in var.names : upper(name)]
⚠️ count vs for_each — Quando usar qual?
  • count: Use para recursos idênticos onde só muda o índice. Problema: remover item do meio reordena tudo!
  • for_each: Use quando cada recurso tem identidade própria (nome). Remover um item não afeta os outros.
  • Regra geral: Prefira for_each em 90% dos casos. Use count apenas para condicional (count = 0 ou 1).

6.1 Bloco terraform e required_providers

O bloco terraform {} é onde você configura o próprio Terraform: versão mínima, providers necessários e backend para o state.

providers.tf — Configuração CompletaObrigatório
# ═══════════════════════════════════════════
# BLOCO TERRAFORM — Configuração do próprio Terraform
# ═══════════════════════════════════════════
terraform {
  # Versão mínima do Terraform CLI necessária
  required_version = ">= 1.6.0"

  # Providers necessários e suas versões
  required_providers {
    aws = {
      source  = "hashicorp/aws"        # Registry/organização/nome
      version = "~> 5.30"              # >= 5.30, < 6.0 (minor updates OK)
    }
    random = {
      source  = "hashicorp/random"
      version = "~> 3.6"
    }
  }

  # Backend para armazenar o state remotamente
  # (Detalhado no Módulo 04)
  backend "s3" {
    bucket         = "meu-terraform-state-123456"
    key            = "vpc/terraform.tfstate"
    region         = "us-east-1"
    dynamodb_table = "terraform-locks"
    encrypt        = true
  }
}

# ═══════════════════════════════════════════
# PROVIDER AWS — Configuração da conexão com AWS
# ═══════════════════════════════════════════
provider "aws" {
  region = var.aws_region   # Região padrão para recursos

  # Tags aplicadas AUTOMATICAMENTE a todos os recursos
  default_tags {
    tags = {
      Project     = var.project_name
      Environment = var.environment
      ManagedBy   = "terraform"
      Repository  = "github.com/meu-org/infra-vpc"
    }
  }
}

# ═══════════════════════════════════════════
# PROVIDER RANDOM — Gerar valores aleatórios
# ═══════════════════════════════════════════
# Não precisa de configuração extra
# Usado para suffixes únicos em nomes de recursos

6.2 default_tags — Tagging Automático

O default_tags é uma feature poderosa que aplica tags automaticamente a TODOS os recursos criados pelo provider. Isso garante governança e rastreabilidade:

Estratégia de TagsGovernança
# As default_tags são MESCLADAS com tags do recurso
# Tags do recurso têm precedência em caso de conflito

provider "aws" {
  region = "us-east-1"

  default_tags {
    tags = {
      # Quem gerencia este recurso?
      ManagedBy = "terraform"
      
      # Qual projeto/produto?
      Project = "cloudtrilhas"
      
      # Qual ambiente?
      Environment = var.environment
      
      # Para controle de custos (AWS Cost Explorer)
      CostCenter = "engineering"
      
      # Qual repositório contém o código?
      Repository = "github.com/org/terraform-vpc"
      
      # Quando foi a última atualização?
      LastUpdated = timestamp()
    }
  }
}

# No recurso, você adiciona tags ESPECÍFICAS
resource "aws_vpc" "main" {
  cidr_block = "10.0.0.0/16"
  
  tags = {
    Name = "vpc-${var.environment}"  # Tag específica deste recurso
    # As default_tags são adicionadas automaticamente!
  }
}
# Resultado: o recurso terá Name + TODAS as default_tags

📋 Ordem de Precedência (menor → maior prioridade): 

1. default no variable {} block          ← Menor prioridade
2. terraform.tfvars (automático)
3. *.auto.tfvars (automático, alfabético)
4. -var-file="custom.tfvars" (CLI)
5. TF_VAR_* (variáveis de ambiente)
6. -var="key=value" (CLI)                ← Maior prioridade

Exemplo: se vpc_cidr tem default "10.0.0.0/16" em variables.tf,
mas terraform.tfvars define "172.16.0.0/16",
e você roda: terraform apply -var="vpc_cidr=192.168.0.0/16"
→ O valor usado será "192.168.0.0/16" (maior precedência)

Entenda profundamente os conceitos de rede da AWS: CIDR, subnets públicas e privadas, Internet Gateway, NAT Gateway, Route Tables e como tudo se conecta.

8.1 O que é uma VPC?

Uma VPC (Virtual Private Cloud) é uma rede virtual isolada dentro da AWS, dedicada à sua conta. É como ter seu próprio data center virtual na cloud, com controle total sobre endereçamento IP, subnets, roteamento e segurança.

🏠 Analogia — VPC = Condomínio:

Pense na VPC como um condomínio fechado:

  • VPC = O terreno do condomínio (espaço total de IPs)
  • Subnets = Blocos/prédios dentro do condomínio
  • Internet Gateway = Portão principal (acesso à internet)
  • NAT Gateway = Portão de serviço (internos podem sair, externos não entram)
  • Route Table = Placas de sinalização (para onde cada tráfego vai)
  • Security Group = Porteiro de cada prédio (regras de entrada/saída)
  • NACL = Muros entre os blocos (regras a nível de subnet)

8.2 CIDR — Endereçamento IP

CIDR (Classless Inter-Domain Routing) define o range de IPs disponíveis na sua VPC. Entender CIDR é fundamental para planejar sua rede.

Entendendo CIDRNetworking
# CIDR = IP_BASE / BITS_DE_REDE
# Exemplo: 10.0.0.0/16

# O que significa /16?
# 32 bits total - 16 bits rede = 16 bits para hosts
# 2^16 = 65.536 endereços IP disponíveis

# ═══════════════════════════════════════════
# TABELA DE REFERÊNCIA CIDR
# ═══════════════════════════════════════════
# /16 = 65.536 IPs  → VPC (recomendado)
# /20 = 4.096 IPs   → Subnet grande
# /24 = 256 IPs     → Subnet padrão (251 usáveis*)
# /28 = 16 IPs      → Subnet mínima para ELB
# /32 = 1 IP        → Host único

# * AWS reserva 5 IPs por subnet:
#   .0   = Endereço de rede
#   .1   = VPC Router
#   .2   = DNS da AWS
#   .3   = Reservado futuro
#   .255 = Broadcast (não suportado, mas reservado)

# ═══════════════════════════════════════════
# RANGES PRIVADOS (RFC 1918) — Use estes para VPC!
# ═══════════════════════════════════════════
# 10.0.0.0/8      → 16.777.216 IPs (Classe A)
# 172.16.0.0/12   → 1.048.576 IPs  (Classe B)
# 192.168.0.0/16  → 65.536 IPs     (Classe C)

# Para VPC AWS, use tipicamente:
# 10.0.0.0/16 (mais comum)
# 172.16.0.0/16
# 192.168.0.0/16

│

Disponível: 65.536 - 2.304 = 63.232 IPs para crescimento

⚠️ Subnet Pública vs Privada — A Diferença Real:

Não existe flag "pública" ou "privada" em uma subnet. O que define se uma subnet é pública ou privada é a Route Table associada:

  • Pública: Route Table tem rota 0.0.0.0/0 → Internet Gateway
  • Privada: Route Table tem rota 0.0.0.0/0 → NAT Gateway (ou nenhuma rota para internet)

Além disso, map_public_ip_on_launch = true faz instâncias na subnet receberem IP público automaticamente (comum em subnets públicas).

8.5 NAT Gateway — Por que é Necessário?

Recursos em subnets privadas (EC2, Lambda, ECS) frequentemente precisam acessar a internet para:

  • Baixar atualizações de segurança (apt update)
  • Acessar APIs externas (Stripe, SendGrid, etc.)
  • Download de dependências (pip, npm, etc.)
  • Enviar métricas para ferramentas externas (Datadog, New Relic)

O NAT Gateway permite esse tráfego de saída sem permitir tráfego de entrada não solicitado — mantendo a segurança.

💰 Custo do NAT Gateway:

NAT Gateway custa ~$32/mês (fixo) + $0.045/GB de dados processados. Para ambientes de desenvolvimento, considere:

  • Usar NAT Instance (EC2 t3.nano ~$3/mês) em dev
  • Compartilhar 1 NAT Gateway entre subnets em dev
  • Em produção: 1 NAT Gateway por AZ para alta disponibilidade

9. Recursos da VPC em Terraform

Implemente cada componente da VPC em Terraform com código production-ready: VPC, Subnets, Internet Gateway, NAT Gateway, Route Tables e associações.

9.1 aws_vpc — Criando a VPC

O recurso raiz de toda a rede. Todos os outros componentes dependem dele.

resource "aws_vpc"VPC
# ═══════════════════════════════════════════════════════════════
# VPC — Rede Virtual Principal
# ═══════════════════════════════════════════════════════════════
resource "aws_vpc" "main" {
  # CIDR block — range de IPs da VPC
  # /16 = 65.536 IPs — suficiente para crescer
  cidr_block = var.vpc_cidr  # "10.0.0.0/16"

  # Habilitar DNS hostname para instâncias
  # Necessário para: RDS endpoints, EFS, ELB internal
  enable_dns_hostnames = true

  # Habilitar resolução DNS via Amazon DNS server
  # Necessário para: Route 53 private hosted zones, VPC endpoints
  enable_dns_support = true

  # Instance tenancy — "default" = hardware compartilhado (mais barato)
  # "dedicated" = hardware dedicado (compliance, ~6x mais caro)
  instance_tenancy = "default"

  tags = {
    Name = "${var.project_name}-vpc-${var.environment}"
  }
}

# ═══════════════════════════════════════════════════════════════
# DATA SOURCE — Buscar AZs disponíveis na região
# ═══════════════════════════════════════════════════════════════
data "aws_availability_zones" "available" {
  state = "available"

  # Excluir Local Zones (geralmente mais caras)
  filter {
    name   = "opt-in-status"
    values = ["opt-in-not-required"]
  }
}

# Uso: data.aws_availability_zones.available.names
# Resultado: ["us-east-1a", "us-east-1b", "us-east-1c", ...]

9.2 aws_subnet — Subnets Públicas e Privadas

Subnets dividem a VPC em segmentos menores, cada um em uma Availability Zone diferente para alta disponibilidade.

Subnets Públicas (com for_each)Public
# ═══════════════════════════════════════════════════════════════
# LOCALS — Definir configuração das subnets
# ═══════════════════════════════════════════════════════════════
locals {
  # Quantas AZs usar (normalmente 2-3)
  az_count = min(length(data.aws_availability_zones.available.names), 3)

  # Nomes das AZs que vamos usar
  azs = slice(data.aws_availability_zones.available.names, 0, local.az_count)
}

# ═══════════════════════════════════════════════════════════════
# SUBNETS PÚBLICAS — Uma por AZ
# Estas hospedam: ALB, NAT Gateway, Bastion Host
# ═══════════════════════════════════════════════════════════════
resource "aws_subnet" "public" {
  count = local.az_count

  vpc_id = aws_vpc.main.id

  # cidrsubnet("10.0.0.0/16", 8, 0) → "10.0.0.0/24"
  # cidrsubnet("10.0.0.0/16", 8, 1) → "10.0.1.0/24"
  # cidrsubnet("10.0.0.0/16", 8, 2) → "10.0.2.0/24"
  cidr_block = cidrsubnet(var.vpc_cidr, 8, count.index)

  # Distribuir entre AZs
  availability_zone = local.azs[count.index]

  # Instâncias lançadas aqui recebem IP público automaticamente
  # (necessário para que ALB/Bastion sejam acessíveis)
  map_public_ip_on_launch = true

  tags = {
    Name = "${var.project_name}-public-${local.azs[count.index]}"
    Tier = "public"
  }
}
Subnets Privadas (Aplicação + Database)Private
# ═══════════════════════════════════════════════════════════════
# SUBNETS PRIVADAS (Aplicação) — Uma por AZ
# Estas hospedam: EC2 instances, ECS Tasks, Lambda (VPC)
# ═══════════════════════════════════════════════════════════════
resource "aws_subnet" "private" {
  count = local.az_count

  vpc_id = aws_vpc.main.id

  # Offset de 10 para separar das públicas
  # cidrsubnet("10.0.0.0/16", 8, 10) → "10.0.10.0/24"
  # cidrsubnet("10.0.0.0/16", 8, 11) → "10.0.11.0/24"
  # cidrsubnet("10.0.0.0/16", 8, 12) → "10.0.12.0/24"
  cidr_block = cidrsubnet(var.vpc_cidr, 8, count.index + 10)

  availability_zone = local.azs[count.index]

  # Sem IP público — tráfego de saída vai pelo NAT Gateway
  map_public_ip_on_launch = false

  tags = {
    Name = "${var.project_name}-private-${local.azs[count.index]}"
    Tier = "private"
  }
}

# ═══════════════════════════════════════════════════════════════
# SUBNETS DATABASE — Uma por AZ
# Estas hospedam: RDS, ElastiCache, DocumentDB
# Isoladas — sem acesso internet (nem outbound)
# ═══════════════════════════════════════════════════════════════
resource "aws_subnet" "database" {
  count = local.az_count

  vpc_id = aws_vpc.main.id

  # Offset de 20
  # cidrsubnet("10.0.0.0/16", 8, 20) → "10.0.20.0/24"
  cidr_block = cidrsubnet(var.vpc_cidr, 8, count.index + 20)

  availability_zone = local.azs[count.index]

  map_public_ip_on_launch = false

  tags = {
    Name = "${var.project_name}-database-${local.azs[count.index]}"
    Tier = "database"
  }
}

9.3 aws_internet_gateway — Acesso à Internet

O Internet Gateway permite comunicação bidirecional entre recursos na VPC (com IP público) e a internet. Cada VPC pode ter apenas UM Internet Gateway.

resource "aws_internet_gateway"IGW
# ═══════════════════════════════════════════════════════════════
# INTERNET GATEWAY — Porta para a Internet
# ═══════════════════════════════════════════════════════════════
resource "aws_internet_gateway" "main" {
  # Associar à VPC (1 IGW por VPC)
  vpc_id = aws_vpc.main.id

  tags = {
    Name = "${var.project_name}-igw-${var.environment}"
  }
}

# O IGW por si só não faz nada!
# É necessário criar uma ROTA na Route Table apontando para ele.
# Sem a rota 0.0.0.0/0 → IGW, nenhum tráfego vai para internet.

9.4 aws_eip + aws_nat_gateway — NAT para Subnets Privadas

O NAT Gateway precisa de um Elastic IP (IP público fixo) e fica em uma subnet pública. Ele traduz endereços privados para públicos (outbound only).

Elastic IP + NAT GatewayNAT
# ═══════════════════════════════════════════════════════════════
# ELASTIC IP — IP público fixo para o NAT Gateway
# ═══════════════════════════════════════════════════════════════
resource "aws_eip" "nat" {
  # Em produção: 1 EIP por AZ (alta disponibilidade)
  # Em dev: 1 EIP compartilhado (economia)
  count = var.environment == "production" ? local.az_count : 1

  # domain = "vpc" indica que é um EIP para uso dentro de VPC
  domain = "vpc"

  tags = {
    Name = "${var.project_name}-eip-nat-${count.index + 1}"
  }

  # O EIP depende do IGW existir
  # (sem IGW, o NAT não consegue rotear para internet)
  depends_on = [aws_internet_gateway.main]
}

# ═══════════════════════════════════════════════════════════════
# NAT GATEWAY — Tradução de endereço para subnets privadas
# ═══════════════════════════════════════════════════════════════
resource "aws_nat_gateway" "main" {
  # Mesmo count do EIP
  count = var.environment == "production" ? local.az_count : 1

  # Associar o Elastic IP
  allocation_id = aws_eip.nat[count.index].id

  # NAT Gateway DEVE ficar em subnet PÚBLICA!
  # (ele precisa de acesso direto à internet via IGW)
  subnet_id = aws_subnet.public[count.index].id

  tags = {
    Name = "${var.project_name}-nat-${count.index + 1}"
  }

  # Garantir que IGW existe antes de criar o NAT
  depends_on = [aws_internet_gateway.main]
}

# ═══════════════════════════════════════════════════════════════
# RESUMO DO FLUXO:
# Instância Privada (10.0.10.5)
#   → Route Table: 0.0.0.0/0 → NAT Gateway
#     → NAT traduz IP privado → EIP público
#       → Internet Gateway → Internet
# Resposta volta pelo mesmo caminho (connection tracking)
# ═══════════════════════════════════════════════════════════════

9.5 aws_route_table + aws_route — Regras de Roteamento

Route Tables contêm regras que determinam para onde o tráfego de rede é direcionado. Cada subnet deve estar associada a exatamente uma route table.

Route Table PúblicaRotas
# ═══════════════════════════════════════════════════════════════
# ROUTE TABLE PÚBLICA — Todo tráfego externo vai para IGW
# ═══════════════════════════════════════════════════════════════
resource "aws_route_table" "public" {
  vpc_id = aws_vpc.main.id

  # Rota local (10.0.0.0/16) é criada AUTOMATICAMENTE
  # Não precisa declarar — permite comunicação dentro da VPC

  tags = {
    Name = "${var.project_name}-rt-public-${var.environment}"
  }
}

# Rota padrão: todo tráfego não-VPC vai para Internet Gateway
resource "aws_route" "public_internet" {
  route_table_id         = aws_route_table.public.id
  destination_cidr_block = "0.0.0.0/0"          # Qualquer destino
  gateway_id             = aws_internet_gateway.main.id  # Via IGW
}

# ═══════════════════════════════════════════════════════════════
# ASSOCIAR Route Table Pública às Subnets Públicas
# ═══════════════════════════════════════════════════════════════
resource "aws_route_table_association" "public" {
  count = local.az_count

  subnet_id      = aws_subnet.public[count.index].id
  route_table_id = aws_route_table.public.id
}
# Resultado: todas as subnets públicas compartilham a mesma route table
# que direciona tráfego 0.0.0.0/0 → IGW
Route Table Privada (com NAT)Private
# ═══════════════════════════════════════════════════════════════
# ROUTE TABLE PRIVADA — Tráfego externo vai para NAT Gateway
# Em produção: 1 RT por AZ (cada uma aponta para NAT local)
# Em dev: 1 RT compartilhada (aponta para único NAT)
# ═══════════════════════════════════════════════════════════════
resource "aws_route_table" "private" {
  count  = var.environment == "production" ? local.az_count : 1
  vpc_id = aws_vpc.main.id

  tags = {
    Name = "${var.project_name}-rt-private-${count.index + 1}"
  }
}

# Rota: tráfego externo vai pelo NAT Gateway
resource "aws_route" "private_nat" {
  count = var.environment == "production" ? local.az_count : 1

  route_table_id         = aws_route_table.private[count.index].id
  destination_cidr_block = "0.0.0.0/0"
  nat_gateway_id         = aws_nat_gateway.main[count.index].id
}

# Associar Route Table Privada às Subnets Privadas
resource "aws_route_table_association" "private" {
  count = local.az_count

  subnet_id      = aws_subnet.private[count.index].id
  route_table_id = aws_route_table.private[
    var.environment == "production" ? count.index : 0
  ].id
}

# ═══════════════════════════════════════════════════════════════
# ROUTE TABLE DATABASE — Sem acesso à internet (mais segura)
# ═══════════════════════════════════════════════════════════════
resource "aws_route_table" "database" {
  vpc_id = aws_vpc.main.id

  # SEM rota para 0.0.0.0/0 — isolamento total
  # Subnets de database não precisam acessar internet

  tags = {
    Name = "${var.project_name}-rt-database-${var.environment}"
  }
}

resource "aws_route_table_association" "database" {
  count = local.az_count

  subnet_id      = aws_subnet.database[count.index].id
  route_table_id = aws_route_table.database.id
