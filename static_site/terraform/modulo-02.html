1. Data Sources — Consultar sem Criar

Data Sources permitem consultar informações de recursos existentes na AWS (ou em outros providers) sem criar ou modificar nada. São a ponte entre o mundo real e seu código Terraform.

1.1 O que são Data Sources?

No Terraform, tudo que começa com resource cria algo. Tudo que começa com data consulta algo que já existe. Essa distinção é fundamental.

Pense assim: você está montando um quebra-cabeça (sua infraestrutura). Algumas peças você fabrica do zero (resource). Outras peças já existem na mesa e você precisa apenas encontrá-las para encaixar (data).

🔍 Analogia — O Catálogo da Biblioteca:

Imagine que você está em uma biblioteca e precisa de um livro específico. Você não vai criar o livro — ele já existe. Você vai ao catálogo (data source), busca pelo título e autor (filters), e o catálogo retorna a localização exata do livro (atributos). Com essa localização, você pega o livro e usa no seu trabalho.

Sintaxe Básica — resource vs dataComparação
# ═══════════════════════════════════════════════════════════════

1.2 aws_ami — Buscar AMI Dinamicamente

O data source mais usado em projetos EC2. Em vez de hardcodar um AMI ID (que muda por região e é atualizado frequentemente), você busca dinamicamente a AMI mais recente que atende aos seus critérios.

data "aws_ami" — AMI mais recente do Amazon Linux 2023Produção📖 Docs
# ═══════════════════════════════════════════════════════════════
# Busca a AMI mais recente do Amazon Linux 2023
# Isso garante que sempre teremos a última versão com patches
# ═══════════════════════════════════════════════════════════════
data "aws_ami" "amazon_linux_2023" {
  # most_recent = true → Se múltiplas AMIs atendem aos filtros,
  # retorna apenas a mais recente (pela data de criação)
  most_recent = true

  # owners → Quem publicou a AMI
  # "amazon" = AMIs oficiais da AWS
  # "self"   = AMIs da sua conta
  # "123456789012" = AMIs de conta específica
  owners = ["amazon"]

  # filter → Critérios de busca (AND entre filtros)
  filter {
    name   = "name"
    # Padrão de nome da AMI — usa wildcard (*)
    # al2023-ami-2023.* → Amazon Linux 2023
    # -kernel-6.1-*     → Kernel versão 6.1
    # -x86_64           → Arquitetura x86 (64 bits)
    values = ["al2023-ami-2023.*-kernel-6.1-x86_64"]
  }

  filter {
    name   = "architecture"
    values = ["x86_64"]  # ou "arm64" para Graviton
  }

  filter {
    name   = "virtualization-type"
    values = ["hvm"]  # Hardware Virtual Machine (padrão moderno)
  }

  filter {
    name   = "root-device-type"
    values = ["ebs"]  # Boot de EBS (não instance-store)
  }
}

# ═══════════════════════════════════════════════════════════════

1.3 aws_availability_zones — Zonas Disponíveis

Cada região AWS tem múltiplas Availability Zones. Em vez de hardcodar ["us-east-1a", "us-east-1b"], consulte dinamicamente:

data "aws_availability_zones"Dinâmico📖 Docs
# ═══════════════════════════════════════════════════════════════
# Busca todas as AZs disponíveis na região configurada no provider
# ═══════════════════════════════════════════════════════════════
data "aws_availability_zones" "available" {
  # state = "available" → Apenas AZs ativas (exclui deprecated)
  state = "available"

  # Opcional: excluir Local Zones e Wavelength Zones
  filter {
    name   = "opt-in-status"
    values = ["opt-in-not-required"]
  }
}

# Atributos retornados:
# data.aws_availability_zones.available.names
#   → ["us-east-1a", "us-east-1b", "us-east-1c", "us-east-1d", ...]
# data.aws_availability_zones.available.zone_ids
#   → ["use1-az1", "use1-az2", "use1-az3", ...]

# ═══════════════════════════════════════════════════════════════
# Uso prático: criar subnets em cada AZ automaticamente
# ═══════════════════════════════════════════════════════════════
resource "aws_subnet" "public" {
  # count = número de AZs disponíveis (geralmente 3-6)
  count             = length(data.aws_availability_zones.available.names)
  vpc_id            = aws_vpc.main.id
  # cidrsubnet calcula CIDR automaticamente: 10.0.0.0/24, 10.0.1.0/24...
  cidr_block        = cidrsubnet(aws_vpc.main.cidr_block, 8, count.index)
  availability_zone = data.aws_availability_zones.available.names[count.index]

  tags = {
    Name = "subnet-public-${data.aws_availability_zones.available.names[count.index]}"
  }
}

💡 Por que usar data sources em vez de hardcodar?
  • Portabilidade: O mesmo código funciona em qualquer região sem alteração
  • Manutenção: AMI IDs mudam; data sources sempre pegam a versão atual
  • Segurança: Não expor account IDs em variáveis — consulte dinamicamente
  • DRY: Evita repetição de valores que podem ser derivados automaticamente

2. Security Groups — Firewall Virtual

Security Groups são o firewall virtual da AWS que controla todo o tráfego de entrada e saída das suas instâncias. Entenda profundamente como funcionam, por que são stateful e como configurá-los corretamente.

2.1 O que é um Security Group?

Um Security Group (SG) é um firewall virtual stateful que atua no nível da interface de rede (ENI). Ele controla quais conexões são permitidas para entrar (ingress) e sair (egress) de uma instância EC2, RDS, Lambda VPC, ELB, ou qualquer recurso com ENI.

🏢 Analogia — O Porteiro do Prédio:

Imagine que sua instância EC2 é um apartamento em um prédio. O Security Group é o porteiro na portaria. Quando alguém chega (ingress), o porteiro verifica a lista de visitantes autorizados. Se a pessoa está na lista (regra permite), entra. Se não está, é barrada.

A parte stateful funciona assim: se o porteiro autorizou a entrada de um visitante, ele automaticamente permite que esse visitante saia depois — sem precisar de uma regra separada de saída para respostas.

Cada regra de ingress é como uma instrução para o porteiro: "Deixe entrar qualquer pessoa que venha da empresa X (source) e esteja indo para o andar 443 (porta)."

2.2 Stateful vs Stateless — A Diferença Crucial

Essa é uma das perguntas mais frequentes em entrevistas AWS e certificações:

Aspecto Security Group (Stateful) Network ACL (Stateless)
NívelInstância (ENI)Subnet
Stateful✅ Sim — resposta automática❌ Não — precisa regra de retorno
RegrasApenas ALLOW (deny implícito)ALLOW e DENY explícitos
AvaliaçãoTodas as regras são avaliadasRegras avaliadas em ordem numérica
DefaultIngress: deny all / Egress: allow allAllow all (in/out)
AssociaçãoN instâncias podem usar 1 SGAplicada a toda a subnet
MúltiplosAté 5 SGs por ENI (configurável)1 NACL por subnet
🔄 O que "Stateful" significa na prática: 

STATEFUL (Security Group):
═══════════════════════════
1. Cliente envia request na porta 443 (HTTPS)
2. SG verifica regra de INGRESS → porta 443 permitida de 0.0.0.0/0 ✅
3. Request chega na instância
4. Instância responde na porta efêmera (ex: 49152)
5. SG AUTOMATICAMENTE permite a resposta sair ✅ (não precisa regra de egress)

STATELESS (Network ACL):
═══════════════════════════
1. Cliente envia request na porta 443
2. NACL inbound verifica → regra 100 permite porta 443 ✅
3. Request chega na subnet/instância
4. Instância responde na porta efêmera (ex: 49152)
5. NACL outbound verifica → PRECISA de regra permitindo portas efêmeras! ⚠️
   Se não tiver regra para portas 1024-65535, resposta é BLOQUEADA ❌

2.3 Criando Security Groups com Terraform

O recurso aws_security_group cria o grupo, e as regras podem ser definidas inline ou como recursos separados:

Security Group com Regras InlineBásico📖 Docs
# ═══════════════════════════════════════════════════════════════
# Security Group para Web Server (HTTP + HTTPS + SSH restrito)
# ═══════════════════════════════════════════════════════════════
resource "aws_security_group" "web" {
  name        = "web-server-sg"
  description = "Security group para servidores web - permite HTTP, HTTPS e SSH restrito"
  vpc_id      = aws_vpc.main.id  # SG pertence a uma VPC específica

  # ─── REGRAS DE ENTRADA (Ingress) ─────────────────────────────
  
  # Permite HTTP de qualquer lugar (para o site público)
  ingress {
    description = "HTTP from anywhere"
    from_port   = 80
    to_port     = 80
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]  # IPv4 qualquer
  }

  # Permite HTTPS de qualquer lugar
  ingress {
    description = "HTTPS from anywhere"
    from_port   = 443
    to_port     = 443
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }

  # SSH apenas da rede interna (NUNCA abra SSH para 0.0.0.0/0 em produção!)
  ingress {
    description = "SSH from VPC only"
    from_port   = 22
    to_port     = 22
    protocol    = "tcp"
    cidr_blocks = [aws_vpc.main.cidr_block]  # Apenas de dentro da VPC
  }

  # ─── REGRAS DE SAÍDA (Egress) ────────────────────────────────
  
  # Permite toda saída (padrão — instância pode acessar internet)
  egress {
    description = "Allow all outbound traffic"
    from_port   = 0
    to_port     = 0
    protocol    = "-1"          # -1 = todos os protocolos
    cidr_blocks = ["0.0.0.0/0"]
  }

  tags = {
    Name        = "web-server-sg"
    Environment = var.environment
    ManagedBy   = "terraform"
  }

  # Lifecycle: evita downtime ao atualizar regras
  lifecycle {
    create_before_destroy = true
  }
}

2.4 Self-Referencing e Múltiplos SGs

Self-referencing permite que instâncias no mesmo Security Group se comuniquem entre si. Isso é comum em clusters onde todos os nós precisam conversar.

Self-Referencing e Source Security GroupAvançado📖 Docs
# ═══════════════════════════════════════════════════════════════
# SG para cluster de aplicação — permite comunicação interna
# ═══════════════════════════════════════════════════════════════
resource "aws_security_group" "app_cluster" {
  name        = "app-cluster-sg"
  description = "Permite comunicacao entre instancias do cluster"
  vpc_id      = aws_vpc.main.id

  # Self-referencing: instâncias com ESTE SG podem se comunicar
  # em qualquer porta (útil para clusters Redis, Kafka, etc.)
  ingress {
    description = "All traffic from same security group"
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    self        = true  # ← SELF REFERENCE
  }

  # Tráfego vindo do Load Balancer (outro SG)
  ingress {
    description     = "HTTP from ALB"
    from_port       = 8080
    to_port         = 8080
    protocol        = "tcp"
    # Em vez de CIDR, referencia OUTRO Security Group
    security_groups = [aws_security_group.alb.id]
  }

  egress {
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }

  tags = { Name = "app-cluster-sg" }
}

# ═══════════════════════════════════════════════════════════════
# Uma instância pode ter MÚLTIPLOS Security Groups
# As regras são UNIDAS (OR) — se qualquer SG permite, passa
# ═══════════════════════════════════════════════════════════════
resource "aws_instance" "app" {
  ami           = data.aws_ami.amazon_linux_2023.id
  instance_type = "t3.medium"
  
  # Múltiplos SGs — regras combinadas
  vpc_security_group_ids = [
    aws_security_group.app_cluster.id,  # Comunicação do cluster
    aws_security_group.monitoring.id,    # Acesso do Prometheus
    aws_security_group.ssh_bastion.id,   # SSH via bastion
  ]

  subnet_id = aws_subnet.private[0].id
  tags      = { Name = "app-server-01" }
}
⚠️ Best Practices de Security Groups:
  • Least Privilege: Abra apenas as portas necessárias, para os sources necessários
  • Nunca 0.0.0.0/0 para SSH: Use bastion host, VPN ou Systems Manager Session Manager
  • Use source SG em vez de CIDR: Quando o tráfego vem de outro recurso AWS, referencie o SG dele
  • Description em cada regra: Documente POR QUE cada regra existe
  • Nomeie claramente: "web-server-sg" é melhor que "sg-1" ou "allow-all"
  • Um SG por função: Não crie um SG gigante — separe por papel (web, app, db, monitoring)

3. Security Group Rules — Regras como Recursos

Entenda a diferença entre definir regras inline e como recursos separados, padrões comuns para web servers, bastions e databases, e como usar CIDR blocks e source Security Groups.

3.1 Inline Rules vs aws_security_group_rule

O Terraform oferece duas formas de criar regras de Security Group. Cada uma tem vantagens e desvantagens:

Aspecto Regras Inline (dentro do SG) aws_security_group_rule (separado)
DefiniçãoBloco ingress/egress dentro do resourceRecurso independente referenciando o SG
Conflito⚠️ Conflita com rules separadas✅ Pode coexistir com outras rules
Módulos❌ Não permite adicionar regras externamente✅ Módulos podem adicionar regras ao SG
Legibilidade✅ Tudo em um lugar⚠️ Espalhado em vários recursos
RecomendaçãoProjetos simples e pequenosProjetos grandes e modulares
⚠️ NUNCA misture inline e rules separadas para o mesmo SG!

Se você definir regras inline E usar aws_security_group_rule apontando para o mesmo Security Group, o Terraform entrará em um loop infinito de mudanças. O plan sempre mostrará alterações porque um tenta sobrescrever o outro. Escolha UM dos métodos e seja consistente.

aws_security_group_rule — Regras como Recursos SeparadosRecomendado📖 Docs
# ═══════════════════════════════════════════════════════════════
# PADRÃO RECOMENDADO: SG vazio + regras separadas
# Permite que módulos adicionem regras sem modificar o SG
# ═══════════════════════════════════════════════════════════════

# 1. Security Group SEM regras inline
resource "aws_security_group" "web" {
  name        = "${var.project}-web-sg"
  description = "Security group para servidores web"
  vpc_id      = aws_vpc.main.id

  tags = {
    Name = "${var.project}-web-sg"
  }

  # Importante: sem blocos ingress/egress aqui!
}

# 2. Regra de Ingress — HTTP
resource "aws_security_group_rule" "web_http_ingress" {
  type              = "ingress"
  from_port         = 80
  to_port           = 80
  protocol          = "tcp"
  cidr_blocks       = ["0.0.0.0/0"]
  description       = "Allow HTTP from internet"
  security_group_id = aws_security_group.web.id  # ← A qual SG pertence
}

# 3. Regra de Ingress — HTTPS
resource "aws_security_group_rule" "web_https_ingress" {
  type              = "ingress"
  from_port         = 443
  to_port           = 443
  protocol          = "tcp"
  cidr_blocks       = ["0.0.0.0/0"]
  description       = "Allow HTTPS from internet"
  security_group_id = aws_security_group.web.id
}

# 4. Regra de Ingress — SSH apenas do bastion
resource "aws_security_group_rule" "web_ssh_from_bastion" {
  type                     = "ingress"
  from_port                = 22
  to_port                  = 22
  protocol                 = "tcp"
  # Em vez de CIDR, referencia o SG do bastion host
  source_security_group_id = aws_security_group.bastion.id
  description              = "Allow SSH from bastion host only"
  security_group_id        = aws_security_group.web.id
}

4. Key Pairs — Autenticação SSH

Entenda como funciona a autenticação por chaves SSH, como gerar key pairs, registrá-los na AWS com Terraform e as alternativas modernas como Systems Manager.

4.1 Como Funciona a Autenticação SSH por Chaves

A autenticação SSH por chaves é baseada em criptografia assimétrica — um par de chaves matematicamente relacionadas onde uma é pública (pode compartilhar) e outra é privada (NUNCA compartilhar).

🔐 Analogia — A Chave de Casa:

Imagine que a chave pública é a fechadura instalada na porta da sua casa (EC2). Qualquer um pode ver a fechadura, mas só quem tem a chave privada (que fica no bolso, protegida) consegue abrir. Você pode instalar cópias da mesma fechadura em várias casas (instâncias), mas a chave privada é única e pessoal.

Fluxo de Autenticação SSHDiagrama

┌──────────────────────┐                    ┌──────────────────────┐
│   Seu Computador     │                    │    EC2 Instance      │
│                      │                    │                      │
│  ~/.ssh/id_rsa       │ ── SSH Connect ──▶ │  ~/.ssh/authorized   │
│  (Chave PRIVADA)     │                    │  _keys               │
│  🔑 Secreta          │                    │  (Chave PÚBLICA)     │
│                      │                    │  🔓 Pode compartilhar│

         │                                            │

         │─────────────────────────────────────────▶  │
         │                                            │
         │  2. Servidor envia desafio criptográfico   │
         │  ◀─────────────────────────────────────────│

4.2 Gerar Chaves SSH Localmente

O método mais seguro é gerar as chaves no seu computador — a chave privada nunca sai da sua máquina:

ssh-keygen — Gerar Par de ChavesTerminal
# Gerar par de chaves RSA 4096 bits (mais seguro que 2048)
ssh-keygen -t rsa -b 4096 -C "terraform@cloudtrilhas" -f ~/.ssh/terraform-key

# Parâmetros explicados:
# -t rsa     → Algoritmo RSA (compatível com tudo)
# -b 4096    → 4096 bits (força criptográfica alta)
# -C "..."   → Comentário (identificação da chave)
# -f path    → Arquivo de saída (sem extensão = privada, .pub = pública)

# Resultado:
# ~/.ssh/terraform-key      ← Chave PRIVADA (chmod 600!)
# ~/.ssh/terraform-key.pub  ← Chave PÚBLICA (registrar na AWS)

# ALTERNATIVA: ED25519 (mais moderno e rápido)
ssh-keygen -t ed25519 -C "terraform@cloudtrilhas" -f ~/.ssh/terraform-ed25519

# Proteger a chave privada (OBRIGATÓRIO)
chmod 600 ~/.ssh/terraform-key
chmod 644 ~/.ssh/terraform-key.pub

# Verificar o conteúdo da chave pública
cat ~/.ssh/terraform-key.pub
# ssh-rsa AAAAB3NzaC1yc2EAAAA... terraform@cloudtrilhas

5.1 Famílias e Tipos de Instância

5.2 Criando uma EC2 Instance Completa

Vamos criar uma instância EC2 de produção com todos os componentes necessários:

aws_instance — Instância Completa de ProduçãoProdução📖 Docs
# ═══════════════════════════════════════════════════════════════
# EC2 Instance — Web Server completo
# ═══════════════════════════════════════════════════════════════
resource "aws_instance" "web" {
  # ─── AMI (Sistema Operacional) ────────────────────────────────
  ami = data.aws_ami.amazon_linux_2023.id  # Consulta dinâmica (seção 1)

  # ─── Tipo da Instância ────────────────────────────────────────
  instance_type = var.instance_type  # Ex: "t3.small"

  # ─── Networking ───────────────────────────────────────────────
  subnet_id                   = aws_subnet.public[0].id  # Subnet onde será criada
  vpc_security_group_ids      = [aws_security_group.web.id]  # SGs (lista)
  associate_public_ip_address = true   # IP público (para subnet pública)

  # ─── Autenticação SSH ─────────────────────────────────────────
  key_name = aws_key_pair.deployer.key_name  # Key pair para SSH

  # ─── IAM Role (permissões da instância) ───────────────────────
  iam_instance_profile = aws_iam_instance_profile.web.name

  # ─── Volume Raiz (EBS) ───────────────────────────────────────
  root_block_device {
    volume_type           = "gp3"     # General Purpose SSD v3 (melhor que gp2)
    volume_size           = 20        # 20 GB
    iops                  = 3000      # gp3 permite configurar IOPS
    throughput            = 125       # MB/s
    encrypted             = true      # SEMPRE encripte volumes!
    delete_on_termination = true      # Deletar volume quando instância for destruída
    
    tags = {
      Name = "web-server-root-volume"
    }
  }

  # ─── Volume Adicional (dados da aplicação) ────────────────────
  ebs_block_device {
    device_name           = "/dev/sdf"  # Nome do device no Linux
    volume_type           = "gp3"
    volume_size           = 50           # 50 GB para dados
    encrypted             = true
    delete_on_termination = false        # PRESERVA dados se instância for destruída!

    tags = {
      Name = "web-server-data-volume"
    }
  }

  # ─── User Data (script de bootstrap) ─────────────────────────
  user_data = templatefile("${path.module}/scripts/user_data.sh", {
    environment = var.environment
    app_port    = var.app_port
  })

  # ─── Metadata Options (IMDSv2 — mais seguro) ─────────────────
  metadata_options {
    http_endpoint               = "enabled"
    http_tokens                 = "required"  # Força IMDSv2 (previne SSRF)
    http_put_response_hop_limit = 1
  }

  # ─── Monitoring ──────────────────────────────────────────────
  monitoring = true  # Métricas detalhadas (1 min em vez de 5 min)

  # ─── Tags ────────────────────────────────────────────────────
  tags = {
    Name        = "${var.project}-web-server"
    Environment = var.environment
    Role        = "web-server"
    ManagedBy   = "terraform"
    Backup      = "daily"
  }

  # ─── Lifecycle ───────────────────────────────────────────────
  lifecycle {
    # Se trocar AMI, cria nova instância ANTES de destruir a antiga
    create_before_destroy = true
    
    # Ignorar mudanças no user_data (evita recreação desnecessária)
    ignore_changes = [user_data]
  }
}

REGRA DE OURO:
- Subnet PÚBLICA: recursos que PRECISAM receber tráfego da internet
  (ALB, bastion, NAT Gateway)
- Subnet PRIVADA: recursos internos que NÃO devem ser acessados diretamente
  (app servers, databases, workers, caches)
⚠️ Erros Comuns de Networking:
  • EC2 sem IP público + subnet pública: Se associate_public_ip_address = false em subnet pública, a instância não terá IP público mesmo estando na subnet certa
  • EC2 em subnet privada sem NAT: A instância não conseguirá acessar a internet (nem para instalar pacotes com yum/apt)
  • SG sem egress: Se você remover a regra de egress padrão, a instância não pode fazer requisições HTTP de saída
  • Usar security_group_ids em vez de vpc_security_group_ids: O primeiro é deprecated — sempre use vpc_security_group_ids

7. Elastic IP — IP Público Fixo

Entenda quando usar Elastic IPs, como associá-los a instâncias e os custos envolvidos. Spoiler: na maioria dos casos modernos, você NÃO precisa de Elastic IP.

7.1 O que é um Elastic IP?

Um Elastic IP (EIP) é um endereço IPv4 público estático que você aloca na sua conta AWS. Diferente do IP público automático (que muda a cada stop/start da instância), o EIP permanece fixo até você liberá-lo.

📞 Analogia — Número de Telefone Fixo:

O IP público automático de uma EC2 é como um celular pré-pago — se você desligar e ligar de novo, ganha um número novo. O Elastic IP é como um número de telefone fixo empresarial — não importa quantas vezes você reinicia o equipamento, o número continua o mesmo. Clientes sempre conseguem ligar no mesmo número.

Comportamento de IPs na EC2Comparação

│                                                                 │
│  EC2 Start → IP: 54.210.33.44                                   │
│  EC2 Stop  → IP: (liberado, perdido)                            │
│  EC2 Start → IP: 18.205.77.12  ← NOVO IP! DNS precisa atualizar│
│                                                                 │
├─────────────────────────────────────────────────────────────────┤
│                ELASTIC IP (Fixo)                                  │
│                                                                 │
│  EIP alocado → 52.90.100.200 (fixo na sua conta)               │

│  EC2 Stop  → EIP continua alocado (mas cobra $0.005/hora!)      │

8. Lifecycle Rules — Controle de Vida dos Recursos

Lifecycle rules permitem customizar como o Terraform cria, atualiza e destrói recursos. São essenciais para evitar downtime, proteger dados e lidar com mudanças que forçam recriação.

8.1 Visão Geral das Lifecycle Rules

O bloco lifecycle pode ser adicionado a qualquer recurso para controlar seu comportamento:

Regra O que faz Quando usar
create_before_destroyCria o novo ANTES de destruir o antigoZero-downtime updates (SGs, instâncias atrás de LB)
prevent_destroyImpede terraform destroy de deletar o recursoDatabases, S3 buckets com dados críticos
ignore_changesIgnora mudanças em atributos específicosAtributos gerenciados externamente (ASG desired_count, tags manuais)
replace_triggered_byForça recriação quando outro recurso mudaRecriar instância quando AMI é atualizada

8.2 create_before_destroy

Por padrão, quando um recurso precisa ser recriado (alteração incompatível), o Terraform destrói primeiro, depois cria. Isso causa downtime. Com create_before_destroy, a ordem inverte:

create_before_destroy — Zero DowntimeEssencial📖 Docs
# ═══════════════════════════════════════════════════════════════
# SEM create_before_destroy (padrão):
#   1. Destroy instância antiga → DOWNTIME!
#   2. Create instância nova
#   Período sem instância = segundos a minutos de downtime
#
# COM create_before_destroy:
#   1. Create instância nova (em paralelo com a antiga)
#   2. Nova instância fica healthy
#   3. Destroy instância antiga
#   Zero downtime (ambas coexistem brevemente)
# ═══════════════════════════════════════════════════════════════

resource "aws_security_group" "web" {
  name_prefix = "web-sg-"  # Note: name_PREFIX (não name)
  description = "Web server security group"
  vpc_id      = aws_vpc.main.id

  ingress {
    from_port   = 443
    to_port     = 443
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }

  egress {
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }

  lifecycle {
    # Cria o novo SG antes de destruir o antigo
    # Necessário porque dois SGs não podem ter o MESMO name
    # Por isso usamos name_prefix em vez de name!
    create_before_destroy = true
  }

  tags = { Name = "web-sg" }
}

# Instância com create_before_destroy
resource "aws_instance" "web" {
  ami           = data.aws_ami.amazon_linux_2023.id
  instance_type = "t3.small"
  subnet_id     = aws_subnet.public[0].id

  vpc_security_group_ids = [aws_security_group.web.id]

  lifecycle {
    create_before_destroy = true
  }

  tags = { Name = "web-server" }
}
⚠️ Cuidado com name conflicts:

Se usar create_before_destroy = true com Security Groups que têm name fixo, vai falhar porque dois SGs não podem ter o mesmo nome na mesma VPC. Solução: use name_prefix em vez de name — o Terraform gera sufixo aleatório para evitar conflito.

8.4 ignore_changes

Ignora mudanças em atributos específicos durante o plan/apply. Útil quando algo externo modifica o recurso e você não quer que o Terraform "conserte" de volta.

ignore_changes — Cenários ComunsPrático📖 Docs
# ═══════════════════════════════════════════════════════════════
# Cenário 1: Auto Scaling muda desired_capacity externamente
# Sem ignore_changes, Terraform reverteria ao valor do código
# ═══════════════════════════════════════════════════════════════
resource "aws_autoscaling_group" "app" {
  name                = "app-asg"
  desired_capacity    = 2   # Valor inicial
  min_size            = 1
  max_size            = 10
  vpc_zone_identifier = aws_subnet.private[*].id

  lifecycle {
    # ASG pode escalar para 5, 8, etc. Terraform não reverte para 2
    ignore_changes = [desired_capacity]
  }
}

# ═══════════════════════════════════════════════════════════════
# Cenário 2: Tags adicionadas manualmente ou por AWS Config
# ═══════════════════════════════════════════════════════════════
resource "aws_instance" "legacy" {
  ami           = data.aws_ami.amazon_linux_2023.id
  instance_type = "t3.medium"
  subnet_id     = aws_subnet.private[0].id

  tags = {
    Name      = "legacy-app"
    ManagedBy = "terraform"
  }

  lifecycle {
    # Equipe ops adiciona tags manuais — Terraform não remove
    ignore_changes = [tags]
  }
}

# ═══════════════════════════════════════════════════════════════
# Cenário 3: user_data atualizado mas não quer recriar instância
# ═══════════════════════════════════════════════════════════════

  ami           = "ami-12345"
  instance_type = "t3.large"
  user_data     = file("setup.sh")

    # Mudou o script? Não recriar a instância (tem dados locais)

  }
}

# ignore_changes = all → Ignora TUDO (recurso nunca é atualizado)
# Use com MUITA cautela — basicamente "desliga" gestão do recurso
# ═══════════════════════════════════════════════════════════════

    ignore_changes = all  # Terraform só cria, nunca atualiza

Último Recurso

9. Provisioners (e Por Que Evitá-los)

Provisioners executam scripts locais ou remotos durante a criação de recursos. Embora poderosos, a HashiCorp os considera um "último recurso". Entenda quando são necessários e as alternativas superiores.

9.1 O que são Provisioners?

Provisioners são blocos que executam ações imperativas (scripts, comandos) dentro de um fluxo declarativo. Eles quebram o paradigma do Terraform e por isso devem ser usados com cautela.

⚠️ A Posição Oficial da HashiCorp:

"Provisioners are a Last Resort. [...] Most common situations can be covered with user_data, configuration management tools (Ansible, Chef, Puppet), or cloud-init." — Terraform Documentation

Provisioners estão marcados como deprecated no roadmap do Terraform e podem ser removidos em versões futuras.

Por que Provisioners são ProblemáticosRazões

┌─────────────────────────────────────────────────────────────────┐
│              PROBLEMAS DOS PROVISIONERS                           │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  1. NÃO estão no State                                          │
│     → Terraform não sabe se o provisioner já rodou              │
│     → Não é possível "reverter" um provisioner                  │
│                                                                 │
│  2. FALHA = recurso marcado como "tainted"                      │
│     → Se o script falhar, Terraform destrói e recria o recurso  │
│     → Pode causar perda de dados                                │
│                                                                 │
│  3. NÃO são declarativos                                        │
│     → Rodar 2x pode causar problemas (não são idempotentes)     │
│     → Terraform não pode "planificar" o resultado               │
│                                                                 │
│  4. Dependem de conectividade                                   │
│     → remote-exec precisa SSH/WinRM funcionando                 │
│     → Network issues = deploy quebrado                          │
│                                                                 │
│  5. Rodados APENAS na criação (por padrão)                      │
│     → Se a instância existir, alterações no provisioner         │
│       são IGNORADAS completamente                               │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘

Apesar das desvantagens, é importante conhecer os provisioners para entender código legado e casos extremos:

  connection {
    type        = "ssh"
    user        = "ec2-user"
    private_key = file("~/.ssh/key.pem")
    host        = self.public_ip
  }

  # Copiar arquivo de configuração para a instância
  provisioner "file" {
    source      = "configs/app.conf"         # Arquivo local
    destination = "/tmp/app.conf"            # Destino na instância
  }

  # Copiar diretório inteiro
  provisioner "file" {
    source      = "scripts/"                 # Diretório local
    destination = "/home/ec2-user/scripts"   # Destino na instância
  }

  # Depois de copiar, executar setup
  provisioner "remote-exec" {
    inline = [
      "sudo mv /tmp/app.conf /etc/app/app.conf",
      "sudo systemctl restart app",
    ]
  }
}

# ═══════════════════════════════════════════════════════════════
# NULL_RESOURCE — Executa provisioners sem criar recurso real
# Útil para rodar scripts que não estão atrelados a um recurso
# ═══════════════════════════════════════════════════════════════
resource "null_resource" "post_deploy" {
  # triggers: quando qualquer valor muda, re-executa os provisioners
  triggers = {
    instance_id = aws_instance.app.id
    config_hash = filesha256("configs/app.conf")
  }

  provisioner "local-exec" {
    command = "bash scripts/post-deploy.sh ${aws_instance.app.public_ip}"
  }
}

# NOTA: terraform_data é o substituto moderno de null_resource
resource "terraform_data" "post_deploy" {
  triggers_replace = [aws_instance.app.id]
  
  provisioner "local-exec" {
    command = "echo 'Deploy concluído para ${aws_instance.app.public_ip}'"
  }
}

Conectando Recursos

10. Outputs e Referências Cruzadas

Aprenda a conectar recursos entre si usando referências implícitas, entenda o grafo de dependências, quando usar depends_on explícito e como outputs expõem valores úteis.

10.1 Referências Implícitas — O Poder do Grafo

Quando você referencia um atributo de outro recurso (ex: aws_vpc.main.id), o Terraform automaticamente entende que existe uma dependência. Ele constrói um grafo e cria recursos na ordem correta.

Cadeia de Dependências ImplícitasAutomático📖 Docs
# ═══════════════════════════════════════════════════════════════
# Terraform infere AUTOMATICAMENTE a ordem de criação:
# VPC → Subnet → Security Group → EC2 Instance → EIP
#
# Ele sabe disso porque cada recurso REFERENCIA o anterior!
# ═══════════════════════════════════════════════════════════════

# 1. VPC (não depende de nada — criada primeiro)
resource "aws_vpc" "main" {
  cidr_block = "10.0.0.0/16"
  tags       = { Name = "main-vpc" }
}

# 2. Subnet (depende da VPC — criada segundo)
resource "aws_subnet" "public" {
  vpc_id            = aws_vpc.main.id  # ← Referência implícita à VPC
  cidr_block        = "10.0.1.0/24"
  availability_zone = "us-east-1a"
  tags              = { Name = "public-subnet" }
}

# 3. Security Group (depende da VPC — pode ser criado em paralelo com subnet)
resource "aws_security_group" "web" {
  vpc_id = aws_vpc.main.id  # ← Referência implícita à VPC
  name   = "web-sg"
  
  ingress {
    from_port   = 80
    to_port     = 80
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }
  
  egress {
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }
}

# 4. EC2 Instance (depende de Subnet + SG — criada terceiro)
resource "aws_instance" "web" {
  ami                    = data.aws_ami.amazon_linux_2023.id
  instance_type          = "t3.micro"
  subnet_id              = aws_subnet.public.id             # ← Ref à Subnet
  vpc_security_group_ids = [aws_security_group.web.id]      # ← Ref ao SG
  key_name               = aws_key_pair.deployer.key_name   # ← Ref ao Key Pair
  tags                   = { Name = "web-server" }
}

# 5. Elastic IP (depende da EC2 — criado por último)
resource "aws_eip" "web" {
  domain   = "vpc"
  instance = aws_instance.web.id  # ← Referência implícita à EC2
  tags     = { Name = "web-eip" }
}

# GRAFO RESULTANTE (terraform graph):
#
#         aws_vpc.main
#         /          \
#   aws_subnet     aws_security_group
#   .public        .web
#         \          /
#       aws_instance.web
#              |
#         aws_eip.web

10.2 depends_on — Dependências Explícitas

Em raros casos, não existe referência direta entre dois recursos mas mesmo assim um depende do outro. Use depends_on nesses casos:

depends_on — Quando Terraform Não Consegue InferirExplícito📖 Docs
# ═══════════════════════════════════════════════════════════════
# Cenário: A instância em subnet privada precisa da rota NAT
# para acessar a internet (download de pacotes no user_data).
# Mas NÃO há referência direta entre instância e rota/NAT.
# Sem depends_on, Terraform poderia criar a instância ANTES
# da rota estar pronta → user_data falha!
# ═══════════════════════════════════════════════════════════════

resource "aws_nat_gateway" "main" {
  allocation_id = aws_eip.nat.id
  subnet_id     = aws_subnet.public[0].id
  tags          = { Name = "nat-gw" }
}

resource "aws_route" "private_nat" {
  route_table_id         = aws_route_table.private.id
  destination_cidr_block = "0.0.0.0/0"
  nat_gateway_id         = aws_nat_gateway.main.id
}

resource "aws_instance" "app" {
  ami           = data.aws_ami.amazon_linux_2023.id
  instance_type = "t3.small"
  subnet_id     = aws_subnet.private[0].id

  # User data precisa de internet (yum install)
  user_data = file("scripts/setup.sh")

  # Dependência EXPLÍCITA — garante que NAT route existe antes
  # Sem isso, a instância poderia iniciar sem internet!
  depends_on = [aws_route.private_nat]

  tags = { Name = "app-server" }
}

# ═══════════════════════════════════════════════════════════════
# Outro caso: IAM policy que precisa existir antes do recurso usá-la
# ═══════════════════════════════════════════════════════════════
resource "aws_iam_role_policy_attachment" "s3_access" {
  role       = aws_iam_role.app.name
  policy_arn = aws_iam_policy.s3_read.arn
}

resource "aws_instance" "worker" {
  ami                  = data.aws_ami.amazon_linux_2023.id
  instance_type        = "t3.micro"
  iam_instance_profile = aws_iam_instance_profile.app.name

  # Garante que a policy está attached antes de criar instância
  # (eventual consistency da API IAM)
  depends_on = [aws_iam_role_policy_attachment.s3_access]
}
💡 Regra de Ouro para depends_on:
  • Se existe referência direta (ex: vpc_id = aws_vpc.main.id): NÃO use depends_on — já é automático
  • Se NÃO existe referência mas há dependência lógica: USE depends_on
  • Uso excessivo de depends_on: É um "code smell" — geralmente indica que o código pode ser reestruturado para usar referências naturais

10.4 Referências Cruzadas entre Módulos

Quando você divide infraestrutura em módulos, os outputs de um módulo alimentam as variáveis de outro:

Módulo Network → Módulo ComputeComposição
# ═══════════════════════════════════════════════════════════════
# main.tf — Chamando módulos e conectando outputs → variables
# ═══════════════════════════════════════════════════════════════

# Módulo de rede (cria VPC, subnets, SGs)
module "network" {
  source = "./modules/network"

  vpc_cidr    = "10.0.0.0/16"
  environment = var.environment
}

# Módulo de compute (cria EC2, usando outputs do network)
module "compute" {
  source = "./modules/compute"

  # Outputs do módulo network → variáveis do módulo compute
  vpc_id             = module.network.vpc_id              # ← Ref cruzada
  subnet_ids         = module.network.private_subnet_ids  # ← Ref cruzada
  security_group_ids = [module.network.app_sg_id]         # ← Ref cruzada

  instance_type = "t3.small"
  environment   = var.environment
}

# Output final composto
output "application_url" {
  value = "http://${module.compute.public_ip}"
}

# ═══════════════════════════════════════════════════════════════
# O Terraform entende automaticamente:
# module.network DEVE ser criado ANTES de module.compute
# porque compute referencia outputs do network
# ═══════════════════════════════════════════════════════════════

Exercício 4 — Lifecycle Rules e Proteção

Objetivo: Modificar a infraestrutura do exercício anterior para incluir lifecycle rules que protegem contra downtime e destruição acidental.

Requisitos:

  • Security Group com create_before_destroy (use name_prefix)
  • EC2 Instance com ignore_changes em [user_data, ami]
  • Criar um "fake" RDS com prevent_destroy = true
  • Usar replace_triggered_by para recriar a instância quando um terraform_data mudar
  • Adicionar output do comando de SSH e URL do servidor

# ═══════════════════════════════════════════════════════════════
# Demonstração completa de Lifecycle Rules
# ═══════════════════════════════════════════════════════════════

# Trigger para forçar recriação (simula mudança de config)
resource "terraform_data" "app_config_version" {
  input = var.app_config_version  # Mude para forçar redeploy
}

# Security Group com create_before_destroy
resource "aws_security_group" "demo" {
  name_prefix = "${var.project}-demo-"  # Prefixo permite coexistência
  description = "Demo SG with lifecycle rules"
  vpc_id      = aws_vpc.main.id

  ingress {
    from_port   = 80
    to_port     = 80
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }

  egress {
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }

  lifecycle {
    # Cria novo SG antes de deletar o antigo → zero downtime
    create_before_destroy = true
  }

  tags = merge(local.common_tags, { Name = "${var.project}-demo-sg" })
}

# EC2 com ignore_changes e replace_triggered_by
resource "aws_instance" "demo" {
  ami           = local.ami_id
  instance_type = var.instance_type
  subnet_id     = aws_subnet.public[0].id
  key_name      = aws_key_pair.web.key_name

  vpc_security_group_ids = [aws_security_group.demo.id]
  user_data              = file("${path.module}/scripts/user_data.sh")

  root_block_device {
    volume_type = "gp3"
    volume_size = 20
    encrypted   = true
  }

  lifecycle {
    # Não recriar quando user_data ou AMI mudar acidentalmente
    ignore_changes = [user_data, ami]

    # MAS recriar quando explicitamente mudarmos a versão da config
    replace_triggered_by = [terraform_data.app_config_version]

    # Criar nova antes de destruir antiga
    create_before_destroy = true
  }

  tags = merge(local.common_tags, { Name = "${var.project}-demo-instance" })
}

# Simulação de recurso protegido (RDS)
resource "aws_db_instance" "protected" {
  identifier     = "${var.project}-protected-db"
  engine         = "postgres"
  engine_version = "15.4"
  instance_class = "db.t3.micro"

  allocated_storage = 20
  storage_encrypted = true

  db_name  = "app_db"
  username = "admin"
  password = var.db_password

  skip_final_snapshot = true  # Para facilitar testes (em prod = false)
  deletion_protection = true  # Proteção na API AWS

  lifecycle {
    # Terraform NÃO pode destruir este recurso
    prevent_destroy = true
  }

  tags = merge(local.common_tags, { Name = "${var.project}-protected-db" })
}
