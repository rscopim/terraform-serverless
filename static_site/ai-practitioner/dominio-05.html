2. Serviços de Segurança AWS para IA

ServiçoFunçãoAplicação em IA
IAM Controle de acesso (quem pode fazer o quê) Restringir acesso a modelos, endpoints, dados de treino
KMS Gerenciamento de chaves de criptografia Criptografar dados de treino, modelos, logs de inferência
VPC Isolamento de rede SageMaker em VPC privada, endpoints isolados
PrivateLink Acesso privado a serviços sem internet Chamar Bedrock sem tráfego pela internet pública
Macie Descoberta e proteção de dados sensíveis Encontrar PII em datasets de treinamento no S3
CloudTrail Auditoria de API calls (QUEM fez O QUÊ) Auditar quem invocou modelos, quando, de onde
CloudWatch Monitoramento de métricas e logs (COMO está performando) Latência de inferência, erros, throughput, alarmes
Model Monitor Monitoramento de qualidade do modelo em produção Detectar data drift, model drift, viés emergente
Invocation Logging Log de inputs/outputs do Bedrock Registrar prompts e respostas para auditoria e debug
⭐ Diferenciação Crítica:

CloudTrail = QUEM fez O QUÊ e QUANDO (auditoria de ações/API calls)
CloudWatch = COMO está performando (métricas, logs operacionais, alarmes)

Pergunta sobre "auditar acesso" ou "compliance" → CloudTrail
Pergunta sobre "monitorar latência" ou "alarme de erros" → CloudWatch

3. Criptografia

At Rest vs In TransitEncryption
Criptografia para Workloads de IA:
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

AT REST (dados armazenados):
• S3: SSE-S3, SSE-KMS, SSE-C
• EBS volumes: AES-256
• SageMaker: notebooks, training jobs, models
• Bedrock: dados de fine-tuning, knowledge bases
• Chaves: AWS managed key ou Customer managed key (CMK)

IN TRANSIT (dados em movimento):
• TLS 1.2+ para todas as API calls
• HTTPS obrigatório para endpoints
• VPC PrivateLink: tráfego nunca sai da rede AWS
• Certificate Manager (ACM) para certificados

Bedrock específico:
• Dados de inferência criptografados em trânsito (TLS)
• Dados de customização criptografados at rest (KMS)
• Opção de CMK para controle total das chaves
• Dados NÃO são usados para treinar modelos da AWS

4. Privacidade e Proteção de Dados

Proteção de DadosPrivacy
Privacidade em Workloads de IA:
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

TIPOS DE DADOS SENSÍVEIS:
• PII (Personally Identifiable Information)
  - Nome, CPF, RG, endereço, telefone, email
• PHI (Protected Health Information)
  - Diagnósticos, tratamentos, histórico médico
• Dados financeiros
  - Cartão de crédito, conta bancária, renda

PRINCÍPIOS DE PROTEÇÃO:
1. Data Classification
   → Classificar dados por sensibilidade
   → Macie para descoberta automática

2. Data Minimization
   → Coletar apenas o necessário
   → Reter apenas pelo tempo necessário

3. Least Privilege
   → Acesso mínimo necessário (IAM)
   → Segregação de duties

4. Data Residency
   → Dados ficam na região escolhida
   → Compliance com leis locais (LGPD, GDPR)

5. PII Handling
   → Bedrock Guardrails: PII redaction
   → Macie: descoberta em S3
   → Comprehend: detecção de PII em texto

6. Governança Específica para IA

AI GovernanceLineage & Policies
Governança Específica para IA:
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

DATA LINEAGE (Linhagem de Dados):
• Rastrear origem e transformações dos dados
• De onde vieram os dados de treinamento?
• Quais transformações foram aplicadas?
• Quem teve acesso e quando?
• SageMaker ML Lineage Tracking

MODEL LINEAGE (Linhagem de Modelos):
• Versionar modelos e seus artefatos
• Qual dataset treinou qual versão?
• Quais hiperparâmetros foram usados?
• Resultados de avaliação por versão
• SageMaker Model Registry

ACCEPTABLE USE POLICIES:
• Definir usos permitidos e proibidos
• Quem pode acessar quais modelos?
• Quais dados podem ser enviados ao modelo?
• Limites de uso (rate limiting, budget)
• Processo de aprovação para novos use cases

AUDIT & MONITORING:
• CloudTrail: quem invocou o modelo
• Invocation Logging: o que foi enviado/recebido
• CloudWatch: métricas operacionais
• Alertas para uso anômalo

8. Ameaças de Segurança Específicas de IA

AmeaçaDescriçãoMitigação
Prompt Injection Inserir instruções maliciosas no input para manipular o modelo Guardrails, input validation, separação de system/user prompt
Data Leakage Modelo expõe dados sensíveis do treinamento ou contexto PII redaction, data minimization, output filtering
Model Poisoning Contaminar dados de treinamento para alterar comportamento Data validation, provenance tracking, anomaly detection
Adversarial Attacks Inputs crafted para enganar o modelo (imperceptíveis a humanos) Adversarial training, input preprocessing, ensemble models
Toxicity Modelo gera conteúdo ofensivo, prejudicial ou inapropriado Guardrails content filters, RLHF, output moderation

9. Técnicas de Grounding

Grounding é o processo de ancorar respostas do modelo em fatos verificáveis, reduzindo alucinações.

GroundingAnti-Hallucination
Técnicas de Grounding:
━━━━━━━━━━━━━━━━━━━━━━

1. RAG GROUNDING
   • Buscar informações em fontes confiáveis
   • Incluir contexto verificável no prompt
   • Bedrock Knowledge Bases para implementação
   • Instrução: "Responda APENAS com base no contexto"

2. OUTPUT VALIDATION
   • Verificar claims contra fontes conhecidas
   • Cross-reference com databases
   • Bedrock Guardrails Grounding Check
   • Rejeitar respostas sem suporte factual

3. CONFIDENCE SCORING
   • Modelo indica nível de certeza
   • Threshold para aceitar/rejeitar respostas
   • Encaminhar baixa confiança para humanos
   • Calibração de confidence scores

4. SOURCE CITATION
   • Modelo cita fontes específicas
   • Verificável pelo usuário
   • Aumenta transparência e confiança
   • RAG com metadata de fonte

Bedrock Guardrails — Grounding Check:
• Compara resposta com contexto fornecido
• Score de 0-1 (quanto está "grounded")
• Threshold configurável
• Bloqueia respostas não fundamentadas
🎯 Dica de Exame: Se a pergunta menciona "reduzir alucinações" → RAG + Grounding Check. Se menciona "verificar se resposta é baseada em fatos" → Bedrock Guardrails Grounding Check. Grounding = ancorar em fatos verificáveis.
